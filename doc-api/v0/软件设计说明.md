## 1. 引言

### 1.1 编写目的
本文档从软件设计角度，系统阐述课程预约系统（lesson-appointment-api）的架构设计、模块划分、数据设计、接口设计、安全设计及关键技术实现，为开发、测试、维护提供设计依据。

## 3. 安全设计

### 3.1 认证机制设计

采用 **双Token机制**（Access Token + Refresh Token），实现无状态认证 + 免登刷新：

```
前端                      后端                        数据库
  │                        │                           │
  │── POST /auth/login ──→ │                           │
  │    {account,password}  │                           │
  │                        │── 校验密码(BCrypt) ──────→│
  │                        │── 生成AccessToken(HS512)  │
  │                        │── 生成RefreshToken(HS256) │
  │                        │── 持久化RefreshToken ───→│ user_refresh_token表
  │← {token,refreshToken} ─│                           │
  │                        │                           │
  │── GET /api (Bearer t)─→│                           │
  │                        │── JwtAuthFilter解析Token  │
  │                        │── 写入SecurityContext      │
  │                        │── 授权通过，执行业务       │
  │← 200 {data} ──────────│                           │
  │                        │                           │
  │── Token过期(401) ────→│                           │
  │── POST /refreshToken ─→│                           │
  │    {refreshToken}      │── 校验DB中Token未过期 ──→│
  │                        │── 删除旧Token ──────────→│
  │                        │── 生成新双Token          │
  │                        │── 持久化新RefreshToken ─→│
  │← {newToken,newRefresh}─│                           │
```

**Token设计参数**（[JwtUtil.java](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/utils/JwtUtil.java)）：

| 参数 | 值 | 说明 |
|------|-----|------|
| Access Token算法 | HS512 | 高安全性签名算法 |
| Access Token有效期 | 36000000ms（约10小时） | 配置项 `jwt.expiration` |
| Refresh Token算法 | HS256 | 标准签名算法 |
| Refresh Token有效期 | 7天 | 常量 `REFRESH_EXPIRE` |
| 密钥要求 | ≥64字节 | HS512最低密钥长度 |
| 密钥来源 | `jwt.secret`配置项 | Base64编码字符串 |

### 3.2 JWT认证过滤器设计

[JwtAuthenticationFilter](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/config/JwtAuthenticationFilter.java) 继承 `OncePerRequestFilter`，核心流程：

1. **shouldNotFilter**：白名单路径直接放行（登录/注册/静态资源/OPTIONS预检）
2. **提取Token**：从 `Authorization: Bearer <token>` 头提取
3. **校验签名+过期**：调用 `jwtUtil.verifyAccessToken(token)`
4. **解析身份**：提取 `userId` 和 `role`
5. **写入安全上下文**：构造 `UsernamePasswordAuthenticationToken`（权限为 `ROLE_<role>`）
6. **异常处理**：Token非法/过期→清除上下文→交给 `AuthenticationEntryPoint` 返回401

### 3.3 授权规则设计

[SecurityConfig](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/config/SecurityConfig.java) 配置 Spring Security 授权策略：

| 路径模式 | 权限 | 说明 |
|----------|------|------|
| `OPTIONS /**` | permitAll | CORS预检放行 |
| `/auth/login`,`/auth/refreshToken`,`/auth/logout` | permitAll | 认证接口 |
| `/user/student/register`,`/user/teacher/register` | permitAll | 注册接口 |
| `/user/account/exist` | permitAll | 账号查重 |
| `/teacher/published/latest-public`,`/teacher/published/public-get` | permitAll | 教师公开信息 |
| 静态页面 `/index.html`,`/admin.html`等 | permitAll | 前端页面 |
| `/js/**`,`/css/**`,`/images/**` | permitAll | 静态资源 |
| 其他所有请求 | authenticated | 需登录认证 |

**异常响应设计**：
- 未认证 → HTTP 401 + `{code:401, message:"未登录或登录已过期"}`
- 权限不足 → HTTP 403 + `{code:403, message:"无权限访问该资源"}`

### 3.4 权限校验工具设计

[PermissionCheck](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/utils/PermissionCheck.java) 提供细粒度RBAC校验：

| 方法 | 校验逻辑 | 使用场景 |
|------|----------|----------|
| `checkAdmin(token)` | role必须为admin | 模板管理、用户审核、踢出用户 |
| `checkTeacher(token)` | role=teacher 且 status=active | 创建课程、设置排期 |
| `checkStudent(token)` | role=student 且 status=active | 预约课程、评价 |
| `checkTeacherOrAdmin(token)` | admin直接通过；teacher需active | 课程查询、排期管理 |
| `checkTeacherOwner(token, teacherId)` | checkTeacher + 归属校验 | 操作自己的课程/排期 |
| `checkStudentOwner(token, studentId)` | checkStudent + 归属校验 | 操作自己的订单 |

### 3.5 密码安全设计

- **加密算法**：BCrypt（`BCryptPasswordEncoder`，启动类中 `@Bean` 注入）
- **注册时**：`passwordEncoder.encode(password)` 加密后存储
- **登录时**：`passwordEncoder.matches(rawPassword, encodedPassword)` 比对
- **重置时**：管理员重置为固定密码 `"12345678"`（BCrypt加密），用户登录后自行修改

## 4. 数据设计

### 4.1 数据库总体设计

- **数据库名**：`lesson_appointment`
- **字符集**：`utf8mb4`（支持多语言、emoji）
- **排序规则**：`utf8mb4_unicode_ci`
- **存储引擎**：InnoDB（支持事务、外键、行级锁）
- **主键策略**：UUID（varchar(36)），分布式友好；appointment表使用自增int

### 4.2 实体关系设计

  │ 1:N
  ├──→ course (教师课程)
  │         ↑ N:1
  │    course_template (课程模板)
  │         │ 1:N
  │         └──→ course (课程基于模板创建)
  │              │ 1:N

#### 登录流程设计

```
authController.toLogin(LoginDTO)
  │
  ├──→ UserService.login(account, password)
  │       │
  │       ├──→ UserMapper.selectByAccount(account)     // 查用户
  │       ├──→ passwordEncoder.matches(password, hash) // BCrypt比对
  │       ├──→ 校验status: frozen→拒绝 / inactive→拒绝 / pending→提示
  │       ├──→ JwtUtil.generateToken(userId, role)     // 生成AccessToken
  │       ├──→ JwtUtil.generateRefreshToken(userId)    // 生成RefreshToken
  │       └──→ RefreshTokenService.saveNewToken(...)   // 持久化（删旧+存新）
  │
  ├──→ 构造 UsernamePasswordAuthenticationToken
  ├──→ SecurityContextHolder.getContext().setAuthentication(auth)
  └──→ 返回 Result<HashMap> (userId, account, name, role, token, refreshToken)
```

#### 刷新Token流程设计

```
authController.refreshToken(RefreshDTO)
  │
  ├──→ RefreshTokenService.checkValidToken(oldRefreshToken)
  │       ├──→ RefreshTokenMapper.selectByToken()    // 查DB
  │       └──→ 过期→删除脏数据→返回null
  │
  ├──→ 生成新双Token
  ├──→ RefreshTokenService.removeOldToken()           // 旧Token失效
  ├──→ RefreshTokenService.saveNewToken()              // 存新Token
  ├──→ 重写SecurityContext
  └──→ 返回 TokenDTO {token, refreshToken}
```

### 5.3 排期管理模块设计

**Controller**: [ScheduleController](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/controller/ScheduleController.java)
**Service**: [CourseScheduleService](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/service/CourseScheduleService.java)
**工具类**: [ScheduleGenerator](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/common/ScheduleGenerator.java)

#### 排期生成算法设计

`ScheduleGenerator.generateUserZoneSchedule(dto)` 核心逻辑：

1. **输入**：起始日期、结束日期、每日时间、重复类型(none/day/week/month)、重复间隔、重复日列表、源时区、目标时区
2. **遍历日期范围**：从start到end逐日遍历
3. **匹配规则**：
   - `none`：仅首日，`nextDate`跳100年（等效于只执行一次）
   - `day`：每隔`interval`天
   - `week`：匹配`repeatDays`中的星期几（1=周一..7=周日），按`interval`周间隔
   - `month`：匹配`repeatDays`中的日期号（1-31），按`interval`月间隔
4. **时区转换**：
   - 同时区：直接格式化为`yyyy-MM-dd` + `HH:mm:00`
   - 跨时区：`LocalDateTime.atZone(fromZone).withZoneSameInstant(toZone)` 转换
5. **输出**：`List<ScheduleVO>`，每项含`date`和`time`

#### 排期冲突检测设计

`checkScheduleOwnerConflict(dto)` 算法：

```
1. 获取同课程的所有排期列表（排除自身）
2. 对待检测排期调用 ScheduleGenerator 生成实例列表 newInstances
3. 对每个已存在排期：
   a. 生成其实例列表 existInstances
   b. 逐个比较 newInstances × existInstances：
      - 日期不同→跳过
      - 日期相同→比较时间是否重叠（以1小时为互斥区间）
      - 重叠→加入冲突列表
4. 返回冲突排期的 {id, name} 列表
```

#### 分配学生原子操作设计

`asgn_student(scheduleId, studentId, teacherId)` 事务流程：

```
@Transactional
1. 创建Booking记录 (status=booked)
2. 查询排期详情 (CourseSchedule)
3. 构造ScheduleGenerateDTO，调用ScheduleGenerator展开实例列表
4. 为每个实例创建Appointment记录 (classIndex递增, status=active)
5. 批量插入Appointment列表
→ 事务保证：任一步骤失败则全部回滚
```

## 7. 关键设计决策

### 7.1 为什么选择双Token而非单Token

| 方案 | 优点 | 缺点 |
|------|------|------|
| 单Token | 简单 | 过期需重新登录；长有效期有安全风险 |
| **双Token（选用）** | Access短时安全+Refresh长时免登；RefreshToken可主动失效（DB删除） | 实现稍复杂 |

RefreshToken持久化到数据库（`user_refresh_token`表），支持：
- **单设备登录**：登录时删除旧Token
- **强制踢出**：管理员按userId删除全部Token
- **主动登出**：删除当前Token

### 7.2 为什么排期使用字符串时间而非LocalDateTime

排期实体 [CourseSchedule](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/entity/CourseSchedule.java) 中 `startTime`/`endTime` 使用 `String` 类型（格式 `yyyy-MM-dd HH:mm:ss`），原因：

1. 数据库 `DATETIME` 类型与Java字符串直接映射，避免时区自动转换问题
2. 时区转换由 [ScheduleGenerator](file:///h:/2026/lesson-appointment/api/src/main/java/com/reservation/common/ScheduleGenerator.java) 显式处理，在Service层完成DTO↔Entity转换
3. 前端直接使用字符串，无需前端时区处理

### 7.3 为什么Booking和Appointment分离

| 维度 | 设计理由 |
|------|----------|
| 数据量 | 一个排期可能展开数十节课（如每周重复3个月），Appointment表数据量远大于Booking |
| 状态管理 | 每节课有独立状态（active→noted→completed/cancelled），需逐节管理 |
| 查询性能 | 课表浏览只需查Appointment表，无需JOIN Booking |
| 改期支持 | `last_datetime`保留原始时间，`appointment_datetime`为当前有效时间 |

### 7.4 为什么教师发布信息使用静态HTML

`teacher_published_profile.static_html` 存储完整HTML（含Base64内嵌图片），设计意图：

1. **可分享性**：独立HTML可下载、可URL直接访问，不依赖前端框架
2. **版本快照**：发布时的完整状态固化，后续修改不影响已分享版本
3. **公开访问**：`/latest-public`和`/public-get`在SecurityConfig白名单中，无需登录即可查看
4. **配置灵活**：`field_config`(字段勾选+排序) + `style_config`(样式配置) 支持个性化展示

### 7.5 冲突检测算法的设计权衡

当前实现为**保守算法**（与同一课程的其他排期比较），而非精确算法（与已预约时间表比较）：

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 保守算法 | 实现简单，不依赖Booking数据 | 可能误报（排期间有席位空余） | **选用** |
| 精确算法 | 精确到实际预约 | 需JOIN多表，性能开销大 | TBD |

冲突判定以1小时为互斥区间（`existEnd = existStart.plusHours(1)`），边界相等不算冲突。

## 8. 事务与一致性设计

### 8.1 事务策略

| 操作类型 | 传播行为 | 回滚策略 | 示例 |
|----------|----------|----------|------|
| 写操作 | `REQUIRED` | `rollbackFor=Exception.class` | 创建课程、创建排期、创建预约 |
| 读操作 | `REQUIRED`(readOnly可选) | 不回滚 | 查询列表、查询单条 |
| 原子操作 | `REQUIRED` | `rollbackFor=Exception.class` | asgn_student（Booking+Appointments） |

### 8.2 数据一致性保障

| 机制 | 实现位置 | 说明 |
|------|----------|------|
| 外键约束 | database.sql | `ON DELETE CASCADE ON UPDATE CASCADE` 级联删除/更新 |
| 唯一约束 | database.sql | uk_phone, uk_email, uk_lang_level, uk_teacher_id |
| CHECK约束 | database.sql | `end_time > start_time`, `rating BETWEEN 1 AND 5` |
| 事务回滚 | Service层 | `@Transactional(rollbackFor=Exception.class)` |
| 先查后插 | Service层 | 模板/课程创建前先检查唯一性，避免DB层异常 |
| 密码脱敏 | UserService | 分页查询结果中 `user.setPassword(null)` |
