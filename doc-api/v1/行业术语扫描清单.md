## 二、替换风险点（锚点词设计必须处理）

### 1. 人名误伤（高风险）
测试数据里存在 **"王老师"、"刘老师"** 等人名（如 `授课教师：王老师`、admin.html 示例）。若把"老师"整体替换，人名会变成"王律师"。**对策**：人名加入保护词白名单，或仅替换独立的"老师"词（前后非姓氏上下文难判定，建议数据层面人名与称谓分开存储）。

### 2. 复合词连锁替换
- "课后反馈" → 含"课程"无关但含"课"字，注意按整词"课程"替换不会误伤（"课后"≠"课程"），安全
- "开课" 若单独替换需谨慎："即将开课的课程"含两个术语
- "上课时间" 由"上课"+"时间"组成，替换"上课"→"咨询"后自然变成"咨询时间"，符合预期 ✓
- "课时" 与"上课时间"：`th>上课时` 的匹配说明两者前缀重叠，**替换顺序要先长词后短词**（先"上课时间"再"上课"再"课时"），否则"上课时间"会被"课时"规则截断误伤

### 3. 后端文案（196+117+43 处）
后端 Java 里"课程/教师/学生"大量出现在注释、校验消息、日志里。注释无需处理；**校验消息和 API 返回文案需要**——建议后端只返回错误码，前端映射文案时过一遍术语替换（对应方案文档 3.5 节第 4 条）。

### 4. 数据库存量数据
课程名（如"英语口语"）存在数据库里，属于**内容而非称谓**，术语替换不应触及；但下拉选项（法语/英语）属配置数据，多行业时建议做成行业维度的字典表。

## 三、对现有 terms.js 的扩展建议

当前 `js/public/terms.js` 只登记了 3 个 key（course/teacher/student）。按本次扫描结果，建议扩展为：

```js
const TERM_KEYS = [
  { key: "course",     anchor: "课程" },     // A级 367处
  { key: "teacher",    anchor: "教师" },     // A级 138处
  { key: "teacherAlt", anchor: "老师" },     // A级别名 25处（注意人名保护）
  { key: "student",    anchor: "学生" },     // A级 101处
  { key: "lessonTime", anchor: "上课时间" }, // B级，长词优先
  { key: "lessonUnit", anchor: "课时" },     // B级 49处
  { key: "classForm",  anchor: "班级" },     // B级（一对一/小班/大班随 option 文案替换）
];

// 保护词（替换时跳过包含这些词的文本节点）
const PROTECTED_WORDS = ["王老师", "刘老师"];
```

C 级术语（语言类型/法语/难度等级）**不建议进术语表**——它们是行业专属配置，换行业时整个字段可能消失或换含义，应通过"行业配置"控制字段显隐，而不是文字替换。

## 四、结论

- 全站需纳入术语替换引擎的**有效锚点词 7 个**（A 级 4 个 + B 级 3 个），覆盖约 850+ 处前端、480+ 处后端出现
- 两个同义双轨词（教师/老师）和一个前缀重叠（上课时间/上课/课时）是替换引擎设计的两个坑，已在上面给出对策
- 人名保护、C 级字段显隐、后端文案错误码化是三个配套改造点
