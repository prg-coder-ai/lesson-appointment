| 缺陷 | 是否阻断上线 | 理由 |

## 四、流程问题提炼

### 1. 研发侧
- **NOT NULL 列缺乏默认值 / 未与 API 契约对齐**：Defect-1、Defect-2 同源——实体字段 `NOT NULL` 但 DTO 允许为空且未设兜底，插入即 500。属典型「库表约束 vs 入参契约」脱节。
- **多租户唯一索引遗漏 `tenant_id`**（Defect-3）：SaaS 迁移中最典型的隔离坑——唯一约束未纳入租户维度，导致租户间数据互斥。说明迁移时**全表唯一索引需逐一审视是否应包含 tenant_id**。

### 2. 测试侧
- **测试数据建模未考虑隔离**：首轮用「平台共享模板」假设跨租户可见，实际被 TenantLineInnerInterceptor 拦截。多租户测试须「每租户独立建数据」。
- **清理语句引用不存在列**：`template_name` 列不存在导致静默失败、脏数据残留。清理脚本须用真实列并校验执行结果。
- **异步审计未轮询**：审计为异步线程写入，同步断言需轮询等待（已在 harness 修正）。

### 3. 需求/规格侧
- **TC-E-02 规格与实现分歧**：规格期望「租户管理员访问租户列表 → 403」，实现返回「仅本租户数据」。需产品/测试负责人确认规格口径。

## 五、下一版本改进建议

### 研发检查清单（建议沉淀为规范）
1. 所有 `NOT NULL` 列必须有 DB 默认值 **或** API 层 `@NotBlank/@NotNull` 强校验 + 服务端兜底——二者至少其一。
2. **所有业务唯一索引必须包含 `tenant_id`**（除平台级引用表 `sys_*`、UUID 列、全局业务唯一键如 `tenant_code`/`email` 经确认外）。
3. 权限接口统一采用 `checkXxxSelfOrAdmin` 模式，避免「仅 admin 可操作」的不完整鉴权。
4. 引入 **DB 迁移工具（Flyway / Liquibase）** 管理 schema 变更，Defect-3 的 `ALTER INDEX` 应纳入版本化迁移而非手工执行。

### 测试规范（建议沉淀）
1. 多租户用例强制「每租户独立建数据」，禁止依赖跨租户共享。
2. 清理脚本使用真实列名，并对 `DELETE` 执行结果做断言（避免静默失败）。
3. 涉及异步写入（审计/消息）的断言必须轮询等待。
4. 响应结构断言需兼容后端实际字段命名（如 `Id` 而非 `scheduleId`），建议先抓真实响应再写断言。

### 产品/规格
- 明确 TC-E-02 口径；确认 `user.email/phone` 是否应改为租户级唯一；确认教师发布其余接口（`list/get/update/delete`）的鉴权边界。
