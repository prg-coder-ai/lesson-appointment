# 预约系统多行业称谓动态切换方案

> 需求：不同行业对同一概念的称谓不同（教育：课程/教师/学生；法律咨询：咨询话题/律师/咨询者）。用户选择行业后，页面所有称谓即时切换，且动态生成的 HTML 也要正确显示。
>
> 文档版本：v2.0 — 反映已落地的实现状态，含详细原理介绍。

---

## 一、问题本质：领域术语国际化（Domain i18n）

### 1.1 与"中英文切换"的技术同构性

这个需求和"中英文切换"在技术本质上是同一个问题，只是维度不是语言，而是**行业术语表**。i18n 的成熟做法可以直接借鉴：

| i18n 概念 | 本项目对应 |
|---|---|
| locale（语言区域） | industry（行业） |
| translation bundle（翻译包） | TERM_DICT（术语字典） |
| t("key")（查表取译文） | applyTerms()（DOM 遍历替换） |
| 语言切换时刷新页面 | switchIndustry()（原地替换，不刷新） |
| 锚点 key（如 "greeting"） | 锚点词（如 "课程"） |

**核心差异**：传统 i18n 的锚点是抽象 key（如 `"course.title"`），DOM 里写 `t("course.title")`；本项目最初没有 key 体系，DOM 里直接写了中文"课程"。因此需要一种"以默认词为锚点"的方案——DOM 存默认词，切换时遍历替换。

### 1.2 三个核心子问题

| 子问题 | 说明 | 本项目解法 |
|---|---|---|
| ① 术语从哪来 | 每个行业一张术语表 | `terms.js` 中的 `TERM_DICT` |
| ② 术语往哪放 | 页面称谓不能写死，必须能被找到并替换 | `data-term` 标记 + TreeWalker 文本遍历 |
| ③ 何时替换 | 选行业时立即替换；动态 HTML 每次注入后也要替换 | `switchIndustry()` + `DOMContentLoaded` + `MutationObserver` + 渲染函数内显式调用 |

### 1.3 本项目的特殊约束

- 约 30 个 HTML/JS 文件、850+ 处硬编码称谓文案
- 大量页面由 JS 模板字符串动态生成后 `innerHTML` 注入（admin-schedule.js、StudentBookingBrowserCards.js 等）
- 菜单导航通过 `switch(文字)` 匹配，不是 `data-*` 属性
- 纯原生 JS，无框架依赖，不宜引入 i18next 等重型库

## 二、方案选型对比

| 方案 | 原理 | 优点 | 缺点 | 评价 |
|---|---|---|---|---|
| **A. 术语字典 + data-term 属性** | HTML 写 `<span data-term="course">课程</span>`，JS 查表替换 textContent | 精确、可控、性能好 | 存量代码要逐处加属性 | ✅ 长期最优 |
| **B. 术语字典 + 全文遍历替换** | 遍历 DOM 文本节点，整词替换锚点词 | 存量代码零改造 | 有误伤风险（复合词、人名） | ✅ 短期最实用 |
| **C. 服务端渲染时替换** | Thymeleaf 后端模板统一处理 | 单点收口 | 前端动态渲染覆盖不全 | ❌ 不适合 |
| **D. CSS content 替换** | `::after { content: "律师" }` | 零 JS | 无法替换 placeholder/option/alert | ❌ 不可行 |
| **E. 引入 i18next 框架** | 标准 i18n 库 | 功能全 | 重构成本最高，与现有代码风格冲突 | ❌ 过重 |

**采用方案：B 为主 + A 渐进迁移。**

- B 层（TreeWalker 文本遍历）：覆盖所有未标记的硬编码文案，零改造成本起步
- A 层（data-term 标记）：已批量标记 143 处 A/B 级术语，精确控制，无误伤
- 两层互补：data-term 元素直接置词（精确），文本节点遍历兜底（覆盖广）

## 四、核心原理详解

### 4.1 锚点词归一化（防多次切换出错）

**问题**：用户从教育切到法律（课程→咨询话题），再从法律切到心理咨询（咨询话题→？）。如果直接拿"咨询话题"去查心理咨询的表，查不到——因为心理咨询的锚点词是"课程"。

**原理**：DOM 里**永远以默认行业（education）的词为锚点**。切换行业时分两步：

```
步骤 1：restoreAnchorTerms()  当前行业词 → 锚点词（education 默认词）
步骤 2：applyTerms()           锚点词 → 新行业词
```

```
教育(课程) ──switch("legal")──→ 还原(课程→课程,已是锚点) → 替换(课程→咨询话题) ──→ 法律(咨询话题)
法律(咨询话题) ──switch("counseling")──→ 还原(咨询话题→课程) → 替换(课程→咨询项目) ──→ 心理(咨询项目)
心理(咨询项目) ──switch("education")──→ 还原(咨询项目→课程) → 替换(课程→课程,空操作) ──→ 教育(课程)
```

**关键代码**（`termsFunction.js`）：

```js
function switchIndustry(industry) {
  if (!TERM_DICT[industry]) { console.warn("未知行业", industry); return; }
  restoreAnchorTerms();              // ① 当前行业词 → 锚点词
  localStorage.setItem("industry", industry);  // ② 记录新行业
  applyTerms();                      // ③ 锚点词 → 新行业词
}
```

### 4.2 长词优先排序（防前缀截断误伤）

**问题**：TERM_KEYS 里有"上课时间""上课""课时"三个词，如果按短词先替换，"上课时间"里的"上课"会先被替换，导致"上课时间"→"咨询时间"变成"咨询咨询时间"（二次替换错误）。

**原理**：TERM_KEYS 数组**按锚点词长度降序排列**，替换时长词先匹配。同一段文本中"上课时间"先被整体替换，轮到"上课"时该子串已不存在。

```js
// terms.js — 长词在前，短词在后
const TERM_KEYS = [
  { key: "lessonTime",   anchor: "上课时间" },  // 4字，先处理
  { key: "lesson",       anchor: "上课" },      // 2字，后处理
  { key: "course",       anchor: "课程" },
  { key: "teacher",      anchor: "教师" },
  { key: "teacherAlt",   anchor: "老师" },
  { key: "student",      anchor: "学生" },
  { key: "lessonUnit",   anchor: "课时" },      // 2字
  // ... classForm / classLevel / classType 系列
];
```

**反向替换同理**：`restoreAnchorTerms()` 和 `normalizeTermText()` 中构造的反向替换对也按 `from.length` 降序排序——legal 的"咨询时间""咨询时长"先于"咨询"处理，否则"咨询时长"会被拆成"上课时长"。

### 4.3 TreeWalker 文本节点遍历（只改文字，不动结构）

**原理**：DOM 的文本内容存储在 `Text` 节点的 `nodeValue` 中，不是元素的 `textContent`。用 `TreeWalker(SHOW_TEXT)` 遍历文本节点，修改 `nodeValue` 只改文字内容，**不会影响 DOM 结构、事件绑定、子元素**。

**对比 `textContent` 赋值的灾难性后果**：

```js
// ❌ 错误写法（原 switchIndustry 里的 bug）
document.querySelectorAll("*").forEach(el => {
  el.textContent = el.textContent.replace("律师", "教师");
});
// 遍历到 <body> 时，textContent 赋值会把 body 的所有子节点（整个页面）清空，
// 只剩一段纯文本——页面瞬间白屏
```

```js
// ✅ 正确写法
const walker = document.createTreeWalker(root, NodeFilter.SHOW_TEXT);
const nodes = [];
while (walker.nextNode()) { nodes.push(walker.currentNode); }
nodes.forEach(n => { n.nodeValue = n.nodeValue.replace(...); });
// 只改文本内容，DOM 树结构完全不动
```

**先收集后修改的原因**：TreeWalker 遍历过程中直接改 DOM 可能导致遍历器跳过节点（DOM 变化影响 TreeWalker 的遍历位置），所以先收集全部命中节点，遍历结束后统一修改。

**skipTags 机制**：以下标签内的文本节点不替换：

| 跳过标签 | 原因 |
|---|---|
| `SCRIPT` | JS 代码里的"课程"是变量名/字符串，替换会破坏语法 |
| `STYLE` | CSS 选择器/属性值不含业务文案 |
| `TEXTAREA` | 用户输入内容，替换会篡改用户数据 |
| `CODE` / `PRE` | 代码展示区，保持原样 |
| `OPTION` | 选项文本通过 data-term 或动态渲染处理，不走文本遍历 |

### 4.4 data-term 标记层（精确控制层）

**原理**：给关键术语所在的 HTML 元素加 `data-term="key"` 属性，`applyTerms` 和 `restoreAnchorTerms` 中单独遍历这些元素，直接 `textContent = terms[key]` 置词。

**与文本遍历层的关系**：

| 维度 | data-term 层 | TreeWalker 文本遍历层 |
|---|---|---|
| 精确度 | 精确（整词替换，无歧义） | 模糊（整词匹配，但有复合词风险） |
| 覆盖率 | 143 处（约 17%） | 覆盖剩余 700+ 处 |
| 改造成本 | 需逐处加属性 | 零改造 |
| 适用场景 | A/B 级核心称谓 | 注释/placeholder/alert 兜底 |

**当前标记分布**（143 处 / 18 个文件）：

| data-term | 数量 | data-term | 数量 |
|---|---|---|---|
| course（课程） | 59 | lessonUnit（课时） | 10 |
| teacher（教师） | 22 | lessonTime（上课时间） | 9 |
| student（学生） | 11 | classForm 系列 | 9 |
| teaching（授课） | 3 | classLevel 系列 | 10 |
| classType 系列 | 10 | lesson（上课） | 1 |

### 4.5 normalizeTermText（导航归一化）

**问题**：admin.html 和 teacher.html 的菜单导航通过 `switch(title)` 按菜单**文字**匹配：

```js
// admin.html 菜单点击
const title = this.querySelector('span').textContent;  // 取菜单文字
loadAdminPageContent(title);

function loadAdminPageContent(title) {
  switch(title) {
    case '课程排期': renderScheduleCards(); break;   // 锚点词
    case '课程列表': renderCourseList(); break;
    // ...
  }
}
```

`applyTerms` 把菜单文字"课程排期"替换成"咨询话题排期"后，`case '课程排期'` 匹配不上 → 走到 `default` → 什么都不渲染 → **页面空白**。

**原理**：`normalizeTermText(text)` 是纯字符串版的反向替换——把行业词还原成锚点词，**只处理字符串不动 DOM**。在导航入口处调用：

```js
function loadAdminPageContent(title) {
  title = normalizeTermText(title);  // "咨询话题排期" → "课程排期"
  switch(title) {
    case '课程排期': renderScheduleCards(); break;  // ✅ 匹配成功
    // ...
  }
}
```

**实现**（`termsFunction.js`）：

```js
function normalizeTermText(text) {
  if (!text || typeof text !== "string") return text;
  const industry = getCurrentIndustry();
  const terms = TERM_DICT[industry];
  if (!terms || industry === "education") return text;  // 教育行业无需归一化
  // 构造反向替换对（行业词→锚点词），长词在前
  const pairs = TERM_KEYS
    .filter(t => terms[t.key] && terms[t.key] !== t.anchor)
    .map(t => ({ from: terms[t.key], to: t.anchor }))
    .sort((a, b) => b.from.length - a.from.length);
  pairs.forEach(p => { text = text.split(p.from).join(p.to); });
  return text;
}
```

**覆盖范围**：admin.html（第 183 行）、teacher.html（第 154 行）已接入。student.html 使用 `data-menu` 属性取值，不受文字替换影响，无需归一化。

**通用规律**：凡是"拿显示文字做逻辑判断"的代码（switch/if 匹配、textContent 比较）都会被术语替换破坏。正确做法是逻辑用 `data-*` 属性、显示用文字，天然解耦。

### 4.6 MutationObserver 全局兜底

**原理**：在 `api.js`（所有页面都加载的公共脚本）中初始化一个 MutationObserver，监听 `document.body` 的 `childList + subtree` 变化。任何 `innerHTML` 注入新内容后，observer 检测到 `addedNodes`，触发 `applyTerms()`。

**防递归机制**（关键）：`applyTerms` 修改文本节点的 `nodeValue` 本身也会触发 mutation。如果不防递归，会形成"替换→触发observer→再替换→再触发"的死循环。解法：

```js
const mo = new MutationObserver(mutations => {
  let needApply = false;
  for (const m of mutations) {
    if (m.addedNodes.length) { needApply = true; break; }
  }
  if (needApply) {
    mo.disconnect();    // ① 断开监听
    applyTerms();       // ② 执行替换（替换产生的 mutation 不会被捕获）
    observe();          // ③ 重新挂上监听
  }
});
```

**三层调用保障**：

| 层级 | 触发时机 | 代码位置 | 作用 |
|---|---|---|---|
| ① DOMContentLoaded | 页面加载完成 | termsFunction.js 第 114 行 | 静态 HTML 兜底 |
| ② 显式调用 | 渲染函数末尾 | 12 个业务 JS 文件 | 精确、可控、性能好 |
| ③ MutationObserver | 任何 DOM 变化 | api.js 第 47-59 行 | 全局兜底，防遗漏 |

### 4.7 教师双轨词处理（教师 / 老师）

**问题**：项目中"教师"和"老师"两个词并存，且语义相同但使用场景不同——"教师"多用于正式标签（教师管理、教师姓名），"老师"多用于口语化场景和人名后缀（王老师、刘老师）。

**方案**：登记两个独立的 TERM_KEYS 条目，共享同一个行业翻译：

```js
const TERM_KEYS = [
  { key: "teacher",    anchor: "教师" },  // 正式称谓
  { key: "teacherAlt", anchor: "老师" },  // 口语称谓
];

// terms.js 中两者映射到同义词
education: { teacher: "教师", teacherAlt: "老师" }
legal:     { teacher: "律师", teacherAlt: "律师" }
```

**人名保护**：`PROTECTED_WORDS = ["王老师", "李老师", "刘老师"]`——含这些词的文本节点不做 teacherAlt 替换，否则"王老师"会变成"王律师"。当前实现中白名单已定义，但 `applyTerms` 正向替换尚未接入白名单检查（已知遗留项）。

### 5.2 TERM_KEYS 排序规则

```js
const TERM_KEYS = [

  { key: "lessonTime",   anchor: "上课时间" },   // 4字
  { key: "lesson",       anchor: "上课" },       // 2字（包含于"上课时间"）
  { key: "course",       anchor: "课程" },
  { key: "teacher",      anchor: "教师" },
  { key: "teacherAlt",   anchor: "老师" },
  { key: "student",      anchor: "学生" },
  { key: "lessonUnit",   anchor: "课时" },
  { key: "teaching",     anchor: "授课" },
  // ... classForm / classLevel / classType 系列
```

排序原则：**锚点词字符数降序**。同一文本节点中，长词先匹配并替换，短词后处理时长词子串已不存在，避免前缀截断。

### 5.3 保护词白名单

```js
const PROTECTED_WORDS = ["王老师", "李老师", "刘老师"];
```

用途：含这些词的文本节点不做 `teacherAlt` 替换。当前已定义但 `applyTerms` 正向替换尚未接入（已知遗留项，见第八节）。

## 六、动态 HTML 挂钩机制

### 6.1 三层调用保障

本项目大量页面用 JS 模板字符串 + `innerHTML` 注入，每次注入产生新的硬编码文案。三层保障确保不遗漏：

**第一层：DOMContentLoaded（静态 HTML）**

```js
// termsFunction.js 第 114 行
document.addEventListener("DOMContentLoaded", () => applyTerms());
```

```js

  let needApply = false;
```

## 七、JS 数据结构的行业术语处理

### 7.1 问题：JS 变量不在 DOM 遍历覆盖范围内

现有引擎只处理 DOM 文本节点和 data-term 元素，JS 内存中的数据结构（如 `const SUBJECT_OPTIONS = ['法语', '英语']`）无法被触及。

### 7.2 三种场景与对应方案

**场景 A：数组值恰好是锚点词的子串**

适用条件：数组中每个值都能在 `TERM_KEYS` 的 `anchor` 里找到。

```js
// 锚点词 → 当前行业词（纯字符串，不动 DOM）
function mapTermString(str) {
  const terms = TERM_DICT[getCurrentIndustry()];
  if (!terms || getCurrentIndustry() === "education") return str;
  let result = str;
  TERM_KEYS.forEach(t => {
    if (terms[t.key]) result = result.split(t.anchor).join(terms[t.key]);
  });
  return result;
}

// 用法
const labels = ['教师评价', '学生评价'].map(mapTermString);
// legal → ['律师评价', '咨询者评价']
```

局限：教育有 6 种语言、法律只有 4 种案件类型，数量不对齐时不适用。

**场景 B：整组选项随行业变（SUBJECT_OPTIONS 属于这种）**

不同行业的选项集是完全不同的概念，不是词对词翻译。推荐独立的行业配置对象：

```js
const INDUSTRY_SUBJECT_OPTIONS = {
  education: [
    { value: 'english',  label: '英语' },
    { value: 'japanese', label: '日语' },
    // ...
  ],
  legal: [
    { value: 'marriage', label: '婚姻家事' },
    { value: 'labor',    label: '劳动争议' },
    // ...
  ],
};

function getSubjectOptions() {
  const industry = getCurrentIndustry();
  return INDUSTRY_SUBJECT_OPTIONS[industry] || INDUSTRY_SUBJECT_OPTIONS.education;
}
```

关键设计：`value` 是行业无关的稳定标识符，`label` 是行业特定的显示文本。后端存 value、前端显示 label。

**场景 C：HTML `<option>` 有 value 属性**

推荐从配置动态生成 option，不在 HTML 里硬编码：

```js
function renderSubjectOptions() {
  const sel = document.getElementById('f-subject');
  if (!sel) return;
  const currentVal = sel.value;  // 保留已选值
  sel.innerHTML = '<option value="">请选择</option>';
  getSubjectOptions().forEach(opt => {
    const el = document.createElement('option');
    el.value = opt.value;
    el.textContent = opt.label;
    sel.appendChild(el);
  });
  sel.value = currentVal;  // 恢复选中
}
```

在 `switchIndustry` 末尾加 `renderSubjectOptions()`，行业切换后下拉框自动刷新。

### 7.3 classType1-4 应否留在 TERM_DICT

当前 `terms.js` 里 `classType1-4` 放在字典中，但教育有 4 项、法律有 4 项，含义完全不同（语言 vs 案件类型）。它们不是"同一个概念换名字"，而是"换一整组选项"。放在字典里会被 TreeWalker 拿去替换 DOM 里的"法语"文本，但"法语"出现在课程列表、教师资料、搜索条件等多处，全部替换成"婚姻"会导致语义错乱。

**建议**：将 `classType1-4` 从 `TERM_DICT` 迁移到独立的 `INDUSTRY_SUBJECT_OPTIONS` 配置对象，走动态渲染而非文本替换。（待实施）

## 九、方案总结

- **本质**：领域术语 i18n，用"行业术语表 + DOM 文本遍历替换"起步，向"data-term 标记 + 查表"演进
- **三大支柱**：术语字典（数据）、applyTerms（引擎）、锚点词归一化（保证多次切换不出错）
- **三层调用保障**：DOMContentLoaded（静态）+ 渲染函数显式调用（动态）+ MutationObserver（兜底）
- **两个关键原理**：长词优先排序（防前缀截断）、TreeWalker 文本节点遍历（只改文字不动结构）
- **导航归一化**：normalizeTermText 解决"按显示文字做逻辑匹配"被术语替换破坏的问题
- **零依赖**：纯原生 JS，不引框架，和现有代码风格一致
- **渐进迁移**：data-term 标记覆盖率 17%，新代码逐步标记，存量由 TreeWalker 兜底
