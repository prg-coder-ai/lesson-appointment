# 屏幕区域录制器 · 开发与打包记录

> 从「JS 能不能录指定区域」这个问题，做到一个 99MB 的 Windows 绿色单文件。
> 记录技术选型、关键实现、打包流程和踩过的坑。

---

## 1. 项目演进

### 1.1 起点

问题：浏览器里能不能录制屏幕的**指定区域**？

结论：能，但 `getDisplayMedia()` 只能让用户选「整个屏幕 / 某个窗口 / 某个标签页」，**没有"拖选任意矩形"的原生能力**。区域需要在拿到视频流后自行裁剪。

### 1.2 v1 · 单文件 HTML

`screen-region-recorder.html`，自包含（CSS/JS 全内联），零本地依赖。

- 抓画面：`getDisplayMedia()`
- 指定区域：预览画面上拖框，`Canvas.drawImage` 裁剪子矩形
- 录制：`canvas.captureStream()` + `MediaRecorder`
- 转 MP4：`@ffmpeg/ffmpeg`（WASM，走 CDN）

### 1.3 v2 · 定时与分段

- **定时启动**：立即 / 倒计时 N 秒 / 指定时刻（`HH:MM:SS`）
- **分段录制**：按固定时长自动切段，每段独立成文件

### 1.4 v3 · Electron 桌面版

加壳为 Windows 绿色单文件，同时获得两个浏览器永远做不到的能力：

- 枚举窗口供用户选择（不再弹系统选择器）
- 系统声音回环采集（loopback）

后续又把 FFmpeg 引擎从 CDN 下载改成了随程序内置，转 MP4 全程离线。

## 2. 技术选型

| 方案 | 产物 | 现有代码改动 | 窗口枚举 | 原生 ffmpeg |
|---|---|---|---|---|
| **Electron**（选用） | portable exe 99MB | 极小（+2 个文件） | 可做下拉列表 | 可换原生 |

## 4. 核心技术实现

### 4.1 区域裁剪的坐标映射

**最容易错的地方**：不能用 `devicePixelRatio` 反推缩放比。

不同系统上 `getDisplayMedia` 返回的 `videoWidth` 可能是屏幕物理分辨率，也可能是视口尺寸 × DPR。必须以实测值为准：

```js
// 视频像素 / 显示 CSS 像素
const ratio = video.videoWidth / overlay.clientWidth;
```

`overlay`（选区层）只贴在**画面实际绘制区域**上，排除 `object-fit: contain` 产生的 letterbox 黑边：

```js
function getDisplayRect() {
  const cw = preview.clientWidth, ch = preview.clientHeight;
  const vw = preview.videoWidth, vh = preview.videoHeight;
  const scale = Math.min(cw / vw, ch / vh);
  const w = vw * scale, h = vh * scale;
  return { left: (cw - w) / 2, top: (ch - h) / 2, width: w, height: h };
}
```

这样在预览里框哪里，就精确录哪里。

### 4.2 Region Capture 与 Canvas 裁剪的分工

| 方式 | 原理 | 兼容性 | 结论 |
|---|---|---|---|
| `CropTarget.fromElement()` | 把 track 裁到某 DOM 元素的包围盒 | 仅 Chrome/Edge 104+，Firefox、Safari 至今不支持 | 作为可选路径 |
| Canvas 二次裁剪 | 解码 → 截子矩形 → `captureStream()` | 全浏览器 | **默认路径** |

Region Capture 有两个硬限制：只在**同一标签页**内生效；语义是"裁剪到这块区域"，压在上面的内容也会被录进去。

### 4.3 帧率由绘制循环掌控

不用 `captureStream(30)` 自动采样，改用 `captureStream(0)` + 手动推帧，避免重复帧：

```js
S.cropCtx.drawImage(preview, sx, sy, sw, sh, 0, 0, outW, outH);
S.videoTrack.requestFrame();   // 每画一帧推一次
```

用 `setTimeout` 而非 `requestAnimationFrame`：后台标签页的 rAF 会完全停止。

### 4.4 分段录制的零间隙切段

**问题**：先 `stop()` 旧 recorder，等 `onstop` 再建新的，中间几十毫秒是真空，画面会丢。

**方案**：先起新段，再收旧段，让两个 `MediaRecorder` 短暂并存消费同一个 canvas 流。

```js
function rollSegment() {
  const oldRec = S.currentSeg.rec;
  beginSegment();                    // 新段立刻 start
  if (oldRec && oldRec.state !== 'inactive') oldRec.stop();  // 旧的同时停
}
```

切换处最多重叠 1 帧，不会丢画面。

**收尾时机**：不能靠单个 `onstop` 判断结束。切段后立刻点停止时，会有两个 recorder 同时处于 stop 过程中，第一个 `onstop` 到达就收尾会丢掉最后一段。用活跃列表计数：

```js
rec.onstop = () => {
  S.liveRecs = S.liveRecs.filter(r => r !== rec);   // 先出队（空段也要出）
  // ... 落盘 blob
  if (!S.recording && S.liveRecs.length === 0) onAllStopped();
};
```

### 4.5 Electron 窗口枚举与无弹窗捕获

主进程枚举窗口，带缩略图给渲染层做列表：

```js
desktopCapturer.getSources({
  types: ['window', 'screen'],
  thumbnailSize: { width: 320, height: 180 },
  fetchWindowIcons: true
})
```

授权时拦截 `getDisplayMedia`，直接返回前端选定的源：

```js
session.defaultSession.setDisplayMediaRequestHandler(async (request, callback) => {
  const sources = await desktopCapturer.getSources({
    types: ['window', 'screen'],
    thumbnailSize: { width: 0, height: 0 }   // 只要 id，跳过截图开销
  });
  const target = sources.find(s => s.id === pickedSourceId) || sources[0];
  const grant = { video: target };
  if (pickedAudio) grant.audio = 'loopback';   // 系统声音回环
  callback(grant);
}, { useSystemPicker: false });   // 必须 false，否则系统选择器会绕过这里的逻辑
```

渲染层只需在开始捕获前同步一次选中的 id，并把 `audio` 约束设为布尔值。

### 4.6 绿色化

portable 模式会把 exe 解压到临时目录运行，但会注入 `PORTABLE_EXECUTABLE_DIR` 指向 exe 真实位置。据此把用户数据搬出 `%APPDATA%`：

```js
if (process.env.PORTABLE_EXECUTABLE_DIR) {
  const dataDir = path.join(process.env.PORTABLE_EXECUTABLE_DIR, 'ScreenRecorderData');
  fs.mkdirSync(dataDir, { recursive: true });
  app.setPath('userData', dataDir);
  app.setPath('sessionData', dataDir);
}
```

### 4.7 内置引擎与自定义协议

最初转 MP4 是运行时从 CDN 拉 FFmpeg.wasm。改成内置后遇到一个障碍：`file://` 页面下浏览器禁止 `fetch` 和 `new Worker()` 读取本地文件，引擎加载必然失败。

解法是把页面从 `file://` 迁到自定义协议下：

```js
// 必须在 app ready 之前声明
protocol.registerSchemesAsPrivileged([{
  scheme: 'app',
  privileges: { standard: true, secure: true, supportFetchAPI: true, corsEnabled: true, stream: true }
}]);

// ready 之后挂载处理器，按 MIME 返回 asar 内的文件
protocol.handle('app', async (request) => {
  const { pathname } = new URL(request.url);
  const filePath = path.join(__dirname, decodeURIComponent(pathname).replace(/^\/+/, ''));
  if (!filePath.startsWith(__dirname)) return new Response('Forbidden', { status: 403 });

  const ext = path.extname(filePath).toLowerCase();
  const contentType = MIME_MAP[ext] || 'application/octet-stream';

  // HEAD 单独处理：否则为了探测会把 31MB 的 wasm 整个读出来
  if (request.method === 'HEAD') {
    const st = await fs.promises.stat(filePath);
    return new Response(null, { status: 200, headers: { 'content-type': contentType, 'content-length': String(st.size) } });
  }

  const data = await fs.promises.readFile(filePath);
  return new Response(new Uint8Array(data), {
    headers: { 'content-type': contentType, 'content-length': String(data.length) }
  });
});
```

页面改由 `mainWin.loadURL('app://local/screen-region-recorder.html')` 加载。三个关键点：

1. **`standard: true` + `secure: true`** 让 `app://` 成为安全上下文，Worker 和 WebAssembly 才被允许
2. **`application/wasm` 这个 MIME 必须对**，否则 `WebAssembly.instantiateStreaming` 直接拒绝
3. **引擎地址必须转绝对 URL**。ffmpeg.wasm 内部会把 `coreURL` 交给 blob Worker，相对路径是按 blob URL 解析的，必然 404

```js
function vendorUrl(file) {
  return new URL('vendor/' + file, location.href).href;
}
```

渲染层每次启动会 HEAD 一下 wasm，比对 `content-length`，确认引擎可用就在日志里亮绿灯——避免用户录完几十秒、点转码时才发现引擎加载不了。

### 5.6 额外产出：绿色目录版

portable 单文件的代价是每次启动都要解压 341MB。只在自己电脑上用的话，目录版更快：解压一次，之后每次约 2 秒。

```bash
# 1. 生成解包目录（注意不要 portable target）
npx electron-builder --win --dir -c.directories.output=E:/srb-dir

# 2. 重命名目录与主程序（中文名对用户更友好）
#    win-unpacked → 屏幕区域录制器
#    ScreenRegionRecorder.exe → 屏幕区域录制器.exe

# 3. 打成 zip（用 electron-builder 缓存里的 7za，比 Compress-Archive 快很多）
7za a -tzip -mx=5 -mmt=on "屏幕区域录制器-1.0.0-绿色目录版.zip" "屏幕区域录制器"
```

实测 341MB → 146MB，压缩耗时 33 秒。

两个细节：

**1. 重命名 exe 不影响启动。** asar 完整性校验写在 exe 的资源段里，不依赖文件名；`app.getPath('exe')` 也跟随实际路径。

**2. 数据目录要能跟着走。** 原来的绿色化只认 `PORTABLE_EXECUTABLE_DIR`（portable 模式注入的环境变量），目录版没有这个变量，数据会落到 `%APPDATA%`，就不算绿色了。补一个分支：

```js
function resolveDataDir() {
  if (process.env.PORTABLE_EXECUTABLE_DIR) {
    return path.join(process.env.PORTABLE_EXECUTABLE_DIR, 'ScreenRecorderData');
  }
  try {
    const exeDir = path.dirname(app.getPath('exe'));
    if (exeDir.indexOf('node_modules') >= 0) return null;   // 开发模式跳过
    fs.accessSync(exeDir, fs.constants.W_OK);
    return path.join(exeDir, 'ScreenRecorderData');
  } catch (err) {
    return null;   // 装在 Program Files 等只读位置时回落 %APPDATA%
  }
}
```

实测启动 **1.3 秒**（bootstrap → ready-to-show），数据目录正确落在 exe 同级。

`requestExecutionLevel: "user"` 很重要——避免绿色版启动时弹 UAC 提权。

15 条，按阶段归类。都是真实遇到并解决的。

| # | 阶段 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | 打包 | 拉工具链超时 600 秒 | 默认从 GitHub Releases 下载，国内不通 | 设两个镜像环境变量 |
| 2 | 打包 | 卡 8 分钟后报 `Lock file is already being held` | 上次中断的进程在 `%TEMP%` 留下 `eb-dl-*.lock.lock` | 删掉该锁目录再重跑 |

| 8 | 前端 | 倒计时遮罩不该显示时一直盖住画面 | `#countdown` 的 `display:flex` 覆盖了 `[hidden]` | 全局 `[hidden]{display:none!important}` |

### 6.1 两个最隐蔽的坑

**第 4 条 · 环境变量冒充崩溃**

现象是进程无输出、无窗口、退出码 0，看起来像程序崩了。实际是环境变量把 Electron 改成了 Node 解释器——传 `--no-sandbox` 会报 `bad option`，而 `bad option` 是 Node.js 独有的措辞，Chromium 不这么报。

排查手法：在 `main.js` 最顶部写一行文件日志。如果连这行都没生成，说明主进程代码根本没被执行，优先怀疑运行环境而不是代码。

**第 5 条 · 磁盘满导致的静默失败**

portable 启动要把 310MB 解压到 `%TEMP%`，空间不足时解压失败但**不报任何错**，表现只是「卡住」。当时 C 盘只剩 71MB，解压到 79MB 就停了。

排查手法：卡住时先看 `%TEMP%` 下解压目录的实际大小，再看磁盘剩余空间。

## 7. 验证方法

GUI 程序没法自动化点按钮，但可以验证**启动链路完整性**：

主进程在最早期写一份 trace 到 `%TEMP%`（此时 `userData` 可能还没就绪）：

```js
const TRACE_FILE = path.join(process.env.TEMP, 'screenrec-trace.log');
try { fs.writeFileSync(TRACE_FILE, ''); } catch (e) {}   // 每次启动覆盖
trace('=== boot pid=' + process.pid + ' ===');
```

在关键节点打点：`boot → singleInstanceLock → whenReady → bootstrap → loadFile → did-finish-load → ready-to-show`。

启动脚本捕获埋点，出现 `ready-to-show` 即判定成功：

```js
const env = { ...process.env };
delete env.ELECTRON_RUN_AS_NODE;   // 测试环境必须清掉
spawn(EXE, [], { env });
// 轮询 trace 文件，命中 ready-to-show 即通过
```

**实测结果**：

```
boot pid=23332 portable=G:\...\dist
singleInstanceLock OK
whenReady
bootstrap start, userData=G:\...\dist\ScreenRecorderData
loadURL app://local/screen-region-recorder.html → bootstrap done
did-finish-load → ready-to-show
[renderer] [engine] ready, wasm=32232419
✅ 24.8s，error.log 为空，数据目录建在 exe 同级
```

最后那行是内置引擎的自检结果：`content-length` 与本地 wasm 文件的字节数完全一致，说明 asar 打包无损、`app://` 协议能正确返回二进制。

## 8. 已知限制

| 限制 | 说明 | 能否绕过 |
|---|---|---|
| **exe 体积 105MB** | Electron 运行时占 ~99MB，内置引擎 +6MB | 换 Tauri 可降到 ~10MB，但要重写捕获逻辑 |
| **单文件版每次启动约 25 秒** | portable 每次运行都要把 341MB 解压到 `%TEMP%` | 用绿色目录版，实测 1.3 秒启动 |
| **需 C 盘 ≥ 400MB 空闲** | 解压临时文件占用，空间不足时静默失败 | 清理临时目录 |
| **未签名** | 首次运行有 SmartScreen 蓝色警告 | 买 OV 证书（$200–400/年） |
| **只能录可见内容** | `getDisplayMedia` 抓不到被完全遮挡的窗口 | 无（受系统合成器限制） |
| **单线程 WASM 转码** | 1 分钟 1080p 约 20–40 秒，且占用 CPU | 可换原生 ffmpeg.exe（需额外分发 70MB 二进制） |
| **多段数据驻留内存** | 未下载前不释放 | 每段控制在 60–300 秒 |

## 9. 常见问题排查

**双击没反应 / 闪退**

看两个文件：

1. `%TEMP%\screenrec-trace.log` —— 停在哪个阶段
2. `<exe 同级>\ScreenRecorderData\error.log` —— 渲染进程报错

如果 trace 完全没生成，说明主进程没起来，优先怀疑：磁盘空间不足、被安全软件拦截、环境变量 `ELECTRON_RUN_AS_NODE`。

**启动很慢**

正常现象（解压 310MB）。想秒开就用目录版。

**录制画面卡顿 / 掉帧**

- 页面被切到后台时浏览器可能节流定时器 → 让录制窗口保持可见
- 帧率设太高、码率设太高 → 降到 30fps / 4000kbps

**转 MP4 失败**

- `file://` 打开网页版时 Worker 被同源策略拦截 → 用 `python -m http.server 8080` 起本地服务
- 引擎加载失败 → 确认程序目录下 `vendor` 文件夹完整（三个文件共 31MB）
