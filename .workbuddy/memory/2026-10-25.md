## 双 docker 实例（api + message-service）的 Nginx / 前端配置改造

**探测结论（重要）**：云托管只有**两个**有效后端域名
- `https://api-329614-8-1475810246.sh.run.tcloudbase.com` → 200 `booking_api` 2.2.0（容器 8081）
- `https://message-service-329614-8-1475810246.sh.run.tcloudbase.com` → 200 `message-service` 1.1.0（容器 8090）
- `https://message-329614-8-1475810246.sh.run.tcloudbase.com` → **404 `INVALID_HOST`（域名不存在，别配）**

**改动的文件**
1. `doc-develop/nginx-代理远端API-样例.conf` —— 单 upstream → **双 upstream**（`api_remote` / `msg_remote`）。
   关键手法：server 级 `set $proxy_host_hdr "<booking域名>"`，消息服务 4 个 location 各自再 set 覆盖；
   `proxy_set_header Host $proxy_host_hdr` + `proxy_ssl_name $proxy_host_hdr` 放在 server 级只写一遍
   （nginx 阶段顺序：server rewrite → 选 location → location rewrite，content 阶段才求值 header，故生效）。
   新增 `location = /msg-health` 走消息服务 `/api/v1/system/info` 探活。
2. `cloudBased/web/nginx.conf.template` —— 改为 `${API_UPSTREAM}` + `${MSG_UPSTREAM}` 双占位；
   删掉 `proxy_set_header Host $host`（$host 是前端自己的域名 → 云托管 INVALID_HOST/404）；
   不加 upstream 块（占位符带 scheme，server 指令不接受 → 放弃 keepalive，已注明）。
   修正 SPA fallback：`try_files $uri $uri/ =404`（多页应用，fallback 到 index.html 会把错链静默成首页）。
   补 SSE 四件套（原 read_timeout 120s 每 2 分钟掐断 SSE）。
3. `cloudBased/web/Dockerfile` —— 补 `ARG API_UPSTREAM / MSG_UPSTREAM`（之前 build-all 传 --build-arg
   但 Dockerfile 没声明 ARG，参数被静默忽略 → envsubst 拿空串）；加非空校验 + 去尾斜杠
   （proxy_pass 带尾斜杠会替换前缀，吃掉 /api/v1/）；**故意不做 nginx -t**（内网 svc.cluster.local 在构建机解析不到）。
4. `cloudBased/scripts/build-all.sh` / `.ps1` —— 传两个 build-arg，内网地址用
   `http://api.<envid>.svc.cluster.local:8081` 与 `http://message-service.<envid>.svc.cluster.local:8090`。
5. `doc-develop/dev-frontend-remote-tcb.js` —— 同时设 API_URL 与 MSG_URL（之前只设 API_URL）。
6. `doc-develop/dev-frontend-remote.js` —— 新增「云托管只给 API_URL 不给 MSG_URL」的醒目告警（含推测地址）。
7. `doc-develop/dev-proxy.js` —— 新增 `identify(target)`：GET `/api/v1/system/info` 读 `service` 字段，
   启动时打印「服务自述」。**原因：TCP 探活对"域名写错"完全是假绿**（都连同一个网关的 443），
   误配 message-329614-… 时探活照样 ✅。现在两个上游身份分别显示 booking_api / message-service。

**验证**：`DEV_PORT=8098 node doc-develop/dev-frontend-remote-tcb.js`
→ `/api/v1/system/info` 回 `booking_api`；`/api/v1/messages/list` 回 message-service 的 405（"支持：DELETE"）；
`/api/v1/sse/connect` 回 message-service 的 401。分流与 Host/SNI 均正确。

**前端侧结论（零改动）**：走同源反代时 `frontend/js/public/api.js` 的 `API_SERVER_HOST/PORT` 保持空串，
且**不要**设 `window.MESSAGE_API_BASE_URL`（messages-inbox.js / sensitiveWords.js 会优先用它）。
若要跨域直连两个云端域名：booking 的 `CorsConfig` 只放行 localhost/127.0.0.1/152.136.254.127，
必须加白名单才可用；message-service 侧 `allowedOriginPatterns("*")` 是全放开的。
