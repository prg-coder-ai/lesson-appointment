## 审计日志时间口径分析（12:16，结论：存 UTC / 显示不转换 / 筛选边界偏 8h）

**证据（fat jar 内驱动 + Jackson 2.17.2 实跑，只读）**：
库内 `created_at` = `2026-10-24 14:00:15` → `getTimestamp()` 得 `2026-10-24 22:00:15`（本地墙钟），
`Instant` = `2026-10-24T14:00:15Z` ⇒ **DATETIME 列里存的是 UTC 墙钟**。原因是
`application.properties` 的 `serverTimezone=UTC` + Connector/J 8.x `preserveInstants` 默认 true；
写入端 `AuditAspect` 只 `record.setCreatedAt(new Date())`（唯一入口，`auditLogMapper.insert` 一处）。

**三段链路真相**：
1. 存储：UTC ✅
2. 传输：`AuditLog.createdAt` 是 `java.util.Date`，Jackson 默认 `StdDateFormat`(UTC) 输出
   `"2026-10-24T14:00:15.000+00:00"` —— **带时区标识，语义正确** ✅
3. 显示：`frontend/js/auditLog.js#formatTime` → `window.DatetimeDomain.formatDateTime`
   = `String(iso).replace('T',' ').substring(0,19)` —— **纯字符串截断，`+00:00` 被丢弃** ❌
   → 列表/详情显示的是 UTC，比本地慢 8 小时。

**★根因**：`shared/domain/datetime.js` 是"抽共去重"，把旧实现
（注释里明写来源 `frontend/js/public/auditLog.js:144`）原样搬进来，**没做时区修正**。
同模块里真正做转换的是 `utcToZoned()`，但审计日志没调它（全仓只有 appointmentNotes.js 用它）。

**连带**：`AuditLogController` 的日期筛选 `startDate + " 00:00:00"` 直接与 UTC 列比较 →
用户选"本地 10-24"，实际筛 UTC 10-24 00:00~23:59:59 = 本地 10-24 08:00 ~ 10-25 07:59。偏 8 小时。

**覆盖范围**：`admin.html`（租户管理员）与 `platform_admin.html` 都跳同一个 `auditLog.html`
→ 一处修复覆盖两端；`message-service` 无 audit_log 表。
**守卫盲区**：`check:tz-guard` 只管课次链路（`scheduleLocalToUtc` / 禁裸 `now()`），不检查展示层格式化。

**已按用户拍板的方案 A 落地（12:35）**：
- `frontend/js/auditLog.js`：`formatTime` 改走 `DatetimeDomain.utcToZoned(t, undefined, true)`
  （**不再用 `formatDateTime`** —— 它是纯截断，丢 `+00:00`）；新增 `auditZoneName()` /
  `auditZoneOffsetText()` / `renderZoneHint()` / `localDateBoundaryUtc()`。
- `frontend/auditLog.html`：卡片标题加 `<span id="tz-hint" class="tz-hint">`，运行时渲染
  「日期为本地时间（Asia/Shanghai，UTC+08:00）」；表头「时间」加 title 提示。
- `AuditLogController`：新增 `toUtcWallClock(raw, endOfDay)`，日期边界先折算成 UTC 墙钟再比较。
  **★不能用 `ZoneId.systemDefault()` 推导** —— 云托管容器默认 TZ=UTC，会在容器里再错一次；
  本地时区必须由前端算好、以带偏移 ISO 串传入。解析失败返回 null 时必须**跳过**该条件，
  否则 `created_at >= NULL` 恒不成立、整页查询空掉。
- 验算：前端 `2026-10-24` → `2026-10-23T16:00:00.000Z`（起始）/ `2026-10-24T15:59:59.999Z`（结束）；
  后端 `toUtcWallClock` 七种入参（Z / +08:00 / 纯日期 / 坏值）全 PASS。
- 编译 `build_smoke.sh compile` BUILD SUCCESS；`CODEBUDDY_SAFE_DELETE_ENABLED=0 node frontend/build.js`

## 排期页面（租户管理员）操作简便性分析（12:55）

**现状**：`frontend/js/admin-schedule.js`（1712 行）+ `admin.html` 菜单 `key="schedule"`。
一次新建排期 = 8 个环节 / 9 个字段：检索课程→选课程→点新建→填(排期名称·员额·开始日期·
上课时间·结束日期·重复类型·重复周期·重复星期·状态)→预览(自动切走 Tab)→切回→保存→改状态再存。
排期数据模型：`course_schedule`（startTime 暗含起始日期、endTime 暗含重复结束、repeatType/interval/repeatDays/availableSites/status/timeZone/name），**无 teacherId、无 classroomId、无时长**（DTO 里 teacherId 是注释掉的）。

**★三个必须先修的真 bug（"简便"得建立在"正确"上）**：
1. **开始日期默认值用 UTC 算**：`admin-schedule.js:405` 的 `value="${(new Date()).toISOString().split('T')[0]}"` ——
   本地 00:00–07:59 打开页面，默认日期是**昨天**。而 `resetScheduleObject()`（1163 行）用本地分量是对的，
   同一文件两套口径。
2. **冲突检查范围与时长都是假的**：`CourseScheduleService.checkScheduleOwnerConflict` 只查
   `selectByCreateDto(courseId)` —— **只比同一课程**，跨课程撞课查不出；时长硬编码
   `existStart.plusHours(1)`（注释"可视为每节课持续1小时"）→ 90 分钟课排 19:00 与 20:00 判"不冲突"。
   另有 `System.out.println` 调试残留（154 行）。
3. **「检查冲突」按钮与保存重复**：`saveScheduleToDB` 已内置自动查冲突（1462-1484），两处提示文案还不一致
   （一处用 `，` 一处用 `@@` 拼接）。

**复杂度泄露**：页面上「排期时区」+「用户时间预览/用户时区」两个概念对单时区租户是纯噪音。
日历视图 `renderCalendar` 固定 35 天、从第一张课次所在周的周一起，无月份标题、无上/下月 —— 看不了 30 天以上。

**方案分层**（建议 L1 先行）：
- L1 降负（前端，不动后端/表）：名称自动生成、先选星期再自动定日期、重复星期随开始日期自动勾、
  员额随班级形式 1/5/10、状态默认已发布 + 单按钮「保存并发布」、删冗余「检查冲突」、
  预览内联不切 Tab、时间默认整点。→ 8 环节降到 3~4。
- L2 批量：「复制此排期」/「从上周复制」/一次填多行时段后串行提交。
- L3 结构性：周课表网格（7 天 × 时间轴，点格子建、拖拽表时长）——需先补时长与教室字段，否则是沙上建楼。

**待拍板**：① 是否给 `course_schedule` 加时长/教室（决定冲突判定能否可信、L3 是否可行）；
