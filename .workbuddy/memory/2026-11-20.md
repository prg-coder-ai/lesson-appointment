### 一个 P0 发现（用户可感知，必然发生）

**双份 token 快照分叉 → 只要按一次 F5 就掉线。**
- 登录写两份：`auth.js:117` 把 token 同时写进 `localStorage.token` 和 `currentUser.token`
- 刷新只更新前一份：`utility_request.js:196-199`
- 页面 onload 的 `autoLoginCheck()` 取值顺序是 `userInfo.token || STORE.token`（**currentUser 优先**），
  且 `isJwtExpired` 成立就 `removeItem` 三件套 + return null（`api.js:288-306`）→ 调用方跳登录页
- 结论：**发生过一次"过期→刷新"之后，此后任何页面重载都掉线**，refresh token 完全没被使用。
  不是边缘情形——T1 在触发刷新那一刻就已经过期了
- 修法（3 行）：刷新成功后同步回写 `currentUser.token`；配套：`autoLoginCheck` 遇过期不要清 refreshToken

### 其他失效情形（分类口径：A 没发起 / B 发了白搭 / C 长连接不覆盖 / D 该失效却有效）
- A2 消息中心 `mreq`/`areq` 独立 axios（`messages-inbox.js:93`），401 直接 cleanupAuth 跳登录，不刷新
- A3 `noAuthRedirect:true` 的请求不刷新（`utility_request.js:155`）；`promo.js:298` 把需鉴权的
  `/legal/accept` 也打了这个标记 → 协议留痕可能静默丢失
- C1 课堂 WS：`s.token` 是 `connect()` 时快照，`_scheduleRetry` 重连只重开通道、不重读 localStorage
  （`classroom-ws.js:83/111/167`）→ 课内超 1 小时断线后永久连不上
- C2 SSE token 在 URL，EventSource 自动重连带旧票
- D1 **改密/重置密码不撤销 refresh token**（`UserService:919/1002` 只 updatePassword）——
  N5 把"改密旧 token 通行"当问题、给出"落库即可注销"的解法，但这两条路径没调用注销入口
- D3 子服务 `verifyAccessToken` 只验签+过期、**不校验 type**（message/classroom `JwtUtil:58`），
  refresh token 能过它们的签名校验（无 role claim，拿不到管理员能力，属纵深防御缺口）

### 已核对但属"设计如此"，不要当 bug 改
- 无主动续期（纯 401 触发）；refresh 滑动续期、无绝对上限
- 登录 `saveNewToken` 删全部凭证 = 单设备语义；轮换 `rotateToken` 只删旧那条 = 不跨设备互踢
- 登录页/落地页 401 不刷新（防 tCode 重定向死循环）
- `api.js` 里 `autoLoginCheck1()` 是死函数，且重复定义了一份 `isJwtExpired`（后者覆盖前者，行为等价）

### 两处偏离原建议（重要，别再"改回去"）
1. **2 号没做成 async**：`autoLoginCheck()` 被 student/teacher/booking.html 的 onload 直接取返回值，
   改 async 要动三个页面初始化流程（菜单/角色/重定向）。改为「过期也不清态、照常返回」，
   把换票交给首个接口请求（refreshAndReplay 有完整失败分类）。副作用：refresh 也过期时多一次闪烁。
2. **3 号没换统一 service 实例**：mreq 指向 8090、areq 指向 8081，换实例会打到错的服务。
   改成「复用能力不复用实例」——暴露 refreshAccessTokenOnce 给旁路模块调用。

### 课堂实例「容量」字段定性（提交 bcbeb37a）
- `sys_eclassroom_instance.max_capacity`（平台端「最大容量」）= **纯记录字段**：只有表单写入
  + 列表展示，**后端零读取**（api 与 classroom-service 两侧实体都声明了 maxCapacity/currentLoad，
  两边都没用）。`current_load` **从未被写入**，恒 0，UI 也不展示。
- `createInstance`/`updateInstance` 无校验（负数、0 都能存）；`bindTenantClassroom` 不按负载/容量选实例。
- 真限制在另一维度：`classroom.rtc.mesh.max-peers=6`（每课堂人数，超出**只收不发、不拒绝进房**）；
  实例级只有物理天花板（Tomcat 默认 8192 连接 / 200 线程、`-Xmx512m`、Hikari 默认 10）。

- 过载的后果链（重要）：心跳 15s / 判定 60s（≈丢 4 次即判离线）→ 学生 OFFLINE+leave 污染考勤与
  有效时长；教师离线超 120s 触发 `closeAfterEnd` **自动结课**（重算时长/归一状态/课时回流/
  consumption_version+1）→ 账务数据事故。所以过载表现是"掉线误判"而不是"拒绝开课"。
- 现网隐患：实例 id=6 `eclass2cluster` 的 **api_host 是空串（非 NULL）**，而 `buildApiUrl` 只判
  `host == null` → 拼出 `http://:8092/api/v1`；`bindTenantClassroom` 只校验存在+未删除，
  **不校验 api_host 非空、也不校验 status**。绑上即课堂入口全挂。4 个租户现都绑 id=5，未踩到。
