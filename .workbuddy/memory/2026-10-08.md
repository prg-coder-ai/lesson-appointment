### 三个必须钉死的实现点
1. **判定必须落在 Service 且两个入口共用一处**（`UserService.applyRoleAdmission`）。

## 问询：「防超卖逻辑从数据库迁移到 api 判断」是否可行

**结论：可行，且已完成约 90%；剩下 10% 不该搬。**（未改代码，纯核查后给判断）

### 实测：DB 侧与超卖相关的约束只剩 3 条，且都不是"超卖判定"
| DB 约束 | 真实语义 | API 侧等价物 |
|---|---|---|
| `uk_booking_schedule_student`(schedule_id,student_id) | 同学生不可重复订同排期 | `BookingService:66` **在排期行锁内**查重 |
| `course_schedule_chk_sites` `available_sites>=0` | 容量不被改成负数（**防数据损坏，非防超卖**） | `assertSitesNotBelowOccupied` 判"新容量≥已占数"，严格更强 |
| `updateSites` 里 `AND available_sites+#{inc}>=0` | 同上 | 同上；且 rows=0 是**失败信号通道**（调用方据此判失败，删掉会把静默失败变成功） |

**关键认知**：`available_sites` 语义是**总席位**，不是剩余。剩余数每次由
`countOccupyingForUpdate` 从 booking 表实时聚合。→ **超卖判定的正确输入是跨表聚合值，
结构上就不在单行里，DB 的 CHECK/唯一键表达不了"占位数< 容量"这个判定。**
所以"把防超卖搬到 API"这个动作其实已经完成了（BookingSeatService + 5 条写路径全覆盖）。

### 为什么剩下的 3 条不该删
1. `available_sites` 是 **tinyint**，`CourseScheduleService:245` 注释明写"tinyint 允许负值"。
   一旦被减成负数，该排期**永久拒绝新预定**（`totalSites <= 0` 直接抛异常）——
   CHECK 防的是这种不可自愈的损坏，不是超卖。
2. 唯一键是"某条新写路径忘了先加排期锁"时的**唯一兜底**。删了就等于把防线从2 降到 1，
   且失效方式是**静默重复预订**（不报错、列表里出现两条）。
3. `updateSites` 的 `AND available_sites+inc>=0` 不只是防线，更是**原子判定**：
   表达"减到 0 成功、减到 -1 一个行都不改"。API 的先查后写做不到这个原子性
   ——只有靠 `WHERE` 里的谓词才能让 DB 自己拒绝。**这是把约束搬到 API 真正会丢能力的一处。**

### 判据（可复用）
- **判据输入需要跨表聚合 / 依赖业务状态语义** → 放 API（DB 表达不了）
- **单行单值不变量 / 需要原子拒绝 / 兜底防漏** → 留 DB（API 保证不了）
- 二者不是重复，是**不同职责的第二道防线**。与第 4 批"不用DB 级联删"不矛盾：
  级联删是**替业务做决定**（有害），约束是**拒绝非法状态**（无害且必要）。

**五个坑（每个都让守卫看起来是绿的）**
1. **驼峰映射必须与 MP 逐字符等价**。MP `StringUtils.camelToUnderline` 是"每个大写字母前插下划线"，**不做连续大写合并**；`scheduleID` → `schedule_i_d` 而非 `schedule_id`。第一版用合并式正则 → **比运行时更宽容 = 假绿**。表名推导 = `camelToUnderline` + `firstToLowerCase`（`TableInfoHelper.initTableNameWithDbConfig`，已解包 mybatis-plus-core-3.5.3.2-sources.jar 核对）。判据：**宁可误报不存在的列，不能漏报被 MP 映射成别的列的字段**。
2. **带行尾注释的字段被整条丢弃** → 32 条假告警全说"Booking 没有 booking_id"。修法：结构判定用剥行尾注释后的文本，豁免归集用原文。**误报率 100% 的守卫等于没有守卫**。
3. **`AUTO_INCREMENT` ≠ "NOT NULL 且无默认"**。按字面判会给每个自增主键表产假告警。

## 时区安全方案（doc-develop/时区安全：排期生成与 UTC 转换方案）对照审计 —— 18:20

**结论：设计文档的"生成侧"基本落地，"存储/消费侧"完全没有。这是当前最大的单点时区缺陷。**

- `ScheduleGenerator`（common/）已有 `isMatchWeek` / `toUtc` / `toUserZone` / `timeSwitchWithZone`。
- `course_schedule.time_zone` 列存在（varchar36 NOT NULL），`ScheduleGenerateDTO.timeZone` + `userTimeZone` 双字段。

### 缺陷 P0（按严重度）
1. **存库不转 UTC**：设计第 4 步"转 UTC 存库"**未实现**。`CourseScheduleService.CreateDtoToObject:391-405` 直接

3. **`isMatchWeek` 的 zoneId 参数被架空**：ScheduleGenerator:103 `date.getDayOfWeek()`，设计文档要求的
   `date.atStartOfDay(zoneId).getDayOfWeek()` **被注释掉**（行内注释写"wuguan"）。→ 跨时区排期星期仍会错，
   正是设计第 6 节要消灭的现象。这是"改了一半"的典型：形参还在，实现已退化。

### 缺陷 P1
4. **课次继承本地时间且无人转换**：`generateAppointmentsForBooking:575-580` 从 `ScheduleVO` 的 date+time 拼
   LocalDateTime 直接 `appt.setAppointmentDatetime`，`Appointment.timeZone` 字段有但**从不赋值**（永远 null）。
5. **通知检查用服务器时区**：`NotifyDispatchService:128/257` `LocalDateTime.now()`（服务器默认时区），
