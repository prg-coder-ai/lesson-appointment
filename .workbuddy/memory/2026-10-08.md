### 决策：两个入口的口径分歧（用户拍板「按调用者权限收口」）
报告第 5 条写"两个入口都只允许 student/teacher"，但**报告自身矛盾**：落地要点第 4 段说
初始化依赖"管理员在后台新建"；且 `platform-admin-user.js:161-162` 的「新增用户」下拉
**只有 platform_admin / admin 两项** —— 平台管理员正是靠 `/user/add` 开租户管理员。
一刀切会打死该功能。落地口径：
- `/register`（匿名）= 报告原意：白名单 4 角色，admin 走「本租户首个」bootstrap、platform_admin 走
  「全系统首个」bootstrap，其余 pending。
- `/add`（已鉴权）= 按**调用者**角色裁定可建角色：须 admin/platform_admin；**租户管理员不得建
  platform_admin**（否则租户管理员横向拿跨租户权限）；平台管理员可建全部四角色。

### 三个必须钉死的实现点
1. **判定必须落在 Service 且两个入口共用一处**（`UserService.applyRoleAdmission`）。
   Controller 各判一次必然漂移 —— 这正是原缺陷形态（register 无条件 active、add 无条件 active 且无校验）。
2. **`Register` 加了 `approvedByAdmin` 参数**：`/add` 的创建动作本身就是审批，必须直接 active。
   否则套用"非首账号 pending"会让平台后台刚建好的管理员**当场无法使用**（可用性事故）。
3. **bootstrap 并发靠 `FOR UPDATE` 锁定读，已实测非推测**：新增
   `countByTenantAndRoleForUpdate` / `countByRoleGlobalForUpdate`（`@InterceptorIgnore(tenantLine)` +
   SQL 内显式 tenant_id，tenant_id=0 表示平台）。MySQL 8.4.11 / REPEATABLE READ 下双会话实测：
   会话 A 持 `COUNT(*)...FOR UPDATE`（命中 0 行），会话 B 的 INSERT **被阻塞 4115ms**，A 回滚后才继续
   → 零行时同样加 next-key 锁，双激活不成立。**注意 user 表只有单列 `idx_tenant_id`（无 (tenant_id,role)
   复合索引），锁范围是该 tenant_id 整个区间** —— 只影响并发度，不影响正确性。
   ⚠️ 技能文档把「聚合 + FOR UPDATE」列为雷区，那是旧版本行为，8.4 实测可执行。

### changePassword 的真实语义（报告第 6 条需按现状调整）
`/user/account/changePassword` 的**全部真实调用点都是管理员重置他人密码**
（`admin-user.js:247`、`platform-admin-user.js:330`），另有 `api.js` 的本人改密入口
（`showChangePasswordDialog`，被顶栏"修改密码"挂上）。故不能一律禁改他人，改为**两态**：
- 管理员代管：同租户（平台管理员跨租户），不要求原密码 —— 后台重置本就无需知道用户密码。
- 本人改密：**必须原密码**（`oldPassword`，前端已改为 prompt 采集；原代码里那句采集原密码的
  prompt 是被注释掉的，等于"登录后即可改密"，token 一旦被窃账号彻底失守）。
- 其余（非管理员且非本人）403。

### purgeOne 的真实危害面（比报告描述更值得说）
`deleteById(in.getMessageId())` → 实测 DDL：`msg_inbox.id` 是 AUTO_INCREMENT（1~5788），
`msg_message.message_id` 是雪花 ID（约 2.1e18）。**两个序列当前不相交**，所以误删面实测为 0 ——
**这是运气不是设计**：一旦 msg_inbox 被清理重建或 ID 生成策略变化，即出现

未碰 msg_message 主消息（架构红线：单独删主消息会让其他收件人副本空白）。
