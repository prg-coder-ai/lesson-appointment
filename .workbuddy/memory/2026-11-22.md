## 课堂全 500 / 管理端全 403 的真正根因：classroom 库没给 lesson 授权

**★ 500 文案形态是分诊器（本次实验证实，本地起 jar 对照）**
- `{"code":500,"message":"服务器繁忙：MyBatisSystemException"}`（光秃秃类名）
  = **拿不到 JDBC 连接**（库名/账号密码/授权/不可达/池耗尽）
  栈：`PersistenceException ← CannotGetJdbcConnectionException ← Unknown database`
- `服务器繁忙：### Error querying database ... Table 'x.classroom' doesn't exist`（长文案）
  = 连接已建立，**SQL 执行失败**
  机理：`MyBatisExceptionTranslator` 仅在 PersistenceException 的**直接 cause 是 SQLException**
  时翻译出 BadSqlGrammar；否则 `new MyBatisSystemException(e)`，其构造是 `super(null, cause)`
  → `getMessage()` 恒 null → GlobalExceptionHandler 落到 `getClass().getSimpleName()`。

**★ 403 与 500 同源**：`AuthInterceptor:58` 判开关要先查 `lesson_appointment.sys_tenant_eclassroom`，
`TenantEclassroomService:94` 的 `catch → return false` 把"连不上库"降级成"课堂未启用"→403；
平台管理员 tenantId=0 豁免该检查，才直接撞 500。**修连接即同时修 403**，别去查租户绑定数据。

**根因**：`classroom` 库是第三个模块后建的，`deploy/sql/00-create-databases.sql` 里那三条 GRANT
没跑到 → lesson 能连前两个库、唯独没有 classroom 权限。另：classroom.env 的
`DB_USERNAME`/`DB_PASSWORD` 缺失会**静默回落 jar 默认 root/123456**，同样表现为该 500。

## 纯 IP 环境 HTTPS（自签）+ 双栈（16:45）

**形态从三选一变五选一**（同一时间只启用一份，sites-available 里可全留）：
| 文件 | 80 | 443 |
|---|---|---|
| booking.conf | 站点 | - （示例域名） |
| booking-ip.conf | 站点 | - |
| booking-https.conf | 301 | 站点（LE 证书） |
| **booking-ip-https.conf**（新） | 301 | 站点（自签） |
| **booking-ip-dual.conf**（新） | **站点** | **站点（自签）** |

**★ 关键区分：sites-available 只是仓库，nginx 只 include sites-enabled/*。**
所以切形态＝摘 sites-enabled 的软链，**不删文件**（文件留着才能秒切/回滚）。
产生 duplicate default server 的是 Ubuntu 自带 `sites-enabled/default`（也写 listen 80 default_server），
不是这两份新文件（新文件都不带 default_server）。

**★ 自签下必须关闭 HSTS**（booking-ip-https.conf 里刻意注释掉）：
HSTS 一旦记住 max-age，浏览器连"继续前往"的警告页都不给，站点在有效期内彻底不可用，
只能 chrome://net-internals/#hsts 手动清。

**★ 自签的硬边界**：微信内置浏览器无"继续前往"→ 打不开；微信小程序不要 IP 域名也不信自签
→ 小程序端课堂**不可用**。要覆盖这两处只能上域名 + LE。

**★ 双栈的真实代价**：http/https 是不同 origin（scheme 参与同源），localStorage 不共享 →
切换 scheme 会显示"未登录"；http 非安全上下文 → getUserMedia 被禁（只有 localhost 例外），
课堂能看白板但麦克风点了没反应。

## 18:04 事故：误启用域名版站点导致 nginx -t 失败

**现象**：`sudo nginx -t` 报
`cannot load certificate "/etc/letsencrypt/live/your.domain.com/fullchain.pem": BIO_new_file() failed`
→ 结论：`sites-enabled` 里启用的是 **booking-https.conf（域名版）**，且 `your.domain.com`
占位符没替换、证书也没有。纯 IP 环境只允许 http / https-ip / dual 三种。

**关键认知**：`nginx -t` 失败时 `reload` 根本没执行 → nginx 仍跑内存旧配置、站点是活的。
**此时绝不能 `systemctl restart nginx`**（会真的起不来）。修法：摘 sites-enabled 的错链 →
确认/生成自签证书 → 启用正确形态 → `nginx -t` 过了再 reload。

**产出 `deploy/nginx/switch-site.sh`**（防复发，已沙箱实测 4 个场景）
- `switch-site.sh` 无参数 → 打印现状（启用了什么、自签/LE 证书在不在、SAN 内容与到期）
- `switch-site.sh <http|https-ip|dual|https-domain>` → 切换
- 四道前置校验：目标文件存在 / 无 `your.domain.com` 占位符 / 证书+私钥文件存在 /
  **证书 SAN 覆盖 server_name 里的地址**（这条防 ERR_CERT_COMMON_NAME_INVALID）
- `nginx -t` 失败 → **自动把 sites-enabled 恢复到切换前**（实测：从 dual 切 https-ip 失败后
  enabled 仍是 dual）
- sites-enabled 里的真实文件（非软链）会 mv 成 .bak.<ts> 而不是删掉
- 沙箱验证：A 证书缺失拒绝 / B 正常切换成功 / C nginx -t 失败回滚 / D 占位符残留拒绝

**★ 沙箱测试方法**（本机无 nginx 也能验）：把脚本里 `AVAIL=/etc/nginx/...` 等三处路径 sed 成
临时目录 + 用 `printf '#!/bin/sh\nexit 1'` 桩掉 nginx/systemctl，`PATH=桩目录:$PATH` 运行。
注意 `avail/` 里文件名要**去掉 .conf**（部署名是 `booking-ip-dual` 无后缀）。
