### 铁律级新发现（务必记住）
- **★两服务 jwt.secret 曾差 1 字符**（api 882 / classroom-service 883，多一个 `2`）→ 主系统 token 在课堂服务**恒 401**。`aes-key`/`hmac-key` 本来就一致。**跨服务共享密钥必须逐字节比对，不能靠"看起来一样"**。
- **★`Result.fail` 白名单吞业务码**：classroom-service 的 `ALLOWED_CODES` 只有 HTTP 码，而 `GlobalExceptionHandler` 直接下发 5 位业务码（40301/40401…）→ 在异常处理器内部抛 `IllegalStateException`（日志 `Failure in @ExceptionHandler`）→ **所有业务错误变 500**。已把 `ErrorCodes` 的 16 个业务码补进白名单（该文件不在 `check:result-contract` 扫描范围，主系统契约不受影响）。
- **★`@Slf4j` 的 `log` 会被同名局部变量遮蔽**：`ReconcileLog log = new ReconcileLog()` 导致 catch 里 `log.debug` 编译失败；局部变量改名 `row`。
- **★推送时间格式**：booking 库存 `yyyy-MM-dd HH:mm:ss`，classroom `LocalDateTime` 默认只认 ISO → 对端 400。发送侧归一 ISO + 接收侧宽松反序列化，两头都做。
- **★`sys_eclassroom_instance`/`sys_tenant_eclassroom` 在该环境根本不存在**，`classroom` 库也未建 → 课堂功能运行时完全不可用。已建（schema 脚本 + 8 张表）。
- **★`reconcile_log.event_id` 是主键**：重复投递会撞键，catch 里再 logEvent 又撞 → 500；`fail_reason` varchar(500) 装不下 SQL 异常全文。审计旁路必须容错（吞 DuplicateKey + 截断 50/500）。

## 电子课堂完备性分析（13:08 交付，静态分析基线）

产物：`doc-develop/classroom-integration/电子课堂功能完备性分析-20261028.md`

方法：eClassroom 需求 docx 提取全文（57 项 F1-F8，43 P0）→ 逐条对照 `api/classroom-service` 82 个 Java 文件 + booking-api 9 个课堂类 + 前端 7 个 classroom js + nginx/DDL。

结论：接口壳全铺满（设计 17 端点全覆盖 + 7 补充 = 24），实现深度不足。57 项中 ✅5 / 🟡18 / 🧱2 / ⬜32，P0 完全实现 11.6%。整体处 M1 尾 / M2 早期。

六大根因（后续修复抓手）：
1. 闭环未接线——13 个关键方法零调用者（sendAttendanceCallback/sendAlert/sendReconcileReport/startRecording/stopRecording/appendEvent/saveWhiteboardSnapshot/createRoom/generateJoinToken/destroyRoom/handleDiff/timeout/isOnline）。
2. 多租户断裂——`ScheduleEventConsumer:87` 写死 tenantId=0L，payload 无 tenantId → 租户管理员 monitor 恒空；课堂归属零校验。
3. 鉴权三缺口——`/api/v1/schedules/events` 在 WebMvcConfig 白名单（无 JWT 无 HMAC，可伪造事件）；课堂接口无 assertMember（`enter` 还会给非名单用户插 membership）；WS 无 HandshakeInterceptor + WhiteboardHandler/SignalHandler 全局 sessions 广播（跨课堂串台）。`HeartbeatHandler:52` 取 parts[4]="heartbeat" 而非 scheduleId。
4. 有效时长算法错——`AttendanceService:59-60` 单段 checkIn→checkOut 取 max：离线时长被计入、未扣 60s 抖动、未封顶 duration（账务风险）。
5. 文件/媒体全桩——OssClient 四方法 + MediaService 三方法 stub；录制零调用，F6 全空。
6. 定时驱动缺失——@EnableScheduling 只挂 2 个空任务；缺就绪/自动开课/自动下课/掉线扫描/点名超时/教师掉线结课/清理 共 7 个扫描器。

另记两条部署地雷：
- `sys_eclassroom_instance.api_base_path` 默认 `/api/v1/classroom` → 推送 URL 变 `/api/v1/classroom/schedules/events`（真实路由 `/api/v1/schedules/events`）404；且前端拿到非空 apiBaseUrl 后拼出 `/api/v1/classroom/classrooms/{sid}/enter` 404 →「绑定租户=课堂页全挂」。
- nginx `location /api/v1/classrooms/ → 8092` 与 booking-api 回调端点同前缀 → 回调走公网域名必 404（现仅靠直连 8081 侥幸可用）。

另：两侧 AttendanceCallbackReq 字段集完全不同（courseId/classroomId、actualStart/startTime、attendanceStatus/status…），且 booking 侧 `verifySignature` 反序列化再序列化后比对 → 必然 403。

改动：有效时长改**在线区间累加**（新表 `classroom_presence_segment`，间隙≤60s 视为抖动重连计入、封顶 `classroom.duration`，向下取整）；课堂创建**初始化出勤名单 ABSENT**；`endClass` 接**五步收尾**（闭合区间/重算时长/归一名单/置离线/回流），`ClassroomClosingService` + TransactionTemplate 显式事务，**回调必须在提交后发**；`consumption_version` 每次收尾 +1；排期事件**透传 tenantId**（消费端不再写死 0L）。

★★ 三个只有跑起来才暴露的缺陷：
1. **`AttendanceMapper`/`MembershipMapper` 的 `updateById` 从未存在**：两表是 `(schedule_id,user_id)` 复合主键、实体无 `@TableId`，MP 不生成该方法 → `Invalid bound statement`。`insert` 正常、只有更新炸，表现是「/end 返回 200、状态已 CLOSED、出勤一条没更新」的**半失败**。已加显式 `updateByKey`（顺带解决 join 重入清 `leave_time` 时 MP 忽略 null 的问题）。其余 10 实体都有 @TableId，已核对。
2. **预置 ABSENT 反而造成全员缺席**：`checkIn` 只有 null/LEFT 两分支，ABSENT 不命中 → 状态永远停缺席。已补 ABSENT→PRESENT/LATE 升级分支（我自己造的回归，靠 S7 用例抓出）。
3. **`TenantEclassroomService` 课堂开关有 5 分钟内存缓存**：给租户开通课堂后最坏等 5 分钟或重启 classroom-service 才生效（联调时被这个坑过）。

实测判据：10:00-10:20 + 11:00-11:30 课时60 → **50**（旧算法 90）；+30s 抖动重连 → 50；在线60课时30 → 30；未闭合段 → 按下课时间闭合得 10。
