## 10:20 修复登录与 refreshToken 机制的两个问题

### 问题 1（P0 安全）：verifyAccessToken 不校验 token 类型
- **位置**：`api/src/main/java/com/reservation/utils/JwtUtil.java:225`
- **根因**：`verifyAccessToken` 只调 `parseClaimsJws` 验签+过期，不读 `type` claim。refresh token（HS256）与 access token（HS512）共用同一把 signingKey，能通过签名验证。此前靠 refresh token 无 role claim → `getRoleFromToken` 返回 null → 过滤器不设 SecurityContext "碰巧"防住。一旦 refresh token 加了 role claim，防线立即失效。
- **修复**：`verifyAccessToken` 解析出 Claims 后校验 `type == null || "access".equals(type)`。老 token（无 type）兼容放行；新 token 必须是 access。
- **调用方确认**：4 处（JwtAuthenticationFilter、MessageNotifyService:462、UserService:1434/1465）都是校验 access token，改动安全。
- **实测**：
  - access token → /user/self：200 ✅
  - refresh token → /user/self：401 ✅（修复后显式拒绝，不再靠 role=null 碰巧）
  - refresh token → /auth/refreshToken：200 ✅（正常刷新）
  - access token → /auth/refreshToken：401 ✅（access 不能冒充 refresh）
  - 双向对称防御已到位。

### 问题 2（P1 功能 bug）：前端 isNetworkError 误判冻结用户为网络故障
- **位置**：`frontend/js/public/utility_request.js:475`
- **根因**：原判据 `!refreshErr.response && !refreshErr.message.includes('刷新')`。`getNewToken` 手动 `throw new Error(message)` 产生的 Error 无 `.response` 属性；后端冻结用户返回 401 + "账号已被冻结"（不含"刷新"二字）→ 被误判为网络故障 → 不清登录态、不跳登录页，用户卡在"网络异常"提示。
- **修复**：判据改为基于 axios error code：`refreshErr && typeof refreshErr === 'object' && !refreshErr.response && (refreshErr.code === 'ECONNABORTED' || refreshErr.code === 'ERR_NETWORK')`。
  - 手动 throw 的 Error（无 .code）→ 凭证失效 ✅
  - HTTP 4xx（有 .response）→ 凭证失效 ✅
  - 超时（code=ECONNABORTED）→ 网络故障 ✅
  - 断网（code=ERR_NETWORK）→ 网络故障 ✅
- **小程序不受影响**：`miniprogram/core/request.js` 没有这个判断，直接 catch → clearSession → onAuthFail。
- **验证**：8 个测试用例全部行为正确（null 返回 falsy 等价 false，功能无误）。
