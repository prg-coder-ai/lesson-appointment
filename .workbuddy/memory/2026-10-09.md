## 回合 1：审计「通知正文按排期时区渲染」的合理性

用户问：通知正文按排期时区渲染，时间口径是否合理。**只分析，未改代码。**

### 结论：设计意图成立，但落地只做了一半 —— 存在 P0 缺陷

**核心事实（证据）**：
- 候补递补 `notifyWaitlistPromoted` → `firstAppointmentText` → `utcToUserZone(appt, scheduleZone)`：**已转**（MessageNotifyService.java:303-320）。
- 上课提醒 `NotifyDispatchService.pushToRecipients:355-357`：
  `LocalDateTime lesson = appointment.getAppointmentDatetime();`（已是 UTC）
  `String lessonAtText = lesson.format(TIME_FMT);` → **裸 UTC 直接格式化，未转任何时区**。
  经 `notifyLessonReminder` 直接进模板 `{lessonAt}`。
- 影响面：上课提醒是 4 档位 × 每分钟轮询的高频通知（候补递补是低频单次），
  排期 Asia/Shanghai 21:00 → 课次存 UTC 13:00 → 提醒正文写「（2026-10-09 13:00）」，用户实际晚上 9 点上课。**必然发生，非理论问题**。

**排期时区 vs 阅读者时区，语义上排期时区是对的**：
1. 通知正文是 msg_message 里的**字符串快照**，发出即固化，不可重渲染 → 渲染时区必须在**发送时刻**定，不能留到阅读时刻。
2. 排期时区是「这节课约定在哪发生」，语义稳定。
3. 「拿不到阅读者时区」的真正根因：**user 表没有 time_zone 列**（只有 language_level/language_type，已核 DDL）。不是设计上不能，是数据缺失。

**三个真漏洞**：
- P0 上课提醒未转（口径分裂，同一系统两种时区口径）。
- P1 `resolveScheduleZone` 返回 null → `safeZone` 降级 UTC → 正文写 UTC 数字且**无时区标注**，用户无从察觉；比「像 firstLesson 那样整句省略」更危险。
- P1 正文无时区标识：跨时区排期（America/Edmonton + 国内学生）用户会把 21:00 误读成本地时间。
- P2 `course_schedule.time_zone` 是可编辑字段（管理员可改），拿它当「事件固有属性」有轻微风险；且它只是当前值，不是发出时的历史快照。

### 备选方案（已摆出，待用户拍板）
- A. 只补上课提醒的转换，两条通知口径统一（改动最小，与现有实现并行）。
- B. 统一走「排期时区渲染 + 正文带时区标注」，并在查不到时区时整句省略。
- C. 根上解决：user 表加 time_zone，通知按收件人时区逐人渲染（改动最大，但语义最正确；逐人推送已支持）。

未执行任何代码修改。

## 回合 2：「消息管理」页面显示"消息管理模块未加载（admin-messageManage.js）"

### 根因：跨脚本全局标识符冲突（不是文件缺失/404/语法写错）

`admin.html` 先加载 `js/public/termsFunction.js:10` →顶层 **`const EP`**；
后加载 `js/admin-messageManage.js:20` → 顶层 **`var EP`**。
ES 规范：全局词法绑定（const/let）**不可被 var 重新声明** → 后者**整个脚本在解析阶段抛
SyntaxError**，一个函数都不注册，`window.renderMessageManagePage` 恒为 undefined。

同样的冲突还有 `js/admin-messageCategory.js:20`（所以"消息分类"页也一并坏了）。

### 为什么难定位（下次遇到同类先查这四点）
1. 控制台报错指向 `admin-messageManage.js:1`，真因在**另一个文件**的第 10 行。
2. 文件在、`node --check` 过、`script` 标签在、dist 产物在 —— 常规四查全绿。
3. 页面兜底文案主动伪装成「模块未加载」，把人引向"文件/路径/部署"方向。
4. 其余菜单全好，只有这一个坏 → 局部故障更难联想到**全局作用域**。

### 修法
- `admin-messageManage.js` / `admin-messageCategory.js` 整体包 `(function(){ 'use strict'; ... })()`，
  函数体统一缩进 4 空格，对外入口显式挂 `window`。
  - messageManage挂 `renderMessageManagePage`
  - messageCategory 挂 `renderMessageCategoryPage` + **4 个内联 onclick 所需**的
    `openMsgCatEditor` / `closeMsgCatEditor` / `saveMsgCat` / `deleteMsgCat`
    （写在 HTML 字符串里的 onclick 只能走全局作用域，漏挂= 按钮全哑）
- ⚠️ **只加 IIFE 不缩进等于没加**：守卫按"缩进 0 = 顶层"判据，不缩进照样红。

### 顺带查出的第二类问题（更隐蔽，浏览器不报错）
`admin-dataMaintainPage.js` 的 `localsearchCourse` / `resetCourseFilter` **在本文件内从未被调用**
（死代码），却因后加载**静默覆盖**了 `admin-course.js` 的同名函数 → 课程管理页的
「搜索/重置」实际调到数据维护页的取数函数。已删除并在原地留注释说明。
**同名顶层 function 浏览器不报 SyntaxError，只是覆盖 —— 比语法错更难查。**

### 新增守卫（第七道）
`tools/check-global-collide.mjs`（`check:global-collide`，已进 pre-commit，跳过 `SKIP_GLOBAL_COLLIDE=1`）
按**页面**（不是文件）聚合，因为冲突只在同页同时加载时成立。判据只看**顶层**（缩进 0）：
- 情况①  两处 `const/let` 同名 → 解析期SyntaxError
- 情况②  `const/let` 被 `var/function` 撞 → 解析期 SyntaxError
- 情况③  两个顶层 `function` 同名 → **不报错，静默覆盖**
豁免：行尾 `// global-collision: allow <理由>`。
排除：`js/shared-domain-bridge.js`（生成镜像，整体已在 IIFE 内，"顶层"判据对它无意义，
  否则会把内联权威源与手写脚本的正常重名全报出来 —— 加这条排除时误报了几十条）。

`tests/check_global_collide_guard.js` **18/18**，其中③是"缩进进 IIFE 后必须转绿"的反向对照，
证明判据确实是顶层而非"文件内出现"。

### 过程中自己踩的三个坑（都写进注释了）
1. **守卫成功路径没写`process.exit(0)`** → 反向测试拿到的 `exit=null` 全判红。守卫必须**每条路径**都 exit。
2. **`if (lexical.size === 0) continue` 让情况③变成死检查** —— 纯 function 的页面不需要任何 const/let，
   这行early-return 直接把情况③跳过。反向测试用只含 function 的探针页打它才暴露。
   **这正是"死检查与真检查输出长得一样"的典型**：初版守卫全绿，但情况③ 从未执行过。
3. **反向测试断言 ⑥ 位置写错** —— 写在`finally` 删除探针之前，探针还在当然判红。还原必须先删再断言。

### 验收
- `node frontend/build.js` EXIT=0；dist 产物 `!function(){` 包裹已生效
- VM 实测（dist 生产产物，两个页面）：**零语法/声明冲突错误**，6 个入口全部注册，
  真实调用 `renderMessageManagePage()` →渲染 1477 字符成功
- 七道守卫全绿：authz / cascade / ddl-align / tz / endpoints / shared-sync / **global-collide**

## 本机（Windows+Git Bash）完成服务器侧运维三项的等价做法

## 根因 D 修复：密钥 env 注入通道打通（第十一道守卫）

### 用户纠正（重要判据）
`123456` 是测试库口令，**不构成密钥泄露**。仓库已跟踪文件里 108 处出现（含 `spring.datasource.password`、清理脚本、`UserService` 默认口令、几十份文档），部署时被覆盖。此前把它称作"真实泄漏风险"是**定性错误**。区分标准：**测试口令≠密钥**；真问题是jwt.secret / aes-key / hmac-key / 微信 secret —— 前者只能连测试库，后者能伪造 Token / 解密字段。

### 真正的根因：env 模板写了，代码没读
- `api/beforeRun/booking.env.template:19` 早就有 `JWT_SECRET=` 占位，但 `application.properties:102` 是**裸明文字面量** → systemd 注入的环境变量**根本没被读**，实际生效的是那串明文。这层断线不报错不告警。
- 改法（双层，不破坏现有部署）：`jwt.secret=${JWT_SECRET:<原明文兜底>}`，共 8 处（api 4 + msg 3 + …），兜底值逐字保留（882 字符核对一致）。

### ⚠️ 实测才敢写下的 Spring 占位符规则（spring-core 6.1.14 对照实验）
用 `SystemEnvironmentPropertySource` + `StandardEnvironment` 跑真实链路：
| 环境变量 | getProperty | 结果 |
|---|---|---|
| `JWT_SECRET` | `jwt.secret` | ✅ V1 生效 |
| `AES_KEY` | `crypto.aes-key` | ❌ **null 不生效** |
| `crypto.aes-key` | `crypto.aes-key` | ✅ V4 |
**只有与属性名"词根一致"的环境变量名才会被命中**。`crypto.aes-key` 词根是 crypto，前缀 `AES_KEY`/`CRYPTO_AESKEY` 都匹配不上 —— **用短名等于没注入且不报错**。（"`${}` 不做松散绑定"的说法不够准确：jwt.secret↔JWT_SECRET 这种能中，差别在词根而非下划线规则。）
- 因此把模板里 `CRYPTO_AESKEY/CRYPTO_HMACKEY` **改名**为 `AES_KEY/HMAC_KEY`（与 properties 对齐）。

### 模板本身也不能带真值
`booking/message.env.template` 里原本有 `JWT_SECRET`/`DB_PASSWORD`/`AES_KEY`/`HMAC_KEY` 真实值 → 模板被复制/改名就连带入库。全部改 `CHANGE_ME`。另补 `WECHAT_APPID/SECRET` 占位（登录已屏蔽）。

### 守卫 tools/check-secret-env-guard.mjs（npm `check:secret-env`，pre-commit 第 11 条，`SKIP_SECRET_ENV=1`）
四条判定，全部反向验证会红：① 必走 `${ENV:兜底}` ② 兜底非空 ③ **逐个模板**校验同名占位（合并变量集会假绿——实测变异"只改 booking 模板名"因 message 模板仍对而被掩盖，已修为 tplScope 数组 + 按模板建集合）④ 模板不得带真值。

### `code=null` 为何是真 bug（不只是不优雅）
`application.properties:34` 有 `default-property-inclusion=non_null` → `code=null` 时 **整个 code 字段从 JSON 消失**，响应只剩 `{"message":"..."}`。客户端 `shared/apiPaths.js unwrapResult()` 判`res.code === 200` 才return data，else抛错 → **功能上碰巧不出错**，但 `err.code=undefined`、按 code 聚合的日志/监控全失效。`fail(0)` 那 5 处更隐蔽：0 不是 null 会正常输出，但既非成功码也非标准错误码。

### 修订后的执行顺序（两条硬依赖，不可并行/颠倒）
```
28-b（Result.code: Integer→int）  ← 地基，必须最先
  ├─▶ 28-a 修 10 处 │ 29-b 统一 HTTP 出口 │ 28-d 删 non_null
26-a（先定死"UTC ISO 带 Z"契约）← 必须先于 26-b/26-c
  ├─▶ 26-b 消灭裸 new ObjectMapper ─▶ 26-c 补全局 Jackson
25独立可并行
```
- `28-b → 29-b`：HTTP 出口要靠 primitive code 判定。
- `26-a → 26-c`：不先定契约就改序列化配置，可能产出前端无法解析的形态。

### `Result.code` 改 int 的连带风险 —— 实测为零
全仓 `getCode()` 命中项**全属别的类**（`IndustryController` 行业编码 String、`authController` 微信 code、`MessageBizException` 已是 int）。`Result.getCode()` **零处被读取**，零处 `getCode()==null` 判断；`Result` 无 XML 映射。→ 建议**直接采用根本修法**，让 `fail(null)/fail(0)` 变成编译期不可能，而非靠守卫盯。

### 其他关键判断
- **状态契约形态选"双源 + 守卫"**，不选 JSON→代码生成（会引入"改了 JSON 忘重新生成"的新漂移面，与本项目"守卫优先"取向不符）；文案改为**登记式守卫**（差异必须在契约 JSON 登记，新增差异未登记即红），既守住一致性又不推翻已拍板的跨端差异。
- **`default-property-inclusion=non_null` 必须删**（28-d）：留着的话未来任何新增可空字段都会重演"字段凭空消失"。前端 `unwrapResult`已有 `res.message || res.msg`兜底，不依赖该配置。
- 本批**明确排除**：Flyway、全仓 Date 一次改完（分P0/P1/P2 三批）、逐个 Controller 改 HTTP 状态、合并 Web/小程序文案、代码生成。
- 每条动作均配可反向验证的守卫（沿用既有做法："改了但不证明=没改"）：`check:status-contract` / `check:date-contract` / `check:result-contract`，跳过后缀 `SKIP_STATUS_CONTRACT / SKIP_DATE_CONTRACT / SKIP_RESULT_CONTRACT`。
