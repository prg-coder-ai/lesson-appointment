## 教师职业信息图形文件「不显示/不存储」代码缺陷分析（22:40）

- **结论**：教师照片与证书图形走的是 **Base64 存储模式**（前端 `teacherInfo-edit.js` 的 `compressImage`+`handlePhotoSelect`/`handleCertPhotoSelect` 把图压成 dataURL 存隐藏域，`saveForm` 发 `personalPhotoBase64`/`certBase64`），但后端这两条列被设计成「只写不读」，导致 **base64 图保存后立刻不显示、且编辑保存即丢失**。URL 模式（`personalPhotoUrl`/`certUrl`）才是唯一能跑通的路径。
- **根因 A（不显示，100%）**：`TeacherProfessional.personalPhotoBase64` 与 `TeacherCertificate.certBase64` 均 `@TableField(select=false)`；`queryTeacherProfessionalInfo` 用 `selectById` 加载主表不拉 base64；`TeacherCertificateMapper.listByTeacherId` 手写 `@Select` **显式排除 `cert_base64`**；列表 `listByConditionPage` 只用 `personal_photo_url`/`first_certificate_url` 子查询。故 detail/list/edit 回填/publish 全部拿不到 base64 → 前端 `fillEditForm`/`teacherInfo-publish.js:334/364` 优先读 base64 永远走不到。
- **根因 B（不存储/丢失，证书 100%、主照片大概率）**：`updateTeacherProfessionalInfo` 先 `certMapper.deleteByTeacherId`（service:142）再 `saveCertificates`（:143）；而 `saveCertificates` 里的「旧 base64 合并」要查已被删除的行 → `oldBase64Map` 恒空；前端 `renderCertRow` 把 detail 的 `certBase64`(null) 写隐藏域，`saveForm` 发 null → 每次编辑证书 base64 被清空。主照片 `personalPhotoBase64` 更无 merge 逻辑，`fillEditForm` 填成 `''`、`saveForm` 发 null，`updateById` 默认把该列写 null。
- **设计层**：双模式（URL+base64）并存，但 base64 被 `select=false` 矫枉过正成只写不可见字段；列表缩略图/详情/发布页全依赖 URL。注释动机是「避免 16MB base64 拉爆查询」，但解法把 base64 彻底屏蔽。
- **修复方向（待用户确认再落地）**：① 单条详情单独显式补查 base64（`selectByIdWithBase64` / 证书 `listByTeacherIdWithBase64`，仅详情用，不动列表大查询）；② 修证书先删后查顺序（删前缓存旧 base64，或按 teacherId+certificateId 回填）；③ 主照片加同样保护；④ 或统一只走 URL（上传取 URL，base64 仅离线兜底）。
- 本次仅分析，未改代码（用户偏好改前先对齐根因+方案）。

## 5MB 边界核查结论（用户专项关注点）

- **DB 列不是瓶颈**：`personal_photo_base64`/`cert_base64` 均为 mediumtext（16MB），5MB 原图 base64≈6.7MB 能装下。
- **真实卡点**有二：① MySQL `max_allowed_packet` —— base64 文本长度超此值，SQL 写入/读取会被拒（"无法读取显示"的 DB 侧真根因）；② Tomcat 请求体上限/`max-swallow-size` —— 原图直传 base64 可能触发 500。
- **前端已兜底**：`compressImage` 把头像压到 300KB、证书 500KB，5MB 原图压完远小于 5MB → 正常走 base64 路径不会被 5MB 卡。
- **本次新增兜底**：① Service `checkImageBase64` 解码体积>5MB 时 `Result.fail(413)`（add/update 双校验）；② 上传端点 `uploadImage` 服务端再限 5MB（413 友好提示），容器层放 20MB 使 5~20MB 区间拿到业务拒绝而非裸 500；③ 统一 URL 上传让 DB 只存短串，彻底绕开 base64 触发 max_allowed_packet 超限丢图。
- **生产须知**：若仍走 base64 降级路径，须确保 `max_allowed_packet ≥ 7MB`（覆盖 6.7MB + 协议开销）；否则大图在 DB 侧仍可能失败。建议生产直接走 URL 上传，DB 只存短串。
