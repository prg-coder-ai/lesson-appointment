## 文档：三个密钥在前端/api/信息中心的配对关系（写入部署手册 6.2）
- 代码核对结论：
  - 前端（dist）**零密钥**：`grep` frontend 无 `JWT_SECRET`/`CRYPTO_*` 引用；前端只存 token、请求头转发，不签发/验签/加解密。
  - `JWT_SECRET` → `jwt.secret`：`JwtUtil` 按 UTF-8 字节读、长度≥64（HS512/HS256）。api 签发+校验；message-service 仅校验（共享密钥域，见 `MessageAuthInterceptor`）。**booking 与 message 必须相同**。
  - `CRYPTO_AESKEY` → `crypto.aes-key`：`CryptoUtil` Base64 解码须正好 32 字节（AES-256-GCM）。
  - `CRYPTO_HMACKEY` → `crypto.hmac-key`：32 字节 HMAC-SHA256 搜索索引。
  - AES/HMAC 两服务复制同一 `CryptoUtil`、共用 `message_center` 库，跨服务解密依赖密钥相同。
- 重要安全发现：`api/src/main/resources/application.properties` 与 `message-service/.../application.properties` **当前已明文写死且生效**三个密钥（AES/HMAC 值与用户示例一致，JWT_SECRET 两处相同）。属"已入库"，生产须用 env 覆盖并建议轮换。

- 给出两套方案：

## 排查：云服务器登录报"密码不对"（152.136.254.127:8081）
- 现象：浏览器登 `http://152.136.254.127:8081/index.html`（平台管理端统一登录入口）报"密码不对"。
- 根因（实测对比，非密钥问题）：**云服务器运行的 booking jar 是旧版本**——其 SecurityConfig 白名单未放行 `/api/v1/*`，导致所有 `/api/v1/*`（含白名单的 /api/v1/auth/login、/api/v1/tenant/name）都返回 401（被 Security EntryPoint 拦）；前端 auth.js 第153行把 401 统一提示成"账号或密码错误" → 用户看到"密码不对"。
- 对比证据：本机 8081（最新 saas 代码，PID 29480）`/api/v1/auth/login` 不存在账号返回 `{"code":404,"message":"账号不存在"}`（进业务）、`/api/v1/tenant/name` 返回 200；云服务器同样路径全 401。→ 服务器 jar 旧，代码层面无需改。
- 前端登录路径正确：auth.js `login()` 用 `/auth/login`，utility_request.js 第29-31行把裸路径拼成 `/api/v1/auth/login`，与 authController 类 `@RequestMapping("/api/v1/auth")`+`@PostMapping("/login")` 一致。
- 密码与 jwt.secret 无关：UserService.login 用 BCrypt（`passwordEncoder.matches`，267行），自包含哈希带盐，不依赖任何密钥；CryptoUtil(AES/HMAC) 只加密 phone/email/name（70-90行）。
- booking.env 三个密钥（JWT/AES/HMAC）配置错误**不会导致**登录 401：登录是无 token 请求，不经过 JWT 验签；AES 错最多让 decryptUserFields 抛异常（非"密码错误"）。属无关变量。
- 修复：用最新 saas 代码重新 `mvn package` api（先停运行中 jar 避免 target 锁），把新 `booking_api-1.0.0.jar` 上传服务器替换并 `systemctl restart booking`；验证 curl `/api/v1/auth/login` 不再 401。
