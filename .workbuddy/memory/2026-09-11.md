## 修复：消息中心「消息不存在 + 未读数不更新」（frontend 消息中心 / message-service）

- **现象**：收件箱点开消息弹「加载失败 / 消息不存在」；点「标记已读」后未读角标不变。
- **根因**：`msg_message.message_id` 是 MyBatis-Plus `ASSIGN_ID` 雪花 ID（19 位，≥2.1e18），超过 JS `Number.MAX_SAFE_INTEGER`(9007199254740991)。后端以 JSON **数字**下发 → 浏览器 `JSON.parse` 静默丢精度（`…418` → `…400`）→ 前端拿错 ID 回查/标记 → 后端 `InboxService.require()` 查不到行，抛 `MessageBizException(404,"消息不存在")`；`markRead` 在 catch 里 return，`bumpBadge/refreshBadge` 都不执行 → 未读数不动。`/messages/ids`、已发列表的 `messageId` 同样中招（全部已读、收回也失效）。
- **实测证据**（恢复 `--server.port=8097` 启动 message-service，用源 `jwt.secret` 自签 token 走真实 HTTP）：
  - 列表原始响应 `"messageId":2097477561867124738`，JS 解析后 `2097477561867124700`
  - `GET /messages/2097477561867124738` → `code:200`（正常）；`GET /messages/2097477561867124700` → `code:404 消息不存在`
  - 用错 ID 标记已读 → 404，未读数 `5 → 5` 不变；用对 ID → `5 → 4`
- **修复**：新增 `api/message-service/.../config/JacksonConfig.java` —— `Jackson2ObjectMapperBuilderCustomizer` 把 `Long`/`long` 一律序列化为字符串（`serializerByType(Long.class, ToStringSerializer.instance)`），一次性覆盖实体 / `Map<String,Object>` / `List<Long>` 所有出口。反序列化仍兼容数字与字符串（路径变量、`List<Long> messageIds` 照常绑定）。前端**无需改动**（本就以字符串拼 URL / 传 body）。
- **回归**：修复后列表 `"messageId":"2097477561867124738"`（string）→ 详情 200「续费通知」→ 标记已读 200 → 批量全已读 `未读数 4 → 0` → 按快照还原为 4，`diff` 与备份完全一致。
- **构建**：message-service 是独立 Maven 工程（不在 `api/pom.xml` 的 modules 里），用 Maven launcher JAR + **`-f "<abs>\pom.xml"`**（Bash 工具每次调用会重置 cwd，不传 `-f` 会报「no POM in this directory」）。`package -DskipTests` BUILD SUCCESS。
- **排查陷阱**：本沙箱 `curl` 完全不可用（`http_code=000`，`--noproxy '*'` 也无效），改用 Node `http` 模块探测；Node 把 `/tmp/x` 当 `C:\tmp\x`，跨工具路径要过 `cygpath -w`。

## 修复：编译报「编码 UTF-8 的不可映射字符 (0xB8)」+ 全仓编码排查

- **报错**：`api/.../mapper/UserSessionMapper.java:[18,8] 编码 UTF-8 的不可映射字符 (0xB8)`。
- **根因**：该文件**整个是 GBK** 存的（`0xB8 0xF7` = 「各」），注释里的中文全是 GBK 字节，javac 按 UTF-8 读就报错。
- **修复**：GBK → UTF-8 转码（1300 → 1366 字节，CRLF 29 个不变）；`mvn -o compile` 复验 **BUILD SUCCESS**。
- **顺带扫出第二个文件**：`frontend/js/public/termsFunction.js` **不是合法 UTF-8**——
  - 类型 A：第 17–21 行整行是 GBK（GBK 解出来完全通顺）；
  - 类型 B：另有 ~66 行是 UTF-8 但个别汉字**丢了最后一个字节**（如 `：`=EF BC 9A → 只剩 EF BC）。
  - 定损结论：258 个替换字符**全部落在注释内**，0 个在代码/字符串 → 无功能影响，但文件非法 UTF-8。
  - 损坏引入点：commit `246b7a9`（坏 238 处），`79f31ed`（涨到 382 处）；最后一次完好版本是 `e4b8bc7`。
- **修复方式**：只补注释，代码字节零改动。5 行整行 GBK 用 gb18030 还原；17 行靠「与 `e4b8bc7` 长度相等 + 片段有序唯一命中」精确还原；49 行按行号逐点补字（补字个数 == 坏点数，脚本自校验）；再润色 46 处丢字节连带丢失的空格/尖括号/引号。
- **验证**：合法 UTF-8 ✔ / `node --check` 通过 ✔ / **去注释后与修复前逐字节相等 ✔**（证明代码没被碰、行数没变 317 行）。
- **判别陷记**：判断「整行 GBK」不能用坏字节占比（短行、含大量 ASCII 的 GBK 行会漏判），也不能用「命中词典字数 - 2×坏点数」打分（会把正常中文行误转成乱码）。可用判据：`cjk(gb18030结果) > 3*cjk(UTF-8容错结果) + 2`。
- **现状**：全工作区非 UTF-8 文本文件 = **0**。
- 新建技能 `source-encoding-repair`（含三类判据、只补注释的安全策略、代码零改动的验证方法）。

## 修复：页面顶部「刷新」按钮点完内容区空白（frontend 通用刷新）
- **现象**：消息中心页内「刷新」正常；点**页面顶部**的「刷新」，中央内容区被清空后不再渲染（空白）。
- **根因**：`refreshRightPage()`（`frontend/js/public/appointmentNotes.js`）把**标题文本**当 key 传给了 `loadAdminPageContent()`：
  ```js
  loadAdminPageContent(pageTitle.textContent);   // 传的是「消息中心」
  ```
  而 `loadAdminPageContent` 只认菜单 key（`messages`/`overview`/`schedule`…），switch 落空 → 而函数开头已 `innerHTML = ''` → 内容清空且无分支渲染。**四个入口页（admin / platform_admin / student / teacher）全部中招**，不是消息中心独有。
- **修复**（符合用户要求："把本页面的刷新函数封装在通用刷新函数中"）：
  1. `appointmentNotes.js` 里 `refreshRightPage()` 升级为通用入口，三级回退：
     ① `window.pageRefreshHandlers[key]` 有注册 → 调页面自有刷新函数（保留分页/标签/搜索词）；
     ② 没注册 → `loadAdminPageContent(key)` 整页重渲染；
     ③ 最后才回退历史行为（标题文本，且加了 `typeof === 'function'` 守卫防 TypeError）。
  2. 新增 `registerPageRefresh(menuKey, fn)` 注册表 + 用 IIFE 包装各页面自己的 `loadAdminPageContent` 以记录 `window.currentMenuKey`（不改动原逻辑）。
  3. `messages-inbox.js` 新增唯一刷新函数 `refreshMessagesView()`（列出列表 + 未读角标 + 离线队列），**页内刷新按钮与顶部刷新共用它**；容器不在文档中则返回 `false` 交通用逻辑兜底。`state` 增加 `container` 字段。
- **验证**（Node `vm` + 伪 DOM/axios 接线测试，源码与压缩后 `dist` 各跑一遍）：**17 PASS / 0 FAIL**；含"顶部刷新 → 重拉列表"、"保留当前标签页（仍请求 `/messages/sent` 而非重置回 `/inbox`）"、"未走整页重渲染"、"其他菜单按 key 重渲染"、"容器卸载后兜底"、"无 loadAdminPageContent 时不抛异常"。
