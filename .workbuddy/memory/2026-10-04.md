## 云端无域名无 HTTPS 时 nginx 启动报错（00:15 排查）
- 现象：云端只有公网 IP、未配域名/HTTPS，启动 nginx 报错。
- 根因：远端启用了 `booking.conf`（含 `listen 443 ssl` + `ssl_certificate /etc/letsencrypt/live/booking.example.com/...`），证书文件不存在 → nginx 加载失败。`deploy/nginx/booking-ip.conf` 才是「纯 IP 无域名」设计的纯 HTTP 版（`listen 80 default_server; server_name _;`，已含 sensitive 分流），应改用它。
- 远端修复：只启用 booking-ip、禁用 booking.conf 与 default：
  `sudo rm -f /etc/nginx/sites-enabled/booking /etc/nginx/sites-enabled/default && sudo ln -sf /etc/nginx/sites-available/booking-ip /etc/nginx/sites-enabled/booking-ip && sudo nginx -t && sudo systemctl restart nginx`
- 部署脚本 `deploy/upload-to-server.sh` 6/6 同步修正：默认只软链 booking-ip（纯 HTTP），不再同时启用带 HTTPS 的 booking.conf；注释「有域名+证书后再手动启用 booking.conf」。`bash -n` 通过。

## 解决 default_server 冲突后仍 404 资源不存在（00:39 排查）
- 现象：删 default/booking 软链、只留 booking-ip 并 restart nginx 后，敏感词仍 `{"code":404,"message":"资源不存在"}`。
- 判据：带 `code` 字段的 404 是后端 `Result.fail` 兜底。message-service 的 GlobalExceptionHandler 中「资源不存在」(第62行) 只用于处理静态资源(favicon/robots)未找到；API 路径找不到 handler 走的是另一条「接口不存在」(第51行)。故"资源不存在"几乎必是 booking(8081) 兜底 → 请求没被转到 8090 → nginx 生效配置里 sensitive 分流没真正生效（或 8090 是老版本无 sensitive 路由）。
- 远端自证三步：`nginx -T | grep -A2 sensitive`（看线上配置有没有分流）、`curl 127.0.0.1:8090/api/v1/sensitive/groups`（看 8090 自身路由在不在，401/数据=在、资源不存在=老版本）、`curl -s -i 127.0.0.1/api/v1/sensitive/groups`（看经 nginx 实际落点）。
- 修复分两支：① nginx 配置无 sensitive → 重传最新 booking-ip.conf 并 reload；② 8090 返回资源不存在 → 远端 message-service 是老版本，需部署 message-service-1.0.1.jar（含 sensitive 路由 + 租户管理员可见性修复），走 deploy/upload-to-server.sh。
- **已闭环（01:01 用户确认）**：远端 `sites-available/booking-ip` 是旧版（不含 sensitive 分流），重传最新 `booking-ip.conf` 并 `systemctl reload nginx` 后敏感词正常。根因=部署时 conf 未同步到远端最新版，与情况 A 一致。经验：改 nginx 分流规则后，远端不仅要 reload，还要确认 `sites-available/*` 文件本身是本地最新那份（手动 scp 易漏）。
