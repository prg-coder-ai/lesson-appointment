## 云托管前端 502 根因定位（21:00-22:10）

**现象**：前端上云托管后，静态页正常、`/api/v1/*` 全 502。

**根因（确证）**：`cloudBased/frontend/Dockerfile` 的 `ARG` 默认值写的是
`http://api.329614-8-1475810246.svc.cluster.local:8081` —— **微信云托管没有这套 K8s Service DNS 记录**。

**实例 WebShell 内实测证据（决定性）**：
- `nslookup api.329614-8-1475810246.svc.cluster.local` → **NXDOMAIN**
- `nslookup api`（同命名空间短名）→ **NXDOMAIN**
- `nc -vz api.<...>.svc.cluster.local 8081` → `nc: bad address`
- `/etc/resolv.conf` **只有一行 `nameserver 127.0.0.1`**（平台本地 stub，不做服务发现）
- 对照：`nslookup api.weixin.qq.com` → 169.254.10.1（正常，说明 DNS 本身活着）
- 公网域名：`nc -vz api-329614-8-1475810246.sh.run.tcloudbase.com 443` → open（124.223.145.112），
  `wget https://.../api/v1/system/info` → **HTTP 200**

**结论口径（写进配置注释，勿再踩）**：微信云托管服务间通信只有两条路 ——
① 控制台「服务设置 → 内网访问」**分配的「内网域名」**（形如 `xxxxx.ap-shanghai.internal-run.tcloudbase.com`，
开启/重新部署才分配，随发布可能变化，必须复制不能拼）；② 公网域名 `https://<服务>-<envid>.sh.run.tcloudbase.com`。
`<服务名>.<envid>.svc.cluster.local` 与短名 `api` 一律 NXDOMAIN。

**同时确认的第二个坑（非本次 502 但会咬人）**：模板用 `set $api_upstream` + `proxy_pass $var`，
nginx 对变量形式的 proxy_pass **强制要求 resolver**，而 resolver 靠 `/docker-entrypoint.d/00-resolver.sh`

## 22:40 登录 403「Invalid CORS request」根因（★重要）

**现象**：502 解决后点登录，`POST /api/v1/auth/login` 返回 **HTTP 403**，
`response.data = 'Invalid CORS request'`（前端提示退化成「无权限访问该资源」）。

**根因（三层叠加，缺一不报）**：
1. 浏览器对**同源 POST** 也自带 `Origin: https://frontend-329614-8-1475810246.sh.run.tcloudbase.com`（规范行为，不是前端写错）；
2. nginx 模板**故意不透传 Host**（上游是云托管域名，靠 Host/SNI 路由，传 $host 会 INVALID_HOST），
   于是后端 `request.getServerName()` = `api-329614-…`；
3. Spring `CorsUtils.isCorsRequest()` 拿 Origin 与 getServerName 比 → 域名不同 → **判为跨域** →
   `DefaultCorsProcessor` 发现白名单无此源 → 403 `Invalid CORS request`。
   而 `application-cloud.properties` 的 `app.cors.allowed-origin-patterns=${APP_CORS_ORIGIN_PATTERNS:}`
   **云端默认为空**（`CorsConfig` 用 `registerCorsConfiguration("/**")`，allowCredentials=true），所以必然拒绝。

**修复（两条路，可并存）**：
- **A 立即生效、不用构建**：给 api 服务加环境变量
  `APP_CORS_ORIGIN_PATTERNS=https://frontend-329614-8-1475810246.sh.run.tcloudbase.com`，重启实例。
- **B 根治（已写进模板）**：`cloudBased/frontend/default.conf.template` 的 server 级加
  `proxy_set_header Origin "";` —— 删掉浏览器带来的 Origin，CorsUtils 判"非跨域"，直接进业务。
  语义正确（浏览器↔nginx 本就同源），且不用改 jar / 重启 api。已 grep 确认后端无任何代码读 Origin，删头安全。
  **前提：同源反代部署**；若将来前端直连后端公网域名（真跨域），须删此行改配环境变量。

**教训**：这类"同源反代 + 上游换域名"的组合，Host 与 Origin 必然不一致，CORS 判断会被误触发；
排查时看 `response.data` 的**纯文本**（不是 JSON），"Invalid CORS request" 是 Spring 的固定文案，
见到它就别再往业务/鉴权方向找。

**验证**：模板渲染断言 9 条 proxy_pass 指令（msg 5 = 4 + msg-health，api 4）、Origin 置空指令存在、
无未替换占位符、XFF 变量未被 envsubst 吃掉。

## 22:50 api 查库报 `Unsupported character encoding 'utf8mb4'`（★配置错误，非代码）

**现象**：登录已到 api，日志 `Caused by: java.sql.SQLException: Unsupported character encoding 'utf8mb4'`。
容器活着、健康检查通过，只有查库的接口挂 —— 典型的"配置错但服务看着正常"。

**根因**：`api/src/main/resources/application-cloud.properties:44` 的 JDBC URL 写了
`characterEncoding=utf8mb4`。Connector/J 的 `characterEncoding` 认的是 **Java charset 名**，
而 Java 里没有 `utf8mb4` 这个 charset（MySQL 字符集名 ≠ Java charset 名）。
本地 `application.properties` 写的是 `utf8`（Java 别名，合法）→ 所以本机从来没暴露。

**铁证（用 fat jar 里的真驱动 + 本机真库跑的）**：
把 `BOOT-INF/lib/mysql-connector-j-8.0.33.jar` 取出来跑三组连接：
- `characterEncoding=utf8mb4` → `UnsupportedEncodingException: utf8mb4`
- `characterEncoding=UTF-8`   → 连接成功，MySQL 8.4.11
- `characterEncoding=utf8`    → 连接成功，MySQL 8.4.11
另：`Charset.isSupported("utf8mb4")==false`，`"utf8"`/`"UTF-8"` 均 true。

**修复（4 处，全部改成 `characterEncoding=UTF-8`）**：
`api/src/main/resources/application-cloud.properties`（唯一进 jar 的）、
`cloudBased/api/application-cloud.properties`、`cloudBased/message-service/application-cloud.properties`（两份副本，防后续误用）、
`doc-develop/A00微信云托管部署操作手册-预约系统-2026-10-14.md`（示例 + 踩坑说明）。

**注意**：① 必须 **mvn package 重新打包**（compile 不换 jar 里的 resources），
现有 `cloudBased/api/booking-api-2.2.0.jar`（11-07 23:05）实测内嵌值仍是 `utf8mb4`；
② message-service 源里**没有** cloud profile 文件（走 application.properties 的 `utf8`），不受影响；
③ 应急可给 api 配 `SPRING_DATASOURCE_URL`，但值里的 `${MYSQL_*}` 不会展开，必须填真值。

### 四、定案架构（现在的形态，勿再退回旧写法）

```
浏览器 ──https──> frontend(nginx:alpine, listen 8080)
                     │  启动: 00-resolver.sh 读环境变量 → 渲染 /opt/nginx/default.conf.template
                     │        → 生成 resolver → nginx -t → 回显生效上游
                     ├─ /api/v1/{message,sse,sensitive,users/} ─> $MSG_UPSTREAM
                     └─ 其余 /api/v1/* ─────────────────────> $API_UPSTREAM
```

- `cloudBased/frontend/` 只剩 4 份：`Dockerfile` / `container.config.json` / `default.conf.template` / `resolver-entrypoint.sh`（`nginx/`、`docker-entrypoint.d/`、`deploy/nginx/cloudbase-web/` 三套遗留已删除）。

- 上游**不进镜像**：`docker build` 不再传 `--build-arg`，改控制台环境变量 `API_UPSTREAM` / `MSG_UPSTREAM`（内网带端口 8081/8090 且是 http；公网则 https 不带端口）。

### 五、教训清单（换环境 / 下次部署先按这个顺序自查）

1. **不要在云托管里用 K8s 服务发现**：`<服务名>.<envid>.svc.cluster.local` 与短名一律 NXDOMAIN，只有控制台分配的「内网域名」或公网域名。
2. **变量形式 `proxy_pass` 必须有 `resolver`**：缺失即每请求 502（`no resolver defined`），而 `nginx -t` **查不出来**（请求期行为）。所以启动脚本取不到 nameserver 必须 `exit 1`。
3. **同源反代换上游域名 → 必然触发 CORS 误判**：删 `Origin` 或配 `APP_CORS_ORIGIN_PATTERNS`，二选一。
4. **`characterEncoding` 写 Java 名字**（`UTF-8`），不是 MySQL 字符集名（`utf8mb4`）。
5. **"失败要可见"**：宁可容器起不来（日志有中文原因），也不要「Running 但全站 502」——后者是本次排查耗时最长的形态。
6. **`git log -S` 比读代码更快**：`-S "RollingFileAppender"` 一步定位到是谁、哪次提交删了日志，比翻文件靠谱。
7. **标题写"调整，无效"的提交也会顺手删掉别的功能**：`7ab34fa0` 只改 logback，看起来与部署无关，实际制造了一个隔天才被发现的哑故障（11-07 15:47 删 → 11-08 23:31 才发现）。提交前 diff 要过一遍。

## 23:55 修复日志页 404：4 处路径补 `/v1`

**根因**：`frontend/js/logBrowser.js` 请求 `/api/logs/{tail,date,search,dates}`，后端 `logController`
是 `@RequestMapping("/api/v1/logs")`，四条 `@GetMapping` 都在 `/api/v1` 下；nginx 只有 `location /api/v1/`。
`/api/logs/...` → 落到 `location /`（root + try_files）→ 404。

关键机制（很多人会误以为 request 会自动补前缀）：`utility_request.js:384` 的 `service` 虽然设了
`baseURL: API_BASE_URL`，但**文件第 27 行注释已写明：axios 对以 `/` 开头的 url 会忽略 baseURL**。
所以写 `/api/logs/x` 就是原样发出，永远不会变成 `/api/v1/logs/x`。

**改动**（3 个源文件）
- `frontend/js/logBrowser.js`：4 处 `api/logs` → `api/v1/logs`（dates / date / tail / search），
  并在 `loadDates()` 上方留了「必须带 /v1 + 为何不会自动补」的注释，防止以后又被改回去。
- `frontend/logBrowser.html`：注释纠错——原写「后端 /api/logs/* 只要求认证、不做角色鉴权」，
  实际 `AuthzRules:291-294` 已把四条登记为 `PLATFORM_OR_TENANT_ADMIN`，非管理员会 403。
- `frontend/build.js` 的 `copyAssets()`：**根治 dist 污染**（见下）。

**产物同步**

**★顺手根治：dist 每次构建都会被 6 项部署文件污染（原先靠 Dockerfile 的 rm -rf 兜底，治不了 deploy/dist 与静态托管）**

`frontend/` 源目录里有 6 项已入库的 Gen3 遗留：`Dockerfile`(5126B)、`container.config.json`、
`nginx/default.conf.template`、`docker-entrypoint.d/40-render-nginx-conf.sh`、`legal.html.orig`、`readme.md`。
`build.js` 的 `copyAssets()` 只靠一个 `SKIP_ROOT` 白名单挡构建元文件，漏洞有三处：

1. 名单里没有 `Dockerfile`、`container.config.json` → 直接复制进 dist；
2. 目录（`nginx/`、`docker-entrypoint.d/`）根本没参与判断，`path.dirname(rel) === '.'` 只匹配根级文件
   → 目录下的文件全部复制；
3. **大小写坑**：名单写的是 `'README.md'`，实际文件名是 `readme.md`，`Set.has()` 区分大小写 → 从未生效。

修法（不动入库文件，只改构建规则）：
- `SKIP_ROOT` 补 `Dockerfile`、`container.config.json`、`readme.md`；
- 新增 `SKIP_ROOT_DIRS = {nginx, docker-entrypoint.d}`，按 `rel.split(/[\\/]/)[0]` 判顶层目录整体跳过；
- 新增 `/\.orig$/i` 排除备份文件。
`copyAssets()` 的注释里写清了这三条，避免以后被"整理"掉。

**仍存（有意保留，未动）**：`frontend/` 下那 6 项 Gen3 部署遗留本身还在仓库里（已入库）。
只在构建层排除，等于「源文件保留、产物干净」——如果确认彻底不用，可另起一次 `git rm` 清掉
