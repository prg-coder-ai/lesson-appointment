## 11:40-12:10 排查 8080 打不开：node 前端代理假死（非页面/路由问题）+ 交付 deploy/kill-all.bat

**故障**：`https://localhost:8080/admin.html?tCode=TENANT_B` 打不开。

**排查结论**：页面和代码都没问题，是 8080 那个 node 进程（PID 7572，11:29:38 启动）**事件循环冻结**。

证据链：
- netstat 显示 `0.0.0.0:8080` / `[::]:8080` LISTENING（PID 7572 = `node doc-develop/90-tools/dev-frontend-local.js`）
- TCP 可连（18ms），但 http 与 https 请求**都** 6~12s 超时，一个字节都不回 → 连 TLS 握手都没开始
- 进程 CPU 累计仅 1.25s（运行 12 分钟）→ 不是死循环，是阻塞等待
- 主线程（CPU 1.078s）`WaitReason = Executive`、`ThreadState = Wait`
- **对照实验**：同一份脚本另起实例到 8099，`https://127.0.0.1:8099/admin.html` 立刻 200 / 45402 字节 → 排除代码、路由、tCode 参数
- 电源事件排除睡眠：`Kernel-Power 109`（11-20 23:14 进睡眠）、`172`（11-21 11:17:33），进程 11:29 启动时机器已醒

结论：卡在**向控制台同步写日志**（`listen` 回调里的 `onProbe` 一堆 console.log）。Windows 控制台"快速编辑模式"选中文本、或 Ctrl+S(XOFF)，都会让 node 的同步 stdout 写阻塞 → V8 事件循环整体停摆，表现就是"端口在听、TCP 能连、请求全挂、CPU 不动"，Ctrl+C 也常失效。

**次要发现**：`https://localhost:8099` 是 ECONNRESET，`https://127.0.0.1:8099` 才 200 —— localhost 走 IPv6 `::1` 路径，握手被重置。本地调试建议直接用 `127.0.0.1`。

**交付**：`deploy/kill-all.bat`（GBK + CRLF），终止占用 8080/8081/8090/8092 的进程。
- `kill-all.bat` 确认后杀；`/y` 直杀；`/n` 只列不杀；`/h` 帮助
- 只看 LISTENING（不碰 ESTABLISHED 对端连接）；同一 PID 双栈监听只杀一次
- 先把 netstat 落盘再用 findstr 逐端口过滤（避免嵌套管道引号转义）
- 杀前用 tasklist 打出进程名 + 二次确认；杀后复查端口，未释放则报错退出 1
- 跳过 PID 0/4

**编码约定（重要）**：`deploy/` 下 .bat 一律 **GBK + CRLF**（`build-all.bat` 早有同样约定）。本次做法：
Write 出 UTF-8 → python 校验每个字符都能 encode('gbk') → 统一转 CRLF → 写 bytes。校验项：CRLF 205、裸 LF 0、无 BOM、GBK 往返一致。
`.gitattributes` 补 `*.bat text eol=crlf`（LF 结尾时 cmd 对 `goto :label` 解析会失败且不报错）。

**踩坑记录（不要再犯）**
1. **不能从 Bash 调 cmd.exe**——被安全策略直接拒绝（"Invoking cmd.exe from Bash bypasses all command validation"）。所以 .bat 无法在此环境端到端跑，只能做静态检查 + 用真实数据模拟解析逻辑。
2. **Git Bash 的 `find` 不是 Windows 的 find.exe**。测试 `find /c /v ""`（计数行数）时，MSYS 的 find 把 `/c` 当路径，去扫描整个 `C:\`，输出 30MB 被 SIGTERM 拦截。**在 bash 里绝不能写 `find /c`**；也正因如此，kill-all.bat 的复查段改用 `findstr ... >nul` + `errorlevel` 判断有没有命中，彻底去掉对 find.exe 的依赖。
3. 验证解析逻辑的正确姿势：用 python 起一个 GBK 样本文件（含 `0.0.0.0:8080`、`[::]:8080`、**`0.0.0.0:80810`**、一条 ESTABLISHED），再用真实 `findstr '/c::8080 '` 过滤 —— 实测 80810 不误匹配（尾空格起作用），ESTABLISHED 那一行被前一步 `findstr LISTENING` 挡掉。

## 12:09-12:20 kill-all.bat 从 GBK 改为 UTF-8 无 BOM + chcp 65001（修预览/编辑器乱码）

用户反馈预览面板里全是乱码。原因：上一轮按 `build-all.bat` 的老约定存成 **GBK**，而
WorkBuddy 预览、VS Code、Git 网页端一律按 UTF-8 解码 → 中文全成方块/问号。

**定案：与 `deploy/local/*.cmd` 一致的写法**（那两个文件早就是 UTF-8 无 BOM + 第 2 行
`chcp 65001 >nul`，是仓库里已验证可用的范式）：
```
@echo off
chcp 65001 >nul 2>&1
```
- UTF-8 **无 BOM**：有 BOM 会让首行 `@echo off` 被读成乱命令（报 "'∩╗┐@echo' 不是内部或外部命令"）。
- 第 2 行 `chcp 65001`：cmd 按当前代码页解析 bat 文本，切到 65001 后 UTF-8 中文才正常显示。
  因为 cmd 是**逐行读取执行**的，chcp 之后的行才生效，所以它必须紧跟 `@echo off`。
- CRLF 保持（`*.bat text eol=crlf` 已在 .gitattributes）。

**关键论证：chcp 65001 不会破坏脚本的 PID 解析**（这是改编码前必须先想清的）
脚本流程是 `netstat -ano -p TCP | findstr "LISTENING" > %TMPF%` 再用 `for /f "tokens=5"` 取 PID。
实测本机 netstat 原始输出 6766 字节里 32 个非 ASCII（中文表头「活动连接/协议/本地地址」），
但 46 条 LISTENING 行**全 ASCII** → 落盘文件纯 ASCII，与代码页完全无关。
`tasklist /fo csv` 取进程名那步在 65001 下也正常；即使取不到，`PNAME` 回落到 `?`，不影响终止逻辑。

**顺带清理**
- 注释里过时的「本文件以 GBK 保存，不要改为 UTF-8」→ 改写为三条编码铁律（无 BOM / CRLF / 保留 chcp）。
- 两条展示用 `echo` 里的 ASCII 双引号（`"假死"`、`"快速编辑模式"`）换成中文引号 ——
  `echo` 会把 ASCII 引号吞掉，屏幕上显示成「再次端口在听」（少一对引号）。
  `findstr /c:"%~nx0"` 两处引号是语法，必须保留。
- 注释里原来写 `goto :label` 举例，被正则扫成「缺失标签」→ 改成「goto 跳转标签」。

**校验**：UTF-8 解码 OK / GBK 解码失败（证明真的是 UTF-8）/ 无 BOM / CRLF 211 条、裸 LF 0 /
5 个标签与 5 个 goto 目标完全对上 / 括号净差 0 / 212 行。
`deploy/.gitattributes` 的注释同步更新，写明三个 bat 各自编码，且 git 不做工作区编码转换。

**未动**：`build-all.bat`(11605B)、`run-all.bat`(7027B) 仍是 GBK —— 用户只要求改 kill-all.bat。
它们在同一预览面板里同样会乱码，若需要可按同一套路批量转（加 chcp 行 + 转 UTF-8）。

**★ 核心结论：不要照抄云托管那份模板。**它用 `set $up "${API_UPSTREAM}"; proxy_pass $up;`
变量形式 → 强制需要 resolver（缺了每请求 502 且 nginx -t 查不出），云托管为此专门写了

既保留换环境只改 env 的能力，又不引 resolver 依赖。

**写配置时确认/纠正的三件事**
1. **`^~` 的作用范围**：只有「它就是最长前缀匹配」时才压住正则。所以兜底那条
   `^~ /api/v1/` **救不了** `location /api/v1/files/` 漏写 `^~` —— 更长的普通前缀赢过更短的 `^~`，
   仍会试正则 → `/api/v1/files/x.mp4` 返回 404+HTML。我第一版模拟器实现错了（写成"先找 ^~ 最长"），
   改回 nginx 真实语义（`ngx_http_core_find_location`：前缀取最长那个，若它是 ^~ 则不试正则）后才对上。
2. **`X-Forwarded-Proto` 不能写 `$scheme`**：容器是第二层反代，$scheme 永远是 http，会把
   宿主机传来的 https 覆盖掉 → Spring 生成的绝对链接退回 http → https 下登录跳转白屏，
   而 nginx 日志全 200。用 map（`00-proxy-map.conf`，必须在 conf.d 即 http{} 上下文）：
   有 `$http_x_forwarded_proto` 就用它，没有才回落 $scheme。
3. **`app-config.json` 挂目录不挂单文件**：单文件挂载时宿主机路径不存在，docker 会建**同名目录**顶上，
   请求它 403 且报错只说 permission denied。改挂 `/app-config` 目录，entrypoint 判断有就拷进站点根。

## 14:48-15:00 排查生产 reload 报 `zero size shared memory zone "api_zone"`

现象：`systemctl reload nginx` → 先 `syntax is ok`，再 `[emerg] zero size shared memory zone "api_zone"`。

**两个阶段的区别是本条的关键**：syntax ok 只说明指令名/括号/上下文合法；emerg 发生在
`ngx_init_cycle` 的**共享内存 zone 分配**阶段。字面含义 = **有地方引用了 api_zone，
但整个配置里没有任何 `limit_req_zone` 给它尺寸**（引用先以 size=0 登记，没有定义来补尺寸）。

**为什么比 unknown 难查**：这条**不带文件名行号**（解析期的位置信息在 init_cycle 阶段已丢），
而且前面那句 "syntax is ok" 会被误读成「配置没问题」。而同因的另一种报错
`unknown limit_req_zone "api_zone"` 是带 `文件:行号` 的。两者都指向同一件事：
**定义那一半没生效**。

仓库侧核查：`api_zone:20m` 定义在 `deploy/nginx/conf.d/00-limit-req-zone.conf`（正确），
引用在 `booking.conf` 5 处 + `booking-ip.conf` 3 处（api_zone），另有 login_zone / public_zone。
所以仓库没问题 —— 是服务器上丢了定义或丢了 include。

**成对部署的四个失效路径**（写进诊断脚本结论）：conf.d 文件被删/改名成 .bak（`*.conf` 通配扫不到）/
内容被清空/`nginx.conf` 的 `include conf.d/*.conf` 被包管理器升级覆盖/手工只 scp 了 sites 那份。

**两个必须讲清的运维事实**：
- `reload` 失败**不会**停掉在跑的 nginx（旧 worker 继续服务），线上没挂 —— 但**改动也没生效**。
- 千万别改用 `restart` 试：reload 失败只是没生效，restart 失败是整站没了。

**新增 `deploy/nginx/diagnose-limit-zones.sh`**（只读，7 节）：环境 → nginx -t 全文 →
include 是否生效 → zone 定义表 → 引用表 → **交叉比对找孤儿引用**（含逐条修法）→ 尺寸合法性 →
`nginx -T` 看生效配置里各 zone 的定义条数。已用两套构造数据验证：正常配置报"无孤儿"，
把 conf.d 清空后精确报出 `zone「api_zone」被引用但没有尺寸定义` 并打印引用位置。
（`NGX_DIR` / `NGX_CONF` 可覆盖，便于脱离 /etc/nginx 自测；跑通需 root，自测时用 sed 旁路。）

**顺带修正两处与事实不符的注释**（原来只写了 unknown，没写 zero size）：
`deploy/nginx/conf.d/00-limit-req-zone.conf` 的 ⚠ 段（补两种报错文本 + 为何 zero size 难查）、
`deploy/upload-to-server.sh` 第 97 行注释。

## 15:30-16:05 给云托管前端代理补 classroom：三层改动 + 一个真缺陷

用户要求「给 dev-frontend-remote-tcb.js 补充 classroom 相关内容」。查下来这不是改一个文件的事 ——
薄封装只设了 API_URL / MSG_URL 两个地址，而它依赖的 `dev-frontend-remote.js` 压根没解析课堂，
底层 `dev-proxy.js` 还有一处硬缺陷。

**★ 挖到的真缺陷（比"补个变量"重要得多）**
`dev-proxy.js` 的 WS 升级注册条件是 `if (classroomTarget && classroomTarget.protocol === 'http')`。
而云托管里 classroom-service 是 **https/wss** → 这个 upgrade handler **根本没注册** →
课堂的信令/白板/心跳三条 WS 通道一条都连不上，但 HTTP 接口（进入课堂、成员列表）完全正常。
表现是「课堂页一直重连中 / 在线人数恒为 0」，极容易被判成前端信令写错了。
修法：条件改成 `if (classroomTarget)`，内部按 protocol 分派 —— https 用 `tls.connect` 且
**显式带 servername（SNI）**（云托管按 SNI 选证书，缺了握手失败而 Node 只报 ECONNRESET）；
另补 `socket.on('close', () => upstream.destroy())`，否则每次切页留一条半开连接。

1. `dev-frontend-remote-tcb.js`：加 `CLASSROOM_URL` 默认值 + 重写头部（三个服务/三个域名、
   少给各自的症状、域名未核实提示）。76 行。

**三种拓扑的判定（关键设计：课堂不像 MSG_URL 那样缺省跟随 API_URL）**
消息是核心链路，跟错立刻表现为「消息中心转圈」；课堂是可选项，跟错只表现为
