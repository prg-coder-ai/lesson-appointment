# 排期页面操作简化方案

> 创建日期：2026-10-25
> 适用页面：`admin.html` → 课程管理 → 课程排期（`frontend/js/admin-schedule.js`，1712 行）
> 关联需求：课程模板补充「教学语言 / 课时长度」，创建课程时从模板导入，排期上可修改

---

## 一、现状：新建一条排期要 8 个环节、9 个字段

代码路径（改造前）：

```
课程检索（输名 + 筛语言 + 筛难度 + 点搜索）
  → 选课程下拉（触发 loadSchedule）
  → 选排期下拉 → 点「新建」（触发 resetSchedule）
  → 切到「排期设置」Tab
  → 填：排期名称 / 员额 / 开始日期 / 上课时间 / 结束日期 / 重复类型 / 重复周期 / 重复星期 / 状态
  → 点「预览排期」（自动切走到「排期结果」Tab）
  → 手动切回「排期设置」
  → 点「保存」
  → 若要让学员能约：把状态从"待发布"改成"已发布"，再存一次
```

一周 10 个时段就要重复 10 遍。而「周一三五 19:00」这种排法，还得在 7 个复选框里手动挑 3 个——
**开始日期已经告诉系统那天是周三，代码却不自动勾周三**。

## 二、三个必须一并修掉的缺陷

不修这三处，「简化操作」只是把错误操作流程简化了。

### 缺陷 1：开始日期默认值按 UTC 计算，早 8 点前打开页面默认是"昨天"

`admin-schedule.js:405`（改造前）：

```html
<input type="date" id="startDate" value="${(new Date()).toISOString().split('T')[0]}">
```

`toISOString()` 是 UTC。东八区本地 00:00–07:59 之间，UTC 还停在前一天。

同一个文件的 `resetScheduleObject()`（1163 行）却用 `getFullYear/getMonth/getDate` 本地分量——
**两份口径并存，一个对一个错**，谁生效取决于走的是「页面首次渲染」还是「点新建」。

### 缺陷 2：冲突检查只比"同一课程"，且每节课被硬编码成 1 小时

`CourseScheduleService#checkScheduleOwnerConflict`（改造前 86 行、143 行）：

```java
// 只捞本课程的排期来比
List<CourseSchedule> scheduleList = scheduleMapper.selectByCreateDto(
    new ScheduleCreateDTO() {{ setCourseId(dto.getCourseId()); }});
...
LocalDateTime existEnd = existStart.plusHours(1);   // 注释："可视为每节课持续1小时"
LocalDateTime newEnd = newStart.plusHours(1);
```

- 一位老师同时带两门课，周一 19:00 撞车，**系统一个冲突都不报**——因为两条排期的 courseId 不同。
  `course_schedule` 表没有 `teacher_id`，也没有 `classroom_id`（`ScheduleCreateDTO:23` 的 `teacherId` 是注释掉的）。
- 19:00 的 90 分钟课与 20:00 的另一门课，在系统眼里"不冲突"。**根因不是判断写错，而是排期表没有时长字段，它只能猜。**

### 缺陷 3：「检查冲突」按钮是重复入口

`saveScheduleToDB()`（1462–1484 行）保存前已经自动查冲突并内联提示。
页面顶部那个「检查冲突」按钮做同一件事，且两处拼接提示文案的分隔符不同（一处 `，`、一处 `@@`）。

## 三、跟业务无关的概念占了页面

- 排期表单里的「排期时区」（readonly）与右上角「用户时间预览 / 用户时区」（13 个时区下拉）：
  对 99% 的单时区租户永远用不到，却让人以为系统很绕。
- 日历视图 `renderCalendar` 写死 `daysToShow = 35`，从**第一张课次所在周的周一**开始，
  没有月份标题、没有上/下月按钮。一个 3 个月的排期只能看到前 5 周。

## 五、教学语言 / 课时长度的数据流（本次新增）

### 5.1 为什么不是"只加在模板上"

`course_template` 早就有 `language_type` 与 `class_duration`。问题在于这两个属性**只活在模板层级**：

| 表 | 改造前 | 后果 |
|---|---|---|
| `course_template` | 有 `language_type` / `class_duration` | — |
| `course` | 无 | 课程列表只能 `LEFT JOIN course_template` 现查；课程本身不知道自己教什么语言、一节课多长 |
| `course_schedule` | 无 | 冲突检查只能硬编码 1 小时（缺陷 2） |

### 5.2 三级归属与"可覆盖"语义

```
course_template.language_type / class_duration     ← 模板定义（唯一键 = 租户 + 语言 + 难度）
        ↓ 创建课程时由服务端强制导入（不接受前端另填）
course.language_type / class_duration              ← 课程继承
        ↓ 创建排期时带入（排期未显式给值时才带入）
course_schedule.language_type / class_duration     ← 排期可单独覆盖
```

**为什么课程层强制以模板为准**：模板的唯一键就是 `(tenant_id, language_type, difficulty_level)`。
允许课程另填语言，会产出"模板是英语、课程教日语"这种自相矛盾的数据，而时长/语言又要被排期和冲突检查读取，口径必须唯一。

**为什么排期层允许覆盖**：同一门课在不同排期用不同语言授课是真实业务（外教班 / 中教班 / 试听课 25 分钟）。
锁死在课程上就表达不了。

### 5.3 冲突检查不再猜

```
每条排期的有效时长 = 排期自身 class_duration → 课程 class_duration → 60
重叠判定：existStart + 该排期时长 与 newStart + 新排期时长 是否有交集
```

三级回落是必要的：2026-10-25 之前的数据是回填出来的，更早的（外部导入、手写 SQL）可能两处都空。
**返回 0 会让区间端点相等，重叠判断退化成"永远不冲突"，比原来硬编码 1 小时还糟。**

## 六、L2 批量与复制（本次已实施，前端 + 复用既有接口）

| 功能 | 交互 | 行为 |
|---|---|---|
| **复制此排期** | 选中一条排期 → 点「复制」 | 复制成新排期，起止日期各 +7 天，其余字段照搬；弹出确认，显示新日期 |
| **从上周复制** | 点「从上周复制」 | 把该课程**上周（今天-7 ~ 今天-1）起排**的所有排期各顺延 7 天批量新建；目标起始日已存在排期则跳过 |
| **批量时段** | 点「批量时段」→ 弹窗填 3~7 行（星期 + 时间 + 员额） | 一次提交，串行创建，逐行回报成功/失败 |

L2 只读既有接口（`/schedule/selectByCourseId/{courseId}`、`/schedule/create`），**没有新增后端接口**。

一条"周一三五 19:00、周二四 20:00"的周课表：
**10 遍 × 15 次点击 → 1 张表 + 3 分钟。**

## 七、L3 周课表网格（未实施，等数据模型拍板）

7 列（周一~周日）× 时间轴，点空格子直接建排期（时间由格子决定），格子拖拽表示时长，
格子内显示"已约/员额"。这才是管理员脑子里的真实模型——**"这周谁在哪个时段上什么课"**。

两个前提：

1. ~~**老师要不要从"课程级"下沉到"排期级"？**~~ **已拍板 2026-10-25：不下沉。**
   老师继续挂在课程上（`course.teacher_id`），`course_schedule` **不加** `teacher_id`。理由与后果：
   - 口径不变：一门课 = 一位老师，"换老师"用"新建一门课程"表达，不做排期级多老师。
   - **冲突检查的边界就永远只有"同一课程"**。一位老师带两门课、两门课排在同一时段，系统不会报冲突——
     这不是 bug，是"老师不下沉"这个决定在数据模型上的必然结果，属于**已知并接受**的边界。
   - 周课表网格里"这个格子是谁在上课"由格子所属的课程推出，不需要排期自带老师。
   - 若将来业务上出现"一师多课同时段"的真实痛点，再回来讨论下沉（届时需给 `course_schedule` 加
     `teacher_id` 并改冲突检查 SQL，属结构变更）。
2. **教室/场地要不要建模？** 仍未拍板。周课表要表达"同一时段两个教室各一门课"，现在没有这个维度。

时长字段本次已经落地，L3 的另一个前提（拖拽改时长）已具备。
