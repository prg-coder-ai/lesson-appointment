# 预约系统云服务器部署和维护手册

> 适用代码：本仓库 `saas` 分支，三大模块 `api`（预约主系统 / 含平台管理端）、`api/message-service`（消息中心微服务）、`frontend`（业务前端）
> 技术栈：Spring Boot 3.3.5 / **Java 17** / MyBatis-Plus 3.5.7 / MySQL 8.x / Nginx / 原生前端（vanilla JS，构建产物 `dist/`）
> 读者假设：会用命令行复制粘贴命令即可；本文以 **Ubuntu 22.04 LTS** 云服务器为例，CentOS/Rocky 仅包管理命令不同。
>
> **阅读指引**：第 0 章是架构图（先记住）；第 1–2 章是部署前准备；第 3 章是**编译打包**（本机 + 服务器两种方式）；第 4–8 章是**上传与运行**；第 9 章是**日常维护**；第 10 章是故障速查。照第 12 章"一键顺序"从头做到尾即可让系统跑起来。

**三个部署产物 & 端口 & 数据库**

|------|----------|----------|----------|--------|--------------|

> ⚠️ **端口与路径分流要点**：booking 与 message-service 的接口**都挂在 `/api/v1` 前缀下**。两者的区分靠子路径——`/api/v1/message*`、`/api/v1/sse`、`/api/v1/users/` 属于消息服务（→ 8090），其余 `/api/v1/*` 属于主系统（→ 8081）。Nginx 必须按此分流（见第 7 章）。
> ✅ **前端已合并为一份（2026-09-09 起）**：业务前端与平台管理端**都在** `frontend/` 模块，统一构建成 `dist/`，由 Nginx 托管。
> ✅ **booking `:8081` 与 message-service `:8090` 均为纯后台服务**，不再伺服任何页面，各自只保留一个「缺省自我标识页」（`/`），显示程序名 / 版本 / 构建时间 / 服务器时间 / 时区 / 已运行时长，用于确认进程存活。

> 🆕 **服务运行信息接口 getApiInfo（2026-09-09 新增，匿名可访问）** —— 与缺省页同源：
> - booking：`GET /api/v1/system/info`（别名 `/api/v1/apiInfo`）→ 8081
> - message-service：`GET /api/v1/system/info`、`/api/v1/apiInfo`（**直连 8090**），
>   以及 `/api/v1/message/system/info`（**经 Nginx 同源访问**，靠 `/api/v1/message` 前缀分流到 8090）
>
> 前端两处入口已内置：`admin.html` → 数据维护 →「后台信息」Tab（名称/版本/构建时间 + 两个地址）；
> `platform_admin.html` → 系统维护 →「后台信息」（TAB 切换，展示全字段 + 顶部连接地址总览条）。
>
> 🆕 **连接信息 `connection`（2026-09-09 追加/修正）**：接口新增 `connection` 分组，回传**本次请求真实的三段地址**
> （此前只有 `endpoint` 调用 URL 与 `hostAddress` 网卡 IP，都不是"实际连上的地址"）：
> - **① 请求侧** `requestHost` / `requestHostIp`：浏览器访问的域名:端口，以及后端代做 DNS 解析得到的真实 IP —— **这才是实际连过去的服务器地址**；
> - **② 转发侧** `remoteAddress:remotePort`（与后端握手方，经同机 Nginx 为 `127.0.0.1`）、`clientIp` / `forwardedFor`（真实客户端）；
> - **③ 服务侧** `listenAddress:listenPort`：本进程实际监听（`0.0.0.0` 表示监听全部网卡）；
> - 辅助：`viaProxy`（是否经反代）、`summary`（整串链路一句话）。
>
> 前端据此展示三项：**前端调用地址** `endpoint`（origin + 分流前缀）、**实际连接 IP**（`requestHostIp`）、
> **服务监听地址**（`listenAddress:listenPort`），并在下方给出链路摘要。
>
> ⚠️ **`hostAddress` 不是被连接的地址**：它取的是服务进程所在机器的网卡 IP（首个已启用/非回环/非虚拟 IPv4）。
> 多网卡或 Docker 环境下可能是内网/容器 IP（如 `172.17.0.2`），与公网 IP 不一致属正常，仅作对照。
>
> ⚠️ **Nginx 必须转发 `X-Forwarded-*`**（现有配置已包含，勿删）：
> `proxy_set_header Host $host; X-Real-IP $remote_addr; X-Forwarded-For $proxy_add_x_forwarded_for; X-Forwarded-Proto $scheme;`
> 缺了这些头，后端只能看到 Nginx 自己的地址，`viaProxy` 会显示"否"、真实客户端 IP 拿不到。
>
> ⚠️ 部署提示：新增的 `/api/v1/message/system/info` 与 `connection` 字段需
> **重新打包部署两个 jar** 才生效；Nginx 无需改动（现有 `location /api/v1/message` 已覆盖）。
> 前端需重新构建并上传 `frontend/dist`。

## 第 1 章 部署前准备（一次性）

### 1.1 购买服务器

腾讯云控制台 → 轻量应用服务器 / CVM → 新建：

| 配置项 | 推荐 | 说明 |
|--------|------|------|
| 镜像 | **Ubuntu 22.04 LTS** | 本文命令基于此 |
| 套餐 | 2 核 4G 起步 | 应用 + MySQL 同机够用；用户多后升配或分离数据库 |
| 登录 | 密钥对（推荐）或 root 密码 | 密码 ≥16 位随机串 |

> 采购纪律：轻量服务器促销价续费常涨 3–25 倍，成本测算一律按续费价；优先选"续费同价款"或 3 年付。

### 1.2 域名与备案（如需 HTTPS 正式访问）

1. 注册域名（.com 约 ¥60–80/年）。
2. 域名解析到中国大陆服务器**必须 ICP 备案**（约 1–2 周）；备案期间可用 `http://服务器IP` 调试。
3. 本手册需要两个子域名：`booking.example.com`（业务）、`admin.example.com`（管理端）。仅调试也可暂时只用 IP + 管理端直连 `:8081`。

### 1.3 服务器基础环境

```bash
# Ubuntu / Debian
sudo apt update && sudo apt upgrade -y
sudo apt install -y openjdk-17-jdk-headless mysql-server nginx

# CentOS / Rocky
# sudo dnf install -y java-17-openjdk-headless mysql-server nginx

java -version     # 必须 17.x
mysql --version   # 8.x
nginx -v          # 1.18+
```

> 构建既可放在**本机（Windows）**也可放在**服务器**。本机构建需 JDK17 + Maven（见第 3 章）；服务器构建需额外装 Maven 3.9+。两种方式二选一，产物相同。

## 第 3 章 编译与打包（最核心：三模块各自构建）

三个模块**相互独立、没有聚合父 pom**，需分别进入目录构建。

### 3.0 环境要求

- **JDK 17**（三个模块 `pom.xml` 均 `<release>17</release>`；用 Java 21 会编译失败）。
- **Maven 3.9+**（仅构建时需要；若用本机 Windows 且 `mvn` 命令损坏，见 3.4 绕过法）。
- 构建 `api` 与 `frontend` 时会通过 `frontend-maven-plugin` **自动下载 Node v20.11.1 + npm 10.2.4** 并执行 `npm install` + `npm run build`（需联网；Node 下载到各自 `target/` 目录，不影响系统）。

### 3.1 构建 booking（api 主系统）

```bash
# 进入 api 目录
cd api
mvn clean package -DskipTests
```

产物：`api/target/booking_api-1.0.0.jar`（含 platform-admin 前端静态资源，已压缩混淆）。

### 3.2 构建 message-service（消息中心）

```bash
cd api/message-service
mvn clean package -DskipTests
```

产物：`api/message-service/target/message-service-1.0.0.jar`。

### 3.3 构建业务前端（frontend → dist）

```bash
cd frontend
mvn clean package -DskipTests      # packaging=pom，仅触发前端构建，不产 jar
# 等价写法（本机已装 Node 时更快）： npm install && npm run build
```

产物：`frontend/dist/` 目录（HTML/CSS/JS/图片，已压缩混淆）。**上线用 `dist/`，不要用源码 `frontend/`**（源码含 `node_modules/`、`target/`、敏感 `pom.xml`）。

## 第 5 章 服务器：初始化数据库

```bash
ssh $SERVER

# 1) 安全初始化 MySQL（设 root 强密码、禁匿名、禁远程 root）
sudo mysql_secure_installation

# 2) 按顺序导入（脚本自带 CREATE DATABASE，无需提前建库）
mysql -uroot -p < /opt/lesson/sql/lesson_appointment_schema_fixed.sql
mysql -uroot -p < /opt/lesson/sql/lesson_appointment_sys_seed.sql
mysql -uroot -p < /opt/lesson/sql/messagecenter-schema.sql

# 3) 校验
mysql -uroot -p -e "SHOW DATABASES;"          # 应见 lesson_appointment、message_center
mysql -uroot -p lesson_appointment -e "SHOW TABLES;"
```

**创建应用专用账号（不要用 root 跑应用）：**

```sql
CREATE USER 'lesson'@'localhost' IDENTIFIED BY '换成你的强密码';
GRANT SELECT, INSERT, UPDATE, DELETE ON lesson_appointment.* TO 'lesson'@'localhost';
GRANT SELECT, INSERT, UPDATE, DELETE ON message_center.*   TO 'lesson'@'localhost';
FLUSH PRIVILEGES;
```

并确认 MySQL 仅监听本机：`sudo sed -i 's/^#\?bind-address.*/bind-address = 127.0.0.1/' /etc/mysql/mysql.conf.d/mysqld.cnf && sudo systemctl restart mysql`。

### 6.2 密钥与环境变量文件（密钥不进 jar、不进 Git）

三个密钥通过 Spring Boot 宽松绑定从环境变量注入，对应 Java 代码里的 `@Value` 属性：

- `JWT_SECRET` → `jwt.secret`（`JwtUtil`，按 UTF-8 字节读，长度 **≥64**，HS512 签发 access、HS256 签发 refresh）
- `CRYPTO_AESKEY` → `crypto.aes-key`（`CryptoUtil`，Base64 解码须正好 **32 字节**，AES-256-GCM 字段加解密）
- `CRYPTO_HMACKEY` → `crypto.hmac-key`（`CryptoUtil`，Base64 解码 32 字节，HMAC-SHA256 搜索索引）

#### 6.2.1 三个密钥在三端的配对关系（部署前必须看清）

| 密钥 | 用途 / 算法 | 前端（Nginx 伺服的 dist） | api 预约服务（booking） | 信息中心（message-service） | 配对约束 |
|------|-------------|--------------------------|------------------------|------------------------------|----------|
| `JWT_SECRET` | JWT 签名 / 验签 | ❌ **不使用**（登录后仅拿到 token 存本地、请求头带上，前端不持密钥） | ✅ 签发 + 校验用户 token | ✅ **仅校验**（共享同一 `jwt.secret` 域，主系统签发的 token 在此校验，见 `MessageAuthInterceptor`） | **booking 与 message 必须逐字符相同**；前端不参与 |
| `CRYPTO_AESKEY` | 字段级 AES-256-GCM 加解密 | ❌ **不使用**（加解密全在服务端） | ✅ 加密 / 解密业务字段 | ✅ 复制 `CryptoUtil`，同算法同密钥（注释明写「与主系统相同密钥，可互通解密」） | **booking 与 message 必须逐字符相同**（跨库解密互通） |
| `CRYPTO_HMACKEY` | HMAC-SHA256 搜索索引 | ❌ **不使用** | ✅ 生成 / 校验搜索索引 | ✅ 复制，同密钥 | **booking 与 message 必须逐字符相同** |

**为什么必须这样配对（机制依据，来自代码）：**
1. **JWT_SECRET 配对**：api 的 `MessageNotifyService` 用共享 `jwt.secret` 给消息签一个 token（`sub=发送者userId, role, tenantId`），message-service 的 `MessageAuthInterceptor` 用它校验；用户登录 token 也需在两服务间互通（SSE / 消息接口）。**任一侧不一致 → 消息服务返回 401。**
2. **AES / HMAC 配对**：消息标题 / 内容等字段落库时由任一服务加密，另一服务解密读取（两服务共用 `message_center` 库与同一套加密逻辑）。**AES 或 HMAC 不一致 → 跨服务解密失败，数据不可读**（CryptoUtil 解密失败会降级返回原值，但搜索索引对不上，精确检索失效）。
3. **前端始终不参与**：前端是纯静态资源，`grep` 确认代码里没有任何 `JWT_SECRET` / `CRYPTO_*` 引用——不签发、不验签、不加解密。因此这三个密钥**只分发给两个后端服务，前端零密钥**。

#### 6.2.2 当前仓库状态提醒（安全）

`api/src/main/resources/application.properties` 与 `api/message-service/src/main/resources/application.properties` **当前已把这三个值明文写死且生效**（AES / HMAC 值与下方示例一致，JWT_SECRET 在两处相同）。这意味着：
- 开发 / 演示可直接跑，无需额外 env 文件；
- **生产部署必须用环境变量覆盖**，且建议**轮换**这些已入库的密钥为新值（任何拿到仓库的人都能读到它们）；
- 环境变量优先级高于 `application.properties`，写入下方 env 文件即可覆盖，**无需改源码**。

## 第 7 章 Nginx 反向代理 + HTTPS（让系统可被访问）

### 7.1 业务前端站点 `booking.example.com`

`/etc/nginx/sites-available/booking`：

```nginx
server {
    listen 80;
    server_name booking.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name booking.example.com;

    ssl_certificate     /etc/letsencrypt/live/booking.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/booking.example.com/privkey.pem;

    client_max_body_size 20m;

    # 业务前端静态资源（frontend/dist 构建产物）
    root /var/www/frontend;
    index index.html;
    location / {
        try_files $uri $uri/ /index.html;   # SPA 兜底
    }

    # ---- /api/v1 分流：消息服务子路径 → 8090，其余 → 8081 ----
    location /api/v1/message {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
    }
    location /api/v1/sse {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
        proxy_buffering off;          # SSE 必须关缓冲
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_http_version 1.1;
        chunked_transfer_encoding on;
    }
    location /api/v1/users/ {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
    }
    location /api/v1/ {
        proxy_pass http://127.0.0.1:8081;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 120s;
    }
}
```

> `include /etc/nginx/proxy_params;` 已包含 `Host`/`X-Real-IP`/`X-Forwarded-*` 等头；若发行版无此文件，改为显式写 4 行 `proxy_set_header`（照搬第 7.3 管理端示例）。

### 7.2 平台管理端子站点 `admin.example.com`

平台管理端 `platform_admin.html` **已并入前端 `dist/`**（2026-09-09 迁移），与业务前端是同一份静态产物。子域只需把 `root` 指向同一个 `dist` 目录、`/api/v1/` 反代到 booking `:8081` 即可：

```nginx
server {
    listen 80;
    server_name admin.example.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl http2;
    server_name admin.example.com;

    ssl_certificate     /etc/letsencrypt/live/admin.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/admin.example.com/privkey.pem;

    client_max_body_size 20m;

    root /var/www/frontend;                   # 与业务前端同一份 dist 产物
    index index.html;

    location / { try_files $uri $uri/ /index.html; }
    location /api/v1/ {
        proxy_pass http://127.0.0.1:8081;     # 接口仍走 booking 后台
        include /etc/nginx/proxy_params;
        proxy_read_timeout 120s;
    }
}
```

> 管理端实际登录页路径为 `/platform_admin.html`（即 `https://admin.example.com/platform_admin.html`）；它与业务前端**共用同一份 `dist` 静态产物**，由 Nginx 直接伺服，**不再经过 `:8081`**。
> 若没有第二个域名：直接用 `https://booking.example.com/platform_admin.html` 即可（与业务前端同域同端口）。前端登录分发自 2026-09-09 起，平台管理员已改为跳 `FRONTEND_ORIGIN + '/platform_admin.html?tCode=platform'`（原先 `ADMIN_ORIGIN` 指向 `:8081` 的写法已废弃），**无需再配置 `ADMIN_ORIGIN`**。

### 7.3 启用与证书

### 7.4 防火墙（安全组）

只放行 `22 / 80 / 443`；`8081`、`8090`、`3306` **不对外**（`ufw allow 22,80,443/tcp`；云厂商安全组同样配置）。

### 7.5 仅 IP 无域名的临时部署（调试/内测）

> 适用：服务器只有公网 IP、尚未注册/备案域名，但需要尽快跑通联调。正式上线请走 7.1–7.3 的子域 + Let's Encrypt。

**障碍说明**：7.1/7.2 的 `server_name booking.example.com` 与 certbot 证书都依赖域名解析。没有域名时：① `server_name` 改为 catch-all（`server_name _;`）；② Let's Encrypt 的 HTTP-01 验证需要域名做 ACME 校验，无法使用，只能用「纯 HTTP」或「自签名证书（IP SAN）」。

#### 方案 A：纯 HTTP（最省事，仅内测/调试）

单 server 块承载业务前端，管理端直连 `:8081`：

```nginx
# /etc/nginx/sites-available/booking-ip
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name _;                       # 无域名：catch-all 默认主机

    client_max_body_size 20m;
    root /var/www/frontend;
    index index.html;

    location / { try_files $uri $uri/ /index.html; }   # SPA 兜底

    # /api/v1 分流（与 7.1 一致）
    location /api/v1/message { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
    location /api/v1/sse     { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params;
                               proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s;
                               proxy_http_version 1.1; chunked_transfer_encoding on; }
    location /api/v1/users/  { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
    location /api/v1/        { proxy_pass http://127.0.0.1:8081; include /etc/nginx/proxy_params; proxy_read_timeout 120s; }
}
```

- 启用：`sudo ln -s /etc/nginx/sites-available/booking-ip /etc/nginx/sites-enabled/ && sudo rm -f /etc/nginx/sites-enabled/default && sudo nginx -t && sudo systemctl reload nginx`
- 管理端访问：`http://<服务器IP>/platform_admin.html`（与业务前端同域同端口，由 Nginx 伺服 `dist`）。前端"进入管理端"按钮拼 `FRONTEND_ORIGIN`（默认 `:8080`），**无需改前端、无需重构建**。
- 防火墙：安全组放 `22 / 80`（HTTPS 后加 `443`）；`8081`/`8090` 为后端内部端口，**仅 Nginx 本机反代访问，无需对外开放**，`3306` 不对外。
- ⚠️ HTTP 明文传输，**仅放测试数据**；正式用户数据必须升级 HTTPS。

#### 方案 B：自签名 HTTPS（消除明文，但浏览器不信任）

生成含 IP 的 SAN 自签证书（把 `1.2.3.4` 换成你的服务器 IP）：

```bash
sudo openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout /etc/nginx/ip.key -out /etc/nginx/ip.crt -days 825 \
  -subj "/CN=1.2.3.4" -addext "subjectAltName=IP:1.2.3.4"
```

Nginx（TLS 在 Nginx 终结，反代到 `127.0.0.1:8081` 仍走内网 HTTP）：

```nginx
server {
    listen 80 default_server;
    server_name _;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl default_server;
    server_name _;
    ssl_certificate     /etc/nginx/ip.crt;
    ssl_certificate_key /etc/nginx/ip.key;
    client_max_body_size 20m;
    root /var/www/frontend;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }
    # platform_admin.html 已在 dist 产物中，由上面的 `try_files` 直接命中，无需单独反代
    location /api/v1/message { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
    location /api/v1/sse     { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params;
                               proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s;
                               proxy_http_version 1.1; chunked_transfer_encoding on; }
    location /api/v1/users/  { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
    location /api/v1/        { proxy_pass http://127.0.0.1:8081; include /etc/nginx/proxy_params; proxy_read_timeout 120s; }
}
```

- 浏览器访问会报 `ERR_CERT_AUTHORITY_INVALID`（"连接不是私密连接"），点"高级 → 继续访问"即可——这是自签名**必然现象，非配置错误**。
- 移动端 App / 微信内嵌 webview 可能直接拒绝自签证书，故方案 B 仍只适合内测，不适合正式对外。
- 管理端走同块 `https://<IP>/platform_admin.html`（由 Nginx **直接伺服 dist 静态文件**），与业务前端完全同域，无需再为管理端单独开放 `:8081`。

**何时升级到 7.1/7.2**：注册并备案域名后（中国大陆服务器备案约 1–2 周），把 `server_name _;` 换成 `booking.example.com` / `admin.example.com`，删掉自签证书，跑 `certbot --nginx -d booking.example.com -d admin.example.com` 即平滑切到公信任 HTTPS。三个密钥（JWT/AES/HMAC）与传输层无关，**无需改动**。

## 第 10 章 故障速查表

| 现象 | 常见原因 | 排查/解决 |
|------|----------|-----------|
| `systemctl start` 立刻 failed，No such file | jar 名与 service 不一致 | `ls /opt/lesson/*.jar` 核对，改 `ExecStart` |
| 启动报 `Access denied` | 环境变量未注入/密码错 | `systemctl show booking -p Environment`；`mysql -ulesson -p` 验证 |
| 启动即退出、日志空 | JDK <17 | `java -version` |
| 业务前端 404 | dist 未传到 `/var/www/frontend` 或 Nginx `root` 错 | 核对目录与 `nginx -t` |
| `/api/v1/*` 502 | 后端没起 / `proxy_pass` 错 | `ss -lntp \| grep 8081`；`systemctl restart booking` |
| 消息不实时 | Nginx 缓冲未关 | 确认 `proxy_buffering off` 已配并 reload |
| 消息服务 Token 失败 | 两服务密钥不一致 | 核对 `JWT_SECRET`/`CRYPTO_*` 逐字符相同 |
| 时间差 8 小时 | `serverTimezone=UTC` | 连接串改 `Asia/Shanghai` 并重启 |
| 中文乱码 | 缺 `-Dfile.encoding=UTF-8` | `JAVA_OPTS` 已带；`LANG` 设 `C.UTF-8` |
| 崩溃不再拉起 | 触发 `StartLimitBurst=3` | `systemctl reset-failed booking && systemctl start booking` |

**万能三板斧**：`sudo systemctl restart mysql && sudo systemctl restart booking message-service && sudo nginx -t && sudo systemctl reload nginx`
