# 预约系统云服务器部署和维护手册

> 适用代码：本仓库 `saas` 分支，三大模块：`api`（预约主系统，**纯后台 REST**，不再伺服任何页面）、`api/message-service`（消息中心微服务，**纯后台 REST + SSE**）、`frontend`（**全部前端页面**：业务端 + 平台管理端，构建产物 `dist/`）
>
> ⭐ **前后端分离（2026-09-09 起）**：所有 HTML/JS/CSS 都在 `frontend/`，由 **Nginx 伺服 `dist/`**；两个后端只提供 `/api/v1/**` 与一个自我标识的缺省页 `/`。本文所有"前端"章节均按此架构描述。
> 技术栈：Spring Boot 3.3.5 / **Java 17** / MyBatis-Plus 3.5.7 / MySQL 8.x / Nginx / 原生前端（vanilla JS，构建产物 `dist/`）
> 读者假设：会用命令行复制粘贴命令即可；本文以 **Ubuntu 22.04 LTS** 云服务器为例，CentOS/Rocky 仅包管理命令不同。
>
> **阅读指引**：第 0 章是架构图（先记住）；第 1–2 章是部署前准备；第 3 章是**编译打包**（三模块各自构建）；第 4–8 章是**上传与运行**（**第 4 章含「复制文件与文件夹命令速查」4.2**，所有 scp/rsync 写法以它为准）；第 9 章是**日常维护**；第 10 章是故障速查。照第 12 章"一键顺序"从头做到尾即可让系统跑起来。
>
> **只看前端**？直接跳 **3.3（构建 dist）→ 4 章（上传）→ 7.0（前端部署总览）→ 7.2（平台管理端）→ 9.4①（前端发版）**。
> **只改后端**？前端不用动，走 9.4② 发两个 jar 即可。

## 第 0 章 架构总览（先记住这张图）

```
                    ┌──────────────────────────────────────────────────────────┐
  浏览器（用户/管理员）│                云服务器 (Ubuntu)                          │
  https://booking.example.com                                                  │
        │             │  Nginx :443                                             │
        │ ① 全部页面   │  root = /var/www/frontend      ← frontend/dist 的内容     │
        ├────────────▶│    index.html  admin.html  platform_admin.html           │
        │  (静态)      │    student.html teacher.html booking.html               │
        │             │    auditLog.html logBrowser.html  + js/ css/             │
        │             │    location / { try_files ... /index.html; }             │
        │             │                                                          │
        │ ② /api/v1/* │  location /api/v1/message /sse /users/ ──▶ :8090 message  │
        │  (接口)      │  location /api/v1/            （其余）──▶ :8081 booking   │
        └────────────▶│                                                          │
                      └──────────────────────────────────────────────────────────┘
                                    │                          │
                     booking :8081 ─┘                          └─ message-service :8090
                     （纯 REST，仅 "/" 缺省页）                  （纯 REST + SSE，仅 "/" 缺省页）
                          │                                          │
                          └──localhost:3306──▶ MySQL lesson_appointment
                                              └──localhost:3306──▶ MySQL message_center
```

**三个部署产物 & 端口 & 数据库**

| 服务 | 模块目录 | 打包产物 | 监听端口 | 数据库 | systemd 单元 | 是否含页面 |
|------|----------|----------|----------|--------|--------------|-----------|
| **booking**（预约主系统） | `api/` | `booking_api-2.0.0.jar` | **8081** | `lesson_appointment` | `booking.service` | ❌ **无**（仅 `/` 缺省页用于自我标识） |
| **message-service**（消息中心，含 SSE 推送） | `api/message-service/` | `message-service-1.0.0.jar` | **8090** | `message_center` | `message-service.service` | ❌ **无**（仅 `/` 缺省页） |
| **前端**（业务端 + **平台管理端**） | `frontend/` | `frontend/dist/` 目录（非 jar） | 由 Nginx 提供（80/443） | 无（纯静态） | Nginx 站点 | ✅ **全部页面** |

> ⚠️ **分流要点**：两个后端的接口**都挂在 `/api/v1` 前缀下**，靠子路径区分——`/api/v1/message*`、`/api/v1/sse`、`/api/v1/users/` 属消息服务（→ 8090），其余 `/api/v1/*` 属主系统（→ 8081）。Nginx 必须按此分流（见第 7 章）。
>
> ⚠️ **前端只有一份**：业务端与平台管理端**同属 `frontend/`**，一起构建进 `dist/`，由同一个 Nginx 站点伺服。管理端入口是 `/platform_admin.html`（**不是** `:8081` 上的页面，booking jar 里已无静态资源）。
>
> ⚠️ **判别线上是否为新包**（排障最常用）：
>
> ```bash
> # ① 站点层：管理端必须是 200 且返回登录页 HTML
> curl -s https://<站点>/platform_admin.html | head -c 80      # 期望 <!DOCTYPE html>...
>
> # ② 后端层：直连 8081 取页面，必须拿不到（后端已无静态资源）
> curl -s http://127.0.0.1:8081/platform_admin.html            # 期望 {"code":404,"message":"资源不存在"}
> ```
>
> 注意后端对缺失资源是**静默 404**：HTTP 状态码仍是 **200**，内容才是 `{"code":404,"message":"资源不存在"}`
> （`NoResourceFoundException` 被全局异常处理掉，避免日志噪音）。所以**别只看 HTTP 状态码**。
> 若 ② 返回的是完整 HTML 页面 → 线上还是旧 jar。

## 第 1 章 部署前准备（一次性）

### 1.1 购买服务器

腾讯云控制台 → 轻量应用服务器 / CVM → 新建：

| 配置项 | 推荐 | 说明 |
|--------|------|------|
| 镜像 | **Ubuntu 22.04 LTS** | 本文命令基于此 |
| 套餐 | 2 核 4G 起步 | 应用 + MySQL 同机够用；用户多后升配或分离数据库 |
| 登录 | 密钥对（推荐）或 root 密码 | 密码 ≥16 位随机串 |

> 采购纪律：轻量服务器促销价续费常涨 3–25 倍，成本测算一律按续费价；优先选"续费同价款"或 3 年付。

### 1.2 域名与备案（如需 HTTPS 正式访问）

1. 注册域名（.com 约 ¥60–80/年）。
2. 域名解析到中国大陆服务器**必须 ICP 备案**（约 1–2 周）；备案期间可用 `http://服务器IP` 调试。
3. 本手册需要两个子域名：`booking.example.com`（业务）、`admin.example.com`（管理端）。仅调试也可暂时只用 IP + 管理端直连 `:8081`。

### 1.3 服务器基础环境

```bash
# Ubuntu / Debian
sudo apt update && sudo apt upgrade -y
sudo apt install -y openjdk-17-jdk-headless mysql-server nginx

# CentOS / Rocky
# sudo dnf install -y java-17-openjdk-headless mysql-server nginx

java -version     # 必须 17.x
mysql --version   # 8.x
nginx -v          # 1.18+
```

> 构建既可放在**本机（Windows）**也可放在**服务器**。本机构建需 JDK17 + Maven（见第 3 章）；服务器构建需额外装 Maven 3.9+。两种方式二选一，产物相同。

## 第 3 章 编译与打包（最核心：三模块各自构建）

三个模块**相互独立、没有聚合父 pom**，需分别进入目录构建。

### 3.0 环境要求

- **JDK 17**（三个模块 `pom.xml` 均 `<release>17</release>`；用 Java 21 会编译失败）。
- **Maven 3.9+**（仅构建时需要；若用本机 Windows 且 `mvn` 命令损坏，见 3.4 绕过法）。
- 构建 **`frontend`** 时会通过 `frontend-maven-plugin` **自动下载 Node v20.11.1 + npm 10.2.4** 并执行 `npm install` + `npm run build`（需联网；Node 下载到 `frontend/target/`，不影响系统 Node）。
- 前后端分离后 **`api` 不再跑 Node**（已移除其 `frontend-maven-plugin`），构建 `api`/`message-service` 只需要 JDK 17 + Maven；版本信息由 `spring-boot-maven-plugin` 的 `build-info` 生成。

### 3.1 构建 booking（api 主系统）

```bash
# 进入 api 目录
cd api
mvn clean package -DskipTests
```

产物：`api/target/booking_api-2.0.0.jar`。

> **纯后台包**：jar 内**不含任何前端静态资源**（`api/src/main/resources/static/` 已整体删除），
> 只有 REST 接口与一个 `/` 缺省页（显示程序名/版本/构建时间/服务器时间/已运行时长，用于自我标识）。

### 3.2 构建 message-service（消息中心）

```bash
cd api/message-service
mvn clean package -DskipTests
```

产物：`api/message-service/target/message-service-1.0.0.jar`。

### 3.3 构建前端（frontend → dist，业务端 + 平台管理端一起）

```bash
cd frontend
mvn clean package -DskipTests              # packaging=pom，仅触发前端构建，不产 jar
# 等价写法（本机已装 Node 时更快）：  npm install && npm run build
# 只构建不打包（本地联调常用）：      mvn prepare-package
```

产物：`frontend/dist/`（HTML/CSS/JS/图片，已压缩混淆）。**上线用 `dist/` 里的内容，不要用源码目录 `frontend/`**（源码含 `node_modules/`、`target/`、`pom.xml`）。

`dist/` 根目录的页面（`build.js` 全量扫描 `frontend/`，新增页面/脚本自动进 dist，无需改构建配置）：

| 页面 | 用途 | 角色 |
|------|------|------|
| `index.html` | 统一登录入口（含"平台管理员"角色） | 全部 |
| `admin.html` | 租户管理端（含"数据维护 → 后台信息"Tab） | 租户管理员 |
| `platform_admin.html` | **平台管理端**（系统维护 → **后台信息** 全字段页） | 平台管理员 |
| `student.html` / `teacher.html` | 学生端 / 教师端 | 学生 / 教师 |
| `booking.html` | 预约下单页 | 学生 |
| `auditLog.html` | 审计日志 | 管理员 |
| `logBrowser.html` | 日志浏览（平台） | 平台管理员 |

> ⭐ **平台管理端已在 `frontend/`**（2026-09-09 迁出 booking jar）。它和业务端**同一次构建、同一份 `dist`、同一个 Nginx 站点**，
> 不存在"管理端单独部署"这回事——除非你特意给它配一个独立子域（见 7.2，仍然指向同一份 `dist`）。

### 3.4 本机 Windows 的 `mvn` 损坏绕过法（仅在开发机本地构建时需要）

若本机 `mvn` 命令报错（系统 `mvn` 损坏），用 Maven Launcher JAR 直启（Git Bash 中执行）：

```bash
# 每个模块构建前都先 unset CLASSPATH，避免污染
unset CLASSPATH
MVN_HOME="C:/Program Files/apache-maven-3.9.11"
LAUNCHER="$MVN_HOME/boot/plexus-classworlds-2.9.0.jar"

cd api
java -classpath "$LAUNCHER" -Dmaven.home="$MVN_HOME" \
     -Dmaven.multiModuleProjectDirectory=. \
     org.codehaus.plexus.classworlds.launcher.Launcher -B clean package -DskipTests

cd ../api/message-service
java -classpath "$LAUNCHER" -Dmaven.home="$MVN_HOME" \
     -Dmaven.multiModuleProjectDirectory=. \
     org.codehaus.plexus.classworlds.launcher.Launcher -B clean package -DskipTests

cd ../../frontend
java -classpath "$LAUNCHER" -Dmaven.home="$MVN_HOME" \
     -Dmaven.multiModuleProjectDirectory=. \
     org.codehaus.plexus.classworlds.launcher.Launcher -B clean package -DskipTests
```

### 3.5 ⚠️ 核对产物文件名（最容易翻车的一步）

`booking.service` 里可能写的是旧名 `booking-0.2.0.jar`，但 `api/pom.xml` 当前 `artifactId=booking_api`、`version=2.0.0` 且无 `finalName` 覆盖，**实际产物是 `booking_api-2.0.0.jar`**。打包后务必确认：

```bash
ls api/target/*.jar api/message-service/target/*.jar
# 期望看到：booking_api-2.0.0.jar   message-service-1.0.0.jar

# 前端产物（dist 内容与页面清单）
ls frontend/dist/*.html
# 期望看到：index / admin / platform_admin / student / teacher / booking / auditLog / logBrowser
```

第 6 章写 `booking.service` 时，**以 `ls` 看到的真实文件名为准**修改 `ExecStart` 路径，不要照抄示例里的 `booking-0.2.0.jar`。

## 第 4 章 上传到服务器

### 4.1 上传三个产物

在**本机**（不是服务器）执行 scp，把三个产物传上去：

```bash
# 假设服务器 IP 为 1.2.3.4，用户名 root
SERVER=root@1.2.3.4

# 1) 两个 jar（用通配符，避免版本号写死后与实际产物对不上；
#    若 api/target 下留了旧版本 jar，先删掉，否则通配符会把旧包一起传上去）
scp api/target/booking_api-*.jar                        $SERVER:/opt/lesson/
scp api/message-service/target/message-service-*.jar    $SERVER:/opt/lesson/

# 2) 前端：把 dist 的【内容】传成站点根（注意结尾的 /. 或 /*）
rsync -av --delete frontend/dist/           $SERVER:/var/www/frontend/
# 无 rsync 时等价写法：
#   scp -r frontend/dist/*                  $SERVER:/var/www/frontend/

# 3) SQL 初始化文件
scp api/beforeRun/lesson_appointment_schema_fixed.sql \
    api/beforeRun/lesson_appointment_sys_seed.sql \
    api/beforeRun/messagecenter-schema.sql  $SERVER:/opt/lesson/sql/
```

> 服务器目录后续在第 6 章创建；若报"无此目录"，先 `ssh $SERVER` 上去建好 `/opt/lesson/sql` 与 `/var/www/frontend` 再传。
>
> ⚠️ **最容易错的一处**：站点根必须是 `dist` 的**内容**，不是 `dist` 这个目录本身。
> 若写成 `scp -r frontend/dist $SERVER:/var/www/frontend/`，服务器会变成 `/var/www/frontend/dist/index.html`，
> 而 Nginx `root /var/www/frontend` 找不到 `index.html` → 首页 403/404。**传完务必验证（见 4.3）**。

### 4.2 复制文件与文件夹命令速查（含例子）

> 本节是 `scp` / `rsync` 用法的**集中出处**。4.1 及后续章节（第 6 章配置文件、9.4 发版）里的上传命令都按这里写。

**① 一条铁律：结尾的 `/` 决定"传目录本身"还是"传目录里的内容"**

```bash
scp -r frontend/dist  $SERVER:/var/www/frontend/    # ❌ 传【目录本身】→ /var/www/frontend/dist/index.html
scp -r frontend/dist/ $SERVER:/var/www/frontend/    # ✅ 传【目录里的内容】→ /var/www/frontend/index.html
```

**② 单个文件 / 多个文件**

```bash
scp booking_api-2.0.1.jar $SERVER:/opt/lesson/                      # 单文件
scp booking_api-2.0.1.jar $SERVER:/opt/lesson/booking_api.jar       # 上传时改名
scp a.jar b.jar c.sql     $SERVER:/opt/lesson/                      # 多文件（最后一个是目标目录）
scp api/target/booking_api-*.jar $SERVER:/opt/lesson/booking_api.jar   # 用通配符，避免版本号漂移
```

**③ 整个文件夹（递归，必须带 `-r`）**

```bash
scp -r frontend/dist/     $SERVER:/var/www/frontend/     # 前端产物内容 → 站点根
scp -r deploy/nginx/      $SERVER:/tmp/nginx-conf/       # 配置模板 → 先放 /tmp
scp -r api/beforeRun/sql/ $SERVER:/opt/lesson/sql/       # SQL 目录
```

**④ 文件夹同步优先用 `rsync`**（能续传、能用 `--delete` 清掉服务器上多余的旧文件）

```bash
rsync -av --delete frontend/dist/ $SERVER:/var/www/frontend/
rsync -av api/beforeRun/sql/      $SERVER:/opt/lesson/sql/
# 服务器没装：apt install -y rsync；或退回 scp -r frontend/dist/* $SERVER:/var/www/frontend/
```

> ⚠️ `--delete` 会删掉目标目录里"本地没有的文件"，所以**目标目录只能放这一样东西**（`/var/www/frontend/` 里别混放手工文件）。

**⑤ 从服务器复制回本地（下载）**

```bash
scp $SERVER:/opt/lesson/booking.log ./          # 下载单文件
scp -r $SERVER:/var/log/nginx/ ./nginx-logs/    # 下载整个文件夹
rsync -av $SERVER:/var/log/nginx/ ./nginx-logs/ # 增量拉取，更快
```

**⑥ 非常规端口 / 指定密钥**

```bash
scp -P 2222 -i ~/.ssh/id_rsa file $SERVER:/opt/lesson/            # 注意大写 -P
rsync -av -e "ssh -p 2222 -i ~/.ssh/id_rsa" frontend/dist/ $SERVER:/var/www/frontend/
```

**⑦ 目标是 `/etc/**` 这类系统目录：不要直接传**

普通用户对 `/etc/lesson`、`/etc/nginx` 没有写权限，直接 scp 会 `Permission denied`。**先传 `/tmp`，再在服务器上 `sudo mv`**：

```bash
# 本机
scp deploy/nginx/booking.conf            $SERVER:/tmp/
scp api/beforeRun/booking.env.template   $SERVER:/tmp/
scp api/beforeRun/message.env.template   $SERVER:/tmp/

# 服务器
sudo mv /tmp/booking.conf          /etc/nginx/sites-available/booking
sudo mv /tmp/booking.env.template  /etc/lesson/booking.env
sudo mv /tmp/message.env.template  /etc/lesson/message.env
sudo nginx -t && sudo systemctl reload nginx
```

**⑧ 本项目"哪个文件 → 哪个目录"对照**

| 本地路径 | 服务器路径 | 复制命令 |
|---|---|---|
| `api/target/booking_api-*.jar` | `/opt/lesson/booking_api.jar` | `scp api/target/booking_api-*.jar $SERVER:/opt/lesson/booking_api.jar` |
| `api/message-service/target/message-service-*.jar` | `/opt/lesson/message-service.jar` | `scp ... $SERVER:/opt/lesson/message-service.jar` |
| `frontend/dist/`（内容） | `/var/www/frontend/` | `rsync -av --delete frontend/dist/ $SERVER:/var/www/frontend/` |
| `api/beforeRun/*.sql` | `/opt/lesson/sql/` | `scp api/beforeRun/*.sql $SERVER:/opt/lesson/sql/` |
| `deploy/nginx/*.conf` | `/etc/nginx/sites-available/` | 经 `/tmp` 中转 + `sudo mv`（见 ⑦） |
| `booking.env.template` → `booking.env` | `/etc/lesson/booking.env` | 经 `/tmp` 中转 + `sudo mv`（见 ⑦） |
| `message.env.template` → `message.env` | `/etc/lesson/message.env` | 同上 |
| `deploy/backup.sh` | `/opt/lesson/backup.sh` | `scp deploy/backup.sh $SERVER:/opt/lesson/ && ssh $SERVER 'chmod +x /opt/lesson/backup.sh'` |

> jar 文件名带版本号（如 `booking_api-2.0.1.jar`），**以 `ls api/target/*.jar` 看到的为准**，统一用通配符 `booking_api-*.jar` 写命令。

**⑨ 仓库自带的一键上传脚本**

```bash
SERVER=root@1.2.3.4 bash deploy/upload-to-server.sh
```

内部就是上面这些命令的组合（jar + dist + 配置文件）。单独发版时仍建议按 ⑧ 逐项手动执行，便于核对。

### 6.2 密钥与环境变量文件（密钥不进 jar、不进 Git）

三个密钥通过 Spring Boot 宽松绑定从环境变量注入，对应 Java 代码里的 `@Value` 属性：

- `JWT_SECRET` → `jwt.secret`（`JwtUtil`，按 UTF-8 字节读，长度 **≥64**，HS512 签发 access、HS256 签发 refresh）
- `CRYPTO_AESKEY` → `crypto.aes-key`（`CryptoUtil`，Base64 解码须正好 **32 字节**，AES-256-GCM 字段加解密）
- `CRYPTO_HMACKEY` → `crypto.hmac-key`（`CryptoUtil`，Base64 解码 32 字节，HMAC-SHA256 搜索索引）

#### 6.2.1 三个密钥在三端的配对关系（部署前必须看清）

| 密钥 | 用途 / 算法 | 前端（Nginx 伺服的 dist） | api 预约服务（booking） | 信息中心（message-service） | 配对约束 |
|------|-------------|--------------------------|------------------------|------------------------------|----------|
| `JWT_SECRET` | JWT 签名 / 验签 | ❌ **不使用**（登录后仅拿到 token 存本地、请求头带上，前端不持密钥） | ✅ 签发 + 校验用户 token | ✅ **仅校验**（共享同一 `jwt.secret` 域，主系统签发的 token 在此校验，见 `MessageAuthInterceptor`） | **booking 与 message 必须逐字符相同**；前端不参与 |
| `CRYPTO_AESKEY` | 字段级 AES-256-GCM 加解密 | ❌ **不使用**（加解密全在服务端） | ✅ 加密 / 解密业务字段 | ✅ 复制 `CryptoUtil`，同算法同密钥（注释明写「与主系统相同密钥，可互通解密」） | **booking 与 message 必须逐字符相同**（跨库解密互通） |
| `CRYPTO_HMACKEY` | HMAC-SHA256 搜索索引 | ❌ **不使用** | ✅ 生成 / 校验搜索索引 | ✅ 复制，同密钥 | **booking 与 message 必须逐字符相同** |

**为什么必须这样配对（机制依据，来自代码）：**
1. **JWT_SECRET 配对**：api 的 `MessageNotifyService` 用共享 `jwt.secret` 给消息签一个 token（`sub=发送者userId, role, tenantId`），message-service 的 `MessageAuthInterceptor` 用它校验；用户登录 token 也需在两服务间互通（SSE / 消息接口）。**任一侧不一致 → 消息服务返回 401。**
2. **AES / HMAC 配对**：消息标题 / 内容等字段落库时由任一服务加密，另一服务解密读取（两服务共用 `message_center` 库与同一套加密逻辑）。**AES 或 HMAC 不一致 → 跨服务解密失败，数据不可读**（CryptoUtil 解密失败会降级返回原值，但搜索索引对不上，精确检索失效）。
3. **前端始终不参与**：前端是纯静态资源，`grep` 确认代码里没有任何 `JWT_SECRET` / `CRYPTO_*` 引用——不签发、不验签、不加解密。因此这三个密钥**只分发给两个后端服务，前端零密钥**。

#### 6.2.2 当前仓库状态提醒（安全）

`api/src/main/resources/application.properties` 与 `api/message-service/src/main/resources/application.properties` **当前已把这三个值明文写死且生效**（AES / HMAC 值与下方示例一致，JWT_SECRET 在两处相同）。这意味着：
- 开发 / 演示可直接跑，无需额外 env 文件；
- **生产部署必须用环境变量覆盖**，且建议**轮换**这些已入库的密钥为新值（任何拿到仓库的人都能读到它们）；
- 环境变量优先级高于 `application.properties`，写入下方 env 文件即可覆盖，**无需改源码**。

## 第 7 章 Nginx 反向代理 + HTTPS（让系统可被访问）

### 7.0 前端部署总览（前后端分离版，先看这一节）

前后端分离后，前端的部署只有三件事：**构建 dist → 把 dist 内容放到站点根 → Nginx 静态伺服 + `/api/v1` 分流**。

| 项 | 值 / 规则 |
|---|---|
| 构建产物 | `frontend/dist/`（业务端 + **平台管理端**一起） |
| 站点根（Nginx `root`） | `/var/www/frontend`，里面是 `dist` 的**内容**（**不要多一层 `dist/`**） |
| 页面入口 | `/index.html`（登录）、`/admin.html`、`/platform_admin.html`、`/student.html`、`/teacher.html`、`/booking.html`、`/auditLog.html`、`/logBrowser.html` |
| 前端发的请求 | 全部相对路径 `/api/v1/...`，由 Nginx 按子路径分流到 8081 / 8090 |
| 前端是否持有密钥 | ❌ 不持有任何密钥（JWT/AES/HMAC 全在服务端，见 6.2.1） |
| 后端是否提供页面 | ❌ 不提供（两个 jar 只有 `/` 缺省页，用于自我标识与排障） |

**Nginx 侧必须有的三段**：

```nginx
root /var/www/frontend;
index index.html;

location / { try_files $uri $uri/ /index.html; }     # ① 静态页面（含 platform_admin.html）

location /api/v1/message { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }  # ② 分流
location /api/v1/sse     { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params;
                           proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s;
                           proxy_http_version 1.1; chunked_transfer_encoding on; }
location /api/v1/users/  { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
location /api/v1/        { proxy_pass http://127.0.0.1:8081; include /etc/nginx/proxy_params; proxy_read_timeout 120s; }
```

**可选：静态资源缓存**（`js/` `css/` 带 hash 时可用；不带 hash 请谨慎，改版后浏览器会继续用旧文件）：

```nginx
location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$ {
    expires 7d;
    add_header Cache-Control "public, immutable";
}
```

> ⚠️ 若加了缓存策略，**发版后必须让用户强刷（Ctrl+F5）**或改用带 hash 的文件名，否则会遇到"代码已更新但页面还是旧的"。

**前端发版后自检（一条命令全查）**：

```bash
SITE=https://booking.example.com
for p in index.html admin.html platform_admin.html student.html teacher.html booking.html; do
  printf '%-24s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' $SITE/$p)"
done
# 接口分流（期望 booking_api / message-service 各回各的）
curl -s $SITE/api/v1/system/info          | head -c 120; echo
curl -s $SITE/api/v1/message/system/info  | head -c 120; echo
```

### 7.1 业务前端站点 `booking.example.com`

`/etc/nginx/sites-available/booking`：

```nginx
server {
    listen 80;
    server_name booking.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name booking.example.com;

    ssl_certificate     /etc/letsencrypt/live/booking.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/booking.example.com/privkey.pem;

    client_max_body_size 20m;

    # 业务前端静态资源（frontend/dist 构建产物）
    root /var/www/frontend;
    index index.html;
    location / {
        try_files $uri $uri/ /index.html;   # SPA 兜底
    }

    # ---- /api/v1 分流：消息服务子路径 → 8090，其余 → 8081 ----
    location /api/v1/message {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
    }
    location /api/v1/sse {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
        proxy_buffering off;          # SSE 必须关缓冲
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_http_version 1.1;
        chunked_transfer_encoding on;
    }
    location /api/v1/users/ {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
    }
    location /api/v1/ {
        proxy_pass http://127.0.0.1:8081;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 120s;
    }
}
```

> `include /etc/nginx/proxy_params;` 已包含 `Host`/`X-Real-IP`/`X-Forwarded-*` 等头；若发行版无此文件，改为显式写 4 行 `proxy_set_header`（照搬第 7.3 管理端示例）。

```nginx
    client_max_body_size 20m;
    root /var/www/frontend;
    index index.html;

    location / { try_files $uri $uri/ /index.html; }   # SPA 兜底

    # /api/v1 分流（与 7.1 一致）
    location /api/v1/message { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
    location /api/v1/sse     { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params;
                               proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s;
                               proxy_http_version 1.1; chunked_transfer_encoding on; }
    location /api/v1/users/  { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
    location /api/v1/        { proxy_pass http://127.0.0.1:8081; include /etc/nginx/proxy_params; proxy_read_timeout 120s; }
}
```

- 启用：`sudo ln -s /etc/nginx/sites-available/booking-ip /etc/nginx/sites-enabled/ && sudo rm -f /etc/nginx/sites-enabled/default && sudo nginx -t && sudo systemctl reload nginx`
- 管理端访问：`http://<服务器IP>/platform_admin.html`（**与业务端同站点的静态页**，由上面 `root` 直接提供，无需反代、无需开 8081）。
- 防火墙：安全组放 `22 / 80`；`8081`、`8090`、`3306` **一律不对外**（前后端分离后，浏览器不需要直接访问任何后端端口）。
- ⚠️ HTTP 明文传输，**仅放测试数据**；正式用户数据必须升级 HTTPS。

#### 方案 B：自签名 HTTPS（消除明文，但浏览器不信任）

生成含 IP 的 SAN 自签证书（把 `1.2.3.4` 换成你的服务器 IP）：

```bash
sudo openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout /etc/nginx/ip.key -out /etc/nginx/ip.crt -days 825 \
  -subj "/CN=1.2.3.4" -addext "subjectAltName=IP:1.2.3.4"
```

Nginx（TLS 在 Nginx 终结，反代到 `127.0.0.1:8081` 仍走内网 HTTP）：

```nginx
server {
    listen 80 default_server;
    server_name _;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl default_server;
    server_name _;
    ssl_certificate     /etc/nginx/ip.crt;
    ssl_certificate_key /etc/nginx/ip.key;
    client_max_body_size 20m;
    root /var/www/frontend;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }
    location /api/v1/message { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
    location /api/v1/sse     { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params;
                               proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s;
                               proxy_http_version 1.1; chunked_transfer_encoding on; }
    location /api/v1/users/  { proxy_pass http://127.0.0.1:8090; include /etc/nginx/proxy_params; }
    location /api/v1/        { proxy_pass http://127.0.0.1:8081; include /etc/nginx/proxy_params; proxy_read_timeout 120s; }
}
```

- 浏览器访问会报 `ERR_CERT_AUTHORITY_INVALID`（"连接不是私密连接"），点"高级 → 继续访问"即可——这是自签名**必然现象，非配置错误**。
- 移动端 App / 微信内嵌 webview 可能直接拒绝自签证书，故方案 B 仍只适合内测，不适合正式对外。
- 管理端走同块 `https://<IP>/platform_admin.html`（`root` 直接提供的静态页，**不是**反代 8081）。

**何时升级到 7.1/7.2**：注册并备案域名后（中国大陆服务器备案约 1–2 周），把 `server_name _;` 换成 `booking.example.com` / `admin.example.com`，删掉自签证书，跑 `certbot --nginx -d booking.example.com -d admin.example.com` 即平滑切到公信任 HTTPS。三个密钥（JWT/AES/HMAC）与传输层无关，**无需改动**。

### 10.1 `ExecStart` 必须写 `$JAVA_OPTS`（2026-09-09 实战）

**现象**：Ubuntu 上 `systemctl start message-service` 立刻失败：

```
systemd[1]: message-service.service: Main process exited, code=exited, status=1/FAILURE
systemd[1]: message-service.service: Failed with result 'exit-code'.
systemd[1]: message-service.service: Start request repeated too quickly.
systemd[1]: message-service.service: Failed with result 'exit-code'.
```

单元里有 `EnvironmentFile=/etc/lesson/message.env`，env 里也定义了
`JAVA_OPTS=-Xms128m -Xmx256m -Dfile.encoding=UTF-8`，但 `ExecStart` 没写 `$JAVA_OPTS`：
**在 `ExecStart` 补上 `$JAVA_OPTS` 后即恢复正常。**

**根因：`JAVA_OPTS` 不是 JVM 内置变量**

```
/etc/lesson/message.env  定义 JAVA_OPTS=...
        ↓ EnvironmentFile=
进程环境变量里有 JAVA_OPTS      ← JVM 启动时并不会去读它
        ↓ ExecStart 没写 $JAVA_OPTS
/usr/bin/java -jar xxx.jar     ← 裸跑：堆内存/编码全用默认值 → 启动即崩
```

- JVM **自动读取**的环境变量只有两个：`JAVA_TOOL_OPTIONS`、`JDK_JAVA_OPTIONS`。
- `JAVA_OPTS` 只是 Tomcat `catalina.sh` 那套脚本的**约定俗成**，脚本会自己把它拼进命令行；纯 `java -jar` 场景没人帮你拼。
- `EnvironmentFile=` 只把变量放进**进程环境**，不会自动变成 java 参数；必须在 `ExecStart` 里展开（systemd 支持 `$VAR`，取自 `EnvironmentFile`/`Environment`）。

```ini
ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/lesson/message-service.jar   # ✅ 生效
ExecStart=/usr/bin/java -jar /opt/lesson/message-service.jar              # ❌ JAVA_OPTS 成了死变量
```

> 仓库模板 `api/beforeRun/booking.service` 与 `message-service.service` **本来都带 `$JAVA_OPTS`**，
> 服务器上 `/etc/systemd/system/` 那份若是旧版或手改版，就会踩这个坑。

**那三个参数里谁救了场**（按概率，一条命令即可定性，journal 历史还在）：

```bash
sudo journalctl -u message-service --no-pager   | grep -Ei "heap|OutOfMemory|MalformedInput|charset|encoding|Could not reserve" | head -20
```

| 命中字样 | 生效因子 | 说明 |
|---|---|---|
| `Could not reserve enough space` / `OutOfMemory` | `-Xmx256m` | 不限堆时 JVM 默认最大堆 = 物理内存 1/4，与 MySQL + booking 抢内存，小内存云主机易越线 |
| `MalformedInput` / `charset` / `ANSI_X3.4-1968` | `-Dfile.encoding=UTF-8` | systemd 服务**不继承登录 shell 的 locale**，Java 17 下 `file.encoding` 退化为 ASCII（Java 18+ 才默认 UTF-8，JEP 400），读 UTF-8 资源会抛异常 |
| 都没命中 | `-Xms128m` 或综合作用 | 多为内存水位临界，建议整串保留 |

**服务器上的修复步骤（可直接复制）**：

```bash
# ① 先止血：崩溃循环状态下直接 start 会被限流拒绝
sudo systemctl stop message-service
sudo systemctl reset-failed message-service      # 清 StartLimit 计数，否则一直报 too quickly

# ② 改单元：确认 ExecStart 带 $JAVA_OPTS
sudo systemctl edit --full message-service       # 改完保存
#   或：sudo sed -i 's|^ExecStart=/usr/bin/java -jar|ExecStart=/usr/bin/java $JAVA_OPTS -jar|' #         /etc/systemd/system/message-service.service

sudo systemctl daemon-reload
sudo systemctl restart message-service
sudo systemctl status message-service --no-pager
```

**加固三件事**：

1. 两个服务的 `ExecStart` 都写 `$JAVA_OPTS`（同步服务器副本后必须 `systemctl daemon-reload`；`booking` 现在没炸可能只是没踩到阈值）。
2. 兜底：env 里再加一行 `JDK_JAVA_OPTIONS=-Dfile.encoding=UTF-8`，即使 `ExecStart` 漏写，JVM 也会自动应用：
   ```bash
   echo 'JDK_JAVA_OPTIONS=-Dfile.encoding=UTF-8' | sudo tee -a /etc/lesson/message.env
   sudo systemctl restart message-service
   ```
3. 明确 locale：`sudo localectl set-locale LANG=C.UTF-8`，或在单元里加 `Environment=LANG=C.UTF-8`。

### 10.2 前端「接口有数据、页面空白」——响应双重解包（2026-09-09 实战）

**现象**：`/api/v1/system/info`、`/api/v1/message/system/info` 直接 curl 有完整 JSON，但"后台信息"页面一片空白，且不报错。

**根因**：`frontend/js/public/utility_request.js` 的响应拦截器在 `code === 200` 时**已经把内层 `data` 解包**返回了：

```js
const res = response.data;
if (res.code === 200) { return res.data; }     // ← await http.get(url) 拿到的就是业务对象本体
```

页面若再写一次 `body.data`，拿到的是 `undefined` → 渲染空表且静默。

**修复约定**：页面侧统一用解包函数（已实现，勿再手写 `.data`）：

| 文件 | 函数 | 兼容形态 |
|---|---|---|
| `js/platform-admin-backend-info.js` | `unwrapPayload()` | 已解包 / 原始 axios 响应 / 裸 Result 体 |
| `js/admin-dataMaintainPage.js` | `unwrapBackendPayload()` | 同上；解包后为空**显式抛错**（不会静默空白） |

**排障顺序**：① Ctrl+F5 排除缓存 → ② F12 看接口返回是否为 200 且有 `data` → ③ 若页面仍空白但接口正常，检查是否新增了自定义的 `.data` 取值。

**万能三板斧**：`sudo systemctl restart mysql && sudo systemctl restart booking message-service && sudo nginx -t && sudo systemctl reload nginx`

| `start-frontend-local-src.cmd`<br>（或 `node dev-frontend-local-src.js`） | **`frontend/` 源码**（不打包） | 本地 `127.0.0.1:8081` + `:8090` | **日常开发**：改完 js/html 刷新即生效 |
| `start-frontend-local.cmd`<br>（或 `node dev-frontend-local.js`） | `frontend/dist` | 本地 `:8081` + `:8090` | 验证构建产物 |
| `start-frontend-remote.cmd`<br>（或 `node dev-frontend-remote.js`） | `frontend/dist` | 远程 `152.136.254.127:8081/8090` | 后端在服务器、本机只跑前端 |

三者都监听 **`:8080`**：静态页面直接伺服，`/api/v1/**` 按与 Nginx 相同的规则分流（`/api/v1/message`、`/api/v1/sse`、`/api/v1/users/` → 8090，其余 → 8081），并**自动补 `X-Forwarded-*`**（与生产 `proxy_params` 行为一致，否则后端拿不到真实客户端）。

```bash
# 后端（本机）
java -jar api/target/booking_api-2.0.0.jar --server.port=8081
java -jar api/message-service/target/message-service-1.0.0.jar --server.port=8090

# 前端（另开一个终端）
cd doc-develop && node dev-frontend-local-src.js
# → 浏览器打开 http://localhost:8080
```

- 业务端：`http://localhost:8080/index.html`；**平台管理端：`http://localhost:8080/platform_admin.html`**（不再是 `:8081`）。
- 本机 `mvn` 损坏时用第 3.4 的 Launcher 法构建；本机 MySQL 用 `root/123456`（或环境变量 `DB_PASSWORD` 覆盖）。
- ⚠️ **JWT 密钥域铁律**：本机 jar 用源码里的 `jwt.secret`，远程服务用系统密钥，**不可混连**（一端本地、一端远程必然 401）。
