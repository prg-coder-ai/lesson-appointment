# 小程序登录人机识别方案分析

> 主题：微信小程序登录环节如何识别人机、如何把机器人挡在门外
> 分析对象：本项目现有微信登录链路（`/auth/wechat-login`、`/auth/wechat-register`、`/auth/bind-wechat`）
> 编制时间：2026-10-22
> 说明：文中所有现状判断均标注了源码位置。方案分四层漏斗，P0 部分可在一天内落地。

---

## 一、先把问题问对：三个必须先想清楚的问题

多数团队做这件事的第一步就走偏了——直接上图形验证码，然后发现机器人照样进、真人反而被烦跑。原因是没有先回答下面三个问题。

### 问题 1：机器人真的能"凭空登录"吗？

**不能。** 这是最关键的认知前提。

小程序的 `wx.login()` 返回的 `code` 由微信客户端生成，绑定 appid、5 分钟有效、一次性消费。服务端 `code2Session` 用 `appid + secret + code` 换 `openid`——**攻击者在不知道 `secret` 的前提下，无法自己造出一个能通过校验的 `code`**。

也就是说：

> 能被"伪造"的是**请求**，不能被伪造的是**微信身份**。
> 一次成功的 `wechat-login` 必然对应某台设备上某个真实存在的微信。

那么机器人的实际形态只有四种：

| 机器人形态 | 能否拿到合法 code | 说明 |
| --- | --- | --- |
| **真机农场**（群控/云控/多开） | 能 | 一台真手机跑一个真微信，code 完全合法。这是主流 |
| **协议号**（破解微信客户端通信） | 能 | 黑产用模拟客户端登录微信，成本较高但成熟 |
| **重放/盗用 code** | 理论能 | code 一次性 + 5 分钟，且只能换 openid，危害有限 |
| **伪造请求**（自己写 HTTP 打后端） | **不能** | 换不到 openid，直接 `1001` 降级。这条已经被现有设计挡住 |

**结论**：所谓"禁止机器人登录"，实际要打的是**前两类**——它们都持有合法的微信身份。所以问题不是"验证身份真假"，而是"**判断这个身份背后是不是一个愿意花钱、有时间成本的人**"。

### 问题 2：机器人登录之后能拿到什么？

这一点决定了防御的重心。**登录动作本身对攻击者没有收益**，让他有动力的一定是登录后的东西：

| 登录后的目标 | 本项目是否存在这个面 | 现状 |
| --- | --- | --- |
| 刷免费试用、批量建租户 | **有** | `/auth/wechat-register` + 推广路径 1 可自助建租户，试用名额全局限 200（`promotion.trial.global.limit`） |
| 刷推广归因、拿提成 | **有** | 双推广码，`promo_conversion` 记录归因 |
| 薅业务资源（占名额） | 有 | 预约、候补可被批量占位 |
| 爬师资公开数据 | **有** | `/teacher/published` 类展示页免登录可读，其实不需要登录 |
| 枚举 openid/账号对应关系 | 弱 | `wechat-login` 未绑定时只回 1001，不回细节 |

**结论**：真正需要设闸的是 **注册与归因**，而不是"每次登录"。把最强的手段压在注册口，把轻量手段压在登录口——这是成本与体验的最优分配。

### 问题 3：能不能做到"绝对禁止"？

**不能。** 只要对方手里有一个真实微信，服务端就没有任何技术手段能区分"他在用手机点"还是"他的手机被脚本控制着点"。

能做到的是三件事：

1. **提高单次批量成本**（让每个假身份都要付出手机号、时间或验证码解题成本）
2. **识别异常模式**（同一出口、同一设备、同一时段的高频多身份行为）
3. **切断收益**（配额、上限、延迟发放、人工复核）

务实的目标应该写成：

> **把"一台机器一分钟注册 100 个账号"降级为"一台机器一天注册 3 个账号，且每个都要过一道挑战"。**

而不是"零机器人"。

## 二、现状体检（基于当前代码）

### 2.1 现有微信登录链路

```
小程序                               后端 8081
──────────────────────────────────────────────────────────────
wx.login() → code
      │
      ├── POST /auth/wechat-login  (免登录)
      │        └→ WeChatService.code2Session(code)
      │              └→ openid / unionid
      │                    └→ WxUseridService.findByIdentity(unionid → openid)
      │                          ├─ 未绑定 → Result.fail(1001)  ← 前端静默降级
      │                          └─ 已绑定 → 检查 status → 发 access + refresh token
      │
      ├── POST /auth/wechat-register (免登录)
      │        └→ 同上换 openid → UserService.wechatRegister → 建账号/租户
      │
      └── POST /auth/bind-wechat (需登录)
```

对应源码：`WeChatService#code2Session`、`UserService#wechatLogin`（414 行）、`WxUseridService#findByIdentity`。

这一段的设计已经相当严谨，值得肯定的三点：

- **一个微信只绑一个账号**：`uk_wx_openid` / `uk_wx_unionid` 双唯一键全局生效（`WxUseridService` 类注释），跨租户不隔离
- **不静默改绑**：已绑到别的账号时抛 `ConflictException` → 409，避免"账号接管"
- **失败用 1001 不用 401**：因为 401 会触发小程序 `request.js` 的 `onAuthFail` 把用户踢回登录页，静默降级必须是 1001

### 2.2 但风控侧是空的——三个真空

**真空一：全仓没有任何限流。**

```
grep -rn "RateLimit|rateLimit|限流|throttle|429" api/src/main/java  →  0 条结果
```

三个免登录登录/注册端点，**没有次数上限、没有时间窗、没有熔断**。只要 openid 换得快（真机农场），可以无限次打。

**真空二：没有验证码体系。**

唯一与"验证码"相关的代码是密码找回的 6 位码（`authController` 345 行 `@Pattern(regexp = "^\\d{6}$")`），而且它自己的注释写着：

> 若将来要开放自助找回，必须另做验证码/短信校验，不能直接放开本接口。

即：**当前没有任何图形、滑块、行为验证能力可供登录口复用。**

**真空三：唯一存在的防刷在推广注册侧，且有可绕过的缝。**

`PromoService#checkRegisterAbuse`（411 行）做了三闸：

```java
int limit = sysConfigService.getInt("promotion.register.period.limit", 3);
LocalDateTime since = LocalDateTime.now().minusHours(1);
// ① IP 闸：同一 IP 1 小时 3 次
if (countByIpSince(ip, since) >= limit) throw new BusinessException("注册过于频繁");
// ② 手机号闸：同一手机号 1 小时 3 次（HMAC 盲索引比对，不存明文）
if (countByPhoneHmacSince(hmac, since) >= limit) throw new BusinessException("该手机号注册过于频繁");
// ③ 全局试用上限
if (created >= sysConfigService.getInt("promotion.trial.global.limit", 200)) throw ...
```

设计思路是对的（三闸叠加、HMAC 不存明文、上限按 `referred_by` 计而非 `trial_status`），但有两个现实漏洞：

- **手机号是手填的**。`miniprogram/pages/register-tenant/register-tenant.wxml:20` 是一个普通 `<input placeholder="请输入联系电话（选填）">`，不是微信 `getPhoneNumber` 组件。也就是说**手机号闸可以靠"每次换一个号码"直接绕过**，且这个号码连真实性都无法保证。
- **IP 闸可被伪造绕过**。见 2.3。

### 2.3 一个必须先修的底层问题：IP 有两套实现，且都可以被绕过

项目里获取客户端 IP 存在**两种不一致的写法**：

| 位置 | 实现 | 结果 |
| --- | --- | --- |
| `PromoController#clientIp`（232 行） | 读 `X-Forwarded-For` 首段 → `X-Real-IP` → `remoteAddr` | 能拿到真实 IP，**但可伪造** |
| `LegalDocController`、`AuditAspect`、`WeChatPcController` | 同上（各自重复实现一遍） | 同上 |
| **`UserService#currentRequestIp`（623 行）** | **只读 `getRemoteAddr()`** | 反向代理后可能是 Nginx 地址 |

两个后果：

**后果 A：登录会话表里记的 IP 可能全是代理地址。**
`UserService#wechatLogin` 在最后一行调用 `userSessionService.onLogin(..., currentRequestIp(), ...)`，如果容器没有解析 `X-Forwarded-For`，记下来的就是 `127.0.0.1`。这意味着**即使你现在想做 IP 维度的风控，也没有可用的数据**。

> 需实测确认：Spring Boot 3 的 `RemoteIpValve` 在部分配置下会把 `X-Forwarded-For` 解析进 `getRemoteAddr()`，此时结果是对的。验证方式：线上环境打一个请求，看 `user_session`（或任一日志）里记的 IP 是否等于你的外网出口 IP；等于 `127.0.0.1` 或 `172.x` 内网地址即证明未解析。

**后果 B：`X-Forwarded-For` 首段是客户端可写的。**
`proxy_params` 通常配的是 `X-Forwarded-For $proxy_add_x_forwarded_for`——它会把客户端自带的 XFF **追加**到最前面保留，于是：

```bash
curl -H "X-Forwarded-For: 1.2.3.4" https://your.domain/api/v1/promo/register
```

服务端取首段 `1.2.3.4`，攻击者每次换一个假头，**所有 IP 闸全部失效**。

**这是本方案的第一块地基**：限流键必须建立在"服务端可验证"的值上。

修正方向（两件事，都很快）：

```properties
# application.properties —— 显式开启框架层解析，避免依赖容器默认行为
server.forward-headers-strategy=framework
```

```java
// 统一到一个工具类，禁止各处再手写第七遍
public final class ClientIpResolver {
    // 只有来自可信代理（本机/内网）的请求才信任 XFF，且从右往左取第一跳非内网地址
    public static String resolve(HttpServletRequest req, List<String> trustedProxies) {
        String remote = req.getRemoteAddr();
        if (!trustedProxies.contains(remote)) {
            return remote;                    // 直连：客户端自己说了不算
        }
        String xff = req.getHeader("X-Forwarded-For");
        if (xff == null || xff.isBlank()) return remote;
        String[] hops = xff.split(",");
        for (int i = hops.length - 1; i >= 0; i--) {   // ★ 从右往左，不是从左往右
            String ip = hops[i].trim();
            if (!trustedProxies.contains(ip)) return ip;
        }
        return remote;
    }
}
```

> **从右往左**是关键：XFF 是"客户端 → 各级代理"依次追加的，最右侧是**可信代理写进去的那一跳**，最左侧是客户端自己填的。取左侧 = 取攻击者的谎言。

## 三、手段全景：八类方案谁管什么

把人机识别拆成"能证明什么"，八类手段的真实能力如下。

| # | 手段 | 能证明什么 | 抗批量能力 | 接入成本 | 用户体感 | 可绕过方式 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 微信 `code2Session`（**已有**） | 请求来自一个真实微信客户端 | 低（真机农场可直接过） | 0 | 无感 | 真机农场、协议号 |
| 2 | **微信手机号快速验证** `getPhoneNumber` | 背后有一个**真实可收短信的手机号** | **高** | 中（组件 + 解密 + 付费） | 中（需点一次授权） | 黑产手机号池（有成本） |
| 3 | 图形字符验证码 | 有 OCR 之外的一点交互能力 | **低**（识别率 90%+） | 低 | 差 | OCR 打码平台，1 分钱一次 |
| 4 | 滑块 / 旋转 / 点选拼图 | 有真实触摸轨迹 | 中 | 中 | 中 | 轨迹模拟、打码平台真人代答 |
| 5 | 无感行为风控（轨迹 + 环境 + 指纹） | 操作像不像人 | 中高（可调阈值） | 高（自研）或买（腾讯防水墙/极验） | **最好（多数人无感）** | 真人众包打码 |
| 6 | 设备环境检测（模拟器/root/hook/多开） | 客户端环境是否正常 | 中（辅助） | 低 | 无感 | hook 隐藏、改机工具 |
| 7 | **频率与配额**（IP / 设备 / openid / 时间窗） | 行为是否异常密集 | **高（最有效）** | **低** | 无感 | 分布式 IP 池、慢速 |
| 8 | 业务侧配额（试用上限、归因上限、绑定上限） | 收益是否被限制 | **高（兜底）** | 低 | 无感 | 无（这就是终局） |

### 三条来自实战的判断

**判断一：第 7、8 类才是主力，第 3~6 类只是"提高成本的税"。**
限流不需要识别"是不是人"，它识别的是"密度"，而机器人最不可能伪装的就是密度——要绕过密度就得把速度降到和真人一样，那它批量刷的意义就没了。**先把限流做对，比先买验证码有用得多。**

**判断二：第 3 类（图形字符码）在本项目场景里应该直接排除。**
它的实际防护力已经低于成本：OCR 打码 1 分钱一次、准确率 90% 以上，而它对真人（尤其 40 岁以上的律所客户、健身教练）的体验伤害是实打实的。**要做挑战就做滑块/无感，不要做字符码。**

**判断三：第 2 类是本项目性价比最高的一道真闸。**
原因很直接——它把"一次注册的成本"从 0 元变成"一个真实手机号 + 一次授权点击"。真机农场要付手机卡钱，协议号要付接码钱，而正常客户（律所、咨询室、健身工作室的老板）本来就要留联系方式。**这一道闸同时解决了防刷和数据真实性两个问题。**

代价也要说清楚：

- 微信的手机号快速验证组件**仅对企业主体的已认证小程序开放**，个人主体用不了；
- 该组件**按次计费**（具体价格以微信官方当期定价为准，务必先查后台账单再定方案）；
- 一次授权只对应一次验证，**不能拿它当"每次登录都要过"的闸**，否则老用户每次登录都要点授权，体验崩掉。

所以第 2 类的正确位置是：**注册时 / 首次绑定时**，不是每次登录时。

## 四、推荐方案：四层漏斗 + 一个评分器

不要把所有手段都挂在登录按钮上。正确做法是串成漏斗——**绝大多数请求在第一层就被无感放行，只有可疑的才逐层加码**。

```
请求进入 /auth/wechat-login 或 /auth/wechat-register
        │
   ┌────▼─────────────────────────────────────┐
   │ 第 1 层  频率闸（无感，成本 0）            │
   │  · IP 1h 次数      · 设备 1h 身份数        │
   │  · openid 1h 次数  · 全局 1min QPS         │
   │  超限 → 不是直接拒，而是"升级到第 2 层"     │
   └────┬─────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────┐
   │ 第 2 层  风险评分（无感，纯规则）          │
   │  新 openid +新设备 +新 IP 段 +环境异常      │
   │  → 0~100 分；< 40 直接放行；≥ 40 进第 3 层 │
   └────┬─────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────┐
   │ 第 3 层  挑战闸（有感，仅在必要时）        │
   │  · 滑块/点选，服务端出题、一次性消费       │
   │  · 注册口额外要求手机号验证（第 2 类手段） │
   └────┬─────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────┐
   │ 第 4 层  业务配额（兜底，永远最后一道）    │
   │  试用名额、归因上限、同设备可建租户数      │
   └──────────────────────────────────────────┘
```

### 4.1 第 1 层：频率闸的键怎么选

**这是整个方案里最容易做错的一层**，因为键选错了不是"防不住"，而是"把真人一起封了"。

| 键 | 数据来源 | 是否可伪造 | 建议阈值（初始值） | 备注 |
| --- | --- | --- | --- | --- |
| **openid** | `code2Session` 返回，服务端可信 | **不可伪造** | 同一 openid 10 次/小时 | 最可靠，但一个 openid 本来就只该登录一次，意义在防死循环 |
| **deviceId** | 客户端生成 + 服务端下发种子 | 可重置（清缓存） | 同一设备 5 个身份/小时 | **第二可靠**，是识别真机农场的核心 |
| **IP** | 见 2.3 的修正 | **可伪造（若不修正）** | 同一 IP 20 次/小时 | 阈值必须放宽：公司/教室 NAT 出口是共享的 |
| 租户编码 | 请求体 | 可伪造 | 同一租户 60 次/小时 | 防针对单一租户的撞库 |
| 全局 | 无 | — | 300 次/分钟 | 防全站被打挂 |

三条铁律：

1. **IP 阈值必须宽松**。一间培训学校 20 个老师连着同一个 WiFi，出口 IP 完全一样。IP 闸一旦设成个位数，第一个被封的是你的客户。
2. **超过阈值只升级挑战，不直接拒绝**。拒绝是"误伤"，挑战是"多一步"。真实用户多点一次滑块能忍，被拒之门外会流失。
3. **限流键不要用 `code`**。`wx.login()` 每调用一次 code 就变，用它做键等于没限流。

### 4.2 第 2 层：风险评分（规则版，不需要机器学习）

评委们常说"要上模型"，但在数据量只有几千条的早期，一套**可解释的规则打分**比模型好用得多——它能被产品经理看懂、被运营调整、出错时查得到原因。

| 信号 | 分值 | 判定方式 |
| --- | --- | --- |
| openid 首次出现（`wx_userid` 无记录） | +20 | 查库 |
| 设备首次出现 | +20 | 查设备表 |
| IP 属于"历史高危段" 或 该 IP 24h 内出现过 ≥3 个不同 openid | +25 | 查限流表 |
| 环境异常：模拟器/root/越狱/调试开启/无触摸事件 | +30 | 客户端上报 + 服务端交叉校验 |
| 同一设备 1h 内出现 ≥3 个不同 openid | +40 | 查限流表 |
| openid 已存在 + 设备已存在 + IP 无异常 | 0 | 老用户，直接放行 |

**阈值设计**：

- `< 40`：放行，不打搅
- `40 ~ 69`：要求滑块挑战
- `≥ 70`：要求滑块 + 手机号验证（仅注册口），或直接拒绝并记审计

这套规则的"甜点"在于：**老用户永远是 0 分**。老用户不该为陌生人的攻击付出体验代价，这是体验与安全的唯一平衡点。

### 4.3 第 3 层：挑战的工程约束

挑战机制看起来简单（出题 → 解题 → 校验），但四个细节决定了它是"防线"还是"装饰"：

**① 题目必须由服务端下发并绑定身份。**
不能客户端自己生成图片、自己校验——小程序包能被反编译，所有前端判断都等于没有。

```java
// 服务端出题：返回 challengeId + 拼图背景 + 缺口位置（不给坐标，只给图）
public ChallengeVO issue(String openid, String scene) {
    String id = UUID.randomUUID().toString().replace("-", "");
    int targetX = ThreadLocalRandom.current().nextInt(40, 240);  // 缺口横坐标
    int targetY = ThreadLocalRandom.current().nextInt(10, 60);
    // 落库/落缓存：id → (openid, scene, targetX, targetY, expireAt, used=false)
    challengeStore.save(new AuthChallenge(id, openid, scene, targetX, targetY,
            LocalDateTime.now().plusMinutes(2)));
    return new ChallengeVO(id, renderPuzzleBackground(), renderPuzzlePiece());
}
```

**② 一次性消费 + 绑定 openid + 短 TTL。**
校验时三个条件全中才通过：`challengeId` 存在、`openid` 与出题时一致、`used = false`。**校验通过后必须立刻置 `used = true`**——否则同一道题可被反复提交，甚至被判题脚本分钟级暴力试探（缺口只有几百个像素位置，不消费就等于给了足够采样次数）。

**③ 校验要用"容差 + 轨迹"双判。**
只看横坐标误差（±5px）会被"随机猜"攻破；要同时要求：拖动轨迹点数 ≥ N、耗时 ∈ [200ms, 10s]、轨迹有非匀速特征（起手加速、末端减速）。

**④ 失败次数要有上限。**
同一 `challengeId` 连续失败 5 次直接作废并升级到"拒绝"，否则它就变成了一个可无限试错的 oracle。

### 4.4 第 4 层：业务配额（真正的终局防线）

这一层与"识别"无关，但它是唯一能**确定性止血**的手段，而且已经在项目里有了雏形：

```java
// PromoService#checkRegisterAbuse 已有的第三闸，是正确思路：
int globalLimit = sysConfigService.getInt("promotion.trial.global.limit", 200);
long created = tenantService.countPromoCreatedTenants();
if (created >= globalLimit) throw new BusinessException("免费体验名额已满，请联系平台方");
```

建议在这个思路上补三条**按主体**的配额（而不是只有全局）：

| 配额 | 建议初始值 | 作用 |
| --- | --- | --- |
| 同一 `deviceId` 24h 内可创建的租户数 | 1 | 直接掐死"一台机器批量开号" |
| 同一 `deviceId` 24h 内可注册的账号数 | 2 | 同上 |
| 同一推广码 24h 内计入有效归因的数 | 5 | 防刷提成；超额部分"待人工复核"而非直接作废 |
| 同一 openid 可绑定的账号数 | 1（已有 `uk_wx_openid`） | 已具备 |

> 注意第三条的处理方式：**超额不直接判无效，而是标记"待复核"**。因为真实的头部推广者一天带 5 个人是正常的，直接作废会打击真实渠道。

### 5.1 数据表设计

```sql
-- 挑战票据表（一次性消费）

CREATE TABLE `auth_rate_counter` (
  `id`          BIGINT      NOT NULL AUTO_INCREMENT,
  `dim`         VARCHAR(16) NOT NULL COMMENT 'ip / device / openid / tenant',
  `dim_key`     VARCHAR(128) NOT NULL COMMENT '维度值（IP 或 HMAC 后的设备/身份）',
  `window_start` DATETIME   NOT NULL,
  `cnt`         INT         NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),

```

**★ 三张表都必须加入 `MyBatisPlusConfig.IGNORE_TABLES`。**

这不是可选项。原因：登录接口是免登录端点，请求进来时 `TenantContext` 没有任何值，租户插件会兜底拼上 `tenant_id = -1`（详见 `MyBatisPlusConfig` 的 `-1` 兜底逻辑）。这三个表本身也没有 `tenant_id` 列——不加入忽略清单，所有 SQL 会直接报"未知列"或写入 `-1` 脏数据，形成一个**只在免登录路径上才复现**的诡异故障。

这与项目里已有的 16 道守卫体系也有关联：`check-tenant-cross-thread` 的静态检查会扫描跨线程与无上下文场景，新增表若被判定为"业务表"，会被要求有租户归属——**在 `IGNORE_TABLES` 里显式登记，是唯一正确的表达方式**。

### 5.2 服务端骨架

```java
@Service
public class LoginGuardService {

    private final AuthChallengeMapper challengeMapper;
    private final AuthDeviceMapper deviceMapper;
    private final AuthRateCounterMapper counterMapper;
    private final SysConfigService sysConfigService;

    /**
     * 第 1+2 层：评估本次登录请求的风险，返回是否需要挑战。
     *
     * <p>关键设计：本方法<b>永不抛异常</b>。风控组件自身故障时必须放行，
     * 否则风控一挂，全站登录跟着挂——这是"可用性优先于安全性"的取舍，
     * 与项目里微信 secret 占位时回 1001 静默降级是同一姿态。
     */
    public GuardVerdict evaluate(GuardContext ctx) {
        try {
            int score = 0;
            // ① openid 是否首次
            if (!wxUseridService.exists(ctx.openid())) score += 20;
            // ② 设备是否首次
            AuthDevice dev = deviceMapper.selectByDeviceId(ctx.deviceId());
            if (dev == null) score += 20;
            else if (ctx.openid() != null && !ctx.openid().equals(dev.getFirstOpenid())) score += 40;
            // ③ IP 维度：24h 内出现过的不同 openid 数
            if (countDistinctOpenidByIp(ctx.ip(), 24) >= 3) score += 25;
            // ④ 环境异常
            if (ctx.emuFlag()) score += 30;
            // ⑤ 频率超限 → 直接升级（不看分数）
            boolean overLimit = hitRateLimit(ctx);

            if (overLimit)      return GuardVerdict.challenge(score, "rate");
            if (score >= 70)    return GuardVerdict.challenge(score, "risk");
            if (score >= 40)    return GuardVerdict.challenge(score, "suspicious");
            return GuardVerdict.pass(score);
        } catch (Exception e) {
            log.warn("登录风控评估异常，降级放行", e);   // ★ 故障放行
            return GuardVerdict.pass(-1);
        }
    }

    /** 第 3 层：校验挑战。失败时递增 fail_count，超 5 次作废票据。 */
    public boolean verifyChallenge(String challengeId, String openid,
                                   int moveX, int trackPoints, long costMs) {
        AuthChallenge ch = challengeMapper.selectById(challengeId);
        if (ch == null) return false;
        // 一次性 + 身份一致 + 未过期，三个条件缺一不可
        if (ch.getUsed() != 0) return false;
        if (!Objects.equals(ch.getWxOpenid(), openid)) return false;   // ★ 防跨身份复用
        if (ch.getExpireAt().isBefore(LocalDateTime.now())) return false;
        if (trackPoints < 8 || costMs < 200 || costMs > 10_000) return false;
        if (Math.abs(moveX - ch.getTargetX()) > 5) {
            challengeMapper.incrFail(challengeId);
            if (ch.getFailCount() + 1 >= 5) challengeMapper.invalidate(challengeId);
            return false;
        }
        // ★ 先置 used 再返回：条件更新，防并发双花
        if (challengeMapper.markUsed(challengeId) == 0) return false;
        return true;
    }
}
```

`markUsed` 必须写成条件更新（与项目里 `TenantQuotaService.tryAcquire` 同一手法）：

```sql
UPDATE auth_challenge SET used = 1 WHERE id = #{id} AND used = 0
-- 返回影响行数：0 表示已被别人消费，本次校验作废
```

### 5.3 接口契约改造（这里有一个项目特有的坑）

要在登录接口返回"需要人机验证"，必然要新增一个业务状态码。但项目对 `Result` 的实施很严格：

```java
// Result.java 51 行
private static final java.util.Set<Integer> ALLOWED_CODES =
        Collections.unmodifiableSet(new HashSet<>(Arrays.asList(
                200, 400, 401, 403, 404, 405, 409, 500, 1001)));
// fail() 里：不在白名单 → 直接抛 IllegalArgumentException
```

所以下面这行会**在运行期直接炸**：

```java
Result.fail(429, "请求过于频繁");   // ← IllegalArgumentException: code 非法
```

正确做法是**同时改三处**（漏一处就红）：

| 位置 | 改什么 |
| --- | --- |
| `Result.ALLOWED_CODES` | 加入 `429`（或用业务码 `1002` 表示"需人机验证"） |
| `GlobalExceptionHandler` | 若要真 HTTP 429，需在 Advice 里加映射；若走 HTTP 200 + code，则不用 |
| `tools/check-result-contract-guard.mjs` 与它的反向测试 | 契约扩大后守卫的白名单同步更新，`npm run check:result-contract` 必须过 |

选择建议：

- **走 HTTP 200 + `code = 1002`（需验证）**：与项目现有的 `1001` 静默降级姿态一致，前端 `request.js` 里已经在按 `body.code` 分支处理，改动最小。
- 走真 HTTP 429 的代价是前端 axios/小程序两条拦截器都要加处理，且 `Result.fail` 白名单与 Advice 映射都要动，收益不大。

**推荐前者**，并且把 `1002` 语义写进 `shared/apiPaths.js` 或 `shared/domain` 层的常量里，两端共用（项目已有"共享领域模型"的机制，不要在小程序和 Web 各写一遍魔法数字）。

### 5.4 小程序端改造点

现有登录页的行为需要**改造而不是叠加**，因为当前 `onLoad` 是这套流程：

```javascript
// miniprogram/pages/login/login.js:65
try {
  const wxRes = await wechatSilentLogin();     // 静默尝试
  if (wxRes) { goHome(); return; }
  if (tcode) {
    const regRes = await wechatRegister({ tenantCode: tcode });
    if (regRes) { recordLegalAccept(); goHome(); return; }
  }
} catch (e) { /* 静默降级 */ }
```

问题在于：**一旦服务端返回"需人机验证"，"静默登录"就不静默了**。用户打开小程序，页面停在登录页、还要自己拖一个滑块——他不知道为什么，体感极差。

改造要点：

```javascript
// ① 静默登录允许返回"待挑战"状态，由调用方决定是否弹窗
const wxRes = await wechatSilentLogin({ allowChallenge: true });
if (wxRes && wxRes.status === 'ok')  { goHome(); return; }
if (wxRes && wxRes.status === 'challenge') {
  // ② 只有"挑战"时才展示滑块，且要给一句人话解释
  const passed = await showSliderChallenge(wxRes.challenge);   // 自定义组件
  if (!passed) { this.setData({ challengeFailed: true }); return; }  // 落回密码登录表单，不报错
  const retry = await wechatSilentLogin({ challengeId: wxRes.challenge.challengeId });
  if (retry && retry.status === 'ok') { goHome(); return; }
}
```

四条小程序端的实操注意：

1. **`wx.login()` 的 code 不能复用**。挑战通过后重试登录必须**重新调用 `wx.login()` 拿新 code**（旧 code 已在第一次提交时消费掉，微信侧一次性）。这是最容易写成死循环的一处——"挑战通过但登录仍失败"，原因就是拿旧 code 重放。
2. **设备指纹的组成要写对**。`wx.getSystemInfoSync` 已废弃，用 `wx.getDeviceInfo` + `wx.getAppBaseInfo` + `wx.getWindowInfo`；`deviceId = sha256(服务端下发的 seed + brand + model + system + pixelRatio + platform)`。seed 首次由服务端下发并落在 `wx.setStorageSync`，**清缓存会重置**——所以 `deviceId` 只能作为"降低权重"的信号，不能作为唯一判定依据。
3. **滑块用自绘 canvas，不要引重型第三方 SDK**。小程序端引第三方验证码 SDK 通常要配 request 合法域名、加插件、走审核，一套流程下来比自研 canvas 滑块慢得多。自研只需：服务端给两张 base64 图（背景 + 缺口块），前端 canvas 绘制 + 拖动 + 上报 `moveX / trackPoints / costMs`。
4. **必须保留"降级到密码登录"的出口**。挑战失败或组件异常时，用户应该能改用账号密码登录，而不是卡死在小程序里。现有登录页本来就有密码表单，把失败态映射成"提示 + 显示表单"即可。

### 5.5 一个必须同步做的决定：注册口的手机号

如果决定启用微信手机号快速验证，改动点是 `register-tenant.wxml` 第 20 行那个 `<input>`：

```html
<!-- 现状：纯手填，可随便填，闸门形同虚设 -->
<input class="input" placeholder="请输入联系电话（选填）" value="{{phone}}" bindinput="onPhone" />

<!-- 改造后：button 触发微信授权，服务端用 code 换真实号码 -->
<button class="btn-phone" open-type="getPhoneNumber" bindgetphonenumber="onGetPhone">
  {{phone ? phone : '微信手机号验证（必填）'}}
</button>
```

服务端新增一个解密端点，**并且要把手机号直接接进已有的 `CryptoUtil.searchIndex` 盲索引链路**——因为 `PromoService.checkRegisterAbuse` 的手机号闸用的就是 `cryptoUtil.searchIndex(phone)` 生成的 HMAC。这样改造后：

- 号码是真的（微信给的，不是手填的）
- 号码闸真的有效（换号要换真卡）
- 存量 `promo_conversion.phone_hmac` 口径不用变（同一个 `searchIndex` 算法）

**这是本方案里性价比最高的一步改造**：不动架构、不引组件、复用现有加密与防刷代码，把"最容易被绕过的一闸"变成"最硬的闸"。

## 六、六个必踩的坑

### 坑 1：把"每次登录"都变成需要验证

真机农场的成本是"一台设备"，不是"一次登录"。给每次登录都加验证，相当于**让所有正常用户替攻击者付体验税**，而攻击者只需要保持每台设备每天登录一次，就完全不受影响。

正确做法：老 openid + 老设备 + 无异常 → 直接放行（0 分），只有可疑才弹。

### 坑 2：拿 `X-Forwarded-For` 首段做限流键

如 2.3 所述，首段是客户端可写的。攻击者每请求换一个假 IP，你的 IP 闸 100% 失效，而且你从日志里只会看到"IP 分布很健康"。

必做：从右往左取 + 只信任可信代理写的那一跳 + 显式配置 `server.forward-headers-strategy`。

### 坑 3：新表漏进 `IGNORE_TABLES`

见 5.1。这个坑的恶心之处在于：**它只在免登录端点上报错**。你在本地用带 token 的请求测一切正常，上线后用户第一次登录就 500。而且报错信息是"Unknown column 'tenant_id'"，看起来完全不像权限问题。

### 坑 4：`Result.fail(429)` 直接抛异常

见 5.3。这是本项目特有的深坑，因为 `fail()` 对 code 做了白名单硬校验。**新增任何状态码都必须三处同步改**，否则编译能过、启动能过、一上线就炸。

### 坑 5：挑战通过后复用旧 code 重试登录

`wx.login()` 的 code 是一次性的。挑战流程是"提交登录 → 收到挑战 → 解题 → 重试登录"，如果重试时复用第一次的 code，微信侧会返回 `errcode=40163`（code been used），前端表现为"滑块过了还是登不上"，非常难排查。

必做：重试前重新 `wx.login()`，并在日志里记录 code 的前 6 位（不要记全）用于对比。

### 坑 6：限流计数表被"扫表"拖死

`auth_rate_counter` 如果每次请求都 `count(*) where window_start >= x`，在登录高峰会变成全表扫描热点。三种处理：

- 窗口固定化（按分钟/小时对齐），写入走 `INSERT ... ON DUPLICATE KEY UPDATE cnt = cnt + 1`，读只读一行 `uk_dim_window` 主键
- 高频维度（openid、设备）进内存滑动窗口（项目是单实例部署，`ConcurrentHashMap` + 定时清理就够，无需引入 Redis）
- 低价值维度（全局 QPS）纯内存计数，不落库

> 项目当前没有 Redis。这是个重要约束：**不要为了做人机识别而先引入 Redis**。单实例部署下，内存计数 + 关键闸落库，完全够用；等将来上多实例，再考虑把计数挪到 Redis（那时 `SsePushService` 也正好要改 pub/sub，一并处理）。

### 验收指标（P1 上线后必须看的四个数）

| 指标 | 含义 | 健康区间 | 恶化说明 |
| --- | --- | --- | --- |
| **挑战触发率** | 需要过挑战的登录请求 / 总登录请求 | < 8% | 超过 15% 说明阈值太松或规则误判 |
| **挑战通过率** | 通过挑战 / 触发挑战 | > 70% | 低于 50% 说明误伤了真实用户（或滑块本身有 bug） |
| **拦截率** | 被拒绝的请求 / 总请求 | 0.5% ~ 3% | 长期 0 说明没防住；超过 5% 说明严重误伤 |
| **新设备新身份占比** | 首次出现的 (设备, openid) 组合占比 | 与真实拉新曲线一致 | 突然飙升 = 正在被批量刷 |

> 关键运营原则：**把阈值写进 `sys_config`，不要写死在代码里**。项目已有 `SysConfigService.getInt("promotion.register.period.limit", 3)` 这种范式，照抄即可。上线后第一个月一定需要调，写死的阈值等于把调参变成发版。

## 八、明确不推荐的四件事

1. **不要用图形字符验证码**。OCR 打码 1 分钱，防护力已低于体验代价，尤其在 40+ 用户占多数的法律、心理咨询客群里。
2. **不要在前端做任何"是不是人"的判断并相信它**。小程序包可反编译，所有 `if (isRobot) return;` 都等于注释。
3. **不要试图"识别设备唯一性"作为唯一依据**。清缓存、改机工具、多开分身都能重置本地标识。设备指纹只能降低权重，不能做唯一判定。
4. **不要为了这件事引入 Redis / 消息队列 / 风控中台**。单实例 + 内存计数 + 三张表，足够把"一分钟刷 100 个"降到"一天刷 3 个"。过度设计会把一个 1 天的工作变成 2 周，而防护效果没有量级差异。

## 十、一句话总结

> **微信登录已经保证了"身份是真的微信"，剩下的问题不是"验证身份"，而是"提高批量成本"。**
> 所以防线不应该堆在登录按钮上，而应该是：**频率闸（无感）→ 风险评分（无感）→ 触发式挑战（少数人可见）→ 业务配额（兜底）**，
> 并且优先把两个"最容易被绕过的地方"补上——**可伪造的 IP 键**和**手填的手机号**。
