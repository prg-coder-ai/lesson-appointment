## 二、报告未列出的隐患（本次复核新发现）

### 🔴 H1：调度器单线程串行，`MonitorTask` 慢会拖垮上课提醒（P0）

**证据**：`SpringBootMergeApplication.java:18` 有 `@EnableScheduling`，但**两个 `application.properties` 都没有 `spring.task.scheduling.pool.size`** → Spring Boot 默认调度线程池 **size=1**。

全仓共 9 个定时任务，全部挤这一个线程：

| 任务 | 位置 | 频率 |
|---|---|---|
| `NotifyTask.dispatchLessonReminders` | `task/NotifyTask.java:61` | `fixedDelay` 60s |
| `MonitorTask` ×7 | `task/MonitorTask.java` | 55/73/88/108/123/139/171 行 |
| 指标采样等 | | |

而 `NotifyTask` 一轮要做的事很重：查全部租户 → 逐租户 `setTenantId` → `dispatchDueNotifications()` → **对 message-service 发起同步 HTTP**。租户数 × 课次数 × HTTP 往返，全程持有一个线程。

**后果**：报告第 325 行担心的场景反过来出现了 —— 不是"负载均衡识别不了连接池耗尽"，而是**指标采样任务（`MonitorTask`，要读 CPU/内存/磁盘）一旦变慢，上课提醒就会被整体推迟**。上课提醒是 4 档 × 每分钟轮询的高频业务，延迟累积直接影响"30分钟前提醒"的时效。

代码里 `fixedDelay` 的注释已经写明"一轮扫描耗时不确定"，作者清楚单轮很慢，但**没有意识到它跑在唯一的调度线程上**。

**修法**：
```properties
spring.task.scheduling.pool.size=4
spring.task.scheduling.thread-name-prefix=sched-
```
配池后各任务互不阻塞；同时把 `NotifyTask` 内的 HTTP 调用改异步（报告第 20 条后半段），或在 `dispatchDueNotifications` 里对租户做分片。**注意**：改异步前必须先确认 `TenantContext` 在异步线程的传递方式（当前靠 `setTenantId`/`clear` 显式管理，异步化后这套要重新设计，不能直接丢给线程池）。

### 🔴 H2：systemd 那份日志无任何滚动策略，且与 logback 是两个文件（P0）

**证据**（`api/beforeRun/booking.service`）：
```ini
StandardOutput=append:/var/log/lesson/booking.log
StandardError=append:/var/log/lesson/booking.log
```
`append:` 是 systemd 1.4+ 语法，**只追加、不滚动**。全仓 `deploy/` 与 `api/beforeRun/` 下**零 logrotate 配置**（已 grep 确认）。

同时 logback 自己写另一份：`${LOG_PATH:-./logs}/spring-boot-app.log`，带 `SizeAndTimeBasedRollingPolicy`（50MB 切分 + 30 天 + 5GB 上限）—— 但两个 env 模板里 **都没有 `LOG_PATH`**（`booking.env.template` / `message.env.template` grep 计数均为 0），所以 logback 实际落在 `WorkingDirectory=/opt/lesson` 下的 `./logs/`。

**于是系统里有两份日志、两种命运**：

| 日志 | 产生方 | 滚动 | 后果 |
|---|---|---|---|
| `/opt/lesson/logs/spring-boot-app.log` | logback（有策略） | ✅ 自动滚动 | — |
| `/var/log/lesson/booking.log` | systemd stdout（`CONSOLE` appender） | ❌ **永不滚动** | 磁盘写满 → 服务写日志失败 → 可能连带业务异常 |
| `/var/log/lesson/message.log` | message-service 同上 | ❌ **永不滚动**，且它连 logback 都没有 | 同上 |

这正是报告第 325 行说的"没有指标/告警意味着故障只能靠人巡检发现"的同类问题 —— 日志本身先撑不住。

**修法**：① 加 `deploy/logrotate.d/lesson` 配置 `/var/log/lesson/*.log`（`daily` + `rotate 14` + `compress` + `copytruncate`，因 systemd 持有 fd 不能用 rename 式轮转）；② `message-service` 补 `logback-spring.xml`（照抄 api 那份即可）；③ 或者干脆去掉 `CONSOLE` appender 的文件重定向，让 stdout 全部走 journald，由 journald 的 `SystemMaxUse` 管容量 —— 二选一，别两份都半管。

### 🟡 H3：`/monitor/*` 已有指标，但它不是探针（P1，理解偏差）

报告第 19 条要的是**健康检查**（liveness/readiness），仓库里已有的 `/api/v1/monitor/*` 是另一回事：

| | 现有 `/monitor/*` | 报告要的健康检查 |
|---|---|---|
| 目的 | 给人看：CPU/内存/磁盘/QPS/P95 | 给 LB/编排看：还活着吗？能接流量吗？ |
| 鉴权 | `checkPlatformAdmin(token)` —— **平台管理员专用** | 必须免登录 |
| 检查依赖 | 读 OSHI 指标、写 `metric_sample` 表 | 只探进程与关键依赖连通性 |

`MonitorController.java:61` 的 `api-health` 名字很接近，但它要平台管理员 token，**负载均衡探活时不可能带**。

**所以第 19 条不能用"我们已经有 monitor 了"来消掉**。需要的是 Actuator 的 `health` 端点（或一个免登录的 `/healthz`），且要有**独立于业务鉴权**的放行 —— 注意 `SecurityConfig.java:34-36` 明确写着"`SecurityConfig` 白名单与 `JwtAuthenticationFilter.WHITELIST_PATHS` 保持一致，两处分处两地是本批之前的既有隐患"，**加探活端点必须同时改两处**，只改一处会出现 401 或 SecurityContext 被清空。

### 🟡 H4：告警为零（P0）

报告第 19 条里的"**告警**"目前完全没有落点：`monitor` 指标落库了（`metric_sample` / `metric_hourly`），但**没有任何阈值判定与外发通道**。指标只在管理端页面被动展示，需要人主动去看 —— 这与"每周人工 `df -h` 巡检"没有本质区别。

至少该有的三条告警：

| 触发条件 | 为什么必须有 |
|---|---|
| 磁盘使用率 > 85% | 直接对应上面 H2 的日志写满 |
| `NotifyTask` 连续 N 轮 `total=0` 但确有应发课次 | 上课提醒静默失效，外部无任何感知 |
| `message-service` 连续探活失败 | 预约可成功、通知全丢，用户只在课前才发现 |
