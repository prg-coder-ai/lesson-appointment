# 技术方案：小程序平台管理端「移动审批 / 移动检查」

> 编写时间：2026-11-05 11:36　|　状态：**待拍板（本文只出方案，未改任何业务代码）**
> 范围：`miniprogram/package-admin/*`、`shared/apiPaths.js`、`miniprogram/app.json`、`frontend/js/shared-domain-bridge.js`（生成物）
> 目标：把平台管理员「运营」页里 6 个"建设中"菜单接通，围绕移动端两类高频动作设计——**审批**（待审管理员通过/冻结、租户启停、指定套餐）、**检查**（总览数字、名单明细、额度用量、到期预警、日志）。

## 2. 五个关键断点（决定方案形态，不是"照搬 Web"）

1. **Web 端「用户管理」其实没有"审核通过"按钮**：`platform-admin-user.js:98-108` 的按钮由 `isFrozen` 决定，对 `pending` 账号显示的是「冻结」，只有 frozen↔active 来回切。后端 `/user/updateStatus` 却完全支持 `status=active`。→ **移动端补「通过」是一笔真实增量，也是"方便审批"的核心**。
2. **自注册租户没有 pending 态**：`PromoService.registerTenant` 建租户即 `status=1 正常` + `trialStatus='trial'`，14 天试用。所以「审批租户」在移动端的真实动作是：查看新租户 → 指定/切换套餐（转正）→ 必要时停用，而不是点"通过"。
3. **平台用户页必须用 `USER_PLATFORM_PAGE`，不能用 `USER_PAGE`**：后者的 `UserMapper.listByConditionPage` XML **没有 tenantId 条件**，且平台管理员 `tenantId=0` 时租户插件 `ignoreTable=true` 不拼租户条件（11-05 11:21 刚踩过）；前者才返回 `orgName` 且支持 `status=pending`。
4. **「审计日志」是坏链**：菜单已接通但页面空白。若只补"系统日志"而不补它，平台管理员在系统维护组仍会踩空 → 必须一并补实。
5. **两类日志形态不同**：`/logs/*` 是纯文本 tail（含服务器内部信息），`/audit-logs` 是结构化记录。移动端应**结构化优先**，纯文本只做「按级别/关键字查最近 N 行」的轻量查看，不照搬 Web 的整页日志浏览器。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 误操作（停用租户、冻结管理员、指定套餐）在移动端更易发生 | 全部 `wx.showModal` 二次确认 + 写明对象名称；不在移动端放删除类动作；写操作后只刷新当前页，不静默改本地状态 |
| 两处「待审核」数字打架 | 抽 `core/platform-pending.js` 单一实现；运营页与总览页同源 |
| 平台管理员 `tenantId=0`，写接口容易被误传 0 | `create-from-template` 的 `tenantId` **必须来自列表选中项**，禁止从 token/session 取；`/user/add` 类本次不做 |
| `/logs/*` 返回服务器内部文本（IP、堆栈、SQL） | 移动端只读、默认 ERROR 级别、限 100 行、不缓存到本地存储、不提供导出/分享 |
| 小程序 `Page` 内同名方法键会静默覆盖 | 新页方法名统一前缀（如 `pu* / tn* / pkg* / ov* / st* / lg*`），提交前 grep 重复键 |
| 分包体积 / 守卫红 | 现 259K 远低于 2M；新增常量全部有引用点；四步链跑完再提交 |
