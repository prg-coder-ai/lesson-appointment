## 参数 1：`monitor.sample.interval.seconds`（默认 60）

### 一句话

**指标采样落库的最小间隔。** Scheduler 每分钟跑一次，但不是每次都真的写指标表——它看距上次落库够不够这个间隔，不够就跳过。

### 调用链

```
Spring Scheduler 心跳（每 60 秒）
  └─ MonitorTask.sampleMetrics()                       ← [MonitorTask.java:55]
       └─ taskEnabled() == true?                       ← 先查 monitor.task.enabled
       └─ lastSampleTime + interval <= now?             ← [L62-L63] 这个参数参与比较
       └─ MonitorService.sampleAndSave()                ← [L67] 条件满足才真采集
            └─ collect() → INSERT sys_metric_sample      ← [MonitorService.java:104-111]
```

### 关键代码

```java
// MonitorTask.java:55-68
@Scheduled(fixedDelay = TICK_MS)  // TICK_MS = 60_000L，硬写死 1 分钟心跳
public void sampleMetrics() {
    if (!taskEnabled()) return;
    int intervalSeconds = sysConfigService.getInt(KEY_SAMPLE_INTERVAL, 60);
    LocalDateTime now = LocalDateTime.now();
    if (lastSampleTime != null
            && lastSampleTime.plusSeconds(intervalSeconds).isAfter(now)) {
        return;  // ← 间隔没到就跳过，不采
    }
    lastSampleTime = now;
    monitorService.sampleAndSave();
}
```

### 边界条件与改后效果

| 间隔值 | 行为 |
|---|---|
| 60（默认） | 每分钟采一次，`sys_metric_sample` 每分钟多一行 |
| 设 30 | 每 30 秒一行（比心跳还短？不会——心跳本身是 60 秒一跳，所以 30 和 60 实际效果一样） |
| 设 300 | 每 5 分钟一行，采样点稀疏。趋势图上的折线变成阶梯 |
| 设 1 | 心跳 60 秒 + interval 1 → **每次心跳都采**，和 60 没区别 |
| 设 0 | `plusSeconds(0)` → 永远等于 now → 永远跳过 → **永远不采**（坑！想关采样应该用 task.enabled） |

> **坑点**：Scheduler 心跳硬写死为 1 分钟（`TICK_MS = 60_000L`）。interval 设小于 60 没有实际意义——你最多每分钟采一次。真想更密，得改代码里的 `TICK_MS`。

### 用户可见

平台监控面板 → 趋势图的数据点密度变化。间隔越大，曲线越粗糙。

## 参数 4：`monitor.online.idle.minutes`（默认 5）

### 一句话

**"在线"的活跃判定窗口——过去 N 分钟内有活动（心跳续期）就算在线。** 三处用法：在线人数统计、过期会话清理（乘 6）、监控面板展示。

### 调用链（3 个消费者）

```
MonitorService.collect()
  └─ UserSessionService.countOnline(null)                    ← 采样时顺便采一下在线人数
       └─ since = now - idleMinutes                           ← [UserSessionService.java:161]
       └─ SELECT COUNT(*) FROM user_session
            WHERE status = 'online' AND last_active >= since

MonitorTask.cleanExpiredSession()          ← cron "0 0/5 * * * ?" 每 5 分钟
  └─ UserSessionService.cleanExpired()
       └─ expireBefore = now - idleMinutes * 6                ← [UserSessionService.java:188]
       └─ UPDATE user_session SET status='expired'
            WHERE status='online' AND last_active < expireBefore

DashboardService.getExpireWarning()        ← 平台面板"在线用户数"
  └─ 同上 countOnline()
```

### 关键代码

```java
// UserSessionService.java:159-170
public int countOnline(Long tenantId) {
    int idleMinutes = sysConfigService.getInt(KEY_ONLINE_IDLE, 5);
    LocalDateTime since = LocalDateTime.now().minusMinutes(idleMinutes);
    LambdaQueryWrapper<UserSession> wrapper = new LambdaQueryWrapper<>();
    wrapper.eq(UserSession::getStatus, STATUS_ONLINE)
           .ge(UserSession::getLastActive, since);  // ← last_active 晚于 since = 活跃
    // ...
}

// UserSessionService.java:186-198 — 过期清理用的是 idleMinutes * 6
public int cleanExpired() {
    int idleMinutes = sysConfigService.getInt(KEY_ONLINE_IDLE, 5);
    LocalDateTime expireBefore = LocalDateTime.now().minusMinutes(idleMinutes * 6L);  // ← 乘 6！
    // 5 * 6 = 30 分钟没活动才过期
}
```

### 关键机制：乘 6 的缓冲

```
在线判定窗口：idleMinutes = 5   分钟内有心跳 → 算在线
过期清理窗口：idleMinutes × 6 = 30 分钟没心跳 → 置 expired

→ 中间有 25 分钟的缓冲：
   15 分钟没活动 → countOnline() 不算你，但 session 还是 online
   20 分钟没活动 → 同上
   35 分钟没活动 → session 被置 expired
```

### 边界条件

| 值 | countOnline 窗口 | cleanExpired 窗口 | 用户感知 |
|---|---|---|---|
| 5（默认） | 5 分钟 | 30 分钟 | 离开 5 分钟面板上就不算你在线，但登录态不失效 |
| 2 | 2 分钟 | 12 分钟 | 离开很快就显示离线 |
| 30 | 30 分钟 | 180 分钟 | 离开很久还显示"在线"，显得虚 |

```
       └─ 返回 { slowCount, slowThresholdMs, slowApis: [...] }
```

### 关键代码

## 参数 6：`monitor.quota.warn.percent`（默认 80）

### 一句话

**套餐额度预警阈值（黄色）。** 租户某维度用量（course/student/user 等 6 项）占套餐上限的百分比 ≥ 此值 → 租户的"额度等级"变成 `warn`，面板上**标黄**提示。

### 调用链

```
平台面板 / 租户面板 → 用量卡片
  └─ TenantQuotaService.getUsage(tenantId)                   ← [TenantQuotaService.java:265]
       └─ warn = sysConfigService.getInt(KEY_QUOTA_WARN, 80)
       └─ danger = sysConfigService.getInt(KEY_QUOTA_DANGER, 95)
       └─ fill() × 6 个维度 → 每个维度算 percent
       └─ maxPercent = max(6 个 percent)
       └─ if maxPercent >= danger → level = "danger"         ← 红色
          if maxPercent >= warn   → level = "warn"           ← 黄色
          else                    → level = "normal"         ← 正常
```

### 关键代码

```java
// TenantQuotaService.java:272-298
int warn = sysConfigService.getInt(KEY_QUOTA_WARN, 80);
int danger = sysConfigService.getInt(KEY_QUOTA_DANGER, 95);

// fill() 对 6 个维度各算一个 percent（用量/套餐上限×100）
fill(dto, COURSE, pkg, countUsage(tenantId, COURSE));
fill(dto, SCHEDULE, pkg, countUsage(tenantId, SCHEDULE));
// ...

int maxPercent = maxOf(dto.getCoursePercent(), dto.getSchedulePercent(), ...);
if (pkg != null) {
    if (maxPercent >= danger) {
        dto.setQuotaLevel("danger");    // ← 红
    } else if (maxPercent >= warn) {
        dto.setQuotaLevel("warn");      // ← 黄
    }
}
```

### 关键机制

```
6 个维度（course / schedule / user / teacher / student / teacher_publish）
每个维度都算 percent = 当前用量 / 套餐限额 × 100

取 6 个 percent 的最大值 → 与 warn/danger 比较

warn 和 danger 是**两级、取最大值判断**，不是各自独立生效
```

### 边界条件

| 值 | 效果 |
|---|---|
| warn=80, danger=95（默认） | 任意维度到 80% → 黄；到 95% → 红。中间 15% 是缓冲带 |
| warn=90, danger=85 | **逻辑矛盾**：danger < warn，永远到不了 warn 区。`if max >= danger → danger → return`，直接跳过 warn |
| warn=0 | 所有租户立刻变 warn，不合理 |
| warn=100, danger=100 | 只有刚好打满才标红、永远不标黄——等于只有 danger 一档 |

> **代码没有校验 warn < danger**，配错了会导致阈值判定逻辑错误。这是个前端/后端都该加校验的地方。

## 参数 1：`monitor.sample.interval.seconds`（默认 60）

### 后台定时任务：MonitorTask.sampleMetrics()  —— **唯一引用点**

```java
// MonitorTask.java:55-68
@Scheduled(fixedDelay = TICK_MS)  // TICK_MS = 60_000L，硬写死 1 分钟心跳
public void sampleMetrics() {
    if (!taskEnabled()) return;                              // ← 参数 8 开关
    int intervalSeconds = sysConfigService.getInt(KEY_SAMPLE_INTERVAL, 60); // ← 参数 1 在这里读
    LocalDateTime now = LocalDateTime.now();
    if (lastSampleTime != null
            && lastSampleTime.plusSeconds(intervalSeconds).isAfter(now)) {   // ← 值参与比较
        return;  // 间隔没到 → 跳过本次采集
    }
    lastSampleTime = now;                                    // ← 更新基准
    monitorService.sampleAndSave();                          // ← 采集落库 sys_metric_sample
}
```

**值怎么被消费**：`plusSeconds(intervalSeconds)` → 判断"距上次落库是否够这个秒数"。够了才真的采，不够就跳。

```java
    fill(dto, TEACHER, pkg, countUsage(tenantId, TEACHER));
    fill(dto, STUDENT, pkg, countUsage(tenantId, STUDENT));
    fill(dto, TEACHER_PUBLISH, pkg, countUsage(tenantId, TEACHER_PUBLISH));
```

## 参数 10：`tenant.stats.retention.months`（默认 12）—— tenant 组

```java
// MonitorTask.java:171-186
@Scheduled(cron = "0 20 2 * * ?")
public void cleanExpiredSnapshot() {
    if (!taskEnabled()) return;                                  // ← 参数 8
    int keepMonths = sysConfigService.getInt(KEY_STATS_RETENTION, 12); // ← 参数 10
    String deadlineMonth = YearMonth.now().minusMonths(keepMonths).toString(); // ← 比如 2024-10
    LambdaQueryWrapper<TenantStatsMonthly> wrapper = new LambdaQueryWrapper<>();
    wrapper.lt(TenantStatsMonthly::getStatMonth, deadlineMonth);           // ← stat_month < 截止月 的删除
    int rows = tenantStatsMonthlyMapper.delete(wrapper);
    if (rows > 0) log.info("清理过期月度快照, 保留{}个月, 删除{}条", keepMonths, rows);
}
```

### 边界陷阱

| 值 | 效果 |
|---|---|
| 12（默认） | 2026-10 时，2025-09 及以前的快照被清 |
| 0 | `minusMonths(0)` → deadlineMonth = 当前月 → 所有历史快照被清（只留本月） |
| 负数 | `minusMonths(-6)` → deadlineMonth = 未来 6 个月 → **一个快照都清不掉**（`lt(未来月份)` 永远不成立） |
