## 1. 总体结论

项目在**认证基线、多租户隔离框架、登录风控、审计留痕、部署加固**上已有成体系的设计：BCrypt 密码哈希、JWT 双 Token + 类型区分、声明式授权表 + `denyAll` 兜底、MyBatis-Plus 租户插件、登录频率闸 + 滑块挑战、Nginx 限流与安全响应头、非 root 容器运行、Actuator 收敛等，说明前期做过一轮等保导向的整改。

但走读中仍发现一类**结构性薄弱点**：权限校验集中在"角色层"（谁能调用接口），部分写接口与查询接口的"数据归属层"（这条记录是不是我的 / 是不是本租户的）在控制器/服务层缺失或被注释；另有若干公开端点、动态 SQL、前端渲染与配置默认值需要收敛。综合判断：**未发现已确认的高危可直接利用入口，但存在多个中高风险的越权与数据暴露面，建议上线前按第 12 章清单收口。**

风险分布概览：

| 类别 | 高 | 中 | 低 | 主要风险点 |
|---|---|---|---|---|
| 认证与会话 | 0 | 2 | 2 | Token 存 localStorage、无服务端访问令牌黑名单、默认密钥兜底 |
| 授权越权 | 2 | 4 | 1 | 课程/预订/排期数据归属校验缺失或被注释；部分端点角色声明过宽 |
| 数据隔离/完整性 | 0 | 2 | 1 | 忽略租户插件的级联表、动态表名 SQL、软删除/孤儿数据历史 |
| 输入与注入 | 0 | 2 | 1 | DTO 校验覆盖不全、级联 `${}` 动态 SQL 依赖服务端白名单 |
| 文件上传 | 0 | 1 | 1 | MIME 来自客户端、未做魔数校验 |
| 隐私与日志 | 1 | 1 | 1 | 列表接口返回对象字段未裁剪、手机号/邮箱等明文与加密口径 |
| 运营/可用性 | 0 | 2 | 1 | 公开接口面、定时任务串行、错误信息回显 |
| 前端 | 0 | 2 | 1 | innerHTML 拼接用户数据、Token 存储方案 |

## 2. 已具备的安全措施（基线较好的部分）

以下措施在代码中已落地，属于正向基线，整改时应保留：

### 2.1 认证与口令

- **密码哈希**：`UserService` 使用 `BCryptPasswordEncoder` 存储密码，登录 `matches()` 校验；账号不存在时用预置哈希做等价耗时比对（`safeDummyMatch`），缓解时序枚举。
- **账号状态闸**：仅 `active` 可登录，`pending / frozen / inactive` 一律拦截；跨租户账号、归属不符与"账号不存在"返回一致文案，降低账号枚举。
- **双 Token 机制**：access（1 小时）+ refresh（7 天），JWT 带 `type` claim 区分类型；刷新接口忽略前端传入的 role/account，**role 从 user 表实时查询**，修复了"前端传 platform_admin 提权"的旧漏洞；refresh 轮换 + DB 一致性二次校验 + 并发轮换缓存。
- **登录风控**：IP / 账号 / 租户 / openid 多维度频率闸，风险评分 + 滑块挑战（一次性票据、失败次数上限、轨迹点数/耗时校验）；微信登录/注册先限流再调微信 `code2Session`。

### 2.2 授权与租户隔离

- **声明式授权表**：`AuthzRules.RULES` 集中声明每个端点允许的角色，`SecurityConfig` 展开为 `hasRole/hasAnyRole`，兜底 `anyRequest().denyAll()`——漏声明直接 403 而不是静默放行。
- **多租户插件**：`TenantLineInnerInterceptor` 自动拼接 `tenant_id` 条件；无租户上下文时兜底 `-1`（不查全量）；平台管理员 `tenantId=0` 走全量；平台表/共享表在 `IGNORE_TABLES` 显式列出。
- **方法级兜底**：`PermissionCheck` 提供 `checkAdmin / checkPlatformAdmin / checkTeacher / checkStudent / checkTeacherOwner / checkStudentOwner / checkTeacherSelfOrAdmin / checkTenantRead` 等角色与归属校验工具，部分控制器已调用。
- **操作审计**：登录/登出/重置密码/踢人/课程删除/预订取消/指派排期等关键动作带 `@Audit` 注解留痕。

### 2.3 数据与业务完整性

- **并发预订防护**：`BookingService.create` 先对排期加行锁，锁内完成查重、名额校验、落库；候补不占席位；候补转正有 CAS 防重复递补与课次生成幂等。
- **字段级加密**：手机号/邮箱等敏感字段走 AES-GCM-256 + HMAC-SHA256 盲索引；日志中账号以 HMAC 截断形式记录，不打明文。
- **错误体规范**：统一 `Result` 结构与错误码映射，401/403 有独立 EntryPoint/AccessDeniedHandler。

### 2.4 部署与外围

- **Nginx 安全头**：HSTS、X-Frame-Options DENY、nosniff、X-XSS-Protection、Referrer-Policy、Permissions-Policy。
- **分层限流**：登录/注册专用闸、公开 GET 闸、业务 API 闸、SSE 单独配置。
- **容器加固**：非 root 用户运行、JRE 精简镜像、单独信任库；Actuator 仅暴露 health/info，其余端点 Basic Auth 保护，env/beans/loggers/heapdump 等显式关闭。
- **CORS 收敛**：来源走配置，禁止单独 `*`；请求头/方法/暴露头最小化。

## 4. 专题分析一：认证与会话安全

### 4.1 现状

- 过滤器：`JwtAuthenticationFilter` 从 `Authorization: Bearer` 解析，`verifyAccessToken` 验签 + 过期 + type=access 校验，通过后把 `userId/role` 写入 SecurityContext。
- 登录：`authController#toLogin` → 风控闸/挑战票据 → 租户状态校验 → `UserService.login` 校验密码与状态 → 签发双 Token 并持久化 refresh。
- 刷新：`/auth/refreshToken` 校验 type=refresh、JWT 与 DB 一致性、用户未冻结，实时取库内 role，轮换 refresh。
- 登出：清 SecurityContext + 删 refresh 凭证 + 结束会话。

### 4.2 风险点与说明

1. **Access Token 无服务态吊销（M-3）**：JWT 自包含，过滤器只验签名与过期，不查询 DB。以下场景在 access 过期前仍有效：
   - 管理员冻结/停用用户；
   - 管理员踢人（仅删 refresh）；
   - 用户改密码后旧 access 未失效。
   缓解现状：`checkTeacher/checkStudent/checkAnyLogin` 部分路径会查库状态，但覆盖面不全。建议关键写接口补齐状态校验，或引入短期黑名单/token version。

2. **Token 类型兼容期放行（设计取舍，需知悉）**：`verifyAccessToken` 对无 type claim 的老 token 放行；`isTokenOfType` 对老 refresh 兼容。属迁移期折中，DB 兜底，但应设定废弃期限，清理老 token 后收紧为强校验。

3. **登录角色来自请求体（需确认服务端覆盖）**：登录 DTO 带 `role`，`UserService.login` 最终以库内 user.role 签 token（刷新链路已明确忽略前端 role）；建议复核密码登录链路同样以库内 role 为准，避免前端 role 参与签发。

4. **会话与设备档案**：`deviceId` 为端上自报，只作降权信号；`UserSessionService` 做在线统计与踢人。建议复核会话表是否随用户注销/租户删除清理。

5. **密码策略**：strict-mode 下强制 8–64 位 + 大小写 + 数字 + 特殊字符；非严格档降级为非空。需确认生产 cloud 档恒为严格档，且默认重置密码（如 `12345678`）首次登录强制改密。

### 4.3 建议

- access TTL 维持 1 小时；refresh 7 天轮换、单设备可追溯；登出/踢人/冻结同步吊销。
- 关键写接口二次校验 `user.status == active`。
- 登录/注册/找回密码链路统一返回不可区分的错误文案；账号枚举接口保留最严限流。
- 补齐"改密码/解绑微信"后旧设备强制重登的链路。

## 5. 专题分析二：授权与越权（垂直 / 水平 / 跨租户）

### 5.1 授权模型现状

- 垂直角色：`platform_admin / admin / teacher / student`，规则集中在 `AuthzRules.RULES`，Spring Security `hasRole` 匹配。
- 方法兜底：`PermissionCheck` 按角色 + 账号状态 + 归属校验。
- 跨租户：平台管理员 tenantId=0 全量；其余由租户插件自动附加 `tenant_id`。

### 5.2 已识别的缺口

#### 5.2.1 水平越权：预订域（H-1）

`BookingController` 现状：

| 端点 | 角色校验 | 归属校验 | 风险 |
|---|---|---|---|
| `POST /create` | checkAnyLogin | 服务层按 `booking.studentId`，但 studentId 来自请求体 | 需确认 create 时 studentId 强制取 token.userId，禁止客户端指定他人 |
| `POST /update/{id}` | checkAdmin | 管理员路径，按租户隔离 | 复核跨租户 admin 不可操作他租户 |
| `POST /updateStatus` | checkAnyLogin | **未校验归属**（注释挂账） | 学生可传他人 bookingId 改状态 |
| `GET /{id}` | checkAnyLogin | **未校验归属** | 遍历读他人预订 |
| `POST /list` / `POST /page` | checkAnyLogin | 仅租户插件隔离 | 学生可见本租户全部预订列表 |
| `GET /ListByScheduleId/{scheduleId}` | checkAnyLogin | 无课程/排期归属校验 | 可见任意排期名单 |
| `GET /waitlist/{scheduleId}` | checkAnyLogin | 无归属校验 | 爬取候补队列 |
| `GET /countByScheduleId/{scheduleId}` | checkAnyLogin | 无归属校验 | 枚举排期余量 |

**修复方向**：
- 学生视角列表强制 `studentId = 当前 token 用户`；
- 详情/状态变更先加载 booking，比对 `studentId == 当前用户`（教师比对课程 teacherId，管理员比对租户）；
- 排期/课程与 booking 联查时带上归属条件；服务层封装统一 `assertBookingAccessible(booking, token)`。

**实施记录（2026-11-19，学生维度已落地）**

本轮范围经确认后**只收学生维度**，教师维度（教师只能看自己课下的预订）标记为待做，原因见下。

| 端点 | 收口方式 | 位置 |
|---|---|---|
| `POST /create` | 学生：`studentId` 强制取令牌 userId，**不信任请求体**；管理员/教师代订：保留请求体，但要求目标账号真实存在且属本租户（借租户插件判定，平台管理员短路查全量） | `BookingController#applyOwnerOnCreate` + `PermissionCheck#assertSameTenantUser` |
| `POST /updateStatus` | 先加载 booking，学生只能改自己的行；管理员/教师路径不变（**刻意不动**：2026-10-10 曾按管理语义收紧，误伤学生自助操作致 403） | `PermissionCheck#checkStudentSelf` |
| `GET /{id}` | 同上，学生只能读自己的 | 同上 |
| `POST /list`、`POST /page` | **按角色分支**：学生强制 `userId=本人` + `userRole=student`（忽略请求体），教师/管理员原样透传。SQL 侧本就支持这两列过滤，缺的只是「不信任客户端」 | `BookingController#scopeStudentSelf` |

`checkStudentSelf` 的 fail-closed 语义：行的 `student_id` 为空时同样拒绝——判不了归属就必须按不许处理，否则一次脏数据就变成一次越权。

**未做（待办）**：

| 项 | 为什么留到下一批 |
|---|---|
| 教师维度（教师只能看/改自己课下的预订） | 需要 schedule→course→teacherId 两跳查询，且「今日课程」「排期名单」「我的课堂」多页面共用同一批端点，改错会同时打断三端 |
| `GET /ListByScheduleId`、`/countByScheduleId`、`/waitlist` | 学生端确实在用它算「剩余席位」「候补位次」——直接按学生过滤会把位次算错（需要返回「我在队列第几位」而不是「只给我看我自己那行」），属于接口契约调整而非单纯加校验 |
| `POST /update/{id}` | 已是 `checkAdmin`，管理员路径，风险等级低；跨租户复核随平台管理员维度一起做 |

回归：`api/src/test/.../PermissionCheckStudentScopeTest`（8 例）覆盖三条边界——学生只能碰自己的行、**教师/管理员必须原样放行**、代订的同租户闸门 fail closed；变异验证：把归属校验短路成「永不拦」后 2 例立即变红。

#### 5.2.2 水平越权：课程与排期域（H-2）

- `CourseController#update`：`checkCourseOwner` 被注释，`updateById` 全字段更新；请求体可带任意 `courseId/teacherId`。
- `deleteById/{id}`、`deleteByTemplateId/{id}`：仅教师/管理员；教师分支未校验课程归属。
- `ScheduleController#assign-student`：方法体校验被注释，`teacherId/studentId/scheduleId` 全来自请求体。
- `generate`：规则 ALL_ROLES + 校验注释；`checkConflict` 未校验排期归属。

**修复方向**：
- 所有写操作"先查记录再比对归属"，禁止信任请求体中的归属字段；
- 管理员放行，但限定本租户（平台管理员除外）；
- 恢复被注释的 `checkTeacherOrAdmin / checkTeacherOwner` 调用。

**实施记录（2026-11-19，已全部落地）**

| 端点 | 收口方式 | 位置 |
|---|---|---|
| `POST /course/update` | 恢复 `checkCourseOwner`；教师请求体的 `teacherId` 被**钉回本人**（防止把课程改挂到别人名下后接管排期/名单）。管理员保持请求体值（用于课程转交） | `CourseController#assertCourseOwnedByTeacher` |
| `DELETE /course/deleteById/{id}` | 同上。该端点会连带删「排期→预订→课次」，是不可逆整链删除 | 同上 |
| `DELETE /course/deleteByTemplateId/{id}` | 新增 `checkTemplateOwner`：模板下若混有他人课程则拒绝。一个模板可被多名教师共用，而本端点会整批删，教师应改用 `deleteById` 删自己那门 | `CourseService#checkTemplateOwner` |
| `POST /schedule/assign-student` | 恢复 `checkTeacherOrAdmin`；教师调用时校验排期在其本人课下（schedule→course→teacherId 两跳），且**返回的 teacherId 强制为本人**——请求体传别人也不会把预订记到他人名下。管理员保留请求体（可代教师指派，只校验排期存在） | `ScheduleController#resolveAssignTeacher` |
| `POST /schedule/generate` | `AuthzRules` 由 `ALL_ROLES` 收窄为 `TEACHER_OR_ADMIN` + 补方法体校验（原先学生也能调） | `AuthzRules` / `ScheduleController#generateList` |
| `POST /schedule/checkConflict` | 声明本来就是教师/管理员，但方法体零校验——补上。原状会把别的教师排期名回显给任何登录用户 | `ScheduleController#checkConflict` |

权限失败在 `assign-student` 里单独 `catch (NoPermissionException)` 返回 **403**，不再混进原来的 `500 error:...`（前端对 403 提示「无权限」，对 500 只显示失败，混在一起等于把权限问题伪装成系统故障）。

**一处刻意的不对称**：`course/update` 只在教师分支把 `teacherId` 钉回本人。管理员保留请求体是因为「把课程转交给另一名教师」是既有运维动作，统一钉死会让转交失效。

#### 5.2.3 垂直越权：规则与方法体不一致（M-1）

`AuthzRules` 是第一道角色闸，方法体是第二道。两者不一致时：规则宽于方法体 → 靠方法体兜底；方法体被注释 → 规则成唯一防线。需逐端点核对"规则角色 ⊇ 方法体校验角色"，并补守卫脚本检查"被注释的 check*"。

#### 5.2.4 跨租户边界

- 租户插件对走 MP 的表自动隔离；`IGNORE_TABLES` 与 `@InterceptorIgnore` 的表由业务层显式控制，需逐一复核是否都有显式 `tenant_id` 条件。
- 平台表（推广、风控、会话、微信绑定、行业词表等）被排除隔离是业务语义所需，但其中用户关联数据不得按租户串读。
- 公共只读端点（公开教师资料、可用排期）不得泄露未发布/未激活教师信息与敏感联系方式。

## 6. 专题分析三：数据隔离与数据完整性

### 6.1 多租户隔离

- 正向：`TenantLineInnerInterceptor` + `TenantContext`（拦截器从 JWT 解析 tenantId，`afterCompletion` 清理）；无上下文兜底 -1。
- 关注点：
  1. **异步线程/定时任务**：`TenantContext` 是 ThreadLocal，异步线程池内不会自动继承；需确认任务执行时显式设置/清理上下文，否则出现 -1 兜底查空或误查。
  2. **忽略插件的表**：级联 Mapper、推广表、风控表、协议表等，读写必须显式带租户条件；`CascadeMapper` 跳过插件后，入口权限校验（checkTeacherOrAdmin / checkPlatformAdmin）是唯一边界。
  3. **原生 SQL / XML 自定义查询**：需复核是否绕过插件自动条件（XML 手写 where 中 tenant_id 是否补齐）。

### 6.2 数据完整性与级联

- 历史背景：库外键曾全 CASCADE，导致 booking 被级联删除后 appointment 成孤儿；现改为程序内显式规则表 `CascadeRules` + `ReferentialCascadeService`，支持 dryRun 预估影响面、软删除/恢复/物理删除区分。
- 关注点：
  1. 级联规则覆盖是否完整（守卫脚本 `check-cascade-rules` 纳入 CI）；
  2. 软删除后的数据可恢复性与历史留痕；
  3. 并发删除与并发预订的事务边界（排期锁、CAS 递补已具备，需复核取消/删除路径）；
  4. 定时对账（额度/孤儿数据）定期运行并告警。

### 6.3 敏感字段加密

- AES-GCM-256 加密存储 + HMAC 盲索引支持等值检索；日志不打明文。
- 关注点：密钥由环境变量注入，strict-mode 阻断默认值；需确认密钥轮换流程、密钥备份与丢失场景下的数据可恢复性；加密字段在 VO 出参时按角色/必要性解密返回。

## 7. 专题分析四：输入校验、注入与文件上传

### 7.1 SQL 注入

- MyBatis-Plus 条件构造器与 `#{}` 参数绑定为主，常规查询注入风险低。
- **动态 SQL 点**：`CascadeMapper` 使用 `${}` 拼接表名/列名（M-5）。当前取值来自静态规则常量，未接请求参数；建议加标识符白名单校验并在 CI 禁止新增 `${}` 拼接用户可控值。
- XML Mapper 需复核排序字段、表名等动态片段是否存在 `${}`。

### 7.2 入参校验

- 现状：部分 DTO 有 `@Validated`，`LoginDTO` 等缺少字段约束；枚举（语言、难度、形式、状态）应在服务层做白名单校验，不接受任意字符串入库。
- 建议：写接口统一 `@Validated`；补充长度、数值范围（时长 15 的倍数、席位 ≥1、金额 ≥0）、时间格式与时区校验；分页参数上限保护。

### 7.3 文件上传与伺服

- 已做：体积上限（业务 5MB / 容器 20MB）、扩展名白名单、MIME 二次校验、UUID 重命名、按日期分目录、伺服路径规范化防 `..` 穿越。
- 缺口（M-4）：MIME 取自客户端 `Content-Type` 可伪造；未校验文件头魔数；未做服务端图片重绘；公开伺服路径无鉴权（设计如此，供匿名浏览），需确认文件名不可猜之外无目录列举。
- 建议：魔数校验 → 解码重绘压缩 → 隔离存储域；限制响应 Content-Disposition；定期清理无效文件。

### 7.4 其他注入面

- **XSS**：见第 10 章，前端渲染是主要面；后端存储侧建议对富文本/简介做标签白名单过滤。
- **SSRF**：微信 `code2Session` 为固定外部域名；若后续增加 URL 抓取/网页引用（教师外部链接），需防 SSRF（内网地址、协议白名单）。
- **日志注入**：记录账号/UA/设备标识前应去除换行与控制字符。

## 8. 专题分析五：敏感数据与隐私保护

### 8.1 数据分类关注点

| 数据 | 现状 | 建议 |
|---|---|---|
| 密码哈希 | BCrypt 存储，不回显 | 确认任何出参不含 password 字段；哈希不下发前端 |

### 9.1 风控与防刷

- 已有：登录/注册/微信链路限流、滑块挑战、推广注册防刷（IP/手机号/试用名额）。

## 10. 专题分析七：前端安全

### 10.1 Token 存储

- 现状：token/refresh/currentUser 存 localStorage（与 cookie 双写）；注释已自述 XSS 风险。
- 风险：localStorage 可被同源 JS 读取；配合 innerHTML 未转义形成 XSS 后 token 可被窃取。
- 建议（按优先级）：
  1. 先堵住 XSS：统一转义、CSP 头、移除内联风险脚本；
  2. 评估改 HttpOnly + Secure + SameSite Cookie 存 token，JS 不可读；
  3. 过渡期缩短 access TTL、敏感操作要求重新校验；登出时彻底清理本地凭证。

### 10.2 渲染与 XSS

- 现状：大量 `innerHTML = 模板字符串` 拼接姓名、课程名、简介、排期信息等；`document.write` 重复引脚本。
- 建议：
  - 提供统一 `escapeHtml(str)`，所有插入文本的变量先转义；
  - 动态 HTML 结构用 `createElement` + `textContent`；
  - 富文本（教师简介/证书描述）走后端标签白名单；
  - 部署 CSP：`default-src 'self'`，收紧 `script-src / img-src / connect-src`，禁止内联脚本与 `eval`。

### 10.3 其他前端项

- 前端鉴权路由守卫仅为体验层，安全以后端校验为准（不可依赖前端隐藏菜单/按钮）。
- 复核前端代码与构建产物 `dist/` 不夹带测试密钥、内部地址、调试开关。
- 外链（教师个人链接）新窗口打开应加 `rel="noopener noreferrer"`。
