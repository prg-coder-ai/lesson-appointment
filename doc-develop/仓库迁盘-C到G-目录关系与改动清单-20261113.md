# 仓库迁盘：`C:\Users\Administrator\WorkBuddy` → `G:\WorkBuddy`

- 日期：2026-11-13
- 触发：用户把整个 `WorkBuddy` 根目录复制到 G 盘，要求把工作目录切到 `G:\WorkBuddy` 并梳理目录关系
- 结论：**副本完整（8777/8777 文件、28/28 顶层条目、`.workbuddy` 零差异），git 仓库在 G 盘可直接使用；仓库内 16 处硬编码 `C:\...` 绝对路径已改为自定位；但 WorkBuddy 应用本身没有"全局工作目录"配置项，"切到 G 盘"这一步只能在每次创建任务时手动选**

## 一、先把机制说清楚：应用层不存在"设置工作目录"这个开关

查官方文档（[创建任务](https://www.workbuddy.cn/docs/workbuddy/Create-Task)）确认，工作空间是**任务级**指定的：

> 点击输入框左下角的**选择工作空间**，选择当前任务要使用的目录。选择完成后，WorkBuddy 会基于该目录读取和处理文件。也可以直接开始任务，WorkBuddy 会在**默认目录**中生成结果。

即：

| 层级 | 机制 | 能否改 |
|---|---|---|
| 默认目录根 | `C:\Users\Administrator\WorkBuddy`，应用自动创建 `<时间戳>` 子目录 | **无公开配置项** |
| 单个任务的工作空间 | 创建任务时点「选择工作空间」指定任意目录 | 每次手动选 |

所以"设置工作目录到 `G:\WorkBuddy`"的实际落地是：**新建任务时，把工作空间选成 `G:\WorkBuddy\2026-08-30-17-19-24`**（主项目）。不选的话，新任务仍会落在 `C:\Users\Administrator\WorkBuddy\<新时间戳>`，与 G 盘无关。

> 如果连默认目录也要落在 G 盘，唯一技术手段是把 `C:\Users\Administrator\WorkBuddy` 换成指向 `G:\WorkBuddy` 的目录联接（`mklink /J`）。**不建议**：需要管理员权限、必须先清空原目录、且应用对 junction 的路径归一化行为未经验证，一旦出问题是"新建任务失败"级别。本次未做。

## 四、已修复的硬编码绝对路径（16 个文件）

迁盘后这些路径指向不存在的目录，会以「文件读不到 / ClassNotFound / 静默失败」的形式暴露。全部改为**相对脚本自身位置自定位**，以后再换盘符也不用动。

### 4.1 运行时脚本（会直接影响能否启动）

| 文件 | 原写法 | 改法 |
|---|---|---|
| `api/run.sh` | `API="C:/Users/.../api"` | `API="$(cd "$(dirname "${BASH_SOURCE[0]}")" && { pwd -W 2>/dev/null \|\| pwd; })"` |
| `doc-develop/run-api.bat` | `java -jar C:\...\booking-api-2.0.2.jar` | `java -jar "%~dp0..\api\target\booking-api-2.0.2.jar" %*` |
| `doc-develop/run-lcl.bat` | `node C:\...\dev-frontend-local.js` | `node "%~dp0dev-frontend-local.js" %*` |
| `doc-develop/run-rmt.bat` | `node C:\...\dev-frontend-remote.js` | `node "%~dp0dev-frontend-remote.js" %*` |

> `run.sh` 特意用 `pwd -W` 而不是 `pwd`：脚本要把路径传给 Maven launcher，Git Bash 的 POSIX 形态 `/g/...` 会被错转成 `\g\...` 导致 ClassNotFound（该文件头部注释里原本就记着这个坑）。

## 七、需要人工处理的 3 件事

### 7.1 每个新任务都要手动选工作空间

在 WorkBuddy 里新建任务 → 输入框左下角「选择工作空间」→ 选 `G:\WorkBuddy\2026-08-30-17-19-24`。
**不做这一步，任务仍落在 C 盘**，等于没迁。

### 7.2 Windows 计划任务（若曾注册过）

`deploy/healthcheck-local.sh` 头部的 `schtasks` 示例已改 G 盘路径，但**已注册的任务项不会自动更新**。若之前跑过：

```powershell
schtasks /Delete /TN "lesson-healthcheck" /F
schtasks /Create /TN "lesson-healthcheck" /TR "C:\Program Files\Git\bin\bash.exe G:\WorkBuddy\2026-08-30-17-19-24\deploy\healthcheck-local.sh" /SC MINUTE /MO 5 /F
```

### 7.3 C 盘旧副本怎么处置 —— 这是当前最大的风险

**两份副本并存 + 两边都改 = git 分叉**，而且不会有任何报错提示。三个选项：

| 选项 | 做法 | 适用 |
|---|---|---|
| A（推荐） | C 盘那份**改名**为 `2026-08-30-17-19-24.已迁移备份` 或直接移出 `WorkBuddy` 根 | 只要不再需要旧任务历史 |
| B | 保留原样，但当成**只读**，任何改动只做在 G 盘 | 需要一周观察期 |
| C | 直接删除 C 盘那份 | 已确认 G 盘可独立工作且 git 有远端/备份 |

**注意**：本任务执行时，当前会话仍绑定 C 盘工作区（`Workspace Folder: C:/Users/Administrator/WorkBuddy/2026-08-30-17-19-24`），所以本次的代码改动做在 **G 盘副本**上，C 盘那份没有这些修复。若之后误在 C 盘打开旧任务，看到的是"没修过的版本"。

另外 `.workbuddy/workspace-display-names.json`（用户级，位于 `C:\Users\Administrator\.workbuddy\`）里只有 C 盘的 `saas-2.0.2` 显示名映射，**没有** G 盘条目。这是应用自己维护的文件，手工加条目未必被采纳，建议在 G 盘打开一次任务后由应用自行写入。

## 八、已知隐患（迁盘相关，非本次引入）

1. **`cloudBased/deploy-keys.txt` 含明文密钥**（AES_KEY / HMAC_KEY / JWT_SECRET），文件第一行自己写着"不要提交git"。上一次提交时已补 `**/deploy-keys.txt` 到 `.gitignore` 挡住，但它仍以明文躺在工作区。若曾误提交过，三个密钥应视为已泄露需轮换。
2. **`doc-develop/pids.txt` 是进程快照，内含完整命令行**，其中有 MCP Bearer token、`X-WorkBuddy-MCP-Context`（base64 内含 workspace 路径）等。它已入库，属敏感文件，建议清理或移出仓库。
3. **G 盘可用空间 15.9 GB**：`mvn clean package` 的 `target/` + `frontend/build.js` 全量重建 + 日志增长会持续吃空间，需留意。
4. **G 盘若换盘符**（例如插拔后变 H），所有"保留的绝对路径"和计划任务都会失效；但本次修过的 16 处已自定位，不受影响。
5. **`doc-develop/` 下多个 `test_*.js` / `itest_*.js` 依赖已删除的文件**（如 `frontend/js/public/terms.js` 已改名 `enumTerms.js`），是历史脚本，本次只做路径自定位、未修复其业务陈旧性。
