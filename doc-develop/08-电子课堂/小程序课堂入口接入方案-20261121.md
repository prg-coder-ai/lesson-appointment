# 小程序接入在线课堂（菜单与按钮）方案

> 2026-11-21 · 分析 + 方案，本篇不改代码
> 参照物：Web 端 2026-11-13 ~ 11-20 期间落地的课堂入口（我的课堂 / 加入课堂 / 课堂监控 / 在线课堂菜单组）
> 涉及端：学生、教师、租户管理员（平台管理员小程序端仍为占位，不在本期）

---

## 一、结论先行

### 1.1 一句话

**小程序能做的只有"课堂信息与入口"，课堂本体（音视频互动）在小程序里做不了，这是平台能力边界，不是工作量问题。**

### 1.2 能力分档

| 档次 | 内容 | 可行性 | 依据 |
|---|---|---|---|
| 直接可做 | 课堂开关显隐、我的课堂（课次列表 / 状态 / 资料只读 / 回放）、加入课堂（校验名单）、今日课程行内按钮 | 高 | 全部走现有 REST 接口，无浏览器专有能力 |
| 需降级表达 | "进入课堂"按钮 | 中 | 小程序内无法上课，只能引导到电脑浏览器（详见 4.3） |
| 做不了 | 音视频上课、屏幕共享、白板、录制、设备检测与预览 | 无 | 见 4.1 四件套取证 |
| 另立项 | 小程序内真上课 | 低（大工程） | 需 TRTC 小程序端 SDK + 资质 + 后端房间模型改造，见 4.4 |

### 1.3 三条必须先解决的约束（做不到就是白做）

1. **课堂服务 8092 没有同源反向代理**。Web 靠 nginx / dev-proxy 把 `/api/v1/classrooms/**` 分流到 8092，小程序没有这一层，必须**直连 8092 的 https 地址**并加入「request 合法域名」（见 5.5 决策 1）。
2. **`/api/v1/eclassroom/config` 下发的 `apiBaseUrl` 是 `http://127.0.0.1:8092/api/v1`**（`sys_eclassroom_instance.default-local` 的 `api_host`）。Web 端对回环地址做了「归一为同源空串」处理（`feature-flags.js#isLoopbackBase`），小程序没有同源可言，**照抄这行逻辑必然连不上**。
3. **课次标识 `classroomKey` 的拼法目前是 Web 端的私有实现**（`my-classroom-core.js#classroomKeyOf`），不在共享层。小程序若各写一份，迟早有一端拼成 `sid~1`（第 1 课次必须用裸 `sid`），表现为「课堂不存在」且不报错。

## 二、Web 端现状盘点（本次对齐的参照物）

### 2.1 三端菜单

| 端 | 菜单项 | 文件:行 | 受课堂开关控制 | 点击行为 |
|---|---|---|---|---|
| 学生 | 我的课堂 | `frontend/student.html:66` `data-module="classroom"` | 是 | 内嵌渲染 `student-myClassroom.js` |
| 学生 | 加入课堂 | `frontend/student.html:72` `data-module="classroom"` | 是 | 内嵌 `student-joinClassroom.js`（粘贴链接/课堂号 → 校验 → 进课堂） |
| 教师 | 我的课堂 | `frontend/teacher.html:69` `data-module="classroom"` | 是 | 内嵌 `teacher-myClassroom.js` |
| 租户管理员 | 课堂监控 | `frontend/admin.html:108` `data-module="classroom"` | 是 | 跳到独立页 `classroom-ops.html`（监控/告警/学情/对账/审核全套） |
| 平台管理员 | 在线课堂（组） | `frontend/platform_admin.html:86` | 否 | 课堂实例 + 课堂监视（2026-11-20 新增） |

> 显隐机制：`feature-flags.js#applyMenuVisibility` 按 `.menu-item[data-module="classroom"]` 批量 `display:none`，判据是「本标签页是否已与后端核对过」（`sessionStorage.eclassroomConfigVerified`），**不是**「本地缓存里有没有配置」。小程序移植时必须理解这一点，否则会重现"禁用一次后菜单永远回不来"。

### 2.2 两套行内按钮规则（注意它们并不相同）

**规则 A：今日课程卡片**（`my-classroom-core.js:311#buildEntryButtons`）

| 课次阶段 | 学生 | 教师 |
|---|---|---|
| upcoming 未开始 | 课前准备 + 进入课程 | 课程准备 + 进入课程 |
| live 进行中 | 进入课程 | 进入课程 |
| past 已结束 | 课程回看 | 课程回看 |

**规则 B：课次列表操作栏**（`my-classroom-core.js:437-483`）

| 条件 | 学生 | 教师 |
|---|---|---|
| `!finished && state !== 'ongoing'` | 课前准备 | — |
| `!finished` | 进入课堂 | 进入课堂 |
| `finished` | 回放（点击才去查地址） | 文本「已结束」 |

两套差异来自"今日课程"是**预约维度**（有 appointment 行，可算 phase），"课次列表"是**排期维度**（只有课堂状态 state）。小程序建议**统一到规则 A 的 phase 口径**，避免用户在两处看到不一致的按钮（详见 5.6）。

### 2.3 阶段判定的时区坑（必须照抄的量）

`classroomPhase(rawDatetime, durationMinutes)`（`my-classroom-core.js:272`）里 `parseUtcLoose` 把**不带时区后缀的串按 UTC 解析**：

> `appointment.appointmentDatetime` 是 UTC 裸串，按本地时间解析会让东八区整体偏 8 小时 → 出现「课已结束却显示进入课程」。

小程序必须走同一份实现（放共享层），不能各自 `new Date(str)`。

### 2.4 闸门条件（少一个就会出现"能点但点了报错"）

`buildEntryButtons` 里三道短路：

```js
if (!key) return '';                                  // 无课次键
if (!isClassroomEligible(status)) return '';          // cancelled/cancelling/reject/frozen/waiting/delete 等
if (!hasClassroom() && !ignoreSwitch) return '';      // 租户未开通
```

`NON_CLASSROOM_STATUS` 共 14 个状态（`my-classroom-core.js:284`），与后端 `BookingStatus.NON_OCCUPYING` 同口径。

### 3.3 关键字段可得性（**这里有个坑，决定了工作量**）

| 字段 | 来源 | 备注 |
|---|---|---|
| `scheduleId` | `POST /api/v1/course/booking/page` → `Booking.scheduleId`（`entity/Booking.java:23`） | **`GET /api/v1/course/appointment/statistical/listByDays` 返回的 `entity.Appointment` 里没有 scheduleId**（只有 `id/bookingId/classIndex/appointmentDatetime/lastDatetime/status/refundSnapshot`）→ 必须先按 `bookingId` 查一次 booking 才能拿到排期 id |
| `classIndex` | `Appointment.classIndex` | **1-based**：`CourseScheduleService:733` 是 `int index = 1; ... setClassIndex(index++)`。实体注释写的「0~N-1，-1默认」是**过时注释**，按它写 0-based 逻辑必错 |
| `classroomKey` | 服务端在 `GET /api/v1/schedule/class-instances/{sid}` 的响应里下发 | **优先用服务端的值**，只有拿不到时才本地 `classroomKeyOf(sid, classIndex)` |

`classroomKeyOf` 的 `<=1 → 裸 id` 与 1-based 正好自洽：第 1 课次（classIndex=1）→ 裸 `sid`，第 2 课次（2）→ `sid~2`。存量若混有 0 / -1（历史默认课次），同样落回裸 id，行为可接受。

> **工作量提示**：小程序学生端「今日课程」页（`package-student/appointment`）现在**只查了 appointment**，没有 booking 装配。要在那里放课堂按钮，必须先补一次 `GET /api/v1/booking/detail/{bookingId}`（或改调 `BOOKING_PAGE` 一次拿全）。教师端「今日课程」页已有这层装配（`BOOKING_DETAIL(a.bookingId)` → `booking.scheduleId`），改动更小。

## 四、技术边界（这节决定了方案能写到哪一步）

### 4.1 课堂本体依赖的四个浏览器 API，小程序一个都没有

取证（`grep -oE "RTCPeerConnection|getUserMedia|mediaDevices|getDisplayMedia|MediaRecorder" frontend/js/classroom/**`）：

```
mediaDevices   12 处
MediaRecorder   7 处
getUserMedia    5 处
getDisplayMedia 4 处
RTCPeerConnection 4 处
```

| API | 用途 | 小程序 | 说明 |
|---|---|---|---|
| `getUserMedia` | 摄像头/麦克风采集 | 无 | 小程序只有 `wx.chooseMedia`（拍照/录像，非实时流）和 `wx.getRecorderManager`（录音，无视频流） |
| `getDisplayMedia` | 屏幕共享 | 无 | 小程序无对应能力 |
| `RTCPeerConnection` | mesh 房间（`engine-mesh.js`） | 无 | 小程序不发 WebRTC |
| `MediaRecorder` | 录制 | 无 | 同上 |

结论：`classroom.html` 那一整套（`classroom-main/rtc/whiteboard/material/record/controls/panels`）**无法移植**。这不是"暂时没做"，是平台不提供。

### 4.2 白板与讲稿

白板（`classroom-whiteboard.js`）是 canvas + 信令同步，canvas 小程序有，但**信令走 WebSocket 且与媒体房间耦合**，脱离媒体房间单开一块白板没有教学意义。讲稿预览依赖 PDF.js（`讲稿PDF.js自渲染实施方案.md`），小程序只能退回 `wx.openDocument`。

### 4.3 "进入课堂"按钮的三种落地方式

| 方案 | 实现 | 可行性 | 风险 |
|---|---|---|---|
| A. 复制链接 + 提示浏览器打开 | `wx.setClipboardData('https://<域名>/classroom.html?scheduleId=key')` + `wx.showModal` 说明 | **高** | 体验断裂（切浏览器），但语义诚实 |
| B. `web-view` 内嵌 | 新建页面 `<web-view src="...">` | **低** | ① 需配置业务域名（备案 + 校验文件）；② **web-view 内的 H5 同样调不到 `getUserMedia`**（微信会拒绝），等于嵌进去也上不了课；③ 个人主体小程序不支持 web-view |
| C. TRTC 小程序端 SDK | `<live-pusher>` 推流 + `<live-player>` 拉流，走腾讯云 TRTC | 低（大工程） | 需「实时音视频」类目资质 + SDKAppID + 后端从 mesh 改为中心化房间（与现有 `mesh.max-peers=6` 模型冲突） |

**推荐一期走 A**：按钮不隐藏，点击弹窗说明 + 复制链接。理由是"看得见但点了有解释"优于"看不见"——后者会让用户以为功能没上线。

### 4.4 回放是唯一真正能播的内容

`GET /api/v1/recordings/{key}/playback` 返回签名 URL（OSS 的 mp4），小程序 `<video>` 组件可直接播。**这是小程序端唯一"能上课"的部分**。

### 5.2 行内按钮的三阶段判定（统一口径）

```js
// phase 来源：shared/domain/classroom.js#phaseOf(rawDatetime, durationMinutes)
// 与 Web 的 classroomPhase 逐字一致（UTC 裸串解析）
switch (phase) {
  case 'upcoming': 学生 [课前准备, 进入课堂]；教师 [课程准备, 进入课堂]
  case 'live':     [进入课堂]
  case 'past':     [课程回看]
  case 'unknown':  [进入课堂]        // 时间缺失不拦人，交给课堂服务判定
}
```

前置短路（与 Web 同）：`!key` → 不出按钮；`!isClassroomEligible(status)` → 不出按钮；`!classroomEnabled` → 不出按钮。

### 5.4 数据链路（每条都要通）

```
① 课堂开关
   GET /api/v1/eclassroom/config          → 8081（booking）
   ← { enabled, apiBaseUrl, wsBaseUrl, config }
   ⚠ 无行时后端兜 enabled:false（见 EclassroomController#getConfig）

② 我的课堂（学生）
   POST /api/v1/course/booking/page       → 8081  我的预约（pageSize 200，返回 Booking，含 scheduleId）
   → 去重 scheduleId
   GET  /api/v1/schedule/detail/{sid}     → 8081  课程名/时间
   GET  /api/v1/schedule/class-instances/{sid} → 8081  课次（含 classroomKey/state）

②' 今日课程（学生）—— 与 ② 是两条不同的线，别混
   GET  /api/v1/course/appointment/statistical/listByDays → 8081  课次行（含 bookingId + classIndex，**无 scheduleId**）
   → GET /api/v1/booking/detail/{bookingId}  → 8081  取 scheduleId + status（新增装配，见 3.3）
   → classroomKeyOf(scheduleId, classIndex) 或直接拿 scheduleId 裸键
   → phase = classroom.js#phaseOf(appointmentDatetime, schedule.classDuration)

③ 我的课堂（教师）
   GET  /api/v1/schedule/listByTeacher?teacherId=  → 8081  本人 active 排期
        （对应 ENDPOINTS.SCHEDULE_LIST_BY_TEACHER，已存在于 shared/apiPaths.js:252）
   GET  /api/v1/course/list?teacherId=             → 8081  courseId → 课程名
   → 同上 ② 的后两步

④ 资料（只读）
   GET  /api/v1/classrooms/{key}/materials → 8092（课堂服务）
   ⚠ ClassroomAccessGuard 要求调用者在 classroom_membership 名单内，名单在**首次进入课堂**时建立
     → 课前查资料会拿到「你不在本课堂名单内」，这是既有安全模型，不要绕

⑤ 回放
   GET  /api/v1/recordings/{key}/playback  → 8092  返回签名 URL → <video src>

⑥ 加入课堂校验（零副作用）
   GET  /api/v1/classrooms/{key}/status    → 8092  走同一个 guard
   ⚠ 不要用 POST /enter 做校验：它有副作用（建名单 + 签到 + 回流预约侧）

⑦ 同步课堂（教师）
   POST /api/v1/schedule/class-instances/{sid}/sync → 8081
```

### 5.5 四个关键设计决策

#### 决策 1：`classroomBase` 从哪来（三层，与 env.js 现有机制一致）

```
① storage 覆盖   wx.setStorageSync('upstream_override', { classroomBase: '...' })   仅联调
② 远程配置       GET {webBase}/app-config.json → classroomBase                      换域名免发版
③ env.js 内置    develop/rmt: http://127.0.0.1:8092；trial/release: <cloudrun 公网域名>
```

**必须优先用 env/远程配置，不能直接信 `/eclassroom/config` 里的 `apiBaseUrl`**：那是给服务端自调用和同源浏览器准备的，值是 `127.0.0.1`。建议实现为：

```js
// core/classroom.js
function resolveClassroomBase() {
  const cfg = getConfig();                       // /eclassroom/config 结果
  const fromServer = (cfg && cfg.apiBaseUrl) || '';
  // 服务端下发的是回环地址 → 对小程序一律不可用，回落本地配置
  if (!fromServer || isLoopback(fromServer)) return env().classroomBase;
  return fromServer;
}
```

配套运维动作（**不做就是全量 404/连接失败**）：
- 云托管 classroom 服务开「公网访问」，取其 `https://<服务>-<envid>.sh.run.tcloudbase.com`
- 微信公众平台 → 开发管理 → 服务器域名 → request 合法域名加入该域名（**必须 https、不带端口**）
- 本地 develop 环境勾「不校验合法域名」

#### 决策 2：request 分流

`miniprogram/core/request.js:26` 现在只分 messages。新增：

```js
const CLASSROOM_PATH = /^\/api\/v1\/(classrooms|recordings|attendance|uploads|files|schedules)\//;
function resolveBase(url) {
  if (/^https?:\/\//i.test(url)) return '';
  if (/^\/api\/v1\/(messages|users|sensitive|message-categories)/.test(url)) return msgBase();
  if (CLASSROOM_PATH.test(url)) return classroomBase();   // 新增
  return apiBase();
}
```

**注意 `schedules`（复数）归课堂服务，`schedule`（单数）归 booking**——已核对：

| 前缀 | 归属 | 实际 Controller |
|---|---|---|
| `/api/v1/schedule/**`（单数） | booking 8081 | `ScheduleController`（detail / class-instances / listByTeacher / page） |
| `/api/v1/schedules/**`（复数） | 课堂 8092 | `ScheduleEventController`（排期事件推送）、`ReconcileController`（对账） |
| `/api/v1/classrooms\|recordings\|attendance\|uploads\|files/**` | 课堂 8092 | — |

booking 侧全仓**没有任何** `/api/v1/schedules` 映射（已 grep 核验，`grep -rn '"/api/v1/schedules' api/src/main/java` 为空），所以这条分流不会抢单。这个字母差异必须写进注释，否则以后有人为了"整齐"把两条正则合并，会把排期查询整片打到 8092 → 全站 404。

#### 决策 3：`classroomKey` 唯一权威

把 `my-classroom-core.js#classroomKeyOf` 抽到 `shared/domain/classroom.js`：

```js
// 与后端 ClassroomKey.of 逐字同规则：classIndex 为 null / ≤1 → 裸 id
export function classroomKeyOf(scheduleId, classIndex) { ... }
```

Web 侧 `my-classroom-core.js` 改为委托 `window.ClassroomDomain.classroomKeyOf(...)`（保留本地同名函数作回退，防桥未加载）。

为什么必须抽出来：这条规则错了的表现是**"课堂不存在"且不报错**（课堂服务把 `sid~1` 当成另一堂课）。两端各写一份，等于给自己埋一个只在多课次场景才炸的雷。

#### 决策 4：开关缓存的自愈（小程序没有 sessionStorage）

Web 用 `sessionStorage.eclassroomConfigVerified` 标记"本标签页已核对"。小程序对应实现：

```js
// core/classroom.js
const KEY_CFG = 'eclassroomConfig';
const KEY_VERIFIED_AT = 'eclassroomConfigVerifiedAt';   // 时间戳，不是布尔

// 判据：48h 内核对过 → 可信；否则视为过期，进页面时先显示、后台强核对一次
function isVerified() {
  const t = Number(storage.get(KEY_VERIFIED_AT) || 0);
  return t > 0 && (Date.now() - t) < 48 * 3600 * 1000;
}
```

用时间戳而非布尔的原因：小程序页面生命周期长（用户可能挂后台几天），布尔标记会像 Web 早期那样"禁用一次后菜单永远不回来"。另外**登录成功时必须清 `eclassroomConfig`**（换租户后旧配置一定错），与 Web 端 `api.js` 的清缓存口径一致。

### 5.6 状态文案与色调

复用 `shared/domain/` 的既有风格，新增到 `classroom.js`：

| state | 文案 | 色调 |
|---|---|---|
| `upcoming` / `READY` | 未开始 | 中性 |
| `ongoing` / `LIVE` | 进行中 | 成功（绿） |
| `PAUSED` | 已暂停 | 警告 |
| `finished` / `ENDED` | 已结束 | 灰 |
| `CANCELLED` | 已取消 | 灰 |

> 与 Web `STATE_TEXT`、`stateTagHtml` 保持同一张表，避免"同一个课堂两端显示不同状态"。

### 5.7 管理端「课堂监视」的分期

Web 的课堂监控是**独立页面** `classroom-ops.html`（含监控/告警/学情/对账/审核/联调 7 个页签，71KB 的 `ops.js`）。小程序全量移植不现实。

| 期 | 内容 | 数据源 | 前置确认 |
|---|---|---|---|
| 一期 | 菜单项 + `soon:true`（建设中） | 无 | 与 `PLATFORM_GROUPS` 大量 soon 占位一致 |
| 二期（可选） | 只读概览：今日课堂数 / 进行中 / 告警条数 | `GET /api/v1/admin/monitor/overview`、`/alerts`（**8092**） | **必须先确认课堂服务的租户管理员鉴权口径**：`/api/v1/admin/**` 在课堂服务侧是 `isManager()`（不含 system），与 booking 的 `PLATFORM_OR_TENANT_ADMIN` 不是一套；能否放租户管理员要看 `ClassroomAccessGuard`/`AdminConsoleController` 的实参 |
| 三期 | 对账、审计、学情报表 | — | 建议永远不做，桌面端更适合 |
