# 教师端「录制」功能分析 + 合理录制范围建议

- 日期：2026-11-17
- 范围：`frontend/js/classroom/classroom-record.js`、`classroom-controls.js`、`classroom-rtc.js`、`rtc/*`、`classroom-main.js`、`replay.js`；`api/classroom-service/.../controller/RecordingControlController.java`、`recording/*`、`service/RecordingService.java`
- 结论一句话：**当前录制的是教师本机的上行媒体流（摄像头画面 + 麦克风声音），既不录屏幕/网页，也不含任何学生画面、白板、讲稿、聊天。**

---

## 1. 直接结论

| 问题 | 答案 | 依据 |
|---|---|---|
| 录的是视频源还是网页？ | **视频源**——教师本地摄像头 + 麦克风组成的 `MediaStream` | `classroom-record.js#_pickStream()` 取 `vt-local-video.srcObject` 或 `ClassroomRTC.getLocalStream()` |
| 录的是当前网页的显示内容吗？ | **否**。全项目无 `getDisplayMedia` / 屏幕共享代码，`vt-local-video` 是本地摄像头画面 | 全仓 grep `getDisplayMedia|屏幕共享|shareScreen` = 0 命中；`vt-local-video` 在 `rtc-engine.js:64` 创建，绑的是本地摄像头流 |
| 含学生画面/声音吗？ | **否**。学生轨道是各端 P2P 直连，从不汇聚到教师端的一个可录流 | 默认 `native-mesh` 架构，学生轨道只 attach 到各自的 `vt-video-{peerId}` |
| 含网页里的白板/讲稿/聊天/课件吗？ | **否**。这些是 DOM/canvas 内容，不在 `MediaStream` 里 | 录制源只有一条 `MediaStream`，无 canvas.captureStream / drawWindow |
| 含教师麦克风声音吗？ | **是**（若摄像头采集时带音频轨道） | `MediaRecorder(stream)` 录整条流，`mimeType=video/webm;codecs=vp8,opus`（opus=音频） |
| 学员会被通知"正在录制"吗？ | **会**。开/停录都向房间广播 `record:state` | `RecordingControlController#broadcast()`；合规底线，非偷偷录 |
| 谁能开录？ | 教师 / 管理员（manager），学生无录制按钮 | `canRecord()` = `AuthContext.isTeacher() || isManager()`；`classroom-controls.js:41-43` |

一句话概括现状：**这是一条"教师视角的单人出镜录制"——录下来的是一个只有教师音画、时长与课堂同步的 webm 文件，学生回放时看不到自己的画面、看不到白板推演过程。**

## 2. 实现链路（代码级）

### 2.1 录制源：`_pickStream()`（classroom-record.js:204-214）
```
优先：document.getElementById('vt-local-video').srcObject   ← 本地摄像头+麦克风
退路：ClassroomRTC.getLocalStream()                          ← engine.localStream
取不到 → toast「没有可录制的内容（摄像头/麦克风未就绪）」，不录
```
`vt-local-video` 由 `rtc-engine.js:64` 创建（`muted` 本地预览），mesh 引擎 `engine-mesh.js:68/82` 把采集到的 `getUserMedia({video,audio})` 流赋给它。所以**录制流的成分 = 教师摄像头采集的音视频，与 P2P 是否连上无关，与学生无关。**

### 2.2 录制动作（classroom-record.js:50-122）
- 先 `POST .../recording/start` 拿 `recordingId`（服务端授权+登记），成功后才 `new MediaRecorder(stream, {mimeType:'video/webm;codecs=vp8,opus'})`；不支持则退回浏览器默认。
- `recorder.start(1000)` 每秒切块入内存数组（避免长时间攒一个巨大 blob）。
- 停止 → `Blob(chunks)` → **分片上传**（5MB/片，分片 init/part/complete，服务端 `UPLOAD_*` 端点；2GB 上限，90 分钟 720p 约 400~800MB）→ `POST .../recording/{id}/stop` 带 `ossKey` 登记完成。

### 2.3 服务端职责（RecordinControlController / ClientRecordingBackend）
服务端**不碰媒体**，只做三件事：
1. **授权**：仅 teacher/manager 可 start/stop；`accessGuard.assertAccess()` 校验课堂归属。
2. **登记**：`RecordingService.start/finish` 落 `recording` 表（recordingId、startTime、ossKey、状态），归属 scheduleId。
3. **广播**：`record:state{on,recordingId,mode,by}` 通知全房间；写教学环节流水 `record:start/stop`。

`RecordingBackendRegistry`：配置 `classroom.recording.mode=client`（默认）。`cloud` 模式本仓库**无厂商实现**，配了也会降级为 client 并打 WARN——不会偷偷变成云录制。`start()` 返回的 `notice` 原文：`本地录制：只录教师画面与声音，学生画面不进入录制文件`。

### 2.4 回放（replay.js）
回放页按 `scheduleId` 拉 `GET /api/v1/recordings/{sid}`（含签名 URL，服务端支持 Range 206，可拖动/倍速），播放的就是那个 webm。**回放内容 = 教师单人音画**，无白板、无学生。

## 3. 现状评价：它与"合理的录制范围"差在哪

"录制"这个词在在线课堂里，用户（教师/学生/运营）直觉上期望的是**这堂课发生了什么**——至少是"教师讲的内容 + 关键板书/课件 + 师生互动"。当前实现与这个预期的落差：

| 期望维度 | 当前是否满足 | 说明 |
|---|---|---|
| 教师人像 + 声音 | ✅ | 完整录到 |
| 教师讲的课件/讲稿翻页 | ❌ | 讲稿是 iframe/PDF canvas，不在录制流里 |
| 白板推演过程 | ❌ | canvas 内容没进流 |
| 学生发言/连麦画面 | ❌ | 学生轨道 P2P 直连，不汇聚教师端 |
| 聊天/举手/点名等互动 | ❌ | 仅落教学流水，不在录制文件 |
| 学生"回放复习这节课"的价值 | 部分 | 只有教师音画，缺课件与板书时复习价值有限 |

**结论**：作为"教师出镜留档"是合格的；作为"课堂回放"是残缺的——缺了学生端最想看的板书/课件脉络。

## 4. 合理录制范围的建议（按投入排序）

### 方案 A：明确产品口径 + 补齐告知（最低成本，建议立即做）
不改技术路线，先把"只录教师"这件事**在 UI 上讲清楚**，避免误解：
- 开录 toast 与录制按钮 hover/title 明确写"仅录教师画面与声音，不含学生与板书"。
- 回放页列表项的"时长/状态"旁标注"教师视角录制"。
- 服务端 `notice` 文案已有正确表述，前端把它透传到 toast 即可（当前 `classroom-record.js:80` 只显示了通用文案，可改为显示 `resp.notice`）。
- **适用**：预算有限、录制定位就是"教师讲课留档"的场景。

### 方案 B：浏览器端"屏幕/窗口 + 系统音频"录制（中等成本，不依赖厂商）
把录制源从"摄像头流"换成 **`getDisplayMedia`**（教师授权共享屏幕或某窗口）：
```
录教师共享的屏幕 → 白板/讲稿/PPT 全在画面里 + 可勾选"共享系统音频"
```
- 优点：一次共享即可覆盖"教师人像（画中画）+ 板书 + 课件"，最贴近"这堂课发生了什么"。
- 缺点：依赖教师手动选共享源、浏览器对"系统音频"支持不一（Chrome 需勾"分享音频"，Windows 无 Loopback 时可能无声）；手机端不可用。
- 与本项目的契合：项目已有 HTTPS 安全上下文（自签证书那套），`getDisplayMedia` 可用。
- **适用**：教师用电脑授课、需要板书/课件进回放的场景。

### 方案 C：服务端/厂商云录制合流（最高成本，效果最全）
用云厂商（TRTC/声网等）的云端录制，把教师+学生音视频合流录制：
- 优点：完整还原课堂（多人画面 + 声音），无需教师端负担，支持高并发与合规存档。
- 缺点：需厂商 REST + 回调验签、`RecordingBackendRegistry` 里目前**没有任何 CLOUD 实现**（要新写）；有费用；当前 P2P 默认 native-mesh 没有中心媒体节点，云录制通常要先切到 SFU/SDK 模式。
- **适用**：商业化、对回放完整度与合规性有硬要求的场景。

### 建议的组合
1. **短期（方案 A）**：正名与告知，零风险消除误解——这是必须做的。
2. **中期（方案 B）**：若"回放复习"是真实需求，给教师端加一个"共享屏幕录制"选项，与现有"仅教师出镜"并列，让教师按课型选。
3. **长期（方案 C）**：仅在确有云录制预算/合规要求时启动，且先解决 mesh→SFU 的媒体架构前提。

## 5. 几个容易踩的点
- **不要把"只录教师"当成 bug 去"修好"**：源码注释和 `RecordingBackendRegistry` 都反复声明这是有意的技术路线（零成本、私有化可用），不是没做完。
- **`cloud` 配置是空头支票**：`RecordingProperties.mode=cloud` 不会带来云录制，只会降级回 client 并打 WARN；诊断看 `RecordingBackendRegistry.describe()` 的 `active/degraded/implemented`。
- **音频依赖采集时的音轨**：若教师关了麦克风采集（`engine-mesh.js` 的 `setMicEnabled(false)` 会 removeTrack），录制流就没了音频轨——回放会静音。这是"录本地流"路线的固有边界。
- **2GB 上传上限**：90 分钟 720p 约 400~800MB 够用，但若改录屏幕（分辨率更高）要重新评估 `maxUploadBytes`。
- **合规**：无论哪种方案，`record:state` 全员广播（"本堂课正在录制"）必须保留，不能偷偷录。

## 7. 增强需求：录制模式选择 + 回放体验（2026-11-17 补充）

> 本节回应两个新诉求：①录制时增加「教学区域」选项，实现**视频录制 / 内容录制**二选一，产出可存档的教学视频；②回放增加进度条、拖拽、音量等便捷能力。
> 先给代码级现状（避免把"已有能力"当新需求重做），再给可落地的方案与工作量。

### 7.1 先厘清两个事实（很重要）

| 事实 | 证据 | 对需求的含义 |
|---|---|---|
| **回放页已有进度条/拖拽/音量/倍速**，是浏览器原生 `<video controls>` | `replay.html:61` `<video id="rp-video" controls playsinline preload="metadata">`；`replay.js:4-6` 注释明确"Range 206，拖动与倍速是原生能力"；服务端 `FileAccessController#get` 实现了单区间 206 + `Accept-Ranges` | "增加进度条/拖拽/音量"**不是从零开发**，原生已具备。要做的是"增强"（持久化进度、倍速档位、快捷键、清晰标注），不是重复造控件 |
| **当前 `mode` 字段不是录制类型** | `Recording` 实体无 mode 列；`RecordingControlController.start` 返回的 `mode` 来自 `backendRegistry.activeMode()`（client/cloud 后端标识）；`start` 接口无请求体 | 要支持"视频/内容"二选一，**前端要先能选、后端要能存**：start 请求带录制类型 + `recording` 表加一列（或复用现有字段约定） |

### 7.2 需求拆解：两种录制模式

| 模式 | 采集源 | 画面内容 | 音频 | 产出 | 适用 |
|---|---|---|---|---|---|
| **视频录制（现有，保持）** | `getUserMedia` 本地摄像头+麦克风（`_pickStream()`） | 仅教师人像 | 麦克风 | 教师出镜 webm | 讲师出镜课、口语/语言类、留存讲师形象 |
| **内容录制（新增）** | `getDisplayMedia({video,audio})` 屏幕/窗口/标签页 | 教师共享的教学区域：讲稿、白板、PPT、板书推演，可含画中画人像 | 系统音频（若浏览器/系统支持）+ 可选麦克风补一路 | 可存档的教学视频 | 课件讲授、板书推导、需要"回放复习"的课 |

两者**互斥、按课型由教师开录前选择**；不清香全部录下来（避免多流混剪的复杂度）。共享停止（用户点浏览器"停止共享"）时 `track.onended` 应自动收尾录制，与手动点"结束录制"走同一 `_onRecorderStop()`。

### 7.3 录制模式选项：实现方案

**前端 `classroom-record.js` / `classroom-controls.js`：**
- 录制按钮改为"下拉二选一"或开录前弹选择框：`仅人像（默认）` / `教学区域（共享屏幕）`；默认保持现状，不改变老用户习惯。
- `start(mode)`：`mode==='screen'` 时先 `await navigator.mediaDevices.getDisplayMedia({ video: {frameRate:15}, audio:true })` 拿到流；拿不到/用户取消 → 提示并中止，不落录制记录。
- 录制流切换：`_pickStream()` 扩展为 `_pickStream(mode)`——screen 模式返回 display 流，video 模式走原逻辑；`MediaRecorder` 与分片上传链路**完全复用**。
- 混合音频：Chrome 下 `getDisplayMedia` 的标签页音频可选；若教师仍需人声，用 `AudioContext` 把 display 视频轨 + 麦克风音轨合流（`new MediaStream([displayVideoTrack, micAudioTrack])`）——这是可选增强，首期可只录系统音频。
- 共享 `track.onended` → 自动 `stop()`；`record:state` 广播带 `mode`，让学员端提示"正在录制教学区域"而非"教师人像"。

**后端：**
- `RecordingControlController#start` 增加可选 `mode` 参数（`video`/`screen`，默认 `video`），写入 `recording` 表新增列 `record_mode`（DDL 变更需走项目 ddl-align 流程；若想避免改表，可暂把类型塞进 `teaching_session` 的 `record:start` 事件，回放列表不展示类型即可——两种取舍见下）。
- `broadcast()` 的 `record:state` 增 `mode` 字段；`recording/{sid}` 列表返回 `recordMode`，供回放页标注"教学区域录制 / 人像录制"。
- 存储/目录规则不变（仍走 `recording-*` 的 ossKey 与 2h 签名 URL）。

**两种落库取舍**：
- **改表加 `record_mode` 列**（推荐，可长期演进）：回放列表能区分类型、可统计；成本是一次 DDL + 实体/Mapper 同步。
- **不改表**（最快）：类型只写事件流水、不回显到回放列表；回放页无法标注类型，但录制文件本身能看内容。适合先验证需求真伪。

### 7.4 回放体验：增强方案（原生已具备的部分不重做）

现状：`replay.html:61` 用原生 `controls`，进度条/拖拽/音量/倍速**开箱即用**，服务端 Range 206 已支持拖动。建议在此之上做"便捷增强"：

| 增强项 | 做法 | 价值 |
|---|---|---|
| 播放进度记忆 | `timeupdate` 把 `currentTime` 按 recordingId 存 localStorage；下次播放 `loadedmetadata` 后询问/自动续播 | 学生分次复习不用反复拖 |
| 倍速档位快捷按钮 | 1x/1.25x/1.5x/2x 按钮组，直接设 `video.playbackRate` | 复习效率；原生菜单藏在右键里不直观 |
| 快捷键 | 空格播放暂停、←→ 快退/快进 5s、↑↓ 音量；绑在回放容器、避免与输入框冲突 | 便捷操作 |
| 音量与静音状态记忆 | 记 `volume/muted` 到 localStorage，跨录制继承 | 一致性体验 |
| 明确标注与引导 | 回放列表项标"教学区域录制 / 人像录制"；空态文案改为"支持拖动进度条、倍速、音量调节" | 让用户知道能力存在 |
| 播放结束"再看一条" | `ended` 事件高亮下一条并提示 | 连续复习流畅 |

**不建议**：自研自定义进度条/音量滑块覆盖原生控件——原生在移动端、键盘、无障碍、缓冲指示上都更成熟，替换只会引入 bug。

### 7.5 落地清单与风险

**建议顺序**：
1. **P0 回放增强**（纯前端 `replay.js` + `replay.html`，零后端、零 DDL）：进度记忆、倍速按钮、快捷键、标注文案——立刻兑现"便捷功能"诉求。
2. **P1 内容录制（不改表版）**：前端加模式选择 + `getDisplayMedia`，start 带 mode 写事件流；回放先不区分类型。快速验证教师是否真用。
3. **P2 内容录制（完整版）**：加 `record_mode` 列、回放列表回显、广播带 mode、共享停止自动收尾。

**风险与注意**：
- `getDisplayMedia` 需 HTTPS/localhost 安全上下文——项目已具备（自签证书那套），局域网另一台电脑访问要按手册导入 CA 或点继续，否则共享被禁。
- 系统音频支持不一：Chrome 共享标签页可带音频、共享整个屏幕常无声；Windows 无立体声混音时麦克风需单独混入；**首期要在 UI 明确"系统声音可能录不到，建议开麦克风"**。
- 分辨率/码率：屏幕录制内容更细，`video/webm;codecs=vp8,opus` 够用但数据量上升，复核 2GB 上限与 `maxUploadBytes`（90 分钟 1080p 屏幕可能超 800MB）。
- 合规：`record:state` 全员广播必须保留且带模式；共享教学区域可能包含其他窗口隐私，开录前提示教师"确认共享内容、关闭无关窗口"。
- 自动收尾：用户点浏览器"停止共享"`track.onended` 要无缝落到现有 `_onRecorderStop()`，否则录制记录悬在 RECORDING 状态。
- 回放进度记忆以 recordingId 为键；录制记录过期清理后对应的 localStorage 项也应在读取时发现无效即弃。

### 7.6 本次改动性质
本节为**方案补充文档，未改任何代码**；落地时按 7.5 的 P0→P2 顺序推进，P0 可独立先上。
