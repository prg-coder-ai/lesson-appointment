# 课堂实例 · 排期 · 约束 · 统计 · 回收 与生命周期 综合分析

> 适用系统：WorkBuddy 多租户预约系统（`lesson_appointment` 主库 + `classroom-service` 自有库）
> 文档定位：把「课堂实例与排期关系、数量约束、并行统计、实时课堂回收、租户课堂生命周期」五条链路串成一份可留存的工程参考。
> 梳理时间：2026-11-14（2026-11-15 更新：`PAUSED` 暂停态、课堂发布门禁、调度器状态广播）

---

## 0. 一句话总览

租户的「课堂」不是孤立对象，而是 **排期（`course_schedule`，主库）→ 经「租户 → 实例」绑定 → 落到某个课堂实例（classroom-service 节点）** 派生出来的运行态。整条链路由 **套餐配额** 约束排期规模、由 **状态机** 驱动生命周期、由 **`endClass`** 统一回收。

> **2026-11-15 状态机扩展**：新增 `LIVE ⇄ PAUSED`（暂停）。暂停期间**教师端与学生端都不得发布音视频 / 白板 / 聊天**，由 `ClassroomPublishGuard` 在 signal / whiteboard 两个 WS 入口权威拦截；所有状态流转（Controller 的 `/start|pause|resume|end` 与调度器的就绪提醒 / 自动开课 / 自动下课 / 教师掉线结课）都会广播权威 `class:state`，前端据此同步状态徽标与发布门禁。详见 §3.1 / §4 / §5。

## 1. 实体与关系：排期课堂 → 租户 → 实例（多对一）

| 表 | 库 | 角色 | 关键字段 |
|---|---|---|---|
| `sys_eclassroom_instance`（EclassroomInstance） | 主库 `lesson_appointment`（classroom-service 跨 schema 只读） | **课堂实例** = 物理部署的 classroom-service 节点 | `apiHost/apiPort/wsHost/wsPort`、`status`(1正常/0停用/2维护)、`maxCapacity`/`currentLoad`（死字段）、`region` |
| `sys_tenant_eclassroom`（TenantEclassroom） | 主库 | 租户 → 实例绑定 | `tenantId → instanceId`，**`uk_tenant_id` 唯一 = 一租户一实例** |
| `course_schedule`（CourseSchedule） | 主库 | **排期** | `tenantId`，**无 `instanceId`** |
| `classroom`（Classroom） | classroom-service 自有库 | **课堂**（每次排期派生） | 主键 `scheduleId`（IdType.INPUT，多课次复合键 `id` / `id~N`）、`tenantId`、`status`、`startTime/endTime`、`actualStart/actualEnd` |

**关联链路：**
- 建排期（`CourseScheduleService.createSchedule`）→ 事务提交后异步 `pushAfterCommit(tenantId, id, "created")` → classroom-service 的 `ScheduleEventConsumer.handleCreated` 在其库建 `classroom` 行（带 `tenantId`、***不带 `instanceId`***）。
- **运行时解析**：课堂的 `tenantId` → `TenantEclassroom.get(instanceId)` → `EclassroomInstance` → 拿到 api/ws 地址（`EclassroomService.getTenantClassroomConfig`）。即课堂不直存实例，而是经「租户绑定」间接落到某个实例。
- **关系本质**：一个实例可承载多个租户、一个租户可有多个并行课堂但只绑一个实例 —— **排期课堂 → 租户 → 实例是多对一**。实例是「课堂运行的物理容器」，排期课堂是容器里「具体的一次课」，二者靠 `tenantId` 间接牵连。

### 1.1 实例的并发复用模型（一个实例名额能否同时服务多个课次？）

**结论：能。一个 `EclassroomInstance` 本质是「多租户 × 多课次」共享的复用节点，不是「一实例一课堂」。** 「实例名额」指的是**租户被钉到某实例的归属位**，而非按课堂分配的容量单位。

**代码证据：**
1. **绑定语义是「一租户一实例」，不是「一实例一租户」**：`sys_tenant_eclassroom` 的唯一约束在 `tenant_id`（`uk_tenant_id`），多个租户行可指向同一 `instance_id` → 同一实例可承载多个租户。
2. **课次级资源按 `scheduleId` 隔离、且在同一进程内共存**：
   - `WsRoomRegistry`：`signalRooms` / `wbRooms` 是 `Map<scheduleId, Set<WebSocketSession>>`，多个 `scheduleId` 同时存在于同一张表 = 同一实例同时跑多个课次。
   - `ClassroomLiveState`：每课次各存一套 `ConcurrentHashMap`（禁言 / 举手 / 摄像头 / 白板 / 快照），多课次并存。
   - `MediaService.createRoom(scheduleId)`：每课次独立建房（SFU 下独立房间，mesh 下仅逻辑房号）。
   - Redis `online:{scheduleId}:{userId}`：每课次每人在线 key 独立。
3. **开课无任何实例级并发闸**：`startClass` / `markReady` 不查 `currentLoad` / `maxCapacity`；`TenantEclassroomService` 仅校验 `instance.getStatus() == 1`（实例是否启用），不校验负载或并发数（两容量字段是死字段，见 §2 / §8）。

**由此得出：**
- 实例层唯一硬约束 = `status == 1`（启用即可用）；每课次的唯一刚性上限是 mesh 拓扑的 `maxPeers = 6`（≤ 6 人，仅 mesh），切到 SFU 后连该上限也没有。
- 一个实例名额可同时服务「其下所有绑定租户」的「所有并行课次」。

**代价（共享即共损，呼应 §8.4）：**
- **无隔离（noisy neighbor）**：某租户在同一实例开大量 SFU 大课，会抢占 CPU / 带宽，拖累同实例其他租户，系统无 per-instance 配额兜底。
- **单点共损**：实例宕机 = 其下所有租户的所有实时课次同时中断。
- 回收 / 统计仍以课次粒度，不与实例绑定（见 §3 / §4）。

## 2. 数量约束：只限「排期总数」，不限「实时课堂」

**唯一生效的租户级数量约束 = 套餐 `SCHEDULE` 配额，且约束的是「排期总数」而非「实时课堂数」。**

- **来源**：`sys_package_template.schedule_limit` → 套用到 `sys_tenant_package.schedule_limit/schedule_current`（一租户一条）。
- **占用**：建排期时 `TenantQuotaService.acquire(tenantId, SCHEDULE)` → `TenantPackageService.tryAcquire` 用**条件 UPDATE**（`limit=0 OR current+delta<=limit`）原子占用，与插入同事务，超限抛「已达套餐上限」。
- **释放**：删排期 `deleteById` / `deleteByCourseId` 调 `release(SCHEDULE)`；`reconcile` 定时把 `current` 校正为真实行数防漂移（防只增不减）。
- **并发防超卖**：`tryAcquire` 条件 UPDATE 自带行锁语义，避免并发超卖。

⚠️ **关键点**：该配额统计的是 `course_schedule` 行数，**包含普通预约排期与课堂排期、不区分**；它限的是「存在的排期数」，不是「同时开着的课堂数」。

**实时课堂数 / 并行数：classroom-service 侧没有任何约束：**
- `ClassroomService.create` / `startClass` 无数量校验；进课堂只有用户级频率限流（`enter-per-minute:30`），不是租户级上限。
- `EclassroomInstance.maxCapacity` / `currentLoad` 是死字段（全代码无任何后端读写，仅实体定义 + 前端可编辑）。
- 唯一硬约束是「一租户一实例」绑定（`uk_tenant_id`），但它限的是**实例数**不是课堂数。

> **小结**：若想真正约束「租户并行开启的课堂数」，当前没有现成机制，需新增（例如在 `startClass` 时按 `tenantId` 查 `LIVE` 数，与实例 `maxCapacity` 或新增配额类型 `CLASSROOM_CONCURRENT` 比对拦截）。**注意 `PAUSED` 需单独定口径**：它不进 LIVE 计数、不释放媒体房间，但仍是「已开课」的课堂（§3 / §5）。

## 3. 并行开启统计：LIVE 计数

「并行开启」 = 状态机 `SCHEDULED → READY → LIVE ⇄ PAUSED → CLOSED`（+ `CANCELLED`）中的 **`LIVE`**；**`PAUSED` 不计入并行开启数**（课已开但暂时停播，媒体房间保留，见 §8）。

现成能力（均按 `tenantId` 维度）：

- **`MonitorService.overview(tenantId)`**（运营概览首选）：返回 `liveClasses` / `concurrency` = **今日**（`startTime` 在当天）且 `status=LIVE` 的课堂数。刻意用「今日」口径规避僵尸课堂虚高。
- **`ClassroomService.listByStatus("LIVE", tenantId)`**（后台 `monitor` 接口用）：按 `tenant_id + status='LIVE'` **全量**过滤（含跨天僵尸），适合精确统计 / 管理。
- **`MonitorService.alerts()`**：单独暴露 `staleLive`（> 2h 仍 LIVE），用于发现僵尸课堂。**`PAUSED` 不进 `staleLive`**，但自动下课扫描已纳入 PAUSED（§4.1），超时会被结算。
- **数据底座**：`classroom` 表 `tenant_id` + `status` 两列即可；`BizMetrics` 把 live 数回写 Gauge 供 Prometheus 抓取，避免 15s 一次全表扫描。
- **状态同步**：状态流转后广播 `class:state`（Controller 的 `/start|pause|resume|end` + `ClassroomScheduler` 的 `scanReadyReminder|scanAutoStart|scanAutoEnd|scanTeacherDrop`），前端 `ClassroomMain.setClassStatus` 统一消费。此前调度器只改库不广播，自动开课后前端仍按 SCHEDULED 判定，会误禁学生发布。

### 3.1 状态与发布门禁（`ClassroomPublishGuard`）

| 状态 | 学生 | 教师 / 管理员 |
|---|---|---|
| `LIVE` 进行中 | 可发布 | 可发布 |
| `PAUSED` 暂停 | **禁** | **禁**（补充要求：暂停期间师生都不发送） |
| `SCHEDULED / READY / CLOSED / CANCELLED` | 禁 | 可发布 |

- **服务端权威**：signal WS（`ClassroomSignalHandler`，覆盖 chat 与 RTC offer/answer/candidate 透明转发）与 whiteboard WS（`WhiteboardHandler`，独立通道）两个入口前置拦截，拒绝回执 `publish:rejected` / `wb:rejected`；按 `scheduleId` 缓存状态 1.5s，状态流转主动失效，查库异常 fail-closed。
- **前端同步**：`ClassroomMain._applyGate()` 下发控制栏 / 聊天 / 白板 / RTC 四模块；暂停时关闭本地音视频轨道，恢复到 LIVE 时学生 `rejoin()` 重建媒体会话。
- **控制类消息例外**：开课 / 暂停 / 恢复 / 下课、全员禁言、举手批准、白板授权与保存、点名、移出成员不是「课堂内容信息」，**仅教师 / 管理员可发且始终放行** —— 否则暂停后教师无法点「进行中」恢复课堂。

## 4. 回收实时课堂：统一 `endClass`

**回收的语义 = 课堂状态 `LIVE | PAUSED → CLOSED`**，全部由 `ClassroomService.endClass(scheduleId)` 统一执行（状态流转 + 释放媒体房间 + 出勤 / 课时收尾）。`PAUSED` 也必须能下课，否则教师暂停后无法结束课堂。

### 4.1 四条触发路径

| 路径 | 入口 | 权限 | 说明 |
|---|---|---|---|
| 教师 / 管理员手动下课 | `ClassroomController.end` → `endClass` → 广播 `class:state(CLOSED)` | `isTeacher` 或 `isManager` | 租户内回收自己课堂的主路径 |
| 管理员远程下课 | `AdminConsoleController.remoteEnd`（`POST /api/v1/admin/classrooms/{scheduleId}/end`） | `isManager` | 平台管理员可结束任意课堂；租户管理员只能看到 / 结束本租户（`monitor` 按 `tenantId` 过滤），但 `remoteEnd` 本身**未二次校验 tenantId**（潜在越权点） |
| 自动下课（超时） | `ClassroomScheduler.scanAutoEnd`（每 30s）→ 广播 `CLOSED` | 系统 | `findOverdueLive` 的 SQL 为 `status IN ('LIVE','PAUSED')`，计划结束时间已过 `auto-end-grace-minutes`（默认 5 分钟）→ `endClass`。**PAUSED 必须一起扫**，否则教师暂停后忘了恢复会留下永不结算、永不释放媒体房间的僵尸课 |
| 教师掉线结课 | `ClassroomScheduler.scanTeacherDrop`（每 40s）→ 广播 `CLOSED` | 系统 | 只查 `LIVE` 课堂：`OFFLINE` 且离开超 `teacher-drop-grace-seconds`（默认 120s）→ `endClass`；PAUSED 不触发此路径（由超时扫描兜底） |

> 调度器四条状态流转路径（就绪提醒 / 自动开课 / 自动下课 / 教师掉线结课）现均广播 `class:state`，与 Controller 侧同口径，修复「调度器只改库、前端状态滞后」。

### 4.2 `endClass` 释放了什么
1. 状态翻 `LIVE | PAUSED → CLOSED` 写 `actualEnd`；`transitionStatus` 同时使发布门禁状态缓存失效并广播；
2. `mediaService.destroyRoom` 释放 SFU / 媒体房间（按时间计费，这是真金白银的资源）；
3. `closingService.closeAfterEnd` 做出勤收尾 + 课时回流（消费端按 `consumption_version` 丢弃过期报文）。

### 4.3 不能用来回收的路径（注意）
- `ClassroomService.cancel` 在 `status == LIVE` **或 `PAUSED`** 时直接抛 `CLASSROOM_STATUS_CONFLICT` —— 课已开起来（含暂停），取消会抹掉已产生的出勤 / 课时证据，必须先 `end` 到 `CLOSED`。
- `ScheduleEventConsumer` 三处硬判定（改期忽略、整排期取消跳过、清理多余课次跳过）均已补 `PAUSED`，与 `cancel` 同口径。
- 禁用 `disableTenantClassroom` / 解绑 `unbindTenantClassroom`：只改 `sys_tenant_eclassroom`，**不触碰进行中的课堂** —— 已有的 WS 连接、媒体房间继续跑，只阻止新课堂进入。所以「禁用」不是回收实时课堂的手段。

### 4.4 回收的副作用 / 坑点
- 回收后**实例负载不回写**：`EclassroomInstance.currentLoad` 是死字段，开 / 关课堂都不增减它。
- 回收后**不释放 SCHEDULE 套餐配额**：配额按 `course_schedule` 行数占用，与课堂是否开着无关；要等排期被删才 `release(SCHEDULE)`。
- **僵尸课堂**：若计划结束时间异常或自动下课漏触发，课堂会卡在 `LIVE` / `PAUSED` 一直占资源。`staleLive`（> 2h 仍 LIVE）只覆盖 LIVE；PAUSED 已纳入自动下课扫描但要求 `end_time` 非空，若排期缺结束时间且教师忘了恢复仍需人工 `remoteEnd`。
- 只有单课堂回收，**无批量回收接口**。

### 4.5 暂停不是回收
`/pause`（`LIVE → PAUSED`）**保留媒体房间**、不写 `actualEnd`、不做下课收尾；`/resume`（`PAUSED → LIVE`）不重建房间、不重写 `actualStart`。两者都广播 `class:state`，期间由发布门禁拦住师生全部内容发布（§3.1）。

## 5. 租户方课堂生命周期（主线）

状态机：**`SCHEDULED → READY → LIVE ⇄ PAUSED → CLOSED`**（+ `CANCELLED`）；所有状态流转均广播 `class:state`。

```
       创建排期(占SCHEDULE配额)
   [SCHEDULED] ──push created──▶ 建classroom行+membership+roster
        │
   scanReady (默认开课前10分钟) ──broadcast READY
        │
   [READY] ──学生可进──▶
        │
   scanAutoStart / 教师 start ──写actualStart + createRoom──broadcast LIVE
        │
   [LIVE] ──实时媒体/白板/信令/出勤──▶
        │  │
        │  └─ 教师 /pause ─▶ [PAUSED]（师生禁发布，房间保留）
        │         └─ 教师 /resume ─▶ 回到 [LIVE]（不重建房间）
        │
   endClass (手动/remoteEnd/超时/教师掉线；LIVE|PAUSED 均可) ──broadcast CLOSED
        │                                  │
   [CLOSED]                          排期取消/删除 push cancelled
        │                                  │
   留存(永不物理删除)          (LIVE/PAUSED 跳过，留给人工 end)
                                             │
                                       [CANCELLED]
```

1. **派生 SCHEDULED**：建排期 → 占配额 → `push created` → 建 `classroom` 行 + 初始化 membership（师生名单）+ 出勤 roster（全员 ABSENT）。一个排期可展开 N 课次，各建一行（键 `id` / `id~N`）。
2. **就绪 READY**：开课前 `ready-before-start-minutes`（默认 10）扫描 `markReady` → 广播 `class:state(READY)` + 推提醒，学生可进。
3. **开课 LIVE**：到点自动 `scanAutoStart` 或教师手动 `start` → 写 `actualStart`、`mediaService.createRoom` 建房、广播 `LIVE`。**调度器与 Controller 两条路径都广播**，否则前端会停留在 SCHEDULED 而误禁发布。
4. **进行 LIVE**：实时媒体 / 白板 / 信令 / 出勤；**LIVE / PAUSED 态忽略 `updated`（不改期）与 `cancelled`（不随排期取消）事件**。
5. **暂停 PAUSED**（2026-11-15 新增）：教师点「暂停」→ `/pause` → `LIVE → PAUSED`；不释放媒体房间、不写 `actualEnd`、不做收尾，师生全部内容发布被 `ClassroomPublishGuard` 拦截。教师点「进行中」→ `/resume` → `PAUSED → LIVE`，广播 `LIVE`、学生端 `rejoin()` 重建媒体会话。暂停**不计入 LIVE 并行数**（§3），但计入自动下课扫描（§4.1）。
6. **下课 CLOSED**：`endClass` 四路径（LIVE 或 PAUSED 均可）→ `destroyRoom` 释放媒体 + `closeAfterEnd` 出勤收尾与课时回流，广播 `CLOSED`。
7. **取消 CANCELLED**：排期取消 / 删除 → `push cancelled` → `ScheduleEventConsumer.handleCancelled`：**CLOSED / CANCELLED 不动**（保留账务证据）、**LIVE / PAUSED 跳过留给人工 end**、`SCHEDULED / READY → CANCELLED`；多课次整组取消、孤儿课次清理（三处判定均已补 PAUSED）。
8. **留存**：`classroom` 行**永不物理删除**（`scanRetentionCleanup` 只清 presence / rollcall / reconcile / session / submission / recording 过程表），CLOSED / CANCELLED 长期留存作历史与统计底座。

**租户能 / 不能：**
- 能：建排期（派生）、手动 start / pause / resume / end、取消或删排期（非 LIVE / PAUSED 课堂随之取消）。
- 不能：对 LIVE / PAUSED 直接 cancel、暂停期间师生发布内容、用禁用 / 解绑回收进行中课堂、跨实例、碰到并行上限（系统无此限）。

## 6. 风险与改造建议

| 项 | 现状 | 建议 |
|---|---|---|
| 实例负载死字段 | `currentLoad` / `maxCapacity` 无任何后端读写，开 / 关课不维护 | 在 `startClass` / `endClass` 按 `tenantId` 维护；或新增 `CLASSROOM_CONCURRENT` 配额类型实现**并行上限** |
| 僵尸课堂无自动强杀 | `staleLive` 只覆盖 `LIVE`；`PAUSED` 已纳入超时自动下课（要求 `end_time` 非空），但仍无基于「开课时长」的强杀 | 增加「LIVE / PAUSED 超 N 小时强制 `CLOSED`」扫描器，并让 `alerts` 覆盖 PAUSED |
| 调度器状态不同步（**已修 2026-11-15**） | 修复前 `scanAutoStart` 等只改库不广播 `class:state`，前端停留在进页时的旧状态 → 自动开课后学生被前端误禁发布、徽标一直「待开课」 | 已修：就绪提醒 / 自动开课 / 自动下课 / 教师掉线结课均广播；**今后新增状态流转路径必须同步广播**，否则会重现 |
| `remoteEnd` 越权点 | `AdminConsoleController.remoteEnd` 未二次校验 `classroom.tenantId == 当前租户` | `remoteEnd` 内校验归属，租户管理员只能结束本租户课堂 |
| 配额不区分课堂排期 | `SCHEDULE` 配额含普通预约与课堂排期混算 | 若需「课堂排期」单独限额，在 `course_schedule` 加类型标记并拆分配额类型 |

## 8. 实时课堂资源占用：刚性 vs 弹性

租户每开启一节 **LIVE** 课堂，会在多个子系统上占用资源。按「是否与参与者人数 / 互动量 / 时长相关」划分，可分为**刚性（固定预留，与人数无关）**与**弹性（随人数 / 时长 / 互动量增长）**两类。前者决定「容量门槛」，后者决定「账单与峰值」。

> **`PAUSED` 的资源口径**：暂停只关闭内容发布，**不释放任何刚性资源**（媒体房间、WS 房间键、内存运行时态、`classroom` 行全部保留），弹性资源中的带宽/流因前端关闭本地轨道而降到近零，但 SFU 房间仍按时间计费。只有 `endClass → CLOSED` 才真正 `destroyRoom`。

### 8.1 资源清单与分类

| 资源 | 承载位置 | 占用特征 | 刚性 / 弹性 | 释放时机 |
|---|---|---|---|---|
| 租户 → 实例绑定 | `sys_tenant_eclassroom` | 每租户 1 条，持久，即使无课堂也钉住一个实例名额（`uk_tenant_id` 唯一） | **刚性（预留）** | 解绑时才删 |
| `classroom` 课堂行 | classroom 库 `classroom` 表 | 每派生课堂 1 行（不带实例字段），**永不物理删除** | **刚性** | 不释放（历史留存） |
| `classroom_runtime_state` 行 | classroom 库 | 每课堂 1 行，落库全员禁言态（重启可恢复） | **刚性** | 不释放 |
| 媒体房间 | `MediaService.createRoom` → provider | SFU 下服务端固定 1 间（占 SFU 资源 / 端口）；**native-mesh 下 provider 不建任何服务端房间，0 服务端成本**，仅 1 个逻辑房号；`PAUSED` 期间房间继续保留 | **刚性（按课堂）** | 仅 `endClass` → `destroyRoom`（`pause`/`resume` 不释放、不重建） |
| WS 信令 / 白板房间 | `WsRoomRegistry` `signalRooms` / `wbRooms` | 每课堂各 1 个 `scheduleId` 键（键内的 session 集合是弹性的） | **刚性（按课堂）** | 房间空了即移除键 |
| 内存运行时态 | `ClassroomLiveState` | 每课堂 1 套 `ConcurrentHashMap`（禁言 / 举手 / 摄像头 / 白板授权 / 快照） | **刚性（按课堂）** | 房间空了才回收键，长尾不主动清 |
| mesh 人数硬上限 | `RtcProperties.Mesh.maxPeers = 6` | 超出成员「只收不发」，天花板刚性 | **刚性（上限）** | — |
| Redis 在线 key | `OnlineStateManager` `online:{scheduleId}:{userId}` | 每在线者 1 个，TTL = `offline-timeout-seconds + 10` | **弹性** | 掉线删除 / TTL 过期 |
| membership 行 | `classroom_membership` | 每参与者 1 行 | **弹性** | 不释放（历史留存） |
| 出勤过程段 | `classroom_presence_segment` | 每次进出一段，随进出频次增长 | **弹性** | 留存期后清（过程表） |
| 媒体带宽 / 流 | 客户端 ↔ SFU 或客户端两两直连 | **MESH：每人与 N-1 互传，上行 O(N)、总量 O(N²)，≤6 人；SFU：每人恒定 1 路上行、服务端扇出 O(N)**；`studentPublishVideo=false` 学生默认仅音频省上行 | **弹性（核心计费项）** | 下课即停 |
| 白板 ops / 快照 | 内存 + WS 下发 | 随绘制量增长 | **弹性** | 课堂结束 / 清屏 |
| 录制存储 | OSS（`classroom_recording.ossKey`）+ `expireAt` | 仅录制开启时产生，按留存期过期释放 | **弹性（存储）** | `expireAt` 到期 |

### 8.2 刚性资源说明（与人数无关，按「课」或「租户」预留）
- **租户 → 实例绑定是典型刚性预留**：租户一旦开通课堂即被永久钉在一个 classroom-service 实例上，无论是否开课都占一个归属位；「一租户一实例」是真实硬约束（实例本身的 `maxCapacity` / `currentLoad` 虽是死字段，见 §2，但绑定本身不可弹性伸缩）。
- 每节派生课堂在 `classroom` / `classroom_runtime_state` 各留 1 行且**永不物理删除**，是固定小的存储占用。
- 媒体房间、WS 房间键、内存运行时态都是「每课堂 1 份」的固定开销，与同时在线几人无关。
- **mesh 拓扑下媒体服务端零成本**：`NativeMeshRtcProvider` 的建房什么都不做（`MediaService` 注释明示"provider 内部可能什么都不做，如 mesh"），房间只是逻辑占位，代价完全转移到客户端带宽。
- **暂停不降刚性占用**：`PAUSED` 保留媒体房间与所有内存键，`resume` 也不重建；只有 `CLOSED` 才走 `destroyRoom`。因此「暂停」是**发布态开关**，不是资源回收手段（§4.5）。

### 8.3 弹性资源说明（随人数 / 时长 / 互动增长，是主要计费面）
- **带宽 / 流是弹性核心**：
  - **MESH（默认，零服务商依赖）**：浏览器两两直连，每加 1 人新增 N-1 条上行，**上行随人数线性、总流数 O(N²)**，故 `maxPeers = 6` 是刚性天花板；默认学生不发布视频（仅音频）以压低上行。
  - **SFU（LiveKit / TRTC / Agora）**：每人恒定 1 路上行、服务端负责扇出到 N-1，**服务端带宽 / 算力随人数线性 O(N)**，且房间本身占用 SFU 资源（通常按分钟计费）。
- **时长维度贯穿弹性**：媒体房间（SFU 按时长计费）、带宽、录制存储均为「时间 × 用量」弹性计费；Redis / DB 行按留存期。
- **在线 key / membership / 出勤段**随参与者人数线性增长。
- **录制 OSS** 仅当开启录制，且带 `expireAt` 自动过期，是带生命周期的弹性存储。

### 8.4 资源侧现状风险
- **无租户级弹性资源上限**：除 mesh 的 6 人硬上限和全局 `enter-per-minute:30` 频率限流外，系统对「单租户并行课堂数、单课堂人数（SFU 下）、带宽、录制存储」**没有任何租户配额约束**（与 §2 一致：并行课堂数零约束、`currentLoad` 死字段）。
- **SFU 下无单课堂人数 / 带宽闸**：一旦切到 SFU provider，单课堂可突破 mesh 的 6 人，但没有任何服务端人数上限或带宽配额兜底，易被「超大课堂」打爆实例或产生超额账单。
- **录制存储无租户配额**：`expireAt` 仅按全局 `retentionDays`，没有租户级存储上限，超大租户可占满 OSS。
- **内存态不随课堂结束回收**：`ClassroomLiveState` / `WsRoomRegistry` 的键在房间空了才移除，长尾僵尸课堂（§4.4）会持续占用内存键。
- **PAUSED 长尾占用**：暂停课堂保留媒体房间、内存键与 WS 房间键，且不计入 `LIVE` 并行统计 / `staleLive` 告警；若排期缺 `end_time` 又长期不恢复，会成为「统计看不见但仍占资源」的隐性僵尸（§3 / §4.4）。

## 10. 运营与 QoS：实例级 / 租户级课堂限额设计

> **性质：设计方案，尚未实施。** 前 §1~§9 均为现状取证；本节是基于现状的改造建议，用于回答「从运营与 QoS 角度如何对每个实例 / 每个租户的课堂做限额」。

### 10.1 设计原则
- **准入控制（admission control）优于事后限流**：在「课堂变 LIVE」「参与者进房」「录制开始」三个闸口前置拦截，而不是跑起来再砍。
- **并发计数口径先定死**：并行课堂数按 `status='LIVE'`；`PAUSED` 是「已开课但停播」，媒体房间与配额占用都不释放，`/resume` 不应重复占配额。实施 `CLASSROOM_CONCURRENT` 前必须明确这一点，否则暂停/恢复会让计数漂移（§3 / §5）。
- **软硬分级**：并发课堂数、总参与者用**硬上限**（超了直接拒）；带宽 / 清晰度用**软降级**（先关学生视频、降码率，再考虑拒）。
- **配额绑定套餐 / SLA 档**：限额本质是商业化参数，应落在 `sys_tenant_package`（租户级）与 `sys_eclassroom_instance`（实例级上限配置），与现有套餐体系同源。
- **保护存量优于接纳新增**：实例触顶时熔断拒新，优先保住已在场课堂。

### 10.2 限额维度矩阵（实例 × 租户）

| 维度 | 实例级（运维天花板） | 租户级（SaaS 公平 / 套餐） | 准入闸口 |
|---|---|---|---|
| 并行课堂数 | `instance.max_concurrent_classes`（**复用只读字段 `maxCapacity`** 作为配置上限） | 新增配额类型 `CLASSROOM_CONCURRENT` | `startClass`（含 `scanAutoStart`）；`resume` 不重复占额 |
| 单课堂人数 | （由实例总盘子间接约束） | `tenant.class_size`（**SFU 下必做**；mesh 已有 `maxPeers=6` 兜底） | 进房 |
| 总并发参与者 | `instance.max_participants`（新增实例级上限字段） | 新增配额类型 `CLASSROOM_PARTICIPANTS` | 进房 |
| 录制存储 | `instance.recording_storage_gb`（聚合上限） | 新增 `tenant.recording_storage_gb` | 录制开始预检 |
| 时长 / 分钟 | — | 新增 `tenant.daily_class_minutes`（计费口径） | `startClass` 累加 |

### 10.3 三个准入闸口（代码落点）
1. **`ClassroomService.startClass` / `markReady`→自动开课**：查 `instance.concurrentClasses < max` 且 `tenant.concurrentClasses < max` → 原子占用；`endClass` 释放。**这是防「租户开爆实例 / noisy neighbor」的 P0 闸**（现状此路径无任何校验，见 §2）。注意 `scanAutoStart` 也走同一闸；`resumeClass`（PAUSED→LIVE）**不新增占用**，须显式排除，否则一次暂停/恢复会把并发计数加两次。
2. **进房 `enter` / `join`**：查 `instance.totalParticipants < max` 且 `tenant.totalParticipants < max` 且「本课堂人数 < class_size」→ 占用；离场 / `leave` 释放。复用已有 `RateLimitService` 的 Redis 原子计数范式（INCR + 首次 EXPIRE）。
3. **录制开始**：查租户录制存储余量；不足则拒录或转低码率。现状仅 `RecordingProperties.retentionDays=90` / `maxUploadBytes=2GB` 两个**全局**配置，无租户级额度。

### 10.4 机制实现（复用现有骨架，零新依赖）

**(A) 租户级 —— 扩展 `TenantPackageService.QuotaType`**
现有枚举是「成对列」结构：`SCHEDULE("schedule_current", "schedule_limit", "{schedule}")`。新增类型须在 `sys_tenant_package` 同步加 `xxx_current` / `xxx_limit` 两列：
```
CLASSROOM_CONCURRENT("classroom_concurrent_current", "classroom_concurrent_limit", "并行课堂"),
CLASSROOM_PARTICIPANTS("classroom_participant_current", "classroom_participant_limit", "课堂并发人数"),
RECORDING_STORAGE("recording_storage_current", "recording_storage_limit", "录制存储"),
```
沿用 `TenantQuotaService.acquire/release` 的**条件 UPDATE**（`limit=0 OR current+delta<=limit`）原子占用 + 事务内占用、+ `reconcile` 定时校正漂移（防只增不减）。与 `SCHEDULE` 完全同构。

**(B) 实例级 —— Redis 原子计数，不回写主库**
> ⚠️ **关键约束**：`EclassroomInstance` 映射 `lesson_appointment.sys_eclassroom_instance`，实体注释明确「**跨 schema 只读，classroom-service 不应对此表做任何写操作**」。因此 **运行时计数绝不能回写 `currentLoad`**；该字段只能保持为「配置值 / 展示值」，由主系统侧或运维后台维护。

- `maxCapacity`：**只读**作为 `max_concurrent_classes` 的上限配置读取（合规，无需写）。
- 运行时计数放 **Redis**（classroom-service 已有 `OnlineStateManager` 用 Redis）：
  `inst:{instanceId}:classes`、`inst:{instanceId}:participants`，`startClass`/进房用 **Lua「先查限再 INCR」**保证原子；`endClass`/离场 DECR；崩溃残留由 reconcile 扫描 `classroom` 表 **`status IN ('LIVE','PAUSED')`** 重算兜底（PAUSED 仍占房间与并发名额，不能漏；与现有 SCHEDULE reconcile 同源思路）。
- 实例可多节点同 `instance_id` 集群部署，Redis 计数天然跨节点一致，优于本地 `ConcurrentHashMap`。

**(C) 死字段处置**
- `maxCapacity` → 激活为「实例并行课堂上限」配置（读）。
- `currentLoad` → 不激活为运行时计数（只读表不可写）；如需展示，由 Redis 计数派生或由主系统侧单独维护。

### 10.5 QoS 隔离（治 noisy neighbor / 单点共损）
- **降级优先于拒绝**：实例负载 > 80% 时，先强制 `studentPublishVideo=false`（`RtcProperties` 现成开关）、降 SFU 码率、限流白板 ops；> 100% 才熔断拒新准入。
- **熔断（circuit breaker）**：实例并行课堂触顶 → 拒新课堂准入，保护存量课堂。
- **加权公平**：实例临近上限时按租户 SLA 权重（free / pro / enterprise）比例分配剩余名额，避免低档租户饿死高档。
- **单点共损缓解**：§1.1 已证实例为共享节点，宕机=其下所有租户课次全断；限额可配合「实例级总盘子」避免单实例超载，但真正的高可用仍需实例冗余 + 租户可迁移绑定。

### 10.6 运营工具
- `MonitorService.overview(tenantId)` 现有按租户口径，扩**实例视角聚合**：每实例的 LIVE 课堂数 / 总参与者 / 存储 / 利用率%（数据源即 §10.4(B) 的 Redis 计数）。
- 告警：实例利用率 > X%、租户触顶事件、录制存储超阈、僵尸课堂（>2h LIVE，现有 `alerts.staleLive` 已有）；**补 PAUSED 长尾告警**（暂停不进 `staleLive`、不计 LIVE 并行数，但房间仍计费，见 §8.4）。
- **SLA 档位**：套餐决定限额（示例：free 2 并发 / 30 人；pro 10 / 200；enterprise 自定义），运营后台可调。

### 10.7 优先级建议

| 优先级 | 改造项 | 理由 |
|---|---|---|
| **P0** | 实例并行课堂数 + 租户并行课堂数硬上限 | 直接堵住 §2 / §8.4「无并发上限」漏洞；复用 `maxCapacity`(读) + `QuotaType` 扩展，风险最低 |
| **P1** | 单课堂人数（SFU 必做）、实例 / 租户总参与者上限、录制存储配额 | SFU 一旦启用无人数闸，且录制存储无租户额度 |
| **P2** | 降级 / 熔断、SLA 加权档位、实例级监控看板、实例冗余与租户迁移 | 体验与高可用，依赖 P0/P1 的计数底座 |

### 10.8 与现状的对照（为什么必须做）
- §2：并行课堂数**零约束**、`currentLoad`/`maxCapacity` 是死字段、`startClass` 无校验。
- §8.4：SFU 下无单课堂人数 / 带宽闸、录制存储无租户配额、内存态长尾不回收。
- §1.1：实例是共享复用节点，无 per-instance 隔离 → noisy neighbor 与单点共损。
- §3.1 / §5：`PAUSED` 发布门禁已生效，但**并行课堂数仍无硬上限**；新增的 `CLASSROOM_CONCURRENT` 配额必须明确「PAUSED 算不算并发、resume 要不要重新占额」，否则与本节 Redis 计数口径冲突。

**一句话**：以 `QuotaType` 扩展做租户侧硬配额、以 Redis 原子计数做实例侧总盘子（**不回写只读主库表**）、以三个准入闸口做前置拦截、以软降级 + 熔断做 QoS 兜底。

## 11. 课堂数据与页面独立于 booking-api 的可能性、代价及途径

> **性质：架构分析，尚未实施。** 本节回答「能否把课堂相关的数据和页面从 booking-api 独立出来」，先界定「独立」的含义，再逐层给出现状耦合取证、可能性判断、代价清单与分阶段途径。

### 11.1 先界定「独立」的四层含义（避免歧义）

| 层 | 含义 | 现状 |
|---|---|---|
| **L0 服务进程独立** | 独立工程 / 端口 / 进程 / 部署单元 | ✅ **已实现**（classroom-service 独立 Maven 工程、8092、独立 fat jar、`cloudBased/classroom-service/` 独立 Dockerfile） |
| **L1 数据独立** | 自有库、不跨 schema 读主库、可异机部署 | ⚠️ **部分**（14 张 `classroom_*` 自有表已独立，但仍跨 schema 只读 3 类主库表，且被「同 MySQL 实例」约束钉死） |
| **L2 页面 / 前端独立** | 独立构建、独立 dist、独立部署、独立会话入口 | ❌ **未实现**（课堂页与 booking 页同一 `dist`、同一 nginx、共用登录态与配置接口） |
| **L3 产品完全独立** | 独立租户体系、独立登录、独立排期来源、独立运维 | ❌ **不成立**（课堂本质是排期派生，脱离 `course_schedule` 即无课堂来源，见 §1 / §5） |

### 11.2 现状耦合面取证

#### (A) 数据层 —— 最硬的约束是「同 MySQL 实例」

| 耦合项 | 位置 | 说明 |
|---|---|---|
| **同实例硬约束** | `api/classroom-service/src/main/resources/application.properties:17` | 原文：「要求与 booking-api 连接同一个 MySQL 实例」—— 因跨 schema 全限定表名 SQL，两库必须同实例 |
| 跨 schema 只读实体 | `.../entity/EclassroomInstance.java:17`、`TenantEclassroom.java:17` | `@TableName("lesson_appointment.sys_eclassroom_instance")` / `sys_tenant_eclassroom`（主库 DDL `api/sql/schema/20261027-0900-eclassroom-tenant.sql`，2 张表） |
| 跨 schema 只读报名数据 | `.../mapper/BookingRosterMapper.java:28,42` | `SELECT COUNT(1) FROM lesson_appointment.booking`（查报名人数 / 名单） |
| 排期源头 | `api/src/main/java/com/reservation/service/CourseScheduleService.java` | `course_schedule` 在主库；`pushAfterCommit` 在 created(:319) / updated(:363) / cancelled(:394, :772, :841) 多处触发 |
| 套餐配额 | `TenantQuotaService` / `TenantPackageService` | `SCHEDULE` 配额按主库 `course_schedule` 行数占用（§2） |
| 回调回流 | `.../service/CallbackService.java:82,88,94` | classroom → booking `/api/v1/classroom-callback/{attendance,alerts,reconcile}`；签到回流写 `appointment.status`（`ClassroomController.java:74`），课时回流带 `consumptionVersion` |
| 回调路径独占 | `ClassroomCallbackController.java:31-44` | 必须独占 `/api/v1/classroom-callback/**`，否则经公网域名打到课堂服务会 404 |
| 自有库 | `api/classroom-service/sql/classroom-schema.sql` | 14 张表：`classroom` / `membership` / `attendance` / `presence_segment` / `session_record` / `runtime_state` / `material` / `rollcall` / `submission` / `recording` / `reconcile_log` / `reconcile_diff` / `audit_log` |

#### (B) 服务层 —— 已独立，但共享密钥域与双向 HTTP 契约

- **共享密钥域**：`jwt.secret=${JWT_SECRET:…}`、`crypto.aes-key=${AES_KEY:…}`、`crypto.hmac-key=${HMAC_KEY:…}`（classroom-service `application.properties:53,57,58`）→ booking 签发的 token 被课堂服务直接验签，这是当前「免 SSO」的基础，也是鉴权解耦的代价点。
- **booking → classroom**：`ClassroomEventPushService`（`RestTemplate`，事务提交后异步、动态服务发现从 `sys_tenant_eclassroom` 查实例地址、JWT system 身份 + 报文 HMAC 签名、best-effort 失败仅记日志）。
- **classroom → booking**：`booking.api.base-url=${BOOKING_API_URL:http://localhost:8081}` + `CallbackService` 三端点。
- **事件幂等**：`EventIdempotentGuard` Redis SETNX（TTL 7 天）+ `consumption_version` 丢弃旧报文（§5）。

#### (C) 前端页面层 —— 文件已独立，运行时仍强耦合

- **已独立的资产**：`classroom.html` / `classroom-prep.html` / `classroom-ops.html` / `replay.html` 四个页面；`frontend/js/classroom/*.js`（12 个）+ `rtc/*.js`（3 个）；`frontend/css/classroom.css`。
- **共用基础设施**（`classroom.html:172-199`）：`utility_request.js`（axios 封装）、`api.js`（`request` / `EP` / `classroomUrl` / `getClassroomApiBaseUrl` / `sessionStorage` 配置缓存）、`shared-domain-bridge.js`、`feature-flags.js`、`shared/apiPaths.js`、`shared/domain/*`。
- **登录态**：`localStorage.token`（booking 签发）；`classroom-main.js:67` 取 token，`_boot(user)` 的 `userId/name/role/tenantCode` 均来自 booking 会话。
- **配置接口**：`classroom-main.js:69-70` `_ensureConfig` 调 `EP.ECLASSROOM_CONFIG = '/api/v1/eclassroom/config'`（**booking-api 的 `EclassroomController`**）拿 `apiBaseUrl` / `wsBaseUrl` / `enabled`；菜单显隐也依赖此 `enabled`（见项目记忆）。
- **入口散落**：`admin.html` / `student.html` / `teacher.html` / `platform_admin.html` / `replay.html`；跳转链接由 `admin-booking.js:385`、`admin-schedule.js:2638` 生成 `classroom.html?scheduleId=`。
- **平台端管理页归属 booking**：`platform-admin-eclassroom.js` 调 `/api/v1/eclassroom/{instances,tenant/*}`（实例 CRUD、租户 bind/disable/unbind），嵌在 `platform_admin.html`；写接口全部 `checkPlatformAdmin`。
- **构建链**：`frontend/build.js` 单仓单 `dist`（全量重建约 128 文件、`dist`/`deploy/dist` 同步、注入 `shared-domain-bridge`、`copyAssets` 黑名单），并受 `sync-miniprogram-shared` / `check-shared-sync` / `gen-shared-bridge` / `check:bridge-exports` 四步守卫约束（见项目记忆）。

#### (D) 部署层 —— 单前端实例反代三服务

- `cloudBased/frontend/default.conf.template` 一个 nginx：`API_UPSTREAM`(8081) / `MSG_UPSTREAM`(8090) / `CLASSROOM_UPSTREAM`(8092)，14 个课堂 `location` 前缀 + `/ws/classrooms/`（需 Upgrade 头），上游由运行时 envsubst 白名单渲染。
- 课堂前缀清单唯一事实源 `doc-develop/90-tools/dev-proxy.js:76-91`，必须与 nginx 逐字一致；`cloudBased/classroom-service/` 已是独立部署单元。

### 11.3 可能性判断

| 目标 | 可行性 | 判断依据 |
|---|---|---|
| **L0 服务进程独立** | ✅ 已完成 | 独立工程 / 端口 / jar / 部署单元 |
| **L1 数据独立（去跨 schema、可异机）** | ✅ **可行，中低代价** | 只读依赖仅 3 类（实例、绑定、`booking` 报名数）；改为主系统只读 API 或事件投影即可解除「同实例」约束 |
| **L2 页面独立（独立构建 / 部署 / 入口）** | ✅ **可行，中高代价** | 页面与 JS 资产本就独立；真正的难点是**登录态、配置发现、平台端管理页归属**与共享构建链，不是页面本身 |
| **L3 完全独立产品（脱离排期与租户体系）** | ❌ **不成立** | 课堂由 `course_schedule` 派生（§1）、配额来自主库套餐（§2）、课时/签到回流 `appointment`（§5）；脱离 booking 就没有课堂来源与账务闭环 |

**结论**：**「独立」应理解为 L1 + L2，而非 L3**。合理终局是「课堂作为独立服务 + 独立前端子站 + 独立数据库，但共用统一身份（SSO）与排期事件契约」。这不是妥协，而是由「课堂 = 排期派生」的业务本质决定的边界。

### 11.4 代价清单（按维度，含具体改动面）

| 维度 | 代价 | 具体改动面 |
|---|---|---|
| **数据解耦** | 跨 schema 只读 3 类改 API / 投影；解除同实例约束后可异机，但引入**一致性窗口与网络失败** | `EclassroomInstanceMapper` / `TenantEclassroomMapper` / `BookingRosterMapper` / `TenantEclassroomService`；booking 侧需新增只读内部端点；`application.properties:17` 约束说明改写 |
| **契约解耦** | 事件推送 + 回调两条链路需定义独立契约（或引入 MQ）；链路变长后幂等 / 重试 / 对账加重 | `CourseScheduleService` 5+ 处 `pushAfterCommit`、`ClassroomEventPushService`、`ScheduleEventConsumer`、`CallbackService`、`ClassroomCallbackController`、`EventIdempotentGuard`、`consumption_version` 逻辑 |
| **鉴权解耦** | 共享 `JWT_SECRET`/`AES_KEY`/`HMAC_KEY` 密钥域 → 独立需 SSO/OIDC 或网关统一验签 + 身份头透传；密钥轮换策略要重定 | 两端 `JwtUtil` / `JwtAuthenticationFilter` / `application.properties` / 免登录白名单四处（见项目记忆） |
| **前端解耦** | 拆第二套构建与 dist；共享桥改版本化 SDK；菜单显隐、入口跳转、平台端实例管理页迁出 | `build.js`（或新建 `build-classroom.js`）、`shared-domain-bridge.js` + 四步同步守卫、`api.js` `_ensureConfig`/`getClassroomApiBaseUrl`、`feature-flags.js`、`platform-admin-eclassroom.js`、`admin-booking.js` / `admin-schedule.js` 跳转、4 个业务页菜单 |
| **部署 / 网络** | 第二套 nginx / 域名 / 证书 / 安全头 / CORS / WS Upgrade；云托管内网域名 + `resolver` 变量形 proxy_pass 坑（见项目记忆） | `cloudBased/frontend/default.conf.template` 拆分、`resolver-entrypoint.sh` envsubst 白名单、`dev-proxy.js` 前缀清单分家、`/api/v1/classroom-callback/**` 路由归属 |
| **运维** | 多一套发布 / 监控 / 日志 / 扩容；双读双写兼容期；跨服务故障定位复杂度上升 | CI/CD、监控告警、`MonitorService`、日志聚合 |
| **一致性风险** | best-effort 事件在异机 / 跨网后失败率上升；签到与课时回流若丢，主库 `appointment.status` 与课时账务不一致 | 需补对账（`classroom_reconcile_log/diff` 已有底座）+ 补偿重推 |

**最容易被低估的三处**：① `/api/v1/eclassroom/config` 是**页面启动 + 菜单显隐**的双重真相源，迁走后前端缓存不自愈问题会放大（项目记忆）；② `shared-domain-bridge.js` 是手工白名单，拆构建会触发 `check:bridge-exports`；③ 回调路径 `/api/v1/classroom-callback/**` 一旦与前端路由同前缀就会被 nginx 打到课堂服务 404。

### 11.5 途径（分阶段、每阶段可独立交付与回退）

| 阶段 | 目标 | 关键动作 | 回退点 |
|---|---|---|---|
| **S0（已完成）** | 服务进程独立 | 现状 | — |
| **S1 数据解耦** | 去跨 schema、可异机 | booking 提供只读内部 API（实例 / 绑定 / 报名 roster）或把配置表事件投影到课堂库；3 个 Mapper 改 HTTP 客户端；解除 `application.properties:17` 同实例约束 | 保留 Mapper 直连开关，配置切换 |
| **S2 契约解耦** | 事件 / 回调独立化 | 定义版本化事件契约（或引 MQ）；推送与回调各自补幂等 + 重试 + 对账；`consumption_version` 保留 | 双写过渡，HTTP 契约与 MQ 并存 |
| **S3 鉴权解耦** | 统一身份 | booking 作 IdP、classroom 作 RP（OIDC/JWKS），或网关验签后透传身份头；密钥域隔离与轮换 | 兼容期同时接受旧共享密钥 token |
| **S4 前端独立** | 独立子站 | 拆独立 dist / 域名（或 `/classroom/` 路径）；共享桥抽版本化 SDK；菜单改跨站跳转带一次性 ticket；平台端实例管理页并入课堂控制台；`_ensureConfig` 改拉课堂侧配置 | 老域名保留反向跳转 |
| **S5 运维独立** | 独立扩缩容 | 独立部署单元、独立监控与告警；按租户路由到不同实例（呼应 §10 实例级限额） | — |

**推荐路径**：**S1 → S3 → S4**，S2 视事件失败率再决定是否引 MQ（现有 HTTP + 幂等 + 对账已够用，不必为「解耦」而过度改造）。**不建议直奔 L3**：课堂脱离排期与租户体系在业务上不成立，投入产出比为负。

**最小可行解（若只想快速拿到「页面独立」）**：保留共享 JWT 密钥域与 booking 的 `/api/v1/eclassroom/config`，仅拆一套课堂专用构建 + 独立静态域名 + 反向代理到现有 8092，菜单改跨站跳转带 ticket。代价约等于 S4 的一半，但数据层仍受「同 MySQL 实例」约束 —— 属于「页面独立、数据未独立」的过渡态。

### 11.6 一句话结论

**课堂的服务与自有数据已基本独立，页面资产也已独立；真正没解的是「同 MySQL 实例的跨 schema 只读」「共享密钥域的登录态」「booking 侧的配置发现与平台管理页」以及「单 dist / 单 nginx 的部署形态」。** L1+L2 可行且建议分阶段推进（S1 数据 → S3 身份 → S4 前端），L3 完全独立因「课堂 = 排期派生」不成立。
