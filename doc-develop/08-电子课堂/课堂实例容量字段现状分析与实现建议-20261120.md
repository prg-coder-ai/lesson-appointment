# 课堂实例「容量」字段：现状分析与实现建议

> 核对时间：2026-11-20（MySQL 8.4.11 / 本机库 `lesson_appointment`）
> 面向对象：平台运营、后端开发、部署同学
> 涉及代码：`api/.../entity/EclassroomInstance.java`、`api/.../service/EclassroomService.java`、
> `api/.../controller/EclassroomController.java`、`frontend/js/platform-admin-eclassroom.js`、
> `api/classroom-service/.../rtc/*`、`api/classroom-service/src/main/resources/application.properties`

---

## 〇、一句话结论

`sys_eclassroom_instance.max_capacity`（平台端叫「最大容量」）**是纯记录字段**：
能填、能存、能在列表里显示，**但系统里没有任何一处代码读它做校验或统计**。
配套的 `current_load`（当前负载）**从未被写入过任何值**，永远停在建表默认的 `0`。

因此当前系统**对「一个课堂实例能承载多少间并发课堂」没有任何限制**。真正生效的
「人数上限」是 RTC 拓扑的 `max-peers = 6`，那是**每间课堂内部**的约束，与本字段无关。

---

## 一、字段与设计意图

| 项 | 内容 |
|---|---|
| 表 | `sys_eclassroom_instance` |
| 列 | `max_capacity int DEFAULT NULL COMMENT '最大并发课堂数'` |
| 列 | `current_load int DEFAULT 0 COMMENT '当前负载（并发课堂数）'` |
| 平台端表单 | 「基本信息 → 最大容量」，新建时默认填 `100` |
| 平台端列表 | 第 7 列展示 `maxCapacity`（无值时显示 `-`） |

按设计意图，这对字段应承担「实例级准入」：开课前比对 `current_load` 与 `max_capacity`，
满则拒绝。**这个能力当前不存在。**

---

## 二、实际链路：填 → 存 → 显示，然后断了

| 环节 | 现状 | 代码位置 |
|---|---|---|
| 表单提交 | `maxCapacity: f.maxCapacity.value ? Number(...) : null` | `frontend/js/platform-admin-eclassroom.js:227` |
| 落库 | MP 自动映射写入 `max_capacity`，**无任何合法性校验** | `EclassroomService.createInstance` / `updateInstance`（仅 `insert` / `updateById`） |
| 列表展示 | `inst.maxCapacity != null ? inst.maxCapacity : '-'` | `platform-admin-eclassroom.js:102` |
| **后端读取** | **零处** | 全仓库 grep `maxCapacity` / `currentLoad`，只命中两侧实体字段声明 |
| **current_load** | **零处写入** | 同上；建表默认 0 后再无变化 |
| 绑定时参考负载 | 无 | `bindTenantClassroom` 只校验「实例存在且未删除」 |
| 开课时参考容量 | 无 | `markReady` / `startClass` / 排期事件推送均不读该字段 |

> 注意 `EclassroomInstance` 实体在**两个服务里各有一份**（`api` 与 `api/classroom-service`），
> 两份都声明了 `maxCapacity` / `currentLoad`，**两份都没有使用**。
> 课堂服务侧连"读出来看看"都没有，等于该字段对运行时完全透明。

由于 `createInstance` / `updateInstance` 不做校验，`maxCapacity` 可以存成负数或 `0`，
语义上已被污染——即使将来加校验，也得先清理存量脏值。

---

## 三、真正生效的约束在哪（另一个维度）

| 约束层 | 真实值 | 来源 | 超限后的行为 |
|---|---|---|---|
| 单课堂人数（默认 `native-mesh`） | **6 人** | `classroom.rtc.mesh.max-peers=${RTC_MESH_MAX_PEERS:6}` | 超出**只收不发**，不拒绝进房 |
| 单课堂人数（LiveKit/SFU） | 无上限 | `LiveKitRtcProvider:98` `info.setMaxPeers(null)`，注释「SFU 无人数上限，由服务器容量决定」 | 不限制 |
| **每实例并发课堂数** | **无任何校验** | — | 不拒绝，全部照开 |
| 每用户 WS 连接数 | **3 条**（`signal` / `whiteboard` / `heartbeat`） | `frontend/js/public/classroom-ws.js:25` | — |
| WS 连接总数 | Tomcat 默认 `max-connections=8192` ≈ **2730 人** | 未配置，取默认 | 超时静默拒绝 |
| 请求处理线程 | Tomcat 默认 `max-threads=200` | 未配置，取默认 | 请求排队 |
| 心跳 / 掉线判定 | 心跳 `15s`、判定 `60s`、教师掉线宽限 `120s` | `application.properties:70-88` | 见第四节 ① |
| 重连宽限 | `reconnect-grace-seconds=30`（必须 < offline-timeout） | 同上 | — |
| JVM 堆 | `-Xmx512m` | `deploy/classroom.env.template:69` | OOM |
| DB 连接池 | 未配置，Hikari 默认 **10** | 无 `maximum-pool-size` | 等连接超时 |

**结论**：现网 `default-local` 实例填的 `max_capacity=200`，**没有任何代码会去执行这个 200**。

## 四、没有限制会有什么影响（按后果排序）

### ① 过载的表现是「误判掉线 / 误结课」，而不是「拒绝开课」——最严重

心跳每 15s 一次，判定阈值 60s（约 4 次心跳丢失）。实例过载时（线程排队、GC 停顿、
Redis 慢），心跳写入延迟会先于业务失败出现：

- **学生**：DB 在线但 Redis 在线 key 消失 → 判 `OFFLINE` + `leave`，直接影响
  `lesson_attendance` 的状态与有效时长（`attendance.adjust_by` 人工调整之外无法回滚语义）；
- **教师**：离线超过 `teacher-drop-grace-seconds=120` → **触发自动结课**
  （`ClassroomClosingService.closeAfterEnd`）→ 重算有效时长、归一 `ABSENT/PRESENT/LATE`、
  回流课时、`consumption_version + 1` 并推送预约侧。

后者是**数据事故**，不是"卡一下"：正在上的课被系统按"已结束"落账，且预约侧会按新版本
丢弃旧报文。过载的代价被放大成账务与考勤错误。

### ② 平台端没有负载视野

`current_load` 恒为 `0`，列表里的「容量」是静态配置。运营无法判断「该不该扩实例」，
多实例部署时也无法按负载分配——`bindTenantClassroom` 是人工点选实例，不看负载也不看容量。

### ③ 商务承诺与技术能力脱钩

「支持 N 间并发课堂」没有任何代码兜底。超卖不会被系统拦住，只会在上课高峰以掉线形式暴露，
而且事后排查时从日志上看到的是一批"掉线"，看不出根因是并发超限。

### ④ 退化方式是雪崩而非排队

没有准入就没有排队。第 201 间课正常开，所有课堂一起变慢；有准入时至少是"第 201 间被拒绝，
前 200 间保持正常"。

### ⑤ 租户级「人数上限」同样未实现

`sys_tenant_eclassroom.config` 列注释写「如录制开关、人数上限等」，但课堂服务里
**`getConfig()` 没有任何消费点**（全仓库无调用）。大班课 / 小班课无法差异化限制。

## 五、顺带发现：一条会导致故障的实例数据

现网 `sys_eclassroom_instance` 有两条记录：

| id | instance_code | api_host | max_capacity | current_load | 说明 |
|---|---|---|---|---|---|
| 5 | `default-local` | `127.0.0.1` | 200 | 0 | 4 个租户（1/3/18/19）都绑在这条 |
| 6 | `eclass2cluster` | **空串**（`LENGTH=0`，非 NULL） | 5 | 0 | 疑似测试残留 |

风险链：

1. `EclassroomService.buildApiUrl()` 只判断 `host == null`，**空串能通过**，会拼出
   `http://:8092/api/v1` 这种不可用地址；
2. `bindTenantClassroom()` 只校验「实例存在且 `deleted != 1`」，**不校验 `api_host` 非空、
   也不校验 `status`**（`status=0` 停用、`2` 维护中都能被绑）；
3. 于是平台端「课堂配置 → 启用」把某个租户绑到 `id=6` 后，该租户课堂入口会全挂，
   而错误信息不会指向"地址是空串"这个真正原因。

**建议**：要么删掉这条测试残留，要么补全其地址；无论哪种，`bindTenantClassroom` 都该补
`api_host` 非空 + `status == 1` 的前置校验（fail closed）。

## 六、让容量真正生效的路径

### 6.1 最小闭环（建议先做这一步）

1. **让 `current_load` 变真**：开课时 +1、结课时 -1，实现建议用 Redis 计数器做实时值 +
   定时落库到 `current_load` 列（与课堂服务"以 Redis 在线 key 为在线真相源"的既有口径一致）；
2. 平台端列表把 `current_load` 展示出来（现在只有静态的「容量」）。

> 没有真实的 `current_load`，任何容量策略都是空转——这是所有后续步骤的前置条件。

### 6.2 加硬准入

3. 开课入口（`markReady` / `startClass` / 排期事件驱动的自动开课）比对
   `current_load >= max_capacity` → 拒绝并返回明确错误码与文案（建议 `409`，与
   `ClassroomClosingService` 既有 40901「课堂已结束」同族），不做静默降级；
4. `createInstance` / `updateInstance` 补校验：`maxCapacity` 必须为正整数；
5. `bindTenantClassroom` 补校验：`api_host` 非空、`status == 1`；
6. 存量脏值清理（`max_capacity <= 0` 或 `NULL` 的记录）。

### 6.3 多实例阶段才谈的

7. 绑定租户时按 `current_load / max_capacity` 自动选实例（有容量余量的优先）；
8. 若要按 `scheduleId` 分片路由到不同实例，才需要网关侧的分流规则（当前单实例，容量即使
   实现也无处调度）；
9. 租户级 `maxMembers`（`sys_tenant_eclassroom.config` JSON）单独落地，进房时校验；
   注意与 `mesh.max-peers` 区分——**一个是业务上限，一个是技术拓扑上限**，
   两者同时存在时应取较小值，并在错误文案里说明原因。

## 七、核对方法（可复现）

```bash
# 1. 确认字段确实无业务读取（应只命中实体声明与前端表单/列表）
grep -rn "maxCapacity\|currentLoad\|max_capacity\|current_load" \
  api/src/main/java api/classroom-service/src/main/java --include=*.java

# 2. 确认 current_load 从未被写入
grep -rn "current_load" api/src/main/resources api/classroom-service/src/main/resources

# 3. 真实容量相关配置
grep -nE "max-peers|offline-timeout|heartbeat-interval|teacher-drop-grace" \
  api/classroom-service/src/main/resources/application.properties

# 4. 现网实例数据（注意 api_host 是否为空串）
mysql -uroot -p -e "SELECT id,instance_code,api_host IS NULL,LENGTH(api_host),
  max_capacity,current_load FROM lesson_appointment.sys_eclassroom_instance;"
```

## 八、给运营的一句话

容量字段当前等于**备注**，列表里的 `200` 不要写进商务材料；
「支持多少间并发课堂」在代码层没有任何约束。真正要先修的不是容量校验，
而是第五节那条 `api_host` 为空的实例——它一旦被绑定，教室会直接进不去。
