## 零、v2 相对 v1 的两处根本改动

| # | v1 的写法 | v2 按你的决策改为 |
|---|---|---|
| 1 | 按有效时长分档扣（≥80% 扣 1、早退扣 0.5…），状态与钱绑在一起 | **扣费只判「有没有请假」**：只要不是 `cancelling` 族，一律扣 1 课时、减 1 余量；**与上了多久无关**。`checked-in` / `completed` / `absent` 纯粹是**出席现状记录**，不参与计费 |
| 2 | 课堂标识沿用排期级，课次级列为待拍板 | **课堂标识升级为课次级**（`schedule_id + class_index`），因为一个排期会展开 N 个课次，扣减必须落到具体那一课次 |

这两条一改，整个模型的骨架就变了：**计费与出席解耦**。
出勤数据只回答「学生来没来」，扣费只回答「学生请没请假」。

## 一、三个必须先讲清的现状事实

### 1.1 没有「余量」可减 —— 这一步今天无处落地

- `StudentBalanceService` 是接口 + `StudentBalanceServiceStub`，**只打 warn 日志，不落库**；
- 库中 `SHOW TABLES LIKE '%balance%'` 返回**空**：`student_balance` / `student_balance_flow` 都不存在；
- `booking` 表没有课时数字段，`course` 表只有 `class_duration`（单课时长），没有「购买了多少课时」。

**结论**：你要求的「减余量」必须先有账本。本方案在第四节给出 `student_lesson_balance` +
`student_lesson_flow` 两张表的完整 DDL，这是本轮**必须一起做**的前置（否则「减余量」只能写在日志里，正如今天的 Stub）。

### 1.2 课堂是排期级，扣减要课次级（v2 已定为升级）

| 对象 | 粒度 | 证据 |
|---|---|---|
| `classroom` | 一个排期一个课堂（主键 `schedule_id`） | `classroom` 表 DDL |
| `appointment` | 一个排期按重复规则展开 **N 个课次** | `CourseScheduleService:599` `setClassIndex(index++)`，`class_index = 1..N` |
| `lesson_attendance` | 唯一键 `(schedule_id, user_id)` | 第一期 DDL |

一个每周重复排期 → 10 个课次、只有 1 个课堂、1 条出勤。第 3 次与第 8 次无法区分，扣减必然重复或漏扣。

现状：`course_schedule` 中 `repeat_type=0` 100 条、`repeat_type=2` 2 条；现存 `booking` 都是 1 个课次。
**现在还没炸，但代码路径支持 N，一有重复排期就炸。**

### 1.3 没有任何代码会把课次置为 `completed`

`grep "\"completed\""` 只命中 `AppointmentStatus` 常量定义与两处统计 SQL。
库里 5 条 `appointment` **全部是 `active`** —— 课后状态流转这件事，目前完全是空的。
且现有 14 个状态中**没有 `absent`**。

## 二、状态机（纯出席记录，不涉费用）

### 2.1 新增两个状态

| 状态 | 含义 | 写入时机 | 终态 |
|---|---|---|---|
| **`checked-in`** | 学生已进入课堂（**仅表示出席，不产生任何费用动作**） | 学生 `enter` 成功 | 否 |
| **`absent`** | 缺席：课次结束仍未进入过课堂 | 课次收尾 | 是 |

> `checked-in` 的定位按你的要求确定：**只是学生状态**。它不触发扣减、不触发退费、不写任何金额字段。
> 唯一作用是让老师/学生在预约列表上立刻看到「已签到」。

### 2.2 迁移表

| # | 当前状态 | 触发 | 新状态 | 说明 |
|---|---|---|---|---|
| T1 | `active` / `noted1` / `noted2` | 学生首次进入课堂 | `checked-in` | 只写状态，不产生费用 |
| T2 | `checked-in` | 课次收尾 | `completed` | 进过即出席 |
| T3 | `active` / `noted1` / `noted2` | 课次收尾（从未进入） | `absent` | 缺席 |
| T4 | `checked-in` | 学生中途全离场（有效时长为 0 且已离场） | 保持 `checked-in`，收尾时才定终态 | 不在过程中来回改 |
| — | `completed` / `absent` / `cancelled` / `t-cancelled` / `changed` / `frozen` | 任何自动事件 | **不变** | 终态保护；只有管理员改判能改，且留审计 |

### 2.3 `completed` / `absent` 的判定

**主判据：`lesson_attendance.check_in_at` 是否非空。**

- 非空（进过课堂）→ `completed`
- 为空（从未进入）→ `absent`

可选阈值 `classroom.attendance.completed-ratio`（默认 **0**，即「进过就算出席」）：
若你希望「进 2 分钟就走」也算缺席，把它调成 0.5 即可，规则引擎不需要改代码。

> 注意：该阈值**只决定状态**，不影响扣费。扣费只看请假与否（见第三节）。
> 这与 v1 完全不同 —— v1 把阈值同时用于计费，已被你的决策推翻。

## 三、扣减规则（v2 核心，二元判定）

### 3.1 唯一判据：有没有请假

| 课次状态 | 是否请假 | 计扣课时 | 是否减余量 |
|---|---|---|---|
| `cancelling` / `canceling` / `s-cancelling`（申请中） | 是（**已提交申请即算**） | **0** | 否 |
| `cancelled` / `canceled` | 是（已获准） | **0** | 否（退费按 `refund_snapshot` 档位单独处理） |
| `t-cancelling` / `t-cancelled`（**教师**发起） | 否（非学生责任） | **0** | 否 |
| `changed`（已改期） | — | **0**（本次不算，改到新时间再算） | 否 |
| `frozen`（删除预订） | — | **0** | 否 |
| `active` / `noted1` / `noted2` / `checked-in` / `completed` / `absent` | **否** | **1.0** | **是** |

一句话概括：**除「请假 / 教师取消 / 改期 / 冻结」外，每课次必扣 1 课时。**

典型后果（均为设计意图，非 bug）：

- 学生全程没来、也没请假 → `absent` + **扣 1**
- 学生来了 3 分钟就走 → `completed` + **扣 1**（费用与时长无关）
- 学生上满 60 分钟 → `completed` + **扣 1**
- 学生提前 1 天请假获准 → `cancelled` + **扣 0**
- 老师临时取消 → `t-cancelled` + **扣 0**

### 3.2 与退费链路的分工（不重叠）

```
课次 active
   ├── 请假获准 ──▶ cancelled ──▶ refund_snapshot 档位退费（金额/课时按档位比例退回）
   └── 未请假 ──▶ 课次结束 ──▶ 扣 1 课时（全额）
```

两者**互斥**：走了请假的课次不再扣；已扣的课次不允许再走请假退费。
硬校验写在 `AppointmentStateAdvancer` 里（见 6.2）。

### 3.3 参数（全部可配）

```
# 出席判定线（只影响状态，不影响扣费）。默认 0 = 进过即出席
classroom.attendance.completed-ratio=0
# 每课次计扣课时数
lesson.deduction.per-class=1.0
# 余额不足是否允许扣成负数（历史学生没有课时包，只能欠着，运营后补）
lesson.balance.allow-negative=true
```

### 4.2 余量账本（**本轮必须新建**，否则「减余量」无落点）

```sql
-- 学生课时余额
CREATE TABLE `student_lesson_balance` (
  `id`                bigint       NOT NULL AUTO_INCREMENT,
  `tenant_id`         bigint       NOT NULL DEFAULT 0,
  `student_id`        varchar(36)  NOT NULL,
  `total_lessons`     decimal(8,2) NOT NULL DEFAULT 0 COMMENT '累计购买课时',
  `used_lessons`      decimal(8,2) NOT NULL DEFAULT 0 COMMENT '累计消耗课时',
  `remaining_lessons` decimal(8,2) NOT NULL DEFAULT 0 COMMENT '剩余课时（=total-used，允许负数=欠课）',
  `version`           int          NOT NULL DEFAULT 0 COMMENT '乐观锁',
  `create_time`       datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`       datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_slb_tenant_student` (`tenant_id`, `student_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='学生课时余额';

-- 课时流水（幂等核心）
CREATE TABLE `student_lesson_flow` (
  `id`              bigint       NOT NULL AUTO_INCREMENT,
  `tenant_id`       bigint       NOT NULL DEFAULT 0,
  `flow_id`         varchar(36)  NOT NULL COMMENT '流水号UUID',
  `student_id`      varchar(36)  NOT NULL,
  `booking_id`      varchar(36)  NULL,
  `schedule_id`     varchar(36)  NULL,
  `class_index`     int          NULL,
  `appointment_id`  int          NULL,
  `change_lessons`  decimal(4,2) NOT NULL COMMENT '负数=消耗，正数=退回/充值',
  `remaining_after` decimal(8,2) NOT NULL COMMENT '变动后余量（对账用）',
  `source`          varchar(20)  NOT NULL COMMENT 'classroom课堂扣减/leave请假退回/manual人工/grant充值',
  `biz_key`         varchar(128) NOT NULL COMMENT '幂等业务键，见下',
  `reason`          varchar(255) NULL,
  `operator_id`     varchar(36)  NULL,
  `create_time`     datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_slf_flow` (`flow_id`),
  UNIQUE KEY `uk_slf_biz` (`tenant_id`, `biz_key`),
  KEY `idx_slf_student` (`tenant_id`, `student_id`, `create_time`),
  KEY `idx_slf_appt` (`appointment_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='课时流水';
```

**`biz_key` 的取值**（这是绝不重复扣的唯一保障）：

```
classroom:{appointmentId}          ← 课堂结算，一课次一条
leave:{appointmentId}              ← 请假退回，一课次一条
manual:{uuid}                      ← 人工调整，每次一个
```

`uk_slf_biz` 唯一键让「重复回调 / 重试 / 兜底任务再跑一次」都变成 `DuplicateKeyException`，
捕获后直接返回成功 —— **同一课次永远只扣一次**，不依赖任何分布式锁。

### 4.3 为什么业务事实与账务动作要分两层

`lesson_attendance` 记「这堂课发生了什么」，`student_lesson_flow` 记「账上动了多少」。
分开的好处：

- 规则变更（比如以后改成按分钟计费）只需重算 `consumed_lessons`，账本按 `source='classroom'` 的行全量回滚重放；
- 对账时 `SUM(flow.change_lessons)` 与 `balance.used_lessons` 必须相等，不等即有问题；
- 余额表晚建、重建、迁移都不影响已沉淀的上课事实。

## 五、触发时机

计费与出席解耦后，扣减**不再依赖课堂**，因此有两条触发路径，二者幂等共存：

| 路径 | 触发 | 适用 |
|---|---|---|
| **主路径** | 课堂收尾回调 `closeAfterEnd` → booking 侧结算 | 已开通课堂的租户 |
| **兜底路径** | 定时任务：课次结束 + N 小时仍非终态 → 直接结算 | 未开通课堂 / 回调丢失 |

兜底路径的意义（v2 比 v1 更重要）：既然「没请假就扣」，那扣减**不应该因为课堂没接通而漏掉**。
未开通课堂的租户也必须按时结算，否则课时永远欠着、账永远是糊涂的。

```
兜底任务（每 10 分钟）：
  SELECT * FROM appointment
   WHERE status IN ('active','noted1','noted2','checked-in')
     AND appointment_datetime + INTERVAL 24 HOUR < NOW();
  -- 逐个：无课堂记录 → 若从未进入则 absent，否则 completed；然后结算扣 1
```

N 小时默认 24（给迟到补录与人工改判留窗口），可配 `lesson.settle.grace-hours`。

## 八、边界场景

| # | 场景 | 期望 |
|---|---|---|
| 1 | 学生全程未进、未请假 | `absent`；扣 1；`consumption_state='settled'` |
| 2 | 学生进 3 分钟就走 | `completed`（默认阈值 0）；扣 1；明细里 `attendance_status=LEFT`、`effective_minutes=3` |
| 3 | 学生请假获准 | `cancelled`；扣 0；`consumption_state='waived'`；走 `refund_snapshot` 退费 |
| 4 | 学生提交请假但未审核（`cancelling`） | 扣 0（按你的口径「申请即算」）；审核驳回后需**补扣 1**（见下） |
| 5 | 老师取消（`t-cancelled`） | 扣 0 |
| 6 | 改期（`changed`） | 本次扣 0；新时间的新课次正常扣 |
| 7 | 同一课次重复回调 | `uk_slf_biz` 拦截，第二次返回幂等成功，余额不变 |
| 8 | 课堂取消（教室没开成） | `appointment.status` **不变**；是否扣费按「学生是否请假」判，不按课堂状态判 |
| 9 | 余额不足（历史学生 total=0） | 允许扣成负数（`allow-negative=true`），前端提示欠课；运营补录 `grant` |
| 10 | 回调与兜底任务同时结算同一课次 | `biz_key` 幂等，先到先得，后到直接成功返回 |

**场景 4 的补充**：按「申假即不扣」的宽松口径，存在「先申请→不扣→事后被驳回」的漏洞。
处理：审核驳回（`cancelling → active`）时触发**补扣**，`biz_key='classroom:{appointmentId}'` 若尚未存在则补记。
这条要写进 `RefundRuleService` 的审核分支。

## 九、验收判据

1. **状态三态**：`active` 课次 → 学生 enter → `checked-in`（余额不变）→ 课堂收尾 → `completed`（扣 1）。
2. **缺席**：全程未进 → `absent`，扣 1，`flow.change_lessons=-1`。
3. **请假**：`cancelling` → 扣 0；审核驳回后补扣 1（验证场景 4）。
4. **时长无关**：同一课次分别造「进 3 分钟」与「进 60 分钟」，两者 `consumed_lessons` 都必须为 1。
5. **幂等**：同一课次回调重放 3 次 + 兜底任务再跑 1 次 → `student_lesson_flow` 只有 1 行，余额只减 1。
6. **课次级**：一个 `repeat_type=2` 排期生成 3 个课次，分别上课 → 3 条 `lesson_attendance`、3 条 flow、余额减 3。
7. **对账**：`SUM(flow.change_lessons)` 与 `balance.used_lessons` 全租户相等。
8. **兜底**：造一条 25 小时前、无课堂记录的 `active` 课次 → 任务跑完变 `absent` 且已扣 1。

### 12.1 落地时做的三个与方案不同的决定

1. **课次级标识用「复合编码」而不是联合主键**（S5）
   方案原写「`classroom` 主键升 `(schedule_id, class_index)`」。实际改法是编码成
   `scheduleId~classIndex`（第 1 课次保持裸 id）。原因：改联合主键要动 8 张表、
   9 个控制器、11 个服务，而其中绝大多数只是把标识原样传给下一层；
   编码方案下 `schedule_id` 列直接存编码串，表结构与查询一字不改。
   分隔符选 `~` 是因为 `#` 会被浏览器当 fragment 截断、`:` 可能被代理当端口。

2. **余额并发用行锁而不是乐观锁重试**（S2）
   方案写的是乐观锁。实际用 `SELECT ... FOR UPDATE`：同一事务内重试在 RR 隔离级别下
   读到的是同一快照，version 永远不变，重试恒定失败——这个坑比不加锁更难查。

3. **扣余额 + 写流水用 `TransactionTemplate` 内层事务**（S2）
   若在外层 `@Transactional` 里 catch 住唯一键冲突，Spring 已把事务标记 rollback-only，
   提交时会抛 `UnexpectedRollbackException`；不 catch 则余额已经多扣。必须分两层。

# 十三、课堂状态转换 / 时间维度限制 / 已结束重开（2026-11-17 补充）

> 视角：管理端与教师端的**在线课堂**（classroom-service 的 `classroom` 表状态），不是预约侧的 `appointment` 课次状态（后者见第二/三节）。两套状态各管一层，别混。
> 本文只做现状梳理与方案分析，**未改代码**。

## 13.1 课堂状态机现状（权威口径）

```
                    ┌──────────── READY（就绪提醒；手动模式只提醒不翻）
                    │                    │
SCHEDULED ──────────┤                    ├──▶ LIVE ◀──PAUSED
   （已排期）        └──(直接开课)────────┘      │        │
                                                │ 暂停⇄恢复│
                                                ▼        ▼
                                              CLOSED / CANCELLED（终态）
```

| 状态 | 含义 | 谁能触发进入 | 是否可发布内容 |
|---|---|---|---|
| `SCHEDULED` | 排期已建课堂 | 排期事件创建 | 学生禁；教师可 |
| `READY` | 就绪（提醒已到） | 就绪扫描（自动模式） | 学生禁；教师可 |
| `LIVE` | 进行中 | `/start`（教师/管理员）或自动开课 | 全员可 |
| `PAUSED` | 教师暂停 | `/pause` | **师生全禁** |
| `CLOSED` | 已下课 | `/end`（教师/管理员强制）或自动下课 | 学生禁；教师可（内容），但无讨论意义 |
| `CANCELLED` | 已取消 | `/cancel` 或排期取消事件 | 同上 |

### 触发入口（代码级）
- 教师/管理员端：`ClassroomController` `/start` `/pause` `/resume` `/end`（均 `isTeacher||isManager` 校验 + `assertAccess`），`/cancel` 在 `ClassroomService.cancel`。
- 后端扫描器：`ClassroomScheduler` 七个（下面 13.3 详述），自动流转由 `classroom.state-manual-only` 总闸控制。
- 管理端强制结束：`AdminConsoleController#end`（与教师 `/end` 同一 `endClass` 入口）。

### 状态流转的强约束
- `transitionStatus(scheduleId, from, to)` 用 `UPDATE ... WHERE status=from` 的**乐观前置**（`ClassroomMapper.xml:5-9`），affected=0 即抛 409 状态冲突——并发下同一课堂不会被重复开课/下课。
- 每次流转后 `publishGuard.invalidate()` 清门禁缓存（`ClassroomService:80`）。

## 13.2 已结束（CLOSED）的课能否再次开始？—— 现状：**不能**

### 直接原因：`startClass` 只接受 READY/SCHEDULED
`ClassroomService.startClass:121`：
```java
if (!"READY".equals(c.getStatus()) && !"SCHEDULED".equals(c.getStatus())) {
    throw ... "当前状态不可开课：" + c.getStatus();   // CLOSED 走到这里被拒
}
```
前端"进行中"按钮在 CLOSED 下**没有被禁用**（`classroom-controls.js:84` 只切 active 高亮，不 disable），所以教师仍可点，但点了会收到 409 —— **表现为"按钮能点却开不了课"，是个体验坑**。

### 更深层原因：下课收尾是不可逆的（这才是"不该随便重开"的正当理由）
`endClass → closeAfterEnd`（`ClassroomClosingService`）一次性做五件事，且都带副作用：
1. 闭合所有未结束的在线区间（写死 `leave_at`）；
2. 重算每位学生有效时长并归一出勤结论（ABSENT/PRESENT/LATE）；
3. 成员全部置 OFFLINE；
4. 录制中孤儿标 FAILED；
5. **`consumption_version += 1` 并向预约系统回流出勤 → 触发课时扣减（见第二/三节）**。

如果允许 CLOSED → LIVE 直接重开，会出现一串数据事故：
- 二次下课会**再回流一次出勤**。虽有 `consumption_version` 让预约侧丢弃旧报文，但同一课次扣两次的风险要重新论证；
- 已闭合的出勤区间、已归一的结论会被新的 join/checkIn 再次改写（`AttendanceService.checkIn` 对重进只改 REJOINED，**不覆盖 checkInAt**，但会新开区间）；
- 媒体房间已 `destroyRoom`，重开需要重建（`startClass` 里有 `createRoom`，但下课清掉的在线态、录制、时钟都要重来）；
- 课堂已过计划结束时间（`end_time`），重开后 `listOverdueLive` 会立刻又把它判为超时（自动模式下）。

**结论：现状"不能重开"是有意的、正确的守卫，不是 bug。** 真正的问题是"入口没跟着隐藏 + 没有给出可解释的提示"。

### 一个反直觉的事实：`enter` 不拦状态
`ClassroomController.enter:68-87` 没有校验课堂状态——CLOSED/CANCELLED 的课堂只要名单通过，仍可 `join` + `checkIn` + 开在线区间（`MembershipService.join` / `AttendanceService.checkIn` 均无状态前置）。也就是说：
- 学生**能进入**已结束的课堂（页面显示"已结束"，但成员表和区间会写脏数据）；
- 挡住重开的只有 `startClass` 一处，门禁与入口不对称。

## 13.3 时间维度上的限制（现状全景）

### 三个硬时间窗（SQL 层，ClassroomMapper.java）
| 扫描 | SQL 条件 | 参数 | 含义 |
|---|---|---|---|
| 就绪提醒 | `status='SCHEDULED' AND start_time <= NOW()+N min` | `ready-before-start-minutes=10` | 上课前 10 分钟起，已过开始时间仍卡的也扫（不设下界，故意） |
| 自动开课 | `status IN('SCHEDULED','READY') AND start_time<=NOW() AND (end_time IS NULL OR end_time>=NOW())` | 无 | **过了 end_time 的课绝不自启**——时间窗是开课的硬边界 |
| 自动下课 | `status IN('LIVE','PAUSED') AND end_time<=NOW()-grace` | `auto-end-grace-minutes=5` | 计划结束后 5 分钟才自动收，给拖堂留缝 |

### 手动模式总闸（2026-11-16 起默认）
`classroom.state-manual-only=true`：**扫描器 2/3/6 整轮跳过，扫描器 1 只提醒不改状态**。即当前生产口径是"时间只产生提醒，不驱动状态；状态全靠人点"。
- 代价（有意接受）：结束必须有人点"下课"，否则课堂一直 LIVE、不结算、不释放媒体房间；运营台"活跃课堂"能看到这类僵尸课。
- `classroom.auto-start=false` 是第二道开关（仅自动模式下生效）。

### 其它时间常数（都在 application.properties）
- 在线判定：`offline-timeout-seconds=60`、`reconnect-grace-seconds=30`（必须先于 offline-timeout）；
- 教师掉线结课宽限 120s（仅自动模式）；点名超时 2min；
- 历史保留：session 180 天、recording 90 天等（只清过程表，不动 `classroom` 主表）。

### 时间维度的核心矛盾
1. **计划时间（start_time/end_time）被当成状态闸门**：自动开课"过了 end_time 不自启"是对的，但手动模式下人可以在任何时间点开课——**时间约束对手动路径完全失效**，全靠操作者自觉。
2. **没有"最早可开课/最晚可下课"的显式约束**：教师可以提前一小时开课、也可以拖堂三小时不下课，系统不拦也不提示。
3. **过期课无自动终态**：手动模式下一堂 SCHEDULED 的课永远不来上课，会永远停在 SCHEDULED；只有 `end_time` 过去了也不会自动 CANCELLED/CLOSED。对账靠 `listStaleLive`（只找 LIVE 超时）覆盖不到这种"没开起来"的课。

## 13.4 综合运维与教学业务的分析

### 教学侧诉求
- **补上 / 重上的真实需求存在**：教师误点下课、网络中断被迫中止、临时换教室、学生到齐晚需要延后——这些场景下"这节课还得继续"是合理业务诉求，一刀切禁止重开会让教师只能把学生赶到别的课堂。
- 但"重开"必须回答两个问题：**课时扣几次**、**出勤算哪段**。按第二节决策，扣费只判"有没有请假"、一课次只扣 1（幂等 `biz_key`），所以**重开不应产生第二次扣费**——这一点现有账本设计已支持（`classroom:{appointmentId}` 唯一键）。

### 运维侧诉求
- **可解释、可追溯**：谁在什么时间把哪堂课从 CLOSED 改回 LIVE，必须留痕（操作人、原因、前后状态），否则对账时无法解释"一课次两段出勤"；
- **不能破坏幂等与终态保护**：第二节 T-行明确 `completed/absent/cancelled` 是终态，只有管理员改判能动且留审计——课堂侧重开必须与预约侧改判口径一致，否则两边状态打架；
- **僵尸课要能被发现**：手动模式下的"忘记下课""没开起来"要靠运营台/对账暴露，不能静默。

### 结论：分三类场景，不要一个"重开"按钮包打天下

| 场景 | 建议处理 | 理由 |
|---|---|---|
| **A. 误点下课，马上发现（秒级~分钟级，尚未真正产生出勤/回流）** | 允许**撤销下课**：CLOSED → 恢复开课前状态（LIVE/PAUSED），且**回滚本次收尾**（或标记回流作废） | 这是最常见的操作失误；此时二次收尾弊大于利，应给"撤销"而非"重开" |
| **B. 因故障中断，需要续上同一堂课（已回流、已扣费）** | 提供**续课**语义：新建续课 session（或复用课堂但新增 `session_seq`），**不再扣费**，出勤时段分段记录并合并 | 教学上合理；账上已扣的 1 课时覆盖两段，符合"一课次一扣" |
| **C. 课后补上/重新上一遍（跨时段，已结算）** | **不走重开**：为同一排期课次新建/改期一个新课堂（新 scheduleId），或走预约侧"改期→新一课次"；旧 CLOSED 保持终态 | 保持终态不可变与审计链，避免二次扣费与出勤覆盖 |

## 13.5 方案建议（按优先级）

### P0 — 修体验坑（小改动，立即做）
1. **CLOSED/CANCELLED 时隐藏或禁用"进行中/暂停/下课"按钮**，或点击后给明确提示"课堂已结束，不能再次开始；如需续课请联系管理员/新建课堂"，而不是抛一个 409。
2. **`enter` 加状态前置**：CLOSED/CANCELLED 不允许进入（或进入但明确只读、不 join / 不 checkIn / 不开区间），堵住 13.2 "能进已结束课堂"的脏数据口子。
3. **运营台暴露僵尸课**：把"已过 end_time 仍 SCHEDULED/READY"（没开起来）与"LIVE 超时"（忘了下课）两类都列为对账告警（现有 `listStaleLive` 只覆盖后者）。

### P1 — 撤销下课（场景 A）
- 新增 `/classrooms/{sid}/undo-end`：仅允许 CLOSED 且 `actual_end` 在 N 分钟内（如 5 分钟，可配 `classroom.undo-end-window-minutes`）、且**尚无后续成员进出**时执行。
- 动作：`CLOSED → LIVE/PAUSED`（记住下课前的状态）、`actual_end=NULL`、`consumption_version` 处理（回退或标记本次回流作废，通知预约侧丢弃）、恢复媒体房间。
- 必须写审计（操作人/原因/前后状态）并幂等。

### P2 — 续课（场景 B，需与课时口径一起定）
- 引入"续课"标识（如 `classroom.session_seq` 或独立 resume session 表），明确"一次课次可有多段实际授课，但只扣一次费"。
- 出勤按段记录、合并计算有效时长；回流时携带段信息，预约侧按 `appointmentId` 幂等，**不重复扣**。
- 这与 13.2 的 `consumption_version` 机制要对齐：续课产生的是"同一课次的补充出勤"，不是"第二次下课"。

### P3 — 时间约束显式化（运维友好）
- 给手动开课加**宽软约束**：早于 `start_time - N` 或晚于 `end_time + M` 点开课时弹确认（"当前不在计划上课时间，确定开课？"），不硬拦——教学临时调整是常态，硬拦会误伤。
- 计划结束时间到点后，手动模式下把"仍 SCHEDULED/READY"的课在运营台标"未开课（待处理）"，由人决定取消还是补上，而不是静默过期。
