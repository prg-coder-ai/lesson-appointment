## 2. 部署方法

### 2.1 前置条件

- **构建工具**：Maven（与后端 `api` 同款；系统 `mvn` 损坏时改用 launcher JAR 直启，见 2.6）。`frontend/pom.xml` 通过 `frontend-maven-plugin` 在 `prepare-package` 阶段**自动下载 Node v20.11.1 + npm 10.2.4** 并执行 `npm install` + `npm run build`，**本机无需预装 Node/npm**；`frontend/.npmrc` 已锁定官方 registry。
- Nginx 1.27.4（本机安装目录 `C:/Temp/nginx-1.27.4`；生产可装任意路径）
- 后端 API 服务可达：本地 `127.0.0.1:8081`（运行 `api/run.sh`）或远端 `152.136.254.127:8081`
- 操作系统：Windows（本手册命令均 Windows 原生）；**Ubuntu/Linux 服务器部署见第 6 节**

### 2.2 部署步骤

1. **构建（生成 dist）**：进入 `frontend/` 执行 `mvn package`（系统 `mvn` 损坏时用 Maven launcher，见 2.6）。`frontend-maven-plugin` 自动下载 Node/npm 并跑 `npm run build`，产出 `frontend/dist/`（压缩混淆后的部署产物）。
2. **部署 dist**：将 `frontend/dist/` 整体拷贝到目标 Web 根（本机可直接以 `frontend/dist` 为根；服务器放 `/var/www/frontend` 或任意目录，只需与 nginx `root` 一致）。**注意发布的是 `dist/`，不是源码 `frontend/`**——源码含 `node_modules/`、`target/`（Node 运行时）、`pom.xml` 等，不应上线。
3. **准备 nginx 配置**：复制/维护 `conf/nginx.conf`（见第 5 节附录），确认 `root` 指向 `dist` 目录、`proxy_pass` 指向实际后端地址。
4. **启动 Nginx**（见 2.4）。
5. **健康检查**（见 4.1）。

### 2.3 Nginx 配置要点

- `listen 8080;` —— 前端统一端口
- `root <frontend/dist 绝对路径>;` `index index.html;`（部署产物为 `dist/`，非源码 `frontend/`）
- `location /api/v1/ { proxy_pass http://<后端host>:8081; ... }` —— 同源反代，**浏览器侧无跨域**
- `location / { try_files $uri $uri/ /index.html; }` —— 未知路径 SPA 兜底到 `index.html`
- **Windows 路径坑**：必须使用 Windows 原生 `C:/` 路径；启动务必带 `-p <nginx前缀目录> -c <配置文件>`，否则 Nginx 会去「当前工作目录/conf/nginx.conf」找配置而失败。

### 2.4 启动 / 停止 / 重载（Windows）

```bash
# 校验配置（改配置后必做）
C:/Temp/nginx-1.27.4/nginx.exe -t -p C:/Temp/nginx-1.27.4 -c C:/Temp/nginx-1.27.4/conf/nginx.conf

# 启动（daemon 化，后台常驻）
C:/Temp/nginx-1.27.4/nginx.exe -p C:/Temp/nginx-1.27.4 -c C:/Temp/nginx-1.27.4/conf/nginx.conf

# 热重载（改配置后不中断服务）
C:/Temp/nginx-1.27.4/nginx.exe -s reload -p C:/Temp/nginx-1.27.4

# 停止
C:/Temp/nginx-1.27.4/nginx.exe -s stop -p C:/Temp/nginx-1.27.4
```

> 日志：`C:/Temp/nginx-1.27.4/logs/access.log`、`error.log`。`logs/` 目录需存在，否则 Nginx 启动报「could not open error log file」。

### 2.5 跨源导航模型（最终态）

| 角色       | 页面所在       | 访问地址                                                    |
| -------- | ---------- | ------------------------------------------------------- |
| 平台管理员    | 前端 `:8080` | `http://<host>:8080/platform_admin.html?tCode=platform` |
| 租户管理员    | 前端 `:8080` | `http://<host>:8080/admin.html?tCode=<tenantCode>`      |
| 学生/教师/预约 | 前端 `:8080` | `http://<host>:8080/{student,teacher,booking}.html`     |
| 所有 API   | 统一前缀       | `/api/v1/*`（由 Nginx `:8080` 反代或直连 `:8081`）              |

两个全局变量在 `js/public/api.js` 中定义（前端与后端各一份，须同步）：

```js

登录分发改写（**2026-09-09 起 platform_admin 也走 FRONTEND_ORIGIN**）：`platform_admin` 角色 → `FRONTEND_ORIGIN + '/platform_admin.html?tCode=platform'`；`admin` 角色 → `FRONTEND_ORIGIN + '/admin.html?tCode=' + tenantCode`。
> 迁移前 platform_admin 跳的是 `ADMIN_ORIGIN`（`:8081`）。现在平台管理页已在前端，若仍跳 `:8081` 会 404/500，故已统一改为 `FRONTEND_ORIGIN`。

### 2.6 前端构建（压缩混淆）

源码在 `frontend/`，部署产物在 `frontend/dist/`。构建由 Maven 驱动，无需本机预装 Node/npm。

- **构建命令（标准）**：
  ```bash
  cd frontend
  mvn package          # prepare-package 阶段触发 frontend-maven-plugin
  ```
- **构建命令（系统 mvn 损坏时，用 Maven launcher 直启）**：
  ```bash
  unset CLASSPATH
  M2='C:\Program Files\apache-maven-3.9.11'
  FRONTEND='C:\Users\Administrator\WorkBuddy\2026-08-30-17-19-24\frontend'
  cd "$FRONTEND"
  java -classpath "$M2\\boot\\plexus-classworlds-2.9.0.jar" \
    -Dclassworlds.conf="$M2\\bin\\m2.conf" \
    -Dmaven.home="$M2" -Dmaven.multiModuleProjectDirectory="$FRONTEND" \
    org.codehaus.plexus.classworlds.launcher.Launcher -B package
  ```
- **构建链路**：`install-node-and-npm`（自动下载 Node v20.11.1 + npm 10.2.4 到 `frontend/target/`）→ `npm install`（装 terser/clean-css/html-minifier-terser，读 `frontend/.npmrc` 官方源）→ `npm run build`（执行 `build.js`）。
- **`build.js` 压缩范围**（产物结构镜像源码、文件名不变，HTML 直接引用）：
  - JS：`terser` 压缩 + **仅混淆局部变量**，顶层全局（`ADMIN_ORIGIN`/`FRONTEND_ORIGIN`/`request` 等跨文件引用名）不重命名，保证多文件引用不断。
  - CSS：`clean-css` 压缩。
  - HTML：`html-minifier-terser` 折叠空白、去注释、压缩内联 CSS；**内联 JS 不压缩**（重逻辑在外部 js 已压缩）。
  - 资源：`images/`、`favicon.ico` 等原样拷贝。
- **不进 `dist/` 的文件**：`node_modules/`、`target/`（Node 运行时）、根级 `package.json`/`build.js`/`.gitignore`/`pom.xml`/`package-lock.json`/`README.md`/`.npmrc`、`js/test/`（测试）。由 `build.js` 的 `walk()`/`copyAssets()` 排除。
- **忽略项**：`dist/`、`node_modules/`、`target/`、`npm`/`node`（frontend-maven-plugin 产物）、`package-lock.json` 均写入 `frontend/.gitignore`，不入库。
- **平台管理端**：`platform_admin.html`、`logBrowser.html`、`js/platform-admin-*.js`(7)、`js/main.js`、`js/logBrowser.js` 已于 2026-09-09 迁入本前端，由 `build.js` 全量扫描**自动**压缩进 `dist/`，无需额外配置（见 2.7）。

## 3. 维护方法

### 3.1 日常运维

- **健康检查**：
  ```bash
  curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8080/admin.html        # 期望 200
  curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8080/api/v1/sys/config/list  # 期望 401（鉴权门正常）
  ```
- **静态文件改动无需重启 Nginx**：直接覆盖 `frontend/` 下文件即生效（注意浏览器缓存，必要时强刷或加版本查询串）。
- **日志排查**：访问异常先看 `logs/access.log`（状态码）、`logs/error.log`（Nginx/反代错误，如 `connect() failed` 表示后端不可达）。

### 3.2 增加 / 修改页面

1. 在 `frontend/` 下新增 `xxx.html`，资源用**相对路径**引用（如 `css/xxx.css`、`js/xxx.js`、`images/xxx.jpg`）。
2. 复用公共依赖：`js/public/*` 已含请求封装、鉴权、术语等，勿重复造轮子。
3. 跨源跳转一律用 `FRONTEND_ORIGIN` 变量（**平台管理端与业务端现已同源，均走它**），**禁止硬编码 `:8081`/`:8080` 或后端 IP**，否则换环境即失效。`ADMIN_ORIGIN` 为遗留变量，已不再使用。
4. 新页面若需调 API，走 `utility_request.js` 封装（自动补 `/api/v1` 前缀），不要手写完整 URL。

### 3.3 请求层约定（务必遵守）

- 所有 API 调用经 `js/public/utility_request.js` 的 `normalizeUrl(url)`，统一收敛到 `/api/v1`。
- 规则：绝对 http(s) 原样；`/api/v1` 开头原样；`/api/` 开头 → 替换为 `/api/v1`；`/` 开头 → 补 `/api/v1`；其余原样。
- **原因**：axios 对以 `/` 开头的 url 会忽略 `baseURL`，因此只能改 url 字符串、不能靠设 `API_BASE_URL`。改这一处即全站适配，勿在业务 JS 里逐个拼接前缀。

### 3.5 前端与后端静态一致性

- **平台管理端已在本前端**（Phase 3），后端不再有任何静态页面。因此不存在「前后端两份 `js/public/*` 需同步」的问题。
- 前端页面命名区分：`platform_admin.html` + `js/platform-admin-*.js` = **平台管理端**（系统级）；`admin.html` + `js/admin-*.js` = **租户管理端**（租户级）。两者共用 `css/admin.css`。

### 3.6 常见问题排查

| 现象                           | 可能原因                                  | 处理                                                                |
| ---------------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| 页面 404                       | 文件未同步到 `frontend/` 或相对路径写错            | 核对文件存在 + 引用路径；检查 Nginx `root`                                     |
| `/api/v1/*` 返回 502           | 后端未启动 / 被回收 / `proxy_pass` 指错         | 重启后端 `api/run.sh`；核对 `proxy_pass` 地址                              |
| 登录后跳到错误端口                    | `FRONTEND_ORIGIN` 异常，或仍是旧的 `ADMIN_ORIGIN`（`:8081`）写法 | 检查 `js/public/api.js`；**所有角色（含 `platform_admin`）都应落在前端 `:8080`** |
| Nginx 启动报找不到配置               | 未带 `-p`/`-c`，或路径用了 `/c/` 格式           | 用 `C:/` 原生路径 + `-p <前缀> -c <配置>`                                  |
| 报 `could not open error log` | `logs/` 目录不存在                         | 在 nginx 前缀目录下建 `logs/`                                            |
| 改了静态文件不生效                    | 浏览器缓存                                 | 强刷 / 加版本串 `?v=1`                                                  |
| 跨域报错（未来 L2 独立域名时）            | `CorsConfig` 白名单未含新域名                 | 扩 `allowedOriginPattern`（当前仅 localhost/127.0.0.1/152.136.254.127） |

### 3.7 备份与回滚

- `frontend/` 源码（除 `dist/`、`node_modules/`、`target/` 等忽略项）与 `nginx.conf` 均纳入 Git 版本管理；`dist/` 由 `mvn package` 生成，不入库，发布时从本地/CI 构建取得。
- 回滚：`git checkout <版本> -- frontend nginx.conf` → `nginx -s reload`。
- 生产发布建议：先备份当前 `frontend/` 快照，再覆盖；异常即还原并重载。

## 6. 本地前端以远程 API 服务器为目标（开发代理模式）

> 场景：你人在本地改 `frontend/` 源码，后端已经部署在云服务器 `152.136.254.127`（`:8081` + 消息服务 `:8090`），想用本机浏览器连**真实远程数据**联调，而不在本地起后端。
> 配套脚本已随手册放在 `doc-develop/`：`dev-proxy.js`（公共引擎）、`dev-frontend-local.js`（连本地 API）、`dev-frontend-remote.js`（连服务器 API）、`dev-frontend.js`（兼容入口）、`start-frontend-local.cmd`、`start-frontend-remote.cmd`、`start-frontend.sh`、`start-frontend.cmd`。

### 6.1 为什么用「代理」而不是「改 API 地址」

前端请求封装在 `frontend/js/public/utility_request.js`：

- 第 16 行 `const API_BASE_URL = window.API_BASE_URL || '';` —— 默认**空，即相对路径**。
- 第 26~33 行 `normalizeUrl()` —— 所有 `/xxx` 自动补成 `/api/v1/xxx`；绝对 `http(s)` 地址原样返回。
- **第 24 行注释明确**：_“axios 对以 `/` 开头的 url 会忽略 baseURL，故不能靠设 baseURL 解决”_。

即：即便写 `window.API_BASE_URL='http://152.136.254.127:8081'`，实际请求 url 是 `/api/v1/...`（以 `/` 开头），**axios 会忽略 baseURL**，请求仍落在本页同源主机。所以「改 API_BASE_URL 指远程」**无效**。

唯一稳妥做法：**同源 + 反向代理**。

```
浏览器 ──http://localhost:8080/──> 本地 Node 代理(dev-frontend.js)
                                      │  静态文件 → 读 frontend/ 源码
                                      ├─ /api/v1/*                      → http://152.136.254.127:8081  (booking)
                                      └─ /api/v1/{message,sse,users/*}  → http://152.136.254.127:8090  (message-service)
```

浏览器全程只跟 `localhost` 通信（同源），**无 CORS 问题**；远程主机只要对**你的本地公网 IP** 放行 8081/8090 即可。

### 6.2 前置条件

1. 本地装 **Node.js ≥ 16**（脚本仅用内置模块，无需 `npm install`）。
2. 云服务器 `152.136.254.127` 的 `8081`、`8090` **对你的本地公网 IP 放行入站**（云厂商安全组 + 服务器 `ufw`/`iptables`）。否则代理报 `502` / 超时。
   - 自测可达：`curl http://152.136.254.127:8081/api/v1/tenant/name` 应返回 `{"code":200,...}`。
3. 本仓库 `frontend/` 源码在本机（与 `doc-develop/` 同级）。

### 6.5 排错

| 现象 | 原因 | 处理 |
|------|------|------|
| 启动即 `EADDRINUSE` | `DEV_PORT` 被占用 | 换 `DEV_PORT=8080` 或杀占用进程 |
| 页面能开，接口全 `502 Bad Gateway` | 远程 8081/8090 不可达（安全组/防火墙未放行你的 IP） | 见 6.2；`curl http://152.136.254.127:8081/api/v1/tenant/name` 自测 |
| 接口 `401`（被 Security 拦） | 服务器跑的是旧 jar，白名单未放行 `/api/v1/*` | 见云服务器部署手册「登录报密码不对」一节，重部署最新 booking jar |
| 静态资源 404 | `FRONTEND_ROOT` 指错目录 | 确认指向含 `admin.html` 的 `frontend/` 或 `frontend/dist` |
| 改源码不生效 | 浏览器缓存 | 硬刷新 `Ctrl+F5`；本脚本每次实时读文件，无构建缓存 |

### 6.6 脚本要点（dev-frontend.js）

- 零依赖：仅用 Node 内置 `http`/`fs`/`path`，无需 `npm install`。
- 静态伺服：读 `FRONTEND_ROOT` 下文件，含目录穿越防护。
- 反向代理：以 `/api/v1` 为前缀统一转发；`/api/v1/message`、`/api/v1/sse`、`/api/v1/users/` 分流到 `MSG_PORT`（与部署手册 Nginx 分流规则一致）。
- SSE：对 `text/event-stream` 关闭缓冲（`X-Accel-Buffering: no` + `Cache-Control: no-cache`），保证实时推送。
- **仅用于本地开发联调**，不要当生产服务器（无并发/缓存/HTTPS 优化）；生产仍用 Nginx 伺服 `dist`（见第 2、5 章）。

**2026-09-09 重构**：代理引擎已抽到 `dev-proxy.js`（导出 `startProxy(options)`），`dev-frontend-local.js` / `dev-frontend-remote.js` / `dev-frontend.js` 三个入口都只是薄封装（拼参数 + 打印提示）。新增能力：

- 启动前 **TCP 探活**：输出 `booking ✅ 可达 / message-service ❌ 不可达`，并按模式给出对应修复命令（本地模式提示 `java -jar ... --server.port=8090`；远程模式提示防火墙放行 8090）。
- **混合拓扑守卫**：booking 与 message-service 一个指本地、一个指远程时，启动即打印告警（密钥域不同 → 401）。
- 客户端断开（如关闭 SSE 页面）时销毁上游连接；缺 `favicon.ico` 时返回 204 不再刷 404。

### 6.8 登录后为何跳到 8080，以及如何形成闭环（必读）

**现象**：用本脚本登录成功后，页面自动跳到一个带 `:8080` 的地址（如 `http://localhost:8080/admin.html?tCode=xxx`），而不是停留在登录页的端口。

**根因**：前端 `js/public/api.js` 第 2~3 行在页面加载时就按「当前访问 hostname + 固定端口」算好两个跨源地址：

```js
window.ADMIN_ORIGIN    = 'http://' + location.hostname + ':8081'; // 遗留变量（平台管理端已迁前端，实际不再使用）
window.FRONTEND_ORIGIN = 'http://' + location.hostname + ':8080'; // 业务前端（含 admin.html、platform_admin.html）
```

登录成功后 `api.js` 第 202 行据此分发：
- `platform_admin` 角色 → 跳 `FRONTEND_ORIGIN + '/platform_admin.html?tCode=platform'`（**2026-09-09 起**，原为 `ADMIN_ORIGIN` `:8081`）
- 租户 / 教师 / 学员等角色 → 跳 `FRONTEND_ORIGIN`（`:8080`，即本业务前端 `admin.html`）

所以「跳 8080」是前端**写死的默认行为**，不是 bug，也不是密钥/接口问题。

**为什么之前（5173）会"跳空"**：若脚本跑在 `:5173`，登录后却跳 `:8080`，而本机 8080 没有服务（或旧 Nginx 已停）→ 跳转目标打不开。

**闭环做法（本脚本默认即为 8080）**：把本地开发代理**直接监听 8080**，则：
- 你访问 `http://localhost:8080/admin.html` 登录；
- 登录成功后 `FRONTEND_ORIGIN` 仍是 `http://localhost:8080`，跳 `http://localhost:8080/admin.html?tCode=xxx`；
- 仍是**同一个 8080 服务**，且走同源 `/api/v1` 反代远程 `:8081` —— 登录态、Token 全部保留，无缝衔接。

```
访问 http://localhost:8080/admin.html
   │  登录 POST /api/v1/auth/login  → 代理 → 152.136.254.127:8081
   ▼  成功
前端按 FRONTEND_ORIGIN 跳  http://localhost:8080/admin.html?tCode=xxx
   │  还是本 8080 服务（同源 /api/v1 代理远程）→ 闭环 ✅
```

> 若你**必须**用其他端口（如 5173）跑脚本，又想登录后不跳空，有两种办法：
> 1. 浏览器先在 `:5173` 页面按 F12 控制台执行 `window.FRONTEND_ORIGIN='http://localhost:5173'` 再登录（仅当次会话有效，麻烦）；
> 2. 或改 `frontend/js/public/api.js` 第 3 行默认端口为你的 `DEV_PORT`（**记得改完同步 `api/src/main/resources/static/js/public/api.js`，且只建议本地临时改**）。
> 推荐直接用默认 `8080`，零改动。
