# 电子课堂（classroom-service）功能完备性分析报告

> 分析对象：`api/classroom-service`（端口 8092）↔ `api`（booking-api，端口 8081）
> 需求基线：`eClassroom/在线教学微服务需求文档.docx` V1.0（57 项功能，43 项 P0）
> 设计基线：`eClassroom/在线教学微服务架构设计.md`、`doc-develop/classroom-integration/对接方案及页面设计.md`
> 分析方法：源码逐文件通读 + 端点/调用链静态追踪 + 两侧 DTO 字段比对 + 部署配置核对
> 版本：V1.0 | 日期：2026-10-28

## 一、结论摘要

**一句话结论：接口"壳"已基本铺满，业务"里"尚未打通——当前状态是可编译、可启动、单点可用的骨架，不具备端到端可验收能力。**

| 维度 | 现状 | 判定 |
|------|------|------|
| 接口覆盖面 | 设计文档列出的 17 个端点全部落地，另有 7 个补充端点（共 24 个业务端点） | **A（良）** |
| 契约一致性 | 下行推送 URL 错位、上行出勤 DTO 两侧字段集不一致、HMAC 验签方式不可靠 | **E（阻断）** |
| 链路闭环 | 排期下行与出勤上行**两端都断**：13 个关键方法零调用者 | **E（阻断）** |
| 功能实现深度 | P0 43 项中完全实现 5 项（11.6%），含部分实现 18 项（41.9%），桩 2 项，未实现 23 项 | **D（不足）** |
| 多租户隔离 | classroom 库 `tenant_id` 恒写 0，租户维度查询永远为空 | **E（阻断）** |
| 安全 | 排期事件接口免鉴权可伪造；课堂状态/进入无成员校验；WS 三通道无握手鉴权且跨课堂广播 | **E（高危）** |
| 媒体/录制 | RTC 仅前端 mesh 兜底；MediaService、OssClient 全为 stub；录制零调用 | **E（未开工）** |

**关键数字**

- 需求项 57 项：完全实现 **5**｜部分实现 **18**｜桩实现 **2**｜未实现 **32**
- P0 43 项：完全实现 **5（11.6%）**｜实现+部分 **18（41.9%）**｜实现+部分+桩 **20（46.5%）**
- 主代码规模约 **3.5k 行 / 82 个 Java 文件**，24 个业务端点平均每端点约 148 行 —— 骨架密度特征明显
- 零调用者的公共服务方法 **13 个**（含出勤回流、告警、对账上报、录制启停、教学流水、白板快照、媒体房间）

**如果要给一句判断**：这不是"功能缺失"问题，而是"接线未完成"问题。绝大部分能力已有类和表承接，缺的是**触发点、房间隔离、租户透传、真实存储与真实计时**这五件事。按第六节路线修，P0 可在 2 个迭代内达到可验收。

## 四、两侧接口对账与阻断项

### 4.1 下行：booking-api → classroom-service（排期事件）

设计 4 条触发点，代码 4 处已埋：

| 触发点 | 代码位置 | 事件 | 状态 |
|--------|---------|------|------|
| 排期创建 | `CourseScheduleService:207` | `created` | ✅ 已埋 |
| 排期更新 | `CourseScheduleService:247` | `updated` | ✅ 已埋 |
| 排期状态变更 | `CourseScheduleService:278` | `cancelled` | ✅ 已埋 |
| 排期删除 | `CourseScheduleService:637` | `cancelled` | ✅ 已埋 |

埋点质量是好的：`pushAfterCommit` 用事务同步回调，避免"服务先收到事件、库还没提交"；地址从 `sys_tenant_eclassroom` 动态查，未启用课堂的租户静默跳过；连接/读取超时 2s/5s。

**但这条链现在打不通，原因是 URL 拼接错位（B1）。**

```
ClassroomEventPushService:126   String eventUrl = apiBaseUrl + "/schedules/events";
EclassroomService.buildApiUrl   → http://host : 8092 + api_base_path
DDL 默认 api_base_path = /api/v1/classroom
实际请求                        → http://host:8092/api/v1/classroom/schedules/events
classroom-service 真实路由       → /api/v1/schedules/events
                                → 404，best-effort 只 log.warn，业务侧无感
```

叠加一个副作用：`/api/v1/classroom`（单数）与 classroom-service 任何路由都不匹配，所以**前端只要拿到非空 `apiBaseUrl`，课堂页所有接口也一起 404（B5）**——"启用课堂"这个动作反而让功能全挂。

### 4.2 上行：classroom-service → booking-api（出勤/事件/告警/对账）

设计 4 个回调 + 重试 3 次 + 死信，实现情况：

| 回调 | 发送方法 | 是否被调用 | 重试 | 死信 |
|------|---------|-----------|------|------|
| `/classrooms/attendance` | `CallbackService.sendAttendanceCallback` | **0 次调用** | ❌ | ❌ |
| `/classrooms/events` | 无对应方法（`ClassroomEventCallbackReq` 仅 booking 侧存在） | **未实现** | — | — |
| `/classrooms/alerts` | `CallbackService.sendAlert` | **0 次调用** | ❌ | ❌ |
| `/classrooms/reconcile` | `CallbackService.sendReconcileReport` | **0 次调用** | ❌ | ❌ |

`CallbackService:67` 自带注释承认现状：`投递失败（M1阶段降级为日志，后续接入重试+死信队列）`。

即使把调用补上，两侧 DTO 也对不上（B3）：

| 字段 | classroom 侧 `dto/AttendanceCallbackReq` | booking 侧 `dto/AttendanceCallbackReq` |
|------|------------------------------------------|----------------------------------------|
| 排期 | `scheduleId` | `scheduleId` ✅ |
| 课堂标识 | `courseId`、`classroomStatus` | `classroomId` ❌（语义不同：课程 vs 课堂） |
| 起止 | `actualStart`、`actualEnd` | `startTime`、`endTime` ❌ |
| 时长 | 无 | `durationMinutes` ❌ |
| 明细-状态 | `attendanceStatus` | `status` ❌ |
| 明细-签到 | `checkInAt`、`checkOutAt` | `joinTime`、`leaveTime` ❌ |
| 明细-时长 | `effectiveMinutes` | `onlineMinutes` + `effectiveMinutes`（部分） |
| 版本 | `consumptionVersion` | 无 ❌ |

**并且验签方式本身也不成立**：`ClassroomCallbackController:57` 的 `verifySignature` 是"先反序列化成 booking 侧 DTO，再 `objectMapper.writeValueAsString` 重新序列化"后比对 HMAC。签名原文是 classroom 侧序列化的 JSON，两侧字段集不同、字段顺序不同 → 重序列化结果必然不等 → **必然 403**。正确做法是直接对原始请求体字节验签（`@RequestBody String` 或 `ContentCachingRequestWrapper`）。

### 4.3 客户端接口（前端 → 8092）

前端 `ClassroomAPI` 已封装 22 个方法，与后端端点基本一一对应，这条路是通的**前提是 `apiBaseUrl` 为空（走 nginx 同源）**：

```
apiBaseUrl 为空 → url = /classrooms/{sid}/enter → normalizeUrl → /api/v1/classrooms/{sid}/enter
               → nginx location /api/v1/classrooms/ → 127.0.0.1:8092 ✅
```

以下三个"参数风格"不一致会直接 400/415，属于实现期疏漏：

| 前端调用 | 后端接收 | 结果 |
|---------|---------|------|
| `uploadMaterial(formData)`（FormData） | `@RequestBody MaterialUploadReq`（JSON） | 415 / 反序列化失败 |
| `turnPage(...,{page})`（body） | `@RequestParam int page` | 400 缺少参数 |
| `manualAdjust(...,{userId,reason})`（body） | `@RequestParam String userId/reason` | 400 缺少参数 |
| `reviewSubmission(...,{comment,score})`（body） | `@RequestParam comment/score` | 400 缺少参数 |

### 4.4 部署路由（一个必须在上线前解决的冲突）

`deploy/nginx/booking.conf:61`：

```nginx
location /api/v1/classrooms/ { proxy_pass http://127.0.0.1:8092; }
```

而 booking-api 的回调接收端也在同一前缀下（`ClassroomCallbackController` 映射 `/api/v1/classrooms`，SecurityConfig / JwtAuthenticationFilter / WebMvcConfig 三处白名单均为 `/api/v1/classrooms/attendance|events|alerts|reconcile`）。

后果：**经 nginx 访问 `/api/v1/classrooms/attendance` 会被打到 8092 并 404**。目前回调默认直连 `http://localhost:8081` 所以本地能过；一旦把 `BOOKING_API_URL` 指向公网域名（生产常态），上行回流全部 404。

另：设计 3.1 节要求新增 `/api/v1/schedules/events`、`/api/v1/schedules/sync` 两条 location，实际**两条都没加**（服务间直连可绕过，但与文档不符，且一旦想走同源调试就不可用）。

### 4.5 WebSocket（3 条通道，协议与实现脱节）

| 项 | 设计 | 实现 |
|----|------|------|
| 端点 | `/ws/classrooms/{sid}/{whiteboard,heartbeat,signal}` | ✅ 三条都注册 |
| 握手鉴权 | JWT（`?access_token=`） | ❌ `WebSocketConfig` 无 `HandshakeInterceptor`，参数被完全忽略 |
| 房间隔离 | 按 scheduleId 广播 | ❌ `WhiteboardHandler:30`、`ClassroomSignalHandler:30` 对**全局 `sessions.values()`** 转发 |
| 在线状态 | 心跳 15s / IDLE 15-60s / OFFLINE>60s | ❌ 仅写 Redis TTL 30s，无过期扫描、无 IDLE、不回写 `membership.online_state`、不广播 |
| scheduleId 解析 | 路径第 3 段 | ❌ `HeartbeatHandler:52` 取 `parts[4]` → 恒定取到字符串 `"heartbeat"` |

跨课堂串台 + 无鉴权，是把课堂模块放到公网前必须先堵的洞。

## 六、六大系统性缺口（根因归纳）

57 项问题看似分散，实际收敛到 6 个根因。修这 6 件事，绝大多数条目会连带转正。

### 6.1 闭环未接线：13 个方法零调用者

| 方法 | 所在类 | 应有触发点 |
|------|--------|-----------|
| `sendAttendanceCallback` | CallbackService | `endClass` 成功后 1 分钟内 |
| `sendAlert` | CallbackService | 教师未到/中断/大面积掉线判定 |
| `sendReconcileReport` | CallbackService | `dailyReconcile` 结束后 |
| `startRecording` / `stopRecording` | RecordingService | `startClass` / `endClass` |
| `appendEvent` | TeachingSessionService | 白板/点名/提交/进出课堂各动作后 |
| `saveWhiteboardSnapshot` | TeachingSessionService | `endClass` 时 |
| `createRoom` / `generateJoinToken` / `destroyRoom` | MediaService | enter/start/end |
| `handleDiff` | ReconcileDiffHandler | 对账比对差异后 |
| `timeout` | RollCallService | 点名 30s 未应答 |
| `isOnline` | OnlineStateManager | 出勤/掉线判定 |

**这是本报告最重要的一条**：能力已经写好，只是没人调用。补触发点的成本远低于重写，但没有触发点，一切等于零。

### 6.2 多租户断裂：`tenant_id` 恒为 0

`ScheduleEventConsumer:87` 写死 `c.setTenantId(0L)`，而 `ScheduleEventReq` 根本没有 `tenantId` 字段；booking 侧 `buildEventPayload` 也没放租户。

后果链：
1. classroom 库所有课堂 `tenant_id=0` → `AdminConsoleController.monitor` 对租户管理员按 `tenant_id = 当前租户` 过滤 → **恒空列表**；
2. classroom-service 无租户拦截器，任意租户用户用自己 token 可读写他人课堂（`getStatus`/`enter`/`leave`/`recordings` 全无归属校验）；
3. 租户课堂开关守卫（`AuthInterceptor` + `TenantEclassroomService`，含 5 分钟内存缓存）**设计是对的，但它只挡"该租户有没有开通课堂"，不挡"这堂课是不是这个租户的"**。

修法：payload 增 `tenantId`（服务间可信，由 booking 从 token 派生并签名）→ 落库 → 所有按 `scheduleId` 的读写前置"课堂归属校验"。**绝不能让客户端传 tenantId**（同主系统"target 服务端派生"的既定口径）。

### 6.3 鉴权三处缺口

| 缺口 | 位置 | 风险 |
|------|------|------|
| 排期事件接口免鉴权 | `WebMvcConfig` excludePathPatterns 含 `/api/v1/schedules/events` | 任何人可 POST 伪造 `created/updated/cancelled`，创建/篡改/取消任意课堂；booking 侧虽带 Bearer，但服务端不校验 |
| 课堂状态/进入无成员校验 | `ClassroomController:31,37` | 任意登录用户可查任意课堂信息；`enter` 还会给非名单用户**新增 membership 行**并签到 |
| WS 无握手鉴权 + 全局广播 | `WebSocketConfig`、`WhiteboardHandler:30`、`ClassroomSignalHandler:30` | 匿名可订阅所有课堂的笔迹/信令/聊天；跨课堂数据串台 |

正确姿势：`/schedules/events` 走 **HMAC + 时间戳（±5 分钟）**（需求 4.4 第 3 条、9.4 第 3 条均如此要求），与上行回调同一套 `HmacSigner`；课堂接口统一前置 `assertMember(scheduleId, userId)`；WS 加 `HandshakeInterceptor` 解析 `access_token`，并用 `Map<scheduleId, Set<WebSocketSession>>` 做房间隔离。

### 6.4 有效时长算法不合格（账务风险）

`AttendanceService.checkOut` 现行逻辑：

```java
int minutes = (int) Duration.between(a.getCheckInAt(), a.getCheckOutAt()).toMinutes();
a.setEffectiveMinutes(Math.max(minutes, a.getEffectiveMinutes()));
```

三个问题：
1. **离线时长被计入**：首次签到 10:00、掉线 10:20、11:00 回来再退 → 有效时长 60 分钟，实际在线 20 分钟；
2. **未扣 60 秒抖动**：需求 6.3 / F2-03 明确要求扣除 60 秒内抖动重连；
3. **未封顶课时**：需求 9.3 节 `Math.min(sum, duration)` 未实现。

这是直接产出"课时消耗"的算法，一旦回流到账务就会产生纠纷（风险清单 R08 已标为高）。必须改为**在线区间累加**：`membership` 每次 `join/leave` 记一段区间，`sum(各段) - 60s 内抖动段`，再 `Math.min(..., duration)`。

### 6.5 文件与媒体全是桩

| 组件 | 现状 | 影响 |
|------|------|------|
| `OssClient` | `upload/download/delete` 只打日志，`generateSignedUrl` 拼假 URL | 讲稿、作品、录制文件都无处可存、无 URL 可取 |
| `MediaService` | 三个方法返回固定串且零调用 | F4-01 实质由前端 mesh 承担，无 TURN、无 SFU、无服务端管控 |
| 录制 | 无任何对接 | F6 五项全空 |

结论：**F4-04/05/06、F5-01、F6-01~05 不能算"待完善"，应算"未开工"**。这块是独立工作量（对象存储接入 + RTC/SFU 选型 + 录制合流），不适合藏在"功能完善"里做。

### 6.6 定时驱动缺失（5 条需求因它悬空）

`@EnableScheduling` 已开，但只挂了 2 个空任务。缺失的扫描器：

| 应有任务 | 对应需求 | 频率 |
|---------|---------|------|
| 就绪流转（`SCHEDULED→READY`，startTime-10min） | F1-02 | 1 min |
| 自动开课（`→LIVE`，startTime+60s 内） | F1-04 | 30 s |
| 自动下课（`→CLOSED`，endTime） | F3-06 | 1 min |
| 掉线扫描（Redis key 过期 → IDLE/OFFLINE + 广播） | F3-02/04 | 15 s |
| 点名超时（30 s → TIMEOUT） | F4-13 | 10 s |
| 教师掉线 5min 自动结课 + 告警 | F3-07 | 1 min |
| 录制/作品到期清理 | F6-05 / F5-04 | 每日 |

这 7 个任务都不复杂（单表条件更新 + Redis 扫描），但它们是"课堂自己会走"的前提。当前课堂状态只能靠人点按钮推进。

## 八、阶段判定与修复路线

### 8.1 当前处于什么阶段

对照需求 12.1 里程碑：

| 里程碑 | 目标 | 实际 |
|--------|------|------|
| M1 契约与框架（1-4 周） | 骨架、幂等、Mock 联调通过、DDL | **约 85%**：骨架/DDL/幂等设施齐备；"联调通过"未达成（B1/B3 两条断路） |
| M2 教学核心（5-12 周） | F1-F4 全量，含媒体与信令 | **约 25%**：签到/退出/移出可用；媒体为 stub，白板/点名/讲稿只有壳 |
| M3 稳定与上线（13-18 周） | F5-F8、回流对账、压测 | **约 8%**：作品写入可用，其余全空 |

**整体判定：M1 尾部 / M2 早期。** 若按原计划"F1-F4 全量上线"作为 M2 出口，当前距离出口还有约 60% 的功能量与全部媒体工作。

### 8.2 建议修复顺序（按"阻断度 × 成本"排序）

**P0-A 打通链路（最高优先，估计 3-5 人日）**

1. 统一 base_path：`sys_eclassroom_instance.api_base_path` 默认值改为 `/api/v1`（或 push 时不再拼 base_path，直接 `host:port + /api/v1/schedules/events`）；同步修 `EclassroomService.buildApiUrl/buildWsUrl` 与 `ClassroomAPI` 的拼接契约 —— **一条改动同时解决 B1 与 B5**。
2. 两侧出勤 DTO 归一：建议以需求 8.3 节字段为准（`attendanceStatus/checkInAt/checkOutAt/effectiveMinutes/consumptionVersion`），改 booking 侧 DTO 而非 classroom 侧。
3. 验签改为原文验签：booking 侧改 `@RequestBody String body` + `hmacVerifier.verify(body, signature)`，杜绝重序列化。
4. 补 `BookingAttendanceService.updateAttendance`，落库课次出勤与课时消耗（替换 `ClassroomCallbackController:52` 的 TODO）。
5. nginx 冲突消解：回调路径改为 `/api/v1/classroom-callback/*`（或让 classroom-service 回调走内网直连端口并禁止公网暴露该前缀），避免与前端 `/api/v1/classrooms/` 撞车。

**P0-B 安全（3 人日，必须与 P0-A 同批）**

6. `/schedules/events` 接 HMAC + 时间戳校验（复用 `HmacSigner`）。
7. 课堂接口统一前置 `assertMember`：`status/enter/leave/start/end/kick/attendance/materials/rollcall/submissions/recordings` 全覆盖；`enter` 校验"在名单内"再允许插 membership。
8. WS 握手鉴权 + 按 `scheduleId` 分房间；修 `HeartbeatHandler:52` 的 `parts[4]`→`parts[3]`。

**P0-C 账务正确性（2-3 人日）**

9. 有效时长改在线区间累加 + 扣 60s 抖动 + 封顶 duration。
10. 课堂创建时按名单初始化 ABSENT 行（否则缺席永远不存在）。
11. `endClass` 补齐收尾五件事：停录制 → 存白板快照 → 生成出勤名单 → 写 `session_record.actual_minutes` → 触发 `sendAttendanceCallback`。

**P0-D 定时驱动（3 人日）**

12. 上 7 个扫描任务（见 6.6），全部用条件更新（`UPDATE ... WHERE status=? AND start_time<=?`）保证多副本安全。

**P1 教学环节闭环（1-2 周）**

13. 讲稿：multipart 上传 + OSS 真实接入 + 翻页 WS 广播 + 学生端跟随。
14. 点名：随机选人、WS 下发、30s 超时、强提示 UI。
15. 作品：multipart/直传双通道 + 学生端"我的提交" + 参数风格统一（改后端为 `@RequestBody`）。

**P2 媒体与录制（独立项目量级，需先做技术选型）**

16. TURN 部署（mesh 兜底可用性）+ 或接入第三方 RTC；`MediaService` 由 stub 转真实实现。
17. 录制合流 + 生命周期（READY/过期清理）+ 回放页（权限、拖动、倍速）。

### 8.3 验收判据（建议写进 M2 出口条件）

| 判据 | 通过标准 |
|------|---------|
| 链路 | 创建排期 → classroom 表出现记录（`tenant_id` 正确）；下课 → booking 侧 `appointment` 出勤与课时被更新，`consumptionVersion` 落库；连续投递 3 次仅生效 1 次 |
| 鉴权 | 无 token 调 `/schedules/events` 返回 401/403；非名单用户 `enter` 返回 40301；A 租户 token 查 B 租户课堂返回 403 |
| WS | 两课堂并发时，A 课堂笔迹不出现在 B 课堂；未带 token 握手被拒 |
| 时长 | 用例：10:00 进 / 10:20 掉线 / 11:00 回 / 11:30 退，课时 60 → 有效时长应 ≈ 50 分钟（20+30），非 90 |

## 十、勘误（2026-10-28 运行时联调发现）

第一期修复（P0-A 链路 + P0-B 安全）在真实起服务联调时，暴露了 5 个静态分析**没能看出**的问题。此处更正本报告结论，并记录到 `修复记录-第一期-20261028.md`。

| # | 更正内容 | 说明 |
|---|---------|------|
| E1 | 3.1 节「共享 JWT 密钥域 ✅」→ **❌** | 两服务 `jwt.secret` 相差 1 个字符（882 vs 883 字节）。**主系统签发的任何 token 在课堂服务都 401**，课堂功能整体不可用。`aes-key`/`hmac-key` 两把本来一致。已修。 |
| E2 | 6.3 节鉴权缺口「三处」→ **四处** | 补：`Result.fail` 白名单只含 HTTP 码，而下发的是 5 位业务码，导致**所有业务异常被吞成 500**（日志 `Failure in @ExceptionHandler`）。已修。 |
| E3 | P1 结论「version 恒 1」→ 实际影响更大 | 不止「乱序检测失效」：`duration` 根本没发（对端回落 60 分钟），`startTime` 发的是空格格式而对方只认 ISO → **推送 400，事件从未真正进城**。已修。 |
