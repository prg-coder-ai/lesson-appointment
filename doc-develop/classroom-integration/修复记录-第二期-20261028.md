## 一、这轮到底改了什么

第一期的结论是「接口壳铺满、业务里子没通」。P0-C 补的是**里子里最贵的一段**：
把「课堂结束后产出课时消耗」这条链真正接上，并且让算出来的数字可信。

| # | 改动 | 修复前的实际行为 |
|---|---|---|
| C1 | 有效时长改**在线区间累加**（新表 `classroom_presence_segment`） | 只算「首次签到→最后一次签退」单段差并取 max：离线时长全被算进去 |
| C2 | 抖动重连豁免（间隙 ≤60s 视为连续在线） | 切一次网就断成两段，时长按两段合并后的跨度算（错），或不合并（更错） |
| C3 | 有效时长**封顶课时时长** | 学生挂着不走的页面能把课时刷超 |
| C4 | 课堂创建时**初始化出勤名单**（全员 ABSENT） | 名单为空 → 「缺席」与「不在名单里」无法区分，一次都没进课堂的学生统计不到 |
| C5 | 下课收尾五件事（闭合区间/重算时长/归一名单/置离线/回流） | `endClass` 只改状态 + 记 actualEnd，**出勤不生成、回调不发出** |
| C6 | `consumption_version` 每次收尾 +1 并随回调下发 | 无版本号，重放会把已结算明细覆盖回旧值 |
| C7 | 排期事件**透传 tenantId**（此前消费端写死 `0L`） | 租户管理员按租户查监控列表**恒空**；A 租户 token 能读 B 租户课堂 |

C5 是这一轮的核心：`sendAttendanceCallback` 从「零调用者」变成「下课必经之路」。

## 二、有效时长算法（需求 F2-03）

### 2.1 规则落地

需求原文：
> 有效时长累计：扣除 60 秒内抖动重连，封顶课时时长
> 多次进出累计有效时长（去掉 60 秒内的抖动重连）；有效时长是课时消耗核算的唯一依据。

实现（`AttendanceService#computeEffectiveMinutes`）：

1. 取该生在本课堂的**全部在线区间**，按 `join_at` 升序；
2. 顺序合并：下一段进入时间 ≤ 上一合并段结束时间 + `classroom.jitter-grace-seconds`（默认 60s）
   → 判为同一次在线（重叠或抖动重连），**间隙计入**；否则间隙**不计**；
3. 合并段秒数求和 → 换算分钟（向下取整）；
4. `Math.min(总分钟, classroom.duration)` 封顶；`duration` 缺失时回落「起止时间差」。

未闭合区间（`leave_at IS NULL`）以传入的参考时刻（下课时间 / 当前时刻）作为结束时间，
所以中途查询也能得到「截至此刻」的时长。

### 2.2 为什么必须新建一张段表

`classroom_membership` 是 `(schedule_id, user_id)` 单行，只存最后一次 join/leave。
「10:00 进、10:20 掉、11:00 回、11:30 退」在它眼里只有两个时间点，
无论怎么算都算不出「两段各 20 / 30 分钟」。区间必须多行存储。

### 2.3 实测结果（全部为真实落库 + 真实接口跑出来的）

| 场景 | 区间 | 课时 | 期望 | 实际 |
|---|---|---|---|---|
| 断续（报告判据） | 10:00–10:20、11:00–11:30 | 60 | 50（旧算法给 90） | **50** ✅ |
| 抖动重连 | 10:00–10:20、10:20:30–10:50 | 60 | 50（间隙 30s 计入） | **50** ✅ |
| 封顶 | 10:00–11:00（在线 60） | 30 | 30 | **30** ✅ |
| 未闭合段 | join = 现在−10min，无 leave | 60 | ≈10 | **10** ✅ |

## 三、下课收尾五件事

`ClassroomClosingService#closeAfterEnd`，由 `ClassroomService.endClass` 触发
（教师手动下课与后续的自动下课走同一入口，避免两条口径）：

1. **闭合区间**：所有 `leave_at IS NULL` 的段按 actualEnd 闭合（否则最后一段会被算到以后）；
2. **重算时长**：逐人 `computeEffectiveMinutes`；
3. **归一名单**：`LEFT`/`REJOINED` 等过程态归一为 `ABSENT`（从未签到）/ `PRESENT` / `LATE`；
4. **置离线**：`classroom_membership` 全部 OFFLINE（不置会让监控台显示「X 人在线」）；
5. **回流**：`consumption_version + 1`，组装明细异步 POST 到
   `booking-api /api/v1/classroom-callback/attendance`（1/5/15 分钟退避重试）。

**事务边界**：1–4 在 `TransactionTemplate` 显式事务内；回调在**提交后**才发。
失败只记 ERROR 不回滚——状态已 CLOSED、人已经走了，回滚反而制造「课上完了但课堂还在直播」。
重放靠人工补跑同一入口（幂等：区间已闭合、名单按结论覆盖、版本号会再 +1 从而覆盖旧报文）。

## 四、联调中发现并修复的三个运行时缺陷

这三个都是静态分析看不出来、只有跑起来才暴露的。

### B1 `updateById` 从未存在（最严重）

```
org.apache.ibatis.binding.BindingException:
  Invalid bound statement (not found): com.classroom.mapper.AttendanceMapper.updateById
```

`classroom_attendance` 与 `classroom_membership` 都是 `(schedule_id,user_id)` 复合主键，
实体上没有 `@TableId`，**MyBatis-Plus 因此不生成 `updateById`**。

隐蔽性在于：`insert` 不需要主键、完全正常，只有更新路径会炸；而更新路径恰恰是出勤结论、
有效时长、成员在线状态唯一的落库方式。表现出来的是「`/end` 返回 200、课堂状态已变 CLOSED、
但出勤一条没更新」——**半失败**，比彻底失败更难发现。

修复：两个 Mapper 各加一个显式 `updateByKey`（`@Update` 全字段）。
顺带解决了「`join` 重入要把 `leave_time` 清回 NULL，但 MP 默认更新策略忽略 null」的问题。

> 其余 10 个实体都有 `@TableId`，逐一核对过，不受影响。

### B2 预置缺席名单把所有人打成缺席（自查发现）

C4 引入 `initRoster` 后，学生进入课堂时 `getOne` 返回已存在的 ABSENT 行，
而 `checkIn` 只有 `null`（首次）与 `LEFT`（重连）两个分支——**ABSENT 不命中任何一个**，
状态永远停在缺席。等于用一个「补齐统计」的改动制造了「全员缺勤」的新 bug。

修复：增加 ABSENT → PRESENT/LATE 的升级分支（写 checkInAt、清 checkOutAt）。

### B3 「课堂未启用」403 有 5 分钟缓存

`TenantEclassroomService` 对租户课堂开关做内存缓存（TTL 5min）。
联调时先跑了一次未灌绑定的用例，false 被缓存住，之后即使补上
`sys_tenant_eclassroom` 仍持续 403，直到重启服务。

不是 bug（开关变更本就低频），但**上线运维必须知道**：给租户开通课堂后，
最坏要等 5 分钟或重启 classroom-service 才生效。

另：本机 Redis 未启动，`EventIdempotentGuard` 与在线状态走降级路径（幂等降级为「按已有记录跳过」），
不影响出勤与时长核算，但生产必须起 Redis，否则幂等与在线状态不可靠。
