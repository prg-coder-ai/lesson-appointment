## 零、v2 相对 v1 的两处根本改动

| # | v1 的写法 | v2 按你的决策改为 |
|---|---|---|
| 1 | 按有效时长分档扣（≥80% 扣 1、早退扣 0.5…），状态与钱绑在一起 | **扣费只判「有没有请假」**：只要不是 `cancelling` 族，一律扣 1 课时、减 1 余量；**与上了多久无关**。`checked-in` / `completed` / `absent` 纯粹是**出席现状记录**，不参与计费 |
| 2 | 课堂标识沿用排期级，课次级列为待拍板 | **课堂标识升级为课次级**（`schedule_id + class_index`），因为一个排期会展开 N 个课次，扣减必须落到具体那一课次 |

这两条一改，整个模型的骨架就变了：**计费与出席解耦**。
出勤数据只回答「学生来没来」，扣费只回答「学生请没请假」。

## 一、三个必须先讲清的现状事实

### 1.1 没有「余量」可减 —— 这一步今天无处落地

- `StudentBalanceService` 是接口 + `StudentBalanceServiceStub`，**只打 warn 日志，不落库**；
- 库中 `SHOW TABLES LIKE '%balance%'` 返回**空**：`student_balance` / `student_balance_flow` 都不存在；
- `booking` 表没有课时数字段，`course` 表只有 `class_duration`（单课时长），没有「购买了多少课时」。

**结论**：你要求的「减余量」必须先有账本。本方案在第四节给出 `student_lesson_balance` +
`student_lesson_flow` 两张表的完整 DDL，这是本轮**必须一起做**的前置（否则「减余量」只能写在日志里，正如今天的 Stub）。

### 1.2 课堂是排期级，扣减要课次级（v2 已定为升级）

| 对象 | 粒度 | 证据 |
|---|---|---|
| `classroom` | 一个排期一个课堂（主键 `schedule_id`） | `classroom` 表 DDL |
| `appointment` | 一个排期按重复规则展开 **N 个课次** | `CourseScheduleService:599` `setClassIndex(index++)`，`class_index = 1..N` |
| `lesson_attendance` | 唯一键 `(schedule_id, user_id)` | 第一期 DDL |

一个每周重复排期 → 10 个课次、只有 1 个课堂、1 条出勤。第 3 次与第 8 次无法区分，扣减必然重复或漏扣。

现状：`course_schedule` 中 `repeat_type=0` 100 条、`repeat_type=2` 2 条；现存 `booking` 都是 1 个课次。
**现在还没炸，但代码路径支持 N，一有重复排期就炸。**

### 1.3 没有任何代码会把课次置为 `completed`

`grep "\"completed\""` 只命中 `AppointmentStatus` 常量定义与两处统计 SQL。
库里 5 条 `appointment` **全部是 `active`** —— 课后状态流转这件事，目前完全是空的。
且现有 14 个状态中**没有 `absent`**。

## 二、状态机（纯出席记录，不涉费用）

### 2.1 新增两个状态

| 状态 | 含义 | 写入时机 | 终态 |
|---|---|---|---|
| **`checked-in`** | 学生已进入课堂（**仅表示出席，不产生任何费用动作**） | 学生 `enter` 成功 | 否 |
| **`absent`** | 缺席：课次结束仍未进入过课堂 | 课次收尾 | 是 |

> `checked-in` 的定位按你的要求确定：**只是学生状态**。它不触发扣减、不触发退费、不写任何金额字段。
> 唯一作用是让老师/学生在预约列表上立刻看到「已签到」。

### 2.2 迁移表

| # | 当前状态 | 触发 | 新状态 | 说明 |
|---|---|---|---|---|
| T1 | `active` / `noted1` / `noted2` | 学生首次进入课堂 | `checked-in` | 只写状态，不产生费用 |
| T2 | `checked-in` | 课次收尾 | `completed` | 进过即出席 |
| T3 | `active` / `noted1` / `noted2` | 课次收尾（从未进入） | `absent` | 缺席 |
| T4 | `checked-in` | 学生中途全离场（有效时长为 0 且已离场） | 保持 `checked-in`，收尾时才定终态 | 不在过程中来回改 |
| — | `completed` / `absent` / `cancelled` / `t-cancelled` / `changed` / `frozen` | 任何自动事件 | **不变** | 终态保护；只有管理员改判能改，且留审计 |

### 2.3 `completed` / `absent` 的判定

**主判据：`lesson_attendance.check_in_at` 是否非空。**

- 非空（进过课堂）→ `completed`
- 为空（从未进入）→ `absent`

可选阈值 `classroom.attendance.completed-ratio`（默认 **0**，即「进过就算出席」）：
若你希望「进 2 分钟就走」也算缺席，把它调成 0.5 即可，规则引擎不需要改代码。

> 注意：该阈值**只决定状态**，不影响扣费。扣费只看请假与否（见第三节）。
> 这与 v1 完全不同 —— v1 把阈值同时用于计费，已被你的决策推翻。

## 三、扣减规则（v2 核心，二元判定）

### 3.1 唯一判据：有没有请假

| 课次状态 | 是否请假 | 计扣课时 | 是否减余量 |
|---|---|---|---|
| `cancelling` / `canceling` / `s-cancelling`（申请中） | 是（**已提交申请即算**） | **0** | 否 |
| `cancelled` / `canceled` | 是（已获准） | **0** | 否（退费按 `refund_snapshot` 档位单独处理） |
| `t-cancelling` / `t-cancelled`（**教师**发起） | 否（非学生责任） | **0** | 否 |
| `changed`（已改期） | — | **0**（本次不算，改到新时间再算） | 否 |
| `frozen`（删除预订） | — | **0** | 否 |
| `active` / `noted1` / `noted2` / `checked-in` / `completed` / `absent` | **否** | **1.0** | **是** |

一句话概括：**除「请假 / 教师取消 / 改期 / 冻结」外，每课次必扣 1 课时。**

典型后果（均为设计意图，非 bug）：

- 学生全程没来、也没请假 → `absent` + **扣 1**
- 学生来了 3 分钟就走 → `completed` + **扣 1**（费用与时长无关）
- 学生上满 60 分钟 → `completed` + **扣 1**
- 学生提前 1 天请假获准 → `cancelled` + **扣 0**
- 老师临时取消 → `t-cancelled` + **扣 0**

### 3.2 与退费链路的分工（不重叠）

```
课次 active
   ├── 请假获准 ──▶ cancelled ──▶ refund_snapshot 档位退费（金额/课时按档位比例退回）
   └── 未请假 ──▶ 课次结束 ──▶ 扣 1 课时（全额）
```

两者**互斥**：走了请假的课次不再扣；已扣的课次不允许再走请假退费。
硬校验写在 `AppointmentStateAdvancer` 里（见 6.2）。

### 3.3 参数（全部可配）

```
# 出席判定线（只影响状态，不影响扣费）。默认 0 = 进过即出席
classroom.attendance.completed-ratio=0
# 每课次计扣课时数
lesson.deduction.per-class=1.0
# 余额不足是否允许扣成负数（历史学生没有课时包，只能欠着，运营后补）
lesson.balance.allow-negative=true
```

### 4.2 余量账本（**本轮必须新建**，否则「减余量」无落点）

```sql
-- 学生课时余额
CREATE TABLE `student_lesson_balance` (
  `id`                bigint       NOT NULL AUTO_INCREMENT,
  `tenant_id`         bigint       NOT NULL DEFAULT 0,
  `student_id`        varchar(36)  NOT NULL,
  `total_lessons`     decimal(8,2) NOT NULL DEFAULT 0 COMMENT '累计购买课时',
  `used_lessons`      decimal(8,2) NOT NULL DEFAULT 0 COMMENT '累计消耗课时',
  `remaining_lessons` decimal(8,2) NOT NULL DEFAULT 0 COMMENT '剩余课时（=total-used，允许负数=欠课）',
  `version`           int          NOT NULL DEFAULT 0 COMMENT '乐观锁',
  `create_time`       datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`       datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_slb_tenant_student` (`tenant_id`, `student_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='学生课时余额';

-- 课时流水（幂等核心）
CREATE TABLE `student_lesson_flow` (
  `id`              bigint       NOT NULL AUTO_INCREMENT,
  `tenant_id`       bigint       NOT NULL DEFAULT 0,
  `flow_id`         varchar(36)  NOT NULL COMMENT '流水号UUID',
  `student_id`      varchar(36)  NOT NULL,
  `booking_id`      varchar(36)  NULL,
  `schedule_id`     varchar(36)  NULL,
  `class_index`     int          NULL,
  `appointment_id`  int          NULL,
  `change_lessons`  decimal(4,2) NOT NULL COMMENT '负数=消耗，正数=退回/充值',
  `remaining_after` decimal(8,2) NOT NULL COMMENT '变动后余量（对账用）',
  `source`          varchar(20)  NOT NULL COMMENT 'classroom课堂扣减/leave请假退回/manual人工/grant充值',
  `biz_key`         varchar(128) NOT NULL COMMENT '幂等业务键，见下',
  `reason`          varchar(255) NULL,
  `operator_id`     varchar(36)  NULL,
  `create_time`     datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_slf_flow` (`flow_id`),
  UNIQUE KEY `uk_slf_biz` (`tenant_id`, `biz_key`),
  KEY `idx_slf_student` (`tenant_id`, `student_id`, `create_time`),
  KEY `idx_slf_appt` (`appointment_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='课时流水';
```

**`biz_key` 的取值**（这是绝不重复扣的唯一保障）：

```
classroom:{appointmentId}          ← 课堂结算，一课次一条
leave:{appointmentId}              ← 请假退回，一课次一条
manual:{uuid}                      ← 人工调整，每次一个
```

`uk_slf_biz` 唯一键让「重复回调 / 重试 / 兜底任务再跑一次」都变成 `DuplicateKeyException`，
捕获后直接返回成功 —— **同一课次永远只扣一次**，不依赖任何分布式锁。

### 4.3 为什么业务事实与账务动作要分两层

`lesson_attendance` 记「这堂课发生了什么」，`student_lesson_flow` 记「账上动了多少」。
分开的好处：

- 规则变更（比如以后改成按分钟计费）只需重算 `consumed_lessons`，账本按 `source='classroom'` 的行全量回滚重放；
- 对账时 `SUM(flow.change_lessons)` 与 `balance.used_lessons` 必须相等，不等即有问题；
- 余额表晚建、重建、迁移都不影响已沉淀的上课事实。

## 五、触发时机

计费与出席解耦后，扣减**不再依赖课堂**，因此有两条触发路径，二者幂等共存：

| 路径 | 触发 | 适用 |
|---|---|---|
| **主路径** | 课堂收尾回调 `closeAfterEnd` → booking 侧结算 | 已开通课堂的租户 |
| **兜底路径** | 定时任务：课次结束 + N 小时仍非终态 → 直接结算 | 未开通课堂 / 回调丢失 |

兜底路径的意义（v2 比 v1 更重要）：既然「没请假就扣」，那扣减**不应该因为课堂没接通而漏掉**。
未开通课堂的租户也必须按时结算，否则课时永远欠着、账永远是糊涂的。

```
兜底任务（每 10 分钟）：
  SELECT * FROM appointment
   WHERE status IN ('active','noted1','noted2','checked-in')
     AND appointment_datetime + INTERVAL 24 HOUR < NOW();
  -- 逐个：无课堂记录 → 若从未进入则 absent，否则 completed；然后结算扣 1
```

N 小时默认 24（给迟到补录与人工改判留窗口），可配 `lesson.settle.grace-hours`。

## 八、边界场景

| # | 场景 | 期望 |
|---|---|---|
| 1 | 学生全程未进、未请假 | `absent`；扣 1；`consumption_state='settled'` |
| 2 | 学生进 3 分钟就走 | `completed`（默认阈值 0）；扣 1；明细里 `attendance_status=LEFT`、`effective_minutes=3` |
| 3 | 学生请假获准 | `cancelled`；扣 0；`consumption_state='waived'`；走 `refund_snapshot` 退费 |
| 4 | 学生提交请假但未审核（`cancelling`） | 扣 0（按你的口径「申请即算」）；审核驳回后需**补扣 1**（见下） |
| 5 | 老师取消（`t-cancelled`） | 扣 0 |
| 6 | 改期（`changed`） | 本次扣 0；新时间的新课次正常扣 |
| 7 | 同一课次重复回调 | `uk_slf_biz` 拦截，第二次返回幂等成功，余额不变 |
| 8 | 课堂取消（教室没开成） | `appointment.status` **不变**；是否扣费按「学生是否请假」判，不按课堂状态判 |
| 9 | 余额不足（历史学生 total=0） | 允许扣成负数（`allow-negative=true`），前端提示欠课；运营补录 `grant` |
| 10 | 回调与兜底任务同时结算同一课次 | `biz_key` 幂等，先到先得，后到直接成功返回 |

**场景 4 的补充**：按「申假即不扣」的宽松口径，存在「先申请→不扣→事后被驳回」的漏洞。
处理：审核驳回（`cancelling → active`）时触发**补扣**，`biz_key='classroom:{appointmentId}'` 若尚未存在则补记。
这条要写进 `RefundRuleService` 的审核分支。

## 九、验收判据

1. **状态三态**：`active` 课次 → 学生 enter → `checked-in`（余额不变）→ 课堂收尾 → `completed`（扣 1）。
2. **缺席**：全程未进 → `absent`，扣 1，`flow.change_lessons=-1`。
3. **请假**：`cancelling` → 扣 0；审核驳回后补扣 1（验证场景 4）。
4. **时长无关**：同一课次分别造「进 3 分钟」与「进 60 分钟」，两者 `consumed_lessons` 都必须为 1。
5. **幂等**：同一课次回调重放 3 次 + 兜底任务再跑 1 次 → `student_lesson_flow` 只有 1 行，余额只减 1。
6. **课次级**：一个 `repeat_type=2` 排期生成 3 个课次，分别上课 → 3 条 `lesson_attendance`、3 条 flow、余额减 3。
7. **对账**：`SUM(flow.change_lessons)` 与 `balance.used_lessons` 全租户相等。
8. **兜底**：造一条 25 小时前、无课堂记录的 `active` 课次 → 任务跑完变 `absent` 且已扣 1。

### 🔴 2. 历史学生没有课时包，首次扣减会扣成负数，接受吗？

现有 `booking` 5 条、`appointment` 5 条全是 `active`，没有任何课时包记录。
扣减一旦上线，这些学生第一次被扣就是 `0 - 1 = -1`。

- **选项 A（推荐）**：允许负值，前端显示「欠 1 课时」，运营后台补录 `total_lessons` 平账；
- **选项 B**：首次扣减时若 `total_lessons=0`，跳过扣减只记 `pending`，等运营补录后再补扣。

## 十一、实施顺序

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **S1** | 状态枚举 + 影响面 7 处同步（把「加状态」做安全） | 无 |

| **S4** | 兜底结算任务 | S3 |

| **S6** | 请假驳回补扣 | S3 |
| **S7** | 前端状态与「我的课时」 | S1 |

S1–S4 做完，闭环即成：**课前签到有记录、课后状态会动、课时会扣、重复调用不重复扣**。
S5 是重复排期的正确性前提，建议同批上线。
