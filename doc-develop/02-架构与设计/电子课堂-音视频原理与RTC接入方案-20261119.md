## 0. 结论速览

| 问题 | 答案 |
|---|---|
| 默认怎么通音视频 | **原生 WebRTC 全互联（MESH）**，浏览器两两直连，无媒体服务器 |
| 要扩容怎么办 | 后端把 `classroom.rtc.provider` 改成 `livekit`/`trtc`/`agora`，前端**一行不用改**（自动加载对应 SDK） |
| 前端会感知厂商吗 | 不会。后端只下发一份 `RtcJoinInfo` 契约，前端按 `topology` + `sdkType` 选引擎 |
| 音视频数据经过后端吗 | **不经过**。mesh 是 P2P，SFU 是终端↔媒体服务器；后端只管**信令**与**凭证签发** |
| 谁能出声 | 技术上人人可发音频；**能不能真出声由服务端禁言态 + 举手授权在信令层强制**（软门禁，见 §11） |
| 人数上限 | mesh 默认 `max-peers=6`；超过不建连（见 §7.6 的已知偏差） |
| 现在跑的是哪套 | `GET /api/v1/rtc/providers` 看 `configured` / `active` / `degraded` |

```
│ classroom-controls.js  底部控制栏（麦克风/摄像头按钮）                   │

└───────────────────────────────┬───────────────────────────────────────┘
                                │ 只调门面，不碰引擎
┌───────────────────────────────▼───────────────────────────────────────┐
│ 门面 classroom-rtc.js                                                  │
│  init → 拉配置 → 建引擎 → 转发 API；applyGate 发布门禁；授权态 micGranted │
└───────────────────────────────┬───────────────────────────────────────┘
                    ┌───────────┴────────────┐
        topology=MESH│                        │topology=SFU
┌───────────────────▼──────────┐  ┌──────────▼────────────────────────┐
│ engine-mesh.js               │  │ engine-sdk.js                      │
│ 原生 RTCPeerConnection       │  │ LiveKit / TRTC / Agora 适配        │
│ SDP/ICE 走 WS 信令            │  │ SDK 自己与媒体服务器协商，无需 WS   │
└───────────────────┬──────────┘  └──────────┬────────────────────────┘
                    │  失败回落 ─────────────┘
┌───────────────────▼───────────────────────────────────────────────────┐
│ 后端：MediaService（薄门面）→ RtcProviderRegistry（选型+降级）          │
│       → RtcProvider SPI：native-mesh / livekit / trtc / agora          │
│ 对外：GET /api/v1/classrooms/{sid}/rtc/config  →  RtcJoinInfo           │
└───────────────────────────────────────────────────────────────────────┘
```

**一句话**：前端按"一份契约 + 一套引擎接口"写，后端按"SPI + 注册表"扩展；换服务商是**配置级**动作，不是代码级动作。

## 2. 控制面与数据面分离

课堂里跑着两类完全不同的流量，混在一起看必然迷路：

| | 数据面（音视频） | 控制面（信令） |
|---|---|---|
| 走什么 | WebRTC（SRTP/UDP）或厂商 SDK | WebSocket（3 条连接） |
| 经过后端吗 | **不经过** | 全经过 |
| 谁建连 | 浏览器之间（mesh）／终端与媒体服务器（SFU） | 终端 ↔ classroom-service |
| 后端能管什么 | 只管"给你什么凭证、能不能推流" | 能拦、能改状态、能广播 |
| 典型延迟 | 100~300ms | 单程几十 ms（同机房） |

**这条边界决定了很多现象**：后端停掉不会让正在通话的 P2P 立刻断，但会让"举手/静音/白板"全部失效；反过来信令通但 ICE 打不通，就是"能看见人但没画面没声音"。

### 2.1 三条 WebSocket 通道

一条 URL 模板，三个 channel（`frontend/js/public/classroom-ws.js:30`）：

```
{wss_origin}/ws/classrooms/{scheduleId}/{signal|whiteboard|heartbeat}?access_token=…&traceId=…
```

| 通道 | 路径 | 干什么 | 后端 Handler |
|---|---|---|---|
| signal | `/signal` | 课堂信令：`rtc-*`（SDP/ICE）、举手、禁言、摄像头、聊天、授权、开课/下课 | `ClassroomSignalHandler` |
| whiteboard | `/whiteboard` | 白板笔迹 / 清空 / 撤回 / 快照 | `WhiteboardHandler` |
| heartbeat | `/heartbeat` | 15s 心跳，维持在线态（Redis） | `HeartbeatHandler` |

三条连接共用同一个 `traceId`（`classroom-ws.js:43-49`），服务端在握手时绑定进 MDC——否则一次"白板没同步"要在三份日志里各找一遍。

**握手鉴权**（`WsHandshakeAuthInterceptor`）做三件事：
1. 校验 `access_token`（共享 `jwt.secret`，HS512），无效直接拒绝握手；
2. 从路径解析 `scheduleId` 写入 session 属性——handler 据此**按房间广播**，不再是全局 sessions 广播（历史上正是这里漏了，导致 A 课堂笔迹出现在 B 课堂）；
3. 用 `ClassroomAccessGuard` 断言"这堂课归你"：非名单成员、非本课教师、被移出者、跨租户一律握不上手。

### 2.2 房间表在内存，在线态在 Redis

| 状态 | 存在哪 | 影响 |
|---|---|---|
| 谁连着 WS | `WsRoomRegistry` 的 `ConcurrentHashMap`（`signalRooms` / `wbRooms`） | **单实例内存**：多副本部署必须做会话粘性，否则 A 副本广播不到 B 副本上的连接 |
| 谁在线 | `OnlineStateManager` → Redis | 掉线判定、出勤的真相源；Redis 挂了下课扫描器会跳过离场判定（日志每 20s 一条 WARN） |

```
   │     · ClassroomAccessGuard.assertAccess      ← 名单/租户校验

   │
   ├─② 建 3 条 WS，握手鉴权通过后服务端 pushInitialState
   │     （禁言态、各人摄像头态、举手态、开麦授权、白板授权一次性补发）
   │
   ├─③ ClassroomRTC._applyConfig → _buildEngine → engine.join()

   ├─④ 协商（仅 mesh）
```

## 4. 统一契约：RtcJoinInfo

所有 provider 都必须返回这一份结构（`api/.../rtc/RtcJoinInfo.java`）。前端**只认它**：

| 字段 | 说明 | mesh 取值 |
|---|---|---|
| `provider` | 生效的服务商名 | `native-mesh` |
| `topology` | `MESH` / `SFU` → 决定前端用哪套引擎 | `MESH` |
| `roomId` | 房间号，**服务端派生**，客户端改不了 | `mesh-<scheduleId>` |
| `sdkType` | `native` / `livekit` / `trtc` / `agora` | `native` |
| `sdkUrl` | SDK 脚本地址（非 native 时前端动态注入） | `null` |
| `serverUrl` | LiveKit 的 wss / TRTC 的 sdkAppId / Agora 的 appId | `null` |
| `token` / `tokenExpireAt` | 厂商凭证及其过期时间 | `null`（P2P 不需要凭证） |
| `iceServers` | STUN/TURN 列表（mesh 必需） | STUN + 可选 TURN 临时凭证 |
| `maxPeers` | mesh 人数上限 | 6（可配） |
| `canPublish` / `canPublishVideo` / `canSubscribe` | 发布/订阅权限 | 音频恒 true；视频看角色与开关 |
| `recordingMode` | `CLOUD` / `CLIENT` / `NONE` | `CLIENT` |
| `extra` | 附加信息（如 `transport=p2p`、`turnEnabled`、容量提示） | — |

> 房间号为什么必须服务端派生：否则"拿到一个 token 就能进任意房间"。这条写进了 `RtcProvider` 接口约定。

前端引擎接口（`rtc-engine.js` 顶部注释即契约）：

```js
engine.join([isRejoin])        // 采集 + 进房，返回 Promise
engine.leave([silent])         // 离房 + 释放采集
engine.onSignal(msg)           // SDP/ICE（仅 mesh 需要；SFU 空实现）
engine.setMicEnabled(bool)     // 返回生效后的布尔
engine.setCamEnabled(bool)
engine.switchDevice(kind, id)  // 运行中切设备（mesh 用 replaceTrack，不重协商）
engine.broadcastJoin()         // WS 就绪后补发 join，返回是否真发出
engine.audioOk / videoOk       // 分别标记麦克风/摄像头是否可用
engine.isJoined()
```

## 5. MESH：默认路径的原生 P2P

### 5.1 拓扑与成本

N 个成员的 mesh 里，每人要**上行 N-1 路**。720p 约 1~1.5Mbps，6 人就是 5~7Mbps 上行——家用宽带上行普遍 10~30Mbps，再加上编码 CPU，**6 人就是现实硬顶**。

```
        A ──── B
        │ ╲  ╱ │          每人 N-1 条 RTCPeerConnection
        │  ╳   │          SDP/ICE 走 WS，媒体走 UDP 直连
        │ ╱  ╲ │
        C ──── D
```

配置项：`classroom.rtc.mesh.max-peers`（默认 6）。

### 5.2 谁发 offer：字典序规则

`engine-mesh.js:_onPeerJoin`：

```
收到 rtc-peer-join(from = peerId)
  ├ 已有 PC？
  │   ├ msg.rejoin            → 拆掉重建（对端媒体会话已换新）
  │   ├ failed/closed/disconnected → 拆掉重建
  │   ├ new + stable + 未在协商 → 拆掉重建（空转连接，不重建会永久卡死）
  │   └ 其余                  → 忽略这条重复 join
  └ 建连判定：
      this.userId > peerId  → 我发 rtc-offer
      否则若 msg.reply 为假  → 回一条 reply=true 的 join，让对方发 offer
```

**为什么要字典序**：双向同时 `createOffer` 会 glare（双方 `have-local-offer`，谁也进不去）。用不可变的 userId 排大小是零协调的确定性规则。

**为什么要 reply**：先进房的人课前那条 join 可能被服务端发布门禁丢弃（课堂没到 LIVE），字典序小的一方以为"对方知道我"，对方却不知道我存在 → 永远没人发 offer。reply join 补上"我在这儿"。

### 5.3 ICE / STUN / TURN

- `iceServers` 由后端下发，`NativeMeshRtcProvider.buildIceServers` 组装；
- STUN 默认 `stun:stun.l.google.com:19302`（可用 `RTC_STUN` 覆盖）；
- **生产必须配 TURN**：只有 STUN 时，对称型 NAT / 企业防火墙下约 2~3 成用户建连失败；
- TURN 用 **coturn REST 临时凭证**，不落固定账号：

```
username   = "<过期unixtime>:<userId>"
credential = base64(HMAC-SHA1(secret, username))
```

配 `RTC_TURN_URLS` + `RTC_TURN_SECRET` 即启用，TTL 默认 3600s。固定账号一旦泄露，别人能拿它当免费中继刷流量——所以代码里压根不提供这种模式。

### 5.4 幂等与重建（踩过的坑）

| 场景 | 处理 | 不处理的后果 |
|---|---|---|
| 同一对端多条 join（补发/reply 机制必然产生） | 幂等判定，健康连接直接忽略 | 重复 `createOffer` 抛 `InvalidStateError`，协商被搅乱 |
| 空转连接（PC 建了但 offer 没发出） | 判为 idle 拆掉重建 | 一次 createOffer 失败 → 这对端永久卡死 |
| 网络恢复 / 切引擎 | `rejoin` 标记跨补发保留 | 对端继续用旧 PC，重建白做 |
| WS 握手晚于采集完成 | `join` 返回布尔，`onOpen` 时补发 | 双方都不发 offer，学生端永远看不到教师画面 |

### 5.5 采集与设备

`engine-mesh.js:_startLocalMedia` + `frontend/js/classroom/media-devices.js`：

- **音视频分离请求**：一个设备缺失/被占用不再连累另一路（旧版一个 Promise 全废）；
- 应用课前准备页保存的 `deviceId` 偏好，失效自动回退系统默认；
- `NotAllowedError` / `NotFoundError` / `NotReadableError` 翻成中文自救提示；
- `audioOk` / `videoOk` 分开标记，`mediaOk` 仅作兼容；
- 运行中切设备走 `replaceTrack`（`_closePeer` 之外的路径），**不重协商、对端无感**，且继承原轨道的 `enabled` 状态（已关麦时切设备不会把麦重新打开）。

非 HTTPS/localhost 时 `getUserMedia` 直接被浏览器禁用——这是"摄像头下拉为空"的第一嫌疑。

### 5.6 开关与门禁

`setMicEnabled` / `setCamEnabled` 的实现是 `track.enabled = false`——**轨道还在，只是不发声/不出画面**。所以对端会收到一条黑屏/静音流，而不是"人消失"。这带来两个后果：

- 录制取本地流时，关着麦录出来就是无声（已在用户手册写明"录课前先开麦"）；
- 想真正停采，得 `track.stop()`（当前没有这条路径，属于妥协点）。

门禁分三层，缺一层就会"看起来限制了其实没限"：

```
① 页面层：canPublish()（PAUSED / 非 LIVE 时禁发）        main.js:161
② 服务端：ClassroomPublishGuard 拦 WS 消息                ClassroomPublishGuard
③ 业务层：学生开麦需 micGranted（教师批准）               classroom-rtc.js:setMicEnabled
```

### 5.7 达上限后的行为：真·只收不发（2026-11-19 已实现）

早期实现是 `_peer()` 直接 `return null`——**既不建连也收不到对方**，超限成员等于"完全缺席"，
但 toast 却写着"只收不发"，属于文案与行为不符。

现在改成真正的降级：

| 项 | 行为 |
|---|---|
| 连接 | 照建（`_peer` 不再返回 null） |
| 本地轨道 | **不加**（`addTrack` 跳过），对方收不到你的音视频 |
| 对端轨道 | 正常接收（对方 offer/answer 里的 track 会触发 `ontrack`） |
| 判定依据 | `_publishedCount() >= maxPeers`，而不是 `Object.keys(peers).length`——后者在"先 `_closePeer` 再 `_peer`"的重建路径上会瞬间少 1，误判成未超限把轨道加进去，造成发布状态抖动 |
| 名额释放 | `_closePeer` 后异步 `_restorePublishing()`：补 `addTrack` + 按字典序重新协商（大的一方 `createOffer`，小的一方发 `rejoin`），自动恢复对外发送 |
| 提示 | 只在首次降级时 toast 一次，避免每个新成员都弹 |

> 残余限制：双方都超限（比如 8 人课堂里第 7、8 位）时，两边都不带轨道的 SDP 会协商成
> `inactive`，互相看不到——这与"完全缺席"等价，属于 mesh 拓扑的硬边界，要突破只能上 SFU。

## 6. SFU：换服务商时走的路

### 6.1 为什么需要

mesh 的上行成本随人数线性上涨，且没有云端录制、没有服务端强管控。SFU（Selective Forwarding Unit）把上行收敛为"每人只发一路给媒体服务器"，由服务器按需转发：

```
mesh:  每人上行 N-1 路        SFU:  每人上行 1 路
```

代价是要么自建（LiveKit + coturn + 带宽），要么按分钟付费（TRTC/Agora），并且多了一个故障域。

### 6.2 三家接入差异（都在 `api/.../rtc/` 下，纯 JDK 签名，不引厂商 SDK）

| | LiveKit | 腾讯云 TRTC | 声网 Agora |
|---|---|---|---|
| 自建 | ✅ 开源，可私有化 | ❌ 云服务 | ❌ 云服务 |
| 凭证 | **HS256 JWT**，`javax.crypto` 直接签 | **UserSig v2**：`base64(zlib(json))`，内含 `HMAC-SHA256` 签名 | AccessToken2（AES+HMAC+pack），**反射调官方 `RtcTokenBuilder2`**，不自己实现 |
| 关键配置 | `LIVEKIT_URL` / `API_KEY` / `API_SECRET` | `TRTC_SDK_APP_ID` / `TRTC_SECRET_KEY` | `AGORA_APP_ID` / `AGORA_APP_CERTIFICATE` + 依赖 `io.agora:authentication` |
| 前端 SDK | `livekit-client`（`LIVEKIT_SDK_URL`） | `trtc.js` v5（`TRTC_SDK_URL`） | `AgoraRTC_N-4.20.0.js`（`AGORA_SDK_URL`） |
| 权限载体 | JWT 的 `video` claim（`canPublish`/`room`） | UserSig 绑定 userId + sdkAppId | token 内 role（PUBLISHER/SUBSCRIBER） |
| 订阅模型 | `RoomEvent.TrackSubscribed` | `on('stream-added')` → subscribe | `user-published` → subscribe |

> **Agora 为什么用反射**：AccessToken2 的算法实现成本高且极易签错，官方 `agora-token-builder` 才是唯一可信实现。依赖不在时 `available()` 直接返回 false 并给出人话原因，不写假实现。

### 6.3 前端统一适配

`engine-sdk.js` 只做三件事：按 `sdkType` 动态加载 SDK（`sdkUrl` 可换 CDN/内网）、把各家 API 翻译成统一接口、**任何一步失败回落 mesh**。

```
SdkRtcEngine.join()
  ├ loadScript(sdkUrl) 失败 → _fallback('SDK 未加载')
  ├ 进房/token 过期/厂商报错 → _fallback(msg)
  └ 成功 → audioOk=true, videoOk=canPublishVideo, _applyDevicePrefs()
```

SFU 下 `onSignal` 是**空实现**——SDP/ICE 由 SDK 与媒体服务器自己协商，走 WS 反而多余。但举手、禁言、白板、授权这些**业务信令仍然走 WS**，不受影响。

### 6.4 降级链（三层，任一层断都不至于开不了课）

```
① 后端选型降级：配置的 provider 不可用 → 回落 native-mesh（启动 WARN 留痕）
② 建房/签发失败：registry.ensureRoom / join 抛异常 → 当场用 mesh 兜一次
③ 前端引擎回落：SDK 加载或进房失败 → ClassroomRTC._fallbackToMesh（保留 ICE/maxPeers，带 rejoin 重建）
```

降级**必须留痕**：启动日志一行 WARN + `GET /api/v1/rtc/providers` 可查 `configured` / `active` / `degraded` / 每家 `reason`。"配了 livekit 却一直跑 mesh"这种事故，靠静默降级是查不出来的。

## 7. 后端 RTC 抽象：SPI 与注册表

### 7.1 RtcProvider（唯一扩展点）

```java
String name();                 // 与 classroom.rtc.provider 取值一致
RtcTopology topology();        // MESH / SFU，决定前端选哪套引擎
boolean available();           // 只判配置是否完备，禁止发网络请求
String unavailableReason();    // 不可用时给人话
String ensureRoom(String sid); // 幂等：开课/首人进房/重连都会调
void destroyRoom(String sid);  // 幂等且不抛语义：下课会调
RtcJoinInfo join(RtcJoinContext ctx);
String roomIdOf(String sid);   // 默认返回 scheduleId
```

四条实现约定（写在接口注释里，新增 provider 必须遵守）：`ensureRoom` 幂等、`destroyRoom` 幂等不抛、`available()` 不做网络探测、**房间号必须由服务端派生**。

### 7.2 RtcProviderRegistry

选型规则只有一条：**配置指定的可用就用它，否则回落 native-mesh**。

- `available()` 是静态判断，不做健康探测（厂商侧真挂了服务端提前不知道，探测只会拖慢开课）；
- `ensureRoom` / `destroyRoom` / `join` 三个出口都包了 try/catch → 失败降级 mesh 而不是抛给业务；
- `describe()` 给运维诊断用。

### 7.3 MediaService：薄门面

业务代码只跟它打交道，因此换服务商不波及课堂生命周期、控制器、前端任何一行。它还固化了**发布权限口径**：

```java
boolean managerLike = isTeacher(role) || isManager(role) || SYSTEM.equals(role);
boolean canPublishVideo = managerLike || rtcProperties.isStudentPublishVideo();
```

即：**音频人人可发**（学生要能举手应答），**视频默认只有教师/管理员发**（省上行，`RTC_STUDENT_VIDEO=false`）。

### 7.4 接入一家新厂商的步骤

1. 新建 `XxxRtcProvider implements RtcProvider`，标 `@Component`；
2. `name()` 返回与配置一致的字符串，`topology()` 按实际返回；`available()` 只判配置齐全；
3. `ensureRoom` / `destroyRoom` 幂等，`join` 里签发凭证并填满 `RtcJoinInfo`（`roomId` 用 `scheduleId` 派生）；
4. `application.properties` 加 `classroom.rtc.xxx.*`，凭证走环境变量；
5. 前端：`engine-sdk.js` 加一个 `_joinXxx()` 分支（**只有这一步要改前端**，因为 SDK API 各不相同）；
6. 验证：`GET /api/v1/rtc/providers` 看 `active` 是否切过去、`degraded=false`；开一节课看 `进房配置签发` 日志里的 `provider` / `topology`。

> 若厂商走标准 WebRTC 且你愿意自己维护 SDK 适配，也可以只做"配置 + 前端分支"，后端不用新代码。

## 8. 信令消息清单

### 8.1 signal 通道（`ClassroomSignalHandler`）

服务端先过发布门禁，再分两路：**已知业务类型**交给 `ClassroomSignalService`（改状态 + 权威广播 + 落事件流水）；**未知类型**原样转发给房间内其他人（`broadcastSignalExcept`）。

| 类型 | 方向 | 说明 |
|---|---|---|
| `rtc-peer-join` / `rtc-peer-leave` | C→S→C | 成员加入/离开，触发建连/拆连 |
| `rtc-offer` / `rtc-answer` / `rtc-ice` | C→S→C | SDP 与 ICE 候选（房间广播 + 客户端按 `to` 过滤，见 §8.3） |
| `hand` | C→S→C | 举手；服务端写权威态后广播 `hand:state` |
| `hand:approve` | C→S→C | `{granted:true|false}` 批准/撤回发言权；服务端校验仍在举手 |
| `mute-all` | C→S→C | 全员静音；服务端撤销全部开麦授权 |
| `cam-state` | C→S→C | 摄像头开关（含 `silent`，进房默认关闭时用） |
| `chat` | C→S→C | 聊天；禁言时被拒并回 `chat:rejected` |
| `wb:grant` | C→S→C | 白板授权（**注意：由 signal 通道下发 `wb:grant:state`**） |
| `class-start` / `class-end` / `class-pause` / `class-resume` | C→S→C | 状态控制，属门禁例外 |
| `rollcall:start` / `rollcall:stop` | C→S→C | 点名 |

服务端主动下发（非对方转发）：`hand:state`、`mic:grant`、`mute:state`、`wb:grant:state`、`class:state`、`chat:msg`、`chat:rejected`、`member-kicked`、`rollcall:start`、`record:state`、`wb:denied`。进房时的 `pushInitialState` 会把这批"当前态"静默补发一遍（禁言/摄像头/举手/开麦授权/白板授权）——**这就是刷新后状态不丢的原因**。

### 8.2 whiteboard 通道（`WhiteboardHandler`）

`draw` / `stroke` / `erase` / `shape` / `text` / `clear` / `undo` / `wb:save` / `wb:init`（快照重放）。
写入前校验 `liveState.canEditWhiteboard(...)`——教师恒可写，学生需 `wb:grant`；`undo` 只允许撤自己的（按握手身份比对 `by`，客户端自报的一律不信）。

> **踩过的坑**：白板消息分两条通道。笔迹走 whiteboard 通道（`broadcastWhiteboard`），而 `wb:grant:state` 走 **signal** 通道（`broadcastSignal`）。前端白板模块一度只有 `onMessage`（whiteboard 入口）没有 `onSignal`，导致"教师授权了、学生还是只读"。已修为 `onSignal` 转投 `onMessage`。

### 8.3 `rtc-*` 是房间广播（2026-11-19 已在客户端收口）

`ClassroomSignalHandler` 对未知类型统一走 `broadcastSignalExcept`——**`rtc-offer` / `rtc-answer` / `rtc-ice` 是广播给房间里除自己以外的所有人**，不是按 `to` 单播。

客户端现在三个入口都做 `to` 过滤（`_onIce` 原本就有，`_onOffer` / `_onAnswer` 于 2026-11-19 补上）：

```js
if (msg.to && msg.to !== this.ctx.userId) return;
```

- 2 人课堂本来就无影响（房间里只有对方）；
- **3 人以上**若不过滤：A 发给 B 的 offer，C 也会收到并回 answer 给 A，A 侧可能把 C 的 answer 套到"给 C 的 offer"上 → SDP 错配/glare，表现为某人黑屏、或某对反复重建。

> 仍是「广播 + 客户端过滤」，不是服务端单播：报文依旧发给全房间，只是各端丢弃不属于自己的。
> 人数多时有无谓的带宽开销（SDP 约 2~4KB/条）。要彻底收敛，应改为后端按 `to` 单播
> （见 §8.4 的演进项），当前按"改动最小、风险最低"选择了前端方案。

## 9. 发布门禁：服务端才是权威

`ClassroomPublishGuard`（1.5s 状态缓存，状态流转主动失效，查库失败按"非 LIVE"处理）：

| 课堂状态 | 学生可发 | 教师/管理员可发 |
|---|---|---|
| LIVE | ✅ | ✅ |
| PAUSED | ❌ | **❌**（暂停期间教师也不发） |
| SCHEDULED / READY / CLOSED / CANCELLED | ❌ | ✅ |

**控制类消息例外**（`CONTROL_TYPES`）：`class-*`、`mute-all`、`hand:approve`、`wb:grant`、`wb:save`、`member-kicked`、`rollcall:*`。不例外的话，教师暂停后就再也没法点「进行中」恢复课堂——这是这条门禁最关键的细节。

前端禁用控件只是体验优化；绕过前端直发 WS 一样会在这里被丢掉：signal 通道回 `{"type":"publish:rejected","reason":"CLASS_NOT_PUBLISHABLE","status":…}`（`ClassroomSignalHandler:120`），whiteboard 通道回 `wb:rejected`（`WhiteboardHandler:124`）。

## 10. 录制与 RTC 的关系

录制是**独立的一条 SPI**（`com.classroom.recording`），跟 RTC 只共享"本地轨道"这一个事实：

| 模式 | 做法 | 现状 |
|---|---|---|
| `CLIENT` | 教师端 `MediaRecorder` 录本地上行流，录完整包上传 | **默认**，零成本、私有化可用；只录到教师自己的画面与声音 |
| `CLOUD` | 媒体服务器侧合流（LiveKit Egress / 声网云录制 / TRTC 云端录制） | 需厂商开通+计费+回调，未配置时 `available()=false`，**不写假实现** |

`RtcJoinInfo.recordingMode` 以录制后端的真实选型为准（不是"这种拓扑通常能做什么"）。

前端录制链路（`classroom-record.js`）：`getLocalStream()` 取轨道 → `MediaRecorder` 录 → 收尾补 EBML `Duration` + `Cues` → 分片上传。补这两个字段是为了让回放能显示总时长、能拖到任意秒；MP4 容器跳过修补（自带 moov）。

> 由此产生一条硬约束：**麦克风/摄像头都关着时录制是黑屏无声**（`track.enabled=false` 仍能录，只是内容空）。

## 11. 谁能出声：三层软门禁

音视频走 P2P/SFU，服务端碰不到音轨，所以"权限"只能落在信令与 UI 上：

```
① 举手 → 教师批准（hand:approve{granted:true}）→ 服务端写 micGranted → 广播 mic:grant
② 学生端 RTC.micGranted=true 才允许 setMicEnabled(true)
③ 教师撤回 / 全员静音 / 学生放下手 → 撤销授权 + 广播，两端复位
```

**残余风险（须知）**：学生改 JS 强制 `track.enabled=true` 仍能出声——服务端只能管信令，管不到媒体。要做到"未批准绝对说不了话"，必须：

- 接收端按授权过滤音轨（`audioEl.muted` 或订阅时拒绝），或
- 换 SFU/TRTC 由服务端 `muteRemoteAudio` 强管控。

当前按"软门禁 + 记录残余风险"处理，覆盖 99% 课堂场景；有真实越权诉求再评估。

## 12. 配置与部署

### 12.1 关键环境变量（`application.properties` §RTC）

| 变量 | 默认 | 说明 |
|---|---|---|
| `RTC_PROVIDER` | `native-mesh` | `native-mesh` / `livekit` / `trtc` / `agora` |
| `RTC_STUDENT_VIDEO` | `false` | 学生是否允许推视频（音频恒可发） |
| `RTC_STUN` | `stun:stun.l.google.com:19302` | STUN 地址 |
| `RTC_TURN_URLS` | 空 | **生产必配**，逗号分隔 |
| `RTC_TURN_SECRET` | 空 | coturn `static-auth-secret` |
| `RTC_MESH_MAX_PEERS` | `6` | mesh 上限 |
| `LIVEKIT_URL` / `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` / `LIVEKIT_SDK_URL` | 空 | LiveKit |
| `TRTC_SDK_APP_ID` / `TRTC_SECRET_KEY` / `TRTC_SDK_URL` | `0` / 空 | TRTC |
| `AGORA_APP_ID` / `AGORA_APP_CERTIFICATE` / `AGORA_SDK_URL` | 空 | Agora |

### 12.2 反代与网络

- WebSocket 必须带 `Upgrade` 头且长连接不超时：`deploy/nginx/booking.conf:191` 的 `location /ws/classrooms/`；
- WS 与 API 同源走 8092（课堂服务），**不要**被 `/api/v1/classroom-callback/` 那条 8081 的规则抢走；
- HTTPS 是硬前提：非安全上下文 `getUserMedia` 直接被禁用；
- TURN 若走 UDP 3478，安全组要放行 UDP（只放 TCP 会出现"部分人能连、部分人不能"）。

### 12.3 部署形态影响

| 项 | 单实例 | 多副本 |
|---|---|---|
| WS 房间表（内存） | ✅ 正常 | ❌ 需会话粘性，或改成 Redis pub/sub 广播 |
| 在线态（Redis） | ✅ | ✅ |
| `ClassroomLiveState`（内存） | ✅ | ❌ 各副本状态不一致（举手/授权会串） |

结论：**当前架构按单实例设计**。要多副本，先解决上面两处共享态。

## 13. 容量与选型建议

| 场景 | 建议 |
|---|---|
| ≤6 人、内网/公网小班 | mesh 够用，配好 TURN |
| 6~20 人 | 必须上 SFU（LiveKit 自建最省钱，需备带宽与 coturn） |
| 需要云端录制/回放 | SFU + 云录制（CLIENT 录制只有教师画面） |
| 强管控（未批准不能出声） | SFU/TRTC 的服务端静音，而非 mesh 软门禁 |
| 完全私有化 | LiveKit 自建 + coturn + 本地对象存储 |

带宽估算（mesh，720p/1Mbps）：教师上行 ≈ 学生数 × 1Mbps；SFU：每人上行 1Mbps + 服务器下行 = 人数 × 1Mbps。

## 14. 排障手册

| 症状 | 第一嫌疑 | 定位方法 |
|---|---|---|
| 进课堂一切正常但**没画面没声音** | ICE 打不通 / 相机麦克风被拒 | F12 看 `getUserMedia` 报错；查 `RTC_TURN_URLS` 是否配置；`chrome://webrtc-internals` 看 candidate 类型只有 host 就是没 STUN/TURN |
| 只有**部分人**看不到 | 对称型 NAT，无 TURN | 同上；补 TURN 后重试 |
| 学生看不到教师画面 | `rtc-peer-join` 丢了，没人发 offer | 看服务端日志有没有 `信令连接建立`；前端是否在 `onOpen` 补发 join |
| **某两人一直连不上**（3 人以上） | 旧版本 `rtc-offer` 广播串答（§8.3，客户端 `to` 过滤已修） | 先确认前端脚本已更新（F12 搜 `msg.to !== this.ctx.userId`）；仍复现则抓 signal 报文看 `to` |
| 白板授权了学生还是只读 | `wb:grant:state` 走 signal 通道，白板模块需 `onSignal` | 前端看 `ClassroomWhiteboard.granted`；确认 `onSignal` 存在 |
| 麦克风开了没声音 | 未获授权被门禁拦 / 全员静音 | toast 文案区分「请先举手」/「全员禁言」；查 `micGranted` |
| 改了后端行为却没变 | **跑的是旧 jar** | `mvn package` 后重启；jar 被占用会报 `Unable to rename ... .jar.original` |
| 健康检查 503 但课堂能用 | Redis 挂了（只影响掉线判定与健康检查） | `netstat` 看 6379；日志「Redis 不可用，本轮跳过离场判定」 |
| 日志里 `active` 不是配置的 provider | 配置不全被降级 | `GET /api/v1/rtc/providers` 看 `reason` |
