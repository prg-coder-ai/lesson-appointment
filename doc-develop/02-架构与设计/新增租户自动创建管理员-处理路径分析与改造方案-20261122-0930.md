# 新增租户自动创建租户管理员：处理路径分析与改造方案

> 日期：2026-11-22 09:30
> 范围：平台管理端「租户管理 → 新增租户」→ `TenantController` → `TenantService` → `sys_tenant` / `sys_user`
> 需求：新增租户时填写的**联系人、联系电话**，在租户创建成功后自动作为该租户的管理员写入 `user` 表

---

## 0. 一句话结论

**现状完全没有这条路径。** 新增租户只写 `sys_tenant` 一张表，前端填的 `contact` / `phone` 只是租户的联系信息，**不产生任何登录凭证**——租户建好后必须人工去「用户管理 → 新增用户 → 选该租户」，或者让客户拿租户码自助注册。

改造的技术难点不在"再插一行 user"，而在 **5 个必须先拍板的边界**：账号取什么、密码策略、账号唯一性口径、`TenantContext` 被清掉、事务回滚。其中 `TenantContext` 那条最隐蔽，写错会导致建完管理员之后同请求内的后续查询"跑到别的租户去"。

好消息：**这个场景已经有现成范式**——`PromoService` 的"自助建租户（路径 1）"做的就是「建租户 + 建首管理员 + 失败整体回滚」，直接照抄结构即可。

## 1. 现状处理路径

### 1.1 全链路时序

| # | 环节 | 位置 | 动作 | 落库 |
|---|---|---|---|---|
| 1 | 前端弹窗 | `frontend/js/platform-admin-tenant.js:184 submitTenant()` | 收集 8 个字段，`POST /tenant/insert` | — |
| 2 | 路由 | `TenantController.java:217` | `@PostMapping("/insert")` | — |
| 3 | 鉴权 | `TenantController.java:220` | `permissionCheck.checkPlatformAdmin(token)` —— 仅平台管理员 | — |
| 4 | 事务入口 | `TenantService.java:171` | `@Transactional(propagation=REQUIRED, rollbackFor=Exception.class)` | — |
| 5 | 校验 | `TenantService.java:173-178` | `tenantCode` 非空、不重复 | — |
| 6 | 补默认值 | `TenantService.java:179-186` | `status=1`、`deleted=0`、`packageId=0`、`expireTime=now+1年` | — |
| 7 | 插入 | `TenantService.java:187` | `tenantMapper.insert(tenant)` | **`sys_tenant` 1 行** |
| 8 | 返回 | `TenantController.java:222` | `Result.success({tenantId})` | — |

**没有第 9 步。** `sys_user` 表在整条链路上一次都没被碰过。

### 1.2 前端提交的字段（`platform-admin-tenant.js:188-197`）

```js
const data = {
  orgName, tenantCode, contact, phone,
  industryId, status, expireTime, remark
};
```

对应用后端 `Tenant` 实体（`entity/Tenant.java:15-40`）：

```java
private Long id;            private String tenantCode;
private String orgName;     private String contact;      // ← 联系人姓名
private String phone;       // ← 联系电话
private Integer status;     private Long packageId;      private Long industryId;
private LocalDateTime expireTime;  private LocalDateTime offlineTime;
private String remark;      private String referredBy;
private String trialStatus; private LocalDateTime trialExpireTime;
private String creatorAccount;     private Integer deleted;
```

> 注意：`Tenant` **没有 email 字段**，前端表单也没有。若未来要用邮箱当账号，需要两端一起加。

### 1.3 字段映射现状（这就是缺口）

| 表单字段 | 现状去处 | 是否产生 user |
|---|---|---|
| `orgName` 机构名称 | `sys_tenant.org_name` | ❌ |
| `tenantCode` 租户编码 | `sys_tenant.tenant_code` | ❌（只作为租户标识） |
| `contact` 联系人 | `sys_tenant.contact` | ❌ 纯文本，无人能用它登录 |
| `phone` 联系电话 | `sys_tenant.phone` | ❌ 同上 |
| `industryId` / `status` / `expireTime` / `remark` | 对应列 | ❌ |

**结论**：租户建完后处于"有壳无人"状态。要么平台管理员再手工建账号，要么把租户码连同注册链接发给客户自助注册。

### 1.4 为什么之前没暴露成 bug

自助注册那条路是通的（`/user/register` + 租户码，`admin` 走"首管理员 bootstrap"自动 `active`）。所以功能上"能用"，只是多了一步人工操作，而且容易出现**建了租户忘了建账号**、客户拿不到登录入口的情况。

## 2. 目标处理路径

### 2.1 改造后时序（在原有第 7 步之后加 8、9 两步）

| # | 环节 | 动作 | 落库 |
|---|---|---|---|
| 7 | 插入租户 | `tenantMapper.insert(tenant)` | `sys_tenant` 1 行 |
| **8** | **建首管理员** | 由 `contact`/`phone` 组装 `User`，调 `userService.Register(user, true)` | **`sys_user` 1 行** |
| **9** | **结果校验** | `Register` 失败 → 抛 `BusinessException` → 整体回滚（租户也不留） | 回滚 |

### 2.2 字段映射（目标）

| 来源 | 目标字段 | 说明 |
|---|---|---|
| `contact`（联系人姓名） | `sys_user.name` | **入库前由 `CryptoUtil` 加密**（现有字段加密规则，不是明文） |
| `phone`（联系电话） | `sys_user.account` **和** `sys_user.phone` | account 是可登录账号；phone 用于短信/找回 |
| `tenantCode` | `sys_user.tenant_code` | 与租户行一致 |
| 新生成的 `tenantId` | `sys_user.tenant_id` | **必须用新租户 id**，漏了就变成平台账号 |
| 固定值 | `sys_user.role = "admin"` | `RoleConst.ADMIN` |
| 由准入逻辑决定 | `sys_user.status` | 见 2.3 |
| 固定/前端传入 | `sys_user.password` | **加密前先过 `PasswordPolicy`**，见 4.2 |
| 系统生成 | `sys_user.user_id` | `UUID.randomUUID()` 去横线，`Register` 内部生成 |

### 2.3 状态（`status`）该是 `active` 还是 `pending`

`applyRoleAdmission(user, regTenantId, approvedByAdmin)` 的两种口径：

| `approvedByAdmin` | 走的分支 | 结果 |
|---|---|---|
| `false` | 首管理员 bootstrap：本租户**尚无 admin** → `active`；否则 `pending` | 依赖"尚无 admin"这个判定 |
| `true` | 创建即审批，角色合法直接 `active` | 不依赖计数 |

**平台端应该用 `true`**：动作发起人已是平台管理员，创建行为本身就是审批。用 `false` 虽然当前也能得到 `active`（租户刚建，必然没有 admin），但语义上把"激活"寄托在一个**可被抢注**的判定上——如果哪天建租户和建管理员之间被插入一次注册，就会退化成 `pending`，租户管理员当场无法登录。

> 已知约束（`applyRoleAdmission` 注释，2026-10-24 明确保留）：首管理员判定**只数 role、不看 status**。被冻结的 admin 也算"已有管理员"。这是有意的（否则禁用后位置可被抢），所以不能靠"改成只数 active"来绕过上面的问题。

## 3. 现成范式：`PromoService` 路径 1

自助建租户时已经实现了完全相同的编排（`PromoService.java:495-524`）：

```java
Long tenantId = tenantService.insertTenant(tenant);

// ...（本项目的业务：签协议、建试用套餐、绑套餐）

// ③ 首管理员（applyRoleAdmission：本租户无 admin → 自动 active）
User admin = new User();
admin.setAccount(account.trim());
admin.setPassword(password);
admin.setName(name);
admin.setPhone(phone);
admin.setRole(RoleConst.ADMIN);
admin.setTenantCode(tenant.getTenantCode());
ResultHolder reg = ResultHolder.of(userService.Register(admin, false));
if (!reg.ok) {
    throw new BusinessException(reg.message);   // 抛异常以回滚，避免孤儿租户
}
```

三个可复制的要点：

1. **只在 `tenantCode` 上关联**，`tenantId` 由 `Register` 内部通过 `resolveTenantByCode` 反查——但平台端我们已经拿到了 `tenantId`，**建议直接 set `tenantId`**，少一次解析、也避免租户码大小写差异带来的坑。
2. **失败必须抛异常**，不能 `return`。`insertTenant` 的 `@Transactional` 只对异常回滚，返回值不做任何处理。
3. **注释里写明"避免孤儿租户"**——这就是整个设计的核心约束：租户与管理员要么都在，要么都不在。

## 4. 五个必须先拍板的边界

### 4.1 账号（`account`）取什么

| 方案 | 优点 | 风险 |
|---|---|---|
| **A. `account = phone`** | 用户零学习成本，填一个手机号就能登录 | `phone` 目前**不是必填**（前端只校验了 `orgName`），为空时无法建账号 |
| B. `account = tenantCode` | 一定非空、可预测 | 极易被猜（`TENANT_A` 之类），且与"用手机号登录"的用户习惯冲突 |
| **C. 前端新增「管理员账号 / 初始密码」两栏** | 最灵活，可控 | 表单变长，需要向业务方确认是否接受 |

**建议：C + A 组合** —— 新增两个字段：账号（默认自动填充手机号）、初始密码；若账号留空则用 `phone`，`phone` 也为空则**拒绝创建并提示"请填写联系电话或管理员账号"**（不要静默跳过建管理员，那等于把需求悄悄降级）。

### 4.2 密码策略（硬约束，最容易被忽略）

`api/.../security/PasswordPolicy.java`：

| 模式 | 规则 |
|---|---|
| `strict-mode=true`（cloud / prod） | 8–64 位，且**大写字母 + 小写字母 + 数字 + 特殊字符各至少一位** |
| `strict-mode=false`（默认） | 至少 6 位 |

`app.security.strict-mode=${APP_SECURITY_STRICT_MODE:false}`。

⚠️ **生产环境开 strict 时，沿用默认密码 `123456` 一定会失败**，表现为建租户成功但建管理员报"密码强度不足"→ 整体回滚 → 用户只看到一句报错，租户也没建成。这是最典型的"上线才发现"的问题。

两条出路：

- 前端让平台管理员填初始密码，并在提交前用同一套规则做前端预校验；
- 或后端用统一生成器产出合规随机密码，在响应里**只回显一次**，同时标记"首次登录必须改密"。

### 4.3 账号唯一性是"租户内"唯一

```java
// UserService.java:1681
public boolean existAccount(String account, Long tenantId) {
    User user = userMapper.getUserByAccount(account, tenantId);
```

判定口径是 **`(account, tenant_id)`**，不是全局。所以同一个手机号在 A 租户和 B 租户可以各有一个 `admin` 账号——这符合既定业务规则（同一联系方式可对应多个账号，DB 不加唯一索引）。

但要提醒业务方：`account = phone` 时，同一个人开两个租户会产生**两个可登录账号**，用户在登录页选错租户就会看到"另一套数据"。这在多租户 SaaS 里是正常语义，但客服话术要提前准备。

### 4.4 `TenantContext` 会被清掉（最隐蔽的一条）

```java
// UserService.Register 内部（:258 附近）
TenantContext.setTenantId(regTenantId);
try {
    ...
} finally {
    TenantContext.clear();      // ← 无条件清空
}
```

而 `api/src/main/java/com/reservation/utils/TenantContext.java` **只有 `set/get/clear`，没有 save/restore**。

后果：平台管理员请求线程原本的上下文（平台侧 `tenantId=0`）在 `Register` 返回后**已被清空**。此时若同请求内还有任何走租户插件的查询，会按兜底值拼条件 → **查错租户的数据，而且不报错**。

`PromoService` 没踩到，是因为它跑在注册接口里，调用前上下文本来就是空。平台端不一样。

**处置**：

```java
Long prev = TenantContext.getTenantId();      // 通常为 0（平台）
try {
    Result<Object> r = userService.Register(admin, true);
    if (r.getCode() != 200) throw new BusinessException(r.getMessage());
} finally {
    TenantContext.setTenantId(prev);          // 恢复外层上下文
}
```

更彻底的方案是给 `TenantContext` 加 `push/pop`（或 `runWithTenant(id, Runnable)`），让嵌套调用天然安全——但那是框架级改动，涉及面大，本次可以先用上面这段兜住。

### 4.5 事务与回滚

- `insertTenant` 已有 `@Transactional(rollbackFor = Exception.class)`，把建管理员放进去即天然同事务；
- `Register` 返回 `Result` 而**不抛异常**，所以必须 `if (!ok) throw`，否则会commit 一个"有租户没管理员"的半成品；
- 反向也要注意：不要在 `insertTenant` 里 `catch` 掉异常后 `return null`，那会让调用方以为成功。

## 5. 推荐实现（代码骨架）

保持 `TenantController` 不变，改 `TenantService`：

```java
@Transactional(propagation = Propagation.REQUIRED, rollbackFor = Exception.class)
public Long insertTenant(Tenant tenant) { ... }   // 保持原样，不做管理员

/**
 * 新增租户 + 自动创建租户管理员（平台管理员后台专用，2026-11-22）
 *
 * 与 insertTenant 拆成两个方法而不是加开关参数：
 * 开关参数会让"要不要建管理员"变成运行期才确定的事，调用方漏传就静默不建。
 */
@Transactional(propagation = Propagation.REQUIRED, rollbackFor = Exception.class)
public Long insertTenantWithAdmin(Tenant tenant, String adminAccount, String adminPassword) {
    Long tenantId = insertTenant(tenant);          // 同类调用，同一事务

    String account = StringUtils.hasText(adminAccount) ? adminAccount.trim() : tenant.getPhone();
    if (!StringUtils.hasText(account)) {
        throw new BusinessException("请填写联系电话或管理员账号，否则无法生成租户管理员");
    }
    // 密码强度先校验，避免 create 之后才失败（虽然同事务可回滚，但报错信息更清楚）
    String pwdErr = passwordPolicy.validate(adminPassword);
    if (pwdErr != null) {
        throw new BusinessException("初始密码不符合要求：" + pwdErr);
    }

    User admin = new User();
    admin.setTenantId(tenantId);                    // ★ 显式指定，不靠 resolveTenantByCode
    admin.setTenantCode(tenant.getTenantCode());
    admin.setAccount(account);
    admin.setPassword(adminPassword);
    admin.setPhone(tenant.getPhone());
    admin.setName(tenant.getContact());              // 入库由 Register 链路上的加密处理
    admin.setRole(RoleConst.ADMIN);

    Long prevTenant = TenantContext.getTenantId();   // ★ 4.4
    try {
        Result<Object> r = userService.Register(admin, true);   // true = 创建即审批 → active
        if (r == null || r.getCode() != 200) {
            throw new BusinessException("创建租户管理员失败：" +
                    (r == null ? "无返回" : r.getMessage()));
        }
    } finally {
        TenantContext.setTenantId(prevTenant);
    }

    log.info("新增租户并自动建管理员, tenantId={}, code={}, adminAccount={}",
             tenantId, tenant.getTenantCode(), account);
    return tenantId;
}
```

`TenantController.insertTenant` 改为调 `insertTenantWithAdmin`，并把前端传来的 `adminAccount` / `adminPassword` 一起接进来（可以放在 `Tenant` 的 `@TableField(exist = false)` 临时字段上，避免改 DTO）。

## 6. 前端改动

**新增两栏（建议放在租户编码之后）**

```html
<div class="form-line"><label>管理员账号</label>
  <input id="adminAccount" placeholder="留空则用联系电话"></div>
<div class="form-line"><label>初始密码</label>
  <input id="adminPassword" placeholder="至少 6 位；生产环境需含大小写+数字+符号"></div>
```

**要点**

1. 账号栏 `onblur` 时若为空，自动填入 `phone`，让用户看到"默认会用手机号"；
2. 密码栏加前端预校验（与 `PasswordPolicy` 同规则），避免提交后才报错；
3. 创建成功后 `alert` 明确回显：「租户已创建，管理员账号：xxx / 初始密码：xxx，请转告客户并提示首次登录修改」；
4. 「编辑租户」时**不要**显示、也不要提交这两栏 —— 否则会被人误以为能改管理员密码。

- [ ] 建租户成功 → `sys_tenant` 有 1 行
- [ ] 同一事务内 `sys_user` 有 1 行：`role=admin`、`status=active`、`tenant_id=新租户id`

- [ ] 故意制造失败（账号已存在 / 密码太弱）→ 报错且 **`sys_tenant` 里没有残留行**
- [ ] `phone` 留空且账号留空 → 明确报错，而不是静默建出"无管理员的租户"
- [ ] 存量租户不受影响（不回填）

## 8. 明确不做的事

| 项 | 结论 |
|---|---|
| 存量租户回填管理员 | **不做**。老租户的联系人未必是真实管理员，批量生成账号风险高；由运营逐个确认 |
| 平台管理员（`tenant_id=0`） | 不适用，本流程只针对租户 |
| 建租户时同时建套餐 | 属于 `PromoService` 的试用逻辑，平台端手工建租户不需要 |
| 修改租户时同步改管理员信息 | 不做。租户联系信息与账号信息是两个概念，改租户不该动账号（要改走用户管理） |
| 自动发短信/邮件通知客户 | 需要短信通道，当前后端无短信端点（`sms_zone` 仅为限流预置），留待后续 |

## 9. 备选方案 B：租户列表加「添加管理员」按钮（半自动）

> 2026-11-22 追加。方案 A（新增租户时自动建管理员）之外的另一种做法：
> 在租户列表每行加一个「添加管理员」按钮，点击后带着**租户编码、联系人、手机号**跳到「用户管理 → 新增用户」，由人确认后保存。

### 9.1 可行性（已逐项验证）

| 前提 | 结论 |
|---|---|
| 能否跨菜单跳转 | ✅ `platform_admin.html:157 switchMenu(key)` → `loadAdminPageContent(key)`，`case "user"` 会调 `renderPlatformUserPage()` 整页重渲染 |
| 弹窗是否依赖当前菜单 | ✅ 不依赖。`createPlatformUserModal()` 把弹窗 `appendChild(document.body)`，`openPlatformAddUser()` 是全局函数，任何菜单下都能调 |
| 现有接口是否够用 | ✅ `POST /user/add` 已支持 `role=admin + tenantCode`（`platform-admin-user.js:236`），**后端零改动** |

实现骨架（`platform-admin-tenant.js`）：

```js
function addAdminForTenant(tenantId) {
  const t = (__tenantCache || []).find(x => x.id === tenantId);
  if (!t) return;
  switchMenu('user');                      // 切到用户管理并完成渲染
  setTimeout(() => {                       // 等 renderPlatformUserPage 完成
    if (typeof openPlatformAddUser !== 'function') return;
    openPlatformAddUser({                  // 需给该函数加可选入参
      tenantCode: t.tenantCode,
      orgName:    t.orgName,
      account:    t.phone   || '',         // 账号默认用手机号
      phone:      t.phone   || '',
      name:       t.contact || ''
    });
  }, 0);
}
```

配套改造 `openPlatformAddUser(prefill)`：有 `prefill` 时把角色默认选为 `admin`、显示租户行、选中对应 `tenantCode`、并回填账号/姓名/手机号/公司名称。

### 9.2 两方案对比

| 维度 | **A：自动创建** | **B：按钮+预填（半自动）** |
|---|---|---|
| 后端改动 | 改 `TenantService` / `TenantController` / `Tenant` 临时字段 | **零** |
| 前端改动 | 表单加「账号/初始密码」两栏 + 预校验 + 结果回显 | 列表加按钮 + `openPlatformAddUser` 支持入参 |
| 上线方式 | 重编译 jar + 重启三服务 + 发 dist | **只发前端 dist** |
| 循环依赖 | ⚠️ **需新建 `TenantProvisioningService`**（见 9.3） | 不存在 |
| `TenantContext` 坑 | ⚠️ 必须 save/restore | 不存在 |
| 密码策略失败 | 整单回滚，用户只看到一句错误 | **当场弹错、可改后重试** |
| 是否真「自动」 | ✅ 是 | ❌ **仍需人点一次保存** |
| 漏做可能 | 无（原子：租户与管理员同事务） | **有**：点了按钮但不保存 → 租户仍然无人 |
| 批量/脚本建租户 | ✅ 天然支持 | ❌ 只能人工逐个点 |
| 可测试性 | 需要后端集成测试 | 手工点一遍即可验证 |
| 长期维护 | 一处逻辑；改密码规则要同步改前端 | 逻辑在"人工操作"里，规则变更无需改代码 |

### 9.3 方案 A 的隐藏成本：循环依赖（本方案文档初版漏写）

```java
// UserService.java:64 —— 用户服务已经依赖租户服务
private TenantService tenantService;
```

若反向在 `TenantService` 里注入 `UserService`，构成 **A ↔ B 循环依赖**。Spring Boot 2.6+ 默认**禁止循环引用**，启动直接失败（`BeanCurrentlyInCreationException`）。

三条出路（按推荐顺序）：

1. **新建 `TenantProvisioningService`**：它同时注入 `TenantService` 与 `UserService`，`TenantController` 改调它。无循环、职责清晰（"开通租户"本就是独立用例）；
2. `@Lazy` 注入 `UserService`：能用，但把问题藏起来，后续易被误改；
3. 在 `TenantController` 里编排：最快，但业务逻辑落到 Controller，与项目现有分层不一致。

这也是方案 B 在工程上的一个实际优势——**它绕开了整块后端风险**。

### 9.4 结论与推荐

**两者定位不同，不是纯替代关系：**

- 需求原文的关键词是**「自动」**（"自动作为该租户的管理员添加到 user 中"）。方案 B **没有消除人工环节**，它只是把「另开菜单、手填 4 个字段」压缩成「一键带参 + 点保存」。如果目标是"建完租户客户就能登录"，B 治不根。
- 但方案 B 的**风险与成本极低**：后端零改动、不碰 `TenantContext`、不碰事务、密码错误当场可见，一天内可上线。
- 方案 B 还有一个 A 不具备的价值：**可作补建/兜底入口**——老租户漏建管理员、管理员账号异常时，都能从租户列表一键跳过去处理。

**推荐组合落地**：

| 阶段 | 做什么 | 理由 |
|---|---|---|
| 第一步 | 先做 **B** | 只发 dist、零后端风险，立刻缓解"建了租户忘了建账号" |
| 第二步 | 再做 **A**（+ 新建 `TenantProvisioningService`） | 让主路径真正原子化；B 保留为补建入口 |

若当前只能选一个：**要"快且稳"选 B，要"真正自动化"选 A**。
