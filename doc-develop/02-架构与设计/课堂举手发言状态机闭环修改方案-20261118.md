## 一、结论先行

你提出的四点（举手后教师高亮批准、批准后显示"发言中"红底、关麦/再点按钮恢复举手、教师再点"已批准"撤销该生举手）**组合起来是一个自洽的三态状态机**，技术上完全可做，改动集中在 8 个文件，**不需要新增接口、不需要改表**。

但**当前代码没有闭环**，差三块：

1. 「发言中」这个态根本不存在，批准后学生按钮仍是「已放下手」（`classroom-student.js:84`）；
2. 学生关麦只改本地轨道，不撤销举手/批准（`classroom-controls.js:126`）；
3. 教师端没有"撤回"动作，服务端也没有"撤回"信令（`ClassroomSignalService.java:103`）。

补完这三块即可闭环。唯一真正的残余风险是**服务端不强制音轨**（P0，见第八节），本次按"软门禁"处理，另附强门禁的选型说明。

## 二、目标状态机

### 2.1 状态定义

服务端只维护两个权威布尔：`handRaised`（是否举手）、`micGranted`（是否已批准发言）。UI 三态由这两个布尔**派生**，不新增存储：

| 派生态 | handRaised | micGranted | 学生按钮 | 按钮样式 | 教师端该行 |
|---|---|---|---|---|---|
| `idle` 可举手 | false | false | 举手 | 常态 | 无按钮 |
| `waiting` 待批准 | true | false | 等待批准 | 黄色高亮 | 「批准开麦」**黄色高亮** |
| `speaking` 发言中 | true | true | 发言中 | **红色底** | 「已批准」绿色，可点撤回 |

> **关键不变式**：`micGranted == true` 必须蕴含 `handRaised == true`。任何撤销举手的路径都必须同时撤销授权；服务端下发状态时也要按此校验（见 4.6）。

### 2.2 迁移表

| # | 起点 | 触发者 | 动作 | 终点 | 服务端动作 |
|---|---|---|---|---|---|
| T1 | idle | 学生 | 点「举手」 | waiting | `hand{raised:true}` → 广播 `hand:state{raised:true}` |
| T2 | waiting | 学生 | 点「等待批准」（放弃） | idle | `hand{raised:false}` → 广播 `hand:state{raised:false}` |
| T3 | waiting | 教师 | 点「批准开麦」 | speaking | `hand:approve{userId,granted:true}` → 校验已举手 → 写 grant → 广播 `mic:grant{granted:true}` |
| T4 | speaking | 学生 | 点「发言中」 | idle | 同 T2，另本地关麦；服务端撤销 grant 并广播 `mic:grant{granted:false,reason:hand_down}` |
| T5 | speaking | 学生 | 关闭麦克风 | idle | 前端调 `cancelSpeaking()`，等同 T4 |
| T6 | speaking | **教师** | **再点「已批准」** | **idle** | `hand:approve{userId,granted:false}` → **撤销 grant + 取消举手** → 广播 `mic:grant{granted:false,reason:teacher_revoke}` + `hand:state{raised:false}` |
| T7 | waiting/speaking | 教师 | 全员静音 | waiting | 撤销全部 grant，广播 `mic:grant{granted:false,reason:mute_all}`，**保留举手** |
| T8 | 任意 | 系统 | 课堂暂停/结束 | idle | 清 grant，广播撤销；结束则清空该 scheduleId 的会话态 |

```
                 ┌──────────── 教师撤回 (T6) ◄───────────────┐
                 │                                            │
  idle ──T1──► waiting ──T3(教师批准)──► speaking ──T4/T5────┤
   ▲             │                          │               │
   └───T2────────┘                          └───────────────┘
```

## 四、后端修改

文件：`api/classroom-service/src/main/java/com/classroom/service/ClassroomLiveState.java`、`ClassroomSignalService.java`

### 4.1 信令协议扩展（向后兼容）

| 信令 | 方向 | 变更 |
|---|---|---|
| `hand {raised}` | 学生 → 服务端 | 不变 |
| `hand:approve {userId, granted?}` | 教师 → 服务端 | **新增可选 `granted`（默认 `true`）**；`false` = 撤回批准并取消该生举手 |
| `hand:state {userId, raised}` | 服务端广播 | 不变；撤回时同样广播 `raised:false` |
| `mic:grant {userId, granted, silent?, reason?}` | 服务端广播 | **新增 `reason`**：`teacher_approve` / `teacher_revoke` / `hand_down` / `mute_all` / `class_end` |

老前端不传 `granted` 时仍按批准处理，**不破坏现有行为**。

### 4.2 `handleHandApprove` 改造

```java
private void handleHandApprove(String scheduleId, String role, JsonNode node) {
    if (!isTeacherOrManager(role)) return;
    String target = node.path("userId").asText(null);
    if (target == null) return;
    boolean granted = node.path("granted").asBoolean(true);
    if (granted) {
        // G4：未举手不批准（迟到的批准直接忽略）
        if (!Boolean.TRUE.equals(liveState.hands(scheduleId).get(target))) return;
        if (liveState.isMicGranted(scheduleId, target)) return;   // 幂等
        liveState.grantMic(scheduleId, target);
        registry.broadcastSignal(scheduleId, grantMsg(target, true, "teacher_approve"));
        teachingSession.appendEvent(scheduleId, "hand_approve", Map.of("userId", target));
    } else {
        // T6：教师撤回 → 撤销授权 + 取消举手，两条广播
        liveState.revokeMic(scheduleId, target);
        liveState.setHand(scheduleId, target, false);
        registry.broadcastSignal(scheduleId, grantMsg(target, false, "teacher_revoke"));
        registry.broadcastSignal(scheduleId, json("hand:state", scheduleId, target, null, "raised", false));
        teachingSession.appendEvent(scheduleId, "hand_revoke", Map.of("userId", target, "by", "teacher"));
    }
}
```

> `json(...)` 已有的工具签名是 `json(type, scheduleId, userId, name, key, value)`；`name` 传 `null` 时需确认该工具能处理空值（当前 `mic:grant` 就是这么用的，安全）。`grantMsg` 是新增的私有小工具，避免两处拼串不一致。

### 4.3 `handleHand` 补事件原因

现有放下手逻辑（`ClassroomSignalService.java:96-101`）已正确撤销 grant 并广播，只需：

- 广播时带 `reason:"hand_down"`；
- 撤销前先判 `isMicGranted` 再广播，保持幂等（已有）。

### 4.4 `handleMuteAll` 撤销全部授权（T7）

```java
if (muted) {
    liveState.revokeAllMicGrants(scheduleId).forEach(u -> {
        registry.broadcastSignal(scheduleId, grantMsg(u, false, "mute_all"));
        teachingSession.appendEvent(scheduleId, "mic_revoke", Map.of("userId", u, "reason", "mute_all"));
    });
}
```
**保留 `handRaised`**——学生回到 `waiting`，教师解除静音后需重新点批准。这样"全员静音 = 收回所有发言权"语义清晰。

### 4.5 `ClassroomLiveState` 新增方法

```java
/** 撤销本课次全部开麦授权，返回被撤销的 userId（供 muteAll / 结束课使用） */
public java.util.List<String> revokeAllMicGrants(String scheduleId) {
    Set<String> s = micGranted.remove(scheduleId);
    return s == null ? java.util.List.of() : new java.util.ArrayList<>(s);
}

/** 清空某课次的全部会话态（课堂结束时调用，避免状态串到下一节） */
public void clearSession(String scheduleId) {
    handRaised.remove(scheduleId);
    micGranted.remove(scheduleId);
    cameras.remove(scheduleId);
    wbGranted.remove(scheduleId);
    whiteboardSnapshot.remove(scheduleId);
    // mute 存库（runtime_state），不在此清理
}
```

> 字段名以文件实际为准；`cameras` / `wbGranted` / `whiteboardSnapshot` 的确切命名需按 `ClassroomLiveState.java` 现有声明对齐。

### 4.6 `pushInitialState` 一致性校验

下发前先裁剪脏数据，保证不变式：

```java
Map<String, Boolean> hands = liveState.hands(scheduleId);
hands.forEach((u, raised) -> send hand:state);
liveState.micGrants(scheduleId).forEach((u, g) -> {
    if (!hands.containsKey(u)) { liveState.revokeMic(scheduleId, u); return; }  // 无举手不发授权
    send mic:grant{granted:true, silent:true};
});
```

### 4.7 课堂结束清理（顺带修 G9）

在结束课（`class-end` 信令处理或 `ClassroomClosingService.closeAfterEnd` 之后）调用 `liveState.clearSession(scheduleId)` 并广播 `mic:grant{granted:false, reason:"class_end"}`。需先确认 `closeAfterEnd` 是否持有 `ClassroomLiveState` 依赖，若无则放在信令层 `case "class-end"` 分支，避免跨服务耦合。

## 六、边界与一致性

| 场景 | 期望行为 | 依赖 |
|---|---|---|
| 刷新 / 重连 | 先收 `hand:state` 再收 `mic:grant{silent:true}`，按钮直接是「发言中」且麦克风打开 | 4.6 |
| 信号丢失 / 乱序 | 任一"撤销"信号（`hand:state false` 或 `mic:grant false`）都清零本地两布尔，幂等 | 5.2、5.3 |
| 全员静音 | 学生回 `waiting`（举手保留），解除后需重新批准；静音期间无法自行开麦 | 4.4、5.1 |
| 课堂暂停/恢复 | 暂停关麦；恢复时学生需仍有授权才恢复麦克风 | 5.1 applyGate |
| 多人同时举手 | 各自独立，教师逐个批准/撤回 | 天然 |
| 多课次 | `scheduleId` 为 `sid~N` 复合键，`liveState` 按课次分桶，互不影响 | 天然 |
| 学生已退房 | 教师的撤回只影响状态表，无副作用 | 天然 |
| 课堂结束 | 清空该课次全部会话态，避免下节课串味 | 4.7 |

## 八、残余风险：服务端不强制音轨（需你拍板）

当前架构是 mesh/P2P，服务端只转发信令，**学生浏览器直接把音轨发给其他端**。因此：

- 本方案做到的是 **"软门禁"**：防误操作、防遗忘、保证多端状态一致；
- 无法防"学生改 JS 直接 `track.enabled=true`"这类绕过。

| 选项 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A. 软门禁（本方案）** | UI + 信令约束，麦克风默认关、未批准开麦有提示 | 0 | **建议先做**，覆盖 99% 课堂场景 |
| B. 接收端过滤 | 学生端收到他人音轨时按 `micGrants` 决定 `audioEl.muted`；每次 grant 变化重新应用 | 中（需在所有 peer 连接处挂钩、需处理迟到 peer） | 若班级有"必须绝对管控"要求再做 |
| C. 切 SFU / TRTC | 服务端 `muteRemoteAudio` 强管控 | 大（媒体架构重写） | 当前不划算 |

**建议**：本次按 A 交付，在文档中明确"发言权为教师端软管控"。后续如遇真实越权诉求，再评估 B。

| 5 | **教师再点「已批准」** | 学生被关麦、按钮回「举手」、✋ 消失；教师按钮回「批准开麦」（不再显示"已批准"） |
| 6 | 撤回后学生再举手 | 教师端显示「**批准开麦**」，**不会**自动批准 |

| 9 | 已批准后刷新 | 按钮是「发言中」红底，麦克风自动开；不弹 toast |
| 10 | 教师全员静音 | 所有发言中的学生被关麦、回「等待批准」；静音期间学生点麦克风被拦 |
| 11 | 解除全员静音 | 学生**不会**自动开麦，需教师重新批准 |
| 12 | 课堂暂停→恢复 | 暂停期间全静音；恢复后未获授权者麦克风保持关闭 |
| 13 | 两个学生同时举手 | 教师可分别批准/撤回，互不影响 |

## 十一、需要你确认的两点

1. **教师按钮文案**：撤回动作是保持「已批准」（hover 提示可点撤回），还是改成「撤回批准」/「已批准 ✕」？
2. **全员静音策略**：静音时是否撤销全部授权（本方案，学生回「待批准」需重新批准），还是保留授权（解除静音后自动恢复发言）？

确认后我按第七节顺序一次改完并编译验证。
