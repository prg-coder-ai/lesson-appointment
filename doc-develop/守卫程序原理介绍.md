# 守卫程序原理介绍

> 生成时间：2026-10-11 00:41　|　最后修订：2026-10-12 23:10（门禁入口搬到版本化路径 + 新增第 15 道 `check:bridge-exports`）
> 适用范围：WorkBuddy 预约系统（api / frontend / miniprogram / shared）

## 一、总体架构：构建期静态门禁（三层）

```
git commit
  └─ tools/git-hooks/pre-commit     ← 门禁入口（**随仓库版本化**，git 经 core.hooksPath 指向它；
       │                              不再是 .git/hooks 下那个未受版本控制的本地副本）
       └─ npm run check:*           ← 15 道守卫的 npm 命令层
            └─ tools/check-*.mjs    ← 守卫本体（Node 静态扫描，不改产物）
```

守卫是**构建期拦截**，不是运行时报错——它拦的全是「不报错、只静默出错」的缺陷类型。紧急跳过必须显式声明环境变量（如 `SKIP_AUTHZ=1 git commit`），钩子注释里写明「不要习惯性跳过」。

### 门禁必须装一次（新克隆 / 新机器）

`core.hooksPath` 是**本地 git 配置**（不入库），所以克隆后要装一次：

```bash
npm run hooks:install     # 等价于 git config core.hooksPath tools/git-hooks
```

- 装完 `git rev-parse --git-path hooks/pre-commit` 应输出 `tools/git-hooks/pre-commit`；
- 用**相对路径**是有意的：git 在「执行钩子时所在目录」解析它，从子目录提交会解析成 `../tools/git-hooks/pre-commit`——各机器/各克隆都可移植，不必写死绝对路径；
- 钩子内部的 `node tools/...` 同样安全：git 始终在**工作树根**执行钩子（已从子目录实测触发全部门禁通过）；
- `git hook run pre-commit` 可手动触发全部门禁且不产生提交，用来验证安装是否生效；
- `tools/git-hooks/*` 在 `.gitattributes` 里锁定 `eol=lf`：本机 `core.autocrlf=true`，不锁的话钩子检出成 CRLF 会被 bash 以 `\r: command not found` 直接崩掉。

> **为什么搬出 `.git/hooks/`**：那个目录不受版本控制，换机器/新克隆即**丢失全部门禁**，而且失效方式是「提交照常成功、毫无提示」——与「守卫是漏配的唯一发现手段」这条项目原则直接冲突。2026-10-12 之前钩子只存在于本机 `.git/hooks/pre-commit`，属典型隐性资产。

## 二、三类守卫原理

### ① 禁形清单型（静态源码扫描）

把领域内已实锤的错误写法编成「禁形清单」，扫描源码**命中即 return 失败**（清单顺序即优先级）。代表：

| 守卫 | 拦什么 |
|---|---|
| `check:result-contract` | `fail(200)` / `success(失败文案)` / 出口 HTTP 映射缺 case 等错误响应契约 |
| `check:global-collide` | 前端顶层标识符不包 IIFE（全局词法冲突=解析期全崩） |
| `check:secret-env` | 密钥硬编码 / Spring 占位符与 env 名词根不一致 |
| `check:tenant-xt` | 租户上下文跨线程丢失 |
| `check:date-contract` | JSON 日期序列化口径漂移 |

### ② 契约登记型（双源比对）

领域规则集中在一个「权威声明源」，守卫比对**声明源 ↔ 实现代码**，两边不一致就红。代表：

- `check:authz`——每个 Controller 端点必须在 `AuthzRules.java` 声明角色（185 端点全覆盖）；因为 SecurityConfig 兜底是 `denyAll()`，漏声明不报编译错、只会在运行期 403，守卫是漏配的唯一自动发现手段；
- `check:ddl-align`——实体字段 vs `api/sql/schema/` DDL 基线，防「改了表忘改实体」或反向漂移；
- `check:status-contract`——状态机契约登记在 `status-contract.json`（登记须理由≥20字），前端/后端/小程序三端状态值比对；
- `check:endpoints`——前端引用的端点常量必须存在；
- `check:cascade`——每个删除/软删除路径必须声明关联子表的处置方式（本项目不用 DB 级联，「新增 delete 忘处置子表」是悬空引用唯一入口）。

### ③ 镜像/产物一致性型（防漂移）

- `check:shared-sync`——小程序镜像的 `shared/` 文件与权威源逐文件比对，改了 `shared/` 不重新 sync 就拒提交；
- `check:itest-sut`——扫 `.git/index` **二进制**验证 itest 运行时生成的 `_sut*` 快照零 git 跟踪 + harness 必须「先删后拷」（防幽灵文件）；
- `check:bridge-exports`——① 生成产物 `shared-domain-bridge.js` 与生成器当前输出逐字节比对，拦「改了 `shared/` 却忘了重跑生成器」；② 逐 domain 核对「源文件导出集合 ↔ 实际挂到 `window.*Domain` 的键集合」，拦「加了导出却忘了补生成器里那份**手工白名单**」；豁免须登记在 `bridge-exports.json`（理由 ≥20 字），且登记表自身的死条目（源已删该导出／实际已挂上 window）也会被判红；
- `check:tz` / `check:scheduler` / `check:actuator`——课次时间 UTC 口径、调度池、Actuator 探针的领域规则钉住。

## 三、守卫本身的可信度工程（反向测试）

守卫自己也是代码，怎么证明「该红的时候真会红」？每道守卫配**反向测试**（`tests/check_*.js`）：

1. 把守卫的输入变异成违规样本（如制造一个 `fail(200)`）；
2. 断言守卫**确实退出非零**；
3. 约束：不用 `spawnSync`（本机 node 子进程会 EBUSY）→ 改**同进程** `import(url + '?t=随机串')` 并拦截 `process.exit`；
4. 多次变异**串行执行**，结束后对守卫文件做 **md5 逐字节校验**，证明测试没有污染守卫本体。

## 四、守卫总表（15 道 pre-commit 门禁 + 1 道手动）

| 领域 | npm 命令 | 领域 | npm 命令 |
|---|---|---|---|
| 授权 | `check:authz` | 调度池 | `check:scheduler` |
| 引用完整性 | `check:cascade` | Actuator | `check:actuator` |
| DDL 对齐 | `check:ddl-align` | 租户跨线程 | `check:tenant-xt` |
| 时区 | `check:tz` | 密钥注入 | `check:secret-env` |
| 错误响应契约 | `check:result-contract` | JSON 日期契约 | `check:date-contract` |
| 前端全局作用域 | `check:global-collide` | 跨端状态契约 | `check:status-contract` |
| 共享源同步 | `check:shared-sync` | itest 快照同步 | `check:itest-sut` |
| 桥接导出对齐 | `check:bridge-exports` | 端点常量（手动/CI） | `check:endpoints` |

> `check:endpoints` **不在 pre-commit 钩子里**：它当前是既有红（`frontend/js/messages-inbox.js` 硬编码 `/api/v1/tenant/list`，该文件注释明写「刻意不进 `shared/apiPaths.js` 以免触发共享桥同步链」），挂进钩子会挡住所有提交。等那处收敛后再入钩子。

## 五、通用实现手法（踩坑沉淀）

- 先 `stripComments` 再判逻辑——注释里的示例代码不能触发误报；
- 正则兼容数组注解（`@PermissionCheck({...})`）与常量引用（如 `ALL_ROLES`）；
- 探测行尾 CRLF/LF 后按原样替换，改完 `grep` 核验；
- **误报比漏报更伤信任**——守卫一旦狼来了几次，用户就会习惯性全跳过，所以宁可少拦不可乱拦。

## 六、一句话总结

**每道守卫 = 一次已经付过学费的事故，固化成「再犯就提交不进去」的机器检查**；权威源唯一、双源比对、反向测试自证、显式跳过，是它的四根支柱。
