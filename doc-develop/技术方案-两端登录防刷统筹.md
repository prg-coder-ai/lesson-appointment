# 技术方案：Web 端与小程序端登录防刷统筹

> 前置篇：《技术方案-小程序登录人机识别》（四层漏斗、威胁模型、评分与挑战协议）
> 本篇解决：Web 端怎么借鉴、两端怎么用**一套**防线而不是两套
> 编制时间：2026-10-22
> 说明：所有现状判断均标注源码位置。核心结论是**守卫收敛在服务端，两端只适配挑战的呈现形态**。

---

## 一、先看清一件事：两端不是两套问题，是同一道闸的两个入口

这一点决定了整个方案的形状。看代码：

**Web 端**（`frontend/js/public/auth.js:34`）

```javascript
function login(data) {
  return request({ url: '/auth/login', method: 'post', data: data, customErrorMsg: false });
}
// 调用处：frontend/login.html:1076  authenticateUser(account, password, { tenantCode, role })
```

**小程序端**（`miniprogram/pages/login/login.js:131`）

```javascript
const res = await login({ tenantCode: finalTenant, account, password, role });
```

**两端打的是同一个 `POST /api/v1/auth/login`，参数结构完全一致 `{ account, password, tenantCode, role }`。**

结论：

> **只要守卫做在服务端 `/auth/login` 这一处，Web 和小程序天然共享防护**。
> 端上唯一需要各自实现的东西，是"需要人机验证时怎么呈现给用户"。

这直接推出统筹的核心原则，也推出一条反例：

| | 做法 | 结果 |
| --- | --- | --- |
| ❌ 错误 | 两端各写一套前端防刷（Web 防连点、小程序防重复提交、各自弹各自的验证码） | 三处逻辑必然漂移；服务端没有拦截，抓包直接绕过 |
| ✅ 正确 | 服务端一个 `LoginGuard` 判"放行/挑战/拒绝"，端上按响应渲染挑战 | 策略只有一份，改阈值不发版；前端只是 UI |

## 二、Web 端比小程序**危险得多**：威胁模型必须分开算

上一篇的结论是"小程序端机器人只能靠真机农场/协议号"。**这个结论对 Web 端完全不成立**——Web 端没有微信身份兜底，密码就是唯一凭证。

| 维度 | 小程序 | Web（frontend） | 差异性质 |
| --- | --- | --- | --- |
| 身份兜底 | `wx.login()` 的 code，**无法凭空伪造** | **无**。密码错就是错 | 根因级差异 |
| 撞库风险 | 低（微信登录无密码） | **高**：`/auth/login` 就是撞库主战场 | 根因级差异 |
| 自动化成本 | 需真机/协议号，成本高 | **Puppeteer/Playwright 十行代码**就能跑 | 数量级差异 |
| 账号枚举 | 无暴露面 | **两个接口都泄露**（见第三节） | Web 独有 |
| 凭证窃取旁路 | storage 沙箱隔离 | localStorage + **无 HttpOnly 的明文 cookie** | Web 独有 |
| 注册入口 | `/auth/wechat-register` | **`/user/register` + 推广建租户表单** | 两端都有 |
| 环境可见性 | `wx.getDeviceInfo` 等，维度有限 | **Canvas/WebGL/字体/时区/`navigator.webdriver`**，维度丰富 | Web 占优 |
| 来源可校验 | Referer 由微信固定注入 | Origin/Referer 可校验，但 `curl` 可任意伪造 | 都不可完全依赖 |

一句话总结这张表：

> 小程序端要防的是"**用真身份批量占便宜**"；Web 端要防的是"**用假凭证批量试密码**"。
> 前者是收益问题，后者是**账号被盗问题**——优先级更高。

所以 Web 端的防护重心不是"滑块"，而是**撞库防御 + 枚举封堵 + 凭证安全**。滑块只是最后一道税。

## 三、Web 端三个已确认的缺口（代码级证据）

### 缺口 1：服务端把"账号不存在"和"密码错误"分开返回

```java
// UserService#login
if (user == null)  return Result.fail(404, "账号不存在");   // 340 / 354 行
if (!pwdOk)        return Result.fail(400, "密码错误");     // 362 行
```

前端确实做了一层遮罩（`auth.js:181`）：

```javascript
// 登录 404（账号不存在 / 密码错误）统一显示固定文案，防止账号枚举
if (err && err.response && err.response.status === 404) throw '账号或密码不正确';
```

**但这层遮罩只骗得过浏览器里的用户，骗不过脚本。** 攻击者直接 `POST /auth/login`，看返回 `code` 是 404 还是 400，就知道账号存不存在——**零成本账号枚举**。

前端那行注释写着"防止账号枚举"，实际上**枚举能力完整地留在接口上**。这是典型的"防护写在看得见的地方"。

### 缺口 2：`/user/account/exist` 是免登录端点

```java
// Controller：GET /user/account/exist?account=xxx
// SecurityConfig.java:166-167      "/user/account/exist", "/api/v1/user/account/exist"
// JwtAuthenticationFilter.java:47  同一对路径
```

四处白名单里都登记了（SecurityConfig / JwtFilter / TenantInterceptor / check-authz）。也就是说**任何人、无需登录、无限次**可以探测任意账号是否存在。前端调用它的是 `auth.js:198` 的 `checkAccountExists`。

这等于官方提供了一台"账号枚举即服务"的机器。配合缺口 1，攻击者连猜都不用猜。

> **处置建议**：这个接口的业务价值是"注册时提示账号已占用"。如果注册流程允许，最干净的做法是**下线它**，让注册冲突在提交时报"账号已存在"（这本来就是一次性的判定）；如果必须保留，至少要给它套同一套频率闸，并允许它返回模糊结果。

### 缺口 3：登录页零前端节流，失败后可以立刻重试

```javascript
// frontend/login.html:1115-1125
} catch (error) {
  loginError.textContent = ...;
  loginBtn.disabled = false;      // ← 立刻恢复可点
  btnText.innerHTML = '登录系统';
  password.value = '';            // ← 只清空密码
}
```

没有失败计数、没有指数退避、没有冷却期、没有挑战。一次失败后再点一次就是一次新的撞库尝试，**脚本可以无限循环**。

对比一下：小程序端 `login.js` 至少还有 `submitting` 状态防误触（虽然那不是安全机制）。**Web 端连误触保护都没有**。

### 附带缺口 4：凭证存放方式让所有登录闸都形同虚设

```javascript
// auth.js:95-131  saveCurrentUserSession
STORE.setItem('token', user.token);
STORE.setItem('refreshToken', user.refreshToken);
STORE.setItem('currentUser', JSON.stringify(currentUser));   // currentUser 里含 token
document.cookie = 'currentUser=' + encodeURIComponent(JSON.stringify(currentUser))
                + ';expires=' + ... + ';path=/';             // ★ 无 HttpOnly / Secure / SameSite
```

`auth.js` 自己在 132-159 行写了一大段 cookie vs localStorage 的安全性对比，结论都写对了：

> cookie：如未设置 HttpOnly，容易被 XSS 窃取…… cookie 用于部分页面切换、tab/iframe 共享
> localStorage：同样易受 XSS 攻击……不建议用于存敏感信息或长久 token

**但代码没有照自己的结论做**：token 同时落在 localStorage 和一个**明文、无 HttpOnly、无 SameSite** 的 cookie 里，且 cookie 里塞的是含 token 的完整 JSON。

这意味着：**任何一处 XSS 就能把长效 refresh token 拿走，攻击者根本不需要"登录"**。所有登录期防刷在这条旁路面前等于零。

> 这一条不是"防刷问题"，但它是**防刷的前提**。防刷方案上线前，建议先把 cookie 里那部分至少去掉 token（`currentUser` 只留展示字段），这是低风险改动。

## 四、统筹原则：四个"一套"，两个"各自"

### 四个必须是"一套"（否则必漂移）

| 项 | 落点 | 为什么必须统一 |
| --- | --- | --- |
| **判定逻辑** | 服务端 `LoginGuardService` | 策略只有一份，改阈值不用发两端的版本 |
| **状态码语义** | `shared/domain/errorCode.js` 的 `resolveResult` | 一个函数改一处，两端同时生效（见第六节） |
| **配置项** | `sys_config`（`SysConfigService.getInt(key, default)`） | 阈值必须能热调，写死等于把调参变成发版 |
| **数据与指标** | `auth_challenge` / `auth_device` / `auth_rate_counter` + 审计 | 两端流量进同一张表才能算总账，否则"两端各看各的"必然互相掩护 |

### 两个必然是"各自"（无法统一，也不该统一）

| 项 | Web | 小程序 |
| --- | --- | --- |
| **挑战呈现** | canvas 滑块 / 点选拼图（DOM + 鼠标/触摸事件） | 自绘 canvas 滑块（`bindtouchmove`），或原生组件 |
| **设备标识采集** | Canvas/WebGL/字体/时区 + `localStorage` 持久化 | `wx.getDeviceInfo` + `wx.getAppBaseInfo` + 服务端 seed |

> 这两项之所以不能统一，是因为**运行环境根本没有共同原语**。硬要抽象成"两端通用指纹组件"，最后会变成一个内部满地 `if (isMiniProgram)` 的怪物。

## 五、统一后的入口矩阵：到底有几个口要守

这是统筹方案最有价值的一张表——**先把口数清楚，才不会漏**。

| # | 入口 | 端点 | 免登录 | 凭证 | 需要的防护层 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **Web 密码登录** | `POST /auth/login` | 是 | 密码 | **全四层 + per-account 计数** | 撞库主战场，优先级最高 |
| 2 | **小程序密码登录** | `POST /auth/login` | 是 | 密码 | 同上 | 同一端点，天然共享 |
| 3 | Web 注册 | `POST /user/register` | 是 | 密码 | 全四层 + 手机号 | `login.html:939` |
| 4 | 小程序微信登录 | `POST /auth/wechat-login` | 是 | code | 频率 + 评分 | openid 天然唯一，压力小 |
| 5 | 小程序微信注册 | `POST /auth/wechat-register` | 是 | code | 全四层 + 手机号 | 刷试用主入口 |
| 6 | **PC 扫码登录** | `GET /auth/wechat/qr` + `qr/status` | 是 | state | **频率（轮询也要限）** | 2s 轮询，`login.html:707` |
| 7 | 推广自助建租户 | `POST /promo/register-tenant` | 是 | 表单 | 已有三闸 + 手机号 | `PromoService#checkRegisterAbuse` |
| 8 | 推广加入租户 | `POST /promo/register-user` | 是 | 表单 | 同上 | |
| 9 | **账号存在性探测** | `GET /user/account/exist` | 是 | 无 | **限流或下线** | 枚举源，见缺口 2 |
| 10 | 刷新令牌 | `POST /auth/refreshToken` | 是 | refreshToken | 频率（防刷新风暴） | 另见 N5 篇的两个疑点 |
| 11 | 绑定微信 | `POST /auth/bind-wechat` | 否 | token | 可不加 | 已有登录态 |
| 12 | 平台/租户自助注册表单 | `login.html` 内 promo 区块 | 是 | 表单 | 同 7 | |

**这张表的用法**：新增任何免登录端点，都要问一句"它在不在这个矩阵里"；不在就补上，然后同步四处白名单（SecurityConfig / JwtFilter / TenantInterceptor / check-authz）——这是项目已有的铁律，防刷新增端点同样适用。

## 六、共享层落点：一个函数改一行，两端同时生效

这是整个统筹方案里**性价比最高的一处**，因为它几乎零成本。

现状：`shared/domain/errorCode.js` 的 `resolveResult` 已经定义了四种结果类型，而且**Web 端已经真的在用**：

```javascript
// frontend/js/public/utility_request.js:319 / 330 / 338
errMsg = window.ErrorCodeDomain.resolveResult(res).message;
```

桥接登记也在（`shared/domain/bridge-exports.json:22` → `{ "file": "errorCode.js", "global": "ErrorCodeDomain" }`）。

于是"需要人机验证"这个新状态，只需要在这里加一个分支：

```javascript
// shared/domain/errorCode.js
export const RESULT_NEED_CHALLENGE = 1002;     // 与服务端 Result.ALLOWED_CODES 对齐

export function resolveResult(res) {
  const code = res && res.code;
  const message = res && (res.message || res.msg) || '';
  if (code === RESULT_OK) return { type: 'ok', message: '', data: res.data, code };
  if (code === RESULT_NEED_CHALLENGE) {
    // ★ 新增：两端共用。Web 弹 DOM 滑块、小程序弹 canvas 滑块，
    //   但"这是挑战、不是错误"这个语义只在这里定义一次。
    return { type: 'challenge', message: message || '请完成安全验证', data: res.data, code };
  }
  if (code === 401) return { type: 'unauthorized', ... };
  if (code === 403) return { type: 'forbidden', ... };
  return { type: 'biz', message: message || '操作失败', data: undefined, code };
}
```

**这一处改完，两端立刻知道"这是挑战而不是错误"**，不会出现"Web 端弹了个红字报错、小程序端 silent catch 掉"这种各自表述的问题。

> 顺带发现一处文档漂移：`errorCode.js:7` 和 `frontend/js/shared-domain-bridge.js:1339` 的注释都写着"Web 端经 P0 构建桥接后可挂 window.ErrorCodeDomain（当前为 P0-Web 阻塞，未接）"，但实际已经接了（utility_request.js 正在调）。**注释比代码旧**，改这个文件时顺手清掉。

### 共享层的四步同步链（必须走，否则两端会不一致）

改动 `shared/domain/errorCode.js` 或 `shared/apiPaths.js` 之后，**必须**依次执行：

```
node tools/sync-miniprogram-shared.js     # 同步到小程序
npm run check:shared-sync                 # 校验两端一致
node frontend/tools/gen-shared-bridge.js  # 重新生成 Web 桥接
node frontend/build.js                    # 重新打包 dist
```

以及：如果新增了共享导出，还要在 `shared/domain/bridge-exports.json` 手工登记（`npm run check:bridge-exports` 会钉住白名单，漏登记就红）。

**这是项目已有的硬约束，防刷新增的共享常量必须走这个流程**，不能直接在小程序和 Web 各写一遍 `1002`。

## 七、双端挑战协议契约（一份协议，两种渲染）

两端呈现不同，但**协议必须完全一致**——这是"一套防线"能成立的技术前提。

### 7.1 请求/响应契约

**① 登录请求（两端同形，加两个可选字段）**

```json
POST /api/v1/auth/login
{
  "account": "xxx",
  "password": "yyy",
  "tenantCode": "abc12345",
  "role": "student",
  "deviceId": "a1b2c3...",      // 新增·可选：端上派生的设备标识
  "clientChannel": "web",       // 新增·可选：web / miniprogram（仅作归因，不做安全判定）
  "challengeId": "9f8e...",     // 新增·可选：上一次响应下发的挑战票据
  "challengeAnswer": { "moveX": 132, "trackPoints": 24, "costMs": 1840 }
}
```

**② 需要挑战的响应（两端同形）**

```json
HTTP 200
{
  "code": 1002,
  "message": "请完成安全验证",
  "data": {
    "challengeId": "9f8e7d6c...",
    "scene": "login",
    "bgImage": "data:image/png;base64,...",     // 背景图
    "pieceImage": "data:image/png;base64,...",  // 缺口块
    "pieceY": 37,                                // 缺口块的纵向位置（前端据此摆放）
    "expireIn": 120                              // 秒
  }
}
```

**注意 `data` 里绝不出现 `targetX`（缺口横坐标）**。这个值只存在服务端，前端如果拿到了，连滑块都不用拖。

**③ 通过后重试**：带 `challengeId` + `challengeAnswer` 再提交一次同样的登录请求。

### 7.2 两端渲染差异对照

| 环节 | Web | 小程序 |
| --- | --- | --- |
| 取背景图 | `new Image().src = bgImage` | `<image src="{{bgImage}}">` |
| 拖拽事件 | `mousedown/mousemove/mouseup`（+ touch 事件给平板） | `bindtouchstart/bindtouchmove/bindtouchend` |
| 绘制 | `<canvas>` 2D 或 CSS `background-position` 平移 | `<canvas type="2d">` + `wx.createCanvasContext` |
| 计时 | `performance.now()` | `Date.now()`（小程序端 `performance` 不可用，注意降级） |
| 提交 | 走 `request()` 封装 | 走 `core/request.js` |
| 失败重试 | 重新请求一次 `/auth/login` | **必须重新 `wx.login()` 拿新 code** 再请求 |

最后一行是小程序独有的坑（上一篇坑 5）：**挑战通过后复用旧 code 会收到 `40163 code been used`**，表现为"滑块明明拖过了还是登不上"。

## 八、Web 端特有的三项加码

### 8.1 加码一：per-account 失败计数（撞库防御的核心，不是 per-IP）

这是很多方案会漏掉的一层。**per-IP 与 per-account 防的是两种完全不同的攻击**：

| 键 | 防什么 | 绕过方式 | 是否必须 |
| --- | --- | --- | --- |
| per-IP | 一台机器打很多账号 | 分布式 IP 池 | 必须 |
| **per-account** | **很多机器打一个账号** | 基本绕不过（账号是固定的） | **必须** |
| per-device | 一台设备换很多账号 | 改机/清缓存 | 建议 |

分布式撞库的典型形态就是"1000 个 IP 各试 3 次同一个账号"——IP 闸完全看不见，只有 per-account 计数能抓住。

```java
// LoginGuardService 增补：按账号维度的失败计数（阶梯退避）
public long recordLoginFail(String accountHmac) {
    int fails = counterMapper.incrAndGet("account", accountHmac, windowStart);
    // 阶梯：1-4 次无延迟，5-9 次 +500ms，10 次以上要求挑战，20 次以上临时锁 15min
    if (fails >= 20) return -1;                       // -1 = 锁定
    if (fails >= 10) return 500L;                     // 返回要求挑战
    if (fails >= 5)  return 500L;                     // 人为延迟
    return 0L;
}
```

三个实现要点：

1. **账号维度必须用 HMAC，不能存明文**。项目已有 `CryptoUtil.searchIndex`（`PromoService` 的手机号闸就在用），直接复用，口径一致。
2. **延迟要加在服务端**（`Thread.sleep` 或异步排队），加在前端等于没加。
3. **锁定状态要按账号 + IP 组合放行**：真实用户的账号被恶意锁定后，用常用设备应该能自解（否则就变成了"攻击者能锁死你的客户"这一新型攻击）。

### 8.2 加码二：响应时序一致化（防时序侧信道）

前面说到要统一 404/400，但**光统一 code 还不够**——如果"账号不存在"直接返回（1ms），"密码错误"要先跑 bcrypt（约 80ms），攻击者用响应时间就能区分两者。

正确做法：

```java
User user = userMapper.getByAccountNoTenant(account);
if (user == null) {
    // ★ 假校验：走一遍同样代价的哈希，让时序一致
    passwordEncoder.matches(rawPassword, DUMMY_HASH);
    auditLog.loginAttempt(accountHmac, "not_found");
    return Result.fail(400, "账号或密码不正确");   // 与密码错误同码同文案
}
```

`DUMMY_HASH` 用一个真实生成过的 bcrypt 串（不能用随机串，`matches` 对格式错误的串会快速返回）。

### 8.3 加码三：Web 端的环境信号更丰富，评分可以更准

| 信号 | 采集方式 | 价值 |
| --- | --- | --- |
| `navigator.webdriver === true` | 直接读 | **自动化框架的强信号**（Puppeteer/Playwright 默认置 true，且难隐藏得干净） |
| Canvas 指纹 | 绘制固定文本 + `toDataURL` 取哈希 | 识别同设备（不同浏览器略有差异，做近似匹配） |
| WebGL renderer | `getParameter(UNMASKED_RENDERER_WEBGL)` | 识别虚拟机/无头环境 |
| 字体列表宽度测量 | 测量若干字体渲染宽度 | 指纹维度 |
| 鼠标/触摸轨迹 | 登录表单内的 `mousemove` 采样 | 真人轨迹有加减速，脚本常是瞬移 |
| `visibilityState` / 焦点事件 | 监听 | 无头环境常不触发 |
| 时区 vs IP 归属 | `Intl.DateTimeFormat().resolvedOptions().timeZone` | 时区与 IP 严重不符 → 代理/农场 |

**但要清醒**：这些都能被绕过，只是提高成本。所以评分里它们只加分，不能单独定生死。

## 九、渠道识别：只用于体验差异化，绝不用于安全降级

服务端有时需要知道"这个请求来自 Web 还是小程序"（为了指标归因、为了下发不同形态的挑战图、为了日志分桶）。四种识别方式：

| 方式 | 可靠性 | 说明 |
| --- | --- | --- |
| **Referer 前缀 `https://servicewechat.com/{appid}/`** | **高** | 小程序请求由微信固定注入，客户端 JS 改不了 |
| 自定义头 `X-Client-Channel` | 低 | 客户端自报，可任意伪造 |
| User-Agent 含 `miniProgram` | 低 | 可伪造 |
| Origin 为自家域名 | 中 | Web 有，但 `curl` 也可设 |

**推荐**：Referer 识别为主 + 自报为辅，两者不一致时**取更严的一档**。

三条必须守住的原则：

1. **绝不能因为"看起来像小程序"就降低防护**。协议号完全能伪造 Referer。
2. **渠道差异只体现在"用哪种 UI"和"指标怎么分桶"**，不体现在"过不过闸"。
3. **客户端自报的 `clientChannel` 只写日志，不参与决策**。

## 十、Web 端落地实现

### 10.1 前端结构（必须遵守项目现有规范）

登录页 `login.html` 有 1488 行，内联 script 里已经堆了登录、注册、扫码、推广建租户四套逻辑。**防刷逻辑绝对不能再塞进去**，理由就是项目自己的铁律：

- 顶层标识符必须包 IIFE（避免全局污染与重名）
- **同文件禁同名函数**（JS 静默覆盖，两类守卫都拦不住）
- 新增文件要走 `frontend/build.js` 打包进 `dist`

所以新建 `frontend/js/public/login-guard.js`：

```javascript
/**
 * 登录人机验证守卫（Web 端 UI 层）
 * 职责单一：识别 code=1002 → 渲染滑块 → 收集答案 → 交回调用方重试
 * 不含任何"是否放行"的判定——判定只有服务端做。
 */
(function () {
  var current = null;   // { challengeId, bgImage, pieceImage, pieceY, expireIn }

  function renderSlider(challenge) {
    return new Promise(function (resolve) {
      // 1. 建立遮罩 + 背景图 + 可拖动的缺口块（DOM 创建，不写死 innerHTML）
      // 2. 监听 mousedown/mousemove/mouseup，同时注册 touch 事件给平板
      // 3. 采样轨迹点（每次 move 记录一次，附带 performance.now()）
      // 4. mouseup 时 resolve({ moveX, trackPoints, costMs })
      // 5. 用户关闭 → resolve(null)，调用方降级为"请稍后再试"
    });
  }

  /**
   * 包装登录调用：自动处理 1002 → 弹滑块 → 带答案重试一次。
   * @param {Function} doLogin  (extra) => Promise<res>，extra 里带 challengeId/challengeAnswer
   * @returns {Promise<res>}   最终登录结果
   */
  window.LoginGuard = {
    wrap: function (doLogin) {
      return Promise.resolve()
        .then(function () { return doLogin({}); })
        .then(function (res) { return res; })
        .catch(function (err) {
          // ★ 关键：challenge 不是"错误"，不能被通用 catch 吞掉
          var r = window.ErrorCodeDomain && window.ErrorCodeDomain.resolveResult(err.body || err);
          if (!r || r.type !== 'challenge') throw err;
          current = r.data;
          return renderSlider(current).then(function (answer) {
            if (!answer) throw new Error('已取消安全验证');
            return doLogin({ challengeId: current.challengeId, challengeAnswer: answer });
          });
        });
    }
  };
})();
```

页面调用处改成：

```javascript
// login.html:1076 原来的 authenticateUser(...) 外面包一层
const user = await window.LoginGuard.wrap(function (extra) {
  return authenticateUser(username.value.trim(), password.value.trim(), {
    tenantCode: ..., role: ..., ...extra
  });
});
```

**注意 `authenticateUser` 内部会把 404 转成字符串抛出**（`auth.js:181`），所以 `LoginGuard` 要么拿到原始 error 对象、要么约定 `authenticateUser` 不再吞掉 `body`。建议微调 `authenticateUser`：把 `err.response.data` 挂到抛出对象的 `body` 上，让上层能判定 `type === 'challenge'`。

### 10.2 服务端骨架（两端共用，与上一篇同构）

```java
@PostMapping("/login")
public Result<HashMap<String, Object>> login(@Validated @RequestBody LoginDTO dto,
                                            HttpServletRequest request) {
    String ip = ClientIpResolver.resolve(request, trustedProxies);
    String accountHmac = cryptoUtil.searchIndex(dto.getAccount());

    // ① 频率闸 + 评分（永不抛异常，内部异常降级放行）
    GuardVerdict v = loginGuard.evaluate(GuardContext.of(ip, dto, request));
    if (v.needChallenge()) {
        return Result.fail(1002, "请完成安全验证");     // data 里带 challenge
    }
    if (v.reject()) {
        auditLog.loginBlocked(accountHmac, ip, v.reason(), v.score());
        return Result.fail(403, "操作过于频繁，请稍后重试");
    }

    // ② 挑战校验（仅当请求带了 challengeId）
    if (dto.getChallengeId() != null
            && !loginGuard.verifyChallenge(dto.getChallengeId(), dto.getOpenid(),
                                           dto.getChallengeAnswer())) {
        return Result.fail(1002, "验证未通过，请重试");
    }

    // ③ 账号维度失败计数（阶梯退避）
    long delay = loginGuard.checkAccountBackoff(accountHmac);
    if (delay < 0) return Result.fail(403, "该账号尝试次数过多，请稍后再试");
    if (delay > 0) sleepQuietly(delay);

    // ④ 走原有登录逻辑（含统一 404/400 与假校验时序一致化）
    return userService.login(dto.getAccount(), dto.getPassword(), resolvedTenantId);
}
```

三个设计约束（与上一篇一致，两端共享）：

1. `evaluate` 内部全 try-catch，**风控挂了必须放行**——不然风控一挂，两端都登不上。
2. `1002` 必须先进 `Result.ALLOWED_CODES`，否则 `fail(1002, ...)` 运行期直接抛异常。
3. 挑战的 `challengeId` 落 `auth_challenge` 表，**该表必须在 `IGNORE_TABLES` 里**（登录端点无租户上下文，否则 `tenant_id = -1`）。

## 十一、不推荐的五件事

1. **两端各写一套验证码/滑块逻辑**。看上去"Web 用现成 jQuery 插件、小程序用原生组件"最省事，结果是策略两套、体验两种、漏洞两处。**服务端协议统一、前端渲染各自，这是唯一解。**
2. **把"是不是小程序"当成安全等级**。Referer 能伪造，协议号满街都是。渠道只决定 UI 形态。
3. **靠 UA 或前端开关做节流**。前端节流只是防误触，不是安全机制；绕过成本为零。
4. **只做 per-IP 限流。** 分布式撞库 1000 个 IP 各试 3 次，IP 闸一次都不触发。
5. **在 Web 端引重型第三方验证码 SDK**。项目前端是零框架 + `build.js` 打包，引一个带全局副作用的 SDK 会撞上"顶层标识符污染"和 dist 体积问题。自研 canvas 滑块 + 服务端出题，两端能共用同一套协议，收益更大。

## 十二、分阶段落地（在上一篇 P0-P3 基础上加 Web 侧任务）

| 阶段 | 服务端（两端共享） | Web 侧新增 | 小程序侧 |
| --- | --- | --- | --- |

## 十四、一句话总结

> **两端不需要"各做一套防刷"，只需要"一套服务端守卫 + 两套挑战皮肤"。**
> 而 Web 端的真实优先级不是滑块，是**封掉账号枚举、统一下失败响应、补上 per-account 撞库计数、别把 token 放在能被 XSS 读走的地方**——
> 这四件事做完，Web 端的安全水位提升幅度远比装一个验证码大。
