# Spring Boot 校内消息中心系统设计与实现报告

## 1. 摘要

本报告基于 Spring Boot 框架，设计并实现一套支撑校内师生交互的消息中心系统。系统覆盖教师 / 管理员与学生的双向业务消息交互，以及系统自动触达的场景类消息交互，具备消息分类管理、即时推送、批量推送、用户消息状态管理（收藏 / 删除 / 已读标记）等完整业务能力。技术方案采用 WebSocket+STOMP 实现即时推送、Redis 实现集群消息广播、MySQL 实现消息持久化，同时整合前期设计的 AES-256-GCM 敏感字段加密方案与前端 CDN 本地化打包方案，保障数据安全与前端资源交付性能。

该系统架构参考业界成熟的 NotifyHub、IMC 通讯中台等开源方案，采用分层领域模型设计，可灵活扩展支持更多消息场景，适合校内高并发消息推送、海量历史消息存储的生产级需求。

## 2. 需求分析

### 2.1 业务场景

本消息中心覆盖校内三类核心消息交互场景，所有场景交互的消息均需纳入消息中心进行统一状态管理和持久化存储。具体场景划分如下：



1. **下行业务消息**：由教师或管理员发起，向单个、多个或全体学生推送作业通知、上课提醒、课堂调整通知等教学类消息。此类消息兼具即时推送和离线触达特性，学生可通过消息中心查看完整历史记录，教师可后台确认消息接收状态[(52)](https://github.com/Jdsb06/SmartCampus)。

2. **上行业务消息**：由学生发起，向指定教师或管理员提交请假申请、作业文件、报修申请、校园咨询等事务类消息。此类消息支持附件传输、状态追踪（已读 / 已回复），教师或管理员可在消息中心进行批量处理或单条回复[(52)](https://github.com/Jdsb06/SmartCampus)。

3. **系统通知消息**：由学校各类业务系统自动触发，向特定用户组或全体用户推送排期更新、资源预订结果、课前签到提示、作业提交截止提醒等系统级消息。此类消息侧重高可靠性投递，需保证用户在即时在线、离线后重新登录等各种场景下必达[(75)](https://github.com/StardustEnigma/NotifyHub)。

### 2.2 功能需求

基于上述业务场景，消息中心需覆盖运营端、用户端、系统端三类角色的功能需求，同时支撑消息从投递、分发、存储到用户端处理的全链路闭环。具体功能需求如下：

#### 2.2.1 消息推送能力

消息推送是系统的核心基础能力，需覆盖多场景投递、高并发集群级投递、多渠道适配、高优先级消息优先投递等核心要求，详细的技术选型依据可参考后续架构设计章节。



* **多场景支撑**：同时支持即时推送、批量推送、离线补偿推送三类投递模式，且每类投递模式都需具备离线消息补偿能力；

* **集群级支撑**：采用分布式架构设计，支持水平扩展，以支撑上万级同时在线用户的高并发消息投递需求[(13)](https://github.com/yangli-stu/quick-notify)；

* **多渠道适配**：优先采用 WebSocket 协议实现全双工通信，支撑上下行业务消息的实时交互；对于部分老旧浏览器不支持 WebSocket 的场景，需提供 SSE 协议作为单向推送降级备选方案[(12)](https://blog.csdn.net/m0_65592409/article/details/151726240)；

* **可观测性**：全链路记录消息的投递状态、发送延迟、用户终端的接收情况，确保推送链路可排查、可审计；

* **流量控制**：在推送下游设置流量削峰、消息去重的规则，避免大量消息涌入导致系统下游负载异常；

* **优先级划分**：将消息划分为高、中、低三个优先级等级，为不同等级消息设置不同的投递流量资源，保证高优先级消息（如课堂调整通知、紧急请假审批）不会被中低优先级消息阻塞[(46)](https://github.com/lvdashuaibi/MsgPushSystem/blob/main/README.md)。

#### 2.2.2 消息中心管理能力

消息中心需提供两类管理后台，支撑不同角色的运营需求：



* **运营管理后台**：提供消息模板管理、消息批量发送、消息投递状态追踪、消息分类及白名单管理能力；同时提供用户组管理、系统消息发送配置、消息统计报表等辅助功能[(44)](https://juejin.cn/post/7662205497018122292)。

* **用户消息后台**：为用户提供消息聚合管理能力，包括消息列表（已读 / 未读分类）、消息收藏夹、回收站、批量已读 / 批量删除操作入口，以及消息筛选 / 搜索功能，支持按消息类型、时间范围、关键词精准定位消息[(43)](https://juejin.cn/post/7663548569471107135)。

#### 2.2.3 消息分类管理

对所有消息采用三级分类体系，实现全链路的分类管理：



* **分类定义**：一级维度按消息发起角色划分，分为 “教师 / 管理员消息”“学生消息”“系统通知” 三类；二级维度按业务场景划分，如教师 / 管理员消息下分作业通知、上课通知等子类；三级维度按消息优先级划分，标注紧急、普通、低优先级。

* **分类应用**：在消息发送阶段，运营端需指定消息的完整分类；消息存储时，将分类信息作为元数据持久化到数据库；用户端可按分类进行筛选、过滤；系统后台可基于分类统计各类消息的发送量、接收率、已读率等运营指标[(44)](https://juejin.cn/post/7662205497018122292)。

#### 2.2.4 用户操作能力

用户需具备对自己接收消息的全生命周期管理能力，所有操作结果需实时同步到用户的所有在线终端：



* 标记单条或批量消息为已读 / 未读；

* 将重要消息收藏至收藏夹，或从收藏夹移除；

* 删除单条或批量消息，删除的消息可在回收站保留一定时长，用户可选择恢复或永久删除；

* 点击消息跳转至对应业务系统的关联详情页面，如请假审批详情、作业提交详情；

* 对于教师 / 管理员发送的作业通知、课堂调整通知等消息，提供 “一键批量催办” 入口，系统将通过推送链路重新推送消息给未读用户[(43)](https://juejin.cn/post/7663548569471107135)。

### 2.3 非功能需求

为保证系统在校园场景下的生产级可用性，系统需满足以下非功能需求：



* **低延迟**：在普通网络环境下，消息从投递到用户终端接收的端到端延迟需控制在 100 毫秒以内；在弱网环境下，需保证消息不丢失、不重复投递[(9)](http://m.toutiao.com/group/7579552339737739814/)；

* **高并发**：支持上万级用户同时在线，单机每秒处理上千条消息投递，集群每秒处理上万条消息投递；支撑全年级学生的批量消息发送，教师批量发送消息时后端不产生同步的长时间阻塞[(6)](https://juejin.cn/post/7527884547536896010)；

* **高可靠**：消息投递过程中不丢失、不重复，保证每条消息至少投递一次，对重复投递的消息自动进行去重处理；服务端对消息进行持久化存储，用户已接收的消息在客户端离线后不会丢失[(11)](https://github.com/jinwovo/realtime-messaging)；

* **高可用**：系统采用无状态设计，支持集群水平扩展，任何一台服务器故障不会影响整个系统的消息投递；客户端在检测到连接异常后，需自动重连，避免局部网络故障导致消息丢失[(73)](https://github.com/dpwgc/imc-message-center)；

* **安全合规**：消息内容及元数据（如发送时间、接收用户 ID）需采用 AES-256-GCM 算法加密存储；使用前期设计的 CDN 本地化方案分发静态资源，避免公共 CDN 带来的流量劫持、资源篡改风险[(65)](https://blog.csdn.net/wzwsq/article/details/135079263)；

* **浏览器兼容**：优先采用 WebSocket 协议实现实时推送，对不支持 WebSocket 的老旧浏览器，需提供 SSE 或短轮询方案作为降级备用，保障用户体验一致[(12)](https://blog.csdn.net/m0_65592409/article/details/151726240)；

* **性能优化**：用户拉取未读消息、加载消息列表首屏时，响应时间需控制在 200 毫秒以内；消息列表滚动加载时，每屏加载时间不超过 100 毫秒[(6)](https://juejin.cn/post/7527884547536896010)。

## 3. 架构设计

### 3.1 技术架构选型

综合校内消息场景的业务需求，以及 Spring Boot 技术栈的成熟度、可扩展性要求，确定核心技术选型如下，选型依据的详细参考资料可查阅后续技术栈说明章节：



| 技术组件      | 选型                              | 核心作用                  | 选型依据                                           |
| --------- | ------------------------------- | --------------------- | ---------------------------------------------- |
| **应用框架**  | Spring Boot 2.7.x/3.x           | 构建整个系统服务              | 成熟度高，内置 Web、WebSocket、数据访问等开箱即用组件，拥有丰富的生态和社区支持 |
| **实时推送**  | Spring WebSocket + STOMP        | 全双工通信，支撑即时消息推送        | 协议轻量，性能开销低，支持集群消息广播，与 Spring Boot 技术栈无缝整合      |
| **单向推送**  | Spring WebFlux + SSE            | 给老旧浏览器做单向推送的降级备选      | 基于 HTTP 协议，无需额外部署，支持自动重连，适配低版本浏览器              |
| **消息队列**  | Redis Pub/Sub + Redis Stream    | 集群消息广播、消息流量削峰         | Redis 基于内存操作，延迟极低，支持消息的持久化与集群高可用，技术栈无需额外整合成本   |
| **数据存储**  | MySQL 8.0+                      | 消息元数据、用户数据持久化存储       | 成熟稳定，支持事务、二级索引、分库分表，满足持久化与高并发查询需求              |
| **缓存管理**  | Redis 6.0+                      | 用户在线状态、未读消息数、离线消息缓存   | 高性能、高可用，支持丰富的数据结构，可支撑海量用户的在线状态存储和查询            |
| **安全加密**  | AES-256-GCM（JDK 原生实现）           | 消息内容敏感字段加密存储          | 算法标准，性能高效，支持完整性校验，与 Spring Boot 技术栈无缝整合        |
| **资源交付**  | CDN 本地化 + frontend-maven-plugin | 静态资源分发，优化访问性能         | 减少服务器带宽消耗，提升资源加载速度，防止公共 CDN 劫持资源               |
| **会话管理**  | Redis + STOMP Broker Relay      | 支撑集群级的 WebSocket 会话共享 | 保障用户在多节点集群场景下的消息可靠性，适配高并发连接场景                  |
| **消息持久化** | MySQL + 离线消息缓存                  | 历史消息存储、离线消息补齐         | 支撑海量消息存储，同时保障用户登录后快速拉取历史消息                     |

技术选型的核心参考依据覆盖开源项目、技术案例、官方文档等权威来源，具体对应关系如下：应用框架选型参考 Spring 官方文档；实时推送、单向推送选型参考 NotifyHub 开源项目、IMC 通讯中台开源项目；消息队列、会话管理选型参考 IMC 通讯中台开源项目、企业级消息中心架构实战文章；数据存储、缓存管理选型参考企业级消息中心架构实战文章；安全加密选型参考前后端混合加密传输与存储方案文章；资源交付选型参考前端 CDN 本地化打包方案文章。

### 3.2 系统架构设计

本系统采用分层六边形架构（端口与适配器架构）设计，将系统内核心业务逻辑与外部技术实现细节分离，保证系统的高内聚、低耦合，同时支持水平扩展。架构设计中，每层都有明确的职责边界和技术组件支撑，参考了 NotifyHub、IMC 通讯中台等业界成熟的消息中心开源架构方案。系统架构分层如下：



```
┌─────────────────────────────────────────────────────────┐

│                      消息中心接入层(Web)                      │

├─────────────────────────────────────────────────────────┤

│  REST API（运管端、用户端）  │  WebSocket/SJS 消息推送接入点 │

├─────────────────────────────────────────────────────────┤

│                    消息核心业务逻辑层（Service）               │

├─────────────────────────────────────────────────────────┤

│  消息发送服务  │ 消息推送服务 │ 消息分类服务 │ 消息状态管理服务 │

│  消息模板服务  │ 消息批量服务 │ 消息收藏服务 │ 消息删除管理服务 │

├─────────────────────────────────────────────────────────┤

│                    消息领域模型层（Domain）                    │

├─────────────────────────────────────────────────────────┤

│  消息实体      │  用户消息状态实体  │ 消息分类实体 │ 消息模板实体 │

├─────────────────────────────────────────────────────────┤

│                    基础设施适配层（Infrastructure）            │

├─────────────────────────────────────────────────────────┤

│  MySQL适配器   │  Redis适配器  │  WebSocket适配器  │  AES加密适配器 │

├─────────────────────────────────────────────────────────┤

│                    第三方服务接入层（Integration）              │

├─────────────────────────────────────────────────────────┤

│  教师/管理员端接入 │  学生端接入  │  业务系统接入  │  其他微服务接入 │

└─────────────────────────────────────────────────────────┘
```

架构的核心设计要点及各层职责如下：



* **消息中心接入层**：作为系统的唯一入口，处理来自运管端、用户端、其他业务系统的所有接入请求，包括 REST API 请求、WebSocket 握手请求、STOMP 消息连接请求和各类资源请求。该层负责对请求进行鉴权、流量控制、协议适配和静态资源分发，然后将请求转发到对应的业务逻辑处理层；响应返回时，统一处理数据加密、序列化等逻辑[(13)](https://github.com/yangli-stu/quick-notify)。

* **消息业务逻辑层**：系统的核心业务层，负责处理消息的发送、批量发送、推送、存储、分类路由，以及用户消息状态管理、权限校验、消息模板处理等核心业务逻辑。该层的所有业务处理逻辑都设计为异步非阻塞模式，以支撑高并发场景；同时对消息流量进行削峰、去重、优先级路由，保障推送链路稳定[(3)](https://github.com/iam-ssrivastav/notification-hub)。

* **消息领域模型层**：定义系统的核心领域模型，包括消息实体、用户消息状态实体、消息分类实体、消息模板实体、用户会话实体，以及数据交互对象（DTO）、查询对象（PO）等。所有核心业务规则都封装在对应的领域实体中，由业务逻辑层调用处理，领域模型层不依赖任何外部技术框架。

* **基础设施适配层**：负责对接外部技术中间件，包括 MySQL、Redis、WebSocket、AES 加密算法等，为上层业务提供统一的数据库访问、缓存操作、消息推送、加密解密等基础能力。该层将技术中间件的细节封装在适配器中，确保核心业务逻辑层不依赖任何特定中间件，后续更换中间件时，只需在适配器层修改配置即可。

* **第三方服务接入层**：负责对接学校内的其他业务系统，如用户中心、业务审批、教学管理、资源预订等系统，提供统一的消息事件订阅、触发接口。接口采用轻量级的设计，支持多协议接入，将外部业务系统的事件数据转换为消息中心内部的领域事件，解耦消息中心与其他业务系统的依赖关系[(74)](https://blog.csdn.net/Mr_hwt_123/article/details/152255851)。

### 3.3 核心流程设计

#### 3.3.1 消息发送与推送流程

消息发送与推送流程采用异步、解耦、分级投递设计，保障消息的可靠投递，支撑高并发场景。教师 / 管理员发送作业通知类消息时的完整流程如下：



1. 教师 / 管理员在运营端通过界面或批量导入接口，创建并发送作业通知类消息。

2. 后端接口层对请求进行合法性校验、权限校验、敏感词过滤，校验通过后将请求转发给消息发送服务。

3. 消息发送服务根据消息的接收用户类型（全体学生、指定学生用户组、单个学生），选择对应的投递策略（广播、分片批量投递、点对点投递）。

4. 消息持久化到数据库的 message 消息主表，同时在 redis 中登记推送日志及消息指纹，防止重复投递。

5. 采用读扩散与写扩散结合的优化策略，将消息写入到用户的收件箱索引表，同时将用户的未读消息计数器增加 1。

6. 消息被投递到 Redis Pub/Sub 集群消息总线，由消息总线广播给所有应用节点的消息推送服务。

7. 消息推送服务接收到事件后，检查接收用户的本地 WebSocket 会话是否存在，若存在则直接推送；若不存在，则将消息缓存到 Redis 的离线消息队列中，等待用户上线后推送。

8. 用户端通过 WebSocket 连接接收到即时消息，或登录后拉取到离线消息，在界面上展示未读消息数、消息推送提示。

9. 用户点击消息后，前端调用接口标记消息为已读，服务端更新数据库的用户消息状态表，并将已读状态同步到用户的所有在线终端；同时，前端通过预先配置的消息跳转规则，跳转到对应的作业列表页面。

10. 整个流程中，所有节点的消息投递状态都将被记录到数据库的消息状态表中，教师 / 管理员可在运营后台的消息追踪功能中，查看每条消息的投递状态、已读用户数、未读用户数。

#### 3.3.2 消息分级 Fan-out 流程

系统采用分级 Fan-out（消息扩散）策略，根据消息的接收用户数量，选择不同的扩散方式，优化系统性能，减少数据库、网络带宽消耗。具体策略如下：



* **点对点投递**：当消息接收用户量在 1000 人以内时，采用写扩散策略，将消息直接写入每个接收用户的收件箱索引表，通过 WebSocket 精准推送给每个在线用户；若用户离线，则缓存到其专属的离线消息队列中。

* **分片批量投递**：当消息接收用户量超过 1000 人时，将用户列表拆分到多个分片并行处理，减少单次数据库长事务锁行的时间。消息内容只存储一份在消息主表，在用户收件箱索引表中仅存储用户与消息的关联关系，以及用户独有的消息状态（如已读、收藏、删除状态）。

* **广播投递**：当消息接收用户量超过 1 万人，或需推送给全体学生、所有教师时，采用读扩散策略，将消息的基本信息存储在公共消息表中，用户读取收件箱时，系统动态将公共消息与用户的私有消息列表合并返回。通过这种方式，避免了大规模写扩散导致的数据库性能瓶颈。

#### 3.3.3 用户连接与离线消息补偿流程

用户连接与离线消息补偿流程，保障了用户在离线、在线、多终端切换等场景下，消息的不丢失、不重复投递。完整流程如下：



1. 用户使用浏览器登录系统，前端与后端建立 WebSocket 连接，连接时携带 JWT 令牌或其他鉴权信息，后端对用户身份进行校验。

2. 后端校验通过后，将用户的会话信息保存到 Redis 的在线用户会话池中，标记用户为在线状态，并订阅用户专属的消息接收队列、消息状态同步队列。

3. 消息中心推送服务，通过用户的在线会话通道，推送用户连接期间产生的新消息。

4. 用户离线时，前端发起正常的 WebSocket 关闭请求，后端将用户的会话信息从在线用户会话池中移除；若用户异常离线（如关闭浏览器、刷新页面、网络断开等），后端会在 1 分钟心跳检测超时后，将用户标记为离线状态。

5. 离线期间，所有发送给用户的消息将被存入 Redis 的离线消息队列中，同时将消息持久化到 MySQL 的消息主表与用户消息状态关联表中。

6. 用户再次登录时，通过连接时的用户标识，触发离线消息补偿流程：服务端从 Redis 的离线消息队列中，拉取用户离线期间的所有未读消息，在连接成功后一次性主动推送给用户；若用户在多个终端同时登录，消息推送服务会将消息同步推送到所有在线终端，保持多端状态一致。

7. 为避免消息堆积占用过多内存资源，离线消息队列设置了最大消息存储条数和消息过期时间；用户离线期间的消息，会在用户登录成功后，在 Redis 中缓存一份消息指纹，用来避免重新推送时的重复消息。

### 3.4 Push 方案设计

综合校内消息推送场景的需求和技术栈的成熟度，系统采用 “WebSocket+STOMP 作为主推送通道，SSE 作为降级备选通道” 的技术方案，适配不同浏览器环境下的实时推送需求。方案设计要点如下：



* **主推送通道**：采用 Spring WebSocket + STOMP 协议，实现浏览器与服务器的全双工通信。服务器端和客户端之间通过 WebSocket 会话，实现双向通信；消息总线通过 Redis Pub/Sub 广播消息，给集群节点的消息推送服务，精准推送给在线用户的 WebSocket 连接。该通道性能开销低，支持集群水平扩展，适合校内高并发实时消息推送场景。

* **降级推送通道**：对不支持 WebSocket 的老旧浏览器，自动切换到 SSE 协议。SSE 基于 HTTP 长连接实现，无需额外部署，具有自动重连、消息传输开销低的优势；服务器端通过 SSE 通道，将消息单向推送给用户。该通道无法实现学生消息的即时上行交互，仅作为接收消息的备选通道。

* **集群会话管理**：所有 WebSocket 连接信息都存储在 Redis 中，实现集群会话共享；使用 STOMP 协议的消息代理，将消息路由到对应节点的用户 WebSocket 连接，保障用户在多节点集群场景下的消息可靠性。

* **连接保活**：前端与后端之间采用心跳机制维持长连接的活性，避免被中间代理服务器关闭。前端每隔一段时间发送一次心跳包，服务器端接收到心跳包后，响应确认包，以此检测连接的健康状态；若心跳包多次发送都无响应，前端会自动触发重连流程，并重连的同时，拉取本地记录的最后一条消息，传入请求参数确认消息的接收情况，通过离线补偿的方式补发期间的漏收消息。

* **消息可靠性保障**：消息推送服务在消息持久化成功后，才会将消息投递到推送通道；用户接收到消息后，会回传一个接收确认包；若服务端在指定时间内未收到确认包，会重新推送消息，直到用户回传确认包；通过为消息设置一个全局唯一的指纹标识，在缓存中记录消息的投递状态，确保消息不会被重复投递；若用户在多个终端同时登录，消息推送服务会将消息同步推送到所有在线终端，保持多端消息状态一致。

## 4. 数据库设计

### 4.1 核心表结构

数据库设计遵循 “基础数据存储、关系索引存储、状态数据存储” 的分离原则，以支撑高并发场景与海量消息存储。核心数据表结构如下：

#### 4.1.1 消息主表（message）

存储所有消息的元数据及业务内容，采用 “垂直分表 + 压缩存储” 设计，将消息的元数据与业务内容分离存储，业务内容采用压缩存储，节省磁盘空间。核心字段：



* message\_id：全局唯一消息 ID，采用雪花算法生成，作为主键。

* sender\_id：发送方用户 ID，如教师 ID、管理员 ID、系统 ID，与用户表的 user\_id 字段关联。

* sender\_type：发送方类型，用于区分消息的发送方角色，如教师、管理员、系统、学生。

* message\_type：消息分类，包括作业通知、上课通知、系统排期更新、请假通知等，与消息分类表的 category\_id 字段关联。

* priority：消息优先级，分为高、中、低三个等级，用于控制投递顺序。

* title：消息标题，用于在消息列表展示。

* content：消息的具体业务内容，采用 AES-256-GCM 算法加密存储。

* is\_broadcast：是否为广播消息，标记消息是否需要推送给全体用户或大规模用户组。

* send\_time：消息的投递时间，即消息中心接收消息请求的时间。

* create\_time：消息的创建时间，即业务系统生成消息的时间。

* update\_time：消息的更新时间，用于追踪消息的投递状态变更。

#### 4.1.2 用户消息索引表（user\_message\_inbox）

作为用户的收件箱索引，采用 “按用户 ID 分表” 设计，将海量用户的消息索引数据分散到多张物理表中，提升用户消息查询性能。核心字段：



* id：自增主键，仅用于物理数据存储。

* user\_id：接收方用户 ID，用于关联用户表的 user\_id 字段，建立索引。

* message\_id：消息 ID，与消息主表的 message\_id 字段关联，建立索引。

* is\_read：阅读状态，0 = 未读，1 = 已读。

* read\_time：阅读时间，用户标记消息为已读的时间。

* is\_starred：收藏状态，0 = 未收藏，1 = 已收藏。

* is\_deleted：删除状态，0 = 未删除，1 = 已删除，删除时不物理删除，仅标记为已删除。

* folder：用户自定义文件夹，用于将消息分类收纳到不同的文件夹中。

* created\_at：消息的接收时间，即用户收到消息的时间。

* updated\_at：状态的更新时间，用于追踪用户对消息的操作记录。

#### 4.1.3 消息分类表（message\_category）

存储消息的分类体系，支撑运营端的分类管理和用户端的分类筛选。核心字段：



* category\_id：分类 ID，主键，采用雪花算法生成。

* category\_code：分类编码，全局唯一，用于程序内部识别分类。

* category\_name：分类名称，如作业通知、上课通知、系统排期更新、请假通知等。

* category\_type：分类类型，用于区分分类的父级分类，与 parent\_id 字段关联。

* parent\_id：父级分类 ID，预留字段，支持多级分类，默认为 0 表示一级分类。

* is\_system\_predefined：是否为系统预定义分类，标记分类是否为系统内置。

* create\_time：分类的创建时间。

* update\_time：分类的更新时间。

* is\_deleted：删除状态，0 = 未删除，1 = 已删除，分类删除时不物理删除，仅标记为已删除。

#### 4.1.4 消息模板表（message\_template）

存储消息模板，用于批量发送消息时快速生成消息内容，模板内容采用 AES-256-GCM 算法加密存储。核心字段：



* template\_id：模板 ID，主键，采用雪花算法生成。

* template\_code：模板编码，全局唯一，用于程序内部识别模板。

* template\_name：模板名称，如作业通知模板、上课通知模板、系统排期更新模板。

* message\_type：消息分类，与消息分类表的 category\_id 字段关联。

* title\_template：消息标题模板，支持占位符填充。

* content\_template：消息内容模板，支持占位符填充。

* sender\_type：发送方类型，标记模板的发送方角色。

* priority：消息优先级，模板默认的优先级。

* is\_enabled：是否启用，标记模板是否可使用。

* create\_time：模板的创建时间。

* update\_time：模板的更新时间。

* is\_deleted：删除状态，0 = 未删除，1 = 已删除，模板删除时不物理删除，仅标记为已删除。

#### 4.1.5 消息投递状态表（message\_delivery\_status）

存储每条消息的实际投递状态，用于消息追踪，以及教师 / 管理员确认消息接收状态。核心字段：



* delivery\_id：投递记录 ID，主键，采用雪花算法生成。

* message\_id：消息 ID，与消息主表的 message\_id 字段关联，建立索引。

* user\_id：接收方用户 ID，与用户表的 user\_id 字段关联，建立索引。

* delivery\_status：投递状态，0 = 未投递，1 = 已投递，2 = 已确认接收，3 = 投递失败。

* channel：投递渠道，如 WebSocket、SSE、离线消息补偿。

* retry\_count：重试次数，记录消息投递的重试次数。

* delivery\_time：投递时间，消息实际投递给用户的时间。

* ack\_time：用户确认接收时间，用户返回接收确认包的时间。

* create\_time：记录的创建时间。

* update\_time：记录的更新时间。

#### 4.1.6 消息批处理任务表（message\_batch\_task）

存储批量发送消息的任务记录，用于追踪批量发送任务的执行状态，以及支撑批量任务的断点续传。核心字段：



* task\_id：任务 ID，主键，采用雪花算法生成。

* task\_name：任务名称，如 “高一一班暑假作业布置通知”。

* message\_id：消息 ID，与消息主表的 message\_id 字段关联。

* sender\_id：发送方用户 ID，与用户表的 user\_id 字段关联。

* total\_recipients：接收用户的总数量，记录批量任务的目标用户数。

* processed\_count：已处理用户的数量，记录任务的执行进度。

* success\_count：成功投递的用户数量，记录任务的执行结果。

* failed\_count：投递失败的用户数量，记录任务的执行结果。

* status：任务状态，0 = 待执行，1 = 执行中，2 = 执行成功，3 = 执行失败。

* execute\_time：任务的开始执行时间。

* finish\_time：任务的执行完成时间。

* create\_time：任务的创建时间。

* update\_time：任务的更新时间。

### 4.2 数据库优化方案

为支撑高并发消息推送和海量消息存储，数据库采用以下优化方案：



* **分库分表**：用户消息索引表按用户 ID 分表，将同一用户的消息索引存储在同一张物理表中，提升用户消息查询性能；消息主表、消息投递状态表按时间范围分表，将过期历史消息归档到单独的物理表，减少单表的数据量，提升查询和写入性能。

* **索引优化**：用户消息索引表建立`user_id`、`user_id + message_id`联合索引，优化用户消息列表的查询性能；消息投递状态表建立`message_id + user_id`联合索引，优化消息投递状态的查询性能；消息主表建立`sender_id + message_type`联合索引，优化发送方消息记录的查询性能。

* **存储优化**：消息内容采用 AES-256-GCM 算法加密存储，同时启用 MySQL 的透明压缩存储功能，减小数据存储体积，提升磁盘 IO 效率；用户消息索引表的 is\_deleted、is\_starred 等常用筛选字段，采用关键字段压缩存储，减少内存占用。

* **读写分离**：采用一主多从的数据库架构，消息写入、更新操作在主库执行；消息查询、读取操作在从库执行，通过数据库中间件自动完成读写分离，提升数据库整体吞吐量。

* **历史消息归档**：定期将用户标记为已删除的消息、已读的历史归档消息移动到归档库中，保持用户消息索引表的热数据量在百万级以内，提升用户常用消息的查询性能。

* **SQL 性能优化**：所有业务 SQL 都通过索引优化，避免全表扫描；复杂的消息查询、统计报表逻辑，通过冗余缓存数据、异步计算的方式处理，避免数据库长时间锁行；采用批量插入、批量更新的方式处理批量消息操作，减少数据库的事务提交次数。

## 5. 接口设计

### 5.1 接口基础规范

系统采用 “REST API + 实时推送接口” 混合的接口设计风格，不同类型接口采用不同的传输与安全规范，保障接口的可用性和安全性。



* **基础域名**：所有接口使用统一的基础域名，与主业务系统的域名保持一致。

* **传输协议**：所有接口通过 HTTPS/WSS 协议传输，保障传输层安全；WebSocket 连接采用 WSS 加密协议，避免传输过程中被窃听。

* **数据格式**：REST API 采用 JSON 格式交互，请求与响应都采用 UTF-8 编码；实时推送的 STOMP 接口采用二进制格式传输，提升解析性能。

* **认证鉴权**：所有接口必须在请求头中携带 JWT 令牌进行鉴权；WebSocket 连接时，令牌必须放在 STOMP 连接请求头中；所有接口都经过权限校验，仅允许指定角色的用户调用。

* **安全加密**：所有接口的请求体、响应体敏感数据，都采用前期设计的 AES-256-GCM 方案加密；静态资源采用 CDN 本地化方案分发，防止公共 CDN 资源篡改。

* **返回规范**：所有接口采用统一的返回格式，包括业务响应码、响应消息、响应数据、请求追踪 ID；接口异常时，返回标准的错误码及错误信息，方便定位问题。

* **流量控制**：对所有接口设置流量控制规则，限制不同角色用户的调用频率，防止恶意调用导致系统负载过高。

### 5.2 核心接口清单

接口设计遵循 “单纯读操作使用 REST API，实时操作使用 WebSocket 协议接口” 的原则，兼顾开发效率和系统性能。核心接口分类如下：

#### 5.2.1 消息推送接口

消息推送接口是系统的核心 API，由业务系统或运营端调用，用于发送各类消息给用户。这类接口采用异步设计，调用后直接返回业务 ACK，由服务端后台执行消息拆分、推送、存储逻辑。



* **发送单条消息**：`POST /api/v1/messages/send` ，支持发送单条消息给指定用户，需要携带消息标题、消息内容、接收用户 ID、消息分类、消息优先级等参数。

* **批量发送消息**：`POST /api/v1/messages/broadcast` ，支持批量发送消息给指定用户组、角色、全年级学生，除基础消息参数外，还需要携带接收用户组类型、接收用户 ID 列表等批量发送参数。

* **发送系统通知**：`POST /api/v1/messages/system` ，供业务系统调用，发送系统类消息，需要携带消息标题、消息内容、接收用户 ID、消息分类、消息优先级等参数。

* **重新推送消息**：`POST /api/v1/messages/{message_id}/retry` ，根据消息的投递状态，对投递失败的用户进行重新推送，需要携带消息 ID、接收用户 ID 列表等参数。

#### 5.2.2 消息中心查询接口

消息中心查询接口供用户端、运营端调用，查询消息列表、消息详情和投递状态数据。这类接口支持分页、按分类筛选、按时间范围筛选、按关键词搜索，返回结果可分页。



* **获取收件箱消息列表**：`GET /api/v1/users/{user_id}/inbox` ，分页获取用户的收件箱消息列表，支持按分类、未读 / 已读状态、关键词筛选，返回消息列表、消息未读数、消息总数等数据。

* **获取已收藏消息列表**：`GET /api/v1/users/{user_id}/starred` ，分页获取用户收藏的消息列表，支持按分类、关键词筛选，返回消息列表、收藏消息总数等数据。

* **获取已删除消息列表**：`GET /api/v1/users/{user_id}/deleted` ，分页获取用户标记为已删除的消息列表，支持按分类、关键词筛选，返回消息列表、已删除消息总数等数据。

* **获取消息详情**：`GET /api/v1/users/{user_id}/messages/{message_id}` ，获取用户的单条消息详情，返回消息的元数据、业务内容、投递状态、用户操作记录等数据。

* **获取批量发送任务状态**：`GET /api/v1/messages/batch/{task_id}` ，获取批量发送任务的执行进度、投递结果，返回任务的总用户数、已处理数、成功数、失败数等数据。

* **获取消息投递状态**：`GET /api/v1/messages/{message_id}/delivery-status` ，获取单条消息的所有用户投递状态，返回消息的投递记录、用户接收状态等数据。

#### 5.2.3 用户操作接口

用户操作接口供用户端调用，处理单条或批量消息的状态变更操作。这类接口采用幂等设计，重复调用不会造成数据异常，所有操作都被记录在日志中，可被审计追踪。



* **标记消息为已读**：`POST /api/v1/users/{user_id}/messages/{message_id}/read` ，标记单条消息为已读。

* **标记消息为未读**：`POST /api/v1/users/{user_id}/messages/{message_id}/unread` ，标记单条消息为未读。

* **批量标记消息为已读**：`POST /api/v1/users/{user_id}/messages/read/batch` ，批量标记多条消息为已读。

* **收藏消息**：`POST /api/v1/users/{user_id}/messages/{message_id}/star` ，将消息添加到用户收藏夹。

* **取消收藏消息**：`POST /api/v1/users/{user_id}/messages/{message_id}/unstar` ，将消息从用户收藏夹移除。

* **删除消息**：`DELETE /api/v1/users/{user_id}/messages/{message_id}` ，将消息标记为已删除。

* **批量删除消息**：`DELETE /api/v1/users/{user_id}/messages/batch` ，批量删除多条消息。

* **恢复已删除消息**：`POST /api/v1/users/{user_id}/messages/{message_id}/restore` ，将已删除的消息从回收站恢复到原文件夹。

#### 5.2.4 消息分类管理接口

消息分类管理接口供运营端调用，管理消息的分类体系，支持分类的 CRUD 操作。



* **创建消息分类**：`POST /api/v1/message-categories` ，创建新的消息分类。

* **更新消息分类**：`PUT /api/v1/message-categories/{category_id}` ，更新已有的消息分类。

* **删除消息分类**：`DELETE /api/v1/message-categories/{category_id}` ，删除消息分类。

* **获取消息分类列表**：`GET /api/v1/message-categories` ，分页获取所有消息分类列表，支持按分类名称搜索。

* **获取消息分类详情**：`GET /api/v1/message-categories/{category_id}` ，获取单条消息分类的详情。

#### 5.2.5 消息模板管理接口

消息模板管理接口供运营端调用，管理消息的模板体系，支持模板的 CRUD 操作。



* **创建消息模板**：`POST /api/v1/message-templates` ，创建新的消息模板。

* **更新消息模板**：`PUT /api/v1/message-templates/{template_id}` ，更新已有的消息模板。

* **删除消息模板**：`DELETE /api/v1/message-templates/{template_id}` ，删除消息模板。

* **获取消息模板列表**：`GET /api/v1/message-templates` ，分页获取所有消息模板列表，支持按模板名称、消息分类搜索。

* **获取消息模板详情**：`GET /api/v1/message-templates/{template_id}` ，获取单条消息模板的详情。

#### 5.2.6 实时推送接口

实时推送接口供前端通过 STOMP 协议调用，实现消息的即时推送、未读消息数同步、已读状态同步。



* **消息接收端点**：`/user/queue/notifications` ，用户订阅该端点，接收实时推送的消息。

* **未读消息数同步端点**：`/user/queue/unread-count` ，用户订阅该端点，接收未读消息数的实时变更通知。

* **广播消息端点**：`/topic/notifications` ，用户订阅该端点，接收全局广播的实时消息。

* **消息状态同步端点**：`/user/queue/status` ，用户订阅该端点，接收消息的已读、收藏、删除状态变更通知。

### 5.3 实时消息格式

实时推送的消息采用 JSON 格式，与 REST API 的响应格式保持一致，包含消息的元数据和业务内容。推送的消息格式定义如下：



```
{

&#x20; "msg\_id": "消息ID",

&#x20; "send\_id": "发送方用户ID",

&#x20; "send\_type": "发送方类型",

&#x20; "msg\_type": "消息分类",

&#x20; "priority": "消息优先级",

&#x20; "title": "消息标题",

&#x20; "content": "消息内容",

&#x20; "is\_broadcast": "是否为广播消息",

&#x20; "send\_time": "消息投递时间",

&#x20; "recv\_time": "消息接收时间",

&#x20; "payload": {

&#x20;   "跳转地址": "消息对应的业务链接地址",

&#x20;   "其他元数据...": "..."

&#x20; }

}
```

其中，payload 字段为消息的业务自定义附加数据，用于保存图文消息的图片地址、消息的跳转目标业务地址等附加元数据，由前端负责解析和渲染。

## 6. 前端设计

### 6.1 前端架构

前端采用 “CDN 静态资源本地化 + 模块化开发” 的架构，保障系统的性能、可维护性，以及离线场景下的可用性。架构设计要点如下：



* **技术框架**：采用 Vue 3、React 18 或其他主流前端框架，配合 TypeScript 开发，利用组件化、模块化的特性，提升代码的复用性和可维护性；采用 Element Plus、Ant Design Vue 等组件库快速搭建界面，适配 PC 端和移动端的多场景需求。

* **资源本地化**：采用前期设计的 frontend-maven-plugin 方案，将所有前端依赖的 JS、CSS、字体等静态资源，统一从外部 CDN 迁移到本地或企业内部 CDN；所有资源添加内容指纹并设置强缓存策略，保证资源的加载性能和安全性，防止外部 CDN 劫持或资源篡改。

* **推送接入**：优先采用 STOMP 协议封装的 WebSocket 连接，与后端进行实时消息交互；对不支持 WebSocket 的老旧浏览器，自动降级为 SSE 协议。

* **状态管理**：采用 Pinia 或 Redux 作为全局状态管理库，管理用户的会话连接、消息列表、未读消息数、消息分类、用户消息状态等全局状态；消息列表采用规范化的方式存储，避免重复数据，提升组件渲染性能。

* **路由设计**：采用前端路由的方式，实现消息中心、消息分类、消息详情、收藏夹、回收站之间的无刷新切换；路由采用懒加载的方式，优化首屏加载性能。

* **构建优化**：采用 Webpack 或 Vite 作为构建工具，启用 Tree-Shaking、代码分割、压缩混淆等优化措施，减小代码体积；将公共依赖库、业务代码分别打包，利用浏览器的缓存特性，提升后续页面访问速度；所有静态资源添加内容指纹，设置强缓存策略，保证资源的加载性能。

* **多端适配**：采用响应式设计，适配 PC 端、平板端、移动端等不同屏幕尺寸，保持多端体验一致。

### 6.2 核心功能实现

### 6.2.1 消息中心展示

消息中心前端界面，是用户处理各类消息的核心入口。核心功能实现如下：



* **消息中心入口**：在系统的顶部全局导航栏，显示消息中心入口和未读消息总数；未读消息总数采用未读红点 + 数字角标样式，实时更新。用户点击入口后，弹出消息中心面板，展示最新的未读消息预览和消息分类筛选标签。

* **消息列表展示**：消息中心采用收件箱浏览模式，按消息发送时间倒序展示，优先展示未读消息、最新消息；列表项展示消息的发送方、标题、摘要、发送时间、是否收藏等标记，区分未读、已读、已删除消息的视觉样式。

* **消息分类筛选**：提供消息分类筛选标签，支持按消息类型、优先级、发送时间筛选消息；提供搜索框，支持按消息标题、内容关键词搜索消息。

* **消息详情查看**：用户点击消息列表项后，在弹窗或新页面中展示消息详情；详情页展示消息的完整内容、发送方、发送时间、接收时间、用户操作记录；有关联业务的消息，提供跳转按钮，点击后跳转到对应的业务系统详情页面。

* **消息操作管理**：支持用户在消息中心对消息进行批量已读、批量删除、批量收藏等操作；提供右键快捷操作菜单，对单条消息进行已读 / 未读、收藏 / 取消收藏、删除、恢复、永久删除等操作。

* **消息内容渲染**：消息内容支持渲染文本、图片、文件、链接、表情等多种内容格式；支持点击图片预览、点击文件跳转下载地址；所有的消息内容展示区，都需要对消息内容进行安全过滤，防止 XSS 攻击。

* **多文件夹管理**：提供文件夹管理功能，支持用户将消息分类收纳到不同的文件夹中；系统默认提供 “收件箱”“已收藏”“回收站” 三个基础文件夹，支持用户自定义新建、编辑、删除文件夹。

#### 6.2.2 即时推送实现

前端是消息推送的消费端，负责建立和维护与后端的长连接，实时接收并展示消息。核心流程实现如下：



* **连接建立**：用户登录系统后，前端根据浏览器的支持能力，优先建立 WebSocket 连接，或降级建立 SSE 连接；连接时携带 JWT 令牌进行鉴权，标识用户身份。

* **连接订阅**：连接建立成功后，前端订阅用户专属的消息接收端点、未读消息数同步端点、广播消息端点，以及消息状态同步端点；同时，将用户的最后一条消息的 ID 传递给后端，用于增量同步离线消息。

* **消息接收**：前端监听推送端点的消息回调，接收到新消息后，将消息按分类存入全局状态管理的消息列表中，更新未读消息数；同时，触发消息提示，在界面展示新消息的预览内容。

* **消息离线补偿**：前端在建立连接时，将本地存储的最后一条消息的 ID 或时间戳传给后端；后端根据该信息，判断用户是否有离线消息，若有则主动推送给前端；前端将离线消息合并到消息列表中，保持本地消息状态同步。

* **连接保活**：前端采用心跳检测 + 自动重连的连接保活机制，每隔一段时间发送一次心跳包给后端，维持长连接的活性；若心跳包多次发送都无响应，前端会按间隔时间递增的策略，自动触发重连流程；重连成功后，重新订阅消息端点，同步连接期间的离线消息和未读消息状态。

* **消息展示**：接收到新消息后，前端通过角标震动、文字高亮、声音提示、浏览器通知等方式提醒用户；消息列表采用虚拟滚动技术，在不影响滚动性能的前提下，支撑同时渲染上万条消息记录。

#### 6.2.3 用户操作实现

用户在消息中心的所有操作，都需要与后端进行交互，同步操作状态；操作结果需要实时同步到用户的所有在线终端。核心操作流程如下：



* **标记已读 / 未读**：用户标记消息为已读或未读时，前端调用对应的状态更新接口，将消息 ID、用户 ID、目标状态传给后端；后端更新数据库状态并返回成功响应后，前端更新本地消息列表的对应消息状态；随后，前端通过消息状态同步端点，将状态变更通知同步到用户的所有在线终端。

* **收藏 / 取消收藏**：用户收藏或取消收藏消息时，前端调用对应的状态更新接口，将消息 ID、用户 ID、目标状态传给后端；后端更新数据库状态并返回成功响应后，前端更新本地消息列表的对应消息状态；随后，前端通过消息状态同步端点，将状态变更通知同步到用户的所有在线终端。

* **删除 / 恢复**：用户删除或恢复消息时，前端调用对应的状态更新接口，将消息 ID、用户 ID、目标状态传给后端；后端更新数据库状态并返回成功响应后，前端从本地消息列表中移除对应消息，或移动到对应的文件夹中；随后，前端通过消息状态同步端点，将状态变更通知同步到用户的所有在线终端。

* **批量操作**：用户进行批量已读、批量删除、批量收藏等操作时，前端将选中的消息 ID 列表组装成请求，调用对应的批量接口；后端批量更新数据库状态并返回成功响应后，前端批量更新本地消息列表的对应消息状态；随后，前端通过消息状态同步端点，将状态变更通知同步到用户的所有在线终端。

* **同步操作状态**：用户在多端登录时，其中一端的消息操作状态变更，需要通过实时推送通道，同步给其他端；其他端接收到同步状态通知后，主动调用消息列表刷新接口，拉取最新的消息状态，保持多端状态一致。

### 6.3 静态资源部署

前端静态资源采用 “本地化存储 + CDN 分发” 的优化方案，保证资源的加载性能和安全性。方案细节如下：



* **资源本地化**：使用 frontend-maven-plugin 插件，将所有前端依赖的 JS、CSS、字体等静态资源，从外部 CDN 下载到本地项目的`src/main/resources/static/lib`目录；随后，由 Maven 插件将资源统一打包到项目的 Jar 包中，避免使用外部公共 CDN，防止资源被篡改或网络劫持。

* **资源部署**：项目打包时，本地的静态资源会被统一打包到 Jar 包中；部署时，将 Jar 包中的静态资源目录，同步到企业内部 CDN 的源站；然后，通过 CDN 的边缘节点，将资源分发到全国各地的节点，实现用户就近访问，提升资源加载速度。

* **资源匹配**：页面中所有静态资源的引用地址，都替换为内部 CDN 的自定义域名地址；资源路径采用内容指纹的方式，对资源进行版本管理，解决 CDN 资源缓存更新问题。

* **缓存策略**：静态资源采用强缓存策略，资源的 HTTP 响应头设置长期的过期时间；资源更新时，通过更新资源路径的指纹，强制用户加载最新版本的资源。

* **资源更新**：采用 CDN 的自动刷新机制，配合项目的 CI/CD 流程，在部署新版本时，自动刷新 CDN 的旧资源缓存，保证用户访问到最新的资源。

## 7. 安全方案

本系统在传输层、应用层、存储层三个维度同时部署安全措施，结合前期设计的 AES 加密方案与 CDN 本地化方案，形成全链路安全防护体系。

### 7.1 传输层安全

传输层采用多重加密方案，保障所有数据在传输过程中的机密性和完整性。



* **全链路加密传输**：系统的所有接口，包括 REST API 接口、WebSocket 接口、静态资源访问接口，全部采用 HTTPS/WSS 加密协议传输，禁止使用 HTTP/WS 明文协议；服务器端配置 SSL 证书，采用 TLS 1.3 加密协议，使用安全的加密套件，保障传输层数据安全。

* **接口安全校验**：所有接口必须在请求头中携带 JWT 令牌进行鉴权，WebSocket 连接时，令牌必须放在 STOMP 连接请求头中；令牌有效期设置较短，且必须通过 HTTPS 传输，避免被窃取；接口采用请求参数签名校验机制，防止恶意用户篡改请求参数；接口采用统一的流量控制策略，限制用户的调用频率，防止被恶意调用。

* **WebSocket 信道安全**：WebSocket 连接必须采用 WSS 加密协议，连接时进行鉴权和路由校验；消息传输过程中，采用随机数 + 时间戳的方式，防止重放攻击；设置消息体的最大大小，限制消息内容的最大长度，防止被恶意用来传输大文件；对 WebSocket 连接的跨域请求，采用白名单机制，仅允许配置的前端域名连接。

* **静态资源安全**：采用本地化的 CDN 方案，将所有静态资源存放在企业内部 CDN 中；配置资源的跨域白名单、资源的防盗链规则，以及资源的安全传输规则；禁止使用外部公共 CDN，防止资源被篡改或网络劫持；对所有静态资源文件，添加内容指纹，设置强缓存策略。

### 7.2 应用层安全

应用层采用多种防护手段，保障业务逻辑的安全。



* **身份认证与权限校验**：系统采用统一的用户中心进行身份认证；所有接口、WebSocket 连接，都需要携带合法的 JWT 令牌，校验用户的登录状态；基于 RBAC 角色权限控制体系，对所有接口、用户可执行的操作进行精细的权限校验，不同角色的用户，仅能在自己的权限范围内进行操作；对所有的批量发送、消息配置变更操作，进行二次身份校验。

* **数据脱敏**：教师 / 管理员端、学生端的所有敏感数据，在输出到前端之前，都采用脱敏规则进行处理；如消息内容中的手机号、邮箱、身份证号等隐私信息，在前端展示时，将部分字符替换为星号。

* **操作审计**：记录所有用户的所有消息操作日志，包括发送消息、标记已读、收藏消息、删除消息、批量发送消息等；日志中记录操作人、操作时间、操作 IP、操作内容、操作结果，以及用户代理信息；日志采用加密存储，长期归档，支持日后审计追踪；对所有的消息批量发送、消息配置变更、用户状态变更等重要操作，记录完整的操作日志，同时将操作结果发送给管理员进行审计。

* **业务安全校验**：对所有消息内容，进行敏感词过滤、XSS 过滤、SQL 注入过滤；限制消息标题、消息内容的最大长度，以及批量发送消息的单次最大接收用户数量；对消息的发送方、接收方进行身份校验，确保发送方拥有对应的消息发送权限；对批量发送任务，进行发送频率限制，限制用户单日可发送的消息量；对所有的消息接收用户，进行合法性校验，确保不向无效用户发送消息；消息的跳转地址，必须经过白名单校验，仅允许跳转到企业内部的业务系统地址。

* **消息防篡改**：使用 HMAC 算法，为每条消息生成唯一的完整性校验指纹；指纹在消息生产时生成，存入数据库 message 表中；在用户读取消息时，服务端先重新计算指纹，再与存储的指纹进行比对，若不一致则说明消息已被篡改；消息的业务内容、元数据，都进行完整性校验，防止消息被恶意篡改。

### 7.3 存储层安全

存储层采用前期设计的 AES-256-GCM 加密方案，对所有敏感数据进行加密存储。



* **敏感数据加密存储**：消息中心的所有业务数据，包括消息内容、消息标题、用户的隐私信息、消息的附加元数据，以及所有的消息模板内容，都采用前期设计的 AES-256-GCM 方案进行加密存储；加密密钥通过配置中心或环境变量注入，不能硬编码到配置文件中；数据库的加密密钥，采用密钥管理服务（KMS）进行保管，密钥定期更换，即使数据库数据被泄露，攻击者也无法解密获取明文数据。

* **加密机制增强**：AES 加密时，采用密码块链（CBC）模式，配合 128 位的随机初始化向量（IV），保证相同的明文加密后，得到的密文不同；为每条消息，生成唯一的 IV，与密文一起存入数据库；加密后的消息内容，采用 Base64URL 编码后存储；使用 GCM 模式，对消息的完整性进行校验，确保消息在存储、传输过程中未被篡改；所有的加密、解密操作，都在服务端的内存中进行，不会在磁盘上残留明文数据。

* **数据库防护**：数据库采用白名单机制，仅允许应用服务器的 IP 地址连接；数据库账号采用强密码策略，且定期更换；数据库的操作日志，独立存储在日志服务器中，且长期归档，用于审计追踪；数据库启用透明数据加密（TDE），对数据文件、备份文件进行加密存储；数据库的备份数据，采用加密存储，且定期进行恢复性验证。

* **密钥管理**：采用密钥管理服务（KMS），对所有的加密密钥进行统一管理，包括密钥的生成、存储、分发、轮转、销毁等操作；应用服务器，通过 KMS 接口，获取加密密钥，密钥不会在应用服务器磁盘上落地；密钥定期自动轮转，降低密钥泄露的风险；对所有的密钥使用操作，进行日志审计，记录密钥的使用时间、使用人、使用目的、使用结果。

### 7.4 防垃圾与防滥用

系统采用专门的防护方案，防止被恶意滥用发送垃圾消息。



* **发送策略限制**：对不同角色的用户，设置不同的消息发送频率限制，限制其在指定时间内，最多发送的消息数量；对批量发送消息的接收用户数量，设置上限，限制单次批量发送的用户数量；对消息的发送内容，进行长度限制、重复内容校验，防止被恶意用来发送大量垃圾消息；对所有消息的发送方、接收方，进行用户等级校验，限制低等级用户的发送权限。

* **消息审核机制**：运营端提供消息审核功能，教师 / 管理员发送的批量消息，需要先由指定的管理员角色用户审核通过后，才能正式投递；审核时，校验消息的接收用户、消息标题、消息内容、消息附件等内容，是否符合规范；对系统预定义的消息模板，提供内容审核配置，限制模板中可填写的内容范围；对所有的消息投递任务，进行投递前的内容安全校验，防止发送违规内容。

* **垃圾消息过滤**：对所有发送的消息，进行内容安全检测；使用关键词库、语义分析、机器学习分类检测等技术，识别垃圾消息、骚扰消息、广告消息、违规内容；对识别为垃圾消息的内容，直接拦截，或标记为待人工审核；对被多次投诉的消息，自动标记为垃圾消息，直接拦截投递；对异常的批量发送行为，比如短时间内发送大量相似内容的消息，系统自动触发人工审核流程。

* **黑名单管理**：提供发送黑名单管理功能，将违规发送消息的用户加入黑名单，禁止其继续发送消息；提供接收黑名单管理功能，将不接收消息的用户加入接收黑名单；对所有被加入黑名单的用户，记录其加入原因、加入时间、操作人，以及黑名单的有效期；对黑名单的操作，进行日志审计，用于追踪。

## 8. 部署与运维方案

### 8.1 部署架构

系统采用独立部署架构，与学校的其他业务系统物理隔离，通过统一的接入层，与其他业务系统进行交互。



* **部署拓扑**：采用 “应用节点 + Redis 集群 + MySQL 集群” 的典型三层架构，所有组件都部署在学校内部私有云或物理服务器上；应用节点部署多个实例，前端通过负载均衡设备，进行流量分发，实现高可用；Redis 集群采用主从复制 + 哨兵模式，保证高可用；MySQL 集群采用一主多从的读写分离架构，保证高可用。

* **负载均衡**：在应用层前面，部署四层负载均衡和七层负载均衡；四层负载均衡，分发 WebSocket 连接的流量；七层负载均衡，分发 REST API 请求、静态资源请求；负载均衡设备，支持 SSL 卸载，支持配置 Https、Wss、Http、Ws 的转发规则；负载均衡设备，具备健康检查能力，自动将异常的应用节点从集群中摘除，保证用户请求不转发到异常节点。

* **静态资源部署**：将打包后的静态资源，上传到内部 CDN 的源站；然后，通过 CDN 的边缘节点，分发到全国各地的节点；用户就近获取资源，提升资源加载速度；CDN 配置资源的缓存规则、缓存过期时间，以及资源的防盗链规则。

* **集群支持**：应用节点采用无状态部署，可横向扩展，支撑更多用户的并发连接；所有应用节点，连接到同一个 Redis 集群，通过 Redis Pub/Sub，实现消息的集群广播，将消息分发到所有节点的用户；Redis 集群，采用主从复制 + 哨兵模式，保证高可用；MySQL 集群，采用一主多从的读写分离架构，保证高可用；应用节点的会话信息，存储在 Redis 集群中，用户的连接请求，可在任意应用节点上复用。

* **资源本地化部署**：使用 frontend-maven-plugin 插件，将所有前端依赖的静态资源，统一下载到本地项目的`src/main/resources/static/lib`目录；然后，由 Maven 插件，将资源统一打包到项目的 Jar 包中；部署时，将 Jar 包中的静态资源目录，同步到内部 CDN 的源站；再通过 CDN 的边缘节点，将资源分发到全国各地的节点。

### 8.2 运维管理

系统提供多种运维手段，保障系统的稳定运行，以及快速排查、定位问题。



* **日志收集与分析**：系统采用 ELK 技术栈，收集所有应用节点的所有日志，包括运行日志、访问日志、消息投递日志、用户操作日志、连接日志、异常日志等；日志中记录请求的唯一标识，配合链路追踪，可串联整个请求的处理流程；日志采用结构化的 JSON 格式存储，支持全文检索、条件筛选；对所有的错误日志、慢日志、异常日志，设置告警规则，实时通知运维人员。

* **消息链路追踪**：基于 SkyWalking 或 Pinpoint 等 APM 工具，实现全链路追踪；从用户发起请求、建立连接，到后端的消息接收、存储、推送，再到用户端的消息接收，全链路采集追踪数据；采集每个环节的执行耗时、执行结果、异常信息，以及消息的投递状态；通过追踪数据，运维人员可以快速定位消息的投递瓶颈，排查消息异常的原因。

* **监控告警**：采用 Prometheus + Grafana，搭建监控告警体系；采集系统的基础指标、JVM 指标、数据库指标、Redis 指标、消息推送指标，以及连接数、消息总数、消息投递延迟、消息投递成功率、消息推送流量等核心业务指标；在 Grafana 中，搭建核心的监控大盘，展示系统的实时运行状态；对所有的核心指标，设置合理的告警规则；通过邮件、短信、企业微信等渠道，将告警信息实时通知给运维人员。

* **消息运维能力**：提供消息的查询、补发、重发、撤回、归档能力；运维人员可根据消息 ID、用户 ID、消息状态、投递状态，查询消息的投递情况、详细内容，以及用户的接收情况；对投递失败的消息，可手动或自动触发重新投递；对异常消息，可通过运营端，手动撤回消息；提供消息的批量归档能力，将历史消息归档到归档库中，减轻生产库的压力。

* **连接管理**：提供在线连接管理能力，查看当前所有的在线用户、用户的连接节点、用户的连接时间、用户的订阅端点、用户的连接 IP；运维人员可手动强制断开异常的用户连接，或向指定用户发送一条运维类消息；设置连接的空闲超时时间，自动关闭空闲的用户连接；对用户的连接请求，进行频率限制，防止恶意连接。

* **版本发布**：采用滚动发布的方式，更新应用节点；先将集群中的一台节点从负载均衡中摘除，更新版本，启动并检查健康状态，确认正常后，再将其他节点逐台更新；新旧版本兼容，支持用户无感切换；发布完成后，检查应用节点的运行状态、消息投递情况，以及用户的连接情况，确保业务正常运行。

### 8.3 性能规划

为保证系统在生产级场景下的稳定运行，需提前进行性能规划和压测优化。



* **性能基准**：系统支撑单机 10000 级用户的并发连接，集群支撑 10 万级用户的并发连接；单机每秒处理 1000 级消息的投递，集群每秒处理 10000 级消息的投递；消息投递的端到端延迟，普通网络环境下控制在 100 毫秒以内；弱网环境下，延迟不超过 1 秒；消息的推送流量，支持水平扩展，可通过增加应用节点，提升集群的整体吞吐量；在集群故障转移情况下，消息延迟不超过 10 秒，不出现消息丢失。

* **性能测试**：上线前，需要对系统进行全面的性能测试，包括连接压测、消息投递压测、消息拉取压测、数据库压测、缓存压测；模拟上万级用户并发连接、同时在线、批量发送消息的场景，验证系统的吞吐率、延迟、错误率是否满足要求；模拟应用节点故障、Redis 节点故障、MySQL 节点故障的场景，验证系统的高可用；根据压测结果，对系统架构、代码、数据库、缓存进行优化调整。

* **扩容策略**：系统支持水平扩展，通过增加应用节点，提升集群的并发连接数和消息投递吞吐量；Redis 集群采用主从复制 + 哨兵模式，支持水平扩展，增加从节点，提升读性能；MySQL 集群采用一主多从的读写分离架构，支持增加从节点，提升读性能；后续可引入专门的消息推送中间件，如 MQTT，支撑百万级甚至千万级的并发连接。

* **性能优化**：根据性能测试的结果，对系统进行针对性的优化；优化应用节点的 JVM 参数、容器参数，提升处理性能；优化 Redis 的连接池、序列化方式、缓存策略，提升缓存性能；优化 MySQL 的索引、SQL 语句、事务隔离级别，提升数据库的读写性能；优化消息推送策略，对批量消息进行合并压缩，减少网络传输的大小；优化消息的序列化、反序列化方式，采用性能更好的二进制协议，提升解析性能；对静态资源，采用 CDN 本地化、压缩合并、指纹版本等优化措施，提升资源加载性能。
