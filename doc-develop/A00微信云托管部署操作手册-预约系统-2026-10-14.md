# 微信云托管（CloudBase 云托管）部署操作手册 · 预约系统

> 适用对象：本项目（lesson-appointment 预约系统，Spring Boot 3.3.5 + Java 21 + MyBatis-Plus + MySQL，含 `api` 主服务 + `message-service` 消息服务 + Web 前端 `dist` + 微信小程序）从「自建服务器」迁移到「微信云托管」时的落地操作指南。
>
> 编写日期：2026-10-14  
> 配套文档：本文与《预约系统云服务器部署和维护手册.md》《腾讯云部署与维护手册-预约系统.md》并列，互为自建方案与云托管方案的对照。

---

## 0. 一句话结论

微信云托管 = 微信官方出的「容器 Serverless + 微信私有网关 + 免鉴权微信接口 + 内建 MySQL」一体化后端托管。**对本项目最大的收益**有三点：

1. **小程序登录免 code2Session**：小程序用 `wx.cloud.callContainer` 调后端时，网关自动把 `X-WX-OPENID / X-WX-UNIONID` 注入请求头，后端直接拿，省掉 `WeChatService` 里 `code2Session` 那套 secret 流程。
2. **微信接口免 access_token**：开启「开放接口服务」后，容器内访问 `api.weixin.qq.com`（含 PC 网站应用 OAuth `sns/oauth2`）自动换 token，**可不再依赖 `WECHAT_OPEN_SECRET`**。
3. **运维归零**：不用买 CVM、不用配 Nginx 反代、不用管 HTTPS 证书、不用配小程序 request 合法域名（走私有协议时），按量计费、自动扩缩容。

代价：要容器化（`Dockerfile` + `container.config.json`），且要适配云托管的环境变量注入方式（与现有 `booking.env` 体系有差异，见第 6 章）。

## 1. 概念与控制台入口

| 概念                    | 说明                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------ |
| 微信云托管 / CloudBase 云托管 | 腾讯云 + 微信团队联合的容器 Serverless 服务，入口在微信生态。                                               |
| 控制台入口                 | <https://cloud.weixin.qq.com/cloudrun> （微信扫码登录；需**实名认证**并**绑定腾讯云账号**，绑定失败会自动建新腾讯云账号） |

| 服务（service）           | 一个容器集群，对应本项目的一个后端模块（`api` 或 `message-service`）。每个服务有独立默认域名。                          |

| 原生网关                  | 微信私有协议 / HTTPS / WebSocket 接入；私有协议下自动注入登录态、防爬防 DDoS。                                 |

## 2. 前置准备（开工清单）

- [ ] 微信账号完成**实名认证**（个人/企业均可，企业主体能解锁微信支付等能力）。
- [ ] 在 cloud.weixin.qq.com/cloudrun 扫码登录并**绑定腾讯云账号**（或自动新建）。
- [ ] 小程序已创建，拿到真实 `appid`（与 `miniprogram/project.config.json` 一致）。
- [ ] **unionid 前提**：小程序已绑定到**同一微信开放平台账号**（否则各端 openid 不同、unionid 不下发，本项目微信打通的根因，见《微信登录与绑定实现路径方案.md》）。
- [ ] PC 网站扫码（P2）需先在微信开放平台创建「网站应用」，拿到 `WECHAT_OPEN_APPID / WECHAT_OPEN_SECRET`。
- [ ] 准备本地 Docker（用于本地预打包镜像，见第 5 章）。
- [ ] 备份本地 `lesson_appointment` 与 `message_center` 两个库（`mysqldump`，见第 4 章）。

## 3. 开通环境与服务骨架

1. 打开 <https://cloud.weixin.qq.com/cloudrun> → 扫码登录 → 新建环境（首次会让你选地域，国内业务选「上海/广州」）。
2. 环境建好后，进入「云托管」→「新建服务」：
   - 服务名 `api`，**打开「公网访问」**（Web 前端和小程序外网调用需要）；内网访问一并打开（两服务互调免域名）。
   - 服务名 `message-service`，同样打开公网 + 内网访问。
3. 此时两个服务都是空壳，下一步做容器化 + 数据库。

> 云托管支持「模板部署」一键起 Spring Boot + MySQL，但本项目代码已成型，**不推荐模板**，直接走「自定义部署 / 上传镜像 / 流水线」更可控。

## 4. 数据库选型与迁移（最关键一步）

本项目有两个库（与两个服务一一对应）：

- `lesson_appointment` ← `api` 主服务（业务库，含租户/课程/预约/推广/微信身份等表）
- `message_center` ← `message-service`（消息中心库，AES/HMAC 密钥域共享）

### 4.1 两种数据库方案

| 方案                  | 做法                                                                                   | 优点                | 缺点                                            |
| ------------------- | ------------------------------------------------------------------------------------ | ----------------- | --------------------------------------------- |
| **A. 用云托管内建 MySQL** | 控制台「数据库」一键开通 Serverless MySQL，自动注入 `MYSQL_ADDRESS / MYSQL_USERNAME / MYSQL_PASSWORD` | 运维归零、按量计费、免备份策略自管 | 变量名与本项目 Properties 不一致，需做映射（见 4.3）；跨服务共享库要手动建 |
| **B. 自带 MySQL**     | 用腾讯云数据库 MySQL（或 CVM 自建），在环境变量里给 `SPRING_DATASOURCE_URL / DB_USERNAME / DB_PASSWORD`  | 与现有配置零改造，两库天然隔离清晰 | 多一份数据库运维/费用                                   |

> **推荐**：测试期用方案 A 快速验证；生产期用方案 B（或 A 但做好映射），因为本项目的双库 + 共享密钥域 + 跨库 JOIN（已有 `COLLATE utf8mb4_general_ci` 依赖）在云托管单一内建 MySQL 里也能跑，但要把两个 schema 都建进去。

### 4.2 Schema 迁移（通用步骤）

```bash
# 1) 本机导出（务必用 --result-file，避免 Windows GBK 乱码；跨库 JOIN 已显式 COLLATE）
mysqldump -uroot -p123456 --default-character-set=utf8mb4 \
  --result-file=api/sql/dump/lesson_appointment.sql lesson_appointment
mysqldump -uroot -p123456 --default-character-set=utf8mb4 \
  --result-file=api/message-service/sql/dump/message_center.sql message_center

# 2) 云托管 MySQL 控制台「导入」这两个 sql，或连上云库后 source
# 3) 校验字符集：所有表/库 charset = utf8mb4，collation = utf8mb4_general_ci
#    （本项目跨库 JOIN 依赖 utf8mb4_general_ci，建库时别用默认的 utf8mb4_0900_ai_ci）
```

> ⚠️ **时区坑（必看）**：本项目 `application.properties` 的 JDBC URL 写的是 `serverTimezone=UTC`，而 `booking.env.template` 里写的是 `Asia/Shanghai`，两处本身就不一致。容器基础镜像默认也是 UTC，**差 8 小时会让所有写入时间、课程时间、定时任务时刻全部错位**。云托管部署时必须三处统一：
>
> - 容器环境变量 `TZ=Asia/Shanghai`；
> - 数据库 `serverTimezone` 与容器 `TZ` 一致；
> - `booking.env.template` 的 `SPRING_DATASOURCE_URL` 改回与 `application.properties` 一致（或反过来统一为 UTC，但中国业务建议统一 `Asia/Shanghai`）。

### 4.3 内建 MySQL 变量名映射（方案 A 必做）

云托管内建 MySQL 注入的是 `MYSQL_ADDRESS / MYSQL_USERNAME / MYSQL_PASSWORD`，而本项目 Properties 读的是 `SPRING_DATASOURCE_URL / DB_USERNAME / DB_PASSWORD`。两种接法：

**接法 1（最小改造，推荐）**：在云托管「服务设置 → 环境变量」里直接按本项目 Properties 的名字填：

```
DB_USERNAME=<云库用户名>
DB_PASSWORD=<云库密码>
SPRING_DATASOURCE_URL=jdbc:mysql://<MYSQL_ADDRESS>/lesson_appointment?useUnicode=true&characterEncoding=utf8mb4&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true
```

**接法 2**：保留 `MYSQL_*` 命名，在 `application.properties` 里改成读 `MYSQL_*`：

```
spring.datasource.url=jdbc:mysql://${MYSQL_ADDRESS}/<db>?...
spring.datasource.username=${MYSQL_USERNAME}
spring.datasource.password=${MYSQL_PASSWORD}
```

> 选接法 1 可不动代码，只是把 `booking.env.template` 的变量名原样搬进云托管环境变量即可。

## 5. 容器化改造（核心）

### 5.1 端口对齐（致命细节）

本项目 `api` 的 `server.port=8081`（**不是 8083**，8083 只是本地 smoke 测试端口），`message-service` 为 `8090`。**云托管的「监听端口 / containerPort」必须与 `server.port` 完全一致，否则部署直接失败、请求 502**。

### 5.2 Dockerfile（本地预打包，最稳）

放在 `api/` 根目录（与 `pom.xml` 同级）。建议**本地先 `mvn package` 出 jar，再打镜像**，避免平台外网拉依赖失败：

```dockerfile
# api/Dockerfile
FROM eclipse-temurin:21-jre-jammy
# 时区：防 8 小时错位
ENV TZ=Asia/Shanghai
RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone
WORKDIR /app
# 本地已打好 jar，COPY 进镜像（jar 名按实际 artifact 调整）
COPY target/api-0.0.1-SNAPSHOT.jar app.jar
EXPOSE 8081
# 用 env 注入的变量驱动；spring.profiles.active 可区分云托管环境
ENTRYPOINT ["java","-jar","app.jar","--spring.profiles.active=cloud"]
```

> `message-service` 同理，`EXPOSE 8090`，`COPY target/message-service-*.jar`。

> ⚠️ **Actuator 探针**：本项目已配 `liveness`/`readiness` 探针（`/actuator/health`），云托管「启动检测延迟 `initialDelaySeconds`」建议设 `10`，避免启动期被误判不健康而反复重启。

### 5.3 container.config.json

放在服务代码根目录，用于流水线部署时定义规格：

```json
{
  "containerPort": 8081,
  "dockerfilePath": "Dockerfile",
  "buildDir": "",
  "minNum": 0,
  "maxNum": 10,
  "cpu": 0.5,
  "mem": 1,
  "policyType": "cpu",
  "policyThreshold": 60,
  "envParams": {},
  "customLogs": "stdout",
  "initialDelaySeconds": 10
}
```

- `containerPort` 必须等于 `server.port`（8081 / 8090）。
- `minNum=0` 允许缩容到 0（省钱，但有冷启动）；若怕冷启动影响上课提醒等定时任务，设 `minNum=1` 常驻。
- `mem` 单位 GB；本项目 8 个 `@Scheduled` 任务 + 连接池，1GB 起步。

## 6. 环境变量与密钥管理（与 booking.env.template 对齐）

### 6.1 普通变量 vs 加密变量

云托管环境变量分两类：**普通变量**（控制台可见明文）和**加密变量**（额外保护、控制台不直显）。**密钥一律走加密变量**：数据库密码、`JWT_SECRET`、`AES_KEY`、`HMAC_KEY`、微信 `WECHAT_SECRET` / `WECHAT_OPEN_SECRET`。

> 修改环境变量后**必须重新发布版本才生效**（启动时注入，不热更新）。

### 6.2 本项目需注入的变量清单

下表以 `api` 服务为例（`message-service` 同表，但库名换 `message_center`，且不含微信变量）：

| 变量名                        | 对应 Properties                | 是否密钥      | 备注                                       |
| -------------------------- | ---------------------------- | --------- | ---------------------------------------- |
| `DB_USERNAME`              | `spring.datasource.username` | 否         | 数据库用户名                                   |
| `DB_PASSWORD`              | `spring.datasource.password` | **是（加密）** | 数据库密码                                    |
| `SPRING_DATASOURCE_URL`    | `spring.datasource.url`      | 否（含地址）    | 见 4.3，时区统一 `Asia/Shanghai`               |
| `JWT_SECRET`               | `jwt.secret`                 | **是（加密）** | api 与 message-service 必须**逐字符一致**（共享密钥域） |
| `AES_KEY`                  | `crypto.aes-key`             | **是（加密）** | 见下方「命名不一致」告警                             |
| `HMAC_KEY`                 | `crypto.hmac-key`            | **是（加密）** | 见下方「命名不一致」告警                             |
| `WECHAT_APPID`             | `wechat.miniapp.appid`       | 否         | 小程序 appid，须与 `project.config.json` 一致    |
| `WECHAT_SECRET`            | `wechat.miniapp.secret`      | **是（加密）** | 小程序 secret；走私有协议后可不再需要                   |
| `WECHAT_OPEN_APPID`        | `wechat.open.appid`          | 否         | 开放平台网站应用                                 |
| `WECHAT_OPEN_SECRET`       | `wechat.open.secret`         | **是（加密）** | 网站应用 secret；开「开放接口服务」后可不再需要              |
| `WECHAT_OPEN_REDIRECT_URI` | `wechat.open.redirect-uri`   | 否         | 须与开放平台「授权回调域」一致（只填域名不带 path）             |
| `TZ`                       | —                            | 否         | `Asia/Shanghai`，防时区错位                    |

### 6.3 ⚠️ 已知不一致（部署前必须修）

`doc-develop/booking.env.template` 里写的是 `CRYPTO_AESKEY` / `CRYPTO_HMACKEY`，但 **`application.properties` 实际读取的是 `AES_KEY` / `HMAC_KEY`**（见 `application.properties` 第 132–134 行 `${AES_KEY:...}` / `${HMAC_KEY:...}`）。**这套 env 模板直接搬进云托管会因变量名对不上而读不到密钥，导致 AES/HMAC 解密失败、姓名回显成密文（本项目 `user.name` 入库加密的既有坑）**。

> **行动项**：把 `booking.env.template` 的 `CRYPTO_AESKEY`/`CRYPTO_HMACKEY` 改名为 `AES_KEY`/`HMAC_KEY`，与 Properties 对齐；云托管环境变量也用 `AES_KEY`/`HMAC_KEY`。同时核对 `腾讯云部署与维护手册` 中对应的变量名是否已同步。

### 6.4 与现有自建体系的对照

| 项目   | 自建（systemd + booking.env）                                     | 云托管                    |
| ---- | ------------------------------------------------------------- | ---------------------- |
| 注入方式 | `EnvironmentFile=/etc/lesson/booking.env`                     | 控制台「服务设置 → 环境变量」（加密变量） |
| 改完生效 | `systemctl restart`                                           | 重新发布版本                 |
| 密钥落点 | `/etc/lesson/*.env`（chmod 600）                                | 云托管加密变量（控制台不直显）        |
| 不变项  | 变量**名字**必须仍为 Properties 实际读取的名字（`AES_KEY` 不是 `CRYPTO_AESKEY`） | 同左                     |

## 7. 微信能力在云托管下的变化（重点差异）

这是本项目迁移云托管**最值得做**的部分，直接影响《微信登录与绑定实现路径方案.md》里 P0/P1/P2 的实现。

### 7.1 小程序登录：可省掉 code2Session

现状：小程序 `wx.login` 拿 code → 后端 `WeChatService` 调 `auth.code2Session`（需 `WECHAT_SECRET`）换 openid/unionid → 落 `wx_userid`。

云托管优化：小程序改用 `wx.cloud.callContainer` 调后端，**微信私有协议网关会自动把以下请求头注入到你的 HTTP 请求**：

| Header            | 含义                                |
| ----------------- | --------------------------------- |
| `X-WX-OPENID`     | 小程序用户 openid                      |
| `X-WX-UNIONID`    | 小程序用户 unionid（满足 unionid 获取条件时才有） |
| `X-WX-APPID`      | 小程序 AppID                         |
| `X-WX-ENV`        | 所在云环境 ID                          |
| `X-WX-SOURCE`     | 调用来源                              |
| `X-Forwarded-For` | 客户端 IP                            |

后端直接从 Header 拿，**不需要 `wx.login`、不需要 `code2Session`、不需要 `WECHAT_MINIAPP_SECRET`**，且由微信团队保证加密防刷。

**本项目改造建议**：

- 在 `authController` / `WeChatService` 增加「从 `X-WX-OPENID`/`X-WX-UNIONID` 直接取身份」的优先分支；当 Header 存在时跳过 code2Session（兼容非云托管部署时仍走旧流程）。
- `WxUseridService.findByIdentity(openid/unionid)` 的匹配逻辑不变，只是数据来源从「换回来的」变成「网关注入的」。
- 资源复用（同主体多小程序）时还有 `X-WX-FROM-OPENID/APPID/UNIONID`，按需处理。

> 若坚持用旧的 `code2Session` 流程也完全可行，云托管不会拦，但等于放弃了「免密钥、防刷」的生态红利，当成普通服务器用。

### 7.2 PC 网站扫码（P2）：仍可走开放平台 OAuth

P2 的 `WeChatPcController`（`/auth/wechat/qr`、`/qr/status`、`/pc-callback`）走的是**开放平台网站应用**的 `sns/oauth2/access_token` + `sns/userinfo`。两种接法：

- **接法 A（保留现状）**：继续用 `WECHAT_OPEN_APPID` + `WECHAT_OPEN_SECRET` 自己换 token。云托管下只是把这两个值放进加密变量。
- **接法 B（推荐，免密钥）**：开启云托管「开放接口服务」（见 7.3），容器内对 `api.weixin.qq.com` 的 OAuth 请求自动换 token，**可不再配置 `WECHAT_OPEN_SECRET`**。

无论哪种，`WECHAT_OPEN_REDIRECT_URI` 必须与开放平台「网站应用 → 授权回调域」**逐字符一致**（只填域名不带 path，生产用已备案 HTTPS）。

### 7.3 免鉴权云调用（开放接口服务）

「开放接口服务」是云托管把 `api.weixin.qq.com` 请求旁加载入容器、自动处理 token/鉴权的能力。

操作步骤：

1. 控制台 → 云调用 → 开放接口服务 → **打开开关**（注意：开关打开后**必须重新构建版本才生效**）。
2. 云调用 → 微信令牌权限配置 → 勾选你要用的接口（如 `sns/oauth2/access_token`、`sns/userinfo`、模板消息、内容安全等）。
3. 业务代码里**仍然用 HTTP 调 `api.weixin.qq.com`，但不带 access_token**；链路正常时返回头会带 `x-openapi-seqid` 标识走的是云调用。

> 收益：彻底不碰 `WECHAT_SECRET` / `WECHAT_OPEN_SECRET`，密钥零暴露面。代价：只能在云托管容器内生效，本地调试时要回退到带 secret 的旧流程（本项目 `WeChatService.warnIfSecretPlaceholder()` 已有占位降级逻辑，可复用）。

### 7.4 合法域名配置差异


| 接入方式                                | 是否需要配小程序 request 合法域名                            |
| ----------------------------------- | ------------------------------------------------ |
| 小程序走 `wx.cloud.callContainer`（私有协议） | **不需要**                                          |
| 小程序走普通 `wx.request` 直连云托管公网域名       | 需要把 `*.sh.run.tcloudbase.com`（或自定义域名）加入「小程序合法域名」 |
| 公众号 H5 / PC 网站                      | 走 HTTPS 即可，PC 回调域在开放平台配                          |

## 8. 前端部署

### 8.1 Web 端（dist）

两种方式：

- **方式 A（静态网站托管）**：把 `frontend/dist/` 上传到云开发「静态网站托管」，拿到一个 URL。适合纯静态前端。缺点是 Web 端调用后端要用云托管公网域名（跨域需后端 `CORS` 或同源网关）。
- **方式 B（Nginx 容器）**：新建一个 `web` 云托管服务，Dockerfile 用 `nginx:alpine`，`COPY dist /usr/share/nginx/html`，`EXPOSE 80`。适合需要反向代理、统一域名、处理跨域的场景（推荐，和现有 `nginx` 反代思路一致）。

> 无论哪种，前端里的后端 API 基地址要改成云托管 `api` 服务的**默认域名**（`https://<api服务>-<envid>.sh.run.tcloudbase.com`），或绑定自定义域名后改之。`shared/apiPaths.js` 与 `miniprogram/shared/apiPaths.js` 的基地址常量需同步。

### 8.2 小程序端

- 若已切到 `wx.cloud.callContainer`（7.1）：**无需改 request 合法域名**，开箱即用。
- 若仍用 `wx.request` 直连：在微信公众平台把云托管公网域名加入「request 合法域名」。
- `miniprogram/project.config.json` 的 `appid` 必须与 `WECHAT_APPID`、开放平台绑定一致（unionid 打通前提不变）。

## 9. 发布与灰度

三种发布方式（控制台「新建版本」时选）：

| 方式                       | 适用                           | 说明                                           |
| ------------------------ | ---------------------------- | -------------------------------------------- |
| 上传代码包 / Dockerfile       | 本地已有代码                       | 平台按 Dockerfile 构建（建议本地预打包 jar，避免外网拉依赖失败）     |
| 上传镜像                     | 已 `docker build` + 推到云托管镜像仓库 | 最稳，构建可控                                      |
| 流水线（GitHub/GitLab/Gitee） | 持续交付                         | 授权代码源 → 建 `container.config.json` → 代码合并触发构建 |

灰度与回滚：

- 新建版本时可设「灰度比例」，按比例放流量，观察正常再全量。
- 版本列表支持「回滚到上一版本」，出事一键退。
- 建议保留最近 2–3 个版本，方便快速回退。

## 10. 自定义域名与 HTTPS

- 默认域名：`https://<service>-<envid>.sh.run.tcloudbase.com`（已带 HTTPS，可直接用）。
- 绑定自定义域名：控制台「服务设置 → 自定义域名」，填入已**备案**的域名，按提示加 CNAME 解析。
- `WECHAT_OPEN_REDIRECT_URI` 的回调域必须与开放平台配置一致——绑定自定义域名后，把回调域也改成自定义域名（只填域名不带 path）。

## 11. 监控、日志、告警

- **日志**：服务「日志」面板自动聚拢容器 `stdout`/`stderr`（`customLogs: stdout` 已配）。排查顺序：实例是否崩溃重启 → 按时间倒序看错误栈 → 用请求路径串上下文。
- **监控**：「监控概览」看 QPS、调用次数、响应耗时、实例数。
- **告警**：自定义告警规则（CPU/内存/错误率阈值），绑定接收人。
- **健康探针**：本项目 `liveness`/`readiness` 已就绪，云托管「启动检测延迟」设 10s，避免启动期误杀。

## 12. 成本与扩缩容

- **按量计费**：精确到 100 毫秒，用多少付多少，官方称比传统服务器省 30%+；新环境赠 400 元免费额度（3 个月）。
- **弹性**：`minNum=0` 可缩到 0（省钱、有冷启动）；`minNum=1` 常驻消除冷启动（推荐生产，尤其本项目有 8 个定时任务，缩到 0 时定时任务不跑）。
- **常驻不销毁**：对延迟敏感接口设常驻实例。
- 内建 MySQL Serverless：「不使用不计费」。

## 14. 常见排障

| 现象                  | 根因                                     | 处理                                           |
| ------------------- | -------------------------------------- | -------------------------------------------- |
| 部署后请求 502 / 健康检查失败  | `containerPort` 与 `server.port` 不一致    | 两者对齐（api 8081 / 8090）                        |
| 所有时间差 8 小时          | 容器 UTC + `serverTimezone` 不一致          | `TZ=Asia/Shanghai` + 统一 `serverTimezone`     |
| 小程序 1001 / 微信静默降级   | `WECHAT_SECRET` 占位未填，或 secret 错        | 填真实值；或切私有协议免 secret                          |
| 姓名回显成 hex:base64 密文 | `AES_KEY`/`HMAC_KEY` 变量名对不上 / 两服务密钥不一致 | 用 `AES_KEY`/`HMAC_KEY` 且与 message-service 一致 |
| 数据库连不上              | 内建 MySQL 变量名没映射到 Properties            | 按 4.3 接法 1 或 2 改名                            |
| 跨域被拦                | 前端直连独立域名                               | 后端开 CORS，或用 Nginx 容器同源反代                     |
| PC 扫码回跳 404 / 不回调   | `redirect-uri` 与开放平台回调域不符              | 逐字符对齐（只填域名不带 path）                           |
| 跨端识别成两个账号           | 小程序未绑同一开放平台                            | 绑定开放平台账号，unionid 才下发                         |
| 冷启动慢 / 定时任务不跑       | `minNum=0` 缩容到 0                       | 设 `minNum=1` 常驻                              |

## 15. 安全提醒（与现有维护手册一致）

- 微信凭证、JWT、AES/HMAC 密钥**只走云托管加密变量 / 环境变量**，**绝不写进镜像、不进 Git**。
- `message-service` 与 `api` 共享密钥域，**同名密钥必须逐字符一致**。
- Actuator 只暴露 `health,info`，`env/beans/configprops/heapdump` 等一律关（本项目已配，迁移后复查一遍）。
- 免登录白名单四处在云托管下仍需保持（SecurityConfig / JwtFilter / check-authz / WebMvcConfig），容器化不改变放行逻辑。

## 16. 与自建方案的取舍

| 维度     | 自建（CVM + systemd + Nginx） | 微信云托管                 |
| ------ | ------------------------- | --------------------- |
| 运维成本   | 高（买机器、装环境、证书、监控）          | 极低（全托管）               |
| 微信生态融合 | 需自己配合法域名、自己管 secret       | 私有协议免域名、开放接口服务免 token |
| 弹性     | 手动扩                       | 自动按量扩缩                |
| 改造量    | 现状已跑通                     | 需容器化 + 变量映射 + 登录流程微调  |
| 数据主权   | 库在自己手里                    | 库在云托管（可方案 B 自带库）      |
| 成本模型   | 包年包月固定                    | 按量，闲时近乎零              |

**建议路径**：先用云托管把 `api` + `message-service` 容器化跑通（方案 A 内建 MySQL 快速验证），小程序登录切私有协议、PC 扫码视情况开开放接口服务；生产期视数据主权诉求决定是否切方案 B 自带 MySQL。本文与两份自建维护手册并存，按需选用。
