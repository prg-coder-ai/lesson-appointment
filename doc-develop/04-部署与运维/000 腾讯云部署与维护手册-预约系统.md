### 1.2 本地数据库初始化（三个库）

本地需要三个库：`lesson_appointment`（业务）、`message_center`（消息中心）、`classroom`（在线课堂）。

SQL 脚本的权威位置是 **`deploy/sql/{schema,seed,patch}/`**（2026-11-18 从 `api/sql/` 迁入），另有 `api/classroom-service/sql/`：

| 顺序 | 真实文件                                                                    | 作用                                                 | 是否自带建库                           |
| -- | ----------------------------------------------------------------------- | -------------------------------------------------- | -------------------------------- |
| 1  | `deploy/sql/schema/20261013-0400-lesson_appointment-schema.sql`         | 业务库全量表结构                                           | ❌ **不带** `CREATE DATABASE`，先建库再导 |
| 2  | `deploy/sql/seed/20261008-1527-lesson_appointment-seed-dict-config.sql` | 行业、套餐模板、系统配置、**术语 317 行**                          | ❌ 需指定库名（术语已并入，不再需要替换占位符）         |
| 3  | `deploy/sql/schema/20261008-1527-message_center-schema.sql`             | 消息库表结构                                             | ❌ **不带** `CREATE DATABASE`       |
| 4  | `deploy/sql/seed/20261008-1528-message_center-seed-sys.sql`             | 消息分类、模板、敏感词                                        | ❌ 需指定库名                          |
| 5  | `api/classroom-service/sql/classroom-schema.sql`                        | 课堂库建库建表（205 行，**不含** `sys_eclassroom_instance` 种子） | ✅ 自带 `CREATE DATABASE` + `USE`   |
| —  | `deploy/sql/patch/*.sql`（19 个）、`api/classroom-service/sql/patch/*.sql`  | 增量补丁，按文件名顺序执行                                      | ❌ 多数需指定库名                        |

> **课堂库的两条隐性依赖**（建库/授权时最容易漏）：
>
> 1. `classroom-service` 要**只读**主业务库的 `sys_tenant_eclassroom`（判断某租户是否开通课堂），  
>    所以它的 DB 账号对 `lesson_appointment` 库必须有 `SELECT` 权限，且**两个库在同一个 MySQL 实例**上；
> 2. 课堂实例表 `sys_eclassroom_instance` 为空 → 前端拿不到 `enabled=true` → **课堂入口根本不出来**。  
>    建库时务必确认该表有种子行（仓库补丁：`deploy/sql/patch/20261029-1300-eclassroom-default-instance.sql`）。

> ⚠️ **schema 快照时点为 2026-10-13**（旧手册里的 `lesson_appointment_schema_fixed.sql` 已不存在）。  
> 快照之后新增的**表**另有一组手写 schema 文件（legal-doc / auth-guard / work-language /  
> eclassroom-tenant / lesson-attendance / student-lesson-ledger，共 11 张，见下面第 2 步），  
> 它们**不在**基线 dump 里，漏一组就对应功能整组 500；而 `deploy/sql/patch/` 里的历史增量  
> 绝大多数已并入当前 schema，**新环境只需要两条**（课堂实例种子 + ws_base_path 修正）。

> 其余仅供追溯"某约束何时加的"，完整口径见 `deploy/sql/README.md`。

### 2.4 ⚠️ 密钥域铁律（本地联调最常见的 401 根因）

> token 只能被**与其同源密钥**的服务校验。`JwtAuthenticationFilter` 只验签名、不查 session。

| 拓扑 | 是否可用 | 前提 |
|------|---------|------|
| 全本地（本地 booking 8081 + message 8090 + classroom 8092） | ✅ | 三者都用源码 `application.properties` 的 `jwt.secret`，同源 |
| 全远程（远程 booking + message-service + classroom-service） | ✅ | 远程三个服务同为系统密钥；需远程 8090/8092 放行 |
| **混合**（本地任一服务 + 远程任一服务） | ❌ **必 401** | 密钥不同源，无解，只能改成上面两种之一 |

典型症状：消息列表/收件人加载报 `{"code":401,"message":"未登录或登录已过期"}`；
课堂页进不去、白板/心跳 WebSocket 握手被拒（同样 401）。
另外要注意：`/api/v1/message/system/info` 返回 booking 的 401 文案，说明**请求根本没路由到 8090**（分流问题），不是权限问题。


### 2.5 本地常见故障

| 症状 | 原因 | 处理 |
|------|------|------|
| 页面空白但接口有数据 | 前端对**已解包**的响应又取了一次 `.data` | 页面必须走 `unwrapPayload` / `unwrapBackendPayload`；详见姊妹篇 10.2 |
| `Address already in use` | 端口被占用 | `netstat -ano \| findstr :8081` 找 PID 后结束，或换 `--server.port` |
| 报数据库连接失败 | MySQL 未启动 / 库未建 / 密码不对 | 按 1.2 重新导库；确认 `root/123456` |
| 排期时间差 8 小时 | `serverTimezone=UTC`（源码默认） | 本地覆盖配置里改 `Asia/Shanghai` |
| 改了 js 刷新没变化 | 伺服的是 dist 不是源码 | 改用 `dev-frontend-local-src.js`，或 `Ctrl+F5` |
| 启动后立刻绑到别的端口 | 环境变量 `SERVER_PORT`/`SERVER__PORT` 被宽松绑定 | 启动命令显式带 `--server.port=8081` |

### 3.1 服务器初始化（一次性）

```bash
ssh root@你的服务器IP

apt update && apt upgrade -y
apt install -y nginx mysql-server redis-server openjdk-17-jdk-headless rsync

java -version     # openjdk 17.x
mysql --version   # 8.x

nginx -v          # 1.18+

mysql_secure_installation      # 设 root 强密码，一路 Y
```

> Redis 加固（公网服务器必做）：只监听本机 + 不设公网访问，课堂用的是 **db 2**，与别的服务互不干扰。
> ```bash
> sudo sed -i 's/^bind .*/bind 127.0.0.1 ::1/' /etc/redis/redis.conf
> sudo sed -i 's/^# requirepass .*/requirepass 换成你的强密码/' /etc/redis/redis.conf
> sudo systemctl restart redis-server && redis-cli -n 2 -a '换成你的强密码' ping
> ```
> 设了密码就**必须**在 `/etc/lesson/classroom.env` 里配 `REDIS_PASSWORD`（见 3.5.2b），否则课堂启动后连不上 Redis。
> 注：`classroom-service` 的源码配置只写了 `spring.data.redis.host/port/database`，没有 password 项 —— 需要密码时用 `SPRING_DATA_REDIS_PASSWORD` 环境变量注入（Spring Boot 的宽松绑定），或改用 Redis ACL 免密内网访问。

该脚本做四件事，**每一件都有理由，别手工拆成几条命令再做漏**：

| 动作 | 为什么必须由脚本统一做 |
|---|---|
| 建三个库，**collation 逐库对齐现网**（`lesson_appointment`=`utf8mb4_unicode_ci`、`message_center`=`utf8mb4_general_ci`、`classroom`=`utf8mb4_0900_ai_ci`） | 统一成一个不会报错，但课堂要**跨库只读**常主库的 `sys_tenant_eclassroom`，collation 不一致会在比较/排序上冒怪结果 |

| 删掉 `root` 的**远程 host**（`%` / `0.0.0.0` / `::`） | 云镜像常见 `root@'%'`；不删等于把库家门敞开 |

> 还要用**全限定表名**只读主库的三处，缺任一处的授权，课堂会以"数据坏了"的样子失败：
>
|  |  |  |  |
| --- | --- | --- | --- |
> | 跨库对象 | 用途 | 缺授权的表现 |
> |---|---|---|
> | `lesson_appointment.sys_tenant_eclassroom` | 判断租户是否开通课堂 | 课堂开关永远判成 `false` → 管理端课堂**全 403「课堂未启用」** |
> | `lesson_appointment.sys_eclassroom_instance` | 取实例地址 / 容量 | 同上（开关判定链第二步就断） |
> | `lesson_appointment.booking` | 花名册人数（`BookingRosterMapper`） | 课堂监视里人数为 0 / 进课堂报错 |
>
> `lesson` 账号对 `lesson_appointment.*` 有库级权限时天然满足；**但 `classroom` 库的授权要单独给** ——
> 课堂是第三个上线的模块，库常常是后建的，于是 `lesson` 能连前两个库、唯独没有 `classroom` 的权限，
> 而 MySQL 报的是 `Access denied`（HTTP 层只剩一句 `MyBatisSystemException`，见 **6.6**）。
>
> ```sql
> -- 一键补齐（幂等，不建账号不改密码；详见 deploy/sql/patch/20261122-1430-classroom-db-grant.sql）
> --   mysql -uroot -p < deploy/sql/patch/20261122-1430-classroom-db-grant.sql
> GRANT ALL PRIVILEGES ON `classroom`.* TO 'lesson'@'127.0.0.1', 'lesson'@'localhost';
> -- 若把主库权限收窄成表级最小权限，这三条也必须有：
> GRANT SELECT ON `lesson_appointment`.`sys_tenant_eclassroom`   TO 'lesson'@'127.0.0.1';
> GRANT SELECT ON `lesson_appointment`.`sys_eclassroom_instance` TO 'lesson'@'127.0.0.1';
> GRANT SELECT ON `lesson_appointment`.`booking`                 TO 'lesson'@'127.0.0.1';
> FLUSH PRIVILEGES;
> ```
>
> 核对：`SHOW GRANTS FOR 'lesson'@'127.0.0.1';`，以及用应用账号真连一次
> `mysql -h127.0.0.1 -ulesson -p classroom -e "SELECT 1"`（**host 必须写 `127.0.0.1`**，
> 与 JDBC 一致；`localhost` 走 socket，是另一个账号身份，能连不代表服务能连）。
> 两个库必须在**同一个 MySQL 实例**上（跨实例读不到，源码用全限定表名写死）。

#### 3.4.1 向服务器复制文件与文件夹：命令速查

> 本节是所有 `scp` / `rsync` 用法的**集中出处**。3.4、3.5 以及后续章节里的上传命令，写法都来自这里。

**① 一条铁律：结尾的 `/` 决定"传目录本身"还是"传目录里的内容"**

```bash
scp -r frontend/dist  $SERVER:/var/www/frontend/    # ❌ 传的是【目录本身】
                                                     #    → /var/www/frontend/dist/index.html
scp -r frontend/dist/ $SERVER:/var/www/frontend/    # ✅ 传的是【目录里的内容】
                                                     #    → /var/www/frontend/index.html
```

Nginx `root /var/www/frontend` 找的是**同一层**的 `index.html`，传错层 → 首页 403/404。这条是本项目最容易翻车的一处。

**② 复制单个文件 / 多个文件**

```bash
# 单个文件
scp booking-api-2.0.1.jar $SERVER:/opt/lesson/

# 上传时就改名（目标写完整文件名）
scp booking-api-2.0.1.jar $SERVER:/opt/lesson/booking-api.jar

# 一次传多个文件（最后一个参数才是目标目录）
scp a.jar b.jar c.sql $SERVER:/opt/lesson/

# 源用通配符（不想写死版本号时）
scp api/target/booking-api-*.jar                  $SERVER:/opt/lesson/booking-api.jar
scp api/message-service/target/message-service-*.jar $SERVER:/opt/lesson/message-service.jar
```

**③ 复制整个文件夹（递归，必须带 `-r`）**

```bash
# 前端产物：传内容到站点根（注意结尾 /）
scp -r frontend/dist/ $SERVER:/var/www/frontend/

# 配置模板：先传到临时目录，因为 /etc 下需要 root
scp -r deploy/nginx/  $SERVER:/tmp/nginx-conf/

# SQL 目录（源是 deploy/sql/）

scp -r api/classroom-service/sql/ $SERVER:/opt/lesson/sql/classroom/
```

**④ 文件夹同步优先用 `rsync`（能续传、能删除多余文件）**

```bash

rsync -av --delete frontend/dist/ $SERVER:/var/www/frontend/
rsync -av deploy/sql/                $SERVER:/opt/lesson/sql/        # 整个 SQL 树（schema/seed/patch）

# 服务器没装 rsync 时先装： apt install -y rsync
# 或退回 scp： scp -r frontend/dist/* $SERVER:/var/www/frontend/
```

> **`--delete` 要小心**：它会把目标目录里"本地没有的文件"删掉。所以**目标目录必须只放这个东西**（`/var/www/frontend/` 里不要混放手工文件）。

### 3.5 配置文件逐份落地（★ 本章核心）

> 下面每个文件都给出「部署路径 + 完整内容」。可以在本地建好、改成自己的值，再按 **3.4.1 ⑦**（传 `/tmp` 再 `sudo mv`）上传。

#### 3.5.0 先生成三个密钥（本地生成即可）

**Windows PowerShell**：

```powershell
# JWT：64 字节随机串（Base64）
[Convert]::ToBase64String((1..64 | ForEach-Object { Get-Random -Maximum 256 }))
# AES / HMAC：各 32 字节（Base64，44 字符，结尾带 =）
[Convert]::ToBase64String((1..32 | ForEach-Object { Get-Random -Maximum 256 }))
```

**Linux / macOS / Git Bash**：

```bash
openssl rand -base64 64    # JWT_SECRET
openssl rand -base64 32    # AES_KEY
openssl rand -base64 32    # HMAC_KEY
```

约束：

- `JWT_SECRET`：≥64 字符；
- `AES_KEY` / `HMAC_KEY`：Base64 解码后**必须正好 32 字节**（44 字符、结尾 `=`）；
- **三个服务（booking / message / classroom）共用这三个值**（2026-11-21 起统一放在 `/etc/lesson/keys.env`，见 3.5.0b），
  不一致会导致消息与课堂请求 401、跨服务解密失败；
- 前端（dist）**不持有任何密钥**。

> ⚠️ **变量名不要写错（2026-10-30 修正）**：源码里是
> `crypto.aes-key=${AES_KEY:默认值}`、`crypto.hmac-key=${HMAC_KEY:默认值}`，
> `CryptoUtil` 用 `@Value("${crypto.aes-key}")` 直读。所以**生效的环境变量名是 `AES_KEY` / `HMAC_KEY`**
> （与 `deploy/*.env.template` 一致）。
> 本手册早期版本写的是 `CRYPTO_AESKEY` / `CRYPTO_HMACKEY` —— **那是无效的**：
> 占位符只认 `AES_KEY`，`@Value` 也不会把 `CRYPTO_AESKEY` 宽松绑定到 `crypto.aes-key`
> （Spring 只把 `crypto.aes-key` 映射成 `CRYPTO_AES_KEY`，多一个下划线都不行）。
> 无效的后果不是报错，而是**静默沿用源码里公开的默认密钥**（三个服务都用同一默认值，仍然互通，所以
> 登录/解密一切正常，极难发现），生产环境的字段加密因此形同虚设。改完务必按 3.6 的自检第 4 步验证。


#### 3.5.0b 文件 `/etc/lesson/keys.env`（三服务共用密钥 + 数据库凭据）

> 仓库模板：`deploy/keys.env.template`。本地实例文件 `deploy/keys.env` **不入库**（已列入 `.gitignore`）。

**为什么单独拆一份**：此前 `JWT_SECRET` / `AES_KEY` / `HMAC_KEY` 在三份 env 里各写一遍，靠人工保证逐字符一致。
2026-11-21 线上事故就是这套做法的必然结果 —— 只有 `message.env` 那份 `JWT_SECRET` 与另外两份不同，
表现为「登录成功后立刻被 401 踢回登录页」，而 booking 返回 200、classroom 也能过验签。
排查时几乎无从下手：**看文件看不出来，必须读 `/proc/<pid>/environ` 才见真相。**

现在三个 systemd 单元都按这个顺序加载：

```ini
EnvironmentFile=/etc/lesson/keys.env        # 共用密钥：唯一权威来源
EnvironmentFile=/etc/lesson/booking.env     # 服务私有配置
```

★ **顺序不能反**：systemd 是「后加载覆盖先加载」，共用凭据必须排前面。
同时三份 `xxx.env` 里**不得再出现本文件定义的任何一个键**（模板里已注释掉，不要打开）——
只要残留一个，就会把 `keys.env` 静默覆盖，重新变回「三处各自维护」。

**本文件现在管五样东西**：

| 键 | 作用 | 能否轮换 |
|---|---|---|
| `JWT_SECRET` | HS512 签名密钥 | ✅ 可（代价是全体重新登录） |
| `AES_KEY` | 字段加密（如 `user.name`） | ❌ **不可**，换了历史密文永久不可解 |
| `HMAC_KEY` | 可搜索索引签名 | ❌ **不可** |
| `DB_USERNAME` | MySQL 账号（三服务共用 `lesson`） | 可 |
| `DB_PASSWORD` | MySQL 密码 | 可（改完三服务都要重启） |

**`DB_USERNAME` / `DB_PASSWORD` 为什么也放这里**（2026-11-22 事故）：
三份 `xxx.env` 各写一遍密码，其中一份与 MySQL 不一致 → 表现为**两级症状**：
先所有查库接口卡 30 秒（Hikari `connectionTimeout`，日志只有一句 `MyBatisSystemException`，完全看不出是密码问题），
`restart` 之后才暴露真错误 `Access denied for user 'lesson'@'localhost' (using password: YES)`。
详见 **§6.7**。

★ **`host` 形态必须分清**：MySQL 默认 `skip_name_resolve=OFF`，从 `127.0.0.1` 发起的 TCP 连接会被反解成
主机名 `localhost`，命中的是 **`'lesson'@'localhost'`**，而不是 `'lesson'@'127.0.0.1'`。
这两个 host 是**两个独立账号、各有各的密码**——只授权/只改密码其中一个，就会出现「课堂正常、booking 401」这类错位。

```bash
sudo vi /etc/lesson/keys.env          # 填入 3.5.0 生成的三项 + 数据库账号密码
sudo chmod 600 /etc/lesson/keys.env

```

**从「三份 env 各写一份 DB 密码」的旧结构迁移（服务器上执行一次，幂等）**

⚠️ 关键：只往 `keys.env` 里加值、却不在 `xxx.env` 里删掉，**等于没做** ——
systemd 是「后加载覆盖先加载」，`xxx.env` 里那一行会把 `keys.env` 的值冲掉。

```bash
# ① 取现有值（挑一份当前能连通的，通常是 classroom.env；连不上就试 booking.env）
U=$(sudo sed -n 's/^DB_USERNAME=//p' /etc/lesson/classroom.env | tr -d '\r')
P=$(sudo sed -n 's/^DB_PASSWORD=//p' /etc/lesson/classroom.env | tr -d '\r')

# ② 写入 keys.env（先删后加，保证只有一份且不重复）
sudo sed -i '/^DB_USERNAME=/d; /^DB_PASSWORD=/d' /etc/lesson/keys.env
printf 'DB_USERNAME=%s\nDB_PASSWORD=%s\n' "${U:-lesson}" "$P" | sudo tee -a /etc/lesson/keys.env >/dev/null

# ③ 三份 env 里必须删掉
for f in booking message classroom; do
  sudo sed -i '/^DB_USERNAME=/d; /^DB_PASSWORD=/d' /etc/lesson/$f.env
done

# ④ 复核：三份都应是 0，keys.env 应各 1 行
for f in booking message classroom; do
  printf "%-12s %s\n" "$f.env" "$(sudo grep -cE '^(DB_USERNAME|DB_PASSWORD)=' /etc/lesson/$f.env)"
done
sudo grep -cE '^(DB_USERNAME|DB_PASSWORD)=' /etc/lesson/keys.env

# ⑤ 重启（env 只在进程启动时读取一次）
sudo systemctl restart booking message-service classroom-service
```

**校验（必做，看进程不看文件）**：

```bash
for s in booking-api message-service classroom-service; do
  PID=$(pgrep -f "$s.jar" | head -1)
  V=$(sudo tr '\0' '\n' < /proc/$PID/environ | sed -n 's/^JWT_SECRET=//p')
  printf "%-18s len=%-4s sha16=%s\n" "$s" "${#V}" "$(printf %s "$V" | sha256sum | cut -c1-16)"
done
```

三行的 `len` 与 `sha16` 必须完全相同。`len` 差 1 多半是 env 文件混入了 CRLF（用 `cat -A` 看是否有 `^M$`）。

⚠️ `AES_KEY` / `HMAC_KEY` **不可随意轮换**：它们加密落库的敏感字段（如 `user.name`），
换掉后历史密文**永久不可解且不报错**，只会看到姓名变乱码。`JWT_SECRET` 可以安全轮换，代价是所有人重新登录。

#### 3.5.3 文件 `/etc/systemd/system/booking.service`

> **`$JAVA_OPTS` 必须写在 `ExecStart` 里**：`EnvironmentFile` 只是把变量放进进程环境，JVM **不会自动读取** `JAVA_OPTS`（JVM 只自动读 `JAVA_TOOL_OPTIONS` / `JDK_JAVA_OPTIONS`）。漏写会导致 `-Xms/-Xmx` 失效；若里面还塞了别的参数，甚至会启动即崩、被 systemd 判定 `Start request repeated too quickly`。

```ini
User=lesson
Group=lesson
WorkingDirectory=/opt/lesson
EnvironmentFile=/etc/lesson/booking.env
```

下面是同一份配置的完整形态，照着核对/手抄都行。**三个服务靠 location 前缀分流**，
分流清单必须与 `doc-develop/90-tools/dev-proxy.js` 及 `deploy/nginx/booking-ip.conf` **逐字一致**。

```nginx
server {
    listen 80;
    server_name booking.example.com;
    location /.well-known/acme-challenge/ { root /var/www/html; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl http2;
    server_name booking.example.com;

    ssl_certificate     /etc/letsencrypt/live/booking.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/booking.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    # 课堂整包直传上限 100MB（分片每片 5MB 走不到这里，但直传会 413）
    client_max_body_size 105m;

    # 前端静态资源（dist 的内容）
    root /var/www/frontend;
    index index.html;
    location / {
        try_files $uri $uri/ /index.html;      # SPA 兜底
    }
    # platform_admin.html 就在这份 dist 里，不需要任何反代

    # ==================================================================
    # /api/v1 三分流：消息 → 8090，课堂 → 8092，其余 → 8081
    # nginx 取最长前缀匹配，书写顺序无关；^~ 用来压制静态资源正则（见下方说明）
    # ==================================================================

    # ── 1) 消息服务 8090 ─────────────────────────────────────────────
    # 前缀 /api/v1/message 覆盖 messages / message-categories / message-templates
    location ^~ /api/v1/message {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
        proxy_set_header Connection '';
    }
    location ^~ /api/v1/sensitive {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
    }
    location ^~ /api/v1/users/ {           # ★ 复数，消息服务的收件人台账
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
    }
    location ^~ /api/v1/sse {              # SSE：关缓冲 + 长超时，少一条就"连上收不到"
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_http_version 1.1;
        proxy_set_header Connection '';    # 不发 Connection: close
        chunked_transfer_encoding on;
    }

    # ── 2) 课堂服务 8092（17 个 location / 24 个端点，一个都不能少）──────────
    location ^~ /api/v1/classrooms/  { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/attendance/  { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/recordings/  { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/schedules/   { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }  # ★复数；主服务是单数 schedule
    location ^~ /api/v1/rtc/         { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/uploads/ {          # 分片上传：低带宽下单片可能超 60s
        proxy_pass http://127.0.0.1:8092;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 300s;
        client_max_body_size 105m;
    }
    location ^~ /api/v1/files/ {            # 签名 URL 直取，依赖 Range（拖动/倍速要 206）
        proxy_pass http://127.0.0.1:8092;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 300s;
    }
    # 运营台：逐个精确前缀，**不能**用 /api/v1/admin/ 一刀切（主服务也有 admin 语义接口）
    location ^~ /api/v1/admin/classrooms/ { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/monitor/    { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/reports/    { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/reconcile/  { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/audit/      { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/contract/   { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/exports/ {    # 流式 CSV，大跨度较慢
        proxy_pass http://127.0.0.1:8092;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 300s;
        proxy_buffering off;
    }
    # ★ 精确匹配：/api/v1/admin/classrooms **本身**（无子段）必须单独一条。
    #   上面的 '/api/v1/admin/classrooms/' 要求末尾斜杠，因此"建临时课堂"这类请求会落到
    #   兜底的 /api/v1/ → 8081，而主服务没有该映射 → 403「无权限访问该资源」。
    #   2026-11-19 真实踩过，看着像权限问题、其实是分流漏了一条。nginx 里 `location =` 优先级最高。
    location = /api/v1/admin/classrooms {
        proxy_pass http://127.0.0.1:8092;
        include /etc/nginx/proxy_params;
    }

    # ── 3) 课堂 WebSocket（白板/心跳/信令）───────────────────────────
    # 少 Upgrade 头 → 101 变 400；超时给不够 → 进去一会儿就掉线重连
    location ^~ /ws/classrooms/ {
        proxy_pass http://127.0.0.1:8092;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;
        proxy_set_header X-Real-IP  $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }

    # ── 4) 课堂回调落点：必须钉在 8081（课堂 → 预约系统的回执）─────────
    location ^~ /api/v1/classroom-callback/ {
        proxy_pass http://127.0.0.1:8081;
        include /etc/nginx/proxy_params;
    }

    # ── 5) 其余全部 → 主服务 8081 ────────────────────────────────────
    # 含 /api/v1/eclassroom（课堂开关，属主服务）、/api/v1/msg-ledger（消息台账，属主服务）
    location ^~ /api/v1/ {
        proxy_pass http://127.0.0.1:8081;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 120s;
    }

    # ── 6) 静态资源长缓存（可选）─────────────────────────────────────
    # ★ 一旦加了这个正则，所有 API location 必须带 ^~，否则 *.mp4 / *.png 结尾的
    #   API 路径（如 /api/v1/files/<token>.mp4）会被当静态文件处理并 404。
    location ~* \.(js|css|png|jpg|jpeg|gif|svg|ico|mp4|webm|woff2?|ttf|eot)$ {
        expires 7d;
        access_log off;
    }
}
```

> `include /etc/nginx/proxy_params;` 已含 `Host` / `X-Real-IP` / `X-Forwarded-For` / `X-Forwarded-Proto`。
> 发行版若无此文件，改成显式四行：
> ```nginx
> proxy_set_header Host $host;
> proxy_set_header X-Real-IP $remote_addr;
> proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
> proxy_set_header X-Forwarded-Proto $scheme;

> ```

**证书**：

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d booking.example.com      # 自动续期
```

#### 3.5.7 文件 `/opt/lesson/backup.sh`（每日备份）

仓库模板：`deploy/backup.sh`。先建免密凭据，再配定时任务：

```bash
sudo mysql_config_editor set --login-path=backup --host=localhost --user=root --password
# 输入 root 密码（加密存储，脚本里不写明文）

sudo chmod +x /opt/lesson/backup.sh
sudo crontab -e
# 追加一行：
0 3 * * * /opt/lesson/backup.sh >> /var/log/lesson/backup.log 2>&1
```

脚本内容**不要抄**：直接用仓库里的 `deploy/backup.sh`（2026-11-20 已把课堂库与课堂文件补齐，
且修掉了"失败被当成成功"的隐患）。文档里再抄一份必然与仓库漂移，所以这里只讲设计要点与产物。

备份范围（4 类产物，落在 `/opt/backup/`）：

| 产物 | 内容 | 保留 |
|---|---|---|
| `lesson_appointment_<日期时间>.sql.gz` | 业务主库 | 14 天 |
| `message_center_<日期时间>.sql.gz` | 消息中心 | 14 天 |
| `classroom_<日期时间>.sql.gz` | 在线课堂 | 14 天 |
| `oss_<日期时间>.tar.gz` | `/opt/lesson/data/oss`（讲稿/作品/**录制**） | **3 天** |

三个要点（都写进了脚本注释，这里给出理由，便于排障时判断"为什么不按想象的走"）：

|  |  |
| --- | --- |
1. **`set -o pipefail` 是必须的**。`mysqldump | gzip > out` 的退出码只看管道**最后一个**命令；
   凭据错 / 库不存在时 mysqldump 报 1045 就退了，gzip 照样产出 **20 字节空包**。
   没有 pipefail 时脚本会认为备份成功：留下假备份 + 照常清理过期文件，直到要回滚那天才发现全空。
   脚本另加「产物必须 > 100 字节」兜底。
2. **失败不留半截文件、整脚本 exit 1**。残缺的 `.sql.gz` 恢复时可能只导进半张表，
   比没有更危险。某项失败不阻断其它项，但退出码非 0，cron 日志里看得见。
3. **两类分开保留、且只清本轮成功的那一类**。录制文件可达 GB 级，14 份全量会撑爆磁盘
   （脚本在超过 `OSS_WARN_MB` 时会告警并提示改 rsync 增量）；而过期清理若不分类型，
   会出现"某天数据库备份失败、却把历史 DB 备份全删了"。

可调环境变量：`DB_KEEP_DAYS`、`OSS_KEEP_DAYS`、`OSS_ROOT`、`BAK_DIR`、`OSS_WARN_MB`、
`BACKUP_DBS=0`（只备文件）、`BACKUP_OSS=0`（只备库）。

**恢复（库与文件必须同一时间点；恢复前先停 classroom-service）**：

```bash
gunzip < /opt/backup/classroom_20261120_030000.sql.gz | mysql -uroot -p classroom
sudo tar -xzf /opt/backup/oss_20261120_030000.tar.gz -C /opt/lesson/data/oss
sudo chown -R lesson:lesson /opt/lesson/data/oss
```

> **为什么必须备课堂文件**：DB 里只存对象 key，真实字节在 `STORAGE_LOCAL_ROOT`。
> 只备库不备文件，恢复后课堂里的讲稿/作品/录制全是"记录在、文件没了"（点开 404）。
> 文件量大时用 `rsync -a` 推到对象存储/另一台机器做异地增量，比在本机留全量包更合适。

### 3.6 启动与验证

```bash

systemctl status booking message-service classroom-service --no-pager
ss -lntp | grep -E '8081|8090|8092|6379'      # 应只监听 127.0.0.1

# ② 直连后端（只有缺省页，200 即活着）
curl -s -o /dev/null -w "8081 %{http_code}\n" http://127.0.0.1:8081/
curl -s -o /dev/null -w "8090 %{http_code}\n" http://127.0.0.1:8090/
curl -s -o /dev/null -w "8092 %{http_code}\n" http://127.0.0.1:8092/
curl -s http://127.0.0.1:8081/platform_admin.html   # 期望 {"code":404,...}：后端无静态资源，正常

# ③ 课堂的两个隐性依赖（最容易"起了但功能不全"）
redis-cli -n 2 ping                                   # PONG
curl -s http://127.0.0.1:8092/api/v1/rtc/providers | head -c 300; echo   # configured/active/degraded
ls -ld /opt/lesson/data/oss && sudo -u lesson touch /opt/lesson/data/oss/.probe && sudo rm -f /opt/lesson/data/oss/.probe

# ③-b 课堂容量准入是否启用（2026-11-20 新增；INSTANCE_CODE 漏了会静默不生效）
sudo grep "\[capacity\]" /var/log/lesson/classroom/*.log | tail -2
#   期望：「容量准入已启用：instance_code=default-local, max_capacity=200」
#   若是「未配置 classroom.instance-code」→ 回 3.5.2b 的 env 补 INSTANCE_CODE 并重启 8092
grep -c "40908" /var/log/lesson/classroom/*.log | tail -1     # 被容量拒绝的次数，长期应为 0

# ④ 经 Nginx：页面
SITE=http://你的域名或IP
for p in index.html admin.html platform_admin.html student.html teacher.html booking.html; do
  printf '%-24s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' $SITE/$p)"
done
# 全部 200 说明前端 dist 就位

# ⑤ 经 Nginx：三分流是否各落对家
curl -s $SITE/api/v1/system/info          | head -c 120; echo   # booking（兜底）
curl -s $SITE/api/v1/message/system/info  | head -c 120; echo   # message-service（兼容别名路径）
curl -s $SITE/api/v1/rtc/providers        | head -c 120; echo   # classroom-service
curl -s -o /dev/null -w "callback %{http_code}\n" -X POST $SITE/api/v1/classroom-callback/ping   # 401/403 正常，404 说明被 8092 抢
curl -s -o /dev/null -w "eclassroom %{http_code}\n" $SITE/api/v1/eclassroom/config                # 401/403 正常，404 说明前缀写错
curl -s -o /dev/null -w "admin/classrooms %{http_code}\n" -X POST $SITE/api/v1/admin/classrooms   # 401/400 正常；**403「无权限访问该资源」= 落到 8081**，缺 location = 精确块
```

> **密钥是否真的生效（3.5.0 那个坑的验收）**：三个服务的日志里不应出现
> `crypto.aes-key 使用内置默认值` 之类的告警；另一种硬核验证是把它当成"三个服务用自己的
> `AES_KEY` 加解密同一库字段仍能互通"来测 —— 只要三份 env 的 `AES_KEY` 一致，跨服务读写就正常。
> 若怀疑仍在使用默认密钥，用 `systemctl show classroom-service -p Environment` 看不到值（EnvironmentFile 不在此列），
|  |  |  |  |  |
| --- | --- | --- | --- | --- |
> 直接用 `sudo tr '\0' '\n' < /proc/$(pgrep -f classroom-service.jar | head -1)/environ | grep -E 'AES_KEY|HMAC_KEY|JWT_SECRET'`
> 确认进程环境里到底有没有这三个变量。


### 3.7 防火墙 / 安全组

腾讯云控制台 → 防火墙，**只放行**：

| 端口 | 来源 | 用途 |
|------|------|------|
| 22 | 你的常用 IP（建议） | SSH |
| 80 | 0.0.0.0/0 | HTTP（跳转 HTTPS） |
| 443 | 0.0.0.0/0 | HTTPS |

**不开放**：8081、8090（Nginx 内部转发）、3306（MySQL 只本机）。

```bash
sudo ufw allow 22,80,443/tcp && sudo ufw enable
```

> **⚠️ 上线后务必自查**：若 `http://服务器IP:8081` 从外网能直接打开，说明后端端口对外暴露了。
> 除在安全组删掉 8081/8090 规则外，还应让 jar **只监听本机回环**（纵深防御）：
>
> ```bash
|  |  |
| --- | --- |
> echo 'SERVER_ADDRESS=127.0.0.1' | sudo tee -a /etc/lesson/booking.env
> echo 'SERVER_ADDRESS=127.0.0.1' | sudo tee -a /etc/lesson/message.env
> echo 'SERVER_ADDRESS=127.0.0.1' | sudo tee -a /etc/lesson/classroom.env
> sudo systemctl restart booking message-service classroom-service
|  |  |  |  |
| --- | --- | --- | --- |
> ss -lntp | grep -E '8081|8090|8092'   # 应显示 127.0.0.1:8081 / :8090 / :8092
> ```
>
> （`SERVER_ADDRESS` 经 Spring Boot 宽松绑定映射为 `server.address`。）
>
> **Redis 不要跟着改成公网可访问**：课堂只需要本机连 6379，`bind 127.0.0.1` 即可（见 3.1）。
> 云托管的「云数据库 Redis」则相反 —— 要走内网地址并在 `classroom.env` 里改 `REDIS_HOST`。

### 3.8 启用 HTTPS（正式环境；**需要域名**）

> **正规证书只签域名，不签 IP。** `https://152.136.254.127` 这种写法拿不到 Let's Encrypt /
> 腾讯云免费 DV 证书，只能自签（浏览器红字告警，且**微信内打不开** —— 微信只认受信任证书）。
> 本地开发的自签做法见《本地开发HTTPS自签名操作手册.md》，服务器上不建议长期使用。
>
> **只有 IP、暂时没有域名** → 不要照本节做，改看
> **《纯IP环境HTTPS自签配置清单-20261122-1645.md》**：`deploy/nginx/gen-selfsigned-cert.sh` 生成两级自签证书，
> 再按需要三选一启用 `booking-ip.conf`（纯 HTTP）/ `booking-ip-https.conf`（仅 HTTPS）/
> `booking-ip-dual.conf`（**HTTP + HTTPS 双栈**，兼容脚本探测与微信外的老客户端）。
> 该清单里写明了自签的硬边界：微信内置浏览器与微信小程序均不可用，课堂音视频必须 https。

**仓库里已有可直接落地的模板**：`deploy/nginx/booking-https.conf`
—— 分流 location 与 `booking-ip.conf` **逐条一致**（`check:proxy` 五份站点一起校验，
以后加课堂端点任一文件不同步就判红），差异只在 server 级别。

**步骤**

```bash
# ① 安全组放通 443（80 必须保留：ACME 校验 + 跳转）；ufw 同样
sudo ufw allow 22,80,443/tcp

# ② 域名 A 记录指向本机，等解析生效
dig +short your.domain.com

# ③ 先放 zone 定义（漏了会报 zero size shared memory zone，见 6.2）
sudo cp deploy/nginx/conf.d/00-limit-req-zone.conf /etc/nginx/conf.d/

# ④ 签发证书（webroot 方式，不改配置，最可控）
sudo apt install -y certbot
sudo mkdir -p /var/www/html/.well-known/acme-challenge
sudo certbot certonly --webroot -w /var/www/html -d your.domain.com \
     --deploy-hook "systemctl reload nginx"

# ⑤ 落地站点：全文只有 your.domain.com 需要替换（4 处）
sudo cp deploy/nginx/booking-https.conf /etc/nginx/sites-available/booking-https
sudo sed -i 's/your\.domain\.com/实际域名/g' /etc/nginx/sites-available/booking-https

# ⑥ 与 IP 版二选一，别同时启用（否则 80 上两个站点抢请求）
sudo rm -f /etc/nginx/sites-enabled/booking-ip /etc/nginx/sites-enabled/default
sudo ln -sfn /etc/nginx/sites-available/booking-https /etc/nginx/sites-enabled/booking-https
sudo nginx -t && sudo systemctl reload nginx
```

**验证**

```bash
curl -I https://your.domain.com          # 200 + strict-transport-security
curl -I http://your.domain.com           # 301 → https
sudo certbot renew --dry-run             # 演练续期（自带 systemd timer，每天两次）
```

**五个 HTTPS 专项坑（都在模板里写了注释）**

| # | 坑 | 说明 |
|---|---|---|
| 1 | `http2 on;` 在 nginx **1.24** 上直接报 `unknown directive` | 1.24（Ubuntu 22.04 默认）必须写成 `listen 443 ssl http2;`；1.25.1 起才支持独立的 `http2 on;` |
| 2 | **课堂 WebSocket 变成混合内容** | 后端 `buildWsUrl` 恒输出 `ws://`。实例的 `api_host`/`ws_host` 必须保持 **`127.0.0.1`**——前端 `feature-flags.js` 会把回环地址判空，从而改用同源 `wss://<域名>`；填成域名或公网 IP 反而会在 https 页面被浏览器拦掉 |
| 3 | 443 上漏了 `/ws/classrooms/` | 表现是「HTTP 页面一切正常，HTTPS 下白板不刷新、课堂反复重连」，Network 里 WS 请求 failed 而非 101 |
| 4 | `client_max_body_size` 不一致 | `booking-ip.conf` 与 `booking-https.conf` 的 `/api/v1/uploads/` 必须**同时**调（课堂单文件 100MB → 105m），否则出现「HTTP 能传、HTTPS 413」 |
| 5 | HSTS 一步到位 | `max-age=31536000` 被浏览器记住后**没法退回 HTTP**。首次上线建议先 `max-age=300` 跑一天，确认页面无 http 资源再改长 |

**切换后必须回归的四项**（漏一个就会在事后才炸）：
① 登录 → 平台首页正常；② 进课堂，Network 里 `wss://<域名>/ws/classrooms/...` 是 **101**；
③ 上传 >20MB 讲稿成功；④ 消息中心能实时收到（SSE 不被缓冲、不 60s 断）。

> `proxy_params` 里的 `X-Forwarded-Proto $scheme` 是后端识别 https 的唯一来源
> （配合 `server.forward-headers-strategy=framework`），**勿删**，否则重定向和绝对链接会退回
> http 被浏览器当混合内容拦掉。

### 5.1.1 服务起不来时，如何看到真正的错误

systemd 只会给 `Failed with result 'exit-code'`，**真实原因在 Java 输出里**。按下面的顺序查：

```bash
# ① 看退出码（先看这个，能直接分大类）
systemctl show booking -p ExecMainStatus -p ExecMainCode

# ② 抓 Java 报错关键字
journalctl -u booking -n 200 --no-pager | grep -iE "status=|Unable to access|Failed to load environment|Caused by|Exception|Port .* was already in use" | head -30

# ③ 前台直接跑（最准，报错会打在当前终端，Ctrl+C 退出）
cd /opt/lesson
sudo -u lesson bash -c 'set -a; . /etc/lesson/booking.env; set +a; /usr/bin/java $JAVA_OPTS -jar /opt/lesson/booking-api.jar'
```

**退出码 / 报错 → 原因对照**：

| 看到 | 含义 | 修复 |
|---|---|---|
| `status=203/EXEC` | `java` 路径不对，或 jar 不存在/无权限 | `which java` 核对路径；`ls -l /opt/lesson/*.jar`；`chmod 644` |
| `status=217/USER` | `User=lesson` 不存在 | `sudo useradd -r -s /bin/false lesson` |
| `Failed to load environment files` | `/etc/lesson/booking.env` 不存在 | 按 3.5.1 建 env |
| `Unable to access jarfile` | `ExecStart` 里的 jar 名与实际不符 | 按 `ls /opt/lesson/*.jar` 的真实名改，或建软链 |
| `Communications link failure` / `Access denied for user` | 数据库连不上 | 查库是否存在、`lesson` 账号授权、env 里密码 |
| `Port 8081 was already in use` | 端口被占（旧进程） | `sudo fuser -k 8081/tcp` 后重启 |
| `Illegal base64` / 密钥长度相关异常 | `AES_KEY`/`HMAC_KEY` 不是 32 字节，或 `JWT_SECRET` 太短 | 按 3.5.0 重新生成 |
| `Unable to connect to Redis` / 课堂日志反复重连 | Redis 没起、密码没配、或 `REDIS_HOST` 写错 | `redis-cli -n 2 ping`；设了 requirepass 就要配 `SPRING_DATA_REDIS_PASSWORD` |
| 课堂上传/录制报 `Permission denied` | `/opt/lesson/data/oss` 属主不是 lesson | `sudo chown -R lesson:lesson /opt/lesson/data/oss` |
| 课堂页 403「课堂未启用」 | `sys_eclassroom_instance` 无该租户行，或 `TenantEclassroomService` 的 5 分钟缓存未过期 | 先查表有没有行（3.3 校验），再等缓存过期或重启课堂 |
| 课堂 WebSocket 400/101 失败 | Nginx 少 `Upgrade` 头或超时太短 | 按 3.5.5 的 `/ws/classrooms/` 段核对 |
| `Start request repeated too quickly` | 连续失败触发了启动限流（不是新毛病） | 修完根因后先 `sudo systemctl reset-failed booking` 再 start |

> 触发限流后 systemd 会拒绝再次启动，**必须**先 `systemctl reset-failed booking`，否则会一直看到同样的提示。

#### 5.5.1 业务接口 HTTP 状态语义（2026-10-10 起生效，建告警前必读）

自 29-b 方案 A 上线后，业务接口的 HTTP 状态**不再是恒 200**：

| 业务结果 | HTTP | body.code | 说明 |
|---|---|---|---|
| 成功 | 200 | 200 | 不变 |
| 业务失败（参数/状态错误） | **400** | 400 | 新：以前伪装成 200 |
| 资源不存在 | **404** | 404 | 新：以前伪装成 200 |
| 冲突（并发/重复） | **409** | 409 | 新：以前伪装成 200。2026-10-11 起新增来源：**时间态闸**（课次已开始不可请假/改期、有已开始课次的预订不可取消、已开始排期不可再预订——属正常业务拒绝，不是故障） |
| 服务器内部错误 | **500** | 500 | 新：以前伪装成 200 |
| 业务 401/403（非鉴权失效） | **200** | 401/403 | 保持 200：映射会触发前端刷新/踢登录 |
| 真鉴权失效（token 无效/过期） | 401 | 401 | Security 过滤器层直出，未变 |

对巡检/告警的影响：

- `deploy/healthcheck.sh` 走 `/actuator/health/readiness`，**不受影响**，维持期望 200。
- 静态页与 `/api/v1/system/info` 探针不受影响。
- **基于 Nginx 访问日志状态码新建告警时**：4xx 现在包含正常业务失败（用户输错参数、
  删除不存在的记录等），不能一见 4xx 就告警；建议只对 5xx 比例或 401 激增设阈值。
- 前端/小程序拦截器已按上表消费（body 真实文案优先），无需改动。

## 第 6 章 故障速查表

### 6.0 首页显示 "Welcome to nginx!"（第一坑，先查这里）

> **这句话的含义**：Nginx 在跑、也在响应，但**请求落到了 Nginx 自带的默认 server**（Ubuntu 默认页 `/var/www/html/index.nginx-debian.html`）。
> 即：**我们的站点配置没被用上**，与后端 jar、前端 dist 都无关。

**第一步：一条命令看清 Nginx 实际加载了什么**

```bash
sudo nginx -T | grep -nE "server_name|^ *root |listen |include .*conf"   # 全部生效配置
ls -l /etc/nginx/sites-enabled/                                          # 启用了哪些站点
grep -rn "index.nginx-debian\|/var/www/html" /etc/nginx/sites-enabled/   # 谁在提供这个默认页
```

**第二步：对照定位**

| 现象（`ls -l /etc/nginx/sites-enabled/`） | 根因 | 修复 |
|---|---|---|
| 只有 `default`，没有 `booking` / `booking-ip` | 站点**没启用**（只写了 sites-available，忘了软链） | `sudo ln -s /etc/nginx/sites-available/booking-ip /etc/nginx/sites-enabled/` |
| `default` 与 `booking` **同时存在** | `default` 带 `default_server`，抢先接管 | `sudo rm -f /etc/nginx/sites-enabled/default` |
| 启用的是 `booking`（域名 + 443），却用 **IP + 80** 访问 | server_name 不匹配 + 只监听 443 → 落到默认 server | 改用 `booking-ip.conf`（80 + `server_name _`），或改用域名访问 |
| 系统**没有 sites-enabled 目录**（CentOS/Rocky/Alma） | 这些发行版只 include `/etc/nginx/conf.d/*.conf` | 把配置放到 `/etc/nginx/conf.d/booking.conf` |
| 配置看着对但没生效 | 改完没 reload | `sudo nginx -t && sudo systemctl reload nginx` |
| `nginx -t` 报错 | 语法错误（漏分号、括号不匹配最常见） | 按报错行号修，再 `nginx -t` |
| `nginx -t` 报 `open() "/etc/nginx/sites-enabled/xxx" failed (2: No such file or directory)` | **悬空软链**：只建了软链，`sites-available/` 里没有源文件（漏上传） | 在 `sites-available/` 建真实文件（内容见 3.5.5 / 3.5.6），或先 `rm /etc/nginx/sites-enabled/xxx` 再重建 |
| 软链已建、`default` 已删，外网**仍是**欢迎页 | 没 reload（改配置后 Nginx 仍用旧配置跑着）；或软链指向的文件内容不对 | `sudo nginx -t && sudo systemctl reload nginx`（reload 即可，不必 restart）；再 `grep -nE "root|server_name" /etc/nginx/sites-available/booking-ip` 核对内容 |
| 没有 `sites-enabled`，但 `/etc/nginx/conf.d/` 里有别的 `.conf` | 默认站点藏在 `conf.d`（Ubuntu 主配置两个 include 都生效） | `grep -rn "index.nginx-debian" /etc/nginx/conf.d/`，找到就 `rm` 或改 `server_name` |

**第三步：一键修复（无域名 / 按 IP 访问的场景）**

```bash
sudo rm -f /etc/nginx/sites-enabled/default
sudo ln -sf /etc/nginx/sites-available/booking-ip /etc/nginx/sites-enabled/booking-ip
sudo nginx -t && sudo systemctl reload nginx
```

**第四步：验证（用来区分"Nginx 没生效"还是"dist 没上传"）**

```bash
ls -l /var/www/frontend/index.html                          # 必须存在，否则是 dist 没上传
ss -lntp | grep ':80'                                       # Nginx 是否在听 80
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/  # 服务器内自测
curl -s http://127.0.0.1/ | head -3                         # 应看到我们自己的 HTML
curl -s http://127.0.0.1/api/v1/system/info | head -c 120; echo
```

- 自测 200 且是我们自己的页面 → 已生效（外网还看旧页就清缓存 / 换无痕窗口）
- 自测也是 Welcome → 回到第二步
- 自测 403/404 → `root` 路径错（常见：多了一层 `dist`，正确是 `/var/www/frontend`）
- 页面 OK 但接口 502/404 → 后端没起或分流没配（见 6.1）

### 6.2 `[emerg] zero size shared memory zone "api_zone"`（2026-11-21 实战）

**现象**

```console
$ sudo nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: [emerg] 3276120#3276120: zero size shared memory zone "api_zone"
nginx: configuration file /etc/nginx/nginx.conf test failed
```

**真实含义（本项目最容易误判的一条）**

`zero size` 的准确含义是：**有地方引用了 `api_zone`，但没有任何 `limit_req_zone` 给它定义尺寸**。

它出现在 `syntax is ok` **之后**——语法解析已经通过，失败发生在**共享内存初始化阶段**，解析期的位置信息已丢失，所以**这行不带文件名和行号**。极易被误读成「语法没问题，所以配置是对的」，实际是语法对、**定义那一半没加载**。

三种同源报错的区分：

| 报错文本 | 含义 | 带行号 |
|---|---|---|
| `zero size shared memory zone "api_zone"` | 有引用、无定义 | ❌ 不带，难查 |
| `unknown limit_req_zone "api_zone"` | 定义不存在（解析阶段就发现） | ✅ 带 `文件:行号` |
| `the shared memory zone ... is already declared for a different use` | 同名 zone 被 `limit_conn_zone` / `proxy_cache_path` 占用 | ✅ |

**为什么这条必须优先修：连锁后果**

nginx `reload` 失败时**旧 worker 不会停**，站点继续用**内存里的旧配置**服务。于是：

1. 磁盘上的配置是坏的，线上跑的是旧配置；
2. 之后所有 nginx 改动（课堂 7 个 `/admin/*` 分流、`location = /api/v1/admin/classrooms`）**一条都没上线**；
3. 表现为「配置明明改了却没变化」，而且**没有任何报错提示**。

本次事故中，2026-11-19 修的课堂分流因此拖了 20 多天未生效，后来直接表现为「创建临时课堂返回 301」。

> ⚠️ **铁律：修好前绝对不要 `systemctl restart nginx`。**
> 当前站点能正常服务完全依赖内存里的旧配置。一旦 restart，旧配置被卸载、磁盘配置又起不来，
> **nginx 会直接起不来 → 整站宕机**，连 `reload` 这条退路都没了。

**排查**

```bash
# ① 全量备份（先做，出问题能整体回滚）
sudo cp -a /etc/nginx /root/nginx.bak.$(date +%F-%H%M%S)

# ② 三件事一次看清
sudo ls -l /etc/nginx/conf.d/                       # zone 定义文件在不在
sudo grep -nE '^\s*include' /etc/nginx/nginx.conf   # include 链是否生效
sudo grep -rn 'limit_req_zone' /etc/nginx/          # 谁在定义 zone
```

判据：

| `grep limit_req_zone` 的输出 | 结论 | 修法 |
|---|---|---|
| **完全无输出** | 定义文件被删/清空/改名 | 见下方 A |
| 有输出但不含 `zone=api_zone` | 定义文件在，漏了这一条 | 见下方 B |
| 含 `zone=api_zone` | 定义在但未被 include | 见下方 C |

仓库内另有只读诊断脚本，可一次跑完全部检查：

```bash
sudo bash deploy/nginx/diagnose-limit-zones.sh
```

**处置**

```bash
# A. 定义文件缺失 —— 补回（4 个 zone：login / sms / public / api）
sudo cp deploy/nginx/conf.d/00-limit-req-zone.conf /etc/nginx/conf.d/

# C. include 被注释或丢失（要位于 http {} 内，且在 sites-enabled 之前）
sudo sed -i 's|^[[:space:]]*#[[:space:]]*include /etc/nginx/conf.d/\*\.conf;|    include /etc/nginx/conf.d/*.conf;|' /etc/nginx/nginx.conf

# 只有 -t 通过才 reload（必须看到 test is successful，不是只有 syntax is ok）
sudo nginx -t && sudo systemctl reload nginx
```

| zone | 尺寸 | 速率 | 覆盖范围 |
|---|---|---|---|
| `login_zone` | 10m | 5 r/s | `/api/v1/auth/login`、`user/register`、`promo/register-*` |
| `sms_zone` | 10m | 1 r/m | 短信验证码（预置，后端暂无短信端点） |
| `public_zone` | 10m | 50 r/s | `/api/v1/teacher/published`、`/actuator` 等匿名入口 |
| `api_zone` | 20m | 100 r/s | 其余业务接口 |

**逃生路径（急上线）**：找不到定义文件又急着让新配置生效时，可临时注释限流引用：

```bash
sudo cp /etc/nginx/sites-available/booking-ip /root/booking-ip.bak
sudo sed -i '/limit_req zone=/s/^[[:space:]]*/#/' /etc/nginx/sites-available/booking-ip
sudo nginx -t && sudo systemctl reload nginx
```

代价是限流暂时关闭（内测可接受，等保项需记待补）。`limit_req_status` 可以单独存在，不用注释。

**为什么反复出现**：`apt upgrade nginx` 会用默认版覆盖 `nginx.conf` 并丢掉 include；手工 `scp` 单文件时又容易只拷站点配置、不拷 `conf.d`。

**预防**

1. 不要单文件 `scp`，整目录同步：`sudo rsync -av deploy/nginx/ /etc/nginx/`；
2. 部署脚本把 `nginx -t` 的返回值当**硬门槛**，失败即中止——本次故障拖了 20 多天，就是因为 reload 失败没人看；
3. 定期 `sudo md5sum /etc/nginx/sites-available/* /etc/nginx/conf.d/*` 与仓库比对。

### 6.3 登录成功后立刻被踢回登录页（message-service 401）

**现象**：输入账号密码，提示「登录成功，正在跳转」，页面闪一下又回到 `login.html`。控制台只有三行：

```
[error]  Failed to load resource: 401 ()   /api/v1/users/<id>/inbox/unread-count
[error]  登录已过期，请重新登录            <js/messages-inbox.js>
[FAILED] Document net::ERR_ABORTED        ← platform_admin.html 加载被中断
```

**触发链**

```
platform_admin.html 加载
  └→ messages-inbox.js 拉未读数 GET /api/v1/users/{id}/inbox/unread-count
       └→ 8090 返回 401「登录状态无效，请重新登录」
            └→ retryWithFreshToken() 换票重试（messages-inbox.js:154）
                 └→ 新 token 仍 401
                      └→ rejectWithMessage() 的 401 分支（messages-inbox.js:180）
                           cleanupAuth() + 600ms 后跳 login.html
```

也就是说：**一个辅助接口（未读数）的 401，被升级成了整个会话失效**。

**根因**：`message-service` 的 `JWT_SECRET` 与 booking（签发方）不一致，`verifyAccessToken` 返回 false。

**关键判据：靠 401 文案反推请求落到哪个服务**

| 返回文案 / 字段 | 出处 | 含义 |
|---|---|---|
| `{"code":401,"message":"登录状态无效，请重新登录"}` | `MessageAuthInterceptor:34` / `classroom AuthInterceptor:45` | **验签失败**（token 到了但密钥不对） |
| `{"code":401,"message":"未登录，请先登录"}` | 同上第 29 行 | **头没带**（Authorization 缺失） |
| `{"code":401,"data":null,"message":"未登录或登录已过期"}` | booking `JwtAuthenticationFilter` | 请求落到了 **8081** |
| `{"code":401,"msg":"..."}` | booking `TenantInterceptor`（字段是 **msg** 不是 message） | 请求落到了 **8081** |

**排查（看进程，不看文件）**

```bash
for s in booking-api message-service classroom-service; do
  PID=$(pgrep -f "$s.jar" | head -1)
  V=$(sudo tr '\0' '\n' < /proc/$PID/environ | sed -n 's/^JWT_SECRET=//p')
  printf "%-18s len=%-4s sha16=%s\n" "$s" "${#V}" "$(printf %s "$V" | sha256sum | cut -c1-16)"
done
```

三行的 `len` 与 `sha16` **必须完全相同**。光比对 env 文件没用——`EnvironmentFile` 有覆盖关系，只有进程环境是真相。

**处置（2026-11-21 起改为单一权威来源）**

共用密钥已统一到 `/etc/lesson/keys.env`，三个 unit 都先加载它，三份 `xxx.env` 里不再定义这三个键：

```bash
sudo cp /opt/lesson/keys.env.template /etc/lesson/keys.env
sudo vi /etc/lesson/keys.env        # 填入真实值；AES/HMAC 必须原样沿用
sudo chmod 600 /etc/lesson/keys.env && sudo chown lesson:lesson /etc/lesson/keys.env

# 确认三份 xxx.env 没有残留（残留会按「后加载覆盖」把 keys.env 冲掉）
for f in booking message classroom; do
  printf "%-10s " $f; sudo grep -cE '^(JWT_SECRET|AES_KEY|HMAC_KEY)=' /etc/lesson/$f.env
done    # 期望三个都是 0
```

### 6.4 课堂接口三连：301 / 403 / 500

三个不同层次的问题，但常连着出现，且**后一个会把前一个盖住**——403 修好后才露出 500，很容易误以为「越修越多」。

#### 6.4.1 `POST /api/v1/admin/classrooms` 返回 301

```console
HTTP/1.1 301 Moved Permanently
Server: nginx/1.24.0 (Ubuntu)
Location: http://<host>/api/v1/admin/classrooms/
Content-Length: 178
```

**含义**：响应头是 nginx 自己生成的（标准 178 字节页面），说明请求落到了**静态 location**，被 `try_files $uri $uri/` 识别为目录后补斜杠，**根本没到 8092**。

**根因**：服务器上的站点配置缺这条精确匹配（`booking-ip.conf` 第 165 行附近）：

```nginx
# POST /api/v1/admin/classrooms（创建临时课堂）不带尾斜杠，
# 上面那条前缀 location（带斜杠）匹配不到 → 落到 location /api/v1/ → 进 8081 → 403
location = /api/v1/admin/classrooms {
    proxy_pass http://127.0.0.1:8092;
    include /etc/nginx/proxy_params;
}
```

**处置**

```bash
sudo nginx -T | grep -n -A3 "admin/classrooms"     # 确认这条是否存在
sudo diff /etc/nginx/sites-available/booking-ip deploy/nginx/booking-ip.conf
sudo cp deploy/nginx/booking-ip.conf /etc/nginx/sites-available/booking-ip
sudo nginx -t && sudo systemctl reload nginx
```

> ⚠️ 浏览器对 301 会把 **POST 降级成 GET**，所以「创建临时课堂」在修好前必然失败，且失败方式很误导（看起来像 404/405）。
> 另外这条通常和 §6.2 同源：配置改了但 reload 一直失败，所以从未上线。

#### 6.4.2 403「课堂未启用」

**来源**：`classroom-service` 的 `AuthInterceptor:62`。注意它是**直接写响应**：

```java
private void write403(HttpServletResponse response, String msg) throws Exception {
    response.setStatus(HttpServletResponse.SC_FORBIDDEN);   // ← 真正的 HTTP 403
    response.getWriter().write("{\"code\":403,\"message\":\"" + msg + "\"}");
}
```

拦截器绕过 `Result` 和 `ResultHttpStatusAdvice`，所以**它是全项目少数能产出真 HTTP 403 的地方**（业务层的 `Result.fail(403)` 一律保持 HTTP 200）。

**触发条件（两个豁免 + 四道关卡）**

```java
// AuthInterceptor:74  豁免
tenantId == null || 0 || -1  → 跳过（平台管理员）
role == "system"             → 跳过（服务间调用）

// TenantEclassroomService:79  四道关卡，任一不过即 false → 403
① sys_tenant_eclassroom 有该租户记录
② 该记录 enabled = 1
③ sys_eclassroom_instance 里 instance_id 对应实例存在、未删除
④ 该实例 status = 1
⑤ 查询不抛异常 ← 关键：catch 里静默降级为 false
```

> ⚠️ **第 ⑤ 关最容易误导**：`catch (Exception e) { log.warn("查询租户课堂开关失败(降级为false)"); return false; }`
> 跨库权限不足、字段类型不匹配、连接串库名错……全都表现为同一句话「课堂未启用」。
> 此时必须去翻 classroom-service 日志里的 `查询租户课堂开关失败` 才能看到真实异常。

**排查**

```bash
# ① 拿当前用户的 tenantId（用 sys_tenant.id，不是 tenantCode）
echo "$TOKEN" | cut -d. -f2 | tr '_-' '/+' | base64 -d 2>/dev/null

# ② 查两张表
mysql -e "SELECT id,tenant_id,instance_id,enabled,status FROM lesson_appointment.sys_tenant_eclassroom WHERE tenant_id=<id>;"
mysql -e "SELECT id,name,status,api_host,ws_base_path,deleted FROM lesson_appointment.sys_eclassroom_instance WHERE id=<instance_id>;"
```

| 现象 | 原因 | 修法 |
|---|---|---|
| ① 查不到行 | 未开通；平台端「解绑」是**物理 delete**，删一次所有租户一起没入口 | 平台端重新绑定，或导 `deploy/sql/patch/20261029-1300-eclassroom-default-instance.sql` |
| ① 有行但 `enabled=0` | 绑了未启用 | `UPDATE ... SET enabled=1 WHERE tenant_id=<id>;` |
| ② 无行 / `deleted=1` | 实例被删，`instance_id` 悬空 | 修正 `instance_id` |
| ② `status≠1` | 实例停用/维护中 | `UPDATE sys_eclassroom_instance SET status=1 WHERE id=<id>;` |
| 两张表都正常 | 走了第 ⑤ 关 | 看日志 `查询租户课堂开关失败` 的真实异常 |

**缓存坑**：`hasClassroomEnabled` 用**进程内 Map** 缓存 5 分钟。改完库不会立刻生效：

- 等 5 分钟，或
- `sudo systemctl restart classroom-service`（缓存是内存态，重启即清，比等更快）

只改库不清缓存 = 典型的「改了没生效」。

**另一个坑**：`ws_base_path` 只填 `/ws` 是错的——它是 WS **根路径**，不含 `/ws/classrooms`，填 `/ws` 会拼出 `/ws/ws/classrooms/...`，表现为课堂页反复重连。正确应为空串（走同源）或完整根路径。

#### 6.4.3 500 `Table 'lesson_appointment.classroom' doesn't exist`

```console
{"code":500,"message":"服务器繁忙：### Error querying database.
 Cause: java.sql.SQLSyntaxErrorException: Table 'lesson_appointment.classroom' doesn't exist
 ... com/classroom/mapper/ClassroomMapper.java"}
```

**含义**：课堂服务连到了 `lesson_appointment` 库，但课堂的 13 张表在 `classroom` 库。

| 位置 | 应为 |
|---|---|
| jar 内默认 `spring.datasource.url` | `jdbc:mysql://localhost:3306/**classroom**` |
| `deploy/classroom.env.template` | `jdbc:mysql://127.0.0.1:3306/**classroom**` |
| 实际报错 | `**lesson_appointment**.classroom` ❌ |

**根因**：`/etc/lesson/classroom.env` 的 `SPRING_DATASOURCE_URL` 是从 `booking.env` 复制来的，库名没改。这两份只有库名不同，一眼扫过去看不出。

**处置**

```bash
sudo sed -i '/^SPRING_DATASOURCE_URL=/d' /etc/lesson/classroom.env
sudo tee -a /etc/lesson/classroom.env >/dev/null <<'EOF'
SPRING_DATASOURCE_URL=jdbc:mysql://127.0.0.1:3306/classroom?useUnicode=true&characterEncoding=utf8&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true
EOF

# 确认库和表（应为 13 张）；没有就导 schema（自带 CREATE DATABASE + USE）
mysql -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='classroom';"
mysql -uroot -p < api/classroom-service/sql/classroom-schema.sql

sudo systemctl restart classroom-service
```

> ⚠️ 顺序：**先建库导表，再重启**。模板里的 URL 没有 `createDatabaseIfNotExist=true`（只有 jar 默认值里有），库不存在时服务会直接启动失败，而不是报这个 500。
>
> 附带一个判据：这个错误返回 **500 而不是 401**，反过来证明课堂服务的 JWT 验签是**通过**的——排查密钥问题时可以拿它当对照。

### 6.5 平台端「新增用户」里看不到刚建的租户

**现象**：平台管理端 → 用户管理 → 「新增用户」→ 角色选「租户管理员」，「所属租户」下拉里没有刚创建的租户。

**根因**（前端页面级缓存，不是后端）：`frontend/js/platform-admin-user.js`

```js
let __puTenantOptions = null;                                   // 页面级缓存
function loadTenantOptions(force) {
  if (__puTenantOptions && !force) return Promise.resolve(__puTenantOptions);   // 有缓存直接返回
  ...
}
loadTenantOptions(false).then(() => fillTenantSelect());        // ← 永远传 false
```

`force=false` 意味着**缓存一旦建立就永不刷新**。而平台端是 `<template>` 渲染的单页，切换菜单**不重载页面**，所以这份缓存能活整个会话——你在租户管理里新增了租户，回到用户管理再打开弹窗，下拉里还是第一次打开时的那份列表。

**第二个坑**：原 `catch` 把**空数组**也缓存了：

```js
.catch(() => { __puTenantOptions = []; return __puTenantOptions; });
```

只要有一次 token 过期或网络抖动，这个下拉就**永久停在空白**，之后网络恢复也不会重新请求（因为空数组被视为「已有缓存」）。表现像「租户全丢了」。

**已修**（2026-11-22）

```js
.catch(() => { __puTenantOptions = null; return []; });   // 失败不缓存，下次可重试
// 打开弹窗时强制刷新
loadTenantOptions(true).then(list => { fillTenantSelect(); /* 空态给出明确提示 */ });
```

改完需重新构建并上传 `dist`（源码改动不会自动生效）：

```bash
CODEBUDDY_SAFE_DELETE_ENABLED=0 node frontend/build.js
```

**5 秒区分「缓存」还是「数据」**：在线上页面按 **F5 强制刷新**后再打开弹窗。

- 能看到新租户 → 就是上面的缓存问题，构建后彻底解决；
- 还是看不到 → 查数据层：

```sql
SELECT id, tenant_code, org_name, status, deleted, created_at
FROM lesson_appointment.sys_tenant ORDER BY id DESC LIMIT 5;
```

`TenantService.listAll()` 只过滤 `deleted = 0`、**不过滤 status**，所以只要 `deleted=1` 就会从下拉里消失。
|  |  |  |

### 6.6 课堂服务全 500 / 管理端课堂全 403（`classroom` 库没给 `lesson` 授权，2026-11-22 实战）

**症状三连**（同时出现，很容易被当成三个 bug）：

| 位置 | 现象 |
|---|---|
| 平台端「在线课堂 → 课堂监视」 | 每个实例一行 `500 : {"code":500,"message":"服务器繁忙：MyBatisSystemException","data":null,"ok":false}` |
| 管理端（租户管理员） | 凡是课堂接口一律 **403**，返回体 `{"code":403,"message":"课堂未启用"}` |
| `/api/v1/eclassroom/config` | 200，但 `enabled:false`、`apiBaseUrl/wsBaseUrl` 全 null → 课堂菜单不出现 |

**第一判据：看 500 的文案形态，能区分"连接层"还是"SQL 层"** —— 这一步能省掉大半排查。

| 响应里的 message | 真实层次 | 日志里能看到 |
|---|---|---|
| `服务器繁忙：MyBatisSystemException`（**光秃秃一个类名**） | **拿不到 JDBC 连接**（库名/账号/密码/授权/MySQL 不可达/池耗尽） | `Caused by: CannotGetJdbcConnectionException: Failed to obtain JDBC Connection` |
| `服务器繁忙：### Error querying database. Cause: … Table 'x.classroom' doesn't exist`（**长文案**） | 连接是通的，**SQL 执行失败**（表/列不存在、语法错） | `Caused by: java.sql.SQLSyntaxErrorException: …` |

原因：`MyBatisSystemException` 的构造是 `super(null, cause)`，`getMessage()` 恒为 `null`，
而 `GlobalExceptionHandler` 走的是 `e.getMessage() == null ? 类名 : e.getMessage()`，于是只剩类名。
它只在 `PersistenceException` 的**直接 cause 不是 `SQLException`** 时产生 —— 连接层失败正是这种情况。

**第二判据：403 不是业务拒绝，是同一个故障的下游。**

```java
// AuthInterceptor:58  租户管理员（tenantId>0）先过课堂开关
if (!tenantEclassroomService.hasClassroomEnabled(tenantId)) → 403「课堂未启用」
// AuthInterceptor:74  平台管理员（tenantId=0/-1）与 role=system 豁免 → 直接进业务，撞上 500
```

`hasClassroomEnabled()` 查的是 `lesson_appointment.sys_tenant_eclassroom`，且有
`catch (Exception e) { log.warn("查询租户课堂开关失败(降级为false)"); return false; }` ——
**库连不上时异常被吞成 `false`**，于是"连不上库"伪装成"课堂未启用"。
所以：平台端 500 + 管理端 403 同时出现，基本可以断定是 classroom-service 的数据源问题，
**不要去查租户绑定的数据**（那些是好的）。

**定位（三条命令）**

```bash
# ① 真实原因（500 响应里看不到，只在日志）
sudo journalctl -u classroom-service -n 300 --no-pager \
  | grep -E "Access denied|Unknown database|Communications link failure|Connection is not available" | tail -3

# ② 进程实际吃到的账号（不是文件！缺 DB_USERNAME/DB_PASSWORD 会静默回落 jar 默认 root/123456）
PID=$(pgrep -f classroom-service.jar | head -1)
sudo tr '\0' '\n' < /proc/$PID/environ \
  | grep -E '^(DB_USERNAME|DB_PASSWORD|SPRING_DATASOURCE_URL)' | sed 's/\(DB_PASSWORD=\).*/\1***/'

# ③ 用应用账号按 JDBC 的方式真连一次（host 必须是 127.0.0.1，localhost 走 socket 是另一身份）
mysql -h127.0.0.1 -ulesson -p classroom \
  -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='classroom';"
```

③ 报 `ERROR 1044/1142 Access denied for user 'lesson'@'localhost' to database 'classroom'`
= **`classroom` 库没给 `lesson` 授权**，本次事故就是这个（前两个库有权限，课堂库后建、没补授权）。

**修复**

```bash
# 幂等脚本：补 classroom.* 全量 + 三张跨库表的只读；账号不存在时只告警不报错
mysql -uroot -p < deploy/sql/patch/20261122-1430-classroom-db-grant.sql

# 手工等价（最小集）
mysql -uroot -p <<'SQL'
GRANT ALL PRIVILEGES ON `classroom`.* TO 'lesson'@'127.0.0.1', 'lesson'@'localhost';
GRANT SELECT ON `lesson_appointment`.`sys_tenant_eclassroom`   TO 'lesson'@'127.0.0.1';
GRANT SELECT ON `lesson_appointment`.`sys_eclassroom_instance` TO 'lesson'@'127.0.0.1';
GRANT SELECT ON `lesson_appointment`.`booking`                 TO 'lesson'@'127.0.0.1';
FLUSH PRIVILEGES;
SQL

# ⚠️ 手工执行两个坑（表象都是"MySQL 不识别 GRANT"）：
#   · 在 bash 里直接粘贴 GRANT → `bash: GRANT: command not found`（此时还没进 mysql 会话）
#   · mysql -e "GRANT ... ON `classroom`.* ..." → 反引号先被 shell 当命令替换掉，
#     MySQL 收到残缺语句 → ERROR 1064；改用单引号包、或去掉反引号、或像上面那样用重定向执行
sudo systemctl restart classroom-service    # 顺带清掉课堂开关的 5 分钟内存缓存，403 才会立刻消失
```

**验证（两步都过才算通）**

```bash
SHOW GRANTS FOR 'lesson'@'127.0.0.1';        # 应含 classroom.* 与三条表级 SELECT

# 连接通了的标志：业务码 40401（HTTP 200），而不是 500 MyBatisSystemException
TOKEN=$(curl -s -X POST http://127.0.0.1:8081/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"account":"admin1@qq.com","password":"123456","tenantCode":"platform","role":"platform_admin","emuFlag":false}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8092/api/v1/schedules/probe123
# 期望：{"code":40401,"message":"课堂不存在：probe123",...}（HTTP 200）
```

**预防**

- 新环境严格按 **3.3** 顺序走：`deploy/sql/00-create-databases.sql` 里本就含三条 `GRANT`，
  漏跑它就会得到本篇这个状态（服务能启动、一查就 500）。
- **后加的库必须单独补授权**。课堂是第三个上线的模块，库往往后建，这是最容易漏的一步。
- 建完库立刻做第 ③ 条（用应用账号真连一次），比等服务报 500 再查省几个小时。
- 若给课堂**单独建账号**，三个跨库对象 + `classroom.*` 一个都不能少（见 3.3 的对照表）。

### 6.7 查库接口全部卡 30 秒 / `Access denied for user 'lesson'@'localhost'`（2026-11-22 实战）

**症状（有迷惑性的一点：它分两级表现）**

| 阶段 | 表现 | 日志 |
|---|---|---|
| 第一级 | 所有**查库**接口卡 **恰好 30.0 秒**后 500；不查库的接口（`/apiInfo`、`/system/info`）秒回 | 只有 `MyBatisSystemException`（message 恒为 null），看不出根因 |
| 第二级 | `systemctl restart booking` 后变成 **1~2 秒**快速 500 | `Access denied for user 'lesson'@'localhost' (using password: YES)` |

两级是**同一个原因**：密码不对 → Hikari 建连被拒 → 池里没有可用连接 → 每个请求等
`connectionTimeout`(默认 30s)；`restart` 把旧池清掉，旧连接（当初认证成功的那批）不复存在，
于是立刻暴露认证失败。

**30 秒这个数字就是判据**：Hikari 默认 `connectionTimeout=30000ms`。若看到「精确 30 秒」，
先怀疑连接获取，不要怀疑 SQL 慢。对照 `/actuator/health` —— 它含数据库探测，也会一起超时。

**定位（三条，按顺序）**

```bash
# ① 用「进程真实吃到」的密码手连，这一步能同时排除密码错、CRLF、行尾空格
PID=$(pgrep -f booking-api.jar | head -1)
PW=$(sudo tr '\0' '\n' < /proc/$PID/environ | sed -n 's/^DB_PASSWORD=//p')
/usr/bin/time -f "耗时 %es" mysql -h127.0.0.1 -ulesson -p"$PW" lesson_appointment -e "SELECT 1"

# ② 三份 env 的密码指纹（不打印明文）
for f in booking message classroom; do
  printf "%-10s " "$f"
  sudo sed -n 's/^DB_PASSWORD=//p' /etc/lesson/$f.env | tr -d '\n' | sha256sum | cut -c1-16
done

# ③ MySQL 侧有哪些 lesson 账号（host 不同就是不同账号）
sudo mysql -e "SELECT user,host,plugin FROM mysql.user WHERE user='lesson';"
```

**处置**

```bash
# 情况 A：某个服务唯独不通 → 把能通的那份值复制过去
P=$(sudo sed -n 's/^DB_PASSWORD=//p' /etc/lesson/classroom.env)
for f in booking message; do sudo sed -i "s|^DB_PASSWORD=.*|DB_PASSWORD=${P}|" /etc/lesson/$f.env; done

sudo mysql <<'SQL'

ALTER USER 'lesson'@'127.0.0.1' IDENTIFIED BY '<env 里的密码>';
FLUSH PRIVILEGES;
SQL

# 三种情况都要：重启（env 只在进程启动时读一次）
sudo systemctl restart booking message-service classroom-service
```

**根治（2026-11-22 起已落地）**：`DB_USERNAME` / `DB_PASSWORD` 并入 `/etc/lesson/keys.env`，
三份 `xxx.env` 不再出现（见 3.5.0b）。`npm run check:secret-env` 会拦住"残留生效值"，
反向测试 `npm run test:secret-env-guard` 共 11 条（含 4 条 DB 凭据变异）。

**两个易错点**

- `EnvironmentFile` 不做转义：密码含 `#`、空格会被截断，行尾 CRLF 会多一个 `\r`。
  用 `sudo cat -A /etc/lesson/keys.env | grep '^DB_PASSWORD='` 确认末尾没有 `^M$`。
- 只改文件不重启 = 没改。env 只在进程启动时读取，`daemon-reload` 只重读 unit、不重读 EnvironmentFile 的值到运行中的进程。

### 6.8 `CannotGetJdbcConnectionException`：连接都没拿到，别再去翻表结构（2026-11-22 实战）

**先分清三类「查库报错」，修法完全不重叠**

| 日志里最关键的那一句 | 含义 | 排查方向 |
|---|---|---|
| `Table 'xxx.tbl' doesn't exist` / `Unknown column` / `SQLSyntaxErrorException` | 连接**已通**，SQL 被 MySQL 拒 | 表/字段/DDL 对齐（见 6.4.3、`npm run check:ddl-align`） |
| `CannotGetJdbcConnectionException: Failed to obtain JDBC Connection` | 连接**没拿到**，SQL 一句都没发出去 | 本节（凭据 / 网络 / 池 / MySQL 存活） |
| `MyBatisSystemException` 且 `message` 为 null、只印类名 | 拿不到连接，且异常被 `super(null, cause)` 吞掉 | 同上，靠 `-A` 抓最深 cause |

**为什么看到的常是「光秃秃的包装」**：`CannotGetJdbcConnectionException` 由 Spring `DataSourceUtils` 抛出，
MyBatis 又包一层 `PersistenceException`，业务/Advice 再包成 500。真正判词在最下面
`Caused by: java.sql.*` 与 Hikari 自己的日志行。**永远用 `-A` 或 `grep "Caused by"` 往下翻，不要停在第一段。**

**反向定位：用 Mapper 方法名认出是哪个页面**

`### The error may involve com.reservation.mapper.XxxMapper.selectList` 里的方法名是唯一入口线索。
booking 里 `SystemConfigMapper` 的调用点只有两类：

| Mapper 方法 | 唯一调用点 | 对应页面 / 接口 |
|---|---|---|
| `selectList` | `SysConfigController.listAll` / `listByGroup` | 平台端「系统配置」，`GET /api/v1/sys/config/list`、`/api/v1/sys/config/group/{group}` |
| `selectOne` | `SysConfigService.getByKey`（被 `getInt/getBool/getString` 复用） | Dashboard、监控、在线人数等全站读配置处 |

> 所以看到 `selectList` = 只坏那一个列表页；看到 `selectOne` = 影响面是全站（几乎所有写操作也会连带失败）。

**服务归属靠包名（三者前缀不同，别想当然）**：`com.reservation.*` = booking；
`com.messagecenter.*` = message-service；`com.classroom.*` = classroom-service。
**三服务同时报 = MySQL 侧**（挂了 / 账号 / `max_connections`）；
**只有 booking 报 = booking 自己的 env 或池**。

> 顺带：classroom-service 抛的是同一个 `com.baomidou` / Spring 异常体系，包名前缀却不同，
> 所以从日志文件名（`classroom.log`）与包名两头都能确认归属。

**Hikari 的默认值（本项目没配 hikari，全是默认）**

`maximumPoolSize=10`、`minimumIdle=10`（固定 10 条）、`connectionTimeout=30000ms`、`maxLifetime=30min`、
无 `leakDetectionThreshold`。→ **精确 30 秒** = 取连接超时；**1~2 秒就 500** = 建连被立即拒（认证 / 端口 / 主机名）。

**五步取证（按序，30 秒定性）**

```bash
# ① 是现在还在发生，还是几天前的历史日志（别把历史当现场）
sudo journalctl -u booking --since "15 min ago" --no-pager | grep -c CannotGetJdbcConnectionException

# ② Hikari 自己的判词（根因都在这几行，MyBatis 包装里没有）
sudo journalctl -u booking --since "1 hour ago" --no-pager \
  | grep -iE "HikariPool|Connection is not available|too many connections|Access denied|Communications link|Unknown database"

# ③ 往下翻最深那层 cause（-A 之后再过滤 Caused by，取最后 5 条）
sudo journalctl -u booking -n 4000 --no-pager \
  | grep -A 120 "CannotGetJdbcConnectionException" | grep "Caused by" | tail -5

# ④ 三服务是否同时中招（同时 → MySQL 侧；只一个 → 该服务 env/池）
sudo journalctl -u message-service -u classroom-service --since "15 min ago" --no-pager \
  | grep -ciE "CannotGetJdbcConnection|Access denied|Communications link"

# ⑤ 绕开应用直接验账号与连接数
mysql -h127.0.0.1 -ulesson -p'<密码>' \
  -e "SELECT 1; SHOW STATUS LIKE 'Threads_connected'; SHOW VARIABLES LIKE 'max_connections';"
```

**判读表（把 ②③ 的输出对号入座）**

| 判词 | 根因 | 处置 |
|---|---|---|
| `Connection is not available, request timed out after 30000ms` 且 `active=10, idle=0, waiting=N` | 池被占满（慢查询 / 连接泄漏 / 并发突增） | `SHOW PROCESSLIST` 找长时间 `Sleep` 的连接；临时 `-Dspring.datasource.hikari.maximum-pool-size=20`；长期查泄漏点 |
| 同上，但 `active` 很小（0~2） | 拿不到新连接：建连被拒 | 走下面三行 |
| `Access denied for user 'lesson'@'localhost' (using password: YES)` | 密码错 / host 不匹配（`127.0.0.1` 反解成 `localhost`） | 见 6.7 全套 |
| `Communications link failure` / `Connection refused` | MySQL 没起或地址错 | `systemctl status mysql`；URL host 用 `127.0.0.1`，别用 `localhost`（可能走 IPv6） |
| `Unknown database 'xxx'` | 库名错 / 库没建 | `SHOW DATABASES LIKE 'xxx'` |
| `Too many connections` | MySQL 侧打满 | 先治连接泄漏，再谈调大 `max_connections` |
| 日志里**完全没有** Hikari 行，只有 MyBatis 包装 | `EnvironmentFile` 没加载到值，用了 `application.properties` 的兜底默认 | 见下一段「静默回落」，直接查 `/proc/<pid>/environ` |

**本项目独有陷阱：`${DB_PASSWORD:123456}` 的静默回落**

`api/src/main/resources/application.properties` 写的是：

```
spring.datasource.username=${DB_USERNAME:root}
spring.datasource.password=${DB_PASSWORD:123456}
```

`/etc/lesson/keys.env` 只要**没被成功加载**，应用**不会报"变量缺失"**，而是静默用 `root/123456`，
然后过一会才在某个查库接口长出本节这条错。让它"没被加载"的四种写法错误，全都**不报错**：

| 错误写法 | 结果 |
|---|---|
| `DB_PASSWORD = xxx`（`=` 两侧有空格） | 变量名变成 `DB_PASSWORD `（带空格），`DB_PASSWORD` 视同缺失 |
| 行尾 CRLF | 密码实际是 `xxx\r`，认证失败（`using password: YES` 但看着密码是对的） |
| 值里有 `#` 或无引号空格 | 被 `#` 截断 / 空格成为值的一部分；Systemd 不做引号转义 |
| unit 里 `EnvironmentFile` 顺序反了 | 后加载覆盖先加载，被 `xxx.env` 里的旧值盖回去 |

一次性看清「进程到底吃到了什么」：

```bash
PID=$(pgrep -f booking-api.jar | head -1)
sudo tr '\0' '\n' < /proc/$PID/environ | grep -E '^(DB_USERNAME|DB_PASSWORD|SPRING_DATASOURCE_URL)='
sudo systemctl show booking -p EnvironmentFiles    # keys.env 必须排在 xxx.env 之前
```

**三种「看着像但不相关」的误判，别浪费半小时**

- 去翻 `sys_config` 表结构、重跑 DDL —— 连接都没建立，表结构不可能影响这次报错。
- 以为是租户隔离插件（`TenantLineInnerInterceptor`）报错 —— 它的报错里会带 SQL 片段和 `tenant_id`；
  这里是 `Failed to obtain JDBC Connection`，插件压根还没轮到执行。
- 以为是前端页面 bug —— 前端只会收到一个 500，不会显示这条堆栈。

**处置后必做**：`sudo systemctl restart booking`（env 只在进程启动时读一次），
再复测 `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8081/api/v1/sys/config/list`（无 token 应回 401/403，而不是 500）。

## 附：多客户部署提示

验证期采用"每客户一实例"时（**每个客户现在是三个进程，不是两个**）：

- 每个客户一个数据库组：`lesson_appointment_a` + `message_center_a` + `classroom_a`，
  端口按 **三个一组** 错开：`8081/8090/8092`、`8082/8091/8093`、`8083/8092/8094`…
  （📌 第二组起要避开 8092 这个"课堂默认端口"，否则第二家的课堂与第一家的课堂撞车）
- 每客户一组 env：`/etc/lesson/{booking,message,classroom}-a.env`，`SERVER_PORT` 必须逐个显式写死
- Nginx 用子域名区分：`firm-a.example.com → 8081/8090/8092`，`firm-b.example.com → 8082/8091/8093`
  每个站点复制一份带 `/ws/classrooms/` 与 14 个课堂前缀的 location 块
- systemd 服务名错开：`booking-a.service`、`message-a.service`、`classroom-a.service`
- **Redis 按客户分 db**（如 A 用 db2、B 用 db3），或每客户一个 Redis 实例 —— 混用会串在线状态
- 课堂存储目录按客户分：`/opt/lesson/data/oss-a`、`-b`（`STORAGE_LOCAL_ROOT`）
- 备份脚本循环导出所有库，课堂文件目录同样循环
- 前端 dist 可以共用一份（同版本），也可按客户子域各放一份目录
- 客户数超过 15 家后走多租户改造，把新客户收进共享池
