# 前端容器化：镜像构建与配置正确性校验

> 日期：2026-11-21 14:35
> 范围：`deploy/docker/frontend/`（本次新增）+ 与 `deploy/nginx/`、`deploy/docker/` 的关系
> 前置：后端三服务已按 `deploy/docker/` 容器化（host 网络），或至少已在本机 8081/8090/8092 监听

---

## 0. 一句话结论

前端 `docker build` 本身不难，**难点全在「容器起来后配置对不对」**：nginx 的 location 优先级、
两层反代下的协议头、单文件挂载建目录、CRLF、变量形式的 `proxy_pass` 需要 resolver —— 这五类
错误**全部都能通过 `nginx -t`、容器也能正常启动**，只是在运行时某一种请求上悄悄出错。

所以本方案的重点不是 Dockerfile，而是三条防线：

| 防线 | 时机 | 工具 | 拦得住什么 |
|---|---|---|---|
| ① 静态自检 | 构建前（本机/CI） | `check-config.mjs` | location 优先级错、proxy_pass 尾斜杠、占位符缺失 |
| ② 构建期自检 | `docker build` 后 | `build.sh` 第 5 步 | dist 不完整、部署文件泄漏、缺环境变量却照样启动 |
| ③ 运行期校验 | 部署后 | `verify.sh` | 分流打错服务、缓存策略、404 语义、真实 IP、文件泄漏 |

## 1. 为什么把前端也容器化（以及不解决什么）

### 1.1 现在的两条既有路径

| 方案 | 资产 | 版本切换方式 |
|---|---|---|
| systemd + 宿主机 nginx | `deploy/nginx/*.conf` + `/var/www/frontend` | `switch.sh frontend` 切软链 |
| 微信云托管 | `deploy/docker/` | 控制台重新部署 |

第一条已经在跑（`deploy/docker/README.md` 里明确「Nginx + 前端 dist 留宿主机」）。那为什么
还要一份镜像？三个真实诉求：

1. **依赖收敛**。前端要的东西（nginx 版本、gzip 配置、location 列表、安全头）分散在
   `/etc/nginx/sites-available/booking`、`conf.d/00-limit-req-zone.conf`、`proxy_params` 里，
   新机器靠文档手工装。镜像能把这些一次性固化，起一台新机器只需要 `docker load` + `up -d`。
2. **前端回滚不再依赖文件系统状态**。软链方案回滚要保证 `/var/www/releases/<id>` 还在、
   软链没被谁手工改过；镜像回滚只是 `docker run` 一个旧 tag，状态由镜像保证。
3. **和云托管同构**。云托管那套已经跑了很久，容器化后自建机与云上行为一致，少一类
   「云上好好的、自建机不一样」的问题。

### 1.2 它不解决什么（避免预期错位）

| 诉求 | 容器化能解决吗 | 说明 |
|---|---|---|
| TLS 证书与自动续期 | ❌ | 证书在宿主机 `/etc/letsencrypt`，certbot 的 renew hook 也在宿主机。搬进容器要额外挂证书 + 重建续期钩子，收益极低 |
| 接口限流（`limit_req_zone`） | ❌ | zone 只能定义在 `http{}` 上下文。容器内自带一套会让限流口径分裂成两处，很难对齐 |
| 换域名 | ❌ | 仍要改宿主机 nginx 的 `server_name` 与证书 |
| 静态资源版本一致 | ✅ | dist 与镜像 tag 绑定 |
| 快速回滚 | ✅ | 切 tag，不依赖目录残留 |

结论：**只把「频繁换版本、无状态」的静态站点装进容器，TLS / 限流 / 安全头继续留宿主机**。
这与后端容器化时的取舍同源（那边也是 MySQL / nginx 不上容器）。

## 2. 三种落位方案：先定这个，再谈配置

配置写成什么样，取决于「谁监听 80/443」。三种方案的正确配置互相不兼容，**先选再写**。

| | 方案 A：容器接管 80/443 | **方案 B：容器 8080 + 宿主机 nginx 前置（推荐）** | 方案 C：容器桥接网络 |
|---|---|---|---|
| 监听 | 容器 `listen 80/443` | 容器 `listen 8080`（仅回环） | 容器 `listen 80` + 端口映射 |
| 谁做 TLS | 容器（挂证书） | 宿主机 nginx | 宿主机 nginx |
| 谁做限流 | 容器（要自带 `http{}` 级 conf） | 宿主机（现状不动） | 宿主机 |
| 容器网络 | `host` | `host` | `bridge` |
| 容器内上游地址 | `127.0.0.1:8081` 可用 | `127.0.0.1:8081` 可用 | ❌ 指向容器自己，必须换 `host.docker.internal` 或宿主 IP |
| 宿主机 nginx 改动 | 停用 | 2 行（静态 root → proxy_pass） | 2 行 |
| 回滚 | 停容器 + 启 nginx | 改回 `root` | 改回 `root` |
| 风险 | 高（证书、限流、acme 都要搬） | 低 | 中（上游地址易错） |

**选 B。** 理由与后端容器化完全一致：env 与 nginx 里所有 `127.0.0.1` 一字不改就能用。

C 为什么不行：桥接网络下容器内 `127.0.0.1` 是容器自己，`BOOKING_UPSTREAM=http://127.0.0.1:8081`
会连到自己，报 `connection refused`。就算改成 `host.docker.internal`，Linux 上还要
`--add-host=host.docker.internal:host-gateway`，且后端若也监听 `127.0.0.1`（本项目就是），
宿主机的回环从容器**根本不可达** —— 无论怎么填都不通。所以 C 在本项目里是死路。

全部在 `deploy/docker/frontend/`：


## 4. 构建步骤

### 4.1 先有 dist

```bash
# 仓库根
CODEBUDDY_SAFE_DELETE_ENABLED=0 node frontend/build.js
```

两个必须知道的坑：

**坑 1：`build.js` 默认会 `rmSync(dist)`，在这个环境里会被安全闸拦下**
（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`），命令退出但 dist 没生成。加环境变量绕过，见上。

**坑 2：仓库里有两份 dist，内容已经不一样**

```
frontend/dist/                  ← build.js 的产物（本次构建用这个）
deploy/docker/dist/       ← 云托管那次的产物
```

今天实测两份的 `build-info.json` 与全部 html 都不同（是不同批次的构建）。
`build.sh` 默认取 `frontend/dist`，可用 `DIST_SRC=` 覆盖。**不要凭「两个都在」就随便挑一个**，
否则会出现「镜像是旧版本，但你说不清为什么」。

### 4.2 版本一致性校验（`build.sh` 第 3 步会自动做）

`frontend/dist/build-info.json` 里有 `buildTime` 与 `gitCommit`：

```json
{ "buildTime": "2026-11-21T04:03:04.615Z", "gitCommit": "9d7221b...", "gitBranch": "auto_deploy" }
```

脚本拿 `gitCommit` 与当前 `HEAD` 比对。不一致时打黄字 WARN 并继续（回滚到旧版前端是有意的
行为，不该直接失败），但会明确告诉你「dist 不是用当前代码构建的」。

镜像 tag 用两段拼：`<buildTime 前 12 位>-<HEAD 短 sha>`，例如 `202611210403-9d7221b`。
前半段回答「内容是哪批」，后半段回答「代码是哪次提交」。

### 4.3 构建

```bash
bash deploy/docker/frontend/build.sh

# 换 dist 来源 / 换镜像名前缀
DIST_SRC=/tmp/dist IMAGE=registry.example.com/lesson/frontend \
  bash deploy/docker/frontend/build.sh
```

为什么 `build.sh` 要先把 dist **拷到 `deploy/docker/frontend/dist/`** 再 build：

- 本目录是构建上下文，Dockerfile 只 `COPY dist`；
- 若把上下文设成仓库根，docker 要把整个仓库（node_modules / target / 两份 dist）打成 tar
  传给 daemon，几百 MB 起步，还必须在仓库根新增 `.dockerignore` —— 那会影响后端镜像构建；
- 拷 5MB 最省事，也与 `deploy/docker/` 的做法一致。

`deploy/docker/frontend/dist/` 已加进 `.gitignore`（不入库）。

### 4.4 构建期三段自检（`build.sh` 第 5 步）

| 检查 | 断言 | 拦的是什么 |
|---|---|---|
| 镜像内容 | `index.html` / `login.html` / 三个配置模板都在；`Dockerfile`、`container.config.json` 不在 | dist 不完整 / 部署文件泄漏 |
| 反向行为 | 不给环境变量时容器**必须失败**，且报错点名 `BOOKING_UPSTREAM` | 「预检没生效」——那是配置错了还静默 502 的根源 |
| 正常路径 | 给全变量时日志里出现 `nginx -t OK` | 模板渲染失败 / 语法错 / 占位符不匹配 |

第三段用了 `docker run -d` + `docker logs` + `docker rm -f`，**没有用 `pkill -f "nginx: master"`** ——
宿主机上可能就有一个 nginx 在跑，一条 pkill 会把线上服务打掉。

### 4.5 分发

```bash
# 开发机
docker save lesson/frontend:202611210403-9d7221b | gzip -1 > fe-202611210403-9d7221b.tar.gz

# 服务器
gunzip -c fe-202611210403-9d7221b.tar.gz | docker load
```

单机、发布频率低，不需要镜像仓库。规模起来后把 `save/load` 换成 `push/pull`，
**切换机制完全不变**（这与后端镜像的处理一致）。

## 5. 配置正确性：17 条判据

每条给出「写错的症状 → 正解」。**症状是重点** —— 这些错误都不会报错。

### 5.1 `network_mode: host`，不用端口映射

- **错法**：`ports: ["127.0.0.1:8080:8080"]` + 默认 bridge
- **症状**：`docker ps` 显示 Up，页面能打开，接口全 **502**，容器日志只有
  `connect() failed (111: Connection refused) while connecting to upstream`
- **正解**：`network_mode: host`，容器内 `127.0.0.1` 即宿主机回环

### 5.2 不要照抄云托管那份「变量形式 `proxy_pass`」

云托管模板是：

```nginx
set $api_upstream "${API_UPSTREAM}";
proxy_pass $api_upstream;        # ← 变量形式
```

**变量形式的 `proxy_pass` 强制要求配置里有 `resolver`**，缺了就是**每个请求** 502，
而 `nginx -t` 查不出来（这是请求期行为）。云托管为此专门写了 `00-resolver.sh`
从 `/etc/resolv.conf` 生成 resolver，取不到就 `exit 1`。

自建机上上游是 `127.0.0.1`，静态可得。本方案改成**占位符渲染成字面量**：

```nginx
proxy_pass ${BOOKING_UPSTREAM};   # 渲染后 → proxy_pass http://127.0.0.1:8081;
```

既保留「换环境只改环境变量」的能力，又不引入 resolver 依赖。副作用还有一个好处：
变量形式下 `Host` 默认取 `$proxy_host`（变量里的主机），字面量形式下我们显式写
`Host $http_host`，语义固定。

### 5.3 两层反代必须传 `Host` 与 `X-Forwarded-Proto`

链路是：浏览器 → 宿主机 nginx(443) → 本容器(8080) → 后端。**容器是第二层**。

| 头 | 写错的症状 | 正解 |
|---|---|---|
| `Host` | 后端 `getServerName()` 拿到 `127.0.0.1:8080`，与浏览器 `Origin: https://域名` 不同源 → Spring 判跨域 → **403 + 纯文本 `Invalid CORS request`**（不是 JSON） | `proxy_set_header Host $http_host;` |
| `X-Forwarded-Proto` | 容器内写 `$scheme` 永远是 `http`，会把上层的 `https` **覆盖掉**；Spring 生成的绝对链接与 `Location` 头退回 `http://`，浏览器按混合内容拦 → 「https 上登录后跳转白屏」，而 nginx 日志全是 200 | 用 map 取上层的值，没有才回落 `$scheme`（见 `nginx/00-proxy-map.conf`） |
| `X-Real-IP` / `X-Forwarded-For` | `ClientIpResolver` 拿到的全是 `127.0.0.1`；登录防刷、审计日志、限流**全部退化成同一个 IP**，且不报任何错 | `proxy_set_header X-Real-IP $remote_addr;` + `$proxy_add_x_forwarded_for` |

`$http_host` 而不是 `$host`：`$host` 会丢掉非默认端口，带端口的直连调试会让后端生成的
绝对链接少一段端口。

**一句话记忆**：看到后端返回**纯文本**而不是 JSON，先想 CORS（Host/Origin 不一致），
不要先怀疑鉴权。

### 5.4 所有 API location 必须 `^~`（本文件最重要的一条）

nginx 优先级：`=` 精确 > `^~` 最长前缀（命中即止） > 正则 > 普通最长前缀。

模板里有一条静态资源正则：

```nginx
location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?|ttf|eot|otf|mp4|webm|webp)$
```

如果某个 API 前缀写成普通前缀（`location /api/v1/files/`），那么
`GET /api/v1/files/xxx.mp4` 的**最长前缀**是它、但它是普通前缀 → 继续试正则 → 命中静态正则
→ 变成「在静态根下找这个文件」→ **404 + text/html**。

症状是「课件 pdf、录播 mp4、活动图片打不开，其他功能都正常」，而 `nginx -t` 完全通过。

**关于 `^~` 作用范围的一个常见误判**（我一开始也写错了）：

> `^~` 只在「它就是最长前缀匹配」时才压住正则。

所以**兜底那条 `^~ /api/v1/` 救不了 `location /api/v1/files/` 漏写 `^~` 的情况** ——
更长的普通前缀会赢过更短的 `^~`，仍然会试正则。这一点用 `check-config.mjs --self-test`
钉住了（变异测试第 1 条）：

```
RED OK  去掉 /api/v1/files/ 的 ^~  →  /api/v1/files/a.mp4  ~* \.(js|  (静态)  FAIL
```

### 5.5 无子段的 `/api/v1/admin/classrooms` 必须用 `=` 精确匹配

`POST /api/v1/admin/classrooms`（创建临时课堂）路径**恰好等于**前缀去掉尾斜杠，
永远匹配不到 `^~ /api/v1/admin/classrooms/`。漏了这条：请求走 `^~ /api/v1/` → 8081 →
主服务没有该映射 → `SecurityConfig` denyAll → **403「无权限访问该资源」**。

看起来像权限问题，实际是分流漏了。`dev-proxy.js` 里对同一处有注释，
（`urlPath === p.replace(/\/$/, '')`），nginx 侧对应 `location = /api/v1/admin/classrooms`。

### 5.6 单数 `schedule` 与复数 `schedules` 是两个服务

| 路径 | 服务 | 用途 |
|---|---|---|
| `/api/v1/schedule/detail` `/class-instances` `/listByTeacher` | 8081 booking | 排期查询 |
| `/api/v1/schedules/`（复数） | 8092 classroom | **排期事件接收** / 对账 |

别为了「整齐」把两条合并。合并后排期查询会整片打到课堂服务，全站 404。
同理 `classroom-service` 里的 `ScheduleEventController` / `ReconcileController` 才是复数那侧的消费者。

### 5.7 `/api/v1/classroom-callback/` 归 8081，不是 8092

直觉上「classroom 开头的都给课堂服务」，但课堂回调（下课收尾回执等）由主服务接收。
这条漏了会掉进 `^~ /api/v1/` → 8081（碰巧是对的），所以**写错也不报错**；
但如果哪天有人把它误加进课堂前缀清单，回调就全丢 —— 出勤收尾不触发，很难查。

### 5.8 `try_files` 不要回退 `index.html` / `login.html`

本项目是**多页应用**（login / admin / teacher / student / platform_admin …），不是 SPA。

```nginx
location / { try_files $uri $uri/ =404; }     # 正解
```

回退的后果不止「错链静默成首页」：静态资源缺失也会被替换成 HTML（`200 + text/html`），
浏览器控制台只报语法错误，完全看不出是 404。

> 注意：宿主机 `deploy/nginx/booking.conf` 现在是
> `try_files $uri $uri/ /login.html`（带 SPA 兜底），与容器这层口径不同。
> 容器是内层，严格 404 才有诊断价值 —— 两层都兜底等于把 404 兜两次，永远查不出来。
> 本次**没改**宿主机那份（它在跑，改动要单独评估），差异记在第 9 节待办。

### 5.9 `add_header` 是覆盖式继承 → 缓存策略一律用 `expires`

nginx 的 `add_header` 在子级出现**任意一条**时，父级那一组**整组不再下发**。
所以若在静态 location 里写 `add_header Cache-Control "max-age=604800"`，
server 级的安全响应头（X-Frame-Options 等）在这个 location 就全没了，
而 js/css/html 恰恰是安全头审计最常查的对象。

正解：`expires 7d`（→ `Cache-Control: max-age=604800`）/ `expires -1`（→ `no-cache`），
它们不参与 `add_header` 继承。

### 5.10 SSE 必须关缓冲

```nginx
proxy_buffering off;
proxy_cache off;
proxy_set_header Connection '';        # HTTP/1.1 下 keep-alive 会把事件攒在一个流里
proxy_read_timeout 3600s;
chunked_transfer_encoding on;
```

漏了 `proxy_buffering off` 的症状是「消息能收到，但延迟几十秒」，看起来像后端慢。

### 5.11 WebSocket 需要 Upgrade 与长超时

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade    $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
```

`Connection "upgrade"` 用字面量即可 —— 这个 location 只承载 WS，不需要按 `$http_upgrade`
做 map 区分（那样还得在 `http{}` 加一处 map，多一个失败面）。

### 5.12 `client_max_body_size` 默认 1m

上传课件、教师头像都走这个容器反代。超过 1m 直接 **413**，前端只看得到「上传失败」。
本方案设 20m，与宿主机 `booking.conf` 保持一致。

### 5.13 部署文件泄漏：镜像层必须再清一次

`frontend/build.js` 的 `copyAssets()` 用**黑名单**挡非站点文件。黑名单与目录一旦不同步，
部署资产就随静态站点发到公网 —— 任何人 GET 一下 `/Dockerfile`、`/container.config.json`
就能看到内部架构。

所以 Dockerfile 里 `RUN rm -rf` 再清一遍，并 `test -f` 断言入口页存在（不清的话不只是
泄漏，还可能把 dist 里那个 nginx 目录当成站点内容）。`verify.sh` 第 6 组会从外部验证
`/Dockerfile`、`/container.config.json`、`/readme.md` 全部 404。

### 5.14 `app-config.json` 挂**目录**，不挂单文件

```yaml
volumes:
  - /var/www/app-config:/app-config:ro        # ✅ 挂目录
# - /host/app-config.json:/var/www/frontend/app-config.json   # ❌ 挂单文件
```

单文件挂载时，宿主机路径**不存在** → docker 会顺手建一个**同名目录** → 容器里
`app-config.json` 成了目录 → 请求它返回 403/500，而报错只说 permission denied，
完全看不出「挂载建了目录」。

正解：挂目录，由 `00-preflight.sh` 判断「有就拷进站点根、没有就跳过」。
没提供时站点返回 404 是正确的（小程序回落 `env.js` 里的地址）。

### 5.15 CRLF 毒害（Windows 开发机的默认状态）

三个文件必须 LF：

| 文件 | CRLF 后果 |
|---|---|
| `entrypoint/00-preflight.sh` | `#!/bin/sh\r` → busybox 报 not found → 配置不渲染 → nginx 起不来或全站 502 |
| `nginx/default.conf.template` | 指令末尾带 `\r`，`nginx -t` 报 `unexpected "\r"`；而它是**启动时**才渲染的，构建期查不出来 |
| `nginx/proxy_params` | 同上 |

已在 `deploy/.gitattributes` 加 `docker/frontend/Dockerfile`、`docker/frontend/nginx/proxy_params`、
`*.template` 三条 `text eol=lf`；Dockerfile 里还有一道 `sed -i 's/\r$//'` + `sh -n` 兜底。

Git Bash 下 `bash` 能容忍 `\r`，所以「本地跑得好好的、容器里必炸」是常态，别信本地。

### 5.16 健康检查不探上游

```dockerfile
HEALTHCHECK CMD wget -qO- http://127.0.0.1:8080/healthz >/dev/null 2>&1 || exit 1
```

`/healthz` 只证明「本容器的 nginx 活着、配置已渲染」，**不探后端**。
探上游的话，后端一宕容器就被判不健康 → 反复重启 → 连静态页都没了，
用户看到白屏而不是「服务维护中」。

### 5.17 端口三元一致

`Dockerfile` 的 `EXPOSE 8080`、模板的 `listen 8080`、宿主机反代的 `proxy_pass http://127.0.0.1:8080`
**必须同值**。改端口要三处一起改，否则宿主机 502 而容器一切正常。

## 6. 部署与版本切换

### 6.1 宿主机 nginx 的改动（方案 B，只有 2 处）

在 443 的 server 块里，把静态托管改成反代：

```nginx
    # root /var/www/frontend;                      ← 注释掉
    # index login.html;
    # location / {
    #     try_files $uri $uri/ /login.html;
    # }

    # 前端静态站点交给容器
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $http_host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
    }
```

**宿主机原有的 `/api/v1/*` 一堆 location 全部保留不动**（它们带限流 zone，且已验证）。
这样容器里的 API 分流在方案 B 下是「冗余备份」，只有切到方案 A（容器直接对外）才成为主路径。

> ⚠ 这意味着**分流清单又多了一个消费者**（`dev-proxy.js` / `deploy/nginx/*.conf` /
> 小程序 `request.js` / 本容器模板，共 4 份）。改分流规则要四处一起改。
> 现状是 `npm run check:proxy` 守前三份，容器这份靠 `check-config.mjs` 的 30 条用例
> 交叉校验（用例里的期望服务与 dev-proxy 清单一一对应）。**建议后续并入 `check:proxy`**，见第 9 节。

改完：

```bash
sudo nginx -t && sudo systemctl reload nginx
```

### 7.3 运行期：`verify.sh`（23 项）

```bash
bash deploy/docker/frontend/verify.sh http://127.0.0.1:8080
bash deploy/docker/frontend/verify.sh https://booking.example.com      # 走宿主机入口更真实
```

七组断言：

| 组 | 断言 | 失败意味着 |
|---|---|---|
| 1 容器自身 | `/healthz` 返回 `ok`、`/` 返回 200 | 容器没起好 / 宿主机反代指错端口 |
| 2 静态与缓存 | html `no-cache`、js/css `max-age=604800`、`build-info.json` 200 | 缓存策略写错（上线后看到旧页面） |
| 3 多页语义 | 不存在的路径返回**真 404** | `location /` 里有 `index.html` 回退 |
| 4 三服务分流 | `system/info` 200、`/msg-health` 200、**`/api/v1/files/x.mp4` 不能返回 HTML**、`/api/v1/admin/classrooms` 不是 404-html、单/复数 schedule 都进反代 | 分流漏了 / `^~` 漏了 |
| 5 WebSocket | `/ws/classrooms/x` 返回 101/400/403（不是 404-html） | 落了静态 location |
| 6 文件泄漏 | `/Dockerfile`、`/container.config.json`、`/readme.md` 全 404 | 镜像里的清理步骤失效 |
| 7 真实 IP | 后端响应里不应出现 `127.0.0.1` / 内网网段 | `X-Real-IP` / `X-Forwarded-For` 没传 |

退出码：`0` 全过；`1` 有硬失败（必须修）；`2` 只有提示级项未通过。

第 4 组的那条 mp4 断言是整套里最有价值的 —— 它把「`^~` 漏写」这个**不报错的 bug**
变成了一个能判红的检查。

## 8. 故障速查表

| 症状 | 最可能原因 | 一条命令定位 |
|---|---|---|
| 页面能开，接口全 502 | 容器用了 bridge 网络 / 上游地址不是 `127.0.0.1` | `docker exec frontend wget -qO- http://127.0.0.1:8081/actuator/health` |
| 接口 403 + **纯文本** `Invalid CORS request` | 没传 `Host`，后端 `getServerName()` 与浏览器 `Origin` 不一致 | `curl -sI https://域名/api/v1/system/info`，看是不是 `Content-Type: text/plain` |
| 课件 pdf / 录播 mp4 404 且返回 HTML | 对应 API 前缀漏 `^~`，被静态正则抢走 | `node deploy/docker/frontend/check-config.mjs` |
| 「创建临时课堂」报无权限 | 缺 `location = /api/v1/admin/classrooms` | `grep -c 'location = /api/v1/admin/classrooms' 容器内模板` |
| 所有 404 都变成登录页 / 返回 200 | `try_files` 回退到 `login.html` | `curl -o /dev/null -w '%{http_code}' https://域名/no-such-page` |
| 上线后用户仍看到旧页面 | html 没 `expires -1`，或被 `add_header` 覆盖 | `curl -sI https://域名/login.html \| grep -i cache-control` |
| `/app-config.json` 403/500 | 单文件挂载把宿主机不存在的路径建成了目录 | `docker exec frontend ls -ld /var/www/frontend/app-config.json` |
| 容器启动即退出，日志一句 `Permission denied` | 上一条的另一种表现 / cap_drop 漏了能力 | `docker logs frontend` |
| 容器日志 `#!/bin/sh` not found | entrypoint CRLF | `docker exec frontend head -c 20 /docker-entrypoint.d/00-preflight.sh \| od -c` |
| 消息推送延迟几十秒 | SSE location 少了 `proxy_buffering off` | `curl -N https://域名/api/v1/sse` |
| 上传 413 | `client_max_body_size` 默认 1m | 看 nginx 日志 `client intended to send too large body` |
| https 下登录后跳转白屏 | `X-Forwarded-Proto` 被容器这层覆盖成 http | `curl -sI https://域名/api/v1/auth/login` 看 `Location` 协议 |

## 10. 三条路径别维护三份

仓库里现在有三套前端 nginx 配置：

| 文件 | 用在哪 | 上游写法 | 监听 |
|---|---|---|---|
| `deploy/nginx/booking.conf` | 宿主机 nginx（现状在跑） | 字面量 `127.0.0.1:8081` | 80/443 + TLS |
| `deploy/docker/default.conf.template` | 微信云托管 | **变量** + resolver | 8080 |
| `deploy/docker/frontend/nginx/default.conf.template` | 自建 CVM 容器（本次） | 占位符渲染成**字面量** | 8080 |

三者不能合并（运行环境不同），但**分流清单必须一致**。差异只允许出现在：

1. 上游写法（字面量 / 变量 / 占位符）
2. 监听端口与 TLS
3. 限流与安全头（谁在最外层谁负责）

location 列表本身必须逐条对齐 `doc-develop/90-tools/dev-proxy.js`。

> 顺带记录一处实测差异：`deploy/docker/default.conf.template` 里 `^~` 出现 **0 次**，
> 而它有 `\.mp4$` 静态正则 —— 也就是说云托管那份存在「课件/录播被静态正则抢走」的隐患。
> 本次没有改云托管那份（它在跑，改动要单独走发布），仅在此留痕。
