## D-001 构建发布存在三条并行路径，产物互不兼容且文档只覆盖两条

- **登记时间**：2026-11-26
- **状态**：**暂缓**（用户 2026-11-26 明确：暂时不考虑 docker 方面）
- **发现场景**：为「3 后端 + 2 前端」补齐 `deploy/build-all.bat` 与 `run-all.bat` 时发现的既有问题，**非本轮引入**。

### 事实依据（逐个文件核对，非推测）

仓库里实际存在 **三条**发布路径，而非一条：

| # | 路径 | 入口脚本 | 目标平台 | 镜像/产物命名 | tag 规则 |
|---|---|---|---|---|---|
| ① | systemd + jar + nginx | `deploy/upload-to-server.sh` | 自建服务器 | jar 落 `/opt/lesson/`；前端 dist 落 `/var/www` 软链 | 无 |
| ② | Docker 容器化 | `deploy/build-backends.sh` + `deploy/docker/build-images.sh` | 自建服务器 compose | `lesson/booking-api`、`lesson/message-service`、`lesson/classroom-service` | `<pom 版本>-<git short sha>[-dirty]`，例 `2.2.0-a1b2c3d` |
| ③ | 腾讯云云托管 | `deploy/build-all.bat` | `ccr.ccs.tencentyun.com/cb-<env-id>/` | `booking-api`、`booking-message-service`、`booking-classroom-service`、`booking-web:latest` | 纯 pom 版本号（`2.2.0` / `1.1.0` / `1.0.0`），前端恒 `latest` |

关键取值证据：
- `deploy/docker/docker-compose.yml:47/74/93` → `image: "lesson/booking-api:${BOOKING_TAG:?BOOKING_TAG-not-set}"`（与 ③ 的镜像名、tag 形态都对不上）。
- `deploy/build-all.bat:106-108` → `VER_API=2.2.0` / `VER_MSG=1.1.0` / `VER_CLS=1.0.0`，:325/336/351 用 `docker build -t booking-api:%VER_API%` 等命名，:397-400 才 `docker tag` 到 `!REGISTRY!/api:%VER_API%`。
- `deploy/docker/build-images.sh:10-12` 明确写了「tag 里带 sha 是回滚能力的地基：同一个 2.2.0 被改三次也分得清是哪次」。

### 影响

1. **三条路径产物不能互用**：③ 构建出的镜像名与 ② 的 compose 引用完全不一致，拿 ③ 的镜像起 compose 会拉不到对象；反之 ② 的 sha tag 也无法填进云托管控制台的镜像地址字段。
2. **回滚能力不对等**：② 侧 tag 带 sha，可回答"线上跑的是哪次提交"；③ 侧只有版本号，同一版本被改多次后无法区分，也没有等价清单文件可核对（② 有 `deploy/docker/env.example` 这份版本清单，③ 的版本号只硬编码在脚本里）。
3. **文档缺一条路径**：`deploy/README.md` 的目录表与 `deploy/docker/README.md` 开头只文档化了 ① 与 ②，并明确写"两条路径不要同时开（同一个 8081 会被两个进程抢）"；**全文 grep 不到 `build-all.bat` / `run-all.bat` / `云托管` / `ccr` / `env-id`**。也就是说 ③ 这条路径的唯一说明书是 `build-all.bat` 自己的文件头注释。
4. **覆盖范围容易漂移**：任何新增服务都要在三处各改一次。本次就是 ③ 落后于 ①②（补齐前只覆盖 2 后端 + 1 前端，且仍指向已不存在的 `cloudBased\` 旧结构）。漏改的表现是"构建成功但少一个服务"，不报错。

- `deploy/build-all.bat`：补 classroom-service 构建、前端拆成 `frontend`(dist) + `classroom-app`(www) 两段、推送补第四个镜像、版本号集中为 `VER_API/VER_MSG/VER_CLS` 三个变量、新增 `--skip-web` / `--skip-app`。
- `deploy/run-all.bat`：补第 5 个窗口（classroom-app 预览 8098）。
- **刻意未做**：未改镜像命名、未改 tag 规则、未把 bat 改成调用 bash/统一脚本、未动 docker 侧任何脚本——因为当前实际走哪条发布路径未确认，属要决策的事。

### 关联的次要缺口（同一片区域，一并记录）

1. **classroom-app 没有 App 打包发布步骤**：`deploy/` 下只有 `build-all.bat` 和 `run-all.bat` 提到 classroom-app。`cap sync` / Android AAB / iOS IPA 的构建、签名、产物归集全无脚本（`classroom-app/package.json` 里只有 `cap:add:*` / `cap:sync` 这类手工命令），靠人工执行。
2. **两个前端产物命运不同，容易被误传**：`frontend` 的 `dist` 参与服务器部署（`cloudBased\frontend\dist` 或 `/var/www` 软链）；`classroom-app` 的 `www` 是打进 App 安装包的 Capacitor 资源，**不参与服务器部署**。`build-all.bat` 里已加提示文字，但没有任何机制阻止误传。
3. **`deploy/docker/env.example` 与 `build-all.bat` 是两套版本清单机制**：前者是文件化清单（含 `BOOKING_TAG` / `MESSAGE_TAG` / `CLASSROOM_TAG` / 可选 `FRONTEND_TAG`，并写明 `/etc/lesson/keys.env` 的加载顺序坑），后者是脚本内硬编码。若日后统一，需先定"版本清单放哪"。

### 待做（按优先级）

1. **轮换全部泄露密钥**（服务端操作，未做）：
   - `JWT_SECRET` —— 泄露即可伪造任意用户/租户 token，**最致命**。更换后所有用户需重新登录，代价可接受。
   - `DB_PASSWORD`（root）、`ACTUATOR_PASSWORD` —— 直连/管理端点风险，同步改容器或环境变量。
   - `AES_KEY` / `HMAC_KEY` —— ⚠️ **不能直接换**：`api/*/utils/CryptoUtil.java` 无 key 版本化机制（全仓 grep `keyVersion|legacyKey` 无命中），直接换会让存量密文（如加密入库的 `user.name`）**不可解密**。必须先做双 key 迁移（旧 key 解密 + 新 key 重加密）或重加密脚本。
2. **文档中残留的密钥需脱敏**（当前 HEAD 仍有，历史亦有）：`doc-develop/09-合规与合同/等保二级整改实施方案.md`（3 处）、`doc-develop/08-电子课堂/在线教学微服务架构设计.md`（3 处）、`等保二级合规分析报告.md`（1 处）、`N7-敏感字段服务级加解密.md`（1 处）。建议替换为 `<已轮换>` 占位，避免二次泄露。
3. **协作者需重新 clone**：历史已重写，所有人的本地分支与远端全部失配，`git pull` 会炸；必须重新 clone 后手工迁移未推送改动。
4. **认知边界**：重写历史无法收回已抓取者手里的副本（fork、镜像、搜索引擎缓存、GitHub 对旧 SHA 的 CDN 缓存）。**轮换密钥才是治本**，第 1 条不能省。

### 根因（值得写进规范）

`.gitignore` 对**已跟踪**文件不生效。任何「我以为它被忽略了」的判断都必须用 `git check-ignore -v <path>` 验证——对被跟踪文件，这条命令会静默无输出，而 `git ls-files <path>` 有输出。正确顺序是：先 `git rm --cached`，再补忽略规则。本仓踩的就是"只加了规则、没做 rm --cached"。
