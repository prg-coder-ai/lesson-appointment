## D-004 代理「[代理失败] classroom -> 127.0.0.1:8092 ECONNRESET」：一半是噪音，且日志无法定位

- **登记时间**：2026-11-26 17:00 / **状态**：已处置
- **发现场景**：桌面端/浏览器联调课堂时，dev 代理窗口打印 `[代理失败] classroom -> 127.0.0.1:8092  ECONNRESET socket hang up`，但课堂功能本身可用。
- **排查过程（排除法，全部有实测）**：
  - 8092 是 **http**（`curl http://127.0.0.1:8092/` = 200，`https://` = 000），代理 `classroom` 继承 `apiProtocol`，`normalizeTarget` 缺省也是 http → **不是协议错**（协议错会报 EPROTO，不是 ECONNRESET）。
  - 8092 进程 12:42:17 启动后**未重启**（`logs/classroom-service.log` 的 `Tomcat started on port 8092` 只有一次）→ 排除"后端重启导致连接全断"。
  - 同一时段 `logs/classroom-service.log` 16:52:58 有完整成功链路（enter 放行 → 签到 → 进房配置签发）→ 服务健康。
  - 逐个请求 9 个 classroom 路径经 8080 → 全部 401/200，无 502 → 转发规则本身没问题。
- **根因（两个，叠加成"看不出来"）**：
  1. **客户端先断开被误报为上游故障**。`res.on('close', () => p.destroy())` 会在用户关课堂页 / 切页 / 取消上传 / SSE 关流时主动销毁上游请求，而销毁过程本身会回吐 `ECONNRESET`，被 `p.on('error')` 一律当成「代理失败」打印。**这是正常中断，不是故障。**
  2. **日志缺 URL**。原格式只有 `label -> host:port`，无法判断是哪个请求挂了，排查只能靠猜。
- **处置（`doc-develop/90-tools/dev-proxy.js` 与 `classroom-app/desktop/server.js` 同步）**：
  - 错误分类三分支：① 客户端已断开（`clientAborted || req.destroyed`）→ 静默，`DEV_PROXY_VERBOSE=1` 才打印；② 无 body 的 GET/HEAD/OPTIONS 遇 `ECONNRESET`/`EPIPE` → **自动重发一次**（残留 keep-alive 复用死 socket 的场景，本地回环新建连接代价可忽略）；③ 真失败 → 打印 `label method url -> host:port code message`，头已发出时改 `res.destroy()` 而不是 `res.end()`（避免 ERR_STREAM_WRITE_AFTER_END）。
  - 实测（假上游：第 1 次连接直接 RST，第 2 次正常）：`[代理重试] classroom GET /api/v1/classrooms/x/status → ECONNRESET，重发一次` → 客户端 **HTTP 200，20ms**，用户无感；客户端 0.5s 中断 3s 慢响应 → **不再打印代理失败**。真实 8092 复测 6 个路径，转发行为不变。
- **遗留**：
  1. 改动在 `dev-proxy.js`，**必须重启 8080 代理窗口才生效**（进程只在启动时加载代码）。
  2. WS（`/ws/classrooms/*`）分支的错误仍是静默 `socket.destroy()`，无日志；排查 WS 问题要看浏览器端。
- **为什么值得写进规范**：把「正常中断」报成 error，比不报更坏——它会训练人忽略日志。日志缺 URL 则是纯自伤：这类问题第一次出现时，光凭 `label + host:port` 无法定位，只能整个流程重放一遍。

## D-005 桌面 exe 里课堂「连接中断，正在重连」：分流清单第三处漏了 WS 前缀

- **登记时间**：2026-11-26 17:20 / **状态**：已处置（需重新打包 exe 才生效）
- **发现场景**：绿色包内进课堂，一直显示「连接中断，正在重连…」；同一账号在浏览器里正常。
- **事实依据**：
  - 课堂三条 WS 通道地址是 `/ws/classrooms/<sid>/{heartbeat,signal,whiteboard}?access_token=…&traceId=…`（`frontend/js/public/classroom-ws.js:39`），**不在 `/api` 下**。
  - `classroom-app/desktop/server.js` 的 `upstreamOf` 只认 `MSG_PREFIXES`(`/api/v1/message…`) 与 `CLS_PREFIXES`(`/api/v1/classrooms/…`)，`/ws/…` 既不命中前缀也不命中 `startsWith('/api/')` → 返回 `null`。
  - → `proxyWs` 第一行 `if (!up || !up.host) { socket.destroy(); return; }` 直接销毁，握手永远建不起来；且该分支错误静默无日志。
- **为什么只有 exe 坏（关键对比，三处清单只错一处）**：
  | 通道 | WS 判定 | 结果 |
  |---|---|---|
  | 本地浏览器 → 8080 | `dev-proxy.js` 的 `urlPath.startsWith('/ws/')` | ✅ 正常 |
  | 生产 nginx | 五份 conf 均有 `location /ws/classrooms/` | ✅ 正常 |
  | 桌面 exe → 内置 server | 清单漏了 `/ws/` | ❌ 一直重连 |
  正因为浏览器与生产都正常，第一反应会去查网络/证书/后端，而不是"桌面端少配了一条前缀"。
- **处置**：
  1. `server.js` 新增 `WS_PREFIXES = ['/ws/']`，判定先于 `/api` 兜底（口径与 `dev-proxy` 一致：所有 `/ws/` 归课堂上游）。
  2. 把 `upstreamOf` 的逻辑提为模块级 `resolveUpstream(rawPath, UP)` 并导出，让守卫复用同一份实现，而不是在守卫里抄第二份清单（抄一份就多一处漂移源）。
  3. `tools/check-proxy-routes.mjs` 增⑤：桌面端 28 个课堂端点 + WS 三通道必须都判到 classroom 上游。
- **验证**：
  - 证伪：禁用该分支 → socket 被直接销毁、无任何响应（复现用户所报现象）；恢复 → `HTTP/1.1 101 Switching Protocols` 且帧透传成功。
  - 真实三跳一致性：直连 8092 / 经 8080 / 经桌面 server，三者响应逐字节同形 → 转发通透。
  - 守卫反向测试：删掉判定行、把 `/ws/` 写成 `/ws/xxx/`，两种情况均报「未把课堂 WS 判到 classroom 上游」；还原后全绿。
  - 产物侧：新包 `app.asar` 内 `resolveUpstream`/`WS_PREFIXES` 各命中 3 次，旧包 0 次。
- **遗留**：
  1. **exe 内是打包时的 server.js**，必须重新打包替换才生效（本次已出 `release-fix/云课堂-绿色版-1.0.0-x64.zip`）。
  2. `release/` 被运行中的 `云课堂.exe` 占用 `app.asar`，重新打包会失败（`ERR_ELECTRON_BUILDER_CANNOT_EXECUTE`）。**打包前先关掉所有 `云课堂.exe` 进程**。
  3. WS 分支的错误仍是静默 `socket.destroy()`。本次靠"三处对比"才定位，建议后续给 WS 分支补一条失败日志（上游未命中 / 连接错误）。
- **为什么值得写进规范**：这是「分流清单多处维护」的第二个实例（第一个是 D-003 的 www 静态承接）。清单每多一处，就多一个只有特定运行形态才暴露的坑；根治办法是让所有清单共用同一份实现并纳入守卫，而不是靠人工同步。
