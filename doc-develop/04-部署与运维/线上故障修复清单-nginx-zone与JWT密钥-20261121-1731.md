# 线上故障修复清单：nginx zone 缺失 + 消息服务 JWT 密钥分叉

> 日期：2026-11-21 17:31
> 环境：`http://152.136.254.127`（公网 IP 内测，nginx 1.24.0 Ubuntu，站点配置 `booking-ip.conf`）
> 入口现象：平台管理员登录成功后立即被 401 踢回登录页
> 关联资产：`deploy/nginx/`、`deploy/*.service`、`/etc/lesson/*.env`

---

## 0. 一句话结论

看起来是一个故障，实际是**三个互不相关的问题叠在一起**，且存在**依赖顺序**：

| # | 问题 | 层次 | 阻塞关系 |
|---|---|---|---|
| **P0-1** | `/etc/nginx` 磁盘配置缺 `limit_req_zone` 定义，`nginx -t` 直接失败 | 运维配置 | **阻塞一切变更**：所有 nginx 改动至今一次都没生效（含课堂分流修复） |
| **P0-2** | `message.env` 的 `JWT_SECRET` 与 `booking.env` 不一致 | 应用密钥 | 直接造成「登录后秒退」 |
| **P1** | 课堂三处遗留：`/api/v1/admin/classrooms` 301、`classroom` 表缺失、`eclassroom` 未开通 | 部署/数据 | 课堂功能不可用，但不影响登录 |

**必须按 P0-1 → P0-2 → P1 的顺序处理。** 先修密钥是没用的——nginx 层再怎么改也不会生效；而先改 nginx 又必须先让配置文件合法。

## 1. P0-1：nginx 磁盘配置坏，线上跑的是内存旧配置

### 1.1 现象

```console
$ sudo nginx -T | grep -n -A3 "admin/classrooms"
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
2026/11/21 17:26:58 [emerg] 3276120#3276120: zero size shared memory zone "api_zone"
nginx: configuration file /etc/nginx/nginx.conf test failed
```

### 1.2 这个报错到底在说什么

`zero size shared memory zone` 的准确含义是：**有地方引用了 `api_zone`，但没有任何 `limit_req_zone` 给它定义尺寸**。

它出现在 `syntax is ok` **之后**，因为语法解析阶段已经通过，失败发生在其后的**共享内存初始化阶段** —— 这也解释了为什么这一行**不带文件名和行号**（解析期的位置信息已丢失），特别容易误读成「语法没问题所以配置是对的」。

对比另一种同源报错，能帮助区分「定义这一半」具体缺在哪：

| 报错文本 | 含义 | 是否带行号 |
|---|---|---|
| `zero size shared memory zone "api_zone"` | 引用已登记，但**没有任何定义**给它尺寸 | ❌ 不带，难查 |
| `unknown limit_req_zone "api_zone"` | 解析阶段就发现定义不存在 | ✅ 带 `文件:行号` |
| `the shared memory zone "api_zone" is already declared for a different use` | 同名 zone 被 `limit_conn_zone` / `proxy_cache_path` 占用 | ✅ |

三者指向同一个事实：**定义这一半没生效**。

### 1.3 这条故障的连锁后果（关键）

nginx `reload` 失败时**旧 worker 不停**，站点继续用内存里的**旧配置**服务。于是：

- 线上跑的是 **2026-11-19 之前的配置**；
- 所以 `/api/v1/admin/classrooms` 才会返回 301（旧配置里没有 `location = /api/v1/admin/classrooms` 这条精确匹配）；
- 所以自 11-19 以来所有 nginx 修改（课堂 7 个 `/admin/*` 分流、`= /api/v1/admin/classrooms`）**一条都没上线**。

> ⚠️ **绝对不要在修复前执行 `systemctl restart nginx`。**
> 当前能正常服务完全依赖内存里的旧配置。一旦 restart，旧配置被卸载、磁盘配置又起不来，
> nginx 会**直接起不来 → 整站宕机**，连 `reload` 这条退路都没了。

### 1.4 诊断

```bash
# ① 全量备份（必须先做，出问题能整体回滚）
sudo cp -a /etc/nginx /root/nginx.bak.$(date +%F-%H%M%S)

# ② 三件事一次看清
sudo ls -l /etc/nginx/conf.d/
sudo grep -nE '^\s*include' /etc/nginx/nginx.conf
sudo grep -rn 'limit_req_zone' /etc/nginx/ 2>/dev/null
```

第三条命令的结果直接决定修法：

| `grep limit_req_zone` 输出 | 结论 | 对应小节 |
|---|---|---|
| **完全无输出** | zone 定义文件被删 / 清空 / 改名 | 1.5-A |
| 有输出但不含 `zone=api_zone` | 定义文件在，漏了 api_zone 这一条 | 1.5-B |
| 含 `zone=api_zone` | 定义在，但文件未被 include | 1.5-C |

仓库内另有一份**只读**诊断脚本，可一次跑完全部检查：

```bash
sudo bash deploy/nginx/diagnose-limit-zones.sh
```

### 1.5 修复

#### A. 定义文件缺失

```bash
sudo cp deploy/nginx/conf.d/00-limit-req-zone.conf /etc/nginx/conf.d/00-limit-req-zone.conf
sudo nginx -t
```

该文件定义 4 个 zone，**少任何一个都会让整个 nginx 起不来**：

| zone | 尺寸 | 速率 | 覆盖范围 |
|---|---|---|---|
| `login_zone` | 10m | 5 r/s | `/api/v1/auth/login`、`user/register`、`promo/register-*` |
| `sms_zone` | 10m | 1 r/m | 短信验证码（预置，当前后端无短信端点） |
| `public_zone` | 10m | 50 r/s | `/api/v1/teacher/published`、`/actuator` 等匿名入口 |
| `api_zone` | 20m | 100 r/s | 其余业务接口 |

#### B. 定义文件在但漏 `api_zone`

```bash
grep -n 'limit_req_zone' /etc/nginx/conf.d/*.conf
```

补齐后 `sudo nginx -t`。

#### C. 定义在但没被 include

`/etc/nginx/nginx.conf` 的 `http {}` 块里必须有 `include /etc/nginx/conf.d/*.conf;`，且要**排在 `include /etc/nginx/sites-enabled/*;` 之前**（zone 必须先定义后引用）。

```bash
# 查看是否被注释掉
sudo grep -n 'conf.d' /etc/nginx/nginx.conf

# 恢复被注释的 include
sudo sed -i 's|^[[:space:]]*#[[:space:]]*include /etc/nginx/conf.d/\*\.conf;|    include /etc/nginx/conf.d/*.conf;|' /etc/nginx/nginx.conf
```

### 1.6 逃生路径（急上线时）

若一时找不到 zone 文件、又急着让课堂分流修复上线，可临时关掉限流引用，先让 `-t` 通过：

```bash
sudo cp /etc/nginx/sites-available/booking-ip /root/booking-ip.bak
sudo sed -i '/limit_req zone=/s/^[[:space:]]*/#/' /etc/nginx/sites-available/booking-ip
sudo nginx -t && sudo systemctl reload nginx
```

- 代价：限流关闭（内测环境可接受，等保项需记待补）
- `limit_req_status` 留着无副作用，可单独存在
- 事后补回 zone 定义，再把这行 `#` 去掉

### 1.7 为什么重复发生

```bash
sudo ls -l --time-style=full-iso /etc/nginx/nginx.conf /etc/nginx/conf.d/
```

若 `nginx.conf` 的 mtime 落在某次 `apt upgrade` 附近，即**包管理器用默认版覆盖了配置**并丢了 include。这类问题会周期性复发，建议：

1. `deploy/nginx/` 整个目录纳入部署脚本统一同步，禁止手工 `cp` 单文件；
2. 部署脚本加 `nginx -t` 前置校验，失败即中止，不允许「改了但没生效」的状态长期存在；
3. 定期比对 `sudo md5sum /etc/nginx/... ` 与仓库版本。

## 2. P0-2：消息服务 JWT 密钥分叉导致登录后被秒踢

### 2.1 现象（CDP 实测，非推测）

用 `admin1@qq.com / 123456` 登录后，控制台只有三行，随即回登录页：

```
[error]    Failed to load resource: 401 ()
           /api/v1/users/132bf642.../inbox/unread-count
[error]    登录已过期，请重新登录              <js/messages-inbox.js>
[FAILED]   Document  net::ERR_ABORTED         ← platform_admin.html 加载被中断

最终 URL = http://152.136.254.127/login.html?tCode=platform
```

网络面板里同一请求出现**两次 401**：第一次是原始请求，第二次是换票重试（`__msgRetry` 标记）。

### 2.2 触发链

```
platform_admin.html 加载
  └→ messages-inbox.js 拉未读数 GET /api/v1/users/{id}/inbox/unread-count
       └→ 8090 返回 401「登录状态无效，请重新登录」
            └→ retryWithFreshToken() 换票重试（messages-inbox.js:154）
                 └→ 新 token 仍 401
                      └→ rejectWithMessage() 的 401 分支（messages-inbox.js:180）
                           cleanupAuth() + 600ms 后跳 login.html
```

### 2.3 为什么确认与 nginx 无关

`booking-ip.conf` 的分流是正确的：

| 请求 | 命中 location | 行号 | 上游 |
|---|---|---|---|
| `/api/v1/message-categories` | `location /api/v1/message` | 57 | `127.0.0.1:8090` ✅ |
| `/api/v1/users/{id}/inbox/unread-count` | `location /api/v1/users/` | 74 | `127.0.0.1:8090` ✅ |

两个请求都准确落到 message-service。且返回文案「登录状态无效，请重新登录」是 `MessageAuthInterceptor.java:34` 的**专属分支**——它前面只有一行 `jwtUtil.verifyAccessToken(token)`，验签失败才会走到这里。

如果是分流打错：

- 打到 8081 booking → 文案为「未登录或登录已过期」（`JwtAuthenticationFilter`）或 `{"code":401,"msg":...}`（`TenantInterceptor`，字段名是 `msg` 不是 `message`）
- 打到 8092 classroom → 验签会通过，返回业务响应而非 401

### 2.4 证据链

同一 token 打三个服务：

| 服务 | 端口 | 真实 token | 伪造签名 token | 判定 |
|---|---|---|---|---|
| booking | 8081 | **200** | 401 | 密钥正确 |
| classroom | 8092 | **500**（DB 报错，说明已过鉴权） | 401 | 密钥正确 |
| message | 8090 | **401「登录状态无效」** | 401 | **密钥不一致** |

补充实验：用仓库内默认密钥（三份 `application.properties` 中该串 sha256 完全相同，882 字节）自签 token，**三个服务全部拒绝** → 证明线上三份值都来自环境变量注入，且只有 message 那份与 booking 分叉。

### 2.5 定位（5 分钟，比猜文件可靠）

不要比对文件内容——`EnvironmentFile` 有多种覆盖可能。**直接看三个进程实际吃到的环境变量**：

```bash
for s in booking-api message-service classroom-service; do
  PID=$(pgrep -f "$s.jar" | head -1)
  printf "%-20s " "$s"
  sudo tr '\0' '\n' < /proc/$PID/environ | sed -n 's/^JWT_SECRET=//p' | tr -d '\n' | sha256sum
done
```

三行 sha256 **必须完全相同**。

| 现象 | 含义 |
|---|---|
| 某行输出 `e3b0c44298fc1c14...`（空串哈希） | 该服务没拿到 `JWT_SECRET`，用的是 jar 内默认值 |
| 三行都有值但不一致 | 当前故障，就是它 |
| 三行完全一致 | 密钥没问题，回头查 `SERVER_ADDRESS` / 端口 / 反向代理 |

核对进程名与 env 路径的对应关系（`deploy/` 下三个 unit）：

| 服务 | 进程标识 | EnvironmentFile | jar |
|---|---|---|---|
| booking | `booking-api.jar` | `/etc/lesson/booking.env` | `/opt/lesson/booking-api.jar` |
| message | `message-service.jar` | `/etc/lesson/message.env` | `/opt/lesson/message-service.jar` |
| classroom | `classroom-service.jar` | `/etc/lesson/classroom.env` | `/opt/lesson/classroom-service.jar` |

### 2.6 修复

```bash
# ① 部署共用密钥文件（2026-11-21 起三服务统一从此文件取值，不再各自维护）
sudo cp /opt/lesson/keys.env.template /etc/lesson/keys.env
sudo vi /etc/lesson/keys.env      # 填入 booking.env 的现值；AES/HMAC 必须原样沿用，不能重新生成
sudo chmod 600 /etc/lesson/keys.env && sudo chown lesson:lesson /etc/lesson/keys.env

# ② 确认三份 xxx.env 里没有残留这三个键（残留会按「后加载覆盖」把 keys.env 冲掉）
for f in booking message classroom; do
  printf "%-10s " $f; sudo grep -cE '^(JWT_SECRET|AES_KEY|HMAC_KEY)=' /etc/lesson/$f.env
done
# 期望：三个都是 0

# ③ 确认三个 unit 都加载 keys.env，且排在各自 env 之前
grep -n "EnvironmentFile" /etc/systemd/system/{booking,message-service,classroom-service}.service
sudo systemctl daemon-reload

# ④ 重启三个服务
sudo systemctl restart booking message-service classroom-service
```

若走 `deploy/docker/` 容器化那套：

```bash
docker compose up -d --no-deps message-service   # --no-deps 保护 Redis
```

### 2.7 验证

```bash
for s in booking-api message-service classroom-service; do
  printf "%-20s " "$s"
  sudo tr '\0' '\n' < /proc/$(pgrep -f "$s.jar" | head -1)/environ \
    | sed -n 's/^JWT_SECRET=//p' | tr -d '\n' | sha256sum
done
# 期望：三行哈希完全一致
```

再用真实 token 打一次消息接口，期望 200：

```bash
TOKEN=$(curl -s -X POST http://152.136.254.127/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"account":"admin1@qq.com","password":"123456","tenantCode":"platform","role":"platform_admin"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $TOKEN" \
  http://152.136.254.127/api/v1/message-categories
# 期望：200
```

浏览器侧：重新登录后控制台不应再出现 `inbox/unread-count` 401。

### 2.8 建议的代码加固（非阻塞）

`messages-inbox.js:180` 把**任何** 401 都升级为 `cleanupAuth()` + 整页跳登录，包括「未读数」这种**辅助接口**。一个非关键请求失败就能清掉整个会话，是本次「登录后被秒踢」体验的放大器。

建议：

- 给 `unread-count` / 列表预取这类请求标 `__silent`，401 时只降级不登出；
- 只有真正需要用户身份才能继续的业务 401 才走 `cleanupAuth()`。

## 3. P1：课堂三处遗留

### 3.1 `/api/v1/admin/classrooms` 返回 301

```console
HTTP/1.1 301 Moved Permanently
Server: nginx/1.24.0 (Ubuntu)
Location: http://152.136.254.127/api/v1/admin/classrooms/
Content-Length: 178
```

响应头是 nginx 自己生成的（标准 178 字节页面），说明请求落到了静态 location，被 `try_files $uri $uri/` 识别为目录后补斜杠，**根本没过 8092**。

仓库 `deploy/nginx/booking-ip.conf:165` 已有精确匹配：

```nginx
# 【2026-11-19 修】POST /api/v1/admin/classrooms（创建临时课堂）不带尾斜杠，
# 上面那条前缀 location 匹配不到 → 落到 location /api/v1/ 进 8081 → 403。
location = /api/v1/admin/classrooms {
    proxy_pass http://127.0.0.1:8092;
    include /etc/nginx/proxy_params;
}
```

对应提交 `f48ca505`。**但因为 P0-1，这条从未上线。**

修复顺序：P0-1 修好 → 同步站点配置 → 验证。

```bash
# P0-1 修完后才能执行：
sudo nginx -T | grep -n -A3 "admin/classrooms"     # 必须能看到 location = /api/v1/admin/classrooms

# 若没有，说明服务器站点文件也是旧版
sudo diff /etc/nginx/sites-available/booking-ip deploy/nginx/booking-ip.conf
sudo cp deploy/nginx/booking-ip.conf /etc/nginx/sites-available/booking-ip
sudo nginx -t && sudo systemctl reload nginx
```

> ⚠️ 浏览器对 301 会把 POST 降级成 GET，所以「创建临时课堂」在修好前**必然失败**，且失败方式具有误导性（看起来像 404/405）。

### 3.2 课堂库表缺失

```console
$ curl -H "Authorization: Bearer $TOKEN" .../api/v1/schedules/today
{"code":500,"message":"服务器繁忙：### Error querying database.
 Cause: java.sql.SQLSyntaxErrorException:
 Table 'lesson_appointment.classroom' doesn't exist
 ...The error may exist in com/classroom/mapper/ClassroomMapper.java"}
```

注意这是 **500 而不是 401**，反而成了一个有用的旁证：课堂服务验签是通过的（见 2.4）。

问题在于课堂服务连的库名是 `lesson_appointment`，而该库里没有 `classroom` 表：

```bash
# 确认课堂服务实际连的库
sudo grep -E '^SPRING_DATASOURCE_URL|^DB_' /etc/lesson/classroom.env

# 确认表在哪
mysql -e "SELECT table_schema, table_name FROM information_schema.tables
          WHERE table_name='classroom';"
```

两种修法：

- 库名配错 → 改 `classroom.env` 的 `SPRING_DATASOURCE_URL` 指向正确库后重启；
- 表没建 → 从 `api/sql/` 补齐建表脚本。

### 3.3 课堂开关未开通

```console
$ curl .../api/v1/eclassroom/config
{"code":200,"message":"查询成功","data":{"apiBaseUrl":null,"wsBaseUrl":null,"config":null,"enabled":false}}
```

`enabled:false` 会让前端 `applyMenuVisibility` 直接把课堂菜单 `display:none`，`apiBaseUrl` / `wsBaseUrl` 为 null 则课堂入口无法拼出请求地址。

排查要点（详见 2026-10-29 的「我的课堂」菜单消失记录）：

- 显隐唯一判据是 `/api/v1/eclassroom/config` 的 `enabled`，来自 `sys_tenant_eclassroom` 表；
- **0 行 = 未开通** → Controller 兜 `enabled:false`；
- 平台端「解绑」是物理 delete，一次清空会让所有租户一起失去入口；
- 前端有缓存（`sessionStorage eclassroomConfigVerified`），**只修库不清缓存等于没修**。

```sql
-- 确认是否有记录（平台管理员 tenant_id=0 场景需确认是按租户还是按平台查）
SELECT id, tenant_id, enabled, api_base_url, ws_base_url
FROM sys_tenant_eclassroom;
```

补齐种子可用 `api/sql/patch/20261029-1300-eclassroom-default-instance.sql`。

## 5. 回滚预案

| 阶段 | 回滚动作 |
|---|---|
| nginx 配置 | `sudo rm -rf /etc/nginx && sudo cp -a /root/nginx.bak.<时间戳> /etc/nginx && sudo systemctl reload nginx` |
| 站点配置单文件 | `sudo cp /root/booking-ip.bak /etc/nginx/sites-available/booking-ip && sudo systemctl reload nginx` |
| 密钥 | 改回原值并 `systemctl restart message-service`（注意：回滚密钥会让登录再次被踢） |

**回滚铁律**：任何阶段只要 `nginx -t` 不通过，就**不要 reload**；旧 worker 会继续用内存配置服务，站点不受影响。这是 nginx 的无损特性，务必利用它而不要用 `restart` 去「试」。

## 6. 本次故障的三个经验

1. **`syntax is ok` ≠ 配置可用。** `zero size shared memory zone` 出现在语法检查之后、不带行号，是本项目最容易被误判的报错。它的真实含义是「定义没加载进来」，不是「语法写错了」。

2. **reload 失败会静默积累技术债。** 配置改动「改完就以为生效了」，实际旧 worker 一直在跑旧配置。11-19 修的课堂分流因此从未上线，直接导致了后来的 301。部署流程里应该把 `nginx -t && reload` 的返回值作为硬门槛，失败必须告警。

3. **跨服务密钥分叉的排查要用进程环境，不要读文件。** 三份 `application.properties` 的默认值 sha256 完全一致，光看代码永远查不出来；`EnvironmentFile` 的实际注入结果才是真相。
