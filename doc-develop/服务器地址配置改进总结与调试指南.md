## 一、背景与问题演进

| 阶段 | 问题 | 根因 |
|---|---|---|
| 部署 008 前 | 前端 dist 无法作为独立容器部署 | 无 Dockerfile |
| 部署 009 | nginx 启动即崩：`invalid URL prefix in default.conf:90` | nginx 官方镜像的 `20-envsubst-on-templates.sh` 在**运行时**渲染模板，但云托管 EKS 未透传镜像 `ENV`，`${API_UPSTREAM}`/`${MSG_UPSTREAM}` 保持字面量 |

| 小程序侧 | 上游地址硬编码在 `app.js`，换后端地址必须重新发版（审核周期长）；`msgBase` 还是 `<envid>` 占位符 | 地址未配置化 |

## 二、前端容器改动（cloudBased/frontend/）

### 2.1 目录结构

```
cloudBased/frontend/
├── dist/                      # 编译产物（含 app-config.json）
│   └── app-config.json        # ★ 小程序远程配置
├── Dockerfile                 # 构建期渲染 + 校验
├── default.conf.template      # nginx 站点配置模板
└── resolver-entrypoint.sh     # 容器入口脚本（生成 resolver 配置）
```

### 2.2 Dockerfile（当前版）

```dockerfile
FROM nginx:alpine
COPY dist /var/www/frontend
COPY default.conf.template /etc/nginx/templates/default.conf.template

COPY resolver-entrypoint.sh /docker-entrypoint.d/00-resolver.sh
RUN chmod +x /docker-entrypoint.d/00-resolver.sh

# 构建期渲染（云托管运行时不透传 ENV，运行时模板渲染不可靠）
ARG API_UPSTREAM=http://api.329614-8-1475810246.svc.cluster.local:8081
ARG MSG_UPSTREAM=http://message-service.329614-8-1475810246.svc.cluster.local:8090
RUN API_UPSTREAM="${API_UPSTREAM}" MSG_UPSTREAM="${MSG_UPSTREAM}" \
    envsubst '$API_UPSTREAM $MSG_UPSTREAM' \
    < /etc/nginx/templates/default.conf.template \
    > /etc/nginx/conf.d/default.conf \
    && rm /etc/nginx/templates/default.conf.template

RUN nginx -t        # 构建期校验（变量形式的 proxy_pass 不会触发 DNS 解析）
EXPOSE 8080
CMD ["nginx", "-g", "daemon off;"]
```

关键设计：

1. **构建期 envsubst 渲染**并**删除模板**（`rm` 必须保留——否则运行时官方镜像会用缺失的环境变量再次渲染，把配置覆盖回字面量 `${...}`，009 的错误重现）
2. **`RUN nginx -t` 构建期校验**：配置有问题时构建即失败，不再等部署 227 秒后才报错

### 2.3 default.conf.template 关键改动

- `root` → `/var/www/frontend`（dist 复制目标，原模板是 `/usr/share/nginx/html`）
- **上游改为 nginx 变量 + resolver 延迟解析**（解决 010 的构建失败 + 运行期后端不可达 crash-loop）：

  ```nginx
  set $api_upstream "${API_UPSTREAM}";
  set $msg_upstream "${MSG_UPSTREAM}";
  ...
  proxy_pass $api_upstream;      # 变量形式：启动/测试时不解析域名
  ```

- 新增 `location = /app-config.json { expires -1; }`：小程序远程配置强制回源，改配置即时生效
- 保留模板原有能力：安全响应头、限流 zone、SSE 三条必配、多页应用 `try_files ... =404`

### 2.4 resolver-entrypoint.sh

官方镜像按文件名序执行 `/docker-entrypoint.d/` 下脚本，`00-` 序号保证最先执行：

```sh
NS=$(awk '/^nameserver/{print $2; exit}' /etc/resolv.conf)
echo "resolver ${NS} valid=10s ipv6=off;" > /etc/nginx/conf.d/00-resolver.conf
```

从 `/etc/resolv.conf` 动态提取 DNS（K8s / Docker 通用），供 `proxy_pass $var` 运行时解析。后端暂不可达时返回 502 而非容器 crash-loop。

### 2.5 app-config.json（小程序远程配置）

```json
{
  "apiBase": "https://api-329614-8-1475810246.sh.run.tcloudbase.com",
  "msgBase": "https://message-service-329614-8-1475810246.sh.run.tcloudbase.com",
  "webBase": "https://api-329614-8-1475810246.sh.run.tcloudbase.com",
  "rev": "20261110-01"
}
```

> ⚠ `app-config.json` 在 `dist/` 内，前端重新构建可能清掉它——构建后务必确认存在（长期应加入构建脚本生成）。

## 三、小程序改动（miniprogram/）

### 3.1 三层配置优先级（app.js onLaunch）

```
① storage 调试覆盖   wx.setStorageSync('upstream_override', {...})
② 远程配置           GET {webBase}/app-config.json（5s 超时，失败静默）
③ 内置默认值         config/env.js 按 envVersion 选 develop/trial/release
```

- `onLaunch` 先注入 ③ 保证请求立即有地址可用（不阻塞启动），再异步拉取 ②
- `core/request.js` 每次请求实时读 `globalData`，远程配置到达后**后续请求自动切换**，已发出请求不受影响
- `applyConfig` 只接受 `apiBase/msgBase/webBase` 三键，防配置文件夹带脏数据
- 远程拉取失败 / 配置结构不合法 / develop 无 webBase → 静默保留 ③ 兜底

### 3.2 config/env.js

按 `wx.getAccountInfoSync().miniProgram.envVersion` 自动切换：

| envVersion | 触发方式 | 地址 |
|---|---|---|
| `develop` | 开发者工具运行 | `http://127.0.0.1:8081` / `:8090`（需勾选「不校验合法域名」） |
| `trial` | 上传后设为体验版 | 云托管 https 域名 |
| `release` | 审核通过正式版 | 同 trial，正式域名变更时只改此块 |

`resolveEnv()` 取不到 envVersion 或基础库过旧时兜底回落 `release`。

### 3.3 app-config.json 变更流程（免发版换地址）

1. 编辑 `cloudBased/frontend/dist/app-config.json`（改完可递增 `rev` 便于核对）
2. 重新构建部署**前端镜像**（nginx 容器托管该文件）
3. 小程序**无需发版**，下次冷启动即拉到新配置

## 四、部署生效步骤

```powershell
# 前端：改 upstream 地址 → 改 Dockerfile 中 ARG 默认值（或 CI 传 --build-arg）→ 重新部署版本
# 小程序：config/env.js 与 dist/app-config.json 同步更新后，重新上传发版一次（此后换地址免发版）
```

云托管控制台「版本配置 → 环境变量」填的运行时 ENV **不会**影响本镜像的 nginx 上游（构建期已渲染、模板已删）；运行时 ENV 只对读取环境变量的进程有效。

## 五、调试方法

### 5.1 前端容器

```bash
# 1) 看渲染后的最终配置（确认上游地址已注入、无字面量 ${...}）
docker exec <容器> cat /etc/nginx/conf.d/default.conf | grep -n "proxy_pass\|set \$"

# 2) 看 resolver 是否生成（应为 /etc/resolv.conf 里的 nameserver）
docker exec <容器> cat /etc/nginx/conf.d/00-resolver.conf

# 3) 容器内验证配置与 DNS
docker exec <容器> nginx -t
docker exec <容器> nslookup api.329614-8-1475810246.svc.cluster.local

# 4) 云托管日志里 502 的三种形态（定位上游问题）
#   "xxx could not be resolved (3: Host not found)"   → 域名/服务名错
#   "connect() failed (111: Connection refused)"      → 域名对但端口错/后端未起
#   "upstream timed out"                              → 网络隔离/安全组拦截
```

### 5.2 小程序

```js
// 开发者工具 console：
// ① 查看当前生效配置
console.log(getApp().globalData)

// ② 临时指向其他后端（优先级最高，命中后跳过远程配置）
wx.setStorageSync('upstream_override', { apiBase: 'http://127.0.0.1:8081', msgBase: 'http://127.0.0.1:8090' })
// 恢复：
wx.removeStorageSync('upstream_override')

// ③ 验证远程配置可达且版本正确：浏览器直接访问
//   https://<webBase>/app-config.json   → 检查 rev 字段与 JSON 结构
```

### 5.3 快速排查清单

- [ ] 页面打不开 → nginx 没起：看启动日志是否 `emerg`；容器是否 crash-loop
- [ ] 页面能开、接口 502 → 上游问题：按 5.1-4) 三种日志形态定位
- [ ] 小程序改配置未生效 → ① 是否有 `upstream_override` 残留 ② `app-config.json` 是否被构建清掉 ③ nginx 是否 no-cache（`expires -1`）
- [ ] 小程序请求直接失败 → 域名是否加入 mp.weixin 后台「request 合法域名」（https、不带端口）

## 六、已知约束与坑（务必遵守）

1. **云托管公网入口只走 443**：上游/前端地址不能带 `:8081/:8090`（网关丢弃非 443 的 SYN，表现为超时）
2. **微信合法域名**：https 且不带端口；`webBase` 自方案二起参与真实请求，必须加白名单
3. **运行时 ENV 不可靠**：云托管未透传镜像 ENV（009 实证），nginx 上游一律走构建期 ARG
4. **模板删除不可省**：保留 `/etc/nginx/templates/` 下模板会被运行时二次渲染覆盖
5. **`message-service` 是连字符**：不是 `message-`（模板作者特别标注过）
6. **`app-config.json` 构建易被清**：每次前端构建后检查
7. **`--build-arg` 值含 `&` 等字符时**注意 shell 转义；地址变更优先改 `Dockerfile` ARG 默认值而非 CI 传参，避免环境间不一致
