# 枚举字段（语言类型/难度/班级形式）在列表中不显示行业词 —— 分析与方案

> 状态：**已按方案 A 实施并完成回归**（2026-09-10 13:10，见第 7 节）
> 原分析保留，用于追溯根因；实际改动以第 7 节为准。
> 现象：legal 行业下，"课程模板"的语言类型下拉显示正常（婚姻 / 劳动 / 刑事 / 行政），
> 但**模板列表**里显示成 `english` / `English` 这类原始 code；"课程列表"（模板信息列）同理。

---

## 1. 结论速览

| # | 结论 | 性质 |
|---|------|------|
| 1 | 列表单元格**直接渲染数据库原始 code**，没有做任何 code → 显示词的转换 | 直接原因 |
| 2 | 全项目**不存在** code → 显示词的转换函数（grep `getLanguageTypeName / typeText` 零命中） | 结构原因 |
| 3 | 显示词只存在于 `<option>` 的 DOM 文本里，靠 `data-term` 换词；**JS 数据层拿不到这层映射**，所以拼字符串的列表渲染必然显示裸 code | 架构原因 |
| 4 | `classType` 用**序号型** key（`classType1..4`），而 `classForm` / `classLevel` 用**code 后缀型**（`classForm1p1`、`classLevelB1`）。因此语言类型**套用不了** `data-term="classForm${code}"` 这个现成土办法 | 语义不一致 |
| 5 | code ↔ 序号 的映射在 **5 处写了 3 套，互相矛盾**（`admin-template.js` 的新增表单与筛选下拉本身就冲突） | **附带 Bug** |
| 6 | `termsFunction.js` 的 `getOptions(tagKey, fallbackOptions)` 正是为解决此事设计的，**目前零使用** | 已有设施未用 |

**一句话**：不是"词条没配"，也不是"行业没切"，而是**列表渲染从未做过 code → 词的反查**，再叠加**同一 code 在不同页面映射到不同序号**的错位。

## 2. 根因拆解

### 2.1 直接原因：列表直接输出裸 code

`js/admin-template.js:401`（课程模板列表）

```js
<td>${template.languageType || ''}</td>      // ← 数据库里是什么就显示什么
```

`js/admin-course.js:390`（课程列表的"模板信息"列）

```js
let tempInfo = templateObj ? templateObj.languageType + " " + templateObj.difficultyLevel + " " + templateObj.classFee : "";
```

同类裸输出还有：

| 位置 | 内容 |
|---|---|
| `js/admin-course.js:73` | 添加课程时"选择模板"下拉：`template.languageType + " " + difficultyLevel + ...` |
| `js/admin-course.js:105` | 教师下拉：`teacher.name + " " + teacher.languageType + ...` |
| `js/admin-dataMaintainPage.js:175` | 数据维护页列定义 `{key:"languageType", label:"语言类型"}`，渲染走通用表格 → 同样是裸值 |
| `js/public/datamaintain_delete.js:100` | 删除确认里的模板信息串 |

### 2.2 结构原因：显示词只在 DOM 里，JS 数据层没有

下拉是这么写的（`js/admin-course.js:256-259`）：

```html
<option value="french"><span data-term="classType1">法语</span></option>
```

- `value` 是 **code**（存库用）
- 可见文本由 `applyTerms()` 把 `data-term="classType1"` 换成行业词（legal 下 = 婚姻）

**"code → 显示什么"这件事只存在于 `<option>` 这个 DOM 节点上**。列表是 JS 拼模板字符串，拿不到 option 的文本，于是只能把 code 拼进去。这就是"下拉正常、列表露馅"的完整解释。

### 2.3 语义不一致：序号型 key vs code 后缀型 key

`sys_term` 现状（`api/beforeRun/sql/sys_term_upsert_to_target.sql`）：

| 字段 | key 命名 | 示例 | 能否 `data-term="前缀${code}"` 拼出来 |
|---|---|---|---|
| 班级形式 | `classForm` + **code** | `classForm1p1`、`classForm1pN`、`classForm1p2N` | ✅ 能 |
| 难度等级 | `classLevel` + **code** | `classLevelB1` … `classLevelB4` | ✅ 能 |
| **语言类型** | `classType` + **序号** | `classType1` … `classType4` | ❌ **不能**（code 是 `english`，序号是 1~4，拼不上） |

所以课程表格里班级形式能用土办法（`js/admin-course.js:405`）：

```html
<span data-term="classForm${templateObj.classForm}">${templateObj.classForm || ''}</span>
```

而语言类型**没法照抄** —— 这就是它单独出问题的原因。

> 备注：`termsFunction.js:23` 的 `getOptions(tagKey, fallbackOptions)` 设计的是 `key = tagKey + '.' + code`
> （如 `classType.french`），但 `sys_term` 里**没有任何点号 key**（`grep 'classType\.'` = 0 条），所以这条现成路也走不通。

### 2.4 附带 Bug：同一 code，5 处写了 3 套映射（互相矛盾）

实测提取（`<option value>` → `data-term`，以及去掉标签后的可见文本）：

| 文件 | 位置 | french | english | chinese | spanish |
|---|---|---|---|---|---|
| `admin-course.js` | 256-259（课程表单） | classType1 法语 | classType2 英语 | classType3 汉语 | classType4 西语 |
| `admin-schedule.js` | 237（排期筛选） | classType1 法语 | classType2 英语 | classType3 汉语 | classType4 西语 |
| `student-bookingCards.js` | 28（学生端筛选） | classType1 法语 | classType2 英语 | classType3 汉语 | classType4 西语 |
| **`admin-template.js`** | **277-281（模板筛选）** | classType2 ❌ | classType1 ❌ | classType3 ✅ | classType4 ✅ |
| **`admin-template.js`** | **101-107（模板新增表单）** | classType2 ❌ | classType1 ❌ | **classType4（spanish）** ❌ | **classType3（chinese）** ❌ |

以平台词表为准（`sys_term` 平台 zh：`classType1=法语 / 2=英语 / 3=汉语 / 4=西语`），
**正确映射只有一套**：`french→1`、`english→2`、`chinese→3`、`spanish→4`（即上表前三行）。

后果（legal 行业：1=婚姻、2=劳动、3=刑事、4=行政）：

| 数据 code | 课程/排期/学生端显示 | 模板筛选显示 | 模板新增表单选中时显示 |
|---|---|---|---|
| `french` | 婚姻 | **劳动** | **劳动** |
| `english` | 劳动 | **婚姻** | **婚姻** |
| `chinese` | 刑事 | 刑事 | **行政** |
| `spanish` | 行政 | 行政 | **刑事** |

→ **同一条模板数据，在"课程"页和"课程模板"页看到的行业词不是同一个**；而且在模板页，"新增时选的词"和"筛选里同一个词"指的不是同一个 code。这比"列表显示 code"更危险，属于数据语义错乱。

### 2.5 同类未走词条的字段（顺带记录）

`js/admin-template.js:402-407` 难度、班级形式是**硬编码三元表达式**：

```js
${template.difficultyLevel === 'B1' ? 'B1入门' : ...}
${template.classForm === '1p1' ? '一对一' : ...}
```

切换行业后这些**永远不会变**（虽然难度/班级形式在各行业词表里的文案确实相同，但与 `classForm${code}` 的土办法并存，属于两套写法、维护两处）。

## 4. 方案对比

### 方案 A（推荐）：建唯一权威 code 表 + 反查函数，沿用现有 `classType1..4`

在 `js/public/terms.js`（或新建 `js/public/enumOptions.js`）声明**一处**权威映射：

```js
const COURSE_TYPE_OPTIONS = [
  { value: 'french',  termKey: 'classType1', anchor: '法语' },
  { value: 'english', termKey: 'classType2', anchor: '英语' },
  { value: 'chinese', termKey: 'classType3', anchor: '汉语' },
  { value: 'spanish', termKey: 'classType4', anchor: '西语' },
];

// 下拉：复用 getOptions（termsFunction.js 已有，需小改以接受显式 termKey）
// 列表反查：
function courseTypeText(code) {
  const o = COURSE_TYPE_OPTIONS.find(x => x.value === String(code || '').trim().toLowerCase());
  if (!o) return code || '';                       // 未知值原样显示，便于发现脏数据
  const t = (typeof getTerms === 'function') ? getTerms() : {};
  return t[o.termKey] || o.anchor;                 // 行业词 → 锚点词 → 兜底
}
```

- 列表/拼接处统一改为 `courseTypeText(x.languageType)`
- 5 处下拉改为由 `COURSE_TYPE_OPTIONS` 生成（顺带修掉 2.4 的三套错位）
- 难度/班级形式同样补 `difficultyText()` / `classFormText()`，消掉硬编码三元

| 优点 | 缺点 |
|---|---|
| 不动后端词条、不动 DB 数据，纯前端 | 仍受"4 个序号"上限约束 |
| 一次修好错位 Bug + 列表显示 | 新增第 5 种语言类型需加词条 |

### 方案 B：词条 key 改为 `classType.french`（点号 = tagKey + code）

- 后端 `sys_term` 补 4 code × 4 行业 × 语言 的词条；前端 `data-term` 全部改写；`getOptions()` 可原样复用（它本来就是这设计的）
- 语义最直白、扩展性好，与 `classForm1p1` 风格一致

| 优点 | 缺点 |
|---|---|
| 一劳永逸，扩展无需改序号 | 需改后端词条数据 + 全部前端引用，改动面大 |
| 与 `classForm*`/`classLevel*` 命名体系统一 | 存量数据的 code 不变，但需保证新旧 key 同时存在或做迁移 |

### 方案 C：沿用序号，页面写 `<span data-term="classType${序号(code)}">`

即把 `code → 序号` 的映射塞进模板字符串。

| 优点 | 缺点 |
|---|---|
| 改动量最小，与 `classForm${code}` 写法一致 | 仍需一个 `序号(code)` 函数 → 本质就是方案 A，但**更脆**：列表刷新后需再 `applyTerms(container)`，且未知 code 会拼出 `classTypeundefined` |
| — | 不解决 2.4 的下拉错位 |

**推荐 A**：改动集中、风险低、能顺带修掉更严重的映射错位；后续若要扩展语言类型，再平滑迁移到 B。

## 7. 实施结果（方案 A，已落地）

### 7.1 新增 `frontend/js/public/enumTerms.js`（唯一权威映射）

独立于 `terms.js` 新建（不污染词典文件），导出到 `window`：

| API | 用途 | 输出示例 |
|---|---|---|
| `COURSE_TYPE_OPTIONS` | code ↔ 词条 key 的唯一映射表（顺序即下拉顺序） | `[{value:'french',termKey:'classType1',anchor:'法语'}, …]` |
| `courseTypeText(code)` | 字符串拼接场景 | `courseTypeText('english')` → legal 下 `"劳动"` |
| `courseTypeCellHtml(code)` | 列表单元格（带 `data-term`，切行业会被 `applyTerms` 刷新） | `<span data-term="classType2">劳动</span>` |
| `courseTypeOptionsHtml(selected, opts)` | 下拉 `<option>` 片段 | 含 `selected`、`{empty:'全部'}` 空选项 |
| `enumTermText(prefix, code)`<br>`enumTermCellHtml(prefix, code)` | code 后缀型字段通用版（难度等级 / 课程形式） | `enumTermText('classForm','1p1')` → legal 下 `"个案咨询"` |

权威映射（与 `TERM_DICT.education` 一致）：

```
french  → classType1（法语）    english → classType2（英语）
chinese → classType3（汉语）    spanish → classType4（西语）
```

兜底链：**服务端合并词 > 当前行业词 > 锚点词**；未知 code **原样输出**（不丢数据、不出 `undefined`）。

### 7.2 修掉的映射错位 Bug

`admin-template.js` 的新增/编辑表单与筛选下拉原本把 `english↔french` 写反（两套还互不相同），
与 `admin-course.js` / `admin-schedule.js` / `student-bookingCards.js`（正确一套）冲突。
即：**同一条数据在模板页显示"劳动"、在课程页却显示"婚姻"**。现已全部收敛到同一份映射。

### 7.4 踩到的两个坑（已沉淀）

1. **`const TERM_DICT` 是词法声明，不挂到 `window`**（浏览器与 Node vm 行为一致），
   模块里必须用裸标识符 + `typeof TERM_DICT !== 'undefined'` 探测，不能写 `window.TERM_DICT`。
2. **服务端词表可能含空串条目**：`Object.assign` 合并后会把行业词覆盖成 `''`，
   若因此直接掉到锚点词，legal 行业下会显示 education 的"英语"。故兜底链里单独加了一层"当前行业词"。
