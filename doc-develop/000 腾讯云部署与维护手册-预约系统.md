# 预约系统腾讯云部署流程与维护手册

> 适用项目：lesson-appointment（**前后端分离架构**，2026-09 起）
> 云平台：腾讯云（轻量应用服务器或 CVM 均适用，本文以轻量应用服务器 + Ubuntu 22.04 为例）
> 读者假设：有基本计算机知识，会用命令行复制粘贴命令即可
>
> **阅读指引**
> - 第 0 章：先记牢四份产物和配置文件都放哪（**所有路径问题在这一章一次说清**）
> - 第 1、2 章：**本地**环境搭建与日常启动联调（开发每天用）
> - 第 3 章：**云服务器**完整部署过程（所有配置文件都给出「文件名 + 完整内容」，可在本地建好再上传）
>   - **3.4.1 是 `scp` / `rsync` 复制文件与文件夹的集中速查**——单文件、多文件、整个目录、下载回本地、指定端口密钥、`/etc` 目录的中转写法，全手册的上传命令都按它写。找不到"怎么把文件传到服务器"就先看这一节。
> - 第 4 章：配置文件位置速查表（本地 vs 服务器对照）
> - 第 5、6 章：日常维护与故障速查
>
> **姊妹篇**：《预约系统云服务器部署和维护手册.md》（同目录）偏"原理 + 排障"，本手册偏"照着做"。两本内容一致，冲突时以本手册第 3 章的操作步骤为准。
>
> **⚠️ 版本变更说明**：本手册早期版本针对 `api-1.0.0.jar`（**jar 内自带前端页面**）。现在前端已迁出为独立产物 `frontend/dist`，各个 jar 是**纯后台**（只提供 REST 接口与一个 `/` 缺省页）。旧步骤里的"访问 8081 看登录页"已不成立。
>
> **⚠️ 三服务说明（2026-10-30 起）**：后端已从 2 个服务变为 **3 个独立服务**，本手册全部相关内容已同步：
>
> | 服务 | 端口 | 独立库 | 责任 |
> |------|------|--------|------|
> | `booking-api`（主业务/平台端） | **8081** | `lesson_appointment` | 租户、用户、课程、排期、预约、推广…；课堂**开关**配置（`/api/v1/eclassroom`）与课堂**回调落点**（`/api/v1/classroom-callback/`）也在这里 |
> | `message-service`（消息中心） | **8090** | `message_center` | 消息收发、收件箱、模板、敏感词、SSE 推送 |
> | `classroom-service`（在线课堂） | **8092** | `classroom`（+ 只读主库做开关判定） | 课堂生命周期、出勤、点名、白板/信令 WebSocket、讲稿与录制、运营台 |
>
> **新增两个外部依赖（前两个服务不需要）**：
> - **Redis**（`classroom-service` 用 db 2）：在线状态判定的唯一真相源 + 用户维度限流计数；
> - **对象存储目录**（默认本机磁盘 `./data/oss`，可扩到 S3/OSS）。
>
> **三个服务是同源分流关系，不是三套部署**：前端只有一份 `dist`，由 Nginx 静态伺服；三个服务只提供 `/api/v1/**`，靠 Nginx 按前缀分流（8092 的分流规则最容易漏，见 3.5.5）。

## 第 0 章 先记牢：四份产物 + 配置文件地图

### 0.1 四份产物（部署时传的就是这四个）

| 产物 | 构建命令（项目根目录执行） | 产物路径 | 是否含页面 | 部署到 |
|------|---------------------------|----------|-----------|--------|

### 1.2 本地数据库初始化（三个库）

本地需要三个库：`lesson_appointment`（业务）、`message_center`（消息中心）、`classroom`（在线课堂）。

SQL 脚本**不在 `api/beforeRun/`**（旧手册写的 `api/beforeRun/sql/` 已在提交 `f0bf2fbd` 删除），真实位置是 `api/sql/{schema,seed,patch}/` 与 `api/classroom-service/sql/`：

| 顺序 | 真实文件 | 作用 | 是否自带建库 |
|------|----------|------|-------------|
| 1 | `api/sql/schema/20261013-0400-lesson_appointment-schema.sql` | 业务库全量表结构 | ❌ **不带** `CREATE DATABASE`，先建库再导 |
| 2 | `api/sql/seed/20261008-1527-lesson_appointment-seed-dict-config.sql` | 行业、套餐模板、系统配置、**术语 317 行** | ❌ 需指定库名（术语已并入，不再需要替换占位符） |
| 3 | `api/sql/schema/20261008-1527-message_center-schema.sql` | 消息库表结构 | ❌ **不带** `CREATE DATABASE` |
| 4 | `api/sql/seed/20261008-1528-message_center-seed-sys.sql` | 消息分类、模板、敏感词 | ❌ 需指定库名 |
| 5 | `api/classroom-service/sql/classroom-schema.sql` | 课堂库建库建表（205 行，**不含** `sys_eclassroom_instance` 种子） | ✅ 自带 `CREATE DATABASE` + `USE` |
| — | `api/sql/patch/*.sql`（19 个）、`api/classroom-service/sql/patch/*.sql` | 增量补丁，按文件名顺序执行 | ❌ 多数需指定库名 |

> **课堂库的两条隐性依赖**（建库/授权时最容易漏）：
> 1. `classroom-service` 要**只读**主业务库的 `sys_tenant_eclassroom`（判断某租户是否开通课堂），
>    所以它的 DB 账号对 `lesson_appointment` 库必须有 `SELECT` 权限，且**两个库在同一个 MySQL 实例**上；
> 2. 课堂实例表 `sys_eclassroom_instance` 为空 → 前端拿不到 `enabled=true` → **课堂入口根本不出来**。
>    建库时务必确认该表有种子行（仓库补丁：`api/sql/patch/20261029-1300-eclassroom-default-instance.sql`）。

> ⚠️ **schema 快照时点为 2026-10-13**（旧手册里的 `lesson_appointment_schema_fixed.sql` 已不存在）。
> 快照之后新增的列/表一律靠 `api/sql/patch/` 补齐，**导完 schema 与 seed 后必须把 patch 全部按序执行**
> （patch 目录随版本累积，以目录内最新清单为准）。

**Windows（Git Bash 或 PowerShell，在项目根目录执行）**：

```bash
cd api/sql

# 0) 先建前两个库（schema 脚本不自带 CREATE DATABASE；课堂 schema 会自建）
mysql -uroot -p123456 -e "CREATE DATABASE IF NOT EXISTS lesson_appointment DEFAULT CHARACTER SET utf8mb4; CREATE DATABASE IF NOT EXISTS message_center DEFAULT CHARACTER SET utf8mb4;"

# 1) 业务库结构 + 种子（种子已含 sys_term 术语）
mysql -uroot -p123456 lesson_appointment < schema/20261013-0400-lesson_appointment-schema.sql
mysql -uroot -p123456 lesson_appointment < seed/20261008-1527-lesson_appointment-seed-dict-config.sql

# 2) 消息库结构 + 种子
mysql -uroot -p123456 message_center < schema/20261008-1527-message_center-schema.sql
mysql -uroot -p123456 message_center < seed/20261008-1528-message_center-seed-sys.sql

# 3) 课堂库（自带 CREATE DATABASE classroom）
mysql -uroot -p123456 < ../classroom-service/sql/classroom-schema.sql

# 4) 增量 patch（按文件名顺序，**按目标库分别执行** —— 别一刀切打同一个库）
#    每个 patch 文件头都标注了目标库；命名含 message 的打 message_center，课堂的 classroom
mysql -uroot -p123456 lesson_appointment < patch/20261011-0100-appointment-refund-snapshot.sql
mysql -uroot -p123456 lesson_appointment < patch/20261029-1300-eclassroom-default-instance.sql
mysql -uroot -p123456 classroom          < ../classroom-service/sql/patch/20261028-1800-closing.sql
#    其余 patch 照此逐个执行（ls patch/ 看现有清单，按时间戳顺序）
```

> 首次部署的最小集就是上面这些；`api/sql/patch/` 里另有与业务无关的一次性脚本（数据修复类），
> 按 `api/sql/README.md` 的说明按需执行，不必全跑。

**Linux / macOS / 服务器**（上传后的落点是 `/opt/lesson/sql/{schema,seed,patch,classroom}`）：

### 1.3 本地配置文件在哪、怎么改（不改源码的三种方法）

**源码配置位置（不要在这里写生产密钥）**：

| 文件 | 关键项 |
|------|--------|
| `api/src/main/resources/application.properties` | `server.port=8081`、DB `lesson_appointment`、`jwt.secret`、`crypto.aes-key`、`crypto.hmac-key`、`DB_USERNAME/DB_PASSWORD` 占位 |
| `api/message-service/src/main/resources/application.properties` | `server.port=8090`、DB `message_center`、三个密钥（必须与 booking 相同） |
| `api/classroom-service/src/main/resources/application.properties` | `server.port=8092`、DB `classroom`、Redis `database=2`、`booking.api.base-url`（回调 8081）、`classroom.storage.*`（本地存储根）、`classroom.rtc.*`（媒体选型）、三个密钥（必须与 booking 相同） |

**三种不改源码的覆盖方式（推荐程度从高到低）**：

1. **命令行参数**（最省事，适合临时调试）

   ```bash
   java -jar api/target/booking-api-2.0.0.jar \
        --server.port=8081 \
        --spring.datasource.url="jdbc:mysql://localhost:3306/lesson_appointment?useUnicode=true&characterEncoding=utf8&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true" \
        --spring.datasource.username=root --spring.datasource.password=123456
   ```

2. **外置 `application.properties`**（适合长期固定一套本地配置）

   Spring Boot 启动时会读 **当前工作目录** 下的 `./config/application.properties` 和 `./application.properties`，优先级高于 jar 内配置。
   在 `api/target/` 下新建文件 **`application.properties`**（与 jar 同目录）：

   ```properties
   # ===== 本地开发环境覆盖配置：api/target/application.properties =====
   # 只在本地生效，不会被打进 jar（target/ 已 gitignore）
   server.port=8081
   spring.datasource.url=jdbc:mysql://127.0.0.1:3306/lesson_appointment?useUnicode=true&characterEncoding=utf8&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true
   spring.datasource.username=root
   spring.datasource.password=123456
   # 本地日志：打印 SQL 便于调试（生产不要开）
   logging.level.com.reservation.mapper=DEBUG
   ```

   同理，`api/message-service/target/application.properties`：

   ```properties
   # ===== 本地开发环境覆盖配置：api/message-service/target/application.properties =====
   server.port=8090
   ```

### 2.4 ⚠️ 密钥域铁律（本地联调最常见的 401 根因）

> token 只能被**与其同源密钥**的服务校验。`JwtAuthenticationFilter` 只验签名、不查 session。

| 拓扑 | 是否可用 | 前提 |
|------|---------|------|
| 全本地（本地 booking 8081 + message 8090 + classroom 8092） | ✅ | 三者都用源码 `application.properties` 的 `jwt.secret`，同源 |
| 全远程（远程 booking + message-service + classroom-service） | ✅ | 远程三个服务同为系统密钥；需远程 8090/8092 放行 |
| **混合**（本地任一服务 + 远程任一服务） | ❌ **必 401** | 密钥不同源，无解，只能改成上面两种之一 |

典型症状：消息列表/收件人加载报 `{"code":401,"message":"未登录或登录已过期"}`；
课堂页进不去、白板/心跳 WebSocket 握手被拒（同样 401）。
另外要注意：`/api/v1/message/system/info` 返回 booking 的 401 文案，说明**请求根本没路由到 8090**（分流问题），不是权限问题。


### 2.5 本地常见故障

| 症状 | 原因 | 处理 |
|------|------|------|
| 页面空白但接口有数据 | 前端对**已解包**的响应又取了一次 `.data` | 页面必须走 `unwrapPayload` / `unwrapBackendPayload`；详见姊妹篇 10.2 |
| `Address already in use` | 端口被占用 | `netstat -ano \| findstr :8081` 找 PID 后结束，或换 `--server.port` |
| 报数据库连接失败 | MySQL 未启动 / 库未建 / 密码不对 | 按 1.2 重新导库；确认 `root/123456` |
| 排期时间差 8 小时 | `serverTimezone=UTC`（源码默认） | 本地覆盖配置里改 `Asia/Shanghai` |
| 改了 js 刷新没变化 | 伺服的是 dist 不是源码 | 改用 `dev-frontend-local-src.js`，或 `Ctrl+F5` |
| 启动后立刻绑到别的端口 | 环境变量 `SERVER_PORT`/`SERVER__PORT` 被宽松绑定 | 启动命令显式带 `--server.port=8081` |

### 3.3 数据库：建账号 + 导两个库

**创建应用专用账号**（应用不用 root）：

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON message_center.*     TO 'lesson'@'localhost';
GRANT SELECT, INSERT, UPDATE, DELETE ON classroom.*          TO 'lesson'@'localhost';
```

> **课堂的跨库只读**：`classroom-service` 除了自己的 `classroom` 库，还要**只读**主库的

#### 3.4.1 向服务器复制文件与文件夹：命令速查

> 本节是所有 `scp` / `rsync` 用法的**集中出处**。3.4、3.5 以及后续章节里的上传命令，写法都来自这里。

**① 一条铁律：结尾的 `/` 决定"传目录本身"还是"传目录里的内容"**

```bash
scp -r frontend/dist  $SERVER:/var/www/frontend/    # ❌ 传的是【目录本身】
                                                     #    → /var/www/frontend/dist/index.html
scp -r frontend/dist/ $SERVER:/var/www/frontend/    # ✅ 传的是【目录里的内容】
                                                     #    → /var/www/frontend/index.html
```

Nginx `root /var/www/frontend` 找的是**同一层**的 `index.html`，传错层 → 首页 403/404。这条是本项目最容易翻车的一处。

**② 复制单个文件 / 多个文件**

```bash
# 单个文件
scp booking-api-2.0.1.jar $SERVER:/opt/lesson/

# 上传时就改名（目标写完整文件名）
scp booking-api-2.0.1.jar $SERVER:/opt/lesson/booking-api.jar

# 一次传多个文件（最后一个参数才是目标目录）
scp a.jar b.jar c.sql $SERVER:/opt/lesson/

# 源用通配符（不想写死版本号时）
scp api/target/booking-api-*.jar                  $SERVER:/opt/lesson/booking-api.jar
scp api/message-service/target/message-service-*.jar $SERVER:/opt/lesson/message-service.jar
```

**③ 复制整个文件夹（递归，必须带 `-r`）**

```bash
# 前端产物：传内容到站点根（注意结尾 /）
scp -r frontend/dist/ $SERVER:/var/www/frontend/

# 配置模板：先传到临时目录，因为 /etc 下需要 root
scp -r deploy/nginx/  $SERVER:/tmp/nginx-conf/

# SQL 目录（源是 api/sql，不是 api/beforeRun/sql —— 后者不存在）
scp -r api/sql/schema/ $SERVER:/opt/lesson/sql/schema/
scp -r api/sql/seed/   $SERVER:/opt/lesson/sql/seed/
scp -r api/sql/patch/  $SERVER:/opt/lesson/sql/patch/
scp -r api/classroom-service/sql/ $SERVER:/opt/lesson/sql/classroom/
```

**④ 文件夹同步优先用 `rsync`（能续传、能删除多余文件）**

```bash
# -a 保留权限时间，-v 显示过程，--delete 删掉服务器上多出来的旧文件
rsync -av --delete frontend/dist/ $SERVER:/var/www/frontend/
rsync -av api/sql/                $SERVER:/opt/lesson/sql/        # 整个 SQL 树（schema/seed/patch）

# 服务器没装 rsync 时先装： apt install -y rsync
# 或退回 scp： scp -r frontend/dist/* $SERVER:/var/www/frontend/
```

> **`--delete` 要小心**：它会把目标目录里"本地没有的文件"删掉。所以**目标目录必须只放这个东西**（`/var/www/frontend/` 里不要混放手工文件）。

**⑤ 从服务器复制回本地（下载）**

```bash
# 下载单个文件（注意最后一个是本地路径，. 表示当前目录）
scp $SERVER:/opt/lesson/booking.log ./

# 下载整个文件夹
scp -r $SERVER:/var/log/nginx/ ./nginx-logs/

# 只增量拉取（比 scp 快，且不会重复下载）
rsync -av $SERVER:/var/log/nginx/ ./nginx-logs/
```

**⑥ 非常规端口 / 指定密钥**

```bash
scp -P 2222 -i ~/.ssh/id_rsa  file  $SERVER:/opt/lesson/     # 注意是大写 -P（rsync 里是 -e "ssh -p 2222"）
rsync -av -e "ssh -p 2222 -i ~/.ssh/id_rsa"  frontend/dist/  $SERVER:/var/www/frontend/
```

**⑦ 目标是 `/etc/**` 这类系统目录：不要直接 scp 进去**

普通用户对 `/etc/lesson`、`/etc/nginx` 没有写权限，直接传会报 `Permission denied`。**先传 `/tmp`，再在服务器上 `sudo mv`**：

```bash
# 本地
scp deploy/nginx/booking.conf $SERVER:/tmp/
scp api/beforeRun/booking.env.template $SERVER:/tmp/

# 服务器
sudo mv /tmp/booking.conf /etc/nginx/sites-available/booking
sudo mv /tmp/booking.env.template /etc/lesson/booking.env
sudo nginx -t && sudo systemctl reload nginx
```

**⑧ 传完必须验证（不要只看 scp 没报错）**

```bash
ssh $SERVER 'ls -l /opt/lesson/*.jar'
ssh $SERVER 'ls /var/www/frontend/*.html'
# 期望：/var/www/frontend 下直接就是 index.html / platform_admin.html ...（不是 dist/index.html）
```

**⑨ 本项目"哪个文件 → 哪个目录"对照**

| 本地路径 | 服务器路径 | 复制命令 |
|---|---|---|
| `api/target/booking-api-*.jar` | `/opt/lesson/booking-api.jar` | `scp api/target/booking-api-*.jar $SERVER:/opt/lesson/booking-api.jar` |
| `api/message-service/target/message-service-*.jar` | `/opt/lesson/message-service.jar` | `scp ... $SERVER:/opt/lesson/message-service.jar` |
| `frontend/dist/`（内容） | `/var/www/frontend/` | `rsync -av --delete frontend/dist/ $SERVER:/var/www/frontend/` |
| `api/beforeRun/*.sql` | `/opt/lesson/sql/` | `scp api/beforeRun/*.sql $SERVER:/opt/lesson/sql/` |

> `api/target` 下的 jar 文件名带版本号（如 `booking-api-2.0.1.jar`），**以 `ls api/target/*.jar` 看到的为准**，脚本/手册里都用通配符 `booking-api-*.jar` 避免版本号漂移。

**⑩ 仓库自带的一键上传脚本**

```bash

```

脚本内部就是上面这些命令的组合（jar + dist + 配置文件），适合"一次全传"。单独发版时仍建议按 ⑨ 逐项手动执行，便于核对。

**⑪ Windows 本机注意事项**

- **Git Bash**：命令与上面完全一致（`scp` 来自 Windows 自带 OpenSSH）。
- **PowerShell**：变量写法不同——用 `$env:SERVER`，或直接把 `root@1.2.3.4` 写在命令行里；路径分隔符用 `/`。
- 路径含空格要加引号；**中文文件名经 scp 偶发乱码**，上传前先改成英文名（本项目产物都是英文名，正常不会遇到）。
- 不想用命令行：**WinSCP / MobaXterm** 拖拽即可。首次连接确认主机指纹；拖文件夹时同样要注意"拖的是文件夹还是文件夹里的内容"。

### 3.5 配置文件逐份落地（★ 本章核心）

> 下面每个文件都给出「部署路径 + 完整内容」。可以在本地建好、改成自己的值，再按 **3.4.1 ⑦**（传 `/tmp` 再 `sudo mv`）上传。

#### 3.5.0 先生成三个密钥（本地生成即可）

**Windows PowerShell**：

```powershell
# JWT：64 字节随机串（Base64）
[Convert]::ToBase64String((1..64 | ForEach-Object { Get-Random -Maximum 256 }))
# AES / HMAC：各 32 字节（Base64，44 字符，结尾带 =）
[Convert]::ToBase64String((1..32 | ForEach-Object { Get-Random -Maximum 256 }))
```

**Linux / macOS / Git Bash**：

```bash
openssl rand -base64 64    # JWT_SECRET
openssl rand -base64 32    # AES_KEY
openssl rand -base64 32    # HMAC_KEY
```

约束：

- `JWT_SECRET`：≥64 字符；
- `AES_KEY` / `HMAC_KEY`：Base64 解码后**必须正好 32 字节**（44 字符、结尾 `=`）；
- **三个服务（booking / message / classroom）的这三个值必须逐字符相同**，否则消息与课堂请求 401、跨服务解密失败；
- 前端（dist）**不持有任何密钥**。

> ⚠️ **变量名不要写错（2026-10-30 修正）**：源码里是
> `crypto.aes-key=${AES_KEY:默认值}`、`crypto.hmac-key=${HMAC_KEY:默认值}`，
> `CryptoUtil` 用 `@Value("${crypto.aes-key}")` 直读。所以**生效的环境变量名是 `AES_KEY` / `HMAC_KEY`**
> （与 `api/beforeRun/*.env.template` 一致）。
> 本手册早期版本写的是 `CRYPTO_AESKEY` / `CRYPTO_HMACKEY` —— **那是无效的**：
> 占位符只认 `AES_KEY`，`@Value` 也不会把 `CRYPTO_AESKEY` 宽松绑定到 `crypto.aes-key`
> （Spring 只把 `crypto.aes-key` 映射成 `CRYPTO_AES_KEY`，多一个下划线都不行）。
> 无效的后果不是报错，而是**静默沿用源码里公开的默认密钥**（三个服务都用同一默认值，仍然互通，所以
> 登录/解密一切正常，极难发现），生产环境的字段加密因此形同虚设。改完务必按 3.6 的自检第 4 步验证。

#### 3.5.3 文件 `/etc/systemd/system/booking.service`

> **`$JAVA_OPTS` 必须写在 `ExecStart` 里**：`EnvironmentFile` 只是把变量放进进程环境，JVM **不会自动读取** `JAVA_OPTS`（JVM 只自动读 `JAVA_TOOL_OPTIONS` / `JDK_JAVA_OPTIONS`）。漏写会导致 `-Xms/-Xmx` 失效；若里面还塞了别的参数，甚至会启动即崩、被 systemd 判定 `Start request repeated too quickly`。

```ini
[Unit]
Description=Lesson Booking Service
After=network.target
Wants=network.target
StartLimitIntervalSec=600
StartLimitBurst=3

[Service]
Type=simple
User=lesson
Group=lesson
WorkingDirectory=/opt/lesson
EnvironmentFile=/etc/lesson/booking.env
# $JAVA_OPTS 必须写在这里；jar 用固定名（升级时直接覆盖文件即可）
ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/lesson/booking-api.jar
Restart=on-failure
RestartSec=10s

StandardOutput=append:/var/log/lesson/booking.log
StandardError=append:/var/log/lesson/booking.log

[Install]
WantedBy=multi-user.target
```

#### 3.5.5 文件 `/etc/nginx/sites-available/booking`（有域名 + HTTPS）

仓库模板：`deploy/nginx/booking.conf`（**已是三服务版**，把 `booking.example.com` 换成你的域名即可，不必手抄）。

下面是同一份配置的完整形态，照着核对/手抄都行。**三个服务靠 location 前缀分流**，
分流清单必须与 `doc-develop/dev-proxy.js` 及 `deploy/nginx/booking-ip.conf` **逐字一致**。

```nginx
server {
    listen 80;
    server_name booking.example.com;
    location /.well-known/acme-challenge/ { root /var/www/html; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl http2;
    server_name booking.example.com;

    ssl_certificate     /etc/letsencrypt/live/booking.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/booking.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    # 课堂整包直传上限 100MB（分片每片 5MB 走不到这里，但直传会 413）
    client_max_body_size 105m;

    # 前端静态资源（dist 的内容）
    root /var/www/frontend;
    index index.html;
    location / {
        try_files $uri $uri/ /index.html;      # SPA 兜底
    }
    # platform_admin.html 就在这份 dist 里，不需要任何反代

    # ==================================================================
    # /api/v1 三分流：消息 → 8090，课堂 → 8092，其余 → 8081
    # nginx 取最长前缀匹配，书写顺序无关；^~ 用来压制静态资源正则（见下方说明）
    # ==================================================================

    # ── 1) 消息服务 8090 ─────────────────────────────────────────────
    # 前缀 /api/v1/message 覆盖 messages / message-categories / message-templates
    location ^~ /api/v1/message {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
        proxy_set_header Connection '';
    }
    location ^~ /api/v1/sensitive {
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
    }
    location ^~ /api/v1/users/ {           # ★ 复数，消息服务的收件人台账
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
    }
    location ^~ /api/v1/sse {              # SSE：关缓冲 + 长超时，少一条就"连上收不到"
        proxy_pass http://127.0.0.1:8090;
        include /etc/nginx/proxy_params;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_http_version 1.1;
        proxy_set_header Connection '';    # 不发 Connection: close
        chunked_transfer_encoding on;
    }

    # ── 2) 课堂服务 8092（14 个前缀，一个都不能少）───────────────────
    location ^~ /api/v1/classrooms/  { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/attendance/  { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/recordings/  { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/schedules/   { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }  # ★复数；主服务是单数 schedule
    location ^~ /api/v1/rtc/         { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/uploads/ {          # 分片上传：低带宽下单片可能超 60s
        proxy_pass http://127.0.0.1:8092;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 300s;
        client_max_body_size 105m;
    }
    location ^~ /api/v1/files/ {            # 签名 URL 直取，依赖 Range（拖动/倍速要 206）
        proxy_pass http://127.0.0.1:8092;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 300s;
    }
    # 运营台：逐个精确前缀，**不能**用 /api/v1/admin/ 一刀切（主服务也有 admin 语义接口）
    location ^~ /api/v1/admin/classrooms/ { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/monitor/    { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/reports/    { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/reconcile/  { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/audit/      { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/contract/   { proxy_pass http://127.0.0.1:8092; include /etc/nginx/proxy_params; }
    location ^~ /api/v1/admin/exports/ {    # 流式 CSV，大跨度较慢
        proxy_pass http://127.0.0.1:8092;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 300s;
        proxy_buffering off;
    }

    # ── 3) 课堂 WebSocket（白板/心跳/信令）───────────────────────────
    # 少 Upgrade 头 → 101 变 400；超时给不够 → 进去一会儿就掉线重连
    location ^~ /ws/classrooms/ {
        proxy_pass http://127.0.0.1:8092;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;
        proxy_set_header X-Real-IP  $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }

    # ── 4) 课堂回调落点：必须钉在 8081（课堂 → 预约系统的回执）─────────
    location ^~ /api/v1/classroom-callback/ {
        proxy_pass http://127.0.0.1:8081;
        include /etc/nginx/proxy_params;
    }

    # ── 5) 其余全部 → 主服务 8081 ────────────────────────────────────
    # 含 /api/v1/eclassroom（课堂开关，属主服务）、/api/v1/msg-ledger（消息台账，属主服务）
    location ^~ /api/v1/ {
        proxy_pass http://127.0.0.1:8081;
        include /etc/nginx/proxy_params;
        proxy_read_timeout 120s;
    }

    # ── 6) 静态资源长缓存（可选）─────────────────────────────────────
    # ★ 一旦加了这个正则，所有 API location 必须带 ^~，否则 *.mp4 / *.png 结尾的
    #   API 路径（如 /api/v1/files/<token>.mp4）会被当静态文件处理并 404。
    location ~* \.(js|css|png|jpg|jpeg|gif|svg|ico|mp4|webm|woff2?|ttf|eot)$ {
        expires 7d;
        access_log off;
    }
}
```

> `include /etc/nginx/proxy_params;` 已含 `Host` / `X-Real-IP` / `X-Forwarded-For` / `X-Forwarded-Proto`。
> 发行版若无此文件，改成显式四行：
> ```nginx
> proxy_set_header Host $host;
> proxy_set_header X-Real-IP $remote_addr;
> proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
> proxy_set_header X-Forwarded-Proto $scheme;

> ```

#### 3.5.7 文件 `/opt/lesson/backup.sh`（每日备份）

仓库模板：`deploy/backup.sh`。先建免密凭据，再配定时任务：

```bash
sudo mysql_config_editor set --login-path=backup --host=localhost --user=root --password
# 输入 root 密码（加密存储，脚本里不写明文）

sudo chmod +x /opt/lesson/backup.sh
sudo crontab -e
# 追加一行：
0 3 * * * /opt/lesson/backup.sh >> /var/log/lesson/backup.log 2>&1
```

脚本内容（备份**三个库** + 课堂文件，保留 14 天）：

```bash
#!/bin/bash
set -e
DATE=$(date +%Y%m%d_%H%M%S)
KEEP_DAYS=14
BAK_DIR=/opt/backup
OSS_DIR=/opt/lesson/data/oss
mkdir -p "$BAK_DIR"

mysqldump --login-path=backup --single-transaction --routines --set-gtid-purged=OFF \
  lesson_appointment | gzip > "$BAK_DIR/lesson_appointment_${DATE}.sql.gz"
mysqldump --login-path=backup --single-transaction --routines --set-gtid-purged=OFF \
  message_center | gzip > "$BAK_DIR/message_center_${DATE}.sql.gz"
mysqldump --login-path=backup --single-transaction --routines --set-gtid-purged=OFF \
  classroom | gzip > "$BAK_DIR/classroom_${DATE}.sql.gz"

# 课堂文件（讲稿/作品/录制）：随库一起打包。文件总量大时把这一行换成 rsync 异机备份，
# 否则每天一份全量 tar，14 天就是 14 倍占用
tar -czf "$BAK_DIR/classroom_oss_${DATE}.tar.gz" -C "$(dirname "$OSS_DIR")" "$(basename "$OSS_DIR")"

find "$BAK_DIR" -name "*.sql.gz" -mtime +${KEEP_DAYS} -delete
find "$BAK_DIR" -name "classroom_oss_*.tar.gz" -mtime +${KEEP_DAYS} -delete
echo "[$(date '+%F %T')] backup done"
```

> **课堂文件要不要备**：DB 里只存对象 key，真实字节在 `STORAGE_LOCAL_ROOT`。
> 只备库不备文件，恢复后课堂里的讲稿/作品全是"记录在、文件没了"。
> 文件量大时改成 `rsync -a --delete` 推到对象存储/另一台机器更合适，`tar` 只是最小可用版。

### 3.6 启动与验证

```bash
# ① 状态：三个服务都应 active (running)
systemctl status booking message-service classroom-service --no-pager
ss -lntp | grep -E '8081|8090|8092|6379'      # 应只监听 127.0.0.1

curl -s -o /dev/null -w "8081 %{http_code}\n" http://127.0.0.1:8081/
curl -s -o /dev/null -w "8090 %{http_code}\n" http://127.0.0.1:8090/
curl -s -o /dev/null -w "8092 %{http_code}\n" http://127.0.0.1:8092/
curl -s http://127.0.0.1:8081/platform_admin.html   # 期望 {"code":404,...}：后端无静态资源，正常

# ③ 课堂的两个隐性依赖（最容易"起了但功能不全"）
redis-cli -n 2 ping                                   # PONG
curl -s http://127.0.0.1:8092/api/v1/rtc/providers | head -c 300; echo   # configured/active/degraded
ls -ld /opt/lesson/data/oss && sudo -u lesson touch /opt/lesson/data/oss/.probe && sudo rm -f /opt/lesson/data/oss/.probe

# ④ 经 Nginx：页面
SITE=http://你的域名或IP
for p in index.html admin.html platform_admin.html student.html teacher.html booking.html; do
  printf '%-24s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' $SITE/$p)"
done
# 全部 200 说明前端 dist 就位

# ⑤ 经 Nginx：三分流是否各落对家
curl -s $SITE/api/v1/system/info          | head -c 120; echo   # booking（兜底）
curl -s $SITE/api/v1/message/system/info  | head -c 120; echo   # message-service（兼容别名路径）
curl -s $SITE/api/v1/rtc/providers        | head -c 120; echo   # classroom-service
curl -s -o /dev/null -w "callback %{http_code}\n" -X POST $SITE/api/v1/classroom-callback/ping   # 401/403 正常，404 说明被 8092 抢
curl -s -o /dev/null -w "eclassroom %{http_code}\n" $SITE/api/v1/eclassroom/config                # 401/403 正常，404 说明前缀写错
```

> **密钥是否真的生效（3.5.0 那个坑的验收）**：三个服务的日志里不应出现
> `crypto.aes-key 使用内置默认值` 之类的告警；另一种硬核验证是把它当成"三个服务用自己的
> `AES_KEY` 加解密同一库字段仍能互通"来测 —— 只要三份 env 的 `AES_KEY` 一致，跨服务读写就正常。
> 若怀疑仍在使用默认密钥，用 `systemctl show classroom-service -p Environment` 看不到值（EnvironmentFile 不在此列），
> 直接用 `sudo tr '\0' '\n' < /proc/$(pgrep -f classroom-service.jar | head -1)/environ | grep -E 'AES_KEY|HMAC_KEY|JWT_SECRET'`
> 确认进程环境里到底有没有这三个变量。


### 3.7 防火墙 / 安全组

腾讯云控制台 → 防火墙，**只放行**：

| 端口 | 来源 | 用途 |
|------|------|------|
| 22 | 你的常用 IP（建议） | SSH |
| 80 | 0.0.0.0/0 | HTTP（跳转 HTTPS） |
| 443 | 0.0.0.0/0 | HTTPS |

**不开放**：8081、8090（Nginx 内部转发）、3306（MySQL 只本机）。

```bash
sudo ufw allow 22,80,443/tcp && sudo ufw enable
```

> **⚠️ 上线后务必自查**：若 `http://服务器IP:8081` 从外网能直接打开，说明后端端口对外暴露了。
> 除在安全组删掉 8081/8090 规则外，还应让 jar **只监听本机回环**（纵深防御）：
>
> ```bash
> echo 'SERVER_ADDRESS=127.0.0.1' | sudo tee -a /etc/lesson/booking.env
> echo 'SERVER_ADDRESS=127.0.0.1' | sudo tee -a /etc/lesson/message.env
> echo 'SERVER_ADDRESS=127.0.0.1' | sudo tee -a /etc/lesson/classroom.env
> sudo systemctl restart booking message-service classroom-service
> ss -lntp | grep -E '8081|8090|8092'   # 应显示 127.0.0.1:8081 / :8090 / :8092
> ```
>
> （`SERVER_ADDRESS` 经 Spring Boot 宽松绑定映射为 `server.address`。）
>
> **Redis 不要跟着改成公网可访问**：课堂只需要本机连 6379，`bind 127.0.0.1` 即可（见 3.1）。
> 云托管的「云数据库 Redis」则相反 —— 要走内网地址并在 `classroom.env` 里改 `REDIS_HOST`。

> 但课堂对预约系统的回调会短暂失败（重试队列会补）。

### 5.1.1 服务起不来时，如何看到真正的错误

systemd 只会给 `Failed with result 'exit-code'`，**真实原因在 Java 输出里**。按下面的顺序查：

```bash
# ① 看退出码（先看这个，能直接分大类）
systemctl show booking -p ExecMainStatus -p ExecMainCode

# ② 抓 Java 报错关键字
journalctl -u booking -n 200 --no-pager | grep -iE "status=|Unable to access|Failed to load environment|Caused by|Exception|Port .* was already in use" | head -30

# ③ 前台直接跑（最准，报错会打在当前终端，Ctrl+C 退出）
cd /opt/lesson
sudo -u lesson bash -c 'set -a; . /etc/lesson/booking.env; set +a; /usr/bin/java $JAVA_OPTS -jar /opt/lesson/booking-api.jar'
```

**退出码 / 报错 → 原因对照**：

| 看到 | 含义 | 修复 |
|---|---|---|
| `status=203/EXEC` | `java` 路径不对，或 jar 不存在/无权限 | `which java` 核对路径；`ls -l /opt/lesson/*.jar`；`chmod 644` |
| `status=217/USER` | `User=lesson` 不存在 | `sudo useradd -r -s /bin/false lesson` |
| `Failed to load environment files` | `/etc/lesson/booking.env` 不存在 | 按 3.5.1 建 env |
| `Unable to access jarfile` | `ExecStart` 里的 jar 名与实际不符 | 按 `ls /opt/lesson/*.jar` 的真实名改，或建软链 |
| `Communications link failure` / `Access denied for user` | 数据库连不上 | 查库是否存在、`lesson` 账号授权、env 里密码 |
| `Port 8081 was already in use` | 端口被占（旧进程） | `sudo fuser -k 8081/tcp` 后重启 |
| `Illegal base64` / 密钥长度相关异常 | `AES_KEY`/`HMAC_KEY` 不是 32 字节，或 `JWT_SECRET` 太短 | 按 3.5.0 重新生成 |
| `Unable to connect to Redis` / 课堂日志反复重连 | Redis 没起、密码没配、或 `REDIS_HOST` 写错 | `redis-cli -n 2 ping`；设了 requirepass 就要配 `SPRING_DATA_REDIS_PASSWORD` |
| 课堂上传/录制报 `Permission denied` | `/opt/lesson/data/oss` 属主不是 lesson | `sudo chown -R lesson:lesson /opt/lesson/data/oss` |
| 课堂页 403「课堂未启用」 | `sys_eclassroom_instance` 无该租户行，或 `TenantEclassroomService` 的 5 分钟缓存未过期 | 先查表有没有行（3.3 校验），再等缓存过期或重启课堂 |
| 课堂 WebSocket 400/101 失败 | Nginx 少 `Upgrade` 头或超时太短 | 按 3.5.5 的 `/ws/classrooms/` 段核对 |
| `Start request repeated too quickly` | 连续失败触发了启动限流（不是新毛病） | 修完根因后先 `sudo systemctl reset-failed booking` 再 start |

> 触发限流后 systemd 会拒绝再次启动，**必须**先 `systemctl reset-failed booking`，否则会一直看到同样的提示。

#### 5.5.1 业务接口 HTTP 状态语义（2026-10-10 起生效，建告警前必读）

自 29-b 方案 A 上线后，业务接口的 HTTP 状态**不再是恒 200**：

| 业务结果 | HTTP | body.code | 说明 |
|---|---|---|---|
| 成功 | 200 | 200 | 不变 |
| 业务失败（参数/状态错误） | **400** | 400 | 新：以前伪装成 200 |
| 资源不存在 | **404** | 404 | 新：以前伪装成 200 |
| 冲突（并发/重复） | **409** | 409 | 新：以前伪装成 200。2026-10-11 起新增来源：**时间态闸**（课次已开始不可请假/改期、有已开始课次的预订不可取消、已开始排期不可再预订——属正常业务拒绝，不是故障） |
| 服务器内部错误 | **500** | 500 | 新：以前伪装成 200 |
| 业务 401/403（非鉴权失效） | **200** | 401/403 | 保持 200：映射会触发前端刷新/踢登录 |
| 真鉴权失效（token 无效/过期） | 401 | 401 | Security 过滤器层直出，未变 |

对巡检/告警的影响：

- `deploy/healthcheck.sh` 走 `/actuator/health/readiness`，**不受影响**，维持期望 200。
- 静态页与 `/api/v1/system/info` 探针不受影响。
- **基于 Nginx 访问日志状态码新建告警时**：4xx 现在包含正常业务失败（用户输错参数、
  删除不存在的记录等），不能一见 4xx 就告警；建议只对 5xx 比例或 401 激增设阈值。
- 前端/小程序拦截器已按上表消费（body 真实文案优先），无需改动。

## 第 6 章 故障速查表

### 6.0 首页显示 "Welcome to nginx!"（第一坑，先查这里）

> **这句话的含义**：Nginx 在跑、也在响应，但**请求落到了 Nginx 自带的默认 server**（Ubuntu 默认页 `/var/www/html/index.nginx-debian.html`）。
> 即：**我们的站点配置没被用上**，与后端 jar、前端 dist 都无关。

**第一步：一条命令看清 Nginx 实际加载了什么**

```bash
sudo nginx -T | grep -nE "server_name|^ *root |listen |include .*conf"   # 全部生效配置
ls -l /etc/nginx/sites-enabled/                                          # 启用了哪些站点
grep -rn "index.nginx-debian\|/var/www/html" /etc/nginx/sites-enabled/   # 谁在提供这个默认页
```

**第二步：对照定位**

| 现象（`ls -l /etc/nginx/sites-enabled/`） | 根因 | 修复 |
|---|---|---|
| 只有 `default`，没有 `booking` / `booking-ip` | 站点**没启用**（只写了 sites-available，忘了软链） | `sudo ln -s /etc/nginx/sites-available/booking-ip /etc/nginx/sites-enabled/` |
| `default` 与 `booking` **同时存在** | `default` 带 `default_server`，抢先接管 | `sudo rm -f /etc/nginx/sites-enabled/default` |
| 启用的是 `booking`（域名 + 443），却用 **IP + 80** 访问 | server_name 不匹配 + 只监听 443 → 落到默认 server | 改用 `booking-ip.conf`（80 + `server_name _`），或改用域名访问 |
| 系统**没有 sites-enabled 目录**（CentOS/Rocky/Alma） | 这些发行版只 include `/etc/nginx/conf.d/*.conf` | 把配置放到 `/etc/nginx/conf.d/booking.conf` |
| 配置看着对但没生效 | 改完没 reload | `sudo nginx -t && sudo systemctl reload nginx` |
| `nginx -t` 报错 | 语法错误（漏分号、括号不匹配最常见） | 按报错行号修，再 `nginx -t` |
| `nginx -t` 报 `open() "/etc/nginx/sites-enabled/xxx" failed (2: No such file or directory)` | **悬空软链**：只建了软链，`sites-available/` 里没有源文件（漏上传） | 在 `sites-available/` 建真实文件（内容见 3.5.5 / 3.5.6），或先 `rm /etc/nginx/sites-enabled/xxx` 再重建 |
| 软链已建、`default` 已删，外网**仍是**欢迎页 | 没 reload（改配置后 Nginx 仍用旧配置跑着）；或软链指向的文件内容不对 | `sudo nginx -t && sudo systemctl reload nginx`（reload 即可，不必 restart）；再 `grep -nE "root|server_name" /etc/nginx/sites-available/booking-ip` 核对内容 |
| 没有 `sites-enabled`，但 `/etc/nginx/conf.d/` 里有别的 `.conf` | 默认站点藏在 `conf.d`（Ubuntu 主配置两个 include 都生效） | `grep -rn "index.nginx-debian" /etc/nginx/conf.d/`，找到就 `rm` 或改 `server_name` |

**第三步：一键修复（无域名 / 按 IP 访问的场景）**

```bash
sudo rm -f /etc/nginx/sites-enabled/default
sudo ln -sf /etc/nginx/sites-available/booking-ip /etc/nginx/sites-enabled/booking-ip
sudo nginx -t && sudo systemctl reload nginx
```

**第四步：验证（用来区分"Nginx 没生效"还是"dist 没上传"）**

```bash
ls -l /var/www/frontend/index.html                          # 必须存在，否则是 dist 没上传
ss -lntp | grep ':80'                                       # Nginx 是否在听 80
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/  # 服务器内自测
curl -s http://127.0.0.1/ | head -3                         # 应看到我们自己的 HTML
curl -s http://127.0.0.1/api/v1/system/info | head -c 120; echo
```

- 自测 200 且是我们自己的页面 → 已生效（外网还看旧页就清缓存 / 换无痕窗口）
- 自测也是 Welcome → 回到第二步
- 自测 403/404 → `root` 路径错（常见：多了一层 `dist`，正确是 `/var/www/frontend`）
- 页面 OK 但接口 502/404 → 后端没起或分流没配（见 6.1）

### 6.1 其他故障

| 症状 | 排查命令 | 常见原因与解法 |
|------|---------|---------------|
| 首页显示 "Welcome to nginx!" | `ls -l /etc/nginx/sites-enabled/`；`nginx -T \| grep server_name` | 站点没启用 / `default` 没删 / 用 IP 访问了只监听 443 的域名站点 → 见 **6.0** |
| 网页打不开 | `systemctl status booking`；`nginx -t` | 服务挂了 → restart；Nginx 配置错 → 看 `nginx -t` 输出 |
| 页面 200 但接口 502 | `ss -lntp \| grep -E '8081\|8090\|8092'` | 后端没监听；检查对应 jar 是否启动成功 |
| **页面能开、所有 `/api/v1` 都 502** | `systemctl is-active booking message-service classroom-service`；`ls -l /opt/lesson/*.jar /etc/lesson/*.env` | 后端整体没起：jar 未上传 / `ExecStart` 路径与实际文件名不符 / env 缺失 / DB 连不上 / 没装 JDK → 按 3.6 启动，看 `journalctl -u booking -n 50` |
| **只有课堂接口 502/404，其他都正常** | `systemctl is-active classroom-service`；`curl -s http://127.0.0.1:8092/api/v1/system/info`；`nginx -T \| grep -c "8092"` | ①课堂没起 ②Nginx 漏了 8092 的 location（改动前只配了两个服务，最常见）③`/ws/classrooms/` 漏配 → 见 3.5.5 |
| **课堂页进不去 / 白板不刷新 / 反复重连** | 浏览器 Network 看 `ws/classrooms/...` 是否 **101**；`nginx -T \| grep -A3 ws/classrooms` | 缺 `Upgrade`/`Connection "upgrade"` 头，或 `proxy_read_timeout` 太短（默认 60s 掐断）；见 3.5.5 第 3 段 |
| **课堂讲稿/作品上传 413** | `grep client_max_body_size /etc/nginx/sites-available/booking` | Nginx 20m 太小（课堂单文件上限 100MB）→ 调到 105m；分片上传每片 5MB 一般撞不到 |
| **课堂里"文件不存在"但记录在** | `ls /opt/lesson/data/oss`；`grep STORAGE_LOCAL_ROOT /etc/lesson/classroom.env` | 存储根被改/被清，或恢复备份时只回了库没回文件 → 见 5.3 |
| **消息接口 401** | 对比三 env 的 `JWT_SECRET`；`curl -s $SITE/api/v1/message/system/info` | 密钥不一致；或分流没到 8090（返回的是 booking 的 401 文案） |
| **生产环境字段加密疑似没生效**（一切正常但密钥是默认值） | `sudo tr '\0' '\n' < /proc/$(pgrep -f classroom-service.jar\|head -1)/environ \| grep AES_KEY` | env 里写成了 `CRYPTO_AESKEY`（无效）→ 改成 `AES_KEY`/`HMAC_KEY`，见 3.5.0 |
| 软链 `/opt/lesson/*.jar` 指向 `/root/...`，服务起不来 | `/root` 默认 700，运行用户 `lesson` **进不去**，读不到 jar | 把真身复制到 `/opt/lesson/`（chown lesson、chmod 644）再软链；**不要** `chmod 777 /root`、也不要改成 `User=root`。诊断：`namei -l /opt/lesson/booking-api.jar`、`sudo -u lesson test -r /opt/lesson/booking-api.jar` |
| `Start request repeated too quickly` | `journalctl -u booking -n 50` | **ExecStart 漏写 `$JAVA_OPTS`** / 端口冲突 / DB 连不上 |
| 微信登录静默 1001 / PC 扫码失败 | `grep -i wechat /etc/lesson/booking.env`；查日志 `warnIfSecretPlaceholder` | 小程序/开放平台 secret 仍是 `REPLACE_WITH` 占位 → `code2Session` 拿不到 openid；填真实 `WECHAT_SECRET` / `WECHAT_OPEN_SECRET` 后 `systemctl restart booking` |
| 排期时间差 8 小时 | 检查 `SPRING_DATASOURCE_URL` 的 `serverTimezone` | 应为 `Asia/Shanghai` |
| 平台管理端跳到缺省页 | 检查 `/var/www/frontend/platform_admin.html` 是否存在 | dist 是旧包（管理端曾在 jar 内）→ 重新构建上传 |
| 改了前端没生效 | `curl -I` 看 `Last-Modified` | 浏览器缓存 / 静态资源缓存策略 → Ctrl+F5；或 rsync 时漏了 `--delete` |
| 上传图片失败 | Nginx `error.log` | `client_max_body_size` 太小（已配 105m） |
| 磁盘满 | `df -h` + `du -sh /opt/lesson/data/oss /var/log/lesson/*` | 日志暴涨：加 logrotate 或清旧日志；课堂录制占空间：按 `classroom.recording-retention-days`(90 天) 清理任务是否在跑 |
| 数据库连不上 | `systemctl status mysql`；查 env 里密码 | MySQL 没起 / 密码错 / 账号没授权 |
| 升级后某些操作突然 403（以前能用） | 授权收紧（2026-10-10 起 SecurityConfig 兜底为 `denyAll`，未在 `AuthzRules` 登记的端点一律 403） | 新端点漏登记 → 按 `doc-develop/角色权限配置指南.md` 三层架构补 `AuthzRules` 规则 + 方法级 `PermissionCheck`；不是 Nginx/前端问题 |
| 学生"取消预订/请假"报 409「课程已开始」 | 时间态闸（2026-10-11 新增，设计行为） | 已开始的课次不可请假/改期，已开始的预订不可取消，已开始排期不可再预订；属业务拒绝非故障 |
| 用户频繁被要求重新登录 | `jwt.expiration` 已收紧为 1 小时（2026-10-11，此前 100 小时）；refresh token 7 天 | 前端 401 会自动刷新 token，正常无感；若真频繁弹登录页，先查三份 env 的 `JWT_SECRET` 是否同源（见 2.4），再看该配置是否被 env 覆盖 |
| 服务器整体卡死 | 控制台 VNC 登录 | 内存耗尽：`free -h`，调小 `-Xmx` 或升配 |

**万能三板斧**（按顺序，解决 80% 问题）：

```bash
sudo systemctl restart mysql redis-server
sudo systemctl restart booking message-service classroom-service
sudo nginx -t && sudo systemctl reload nginx
```

## 附：多客户部署提示

验证期采用"每客户一实例"时（**每个客户现在是三个进程，不是两个**）：

- 每个客户一个数据库组：`lesson_appointment_a` + `message_center_a` + `classroom_a`，
  端口按 **三个一组** 错开：`8081/8090/8092`、`8082/8091/8093`、`8083/8092/8094`…
  （📌 第二组起要避开 8092 这个"课堂默认端口"，否则第二家的课堂与第一家的课堂撞车）
- 每客户一组 env：`/etc/lesson/{booking,message,classroom}-a.env`，`SERVER_PORT` 必须逐个显式写死
- Nginx 用子域名区分：`firm-a.example.com → 8081/8090/8092`，`firm-b.example.com → 8082/8091/8093`
  每个站点复制一份带 `/ws/classrooms/` 与 14 个课堂前缀的 location 块
- systemd 服务名错开：`booking-a.service`、`message-a.service`、`classroom-a.service`
- **Redis 按客户分 db**（如 A 用 db2、B 用 db3），或每客户一个 Redis 实例 —— 混用会串在线状态
- 课堂存储目录按客户分：`/opt/lesson/data/oss-a`、`-b`（`STORAGE_LOCAL_ROOT`）
- 备份脚本循环导出所有库，课堂文件目录同样循环
- 前端 dist 可以共用一份（同版本），也可按客户子域各放一份目录
- 客户数超过 15 家后走多租户改造，把新客户收进共享池
