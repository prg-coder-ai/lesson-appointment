## 1. 范围与红线

### 1.1 六条红线（违反任一即返工）

| # | 红线 | 由来 |
|---|------|------|
| **R1** | **所有面向用户的名词走 `data-term` / `curTerm()`**，不硬编码 | 多行业术语三级作用域是当前主线，律师咨询子行业下"课程=咨询" |
| **R2** | **页面跳转一律 `pageUrl()`、请求一律相对路径 + `location.origin`** | `pageUrl` 自动保留 `tCode`，否则登录回跳断链 |
| **R3** | **新建 HTML 须加载公共 JS 清单 + `pagefoot` + `<title>` 用 `data-term-title`** | 否则行业词不生效、页脚丢失、标题退化 |
| **R4** | **前端的任何身份/归属过滤都不可信，后端必须有同名校验** | 见 §4.3：前端传 `teacherId` 只是过滤，不是权限 |
| **R5** | **改完源码必须重建 dist 并同步**，否则"本地好了线上没变" | 线上跑的是 `frontend/dist`，不是源码 |

### 3.5 学生个人中心：改密 + 微信绑定（已拍板纳入）

后端三条端点**均已存在且已做安全处理，本项零后端改动**：

| 能力 | 端点 | 实证与注意事项 |
|------|------|--------------|
| 查绑定状态 | `GET /auth/wechat-status`（`authController:460`） | 页面初始化即调，据此显示「已绑定 / 去绑定」 |
| 绑定微信 | `POST /auth/bind-wechat`（`:407`） | 语义是「**密码登录成功后**把当前账号与 openid 绑定」——**要求已登录**（token 缺失/非 `Bearer ` 前缀直接返回未授权，见 `:411`）。入参 `WeChatCodeDTO{code}`，userId **由服务端从 token 取**，前端不得传 |
| 解绑微信 | `POST /auth/unbind-wechat`（`:479`） | 🚩 **`auto_register`（微信直接注册）的账号会被拒绝**——这类账号没有密码，解绑后无法登录。前端必须**把拒绝原因原样提示**，不能笼统显示"解绑失败"（源码注释见 `:476-477`） |
| 修改密码 | `POST /user/account/changePassword`（`UserController:336`） | ✅ **已做归属加固**（源码注释写着 P0-2：原先只凭 userId 就能改他人密码）。两种合法路径：本人改密**必须验原密码** / 管理员同租户代管；其余一律 403。已带 `@Audit` |

**施工要点**

1. **前端不得自行判断"能不能解绑"** —— `auto_register` 的拒绝在服务端，前端只对 400/403 结果做友好文案映射。
2. **绑定态与非绑定态 UI 要分离**：未绑定显示"绑定微信"，已绑定显示账号信息 + "解绑"。
3. **改密必须走双字段**：`oldPassword` + `password`。不要图省事只传新密码——那是被修掉的漏洞形态。
4. 全部请求带 `Authorization: Bearer ` 前缀（本项目 `JwtAuthenticationFilter` 强制前缀，不带不报错、直接无身份）。

### 4.2 T1 的正确改法（**不能照原文档做**）

原分析文档建议"移除 `teacherInfo.html:396` 的 `role !== 'admin'` 拒绝"。**不可照做**——该判断已演进为**有意的多租户隔离**：租户 admin 放行、`platform_admin` 显式拒绝并给专属指引。

正确做法是**新增分支**而非移除：

```
role === 'admin'          → 维持原口径（可管理本租户任意教师）
role === 'platform_admin' → 维持显式拒绝 + 专属指引（不变）
role === 'teacher'        → 新增：仅可访问/编辑【本人】资料
```

**前置条件（不可跳过）** —— professional 的三个写端点目前只有 `checkTeacherOrAdmin`（**验角色不验归属**），一旦把入口开给教师，教师 A 就能改教师 B 的资料：

| 编号 | 必须完成的后端补丁 | 优先级 |
|------|------------------|--------|
| SEC-1 | `deleteTeacherProfessionalInfo` 补归属校验（**按主键删且无归属判断，风险最高**） | 最高 |
| SEC-2 | `add/updateTeacherProfessionalInfo` 改为 `checkTeacherSelfOrAdmin` 口径 | 高 |

### 8.2 决策记录（三项待拍板已定案）

#### ✅ P1：`platform_admin` 放行归属校验 —— **照决议执行**

统一写法（与 `checkTeacherSelfOrAdmin` 保持一致）：

```java
if (RoleConst.PLATFORM_ADMIN.equals(role) || "admin".equals(role)) {
    return;   // 管理员/平台管理员放行，可代操作
}
```

**分层原则**：归属校验只回答"是不是你的"，"能不能看到这条数据"交给 `TenantLineInnerInterceptor`。
注意：`teacherInfo.html:396` 对 platform_admin 的显式拒绝属于**前端产品决策**（不给入口），**保持不变**，两处不冲突。

#### ⚠️ P2：`/schedule/generate` —— **决议无法按原方式落地，须修正**

拍板前提是「纳入归属管控」，但源码实证显示**这条前提不成立**：

| 实证 | 结论 |
|------|------|
| `ScheduleGenerateDTO` 字段只有 `startDate/endDate/startTime/repeatType/interval/repeatDays/timeZone/userTimeZone` | **无 `courseId` 也无 `scheduleId`** —— 无从判定归属 |
| `ScheduleGenerator.java` **零 mapper 调用** | **纯时间展开计算，不读不写库**，不存在越权面 |
| 调用方 `courseAndBooking.js:826` 注释：「全站唯一实现：**学生端卡片**（student-bookingCards.js）、管理端排期（admin-schedule.js）都调用这一个入口」 | **学生端约课链路依赖它**，做归属校验会误伤学生浏览 |
| `checkTeacherOrAdmin` 被注释，而 AuthzRules:323 声明 ALL_ROLES | 二者一致（任意已登录角色可用），**不是被遗弃的漏洞** |

**修正后的做法**（替代方案）：

| 编号 | 动作 |
|------|------|
| GEN-1 | **不做归属校验**，保持 ALL_ROLES |
| GEN-2 | 补**防滥用限幅**：限制起止日期跨度（如 ≤ 366 天）、`repeatDays` 长度上限、单次返回条数上限 | 
| GEN-3 | 把源码注释里那段「权限校验：checkTeacherOrAdmin」的过时描述删掉，避免误导后来者照它补一个会误伤学生的校验 |

> 真实风险不在越权，而在**资源放大**：超长跨度 + 多重复日会撑大单次计算量。

#### ✅ P3：学生个人中心包含改密 / 微信绑定 —— **照决议执行**

后端零改动，直接接三个端点，详见 **§3.5**。关键约束：改密必须双字段（本人改密验原密码）、解绑失败要透传 `auto_register` 拒绝原因。
