# N7 敏感字段的服务级加解密：AES-GCM + HMAC 盲索引，以及「没有 TypeHandler」的代价

## 1. 问题背景：手机号入库，是明文还是密文？

预约系统存手机号、邮箱、姓名。放明文，一次拖库就是全村通报会；放密文，三个问题立刻找上来：

1. **登录怎么办**——用户输明文手机号，库里是密文，`WHERE phone = ?` 永远查不中；
2. **后台搜索怎么办**——管理员按姓名搜「张伟」，密文字段上 `LIKE` 是乱码对乱码；
3. **历史数据怎么办**——上线加密功能前已有一批明文本地数据，加解密逻辑要能兼容。

本项目的答卷是「**服务级字段加密 + 复合格式盲索引**」，三个决策值得先记住：

- **加密范围只限 phone / email / name 三列**，`account` 保持明文——账号是登录标识，每次登录都要精确匹配，且它本身不是敏感 PII（手机号才是）；
- **没有 MyBatis TypeHandler**，加解密全部发生在 Service 层的手工调用——这是一个有意识的权衡（§2.3 展开它的代价）；
- **密文格式自带搜索索引**：`<HMAC-SHA256(明文) 十六进制>:<Base64(IV‖密文‖Tag)>`，一列同时承担「可精确检索」与「不可逆」两个职责。

## 2. 原理：三个设计决策

### 2.1 为什么是 AES-GCM 而不是 AES-CBC

`CryptoUtil` 用的变换是 `AES/GCM/NoPadding`，参数是 GCM 的推荐值：

```java
// CryptoUtil.java:27-31
private static final String AES_GCM = "AES/GCM/NoPadding";
private static final int IV_LENGTH = 12;   // GCM 推荐 12 字节 nonce
private static final int TAG_LENGTH = 16;  // GCM 认证标签 128 位
```

| 维度 | AES-CBC | AES-GCM（本项目选择） |
| --- | --- | --- |
| 完整性 | 无——密文被篡改只能解密出乱码，发现不了 | **AEAD**：16 字节认证标签，解密时校验，篡改即抛异常 |
| IV 要求 | 16 字节随机 | 12 字节随机 nonce |
| 性能 | 纯加密 | 加密 + 认证一把出 |
| 每次加密结果 | 相同明文 + 相同 IV → 相同密文 | **每次 IV 随机 → 相同明文每次密文都不同** |

最后一条对字段加密是刚需：如果「张伟」的密文恒定，攻击者拖库后做个频率分析就能猜出高频姓名。`encrypt()` 每次 `SecureRandom` 生成新 IV 拼在密文前（`combined = IV ‖ ciphertext+tag`），库里同一手机号改两次名，密文完全不同。

代价是密文变长：`12 + 明文长度 + 16` 字节再 Base64。手机号 11 位明文 → 39 字节 → Base64 后 52 字符，加 64 字符 HMAC 前缀和冒号共 117 字符——所以 `user.phone` 列要按 `VARCHAR(255)` 设计（schema dump 里确实是宽列）。

### 2.2 HMAC 盲索引：让密文可精确检索

加密字段的最大难题是「服务端不知道明文，但用户按明文搜」。GCM 是概率加密，`WHERE phone = 密文` 连等值都查不了。业界的标准解是**盲索引（blind index）**：用另一个密钥对明文算一个确定性的 HMAC，索引值当「指纹」用。

```java
// 复合格式：hmac:ciphertext
public String encryptWithIndex(String plaintext) {
    return searchIndex(plaintext) + SEPARATOR + encrypt(plaintext);
}
```

于是查询变成前缀匹配：

```java
// UserMapper.java:68
@Select("select * from user where phone LIKE CONCAT(#{hmac}, ':%') OR phone = #{plain}")
List<User> selectByPhone(@Param("hmac") String hmac, @Param("plain") String plain);
```

两个设计细节：

- **`LIKE 'hmac:%'` 而不是 `=`**：前缀匹配能走 B+ 树索引范围扫描（`phone` 列上有普通索引即可），且为「一列多版本密文」留了余地——同一手机号加密两次密文不同但 HMAC 相同，`LIKE` 两条都命中；
- **`OR phone = #{plain}` 是历史明文兼容**：加密功能上线前的存量数据是裸明文，没有 HMAC 前缀。这个 `OR` 分支让老数据在新代码下照样能登录、能搜。**新系统照抄这段 SQL 时千万别漏了这个分支**——漏了就是「上线加密第二天，一半老用户登录不了」。

HMAC 密钥与 AES 密钥**分开配置**（`crypto.aes-key` / `crypto.hmac-key`）：HMAC 的职责只是「产生可检索指纹」，它不泄露明文（单向），但泄露了「哪些行是同一个值」的关系。分密钥意味着将来轮换索引不用动数据加密。

### 2.3 没有 TypeHandler：解密的代价是「每条读路径都要记得」

MyBatis-Plus 的 `TypeHandler` 方案是在读写数据库的边界自动加解密，业务代码无感。本项目选了 Service 层手工调用，原因是字段加密与三个需求耦合太深，自动化解不开：

- **多租户裸查要显式豁免**（N1 的 `@InterceptorIgnore`），解密也得跟着豁免一起决策；
- **内存模糊匹配**需要「先解密再 contains」（§3.4），这是查询策略问题不是序列化问题；
- **局部更新**要「先取原记录解密、合并、再加密入库」（§3.3），TypeHandler 的自动写入会把 null 字段也加密一遍。

但代价必须写进基因里：**解密是 opt-in，忘了调，前端就是 `hex:base64` 乱码**。这不是理论风险——`PromoService.loadUsersForStats` 的方法注释（960-967 行）就是一次真实事故的尸检：

> `user.name` 入库加密、解密是服务级动作（`UserService.decryptUserFields`，无 MyBatis TypeHandler），裸 `SELECT` 拿到的是密文（`hex:base64` 形态）。

防忘机制有三个，按强度排：

1. **代码约定**：所有跨租户裸查（`IgnoreTenant`）回显姓名前必须 `cryptoUtil.decrypt`——`loadUsersForStats` 是范式；
2. **命名暗示**：`decryptUserFields` / `decryptUserList` 成对存在，读方法里 grep 不到它们就是嫌疑对象；
3. **降级不炸**：`decrypt` 对非加密格式（历史明文）原样返回、解密失败只 `log.warn` 不抛异常——**解密故障降级为「显示原值」而不是 500**，业务连续性优先于洁癖（代价见 §4.5）。

### 2.4 三条查询路径，没有一条能全包

加密字段的查询被拆成三条，按条件类型分流（`UserService.listByConditionPage` 915 行的 `if` 就是分岔口）：

| 条件类型 | 路径 | 原理 |
| --- | --- | --- |
| 精确等值（手机号/邮箱全匹配） | SQL `LIKE 'hmac:%'` 或 `OR = plain` | 盲索引 + 历史明文兜底 |
| 模糊包含（姓名/邮箱/手机号片段） | **全量取出 → 内存解密 → contains 过滤 → 手动分页** | 密文无法模糊匹配，只能解密后比 |
| 无加密字段条件（按角色/状态/userId） | SQL 层直接分页 | 不碰密文，走正常 `LIMIT` |

第二条是性能上最痛的：**模糊搜一个「张」，要把租户下（或全平台）用户全查出来解密一遍再过滤**。项目靠两个前提让它可接受：① 分页总量可控（管理员账号、租户用户是千级不是百万级）；② 模糊条件必带其他收窄条件（role/status）。`platformAdminPage` 的注释写得很直白：「分页在内存中完成（管理员账号数量级小，跨租户总量可控）」。

## 3. 源码实现

### 3.1 CryptoUtil：五组方法各司其职

```java
// CryptoUtil.java:42-51 —— 启动即校验密钥，拒绝弱配置启动
@PostConstruct
public void init() {
    byte[] aesBytes = Base64.getDecoder().decode(aesKeyBase64);
    if (aesBytes.length != 32) {
        throw new IllegalArgumentException("crypto.aes-key 解码后必须为 32 字节（AES-256）");
    }
    byte[] hmacBytes = Base64.getDecoder().decode(hmacKeyBase64);
    this.aesKey = new SecretKeySpec(aesBytes, "AES");
    this.hmacKey = new SecretKeySpec(hmacBytes, HMAC_SHA256);
}
```

与 N5 的 `JwtUtil.initSigningKey` 同款哲学：**密钥长度不达标就让应用启动失败**，而不是运行时静默降级到弱算法。配置侧同样用环境变量注入、文件里只留本机兜底：

```properties
# application.properties:131-134
crypto.aes-key=${AES_KEY:HVwcdqAh5A6nScL+...}   # Base64 的 32 字节 AES-256
crypto.hmac-key=${HMAC_KEY:Ip0fg8W0iUXc9...}    # Base64 的 32 字节 HMAC-SHA256
```

注释写明「生产环境应通过环境变量注入，切勿入库」——这是 secret-env 守卫盯的字段之一。

`decrypt` 的双闸门是兼容性设计的核心：

```java
// CryptoUtil.java:74-99（有删节）
public String decrypt(String stored) {
    if (stored == null || stored.isEmpty()) return stored;
    if (!isEncryptedFormat(stored)) return stored;    // 闸门一：不是加密格式 → 原样返回
    String cipherPart = stripIndex(stored);
    try {
        byte[] combined = Base64.getDecoder().decode(cipherPart);
        if (combined.length <= IV_LENGTH) return stored;
        // 拆 IV / 拆密文+tag / GCM 解密（tag 校验失败会进 catch）
        return new String(cipher.doFinal(cipherText), StandardCharsets.UTF_8);
    } catch (Exception e) {
        log.warn("AES-GCM 解密失败，降级返回原值: {}", e.getMessage());   // 闸门二：解不开 → 原值
        return stored;
    }
}
```

`isEncryptedFormat` 的判定极其严格（107-128 行）：必须有分隔符、分隔符前**恰好 64 位十六进制**、分隔符后是**合法 Base64 且解码长度 > IV**。三层都过才承认「这是我家加密的数据」。宁可错放一百条明文过去，不可把一条明文当密文解出乱码。

### 3.2 UserService：三对辅助方法

```java
// UserService.java:77-99（有删节）
// 对 phone/email/name 字段做 AES-GCM 加密并附加 HMAC 搜索索引（复合格式 hmac:ciphertext）
// 注意：account 已决定不再加密，按明文存储与匹配
private void encryptUserFields(User user) {
    // user.setAccount(cryptoUtil.encryptWithIndex(user.getAccount()));   // 已决定不加密
    user.setPhone(cryptoUtil.encryptWithIndex(user.getPhone()));
    user.setEmail(cryptoUtil.encryptWithIndex(user.getEmail()));
    user.setName(cryptoUtil.encryptWithIndex(user.getName()));
}
private void decryptUserFields(User user) { /* 三个 decrypt 对称调用 */ }
private void decryptUserList(List<User> list) { for (User u : list) decryptUserFields(u); }
```

`encryptWithIndex(null)` 返回 null（方法内判空），配合 Mapper XML 的 `<if>` 标签，**局部更新时未传字段不会被加密成 `"null"` 字符串**——`updateUserInfo` 注释专门点了这个配合（870 行）。

注册链路（`Register`）、微信登录（`wechatLogin`）、管理员改资料（`updateUserInfo`）三条写路径全部先 `encryptUserFields` 再落库；登录、列表、详情所有读路径先 `decryptUserList` 再返回。

### 3.3 updateUserInfo：两个坑的显式处理

```java
// UserService.java:831-839 注释原文
1) phone/email/name 在库里是 AES-GCM 密文（见 encryptUserFields）。若把前端传来的
   明文直接落库，会造成：列表查询 decrypt 得到乱码、HMAC 搜索索引丢失导致
   按手机号/邮箱再也检索不到该用户。因此必须与注册路径一样先 encryptWithIndex 再入库。
2) 支持局部更新（未传的字段保持原值），所以不能拿"本次请求里的 phone/email"
   直接判断"至少留一项联系方式"——要先取出原记录合并后再校验，
   否则"只改姓名"这种合法请求会被误拒。
```

对应实现是先取原记录解密、合并、校验、再加密入库（852-876 行）。坑 1 是「加解密对称性」问题：写入侧漏一次加密，读侧就永久乱码，而且**不是当场炸，是下一次列表查询才炸**——这种延迟爆炸最难排查。坑 2 是局部更新的通用陷阱，与加密无关但同处一个方法，一起修了。

### 3.4 listByConditionPage：分岔口的两条路

```java
// UserService.java:915-937（有删节）
if (hasFuzzyCondition(query)) {
    // 含加密字段模糊条件：全量查询（仅按 role/status/userId），内存解密 + contains 过滤 + 手动分页
    List<User> all = userMapper.listByConditionAll(query);
    decryptUserList(all);
    List<User> filtered = new ArrayList<>();
    for (User u : all) { if (u != null && matchFuzzy(u, query)) filtered.add(u); }
    total = filtered.size();
    // 手动分页：from/to 由 filtered 计算，total 也是 filtered 的 size
} else {
    // 无加密字段模糊条件：SQL 层分页查询
    retList = userMapper.listByConditionPage(query);
    decryptUserList(retList);   // 分页数据也要解密！
    total = userMapper.selectCountByContion(query);
}
```

注意两条路都调 `decryptUserList`——**走 SQL 分页的那条路同样存的是密文**，「我不搜加密字段」不等于「我不读加密字段」。这是 N7 最容易被漏的一条：分页接口不模糊搜，就以为不用解密。

`platformAdminPage`（968 行起）是同一模式的跨租户版：`listByConditionAll` 取全平台 → `decryptUserList` → 角色 IN 过滤（内存，因为 SQL 单角色条件表达不了「admin + platform_admin 两类」）→ `matchAdminQuery` 内存模糊 → 手动分页 → `fillOrgName` 补公司名。

### 3.5 PromoService.loadUsersForStats：跨租户裸查的解密范式

```java
// PromoService.java:960-979（有删节）
/**
 * 统计专用：批量取用户并解密姓名，返回 userId → User。
 * <p><b>为什么必须就地解密</b>：user.name 入库加密、解密是服务级动作
 * （UserService.decryptUserFields，无 MyBatis TypeHandler），
 * 裸 SELECT 拿到的是密文（hex:base64 形态）。
 */
private Map<String, User> loadUsersForStats(java.util.Collection<String> ids) {
    for (User u : userService.listByIdsIgnoreTenant(ids)) {
        u.setName(cryptoUtil.decrypt(u.getName()));
        users.put(u.getUserId(), u);
    }
    return users;
}
```

这是全套体系里最该被抄的一段：**`IgnoreTenant` 裸查 + 就地 decrypt + 方法注释写明「为什么」**。三级推广统计（Top20 推广人、最近转化）要按 userId 跨租户批量取人，走的就是这条路。注释里「空值与历史明文由 `CryptoUtil.decrypt` 原样透传，可安全调用」给调用方吃了定心丸——不需要先判格式再解密。

## 4. 踩坑实录

### 4.1 前端满屏 hex:base64：裸查忘了 decrypt

推广统计页上线初期，Top20 列表的推广人姓名列显示 `<hex>:<base64>` 形态的串。根因就是 §2.3 说的：统计链路走 `listByIdsIgnoreTenant` 跨租户裸查，拿到密文直接塞进 VO，没有任何一层自动解密。修复即 `loadUsersForStats` 范式。

**通用教训：新增「绕过 TenantContext 的读路径」时，把 `decrypt` 和 `@InterceptorIgnore` 当成一对来写**——豁免租户过滤的代码 review 清单里必须有一条「此路径回显的加密字段解开了吗」。

### 4.2 改资料不加密：当场不炸，下次查询炸

`updateUserInfo` 坑 1 的场景：如果把前端明文直接 `update` 进 `phone` 列，会发生两件事——该用户的手机号变成「无 HMAC 前缀的明文」；之后任何按手机号搜他的请求，`LIKE 'hmac:%'` 不命中，`OR phone = plain` 反而命中（`plain` 参数恰好是明文手机号）——**登录奇迹般还能用，但后台搜索时灵时不灵**。而列表页该行手机号列，`decrypt` 闸门一判定「非加密格式」原样返回——显示也是对的。真正炸的是「下次改资料」：合并逻辑把明文当已解压缩值，再 `encryptWithIndex` 加密，自此该行变成「明文被加密」的双层怪胎。

**通用教训：加解密不对称的故障有延迟性。写入侧的每一个 `update`/`insert` 都要 review「这条 SQL 最终写进去的列，有对应的加密调用吗」。**

### 4.3 内存分页的 total 从哪来

模糊路径手动分页，`total = filtered.size()` 而不是 `selectCountByContion(query)`——后者数的是 SQL 候选全量，没经过内存 contains 过滤，分页器会显示「共 500 条」却只能翻出 3 条。两个 `if` 分支的 total 语义不同，是这套双路设计的内在复杂度，改代码时别「顺手统一」。

### 4.4 LIKE 前缀匹配的索引幻觉

`WHERE phone LIKE 'hmac:%'` 能走索引，前提是 `phone` 列有索引且 collation 不会让优化器放弃。MySQL 8.4 下 `utf8mb4_general_ci` 对十六进制 + Base64 字符集是大小写不敏感——**HMAC hex 输出必须统一小写**（`bytesToHex` 用的 `%02x` 是小写），若哪天有人「顺手」改成 `%02X`，索引照样走、查询恒不命中，且毫无报错。这类「大小写敏感字段 + 大小写不敏感 collation」的坑，与 N1 跨库 JOIN 要显式 `COLLATE utf8mb4_general_ci` 是同族问题。

### 4.5 解密降级是把双刃剑

`decrypt` 失败只 `log.warn` 不抛异常，好处是业务不中断，坏处是**密钥轮换失败会被静默吞掉**：换了 `AES_KEY` 重启，老数据全部「降级返回原值」——列表页显示密文串而不是登录报错，直到用户投诉才发现。对策不是改成抛异常（那就回到炸业务的老路），而是：① 监控 `log.warn` 的频率，解密降级速率突增即告警；② 密钥轮换走「双密钥期」——新密钥加密、新旧都能解密，过渡期后再退役旧密钥。

### 4.6 两个 isEncrypted 的口径不一致

`CryptoUtil` 里有两个判断方法：实例级的 `isEncryptedFormat`（严格，三条件全查）与静态的 `isEncrypted`（宽松，只查「含分隔符」）。后者名字更短更诱惑，但它会把 `"备注:请看说明"` 这种普通文本也判成加密格式。目前全仓读路径都走 `decrypt` 内部严格版，静态版暂无调用方——**留一个宽松版判断方法本身就是未来的坑**，要么删，要么在 Javadoc 里写清「仅用于日志脱敏判断，不可用于解密前置」。

## 5. 落地 Checklist

**新增加密字段时**
- [ ] 写路径（insert/update）确认有 `encryptWithIndex`，且 null 字段不会被加密成字符串
- [ ] 读路径确认有 `decrypt`（包括**分页接口**——不模糊搜也要解密）
- [ ] 精确检索 SQL 是 `LIKE CONCAT(#{hmac}, ':%') OR field = #{plain}` 双分支，漏 `OR` 分支老数据全丢
- [ ] 模糊检索走「全量 + 内存解密 + contains + 手动分页」，`total` 用过滤后集合的 size
- [ ] 跨租户裸查（`IgnoreTenant`）回显前就地 decrypt，并抄 `loadUsersForStats` 的注释范式

**密钥与运维**
- [ ] `AES_KEY`/`HMAC_KEY` 生产环境走环境变量，仓库里只有兜底值且注释标明
- [ ] 密钥是两个独立的 32 字节（加密与索引分离，轮换互不影响）
- [ ] 启动校验密钥长度，不达标拒绝启动（与 JwtUtil 同款）
- [ ] 监控「解密降级返回原值」的 warn 日志频率，突增 = 密钥事故信号
- [ ] 密钥轮换规划双密钥期，不要一次性热替换

**设计红线**
- [ ] 不引入 `TypeHandler` 做「半自动」加密——要么全自动，要么全手工，混养最恐怖
- [ ] 模糊查询的性能前提（数据量级、必带收窄条件）写进方法注释，数据量涨一个数量级时回来复核
- [ ] HMAC hex 输出固定小写，`bytesToHex` 的格式串是 `%02x`
