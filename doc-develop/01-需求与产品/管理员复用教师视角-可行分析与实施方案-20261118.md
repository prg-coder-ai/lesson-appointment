# 管理员复用教师视角：可行分析与实施方案

- 日期：2026-11-18
- 状态：方案（未实施）
- 目标用户：同时承担机构管理员与授课教师职责的**单一账号**
- 归类：需求与产品 / 角色与入口设计

---

## 1. 背景与目标

现状是「一个用户一个角色」：`sys_user.role` 为单值字符串（`student` / `teacher` / `admin` / `platform_admin`）。
小机构里常见「管理员本人也上课」，目前只能：

1. 用管理员账号进课堂 → 只能看，不能开麦、点名、下课；
2. 再注册一个教师账号 → 两套登录、两套排期归属，操作割裂。

本次目标：

- **简化入口**：管理员在一个页面里同时完成管理动作与上课动作，不再多账号切换。
- **最小改动**：不重构用户角色模型，不改登录/token 体系，不动 DDL。
- **不降低权限边界**：新入口不能让普通教师或学生获得管理员能力，也不能让管理员跨到别的租户。

---

## 2. 现状事实（代码级）

### 2.1 角色是单值，没有多角色机制

| 事实 | 证据 |
|---|---|
| `User.role` 是单个 `String` | `api/src/main/java/com/reservation/entity/User.java:62-63` |
| DDL 中 `role varchar(32) NOT NULL`，无 `user_role` 关联表 | `deploy/sql/schema/20261013-0400-lesson_appointment-schema.sql:915,929` |
| 角色常量只有 4 个（课堂侧另加 `system`） | `api/.../common/RoleConst.java:15-18`；`api/classroom-service/.../common/RoleConst.java:6-10` |
| JWT 直接带 `role` 与 `tenantId`，来自数据库 | `api/.../utils/JwtUtil.java:92-104`；`UserService.java:510` |
| 刷新 token 时重新查库取 role，不接受前端传值 | `authController.java:303-321` |
| 全仓无 impersonate / switchRole / viewAs / delegate 身份切换机制 | 检索零命中 |

### 2.2 后端其实已经放行管理员

`api/classroom-service/.../security/ClassroomAccessGuard.java:70` 把 `isManager(role)` 直接放行；
教师专属接口普遍写成 `if (!isTeacher() && !isManager())`：

| 能力 | 后端位置 | 管理员是否被拦 |
|---|---|---|
| start / pause / resume / end / kick | `ClassroomController.java:100/115/127/153/188` | 否 |
| 点名 | `RollCallController.java:52` | 否 |
| 录制 | `RecordingControlController.java:59,89,117-119` | 否 |
| 发布/静音/白板授权等 WS | `ClassroomPublishGuard.java:39-43,79-91` | 否 |
| 补签、作业点评、材料 | `AttendanceController.java:38`、`SubmissionController.java:93`、`MaterialController.java:58/74/106/124/151` | 否 |

**结论：管理员“不能上课”是前端按钮没渲染，不是后端权限不足。**

### 2.3 前端角色来源与按钮分支

- 课堂页角色：`frontend/js/classroom/classroom-main.js:86`
  `role: this._getParam('role') || user.role` —— **URL 的 `role` 参数已能覆盖 sessionStorage 里的用户角色**。
- 控制栏：`frontend/js/classroom/classroom-controls.js:27-68`
  - `:31-34` 麦克风/摄像头只给 `teacher` / `student`；
  - `:41-49` 全员静音/录制给 `teacher` / `admin`；
  - `:50-54` 点名/保存板书/作业点评只给 `teacher`；
  - `:58-64` 进行中/暂停/下课只给 `teacher`，其他角色渲染「离开」。
- 成员角色写入：`ClassroomController.java:71,79` 用 **JWT 的 role** 写 `classroom_membership.role`，不接受请求体角色。

### 2.4 入口分散

| 角色 | 入口 | 代码位置 |
|---|---|---|
| 教师/学生 | 「我的课堂」→「课程准备 / 进入课堂 / 回放」 | `my-classroom-core.js:184-221,311-357` |
| 管理员 | `admin.html`「预订审核」行内「进入课堂」 | `admin-booking.js:249-251,382-386` |
| 管理员 | `admin.html`「课程排期」详情「进入课堂」 | `admin-schedule.js:2287-2290,2634-2639` |
| 管理员 | `admin.html`「课堂监控」→ 运营台（不进课堂页） | `admin.html:108-111,397-405` |
| 平台管理员 | 只有实例管理，**无进入课堂入口** | `platform_admin.html:54` |

以上入口都只带 `scheduleId`，没有一个带 `role`，所以管理员进课堂时角色恒为 `admin`。

---

## 3. 问题定性

1. **权限问题假的**：后端已把管理员当 staff 放行；前端按 role 把按钮藏了。
2. **入口问题是真的**：管理员要在「预订审核 / 课程排期 / 课堂监控」之间来回找，没有统一的「我的课堂」。
3. **身份语义问题**：管理员以教师方式操作时，成员表里仍是 `admin`，名单显示「管理员」，教师/学生对他的身份认知不一致。
4. **不可直接改 `role` 字段**：把 admin 改成 teacher 会丢掉管理菜单；加 `admin_teacher` 角色会牵动 `RoleConst`、守卫白名单、授权表、注册准入计数，风险与收益不成正比。

---

## 4. 方案对比

| 方案 | 做法 | 改动面 | 风险 | 结论 |
|---|---|---|---|---|
| **A. 教师视角（上下文角色）** | 管理员入口 URL 加 `role=teacher`，前端渲染教师按钮；后端保持 JWT 角色与现有放行逻辑 | 前端 3~4 个文件，后端 0（可选小改） | 低；无 DDL、无 token、无角色常量变化 | **推荐** |
| B. 真正多角色 | 新建 `user_role` 表、JWT 加多角色 claim、鉴权全链路改成集合判断 | DB + 后端 + 前端 + 守卫，数十处 | 高；注册准入计数/自锁守卫语义都要重定义 | 不推荐本次做 |
| C. 新复合角色 `admin_teacher` | 加角色常量并全量补授权 | `RoleConst`、`AuthzRules`、守卫白名单、注册流程 | 高；新增角色字符串会被多道守卫拦截 | 不推荐 |
| D. 把管理员直接改成教师 | 直接改 `sys_user.role` | 一行数据 | 管理功能全丢，`applyRoleAdmission` 准入规则被绕开 | 否决 |

---

## 5. 推荐方案 A：管理员「教师视角」

### 5.1 设计原则

- **不改用户角色**：账号仍是 `admin`，管理菜单照常可用。
- **不新增角色字符串**：避开 `check:authz`、`check:admin-self-lock` 的角色约定。
- **不新增后端接口**：复用 `classroom.html?scheduleId=...&role=teacher`，无需在 `shared/apiPaths.js` 新增端点。
- **视角是上下文，不是提权**：服务端依然按 JWT `admin` 鉴权；管理员本来就被 `isManager()` 放行，UI 只是把已有能力显示出来。

### 5.2 前端改动（核心）

**① 角色参数做白名单收敛** —— `frontend/js/classroom/classroom-main.js:86`

当前 `_getParam('role') || user.role` 允许任意角色覆盖，存在学生手改 `?role=teacher` 造成 UI 误导的隐患。改为：

```
实际角色 actual = sessionStorage 中的 user.role
请求角色 requested = URL 参数 role
若 requested === 'teacher' 且 actual ∈ {'admin','platform_admin'} → 采用 teacher
否则 → 忽略 URL 参数，沿用 actual
```

效果：

- 管理员可以在自己的课堂上看到教师全套按钮；
- 教师/学生即便手改 URL 也拿不到不属于自己的按钮（后端本来也会拒绝）；
- 平台管理员是否允许教师视角，按租户边界另行决定（见 5.4）。

**② 管理员统一入口** —— `frontend/admin.html` + `my-classroom-core.js`

新增「我的课堂」菜单项（`key=my_classroom`），沿用 `teacher.html:69-72 / 507-516` 的加载方式。列表取本租户课次，每行按钮：

| 按钮 | 跳转 | 说明 |
|---|---|---|
| 课程准备 | `classroom-prep.html?scheduleId=...` | 设备检测、资料 |
| 进入课堂（教师视角） | `classroom.html?scheduleId=...&role=teacher` | 主按钮 |
| 巡课 | `classroom.html?scheduleId=...`（无 role） | 保留只读观察入口 |
| 课程回看 | `replay.html?scheduleId=...` | 已结束课次 |

**③ 既有入口改造**

- `admin-booking.js:382-386`、`admin-schedule.js:2634-2639`：管理员的「进入课堂」改为「进入课堂（教师视角）」并带 `&role=teacher`；若要保留观察模式，增加「巡课」次按钮。
- `admin-AppointmentNotes.js`：确认是否补入口（当前无），建议统一收敛到「我的课堂」，不再在通知页加按钮。
- `classroom-controls.js` **不改**：它已按传入 role 正确渲染。

### 5.3 后端可选小改（第二阶段）

若要求名单里的身份也显示「教师」：

- `EnterClassroomReq` 增加可选 `viewRole`；
- `ClassroomController.enter()` 在 JWT role 为 admin/platform_admin、且 `viewRole=teacher` 时，校验该用户是课次教师或本租户管理员，然后把 `membership.role` 写成 `teacher`；
- 增加一条审计日志记录「管理员 X 以教师视角进入课次 Y」。

不改 `classroom_membership` 表结构（复用现有 `role` 列），因此 `check:ddl-align` 不受影响。
**第一阶段不做也能上线**：成员显示「管理员」是可接受的过渡态。

### 5.4 租户与平台边界

- 租户管理员：仅可对自己租户的课次使用教师视角；跨租户课次由 `ClassroomAccessGuard` 现有租户校验拦截。
- 平台管理员：默认**不开放**教师视角（其定位是平台运维，且课堂页当前只有白板/讲稿/离开）；如确需，单独评审后再放开。
- 不改变 `applyRoleAdmission` 的「只数 role 不数 status」规则，也不触碰 `assertNoAdminSelfLock`。

### 5.5 不变的部分

- 登录、JWT 签发与刷新链路；
- `RoleConst` / `AuthzRules` / `check-authz-declarative` 的合法角色集合；
- `sys_user` 与 `classroom_membership` 的 DDL；
- 教师/学生原有入口与「我的课堂」行为。

## 6. 实施步骤（建议顺序）

| 步骤 | 内容 | 涉及文件 | 验收 |
|---|---|---|---|
| 1 | 角色参数白名单收敛 | `classroom-main.js:86` | 学生手改 `?role=teacher` 仍显示学生按钮；管理员带参显示教师按钮 |
| 2 | 管理员「我的课堂」菜单与课次列表 | `admin.html`、`my-classroom-core.js`、新增 admin 适配脚本 | 菜单可见、按钮跳转正确、课次状态正确 |
| 3 | 既有「进入课堂」按钮带教师视角参数 | `admin-booking.js`、`admin-schedule.js` | 进入后控制栏出现麦克风/点名/进行中/暂停/下课 |
| 4 | （可选）成员角色与审计 | `EnterClassroomReq.java`、`ClassroomController.java` | 名单显示教师；审计日志可查；DDL 守卫不红 |
| 5 | 文档同步 | `doc-user/电子课堂使用手册-20261118.md`、`doc-user/电子课堂-操作说明.md` | 两个手册角色表一致 |
| 6 | 回归 | 手工 + 守卫 | 见下 |

### 关键守卫

- `npm run check:authz`：不得新增未声明角色；
- `npm run check:endpoints`：新跳转用已有 `ENDPOINTS` 常量，不硬编码 `/api/v1/...`；
- `npm run check:admin-self-lock`：角色准入与自锁判据不得变；
- `npm run check:global-collide`：新增前端脚本顶层标识符必须包 IIFE；
- `npm run check:ddl-align`：若执行步骤 4，确认实体与 DDL 仍对齐。

---

## 7. 验收标准

1. 同一管理员账号：在 `admin.html` 能审批/排课，点「进入课堂（教师视角）」后能开麦、点名、上传讲稿、录制、暂停、下课。
2. 该账号退出课堂后回到管理端，管理权限完整，无需重新登录。
3. 教师账号看到的界面与之前完全一致；学生无法通过 URL 参数获得教师按钮。
4. 跨租户课次尝试教师视角被拒，无数据泄露。
5. 所有既有守卫与 16 道 pre-commit 钩子通过。
6. 回放、出勤、课时回流在新入口下走同一套逻辑，无重复结算。

## 8. 风险与规避

| 风险 | 规避 |
|---|---|
| 管理员误点「下课」导致结算 | 沿用现有 confirm「确定要结束本次课堂吗？」；在教师视角入口首次进入时提示 |
| 教师视角被当成新角色扩散 | UI 用「视角」措辞，不写「角色变更」；后端不加角色常量 |
| URL 参数被滥用 | 前端白名单收敛；后端权限模型不变，越权调用仍按 JWT 拒绝 |
| 名单身份不一致 | 第一阶段接受显示「管理员」；第二阶段按 5.3 写 `teacher` 并留审计 |
| 单一用户既是管理员又是教师时的数据归属 | 排期/课次的 `teacherId` 仍是该用户 userId，归属不变；不要用 admin 身份覆盖 |

---

## 9. 暂不纳入

- 真正的一人多角色（方案 B）、复合角色（方案 C）；
- 平台管理员教师视角；
- 移动端小程序的同款入口（本期只做 Web）；
- 用「视角」参数绕过教师本人归属校验（若管理员不是该课次教师，应只允许巡课，不允许教师视角——落地时按 5.4 校验）。

---

## 10. 结论

**推荐走方案 A**：它把“管理员不能上课”的问题还原成“前端没渲染按钮”，用工单最小的改动达成单一账号的完整闭环；角色模型、token、DDL、授权守卫全部保持不动。入口统一到管理员「我的课堂」后，原有三处分散按钮可逐步收敛，操作路径从「找标签页」变成「一个列表四个按钮」。

实施上分两阶段：第一阶段只改前端（1~3 步）即可上线；第二阶段按需补成员角色与审计（第 4 步），不阻塞第一阶段。
