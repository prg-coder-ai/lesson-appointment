## 一、口径定义（先钉死，避免实现时摆动）

| 判定项 | 规则 | 说明 |
|-------|------|------|
| **归属基准** | `Course.teacherId == token.userId` | `Course.java:76` 已有 `private String teacherId`，**无需加字段** |
| **管理平台/租户管理员** | 放行，可代任何教师操作 | 保留现有 admin 代建排期能力（`admin-schedule.js` 依赖），不得一刀切 |
| **平台管理员** | ✅ **放行**（2026-10-26 已拍板） | 与 `checkTeacherSelfOrAdmin` 口径一致；数据可见性交 `TenantLineInnerInterceptor`，前端 `teacherInfo.html` 的显式拒绝是产品决策、不变 |
| **教师账号状态** | 必须 `active` | 被停用（`inactive`/`frozen`）或已软删（`delete`）的教师不得再操作排期 |
| **数据来源** | **服务端从 `courseId` 反查**，不接受客户端传 `teacherId` | `ScheduleCreateDTO:23` 的 `teacherId` 已是注释状态，**保持注释不要解封** |
| **拒绝返回** | 抛 `NoPermissionException` → `Result.fail(403, msg)` | `GlobalExceptionHandler:63` 已映射，**HTTP 200 + 业务码 403**（对齐 Result 契约） |

> **为什么强调服务端派生**：本项目已确立「DTO 不接受客户端值，服务端从令牌派生」原则（推广双码 target、此次用户 Tab 均遵此）。解封 `teacherId` 等于把归属开关交回客户端，一个 Burp 改包即可绕过。

## 二、现状：八个排期写端点的实际防护（实证）

**先厘清执行层**：`AuthzRules.RULES` 被 `SecurityConfig.java:266` 展开为 Spring Security 的 hasRole 配置，即**角色维度在过滤器层已生效**；方法体内的 `permissionCheck.*` 是项目称的「**方法级兜底**」（见 `TeacherProfessionalController` 与 `AuditLogController` 的注释）。

**归属维度目前全线为零**：

| 端点 | AuthzRules 角色 | 方法体校验 | 归属校验 | 状态 |
|------|----------------|-----------|---------|------|
| `POST /schedule/create` | TEACHER_OR_ADMIN(315) | `checkTeacherOrAdmin` | ✗ | 需补 |
| `POST /schedule/update` | TEACHER_OR_ADMIN(316) | `checkTeacherOrAdmin` ×7 | ✗ | 需补 |
| `DELETE /schedule/delete/{id}` | TEACHER_OR_ADMIN(318) | `checkTeacherOrAdmin` | ✗ | 需补（经排期→课程） |
| `DELETE /schedule/deleteByCourseId/{courseId}` | TEACHER_OR_ADMIN(319) | `checkTeacherOrAdmin` | ✗ | **最高危**，直接给 courseId |
| `POST /schedule/updateStatus` | TEACHER_OR_ADMIN(322) | **无任何 `permissionCheck`** | ✗ | **方法体零兜底** |
| `POST /schedule/incSite` | TEACHER_OR_ADMIN(317) | `checkTeacherOrAdmin` | ✗ | 需补 |
| `POST /schedule/generate` | **ALL_ROLES**(323) | 规则备注「**校验被注释**」 | ✗ | 需复核后再定 |
| `POST /schedule/assign-student` | TEACHER_OR_ADMIN(325) | 备注「**校验被注释**」 | ✗ | 需补 |
| `POST /schedule/checkConflict` | TEACHER_OR_ADMIN(324) | 只读检测 | ✗ | 建议补（信息泄露面） |

**三个必须点名的具体问题**

1. **`updateStatus` 方法体完全裸调用** —— `ScheduleController.java:74-79` 只有 `scheduleService.updateStatus(dto)`，连 `checkTeacherOrAdmin` 都没有。虽然 AuthzRules 在过滤器层按 TEACHER_OR_ADMIN 拦了角色，但这与项目「方法级兜底」惯例不符，且**一旦过滤器层规则被误删/改，该端点直接裸奔**。
2. **`deleteByCourseId/{courseId}` 是最危险的入口** —— 教师 A 用口耳相传的任意一个 courseId，即可删掉他人课程的全部排期，且它走的是 CascadeRules 场景（连带清课次/预订）。
3. **`generate` 是 ALL_ROLES 且校验被注释** —— 学生角色在过滤器层即可通过，虽然它是"获取排期课次时间"的生成入口，但归属维度没有任何约束。

## 三、后端改造设计

### 3.1 新增统一归属校验（一处定义，八处复用）

在 `PermissionCheck` 中新增（照 `checkTeacherSelfOrAdmin` 的写法，保持术语映射 `TermMsg.t`）：

```java
/**
 * 校验：教师仅可操作【本人授课课程】的排期；租户管理员/平台管理员可代操作。
 * 归属由服务端从 courseId 反查 Course.teacherId，绝不接受客户端传入。
 */
public void checkCourseOwnerOrAdmin(String token, String courseId) {
    String role = getRoleFromToken(token);
    if (RoleConst.PLATFORM_ADMIN.equals(role) || "admin".equals(role)) {
        return;                                   // 管理员代操作放行
    }
    if ("teacher".equals(role)) {
        if (courseId == null || courseId.trim().isEmpty()) {
            throw new NoPermissionException("缺少课程标识，无法确定归属");
        }
        Course course = courseMapper.selectById(courseId);
        if (course == null) {
            throw new NoPermissionException(TermMsg.t("{course}不存在或不属于当前租户"));
        }
        String userId = getUserIdFromToken(token);
        if (!userId.equals(course.getTeacherId())) {
            throw new NoPermissionException(TermMsg.t("{teacher}只能操作本人的{course}排期"));
        }
        // 账号状态门槛：被停用/软删的教师不得再改排期
        if (!isActive(userId)) {
            throw new NoPermissionException(TermMsg.t("{teacher}账号未审核或已冻结，请联系管理员"));
        }
        return;
    }
    throw new NoPermissionException("您无权限执行该操作");
}

/** 排期ID → 课程ID → 走上面的归属校验（供 delete/{id}、updateStatus 等只有 scheduleId 的端点使用） */
public void checkScheduleOwnerOrAdmin(String token, String scheduleId) {
    CourseSchedule s = scheduleMapper.selectById(scheduleId);
    if (s == null) throw new NoPermissionException("排期不存在");
    checkCourseOwnerOrAdmin(token, s.getCourseId());
}
```

> **注**：`CourseSchedule` 实体**没有 `teacherId` 字段**（`CourseScheduleService:461` 源码注释已说明），所以必须走「排期 → 课程 → 教师」两级反查，不能直接比。

### 3.2 逐端点接入清单

| 端点 | 改造动作 |
|------|---------|
| `/schedule/create` | 保留 `checkTeacherOrAdmin`，**增补** `checkCourseOwnerOrAdmin(token, dto.getCourseId())` |
| `/schedule/update` | 同上（DTO 同样含 `courseId`） |
| `/schedule/delete/{id}` | 保留 `checkTeacherOrAdmin`，**增补** `checkScheduleOwnerOrAdmin(token, id)` |
| `/schedule/deleteByCourseId/{courseId}` | 保留，增补 `checkCourseOwnerOrAdmin(token, courseId)` ← **优先做** |
| `/schedule/updateStatus` | **补 `checkTeacherOrAdmin`** + `checkScheduleOwnerOrAdmin(token, dto.getScheduleId())` |
| `/schedule/incSite` | 增补 `checkScheduleOwnerOrAdmin` |
| `/schedule/assign-student` | 解封/补齐被注释的校验 + `checkScheduleOwnerOrAdmin` |
| `/schedule/generate` | ✅ **不纳入归属管控**（实证更正，见 §6 决议 P2）：DTO 无 courseId、`ScheduleGenerator` 零 mapper 调用属纯计算，且被学生端约课链路依赖。改为加**防滥用限幅** |

### 3.3 AuthzRules 备注同步

`AuthzRules` 第 315-325 行的备注字符串需同步标注「**≡checkCourseOwnerOrAdmin（归属在方法体）**」，保持与 `check-authz` 守卫核对表的可读一致性（现成样例见 `:339` `/teacher/published/save` 的写法）。

### 4.3 🚩 阻塞项：时区 TBD 未收敛（**FE-1 前必须解决**）

`ScheduleController.java:47`（create）与 `:56`（update）仍带源码注释：

```java
Map<String, String> resultMap = scheduleService.createSchedule(dto); //////TBD: local->UTC switch
```

而项目口径是「**课次 appointment = UTC 唯一真相源，转换只经 ScheduleGenerator**」。`ScheduleCreateDTO:87` 虽有 `timeZone` 字段，但后端是否消费、是否落 ScheduleGenerator 尚未闭环。

## 五、不能踩的既有机制（回归检查清单）

| 机制 | 关联点 | 注意事项 |
|------|-------|---------|
| **CascadeRules** | `delete/{id}` 已由 Service 内先清课次与预订（`SCHEDULE_DELETE`/`BOOKING_DELETE` 场景） | 新增归属校验**不得改变 cascade 执行顺序**，只在最前置做权限判定 |
| **数据维护用户 Tab** | 新做的 `purge/user` 走 `SCENARIO_USER_DELETE`，删除教师会级联其课程链 | 本方案不动它；但两者共享"教师归属"语义，术语保持一致 |
| **软删状态** | 用户软删态为 `delete`（本次已落：数据维护 Tab） | 新增的 `isActive` 判定须把 `delete` 一并排除，否则被删教师仍能改排期 |
| **TenantLineInnerInterceptor** | `courseMapper.selectById` 会自动带租户条件 | 归属校验天然被限定在同租户内，**不要**为跨租户场景绕过它 |
| **17 道守卫** | `check-authz`（端点登记一致性）、`check-cascade`、`check-endpoints-refs`（零 `/api/v1/` 字面量） | 改前端务必用 `API_BASE_URL` 拼相对路径 |

## 六、决策记录（2026-10-26 已定案）

### ✅ P1：平台管理员放行归属校验

**决定：放行**，写法与 `checkTeacherSelfOrAdmin` 保持一致（见 §3.1 代码示例首条分支）。

分层原则：**归属校验只回答"是不是你的"**，"能不能看到这条数据"交给 `TenantLineInnerInterceptor`。
`teacherInfo.html:396` 对 platform_admin 的显式拒绝属于**前端产品决策**（不给入口），保持原样——两者不冲突。

### ⚠️ P2：`/schedule/generate` —— 原决议前提不成立，已修正

拍板为"纳入管控"，但源码实证显示该前提有误，故**修正**而非照做：

| 实证 | 结论 |
|------|------|
| `ScheduleGenerateDTO` 仅含 `startDate/endDate/startTime/repeatType/interval/repeatDays/timeZone/userTimeZone` | **无 courseId / scheduleId**，无从判定归属 |
| `ScheduleGenerator.java` **零 mapper 调用** | 纯时间展开计算，**不读不写库**，无越权面 |
| `courseAndBooking.js:826` 注释：「全站唯一实现，**学生端卡片**（student-bookingCards.js）、管理端排期（admin-schedule.js）都调这一个入口」 | 学生约课链路依赖它，加归属校验会误伤 |
| `checkTeacherOrAdmin` 被注释，而 AuthzRules:323 声明 ALL_ROLES | 二者一致，**不是被遗弃的漏洞** |

**替代做法**：不做归属校验（GEN-1）；补防滥用限幅——日期跨度 ≤366 天、`repeatDays` 长度上限、单次返回条数上限（GEN-2）；删掉源码注释里「权限校验：checkTeacherOrAdmin」的过时描述，避免后来者照它补一个会误伤学生的校验（GEN-3）。

> 它的真实风险不在越权，而在**资源放大**：超长跨度 × 多重复日会撑大单次计算量。

## 七、分阶段落地与验收标准

| 阶段 | 内容 | 完成标志（DoD） |

## 八、一句话结论

> 这条业务口径在技术上**几乎零成本就能达标**——`Course.teacherId` 已在、`CourseQueryPage` 已支持按教师过滤、前端也已经在传 `teacherId`，缺的只是**后端把"前端传来的过滤条件"升级为"服务端强制校验"**。真正的成本在两处：一是要先把 `updateStatus` 那个零兜底的洞补上，二是**必须等 UTC TBD 收口再开前端**，否则会用"正确的人"写入"错误的时间"。
