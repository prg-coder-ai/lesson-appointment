# 课次记录与凭证实现方案（修改版）

> 版本：v2.0（2026-10-15）
> 范围：① 学生课次余额与流水；② 教师授课次数月度快照；③ 凭证层（审计日志 + 签到 + 请假快照）
> **前提约束**：系统只记录学生"上课次数 + 可用课次"；教师只记授课次数；线上**不涉及支付**
> 依据：全部结论附代码级证据（文件:行），未验证处标注「待实测」

---

## 1. 需求解读

| # | 记录主体 | 业务含义 | 关键问题 |
|---|---|---|---|
| A | 学生 | 已上课次 / 可用课次余额 / 已退课次 | 余额怎么扣、怎么退、怎么追溯 |
| B | 教师 | 月度授课次数（用于结算依据） | 教师维度怎么聚、口径是什么 |
| C | 凭证 | 争议发生时还原真相 | 谁改了状态、谁去了课、请假申请留痕 |

三条记录的共同结构：**事实源（appointment）→ 计量口径（status 定义）→ 流水/快照表 → 审计层**。

## 3. 缺口分析

### 3.1 学生课次记录——缺什么

| 缺 | 具体 | 严重度 |
|---|---|---|
| 学生维度 | appointment 无 studentId 冗余；学生余额计数必须 join booking | 高（性能+复杂度） |
| 教师维度 | appointment 无 teacherId 冗余；教师月度统计必须 join booking | 高 |
| 余额表 | `student_balance` 账户表未建 | 高（无落点） |
| 流水表 | `student_balance_flow` 流水表未建 | 高（无可追溯） |
| 真实 Service | `StudentBalanceServiceStub` 只记日志不写库 | 高（功能空） |
| 余额为负的定义 | Stub 说"余额不足不阻断主流程"，但实际行为未定义 | 中（需拍板） |
| 学生端查询 | 小程序/web 均无"我的课次"页 | 低（先做后端） |

### 3.2 教师授课次数——缺什么

| 缺 | 具体 | 严重度 |
|---|---|---|
| 计量 SQL | 有了冗余列后 GROUP BY appointment 即可 | 低（SQL 已在方案草案给） |
| 月度快照表 | `teacher_lesson_count` 未建 | 高 |
| 月结任务 | 未在 `MonitorTask` 注册 | 中（每月 1 日即可） |
| 重跑幂等 | `uk_teacher_month` 唯一键兜住 | 低（upsert 语义） |

### 3.3 凭证层——缺什么

| 缺 | 具体 | 严重度 | 争议场景 |
|---|---|---|---|
| **状态变更审计** | appointment 只有当前 status 值，不知道"谁在什么时候从什么状态改成什么" | **最高** | "课次被人改成 completed" 无据可查 |
| 签到表缺列 | CourseCheckIn 实体定义了 scheduleId/studentId/teacherId/checkInStatus，但表里没有这四列 | 高 | "学生说没去上课"无法核实 |
| 请假申请留痕 | "请假" = appointment 状态变 cancelling，但谁申请的、理由是什么全丢了 | 中 | "我没请假怎么算我取消了" |

### 3.4 **已有的、可复用的强凭证（不要重复造）**

| 凭证 | 完备度 | 说明 |
|---|---|---|
| `refundSnapshot` JSON 退费档位快照 | ✅ 已上线 | 自动 capture，含判定时刻档位、比例；审核结算的权威依据 |
| `notification_dispatch_log` 系统通知流水 | ✅ 已上线 | 有时间戳、收件人、SENT/FAILED；可证明"系统通知过学生/教师上课" |

## 4. 数据模型设计

### 4.0 设计原则

1. **无任何金额字段**——前提"不涉及支付"，方案原文的 `BigDecimal`/`unit_price`/`amount` 全部砍掉
2. **保留幂等键和 FOR UPDATE**——Stub 已把并发和幂等约束写死，不偏离
3. **平台级表统一进 IGNORE_TABLES**——tenant_id 是归属维度而非隔离维度
4. **凭证先行**——审计日志优先级高于流水表；没有审计日志，流水也站不住脚

### 4.1 appointment 表：3 处 ALTER

```sql
-- ===== ① 学生/教师维度冗余列（计量用，不改 appointment 自身语义） =====
ALTER TABLE `appointment`
  ADD COLUMN `student_id`    varchar(36) DEFAULT NULL COMMENT '冗余自 booking.student_id（计量用）',
  ADD COLUMN `teacher_id`    varchar(36) DEFAULT NULL COMMENT '冗余自 booking.teacher_id（教师课次计量用）',
  ADD KEY `idx_student_status` (`student_id`, `status`),
  ADD KEY `idx_teacher_status` (`teacher_id`, `status`);
-- ⚠️ 唯一键 uk_appt_booking_class 不变；冗余列由 BookingAppointmentSyncService 在建/改预约时同步维护

-- ===== ② 启用 CourseCheckIn 签到（实体已定义，表缺 4 列） =====
ALTER TABLE `course_check_in`
  ADD COLUMN `schedule_id`     varchar(36) DEFAULT NULL COMMENT '排期ID',
  ADD COLUMN `student_id`      varchar(36) DEFAULT NULL COMMENT '学生ID',
  ADD COLUMN `teacher_id`      varchar(36) DEFAULT NULL COMMENT '教师ID',
  ADD COLUMN `check_in_status` varchar(10)  DEFAULT NULL COMMENT '1 checked/0 unchecked';

-- ===== ③ 请假申请快照列（补凭证黑洞） =====
ALTER TABLE `appointment`
  ADD COLUMN `leave_request`   json DEFAULT NULL COMMENT '请假申请：{applicantId, applicantRole, applyTime, reason}';
```

### 4.2 学生课次记录：2 张新表

```sql
-- ===== 学生课次余额账户（一学生一行） =====
-- ⚠️ 登记进 MyBatisPlusConfig.IGNORE_TABLES（平台级表，tenant_id 归属不隔离）
CREATE TABLE `student_balance` (
  `id`               bigint      NOT NULL AUTO_INCREMENT,
  `tenant_id`        bigint      NOT NULL COMMENT '租户归属（冗余，便于按租户审计）',
  `student_id`       varchar(36) NOT NULL COMMENT '学生 user.user_id',
  `lesson_remaining` int         NOT NULL DEFAULT 0 COMMENT '可用课次（可手动增加）',
  `version`          int         NOT NULL DEFAULT 0 COMMENT '乐观锁',
  `create_time`      datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`      datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_tenant_student` (`tenant_id`, `student_id`) COMMENT '租户内唯一（不同租户学生体系独立）'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='学生课次余额账户';

-- ===== 课次流水（每一笔消耗/退还都可追溯） =====
-- ⚠️ 登记进 IGNORE_TABLES
CREATE TABLE `student_balance_flow` (
  `id`             bigint       NOT NULL AUTO_INCREMENT,
  `tenant_id`      bigint       NOT NULL,
  `student_id`     varchar(36)  NOT NULL,
  `adjust_id`      varchar(64)  NOT NULL COMMENT '幂等键：LESSON-{apptId}（扣次）/ APPT-{id}-{level}（退费，同 Stub 现生成规则）',
  `flow_type`      varchar(20)  NOT NULL COMMENT 'consume=上课消耗/refund=退课退回/adjust=人工调整（管理员补余额/改余额）',
  `lesson_delta`   int          NOT NULL COMMENT '课次增减（负=消耗）',
  `appointment_id` bigint       DEFAULT NULL,

  `create_time`    datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_adjust` (`adjust_id`) COMMENT '幂等防重：重复确认/回调重放命中同一条'
```

**账户操作**：SELECT ... FOR UPDATE 后再改余额（Stub 注释已明确要求）；余额不足时**允许为负**（记 `adjust` 流水标记"余额不足已超出"），由租户管理员后续处理——不阻断主流程。

## 5. 计量口径（全端唯一的权威定义）

> 以下同时落文档（`server-side-term-template` 或类注释），前端展示文案以此为准。

| 口径 | 定义（appointment.status） | 用途 |
|---|---|---|
| 已上课次 | `completed` | 扣课次 / 教师授课计数 / 学生端"已上" |
| 已约课次 | `active` | 学生端"待上" / 教师端"待上" |
| 已退课次 | `cancelled` / `canceled` / `s-cancelling` 审批通过 / `t-cancelled` | 退费依据（比例读 `refundSnapshot` 快照） |
| 改期课次 | `changed`（`lastDatetime` 留痕，原时间留在其中） | 不增减总数，只改 `appointmentDatetime` |
| 已冻结 | `frozen`（管理员"删除预订"产生） | 保留行不物理删除，不计入任何有效口径 |

**取消口径注意**：`cancelling` / `s-cancelling` / `t-cancelling` 是"申请中"状态，**不计入"已退"**，只有审批通过后的 `cancelled`/`t-cancelled` 才算退课。

## 6. 实现方法

### 6.1 appointment 冗余列维护（挂现有服务，不改主干）

在 `BookingAppointmentSyncService` 建/改 appointment 的同一处，同步回填 `student_id` / `teacher_id`：

- 写入点：`syncOnStatusChange` 中创建/更新 appointment 的分支
- 来源：直接从当前 booking 对象取（service 已经持 booking 引用）
- 回填 SQL（一次性脚本）：

```sql
-- 分批回填，每批 5000
UPDATE appointment a
JOIN booking b ON a.booking_id = b.booking_id
SET a.student_id = b.student_id,
    a.teacher_id = b.teacher_id
WHERE a.student_id IS NULL OR a.teacher_id IS NULL;
-- 回填后校验：SELECT COUNT(*) FROM appointment WHERE student_id IS NULL; 应为 0
```

### 6.2 学生课次写入链路（挂现有点，不改主干）

| 事件 | 挂点 | 动作 |
|---|---|---|
| 课次确认完成 | appointment.completed 流转处（`BookingAppointmentSyncService` 或 `updateStatusById`） | 同事务插审计 log → 插 `student_balance_flow` consume 流水（adjustId=`LESSON-{appointmentId}`）→ 加锁扣 `student_balance.lesson_remaining` |
| 请假/退课确认 | `LeaveRefundSettleService.settleAfterLeaveConfirmed`（现只记日志） | 替换 `StudentBalanceServiceStub` 为真实实现；按 `refundSnapshot` 档位退课次（adjustId=`APPT-{id}-{level}` 与 Stub 现生成的一致，历史日志键不浪费） |
| 请假申请提交 | appointment 状态变 cancelling 之前 | 插入 `leave_request` JSON 快照 → 同事务写审计 log + 更新 status |
| 课次状态变更（所有入口） | `AppointmentService.updateStatusById` + `BookingAppointmentSyncService.syncOnStatusChange` | **最先**插审计 log，再更新 appointment.status，同事务 |

### 6.3 教师授课次数

- **计量 SQL**（加冗余列后免 JOIN）：
  ```sql
  SELECT teacher_id, COUNT(*) AS lesson_count
  FROM appointment
  WHERE tenant_id = ?
    AND status = 'completed'
    AND appointment_datetime BETWEEN ? AND ?
  GROUP BY teacher_id;
  ```
- **月结任务**（`MonitorTask` 新增，每月 1 日 03:00）：
  1. 显式 `TenantContext.setTenantId` + finally clear（定时任务无 HTTP 上下文的范式）
  2. 遍历全部 active 教师，执行上式计算
  3. UPSERT 到 `teacher_lesson_count`（`INSERT ... ON DUPLICATE KEY UPDATE lesson_count=VALUES(lesson_count)`，`uk_teacher_month` 保证幂等）
- **重跑幂等**：老师事后补完课次 → 任务重跑自动修正当月 lesson_count

### 6.4 CourseCheckIn 签到启用

- **DDL**：已在 4.1 节 ALTER 补 4 列
- **写入流程**：
  1. 教师端：手动点击"我已到课"→ `POST /course/checkin/teacher`
  2. 学生端：教师点"开始上课"后弹出签到码 → `POST /course/checkin/student`
  3. 管理员端：手动标记签到/缺席
- **数据约束**：`check_in_id`（UUID）+ `appointment_id` 唯一；签到时间应在上课时间前后 N 分钟内（可配置）
- **凭证关联**：签到记录在审计查询里与 appointment_status_log / notification_dispatch_log 关联展示

### 6.5 审计日志挂点（必须最先插）

在以下两个方法的最开头（status update 语句之前）插入：

```
// AppointmentService.updateStatusById / BookingAppointmentSyncService.syncOnStatusChange

// 1. 先插审计日志（同 appointment status update 同事务）
AppointmentStatusLog log = new AppointmentStatusLog();
log.setFromStatus(currentStatus);
log.setToStatus(newStatus);
log.setOperatorId(currentUserId);
log.setOperatorRole(currentRole);
log.setEndpoint("AppointmentService.updateStatusById"); // 或 syncOnStatusChange
appointmentStatusLogMapper.insert(log);

// 2. 再更新 appointment status
appointment.setStatus(newStatus);
...
```

## 7. 审计查询视图（争议处理面板）

平台管理员/租户管理员查询一个课次的完整证据链：

```sql
-- 一个 appointment 的全量证据：预约存在 → 通知发了 → 签到状态 → 状态变更历史 → 流水
SELECT
  a.appointment_id,
  a.status                                  AS '当前状态',
  a.appointment_datetime                    AS '上课时间',
  s.course_name                             AS '课程',
  st.name                                   AS '学生',
  t.name                                    AS '教师',

  -- 通知记录
  n.receiver_user_id                        AS '通知收件人',
  n.receiver_role                           AS '通知收件角色',
  n.sent_at                                 AS '通知发送时间',
  n.status                                  AS '通知结果',

  -- 签到记录
  ci.check_in_status                        AS '签到状态',
  ci.check_in_time                          AS '签到时间',

  -- 状态变更历史
  al.from_status                            AS '变更前',
  al.to_status                              AS '变更后',
  al.operator_id                            AS '操作人',
  al.operator_role                          AS '操作人角色',
  al.create_time                            AS '变更时间',
  al.reason                                 AS '变更原因',

  -- 课次流水（学生）
  bf.flow_type                              AS '流水类型',
  bf.lesson_delta                           AS '课次增减',
  bf.create_time                            AS '流水时间',

  -- 退费快照
  a.refund_snapshot                         AS '退费档位快照',

  -- 请假申请快照
  a.leave_request                           AS '请假申请快照'

FROM appointment a
JOIN booking b ON a.booking_id = b.booking_id
LEFT JOIN student s ON a.student_id = s.user_id
LEFT JOIN teacher t ON a.teacher_id = t.user_id
LEFT JOIN notification_dispatch_log n ON n.appointment_id = a.appointment_id
LEFT JOIN course_check_in ci ON ci.booking_id = b.booking_id
LEFT JOIN appointment_status_log al ON al.appointment_id = a.appointment_id
LEFT JOIN student_balance_flow bf ON bf.appointment_id = a.appointment_id
WHERE a.appointment_id = ?
ORDER BY al.create_time ASC, bf.create_time ASC;
```

## 附：一页结论

- **学生课次**：事实源（appointment.status）+ 幂等键（Stub 已生成）+ 退费快照都已就绪；缺的是**学生维度冗余列 + 余额两表 + 真实 Service 换 Stub**——三个挂点已明确（completed 流转、leaveRefundSettleService、请假申请前）
- **教师课次**：加冗余列后 GROUP BY 即可；缺的是**月度次数快照表 + 月结 upsert 任务**——极简表，无金额
- **凭证层**：`notification_dispatch_log`（通知）和 `refundSnapshot`（退费）已上线；缺的是**appointment 状态变更审计日志**（所有争议的地基）+ **启用签到** + **leave_request 请假快照**——这三样补上后，任何争议都有完整证据链
- **砍掉的**：原方案 A 类整套计费系统（4 张金额表 + 微信支付 + 到期停服）、C 类结算金额字段、B 类 purchase/adjust 流程——全部与前提"只记次数不涉及支付"冲突
- **改动量**：原方案 7 张新表 + 3 处 ALTER → 修改后 **5 张新表 + 3 处 ALTER**（少 40% DDL，多了所有争议都需要的凭证层）
