### 3.1 故障①：静态页正常，接口全 502

**现象**：`https://frontend-<envid>...` 打开正常，任何 `/api/v1/*` 请求一律 502 Bad Gateway。容器状态 Running，无重启。

**误判路径（按发生顺序）**

| 怀疑对象 | 检查 | 结果 |
|---|---|---|
| 端口不一致（`listen 80` vs 容器 8080） | 三套 Dockerfile 对照 | 确有隐患（`deploy/nginx/cloudbase-web` 那份是 80），但**不是本次** |
| 上游 api 服务挂了 | 控制台看 api 服务状态 | 正常，健康检查通过 |
| resolver 缺失（`no resolver defined`） | 读模板 | **真问题**（变量形式 `proxy_pass` 必须有 resolver），但只是"万一"，此时根因还没暴露 |
| 域名写法 | 实例内 `nslookup` | ★ **决定性证据** |

**根因**：`cloudBased/frontend/Dockerfile` 的 `ARG` 默认值是
`http://api.329614-8-1475810246.svc.cluster.local:8081` —— 这是自建 K8s 的 Service DNS 写法，
**微信云托管根本没有这套记录**。

**证据（实例 WebShell 内实测，可直接复现）**

```sh
nslookup api.329614-8-1475810246.svc.cluster.local   # → NXDOMAIN
nslookup api                                          # → NXDOMAIN（短名同样不行）
nc -vz api.329614-8-1475810246.svc.cluster.local 8081 # → nc: bad address
cat /etc/resolv.conf                                  # → 只有一行 nameserver 127.0.0.1（平台本地 stub）
nslookup api.weixin.qq.com                             # → 169.254.10.1（对照组：DNS 本身是活的）
```

对照组很关键：**stub 能解析普通公网域名，只是不做服务发现**。所以"DNS 坏了"这个方向可以直接排除。

继续验证公网域名可用：

```sh
nc -vz api-329614-8-1475810246.sh.run.tcloudbase.com 443
# → open（124.223.145.112）
wget -qS -O /dev/null https://api-329614-8-1475810246.sh.run.tcloudbase.com/api/v1/system/info
# → HTTP/1.1 200 OK   ← 上游完全健康，502 纯粹是域名写错
```

**修法（两轮）**

1. 第一轮（`2579535a`）：上游改为**运行时环境变量**注入。镜像不再含任何环境信息，
   启动时由 `/docker-entrypoint.d/00-resolver.sh` 读 `API_UPSTREAM` / `MSG_UPSTREAM`，
   白名单 `envsubst` 渲染 `/opt/nginx/default.conf.template` → `/etc/nginx/conf.d/default.conf`，
   再从 `/etc/resolv.conf` 生成 resolver，最后 `nginx -t`。
   **任一步失败 `exit 1`**：宁可容器起不来（日志有中文原因），也不要「Running 但全站 502」。
2. 模板内同时硬拦：出现 `svc.cluster.local` 直接拒绝启动；两个上游填反也拒绝。

**回归判据**

- 启动日志出现 `[nginx-boot] resolver -> ...` 与 `[nginx-boot] API_UPSTREAM = ...` 两行；
- `grep -n 'set \$api_upstream' /etc/nginx/conf.d/default.conf` 的值等于控制台环境变量；
- `wget -qS -O /dev/null --post-data='{}' --header='Content-Type: application/json' http://127.0.0.1:8080/api/v1/auth/login` 不再 502。

**关键认知（写进模板注释）**：微信云托管服务间通信只有两条路——
① 控制台「服务设置 → 内网访问」**分配的「内网域名」**（形如 `xxxxx.<region>.internal-run.tcloudbase.com`，
开启或重新部署才分配、随发布可能变化，必须**复制**不能拼）；
② 公网域名 `https://<服务>-<envid>.sh.run.tcloudbase.com`。
内网写法必须带端口（8081/8090）且是 `http://`；公网是 `https://` 且不带端口。

### 3.2 故障②：登录 403，body 是纯文本 `Invalid CORS request`

**现象**：502 解决后点登录，`POST /api/v1/auth/login` 返回 HTTP 403，
`response.data` 是字符串 `Invalid CORS request`；前端提示退化成「无权限访问该资源」。

**误判路径**

| 怀疑对象 | 检查 | 结果 |
|---|---|---|
| 权限声明 / AuthzRules | 查 `/auth/login` 是否被要求角色 | 是白名单路径，不该 403 |
| 租户编码 | 查 `sys_tenant` 与前端默认 `tCode` | 有干扰项（保留字 `platform`、默认 `default`），但**不是本次** |
| 账号密码 | 换账号重试 | 无效，说明不经过业务 |
| URL 拼接（`/api/api/v1/...`） | 看 Request URL | 正常 |
| ★ response body 的**格式** | 纯文本 vs JSON | **决定性**：纯文本说明请求被框架层拦下，根本没进 Controller |

**根因（三层叠加，缺一不报）**

1. 浏览器对**同源 POST** 也会自动带 `Origin: https://frontend-<envid>...`（规范行为，前端没有写错）；
2. nginx 模板**故意不透传 Host**（云托管靠 Host/SNI 路由，传前端自己的 `$host` 会 `INVALID_HOST`），
   于是后端 `request.getServerName()` 拿到的是 `api-<envid>...`；
3. Spring 的 `CorsUtils.isCorsRequest()` 用 `Origin` 与 `getServerName()` 比较 → 两个域名不同 → **判为跨域**；
   而 `application-cloud.properties` 里 `app.cors.allowed-origin-patterns=${APP_CORS_ORIGIN_PATTERNS:}`
   **云端默认为空**，`CorsConfig` 又是 `registerCorsConfiguration("/**")` → `DefaultCorsProcessor` 直接拒绝。

**修法（两条，可并存）**

- **A 应急、不重建**：给 **api** 服务加环境变量
  `APP_CORS_ORIGIN_PATTERNS=https://frontend-<envid>.sh.run.tcloudbase.com`，重启实例（多个源用英文逗号，支持通配）。
- **B 根治（已进模板）**：`cloudBased/frontend/default.conf.template:112` server 级加
  ```nginx
  proxy_set_header Origin "";
  ```
  删掉浏览器带来的 `Origin` 后，`CorsUtils.isCorsRequest()` 判定为"非跨域"，直接进业务。
  语义上更正确：浏览器 ↔ nginx 本来就是同源，是 nginx → 上游这一跳换了 Host。
  已全仓 `grep` 确认**后端没有任何代码读 `Origin`**，删头安全。
  ⚠️ 前提是**同源反代**部署；将来若前端直连后端公网域名（真跨域），必须删掉这行改配 A。

**回归判据**：`auth/login` 返回 200 且 body 是 JSON（`{"code":200,...}`）。
若仍 403 但 body 变成 JSON，说明 CORS 已过，问题回到业务侧（那时才轮到租户编码/账号密码）。

**关键认知**：`Invalid CORS request` 是 Spring 的**固定文案**，见到它就别再往鉴权方向找。
"同源反代 + 上游换域名"这个组合下 Host 与 Origin 必然不一致，是本类误判的高发场景。

### 3.3 故障③：登录到 api 后 500，`Unsupported character encoding 'utf8mb4'`

**现象**：登录请求已到 api，日志 `Caused by: java.sql.SQLException: Unsupported character encoding 'utf8mb4'`。
容器活着、健康检查通过，**只有查库的接口挂**。

**误判路径**：几乎没有——异常信息足够直白。真正花时间的是"为什么本地一直好好的"。

**根因**：`api/src/main/resources/application-cloud.properties` 的 JDBC URL 写了
`characterEncoding=utf8mb4`。

`characterEncoding` 是 **Connector/J 的参数，只认 Java 字符集名**；`utf8mb4` 是 **MySQL 的字符集名**，
Java 里不存在这个名字。本地 `application.properties` 写的是 `utf8`（Java 的合法别名）→ **本机永远复现不了**。
这是典型的"双份配置"陷阱：本地档对、cloud 档错，只有上云才暴露。

**证据（用 fat jar 里的真驱动 + 本机真库跑，不是推断）**

从 `booking-api-2.2.0.jar` 取出 `BOOT-INF/lib/mysql-connector-j-8.0.33.jar`，连本机 MySQL 8.4.11：

| `characterEncoding` | 结果 |
|---|---|
| `utf8mb4` | ❌ `UnsupportedEncodingException: utf8mb4` |
| `UTF-8` | ✅ 连接成功 |
| `utf8` | ✅ 连接成功（Java 别名） |

另：`Charset.isSupported("utf8mb4") == false`，`"utf8"` / `"UTF-8"` 均为 `true`。

**修法**：4 处统一改成 `characterEncoding=UTF-8`——
`api/src/main/resources/application-cloud.properties`（唯一进 jar 的）、
`cloudBased/api/application-cloud.properties`、`cloudBased/message-service/application-cloud.properties`（副本，防误用）、
`doc-develop/A00微信云托管部署操作手册-预约系统-2026-10-14.md`（示例 + 踩坑说明）。
其余参数（`useUnicode` / `serverTimezone=Asia/Shanghai` / `useSSL=false` / `allowPublicKeyRetrieval`）一个没动。

**部署要点**：必须 `mvn package`，**`compile` 不会替换 jar 里的 resources**。
实测旧 jar（11-07 23:05）内嵌值仍是 `utf8mb4`。

**回归判据**：api 日志不再出现 `Unsupported character encoding`，且能看到 HikariPool 启动成功；
浏览器登录返回 200 + `{"code":200,...}`。

### 3.4 故障④：`logs/spring-boot-app.log` 不再生成（哑故障）

**现象**：日志页空白。用户反馈"这几天的修改中取消了日志文件"。

**澄清一个常见误解**：这个文件由**后端 api 的 logback** 产生，前端只有 `logBrowser.html` 在读它。
所以恢复点在 api 侧，不在前端。

**定位手段（一步到位）**

```sh
git log -S "RollingFileAppender" -- api/src/main/resources/logback-spring.xml
```

`-S` 追踪"该字符串的增删"，比逐个 `git show` 翻文件快得多。

**根因**：`7ab34fa0`（11-07 15:47，标题「云部署报错——调整，**无效**」）
把 `CONSOLE + FILE` 双 appender 换成 `springProfile prod,eks / dev` 两档，**两档都只挂 CONSOLE**；
`efc7a9b5` 又简化成单一 root console。基线 `a4515e79` 才是完整版。

注意这个提交**只改了 logback 一个文件**（+18/−31），跟"云部署报错"毫无关系——
**标题误导 + 顺手删功能**，制造了一个 32 小时后才被发现的哑故障（11-07 15:47 删 → 11-08 23:31 发现）。

**修法**：按 `a4515e79` 原样还原：

| 项 | 值 |
|---|---|
| 目录 | `LOG_DIR = ${LOG_PATH:-./logs}` |
| 当前文件 | `${LOG_DIR}/spring-boot-app.log` |
| 轮转 | 按日期 + 单文件 50MB 按 `%i` 切分，gz 归档到 `archived/` |
| 保留 | maxHistory 30 天 / totalSizeCap 5GB / cleanHistoryOnStart |
| pattern | `时间 [%X{tenantId}] level logger : msg`，UTF-8 |
| root | CONSOLE + FILE 双挂 |

另补 `<logger name="com.reservation.mapper" / "org.apache.ibatis" = ERROR>`：SQL 打印含手机号/邮箱，属合规线，不放开的第二道保险。
`[%X{tenantId}]` 不是摆设——`TenantInterceptor:61` 确实有 `MDC.put("tenantId", ...)`。

**证据（用真 logback 加载配置，不是看配置猜）**：从 fat jar 取 `logback-classic 1.5.11` + `core` + `slf4j 2.0.16`，
用 `JoranConfigurator` 加载本配置并写日志：

```

2026-11-08T23:33:35.249+08:00  []  WARN  probe : 无租户上下文的一条
```

文件正常生成、时间戳带 `+08:00`、中文无乱码、`[7]` 证明 MDC 生效，logback 内部 status **0 个 ERROR**。

**回归判据**：登录一次后 `tail -5 logs/spring-boot-app.log` 有内容，且每行带租户 ID。

**两个云环境事实**：① 文件日志**不进云平台日志面板**（面板只收 stdout）；② 容器重启即还原。

### 3.5 故障⑤：日志页 404，请求路径少 `/v1`

**现象**：logger 恢复了，日志页仍读不到。F12 里 `/api/logs/tail` 报 404。

**根因（两层）**

1. 前端 `logBrowser.js` 请求 `/api/logs/{tail,date,search,dates}`，后端 `logController` 是
   `@RequestMapping("/api/v1/logs")`，nginx 也只有 `location /api/v1/`（模板 214 行）→
   `/api/logs/...` 落到 `location /` → `try_files` → 404；
2. **为什么没人补前缀**：`utility_request.js:384` 的 `service` 虽然设了 `baseURL`，
   但**该文件第 27 行注释已写明：axios 对以 `/` 开头的 url 会忽略 baseURL**。
   所以写 `/api/logs/x` 就是原样发出，永远不会变成 `/api/v1/logs/x`。

**修法**

- `frontend/js/logBrowser.js`：4 处补 `/v1`，并在 `loadDates()` 上方留注释（"必须带 /v1 + 为何不会自动补"），防止再被改回去；
- `frontend/logBrowser.html`：注释纠错——原写"后端 `/api/logs/*` 只要求认证、不做角色鉴权"，
  实际 `AuthzRules:291-294` 已把四条登记为 `PLATFORM_OR_TENANT_ADMIN`，非管理员会 403；
- 全量重建 dist 并同步 `cloudBased/frontend/dist`（镜像 `COPY dist`）。

**回归判据**：日志页能出内容；用普通租户用户访问时返回 **403 + JSON**（这是设计如此，不是故障）。

### 3.6 附带问题：dist 每构建一次，就把部署资产发到公网一次

**现象**：`frontend/dist/` 里长期混着 `Dockerfile`、`nginx/default.conf.template`、
`docker-entrypoint.d/40-render-nginx-conf.sh`、`container.config.json`、`legal.html.orig`、`readme.md`。
`dist/` 是要发到公网的静态站点——**任何人 GET 一下就能拿到内部上游地址模板与端口规格**。

**根因**：`frontend/build.js` 的 `copyAssets()` 用黑名单挡非站点文件，三处漏洞：

1. 名单里没有 `Dockerfile`、`container.config.json`；
2. **目录没参与判断**：`path.dirname(rel) === '.'` 只匹配根级文件，`nginx/`、`docker-entrypoint.d/` 下的文件全部复制；
3. **大小写坑**：名单写的是 `'README.md'`，实际文件名是 `readme.md`，`Set.has()` 区分大小写 → **这条规则从未生效**。

**为什么之前"清理过又回来了"**：11-08 清的是 `cloudBased/frontend/dist`（产物副本），
源目录 `frontend/` 里的文件还在 → 下次构建原样复活。**清产物治不了根**。

**修法（分两步）**

- 第一步（构建层兜底）：`SKIP_ROOT` 补 `Dockerfile` / `container.config.json` / `readme.md`，
  新增 `SKIP_ROOT_DIRS = {nginx, docker-entrypoint.d}`（按 `rel.split(/[\\/]/)[0]` 判顶层目录），
  新增 `/\.orig$/i` 排除备份文件；
- 第二步（源头清理，2026-11-09）：直接删掉源目录那 5 项部署资产，`readme.md` 移到 `doc-develop/前端程序说明.md`。
  **黑名单故意保留作防回归**——谁再把部署资产放回 `frontend/`，也不会静默随 dist 上线。

**回归判据**：`node build.js` 后 `ls dist` 只有站点文件（16 个 html + `css/ images/ js/` + `favicon.ico` + `build-info.json`）；
`[collect] 清理孤儿 0 文件` 表明 deploy/dist 也无残留。

> 顺带一提 `efc7a9b5` 的一个结构问题：它在**同一个提交里**既建了 `cloudBased/frontend/{Dockerfile,模板,脚本,container.config.json}`，
> 又在 `frontend/` 下建了同名的一套（Gen3 方案）。后者从未被任何构建脚本使用，
> 却因为 `copyAssets()` 一直往 dist 里塞——**两套并行方案并存，是这类污染的温床**。

## 四、为什么这轮排查慢（流程反思）

技术问题都不难，慢在**信息组织方式**。五条：

1. **故障串行暴露，无法并行定位**。502 掩盖 403，403 掩盖 500，500 掩盖日志问题。
   每次只看到"当前层"。对策：**先按层次分开验证**（网关层 / 反代层 / 应用层 / 数据层各一条命令），
   而不是顺着第一个报错往下摸。

2. **"Running 但全站 502"是最坏的失败形态**。容器活着、健康检查过、平台显示绿色，实际全站不可用。
   对策：启动脚本**失败即 `exit 1`**，让"配置错"表现成"起不来"，问题在日志里自陈，而不是靠人猜。

3. **提交标题与内容不符**。11-07 四次提交标题为「调整，无效」「部署云托管」「frontend部署，502 错」「--to be test」，
   既没说改了什么，也没说哪套方案在生效。`7ab34fa0` 更是"标题说部署、内容只有 logback、顺手删了文件日志"。
   对策：提交信息写"改了什么 + 为什么 + 验证过什么"；提交前 `git diff` 过一遍。

4. **多套部署资产并存**。历史上有三套前端镜像定义（`deploy/nginx/cloudbase-web` 听 80、
   `cloudBased/frontend` 听 8080、`frontend/` 下的 Gen3 那套），选错文件就是"全站 502 换一种姿势"。
   对策：**只留一套**，其余删除（已完成）。

5. **双份配置导致"本机永不复现"**。`application.properties`（本地）写 `utf8` 正确，
   `application-cloud.properties`（云）写 `utf8mb4` 错误。本地跑一万次也不会报。
   对策：cloud 档的每个参数都要问一句"本地档写的是什么，为什么不一样"。

## 五、定案架构（勿再退回旧写法）

```
浏览器 ──https──> frontend (nginx:alpine, listen 8080)
                    │ 启动：/docker-entrypoint.d/00-resolver.sh
                    │   读 API_UPSTREAM / MSG_UPSTREAM
                    │   → 白名单 envsubst 渲染 /opt/nginx/default.conf.template
                    │   → /etc/nginx/conf.d/default.conf
                    │   → 从 /etc/resolv.conf 生成 00-resolver.conf
                    │   → 回显生效上游 → nginx -t → 失败 exit 1
                    ├─ /api/v1/{message,sse,sensitive,users/} ──> $MSG_UPSTREAM (8090)
                    └─ 其余 /api/v1/* ────────────────────────> $API_UPSTREAM (8081)
```

六条硬约束：

| # | 约束 | 违反的后果 |
|---|---|---|
| 1 | 上游地址**不进镜像**，只走控制台环境变量 | 换环境/域名变化必须重建镜像，且容易写错（本轮的 502） |
| 2 | 端口 **8080 三处对齐**：`EXPOSE` / `listen` / `containerPort` | 全站 502，且与"配置错"症状无法区分 |
| 3 | 变量形式 `proxy_pass` **必须有 `resolver`** | 每请求 502（`no resolver defined`），而 `nginx -t` **查不出来** |
| 4 | `COPY dist` 后清理部署文件；`build.js` 黑名单同时兜底 | 内部上游模板、端口规格随静态站点公开 |
| 5 | 不透传 `Host`，同时 `Origin ""` 置空 | 前者 `INVALID_HOST`/落错服务；后者 CORS 误判 403 |
| 6 | cloud 档 JDBC `characterEncoding=UTF-8`；logback 双 appender | 500 全库不可用；日志页空白 |

`cloudBased/frontend/` 现在只剩 4 份文件 + `dist/`：
`Dockerfile` / `container.config.json` / `default.conf.template` / `resolver-entrypoint.sh`。

## 六、15 分钟定位法（下次照此自查）

### 6.1 按现象分派

| 现象 | 层次 | 先查什么 |
|---|---|---|
| **连 `/index.html` 都 502** | 网关 ↔ 容器 | `containerPort` 与 `listen` 是否一致；容器是否 crash-loop（`nginx -t` 失败的典型是启动即退出） |
| **静态页 200、`/api/v1/*` 全 502** | nginx ↔ 上游 | ① `00-resolver.conf` 是否存在 ② 上游域名能否解析 ③ 端口能否连通 |
| 偶发 502 | 运行时 | 冷启动/扩容窗口（`minNum:1` 可缓解）。注意 **429 是限流、504 是读超时**，都不是 502 |
| **403 + 纯文本 `Invalid CORS request`** | Spring CORS | 直接按 3.2 处理，别查权限 |
| **403 + JSON** | 授权层 | 查 `AuthzRules` 与账号角色 |
| **500 + SQLException** | 应用/DB | 先看 `Caused by:`，再看 cloud 档配置与本地档差异 |
| 接口 404 | 路由 | 比对前端请求 path 与 `@RequestMapping`、nginx `location`（**大概率漏了 `/api/v1`**） |

### 6.2 容器内命令（`nginx:alpine` 没有 curl，只有 busybox 的 `wget`/`nc`/`nslookup`）

```sh
# 1) 静态页：502 → 网关层；200 → 继续
wget -qS -O /dev/null http://127.0.0.1:8080/index.html 2>&1 | head -3

# 2) resolver 是否生成（不存在 = 接口全 502 的头号根因）
cat /etc/nginx/conf.d/00-resolver.conf; echo ---; cat /etc/resolv.conf

# 3) 上游域名能否解析（NXDOMAIN 表示"这个名字不存在"，不是网络不通）
nslookup <内网域名或公网域名>

# 4) 端口连通性
nc -vz -w 3 <上游域名> <端口>

# 5) 上游是否真答（区分"连通但 404"与"根本连不上"）
wget -qO- --timeout=5 http://<上游>/api/v1/system/info

# 6) 实际生效的配置
netstat -tlnp | grep -E '8080|80'
grep -nE 'listen|proxy_pass|set \$' /etc/nginx/conf.d/default.conf
env | grep -i upstream
```

### 6.3 日志关键字对照（云托管「日志」面板，`customLogs: stdout`）

| 关键字 | 含义 | 动作 |
|---|---|---|
| `no resolver defined to resolve` | resolver 没生成 | 查 `/etc/resolv.conf` 与启动脚本 |
| `host not found in upstream` | 域名写错（envid/服务名不符）或 DNS 不解析 | 从控制台复制内网域名 |
| `connect() failed (111: Connection refused)` | 上游端口不对 | 对齐容器端口 |
| `connect() timed out` / `113 no route` | 内网不通（未开内网访问/跨环境） | 开内网访问，或改公网兜底 |
| `Invalid CORS request` | Spring CORS 拒绝 | 见 3.2 |
| `Unsupported character encoding` | JDBC 参数名非法 | 见 3.3 |
| `[nginx-boot]` 开头的中文失败原因 | 自建启动校验拦截 | 按提示改环境变量，**这是好现象** |

> `WebShell` 里的修改**不持久化**（容器重启即还原），只用来诊断。
> `/var/log/nginx/error.log` 在官方镜像里是软链到 `/dev/stderr`，`cat` 会卡住——错误日志去控制台面板看。

## 七、遗留与后续

| # | 项 | 影响 | 建议 |
|---|---|---|---|
| 1 | `logController.LOG_DIR` 硬编码 `./logs`，不认 `LOG_PATH` | 云托管不设 `LOG_PATH` 时两边都是 `/app/logs`，恰好一致；服务器部署若设了 `LOG_PATH`，日志页会读空目录 | 让 Controller 也读 `LOG_PATH`，与 logback 同源 |
| 2 | api jar 需重新 `mvn package` | `characterEncoding` 与 `logback` 两处修复都在 jar 内 resources，`compile` 不生效 | 一次打包即可（两处改动都在同一个 jar 里） |
| 3 | 公网兜底方案的副作用 | 上游走外网出口，`X-Forwarded-For` 由云托管网关追加，`ClientIpResolver` 只采信"可信代理"那一跳 → 风控取到的 IP 可能变化 | 若之后发现登录滑块/IP 风控行为异常，先想到这个；长期应切内网域名 |
