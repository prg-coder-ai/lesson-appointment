## 一、动作 25：状态枚举「前后端共享」不可实施

### 1.1 设计问题

原文"统一状态枚举为单一常量源 + 单一文案映射（前后端共享）"有两个缺陷：

**缺陷 A —「共享」这个动作无法执行。**
Java 与 JavaScript 无法共享同一份源码。可行的形态只有三种，各有代价：

| 形态 | 做法 | 代价 |
|---|---|---|
| 双源+ 守卫 | 两端各写一份，靠静态守卫比对字面量 | 需人工同步，守卫要维护 |
| 单源 + 代码生成 | 一份 JSON → 生成 Java 常量类 + JS 模块 | 需引入生成步骤，接进 build |
| 后端下发 | 前端不写枚举，运行时拉`/meta/statuses` | 多一次请求 + 离线不可用 |

报告没指定选哪种，等于把最关键的架构决策留空了。而报告的措辞（"前后端共享"）会让实施者误以为存在某个现成机制。

**缺陷 B — 目标其实已经部分达成，报告没看见。**
实测现状：

```
后端：common/BookingStatus.java      common/AppointmentStatus.java
前端：shared/domain/bookingState.js  shared/domain/appointmentState.js
      shared/domain/term.js  datetime.js  errorCode.js  mask.js  refundRule.js
```

`shared/domain/` 已是前端侧单一权威源，`test-shared-domain.mjs` 已有断言。真正缺的不是"统一"，而是**后端与前端两源之间的一致性校验**——报告没提这一层。

**缺陷 C — 与已拍板事实冲突。**
记忆里明确记着：`bookingStatusText(status,{profile:'web'|'default'})` 的 Web/小程序文案差异（「预定待确认」vs「待确认」）是**用户已拍板的差异，不是缺陷**。若按原文"单一文案映射"去合并，会把这个决策推翻。

### 1.2 修订方案

**动作 25 改写为：**

> **25-a.** 在 `shared/domain/status-contract.json` 定义状态契约（状态码 + 语义 + 前缀规则），作为**跨端比对的中间层**，不直接生成代码。
> **25-b.** 后端 `BookingStatus` / `AppointmentStatus` 与前端 `bookingState.js` / `appointmentState.js` 各自保留（形态选"双源 + 守卫"，代价最低、可增量落地），但新增 `tools/check-status-contract-guard.mjs` 强制三方字面量一致。
> **25-c.** 文案映射**保持参数化**（`profile: 'web' | 'miniprogram'`），明确写入守卫白名单：两端文案**允许不同**，但**差异必须是已登记项**，新增差异需登记后才放行。

守卫判定四条：

| # | 判定 | 反向变异 |
|---|---|---|
| ① | 后端常量集合 ≡ JSON 契约 ≡ 前端导出集合（三方等价） | 后端加一个状态 → 红 |
| ② | 课次状态前缀规则一致（`s-`学生 / `t-`教师 / 无前缀整单） | 前端删 `t-` 分支 → 红 |
| ③ | 两端文案差异必须在 JSON `wordingDiff` 中登记 | 私自改一处文案 → 红 |
| ④ | 已占用前缀不得挪作他用（`t-cancelling`/`t-cancelled` 属教师改期） | 把整单取消改成 `t-` → 红 |

**不引入代码生成**。理由：现有 4 个状态文件规模都不大（`AppointmentStatus` 约 30 个值），生成步骤会引入"改了 JSON 忘记重新生成"的新漂移面，与本项目"守卫优先于流程"的既有取向不符。

## 二、动作 26：日期契约 —— 方向对，但漏了两处

### 2.1 实测现状

```
java.util.Date使用者：18 个文件（含 Booking.java / Course.java 等对外实体）
LocalDateTime 使用者：      53 个文件
@JsonFormat 注解：          0 处
spring.jackson 配置：       仅 1 行 —— default-property-inclusion=non_null
new ObjectMapper()：       2 处（WeChatService、TeacherPublishedProfileService）
```

### 2.2 遗漏隐患 A：两处 `new ObjectMapper()` 绕过全局配置

`WeChatService:33` 与 `TeacherPublishedProfileService:36` 各自new了一个裸 `ObjectMapper`。一旦按原方案加全局日期配置，这两处的序列化行为**不会跟着变**，形成"同一份数据、两种 JSON 形态"。这是"补全局配置"这个动作本身带的坑，报告没提。

### 2.3 遗漏隐患 B：前端已经假设后端返ISO 带 Z

`shared/domain/datetime.js:119` 已写明：

```js
// 关键：裸串必须补 Z，否则 new Date() 会按浏览器本地时区解读，偏移一次。
if (!/([Zz]|[+-]\d{2}:?\d{2})$/.test(normalized)) normalized += 'Z';
```

前端**已经按"后端返带时区标识的 ISO 串"设计**。而 `java.util.Date` 在 Spring Boot 默认（`WRITE_DATES_AS_TIMESTAMPS=false`）下序列化的是 **不带时区的 ISO 串**（`2026-10-09T21:31:22.000+00:00` 视 Jackson 版本，实践中常见裸 `2026-10-09T21:31:22.000`）。

这意味着：**只要某个 `Date` 字段漏了时区标识，前端就会自动补 Z 把它当UTC 解读**——若后端本意是本地时间，就是一次静默的时间偏移。这正是第 5 批时区治理刚刚消灭掉的那类 bug，**从日期契约这条路径又开了个口子**。

报告原文给的二选一（"统一 Date→LocalDateTime **或**统一 ISO 格式"）没有意识到这两者对前端的意义完全不同。

### 2.4 修订方案

**动作 26 改写为三步，顺序不可颠倒：**

> **26-a. 先立契约（不动代码）**：明确"后端对外所有时间字段一律为 **UTC 的 ISO-8601 带 Z 串**"。这与第 5 批已定的口径（appointment 起= UTC 唯一真相源，展示按用户时区）完全一致，**不新增第二套口径**。
> **26-b. 消灭裸 `new ObjectMapper()`**：两处改为注入 Spring 容器里的 `ObjectMapper`，使全局配置真正生效。
> **26-c. 再补全局配置**：新增 `JacksonConfig`（`Jackson2ObjectMapperBuilderCustomizer`）统一 `Date`/`LocalDateTime` 序列化；**同步删除** `default-property-inclusion=non_null`（原因见动作 28，二者耦合）。

**关键：26-a 必须先做，且必须与前端口径逐字对齐。** 若不先定契约就改配置，很可能把 `Date` 序列化成前端无法解析的形态。

对 18 个 `Date` 使用者的处置**分批**，不在本批一次改完：

| 优先级 | 范围 | 处置 |
|---|---|---|
| P0 | 对外响应实体（`Booking`、`Course` 等被接口直接返回的） | 改 `LocalDateTime`（UTC） |
| P1 | 入参 DTO（`BookingCreateDTO`、`ScheduleCreateDTO` 等） | 改 `LocalDateTime`，入参须 ISO 带 T |
| P2 | 内部/历史（`AuditLog`、`JwtUtil`、审计切面） | 保留 `Date`，登记豁免 |

⚠️ **口径不得改动前端记忆里的铁律**：入参 `LocalDateTime` 必须是 ISO-8601 带 `T`（现有铁律），这条不变。

## 四、动作 28：唯一真实且最严重 —— 保留并加强

### 4.1 实测：范围比报告更大

报告 P2-8 点名 9 处，实测**全仓 10 处**：

```
BookingController.java     7 处   （43, 52, 124, 138 用 fail(null)；153, 167, 229 用 fail(0)）
ScheduleController.java    3 处   （127, 272, 290 用 fail(0)）
```

message-service 侧干净（`Result.fail(0/null)` 命中 0 处）。

### 4.2 为什么这是真 bug（不只是"不优雅"）

链路事实：

```
① 客户端判定：shared/apiPaths.js unwrapResult() → res.code === 200 才return data
② 后端序列化：spring.jackson.default-property-inclusion=non_null（application.properties:34）
③ 后果：code=null → Jackson 认为 null 值 → 整个 code 字段不出现在 JSON 里
```

也就是说失败响应实际长这样：

```json
{"message":"xxx失败"}        ← 没有 code 字段
```

`unwrapResult` 走 else 分支抛错，**功能上碰巧不出错**。但：

- `err.code = res && res.code` → `undefined`，任何按 `err.code` 做分支的逻辑都落到 falsy 侧；
- 任何日志/上报按`code` 聚合的维度失效；
- **`code=0` 那5 处更隐蔽**：`0` 不是 null，会正常输出 `"code":0`，但它既不是合法成功码也不是标准错误码，属于"看起来有契约、实则无意义"。

**报告的定性是对的**（"客户端判定依赖 `res.code === 200`"），但没说清 HTTP 状态码也是 200 —— 补上这一层才知道严重性。

### 4.3 修订方案

> **28-a.** 修 10 处调用点：`fail(null,…)` → 按异常语义给`400`（`IllegalArgumentException`）或 `500`（`RuntimeException`）；`fail(0,…)` → 按语义给 `400`/`500`/`409`。
> **28-b.** 把 `Result.code` 从 `Integer` 改为 `int`（不可空），从类型上让 `null`/`0` 无法编译通过。**这是根本修法**——让守卫不需要"检查"而是"编译期保证"。
> **28-c.** `Result.fail` 增加断言：code 必须 ∈ {200,400,401,403,404,409,500}，越界直接抛异常（开发期即暴露）。
> **28-d.** **删除 `default-property-inclusion=non_null`**。它与本动作直接耦合：即使 28-b 做完，只要该配置还在，任何未来新增的可空字段都会重演"字段凭空消失"。前端已有 `res.message || res.msg` 的兜底读取（见 `unwrapResult`），不依赖该配置。
> **28-e.** 新增 `tools/check-result-contract-guard.mjs`：扫全仓禁止 `Result.fail(null` / `Result.fail(0`，且校验 `code` 为primitive `int`。

⚠️ **28-b 的连带影响需提前告知**：`Result.code` 改 `int` 后，若有代码依赖 `getCode()` 返回 `null` 做判断，会编译失败。这是**期望行为**（那类代码本就是错的），但要一次改干净。

## 五、动作 29（新增）：HTTP 状态码与 body.code 脱钩

### 5.1 事实

```
全仓 Controller 用 ResponseEntity 的：3 处
SecurityConfig 手写 JSON 的：2 处（且只有这两处正确设置了 HTTP 状态）
  authenticationEntryPoint → setStatus(401) + body.code=401
  accessDeniedHandler      → setStatus(403) + body.code=403
其余全部：HTTP 恒 200，失败只体现在 body.code
```

### 5.2 为什么必须一起改

这是报告完全没提、但与动作 28 同源的问题：

| 层面 | 后果 |
|---|---|
| 网关 / Nginx | 无法按状态码分流、限流、重试；只能解body 才能判断 |
| 监控告警 | 第 5 批刚建的 `healthcheck.sh` 与 Actuator 探针**拿不到失败信号**——业务错误率永远是 0 |
| 浏览器网络面板 | 全部 200，肉眼无法定位失败 |
| 客户端 | 断网、超时、5xx 这类**没有 body** 的情况，`res.code === 200` 之外还要额外判HTTP，易漏 |

也就是说：动作 28 只把"body 里的 code 变规范"，但**HTTP 层依然全是 200**，第 5 批建的可观测性拿到的仍是假数据。

### 5.3 修订方案

> **29-a.** **先不全局改 HTTP 状态码**（改动面过大、风险集中），改为在`Result` 中显式建模，由统一出口处理。
> **29-b.** 新增 `@RestControllerAdvice` 的响应出口：按 `Result.code` 映射 HTTP 状态（200/400/401/403/404/409/500），保证 **body.code 与 HTTP 状态永远一致**。
> **29-c.** 与 `SecurityConfig` 已有的两处对齐（它们已是正确形态，作为口径基准）。
> **29-d.** 守卫校验：`SecurityConfig` 两处手工JSON 的 code 必须与其 HTTP 状态一致，防止后续改出分叉。

⚠️ **29-b 的前置条件是 28-b**：`code` 必须是 primitive `int`，否则出口无法可靠判定。因此 **29 依赖 28，不可并行、不可颠倒**。

## 九、需要拍板的两个决策点

### 决策点 1：状态契约的形态

| 选项 | 代价 | 我的建议 |
|---|---|---|
| **A. 双源 + 守卫** | 需人工同步两边 | ✅ **建议**。规模小、增量、可增量落地 |
| B. JSON 契约 + 代码生成 | 引入生成步骤与新漂移面 | 不建议 |
| C. 后端运行时下发 | 多一次请求、离线不可用 | 不建议 |

### 决策点 2：`Result.code` 改 `int` 的连带影响—— **已实测，无风险，建议直接改**

实测结论（`grep -rn "getCode()"` 全仓）：

- **`Result.getCode()` 在 api 侧零处被读取**。命中的 `getCode()` 全属于别的类：`IndustryController` 的行业编码 `ind.getCode()`（String）、`authController` 的微信 `dto.getCode()`、`MessageBizException.getCode()`（已是 `int`）。
- **零处存在 `getCode() == null` 这类可空判断**。

因此 `Integer` → `int` **不会造成任何编译失败**，且能让 `fail(null)` / `fail(0)` 从"运行时隐患"变成"编译期不可能"。

**建议：直接采用根本修法（改 `int`），不退到保守方案。** 保守方案（保留 `Integer` + 运行时断言 + 守卫）会让守卫成为唯一防线——而本项目已有足够教训说明"靠守卫盯着"不如"让类型系统直接禁掉"（`check-ddl-align` 守卫本可以更严，但 `camelToUnderline` 的差异正是靠"宁可误报"才没漏报）。

⚠️ 唯一需注意的连带点：`@Data` 生成的 `setCode(Integer)` 会变成 `setCode(int)`，若有 XML/JSON 反序列化配置依赖 setter 的可空性，需检查（实测 `Result` 无 XML 映射，应无影响）。
