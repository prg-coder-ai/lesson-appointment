# 排期与预订的时间态处理方案（过时 / 进行中 / 待完成）

> 生成时间：2026-10-11 00:47　|　定位：设计约定（含落地改动点清单），供评审后分批实施

## 一、现有模型盘点（方案的事实基础）

| 实体 | 时间属性 | 状态属性 | 说明 |
|---|---|---|---|
| 排期 `CourseSchedule` | `startTime`（**本地墙钟**）+ `timeZone`（时区列）；`endTime` 暗含重复结束日期；`repeatType/Interval/Days` 重复规则 | `pending / active / inactive / frozen`（**业务状态，不含时间态**） | 一个排期按重复规则展开成多次课 |
| 预订 `Booking`（整单） | **无自身时间**——时间完全来自所挂排期 | `none / booking / waiting / booked / cancelling / cancelled / completed` | `booked` 才由 BookingAppointmentSyncService 生成课次 |
| 课次 `Appointment` | `appointment_datetime`（**UTC 唯一真相源**） | `active / noted1/2 / cancelling / t-cancelling / cancelled / t-cancelled / reject / completed / frozen` | 一次具体的上课 |

关键观察：**排期和预订的表里都没有"过时/进行中/已完成"这类时间态字段**——现有 `status` 全部是业务状态（人工/流程驱动），时间态目前无人判定，这正是本方案要补的空档。

## 二、核心原则：时间态一律「运行时推导」，不落库

**时间态（UPCOMING 待开始 / ONGOING 进行中 / FINISHED 已结束）是派生态，不是存储态。**

理由（常规规则 + 本项目既有哲学）：

1. 落库就必须靠定时任务刷状态 → 定时任务延迟/停摆期间数据是错的；运行时推导永远正确；
2. 服务端时钟是唯一权威——项目已有先例：退改三档（free/partial/none）就是服务端按 UTC 即时算档，不做物化；
3. 展示态与操作闸分离：**前端按推导态控制按钮显隐（体验），后端在写路径按推导态硬校验（闸门）**。与授权守卫同一教训：只藏按钮不校验，等于没闸。

## 三、时间态判定规则（单一实现入口）

新增一个统一的推导入口（建议 `TimePhaseService` 或并入 `ScheduleGenerator` 旁的工具类，**只此一处**，对齐"时间转换只经三入口"的收口哲学）：

```
输入：课次 UTC 时间 / 排期（墙钟 + timeZone 展开成 UTC 课次序列）
基准：服务器 now（UTC）

FINISHED ：now ≥ 课次结束时间（开始时间 + 默认课时长）
ONGOING  ：课次开始时间 ≤ now < 结束时间
UPCOMING ：now < 课次开始时间

可选配置「开始宽限期 G」（默认 0，可按租户配 0~10 分钟）：
ONGOING 的判定起点放宽为 开始时间 + G——即开课 G 分钟内仍按"待开始"处理，
给手滑的学生一个补救窗口。默认 0 = 严格口径，行业约课平台两种都有。
```

时区红线：**所有比较在 UTC 完成**。排期墙钟必须经 ScheduleGenerator 换算成 UTC 再比；严禁用浏览器本地时间判状态（`utcToZoned` 只许用于展示文案）。

## 四、排期的时间态规则

| 时间态 | 展示 | 可预订？ |
|---|---|---|
| 待开始（首课次未到）且 `status=active` 且未满 | 正常展示 | ✅ |
| 已开始（首课次进行中） | 展示但标记「进行中」 | ❌（剩余课次是否可订=业务决策，默认 ❌） |
| 已结束（重复结束日期已过，或末课次已完成） | **不展示给预订**（仅管理端/历史页可见） | ❌ |
| `status != active`（pending/inactive/frozen） | 不展示给学生预订，与管理端时间态无关 | ❌ |

**双闸实现**（缺一不可）：

1. **查询闸**：学生端排期浏览接口增加 `onlyBookable` 过滤——`status=active` 且 `末课次开始时间 > now` 且未满（`full` 标志/锁定读计数）；
2. **写入闸**：预订创建时后端校验所选课次 `now < 开始时间`（+可选提前停订阈值，如开课前 15 分钟停止预订），不满足返回 `fail(409, "该课次已开始或已结束，无法预订")`。

前端隐藏只是体验优化——直接调 API 必须被 409 挡住。

## 五、预订（整单）与课次的操作矩阵

### 预订整单（BookingController.updateStatus 路径）

| 预订状态 × 时间态（按其课次集合推导） | 允许操作 | 禁止 + 提示 |
|---|---|---|
| `booked`，全部课次待开始 | 取消预订（走退改三档提示卡）、候补相关操作 | — |
| `booked`，**存在进行中课次** | — | **❌ 取消预订** → `fail(409, "课程已开始，无法取消预订；单次课次请使用改期/请假")`（即你举的例子） |
| `booked`，全部课次已结束 | — | ❌ 一切变更；等待收口任务置 `completed` |
| `waiting` 候补，临近开课（< N 分钟）未转正 | 自动失效（定时任务），预扣资源释放、通知学生 | — |
| `cancelling`（取消待确认） | 管理员确认/驳回照常（审核的是历史申请） | 学生侧撤回仅限课次未开始 |

### 课次级（appointment，学生 t-/s- 与教师前缀同理）

| 时间态 | active 生效 | cancelling 待确认 | 已结束 |
|---|---|---|---|
| 待开始 | ✅ 请假/改期（改期目标必须也是未来课次；退改档位提示卡照旧） | ✅ 可撤回；管理员可确认 | — |
| **进行中** | ❌ 请假/改期 → `fail(409)`；仅允许签到类动作 | ❌ 变更冻结，管理员保留"课后补处理"特权 | — |
| 已结束 | ❌（结算窗口内教师可补标 `completed`，默认课后 24h） | ❌ | 只读，进入历史 |

## 六、补充：退费档位的时间基准 = 学生提交申请的时刻

**管理端确认退改（取消/改期）时，退费档位按学生提交申请那一刻的提前量判定，不按管理员的确认时刻重算。**

常规依据：

1. 公平性——学生提交申请即完成了自己能控制的全部动作，之后到管理员确认之间的等待时间是机构处理时长，不应由学生承担档位恶化的后果（例如学生提前 3 天提交（免责档），管理员第二天才确认，若按确认时刻算仍应按 3 天前的提交时刻判免责档）；
2. 防拖延双向锁定——对机构同样成立：申请提交即锁定档位，学生不能靠撤回重提刷新提前量，管理员也不能拖到档位对学生不利后"按规矩"少退；
3. 与既有机制的衔接——退改提示卡（`/refund-rule/hint`）目前按**请求时刻**即时算档，申请场景用它是准的；审核场景必须改读"提交时刻"的档位。

**实现口径（推荐快照落库，而非确认时倒推重算）**：

- 学生提交取消/改期申请（课次置 `cancelling` / `t-cancelling`）时，把**当时的档位判定结果**（level、refundPercent、minutesAhead、判定时刻）作为快照随申请落库（可加 `refund_snapshot` 列或独立小表）；
- 管理端审核弹窗读快照展示，"按下列档位登记退费"即为最终口径；
- 无快照的历史申请（存量数据）：按 `update_time`（申请落库时间）回补重算一次并落快照，之后同口径。

**连带改动**：`adminConfirmCancelWithRule` 现有 intro 文案「档位按『此刻』的提前量重新计算，可能与学生申请时不同」与本条矛盾，实施时随 hint 读取口径一并改为「按学生提交申请时的档位执行」。

## 七、completed 的收口（唯一允许的物化点）

展示层全部用推导态，但 `completed` 作为**业务终态**建议保留落库收口：

- 定时任务（项目已有调度池）每日把「已结束超过 24 小时且仍 `active`」的课次批量置 `completed`；
- 目的不是驱动时间态，而是：① 触发完成通知/评价邀请；② 归档迁移（实体注释里已有"completed 移历史库"设计）；③ 给统计口径一个稳定终态。

## 九、一句话方案

**时间不落库、推导不投票：UTC 为基准在服务端单一入口推导三态，排期"过期不可订"、预订"开课不可取消"、课次"开课不可改期"，前端显隐管体验、后端 409 管闸门，completed 由收口任务做唯一物化。**
