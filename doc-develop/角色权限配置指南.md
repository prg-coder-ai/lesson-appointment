# 角色权限配置指南（student / teacher / admin）

> 本项目角色→API 权限分布在**三层**，职责不同、缺一不可。
> 代码证据快照：2026-10-10，26 个 Controller、185 端点、AuthzRules 170 条规则。
> 守卫 `check:authz` 强制第一、二层闭环，漏配在 pre-commit 阶段即被拦截。

---

## 一、三层架构总览

| 层 | 配置文件 | 职责 | 强制机制 |
|---|---|---|---|
| ① URL 级声明式规则（主配置点） | `api/src/main/java/com/reservation/config/AuthzRules.java` | 声明「HTTP 方法 + 路径 → 允许的角色」 | `check:authz` 守卫：未覆盖端点判红；兜底 denyAll |
| ② 匿名放行区（免登录白名单） | `SecurityConfig.java`（59-140 行）+ `JwtAuthenticationFilter.java:69` | OPTIONS 放行、登录/注册/公开页免鉴权 | 两处白名单必须成对改，否则出现"过滤器跳了但 Security 拦了"的 401/403 错位 |
| ③ 方法级业务校验 | `PermissionCheck.java` + Controller 方法体 | 归属类细粒度校验（如教师只能改自己的课） | 越权抛 NoPermissionException（code 403） |

## 二、第①层：AuthzRules 规则表（改这里最多）

### 2.1 位置与结构

```java
// AuthzRules.java
public static final List<Rule> RULES = buildRules();   // :82，共 170 条

private static List<Rule> buildRules() {
    List<Rule> r = new ArrayList<>();
    r.add(new Rule(HttpMethod.GET,  "/api/v1/course/page", ALL_ROLES, "课程分页：三端都可浏览"));
    r.add(new Rule(HttpMethod.POST, "/api/v1/user/delete", ADMIN,     "删除用户仅管理员"));
    // ...
}
```

### 2.2 角色常量

```java
// RoleConst.java:15-18
STUDENT         = "student"
TEACHER         = "teacher"
ADMIN           = "admin"
PLATFORM_ADMIN  = "platform_admin"

// AuthzRules.java:70 —— "任意已登录角色"的语义
ALL_ROLES = {STUDENT, TEACHER, ADMIN, PLATFORM_ADMIN};
```

### 2.3 兜底行为：denyAll

`SecurityConfig` 的 `anyRequest()` 已从 `authenticated()` 切换为 **`denyAll()`**（分两步策略走完）：
- **漏声明 = 运行期 403**，不再静默放行；
- AuthzRules 类注释（28-40 行）记录了该取舍的完整理由。

### 2.4 守卫闭环

`tools/check-authz-declarative.mjs`（`npm run check:authz`）：
- 扫描全部 Controller 端点（185 个，其中 182 个纳入授权检查，页面路由 3 个跳过）；
- `RULES` 未覆盖的 `/api/v1/**` 路径 → 判红 → pre-commit 拦截；
- 同时检查陈旧规则（声明的路径已不存在）。

## 三、第②层：匿名放行区（成对配置）

### 3.1 两个必须同步的位置

| 位置 | 作用 |
|---|---|
| `SecurityConfig.java` 59-140 行 | `auth.requestMatchers(...).permitAll()` 声明匿名可达路径 |
| `JwtAuthenticationFilter.java:69` | `WHITELIST_PREFIXES` 前缀列表，JWT 校验跳过 |

**为什么必须成对改**（SecurityConfig.java:132 注释原文）：
- 这里没放行但过滤器跳了 → 落到兜底 → 401/403 口径错乱；
- 放行了但过滤器没跳 → 带着无效 token 也会被校验逻辑拦截。

### 3.2 现有放行示例

```java
auth.requestMatchers(HttpMethod.OPTIONS, "/**").permitAll();
auth.requestMatchers("/system/info", "/api/v1/system/info", ...).permitAll();
auth.requestMatchers("/interfaces", "/api/v1/interfaces", "/tenant/name", ...).permitAll();
// actuator/health、登录/注册/验证码、师资公开页等
```

## 四、第③层：PermissionCheck 方法级校验

### 4.1 可用方法

```java
permissionCheck.checkAdmin(token);           // 仅双 admin（admin + platform_admin）
permissionCheck.checkTeacherOrAdmin(token);  // 教师/管理员（禁学生，勿用 checkAnyLogin 替代）
permissionCheck.checkAnyLogin(token);        // 任意已登录角色（语义对齐 ALL_ROLES）
```

### 4.2 Controller 用法

```java
public Result<Course> getCourseById(@PathVariable String courseid,
                                    @RequestHeader("Authorization") String token) {
    permissionCheck.checkAnyLogin(token);
    ...
}
```

越权时抛 `NoPermissionException` → `GlobalExceptionHandler` → `Result.fail(403, ...)`（经 29-b 映射业务层 403 保持 HTTP 200，过滤器层真鉴权 401/403 例外）。

### 4.3 已覆盖范围（31 个敏感端点）

Booking 13、DataMaintain 5、log 4、TeacherProfessional 5、AuditLog 3、TimezoneCalc 1。
页面路由 4 个 Controller（Index/Page/DefaultPage/ApiInfo）确认公开，无需方法级校验。

## 五、操作手册（典型场景）

| 想做的事 | 改哪里 | 注意事项 |
|---|---|---|
| **新接口允许某角色访问** | `AuthzRules.buildRules()` 加一条 `r.add(new Rule(...))` | 必做——否则 `check:authz` 红线，提交不过 |
| **新公开接口（免登录）** | ① SecurityConfig `permitAll()`；② JwtFilter `WHITELIST_PREFIXES`；③ AuthzRules 登记说明 | 三处联动，守卫会核对 |
| **新增角色** | ① `RoleConst` 加常量；② 按需补 `ALL_ROLES`；③ 新规则里引用 | 勿忘给 JwtUtil 签发侧同步 role |
| **接口内归属校验** | Controller 方法加 `@RequestHeader("Authorization")` + `permissionCheck.xxx(token)` | URL 层已放行宽角色时，这里做细粒度兜底 |

---

## 六、一句话记忆

> **路径层看 AuthzRules（170 条规则表），匿名层看 SecurityConfig + JwtFilter 白名单（成对改），业务层看 PermissionCheck 方法调用**。
> 守卫 `check:authz` 强制前两者对齐——漏配在 pre-commit 就被拦下，不会等到线上 403 才发现。
