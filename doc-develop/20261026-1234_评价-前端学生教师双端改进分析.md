## 三、结合项目现状才能看到的五个缺口

这是文档最薄弱的地方。它不是"没写全"，而是**写作时未把项目当前主线纳入视野**。

### 缺口 1：横向越权（最严重）

当前后端对教师写操作的保护止于「角色」，不止于「归属」：

```
POST /teacher/professional/add|update|deleteTeacherProfessionalInfo
   → permissionCheck.checkTeacherOrAdmin(token)     // 只验是不是教师/管理员
POST /api/v1/schedule/create | /update
   → permissionCheck.checkTeacherOrAdmin(token)     // 同上，不验课程是不是你的
POST /api/v1/teacher/published/save
   → permissionCheck.checkTeacherSelfOrAdmin(...)   // ← 唯一做了归属校验的一个
```

**一旦按 P0-T1/T2/T3 解除前端限制，教师 A 就能凭 `teacherId`/`courseId` 修改教师 B 的职业信息、给他人课程建排期。** `deleteTeacherProfessionalInfo` 按主键删除且无归属校验，风险最高。

> 这不是文档臆造的风险：本项目近两周刚处理过同类问题（`assertNoAdminSelfLock`、`purge/user` 显式登记 `CascadeRules`）。**开放写能力前必须先补齐归属校验，否则是拿生产数据冒险。**

### 缺口 2：排期创建的时区口径尚未收敛

`ScheduleController.java:47` 与 `:56` 仍留有源码注释：

```java
Map<String, String> resultMap = scheduleService.createSchedule(dto); //////TBD: local->UTC switch
```

而项目已确立的口径是「**课次 appointment = UTC 唯一真相源，转换只经 ScheduleGenerator**」。在 TBD 未消除前照 P0-T2 实现教师自助排期，**大概率写入时间错乱的课次数据**——这类脏数据进入排期/课次链路后极难回溯。

**建议**：P0-T2/T3 必须等该 TBD 收敛，或由前端严格走既有 `ScheduleGenerator` 口径，不得自行拼本地时间。

### 缺口 3：多租户与术语三级映射完全缺席

文档建议新建两个页面（`course-detail.html`、`teacher-list.html`），但项目当前主线是**多租户 SaaS + 多行业术语三级作用域**（`sys_term`：平台词 → 行业词 → 租户词）。新页面若不接入：

- `applyTerms` / `curTerm()` 术语映射 → 标题会硬编码成"课程/学生/教师"，与**律师咨询子行业**（咨询师/咨询）直接冲突
- `pageUrl()` / 相对路径 + `location.origin` → 租户编码 `tCode` 丢失，登录回跳断链
- `TenantLineInnerInterceptor` 的 tenantId 隔离 → 租户 A 的教师可能出现在租户 B 视野

现成参照：`frontend/admin.html`、`platform_admin.html`、`student-landing.html` 均已接入 `pageUrl`，照抄即可。

### 缺口 4：交付闭环缺失（改完怎么上线）

文档通篇只说"改 `xx.js`，然后取消注释"，但本项目**线上跑的是 `frontend/dist`，不是源码**。忘记这一步的结果是"本地改好了、服务器纹丝不动"——这正是本周反复出现的现象。

施工后必须执行（本机已验证的可用参数）：

```bash
cd frontend
NODE_OPTIONS=--max-old-space-size=4096 CODEBUDDY_SAFE_DELETE_ENABLED=0 node build.js
# 然后将 frontend/dist 同步到服务器
```

> 两个参数是硬约束：默认堆会在 terser 阶段 `Fatal process out of memory` 崩溃，且此时 dist 已被清空；不加 `CODEBUDDY_SAFE_DELETE_ENABLED=0` 会被 safe-delete 闸拦下（>50 文件）。
> **好消息**：`build.js:80` 用 `readdirSync(ROOT).filter('.html')` 扫描根目录，所以**新建 HTML 页面会自动进 dist**，无需改构建配置。但 `js/test/` 被显式排除——不要往那里放，也不要让生产页面引用它。

### 缺口 5：与十七道守卫的交互未评估

新增/调整的后端调用会撞上守卫：

| 涉及改动 | 必过的守卫 | 说明 |
|---------|-----------|------|
| 新增任何 `/api/v1/**` 调用 | `check:authz` | 未登记即 403；新增端点须同步登记 `AuthzRules` |
| 涉及删除的后端 Service | `check:cascade` | 方法体内必须出现 `cascadeService.run` 或 `cascadeDelete*` 辅助方法（本次 `purge/user` 就因私有方法命名被拦过一次） |
| 新增免登录页面 | 四处白名单一致性 | `SecurityConfig` / `JwtAuthenticationFilter` / `check-authz` 的 `PERMIT_ALL` / `WebMvcConfig.EXCLUDE_PATTERNS` **缺一即整体失效** |

## 四、修订后的执行建议

原文档按 ROI 排序的思路是对的，但缺「安全前置条件」这一层。重排如下：

### 🔴 第 0 阶段：安全前置（原文档完全缺失，**必须先于所有 P0**）

| 编号 | 事项 | 说明 |
|------|------|------|
| **SEC-1** | 给 `deleteTeacherProfessionalInfo` 补归属校验 | 当前按主键删除且无归属判断，风险最高，改动最小。**建议优先做这一条** |
| **SEC-2** | `add/updateTeacherProfessionalInfo` 改为 `checkTeacherSelfOrAdmin` | 与已加固的 `published/save` 对齐口径 |
| **SEC-3** | `/schedule/create`、`/schedule/update` 补课程归属校验 | 否则解除 readonly 后教师可改他人课程排期 |
| **SEC-4** | 收敛 `ScheduleController` 的 `local->UTC` TBD | 未收敛前不做教师自助排期的时间类写操作 |

### 🔴 第 1 阶段：零风险、纯前端（可立即开工）

- **P0-S1** 课程卡片丰富化 — 数据已在 `/course/page` 返回，纯展示层收益最高，**建议第一个做**
- **P0-S3** 预约 alert → Modal/Toast — 22 处分支里先覆盖 "满额/已下架/加载失败" 三条高频路径
- **P1-T1** 移除 teacher.html 的 mock 评价与个人中心 — 假数据上线是信任问题，优先级高于多数新功能
- **P0-T1（改法要变）** 开放职业信息入口：不是"移除 `role !== 'admin'`"，而是**新增 `role === 'teacher'` 分支进入"本人只读/编辑"形态，保留 platform_admin 的显式拒绝**

### 🟠 第 2 阶段：依赖 SEC 完成

- P0-T2/T3/T4 排期创建/编辑/删除/状态切换 — **必须在 SEC-3 + SEC-4 之后**
- P0-S5 筛选维度扩展、P0-S2 名额进度条
- P1-S1 学生个人中心启用

### 🟡 第 3 阶段：新建页面（须接入术语映射与租户上下文）

- P1-S2 课程详情页 → 接口是 `/course/{courseid}`（注意全小写），须接 `applyTerms` + `pageUrl`
- P1-S3 教师列表页 → 走 `/teacher/published/public-list`（免登录），注意其已在四处白名单登记，改动须同步四处
- P1-S4 日历月份切换

### 🟢 第 4 阶段：需后端新增

- P2-S1 课程评价（新增 Controller/Service/Mapper，须登记 `AuthzRules` + 如涉删除则登记 `CascadeRules`）
