## 一、总体结论

| 维度 | 评价 |
|---|---|
| 功能覆盖面 | **基本够用**，四大块覆盖了「租户生命周期 / 系统健康 / 租户用量 / 平台经营」四层，方向正确 |

## 三、P0 缺陷：先修这个，否则租户管理页面跑不通

`migration-20260830-saas.sql` 中 `sys_tenant` 的列名带**连字符**，而 `Tenant` 实体是**驼峰命名**：

```sql
-- 现在的建表（有问题）
`tenant-code`  VARCHAR(56)  NOT NULL,
`org-name`     VARCHAR(255),
`contact  `    VARCHAR(255),   -- 还多了两个空格
`package-id`   BIGINT,
`expire-time`  DATETIME,
`create-time`  DATETIME,
`update-time`  DATETIME,
```

```java
// Tenant.java（MyBatis-Plus 默认驼峰转下划线）
private String tenantCode;   // → 实际查 tenant_code，与 tenant-code 不匹配
private String orgName;      // → org_name
private LocalDateTime createTime; // → create_time
```

**后果**：所有租户查询都会抛 `Unknown column 'tenant_code'`，且 `sys_tenant` 表在 MySQL 中带连字符的列名每次书写都必须反引号包裹，极易出错。

**修法**（二选一，推荐 A）：

```sql
-- A：统一改为下划线命名（推荐，与全库其余表一致）
ALTER TABLE `sys_tenant`
  CHANGE COLUMN `tenant-code`  `tenant_code`  VARCHAR(56)  NOT NULL COMMENT '租户唯一编码',
  CHANGE COLUMN `org-name`     `org_name`     VARCHAR(255) DEFAULT NULL COMMENT '机构名称',
  CHANGE COLUMN `contact  `    `contact`      VARCHAR(255) DEFAULT NULL COMMENT '联系人',
  CHANGE COLUMN `package-id`   `package_id`   BIGINT       DEFAULT 0 COMMENT '关联套餐ID',
  CHANGE COLUMN `expire-time`  `expire_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '到期时间',
  CHANGE COLUMN `create-time`  `create_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  CHANGE COLUMN `update-time`  `update_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间';
```

> 若选 B（保留连字符 + `@TableField("`tenant-code`")` 逐个映射），后续每个字段都要写注解，且 SQL 里到处要反引号，维护成本高，不建议。

**同时建议补齐的租户表字段**（后面几项功能都依赖）：

```sql
ALTER TABLE `sys_tenant`
  ADD COLUMN `status`        TINYINT      NOT NULL DEFAULT 1 COMMENT '状态：1正常 2停用 3已退租 4已过期' AFTER `phone`,
  ADD COLUMN `offline_time`  DATETIME     DEFAULT NULL COMMENT '退租/停用时间' AFTER `expire_time`,
  ADD COLUMN `remark`        VARCHAR(500) DEFAULT NULL COMMENT '备注' AFTER `offline_time`,
  ADD KEY `idx_status` (`status`),
  ADD KEY `idx_create_time` (`create_time`);
```

> 注意：原表 `status` 字段已存在但**无字典定义**，运营统计的「退租数」依赖它，必须先把枚举值定下来。
>
> 更正（此前理解有误）：`sys_tenant.package_id` 指向的是**套餐模板**（`sys_package_template.id`），
> 而 `sys_tenant_package.tenant_id` 指向租户本身，两者不是冗余关联，各司其职：
> - `sys_package_template` —— 规格定义（免费版/标准版/旗舰版），只有限额
> - `sys_tenant.package_id` —— 该租户选用了哪个模板
> - `sys_tenant_package` —— 该租户实际持有的套餐（限额从模板套用 + 当前用量），`tenant_id` 必填且唯一
>
> 因此需要**新增套餐模板表及其编辑功能**。

### 4.2 系统监视

**评价**：指标列举了但**口径未定义**，且当前项目无任何监控依赖，需要从 0 搭建。

#### 指标口径必须先定死

| 指标 | 建议口径 | 数据来源 |
|---|---|---|
| CPU | 系统 CPU 使用率 + 进程 CPU 使用率（分别看） | OSHI / `OperatingSystemMXBean` |
| 内存 | JVM 堆已用/上限 **+** 系统物理内存已用/总量（两个都要，运维看系统，研发看 JVM） | `MemoryMXBean` / OSHI |
| 带宽 | 网卡入/出速率（Mbps）+ 当日累计流量；**多网卡需指定或聚合** | OSHI `NetworkIF` |
| 延迟 | **服务端测不了网络 RTT**。建议改为：接口 P95/P99 耗时 + 前端上报的首字节时间（TTFB） | `sys_audit_log.cost_ms` 聚合 / 前端打点 |
| 磁盘 | 各挂载点已用/总量，>85% 告警 | OSHI |
| 连接 | 数据库连接池活跃/空闲/等待数、当前 TCP 连接数 | HikariCP MXBean |
| 线程 | JVM 线程数、各状态分布 | `ThreadMXBean` |

#### 补充的监控项（原需求没提但很关键）

- **接口健康度**：QPS、错误率（4xx/5xx 占比）、慢接口 Top10 —— 直接查 `sys_audit_log`，成本极低价值极高
- **JVM**：GC 次数与耗时、堆内存趋势图、类加载数
- **在线实例**：集群部署时要能按实例切换查看（见第八节）
- **日志**：已有 `logBrowser.html`，建议接入监控页并支持 ERROR 日志实时推送
- **磁盘 / 数据库连接池 / 线程池** 的健康状态灯

#### 技术方案建议

```xml
<!-- 基础监控：actuator + micrometer，暴露 /actuator/metrics、/health -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<!-- 系统级指标（CPU/内存/磁盘/网卡），Java 标准 API 拿不到网卡和磁盘 -->
<dependency>
    <groupId>com.github.oshi</groupId>
    <artifactId>oshi-core</artifactId>
    <version>6.6.5</version>
</dependency>
```

**采样与存储**（原需求完全没提，必须补）：

- 采样频率：实时页 5s 一次轮询，历史数据 1 分钟落库
- 建 `sys_metric_sample` 表存历史（否则只能看当前瞬间，看不到趋势和故障回溯）
- 留存策略：明细 7 天，小时聚合 90 天
- 监控接口 `/monitor/**` 必须走 `platform_admin` 鉴权，且 actuator 端点**禁止公网暴露**

**新增接口：**
```
GET /monitor/overview       系统概览（CPU/内存/磁盘/网络/JVM 一次返回）
GET /monitor/trend          历史趋势（传 metric + 时间范围）
GET /monitor/api-health     接口健康度（QPS/错误率/慢接口 Top10）
GET /monitor/instances      实例列表（集群时）
```

### 4.3 运行管理（租户用量与额度）

**评价**：需求定义得最清楚的一项，且 `sys_tenant_package` 表已经把数据结构备好了，**可行性最高**。

**需要明确的点：**

1. **「与上月的变化」怎么算？**
   - 现状：只能算**当前累计总量**（`SELECT COUNT(*) ... WHERE tenant_id=?`），算不出环比
   - 解法：建月度快照表，每月 1 日凌晨定时任务跑批

```sql
CREATE TABLE IF NOT EXISTS `sys_tenant_stats_monthly` (
  `id`            BIGINT   NOT NULL AUTO_INCREMENT,
  `tenant_id`     BIGINT   NOT NULL COMMENT '租户ID',
  `stat_month`    CHAR(7)  NOT NULL COMMENT '统计月份 yyyy-MM',
  `teacher_count` INT      NOT NULL DEFAULT 0,
  `student_count` INT      NOT NULL DEFAULT 0,
  `course_count`  INT      NOT NULL DEFAULT 0,
  `schedule_count`INT      NOT NULL DEFAULT 0,
  `booking_count` INT      NOT NULL DEFAULT 0,
  `create_time`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_tenant_month` (`tenant_id`, `stat_month`),
  KEY `idx_month` (`stat_month`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='租户月度用量快照';
```

2. **额度占比的可信度问题（重要）**
   `sys_tenant_package` 的 `*_current` 是靠业务代码原子递增维护的，一旦出现并发异常、手动改库、历史数据迁移，就会与真实 `COUNT(*)` 漂移。
   → **建议加每日对账任务**：凌晨对比 `*_current` 与真实 count，不一致则以真实值为准校正，并记录差异日志。否则运营看到的占比是假的。

3. **统计口径**：
   - 教师/学生数建议只统计 `status='active'`（待审核 `inactive`、冻结 `frozen` 不计入占用）
   - 课程数建议排除已删除/已归档
   - 排期数建议区分「历史的」与「未来的」，运营更关心未来 30 天排期

4. **预警**：占比 ≥ 80% 标黄、≥ 95% 标红，并在租户侧也给出提示（别等创建失败才告知）

**新增接口：**
```
GET /dashboard/tenant/usage        全租户用量概览（分页 + 排序，支持按占比排序找临界租户）
GET /dashboard/tenant/{id}/usage   单租户用量详情 + 环比 + 额度占比
GET /dashboard/usage/export        导出 CSV
POST /dashboard/usage/reconcile    手动触发对账（管理员）
```

### 4.4 运营统计

**评价**：指标合理，但「在线人数」无数据基础，「退租数」无字段支撑。

#### 在线人数：需要专门设计（当前无解）

现状：`user` 表无 `last_active_time`、无 `online` 字段、无会话表 —— 三个来源都没有。

**推荐方案（按成本从低到高）：**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A（推荐，低成本） | `user` 表加 `last_active_time`，拦截器每次请求更新（可加 60s 节流避免高频写）；「在线」= `last_active_time` 在最近 5 分钟内 | 改动小，无需新表 | 有 5 分钟误差；高频写需优化 |
| B（精确） | 建 `sys_user_session` 表，登录写、登出删、心跳续期，过期任务清理 | 精确、可查 IP/设备/登录时长 | 需维护会话生命周期 |
| C（分布式） | 用 Redis 存活跃 token 集合，按租户分桶计数 | 性能好、天然支持集群 | 需引入 Redis |

**SQL（方案 A + B 结合，推荐先落 A）：**

```sql
ALTER TABLE `user`
  ADD COLUMN `last_active_time` DATETIME DEFAULT NULL COMMENT '最近活跃时间（用于在线统计）',
  ADD KEY `idx_tenant_active` (`tenant_id`, `last_active_time`);
```

> 若选方案 B：
```sql
CREATE TABLE IF NOT EXISTS `sys_user_session` (
  `id`          BIGINT      NOT NULL AUTO_INCREMENT,
  `session_id`  VARCHAR(64) NOT NULL COMMENT '会话ID',
  `tenant_id`   BIGINT      NOT NULL DEFAULT 0 COMMENT '租户ID',
  `user_id`     VARCHAR(36) NOT NULL,
  `user_role`   VARCHAR(10) DEFAULT NULL,
  `ip`          VARCHAR(64) DEFAULT NULL,
  `user_agent`  VARCHAR(500) DEFAULT NULL,
  `login_time`  DATETIME    NOT NULL,
  `last_active` DATETIME    NOT NULL,
  `status`      TINYINT     NOT NULL DEFAULT 1 COMMENT '1在线 2已登出 3已过期',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_session` (`session_id`),
  KEY `idx_tenant_status` (`tenant_id`, `status`),
  KEY `idx_last_active` (`last_active`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户会话表（在线统计）';
```

#### 退租数

需要先落第三节的 `status` 字典 + `offline_time`，才能按月份统计。

#### 补充的运营指标

- **套餐分布**：各套餐下的租户数（看出哪个套餐最好卖）
- **到期预警**：30 天内到期租户列表（续费跟进）
- **活跃度**：近 30 天有排期/预约产生的租户数 vs 沉默租户 —— 比单纯租户数更有价值
- **趋势图**：租户数、用户数的 12 个月折线

**新增接口：**
```
GET /dashboard/overview            平台总览（租户数/用户数/在线数/本月新增/本月退租）
GET /dashboard/tenant/trend        租户增减趋势（按月）
GET /dashboard/online              在线统计（总数 + 各租户分布）
GET /dashboard/expire-warning      到期预警列表
```

## 八、需要你确认的问题

1. **部署形态**：单机还是多实例集群？集群的话在线人数、系统指标都要按实例聚合，设计不同。

3. **「延迟」到底想看什么**？接口响应时间（服务端可测）还是用户侧网络延迟（需前端打点）？
4. **历史数据要存多久**？影响 `sys_metric_sample` 的表设计与清理策略。
