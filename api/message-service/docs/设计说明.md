# 消息中心微服务（message-service）设计说明

> 依据《Spring Boot 校内消息中心系统设计与实现报告》落地，完成消息中心的微服务化设计与编码实现，并具备管理员对消息的管理能力。

---

## 1. 背景与目标

原消息中心能力内嵌于预约系统主应用（api 模块）。随着多租户 SaaS 化推进，需将"消息/通知"能力解耦为**独立部署、独立数据库、独立端口**的微服务，使其可独立演进、独立扩容，同时**复用主系统已有的用户体系与登录态（JWT）**，避免重复建设账号/鉴权。

目标：
- 独立服务：独立 Spring Boot 应用、独立端口（8090）、独立库（message_center）。
- 能力闭环：消息收发、收件箱状态、三级分类、模板、投递/批量任务追踪、管理员管理。
- 实时性：REST 落库 + SSE 单向实时推送（已与用户确认）。
- 安全：复用主系统 JWT 密钥与 AES 密钥，token 直通校验，敏感字段落库加密。

---

## 2. 工程拓扑与方案选型

| 维度 | 决策 | 说明 |
|------|------|------|
| 形态 | api 下的**独立应用模块** `message-service` | 与 api 主服务平级，拥有自己的 pom、启动类、端口、库，不依赖 api 主服务类 |
| 端口 | 8090 | 独立于主服务 8081 |
| 数据库 | 独立库 `message_center` | 与主业务库（lesson_appointment）物理隔离 |
| 复用策略 | **复制轻量工具类 + 共享密钥** | 复制 `Result` / `JwtUtil` / `CryptoUtil` / `RoleConst` 等无业务依赖工具；`jwt.secret` 与 `crypto.aes-key`/`crypto.hmac-key` 与主系统**完全一致** |
| token 互通 | 主系统登录签发的 JWT 可直接调用本服务 | 拦截器用同一 secret 验签 HS512，无需二次登录 |
| 推送选型 | REST 落库 + SSE 单向推送 | 已确认：服务端向在线客户端主动推送，客户端无需轮询 |

**不选** Feign 内部调用、共享主库表：避免跨服务事务耦合，保证消息服务可独立演进与故障隔离。

## 3. 系统架构

```
                          ┌─────────────────────────────┐
   主系统登录(api:8081)    │        message-service       │
   签发 JWT ──────────────▶│         (port 8090)          │
                          │                              │
   客户端 / 业务系统       │  MessageAuthInterceptor      │
        │  HTTPS           │   (解析 Bearer → Context)    │
        ├─────────────────▶│           │                 │
        │                  │     Controller 层            │
        │                  │           │                 │
        │   SSE 长连接 ────▶│     SseController           │
        │  ◀───────────────┤     SsePushService(内存注册表)│
        │   实时推送        │           │                 │
        │                  │     Service 层              │
        │                  │           │                 │
        │                  │     Mapper 层               │
        │                  │           │                 │
        │                  │  ┌────────┴─────────┐       │
        │                  │  │  message_center   │       │
        │                  │  │  (MySQL 独立库)   │       │
        │                  │  └──────────────────┘       │
        └──────────────────┘                            │
                              └──────────────────────────┘
```

- **鉴权流**：所有请求经 `MessageAuthInterceptor`，从 `Authorization: Bearer <token>` 解出 `userId / role / tenantId`，写入 `MessageAuthContext`（ThreadLocal）；控制器再做显式角色校验。
- **推送流**：发送成功后，`SsePushService` 按 `tenant + userId` 在内存注册表中查找在线 `SseEmitter`，向在线接收者主动推送；离线用户下次拉取收件箱即可见。

## 4. 数据模型（6 张表，均带 tenant_id）

| 表 | 作用 | 关键字段 |
|----|------|----------|
| `msg_message` | 消息主表（标题/内容/附加数据 AES 加密存储） | id, sender_user_id, sender_role, category_code, priority, title(密), content(密), payload(密), tenant_id, status |
| `msg_inbox` | 收件箱状态（每用户每消息一行） | id, message_id, user_id, is_read, is_starred, folder(inbox/starred/trash), is_deleted, tenant_id |
| `msg_category` | 消息三级分类 | id, category_code, category_name, parent_id, category_level(1/2), sort, tenant_id |
| `msg_template` | 消息模板（占位符填充） | id, template_code, template_name, category_code, title_template, content_template(密), sender_type, priority, is_enabled |
| `msg_delivery` | 单条投递状态 | id, message_id, recipient_user_id, delivery_status(sent/failed/read), push_status, tenant_id |
| `msg_batch_task` | 批量发送任务进度 | id, message_id, total, success, failed, status, tenant_id |

预置数据：`msg_category` 已插入 **11 条平台预置分类**（全部 `tenant_id=0`、`is_system_predefined=1`）：一级 3 条（教师/管理员消息、学生消息、系统通知）+ 二级 8 条（作业通知、上课/课堂调整通知、请假审批通知、资源/报修/咨询、排期/签到/截止提醒、预约/候补申请、预约确认/候补递补、学生请假申请）。其中 `BOOKING_CREATED`/`BOOKING_CONFIRMED`/`LEAVE_CREATED` 由 booking api 的 `MessageNotifyService` 自动发送时使用，必须存在，否则 `send` 会因业务码 404 拒收。

## 5. 核心能力闭环

1. **消息发送**：单发/群发（指定 `recipientUserIds`）、广播（按角色/全体）、系统通知。`title/content/payload` 落库前 AES-GCM 加密。
2. **收件箱**：分页列表（支持 folder / keyword / unreadOnly / categoryCode / priority / 时间区间过滤）、详情（解密返回）、未读计数、已读/未读、收藏/取消、删除（软删进 trash）、恢复、**彻底删除（purge，物理删个人副本）**、批量已读/删除（软删）/批量彻底删除（purge）。
3. **三级分类**：`parent_id + category_level` 表达层级；提供 `tree` 查询（扁平 List）与管理端 CRUD（仅 admin / platform_admin）；新增时 `categoryCode` 留空自动生成 `CAT_xxx`；系统预置分类受保护。
4. **模板**：维护标题/内容模板（支持 `{name}` 占位符），基于模板 + 参数填充后发送。
5. **投递 / 批量任务追踪**：`msg_delivery` 记录每条投递状态；`msg_batch_task` 记录批量进度；提供 `delivery-status`、`batch/{taskId}` 查询接口。
6. **管理员管理**：发送历史查询、单条撤回（withdraw）、失败重推（retry）、接收回执（ack）、**全局彻底删除（级联删主消息+全部副本+投递记录）**。

### 5.1 删除维度设计（三类不可混淆）

消息删除存在**三种语义完全不同的维度**，已在代码与接口层严格分层，避免误删：

| 维度 | 接口 | 作用表 | 影响范围 | 权限 |
|------|------|--------|----------|------|
| 软删（移回收站） | `DELETE /users/{uid}/messages[/batch]` | `msg_inbox`（`is_deleted=1`,`folder=trash`） | 仅当前用户个人副本 | 本人 |
| 彻底删除（purge） | `DELETE /users/{uid}/messages[/batch]/purge` | `msg_inbox`（**物理删行**） | 仅当前用户个人副本，主消息与其他接收者不变 | 本人 |
| 收回（withdraw） | `POST /messages/{id}/withdraw` | `msg_inbox`（`is_deleted=1`） | 仅撤「接收方均未读」的副本 | 管理员/发送者 |
| 全局彻底删除 | `DELETE /messages/{id}` | `msg_message` + 全部 `msg_inbox` + `msg_delivery` | 全租户所有接收者（覆盖已读副本）+ SSE `message_deleted` | 管理员（平台管理员跨租户） |

> **架构红线**：收件人 `msg_inbox` 的标题/内容**联表取自主消息 `msg_message`**（不冗余存储），因此**绝不能让发送者自助删主消息，也绝不能单独 `DELETE` 主消息**——否则所有收件人副本会变成空白标题。全局彻底删除必须级联 `msg_inbox` + `msg_delivery` + `msg_message` 三表，且限定管理员。
> message-service **不挂 `TenantLineInnerInterceptor`**，租户隔离靠显式 `tenantId` 过滤，全局删除不受租户插件干扰，平台管理员可正确跨租户级联删。

## 6. 鉴权模型

- **拦截器** `MessageAuthInterceptor`（HandlerInterceptor）：解析 `Authorization: Bearer <token>`，用共享 `jwt.secret` 验签（HS512），填充 `MessageAuthContext`。
- **上下文** `MessageAuthContext`：ThreadLocal 保存 `userId / role / tenantId`，业务与控制器统一取用。
- **SecurityConfig**：`permitAll`（鉴权已在拦截器完成），仅 SSE/静态资源放行。
- **角色常量** `RoleConst`：`student / teacher / admin / platform_admin / system`；提供 `isManager()`、`canSendDownstream()` 等判定，控制器显式校验（如学生不可广播、仅管理员可管理分类/模板/历史）。

---

## 7. 字段加密

- `CryptoUtil` 采用 AES-256-GCM，输出格式 `hmac:cipher`，密钥与主系统一致 → 可互通解密。
- 加密字段：`msg_message.title / content / payload`、`msg_template.content_template`。
- 详情接口（`GET /messages/{messageId}`）在返回前解密，调用方拿到的始终是可读本文字段。

## 8. 与源设计报告的能力映射

| 报告设计能力 | 本服务落地端点 |
|--------------|----------------|
| 消息发布（单发/群发/广播/系统） | `POST /api/v1/messages/send`、`/broadcast`、`/system` |
| 收件箱（已读/未读/收藏/软删/恢复/彻底删除） | `UserInboxController` 全量接口（含 `/messages/.../purge`、`/messages/batch/purge`） |
| 消息分类（多级 + 管理端 CRUD） | `MessageCategoryController`（含 `/tree` 扁平返回）；`CategoryService` 租户隔离+编码唯一+系统预置保护 |
| 消息模板 | `MessageTemplateController`（含 `/send` 占位填充） |
| 投递状态 / 批量任务追踪 | `MessageManageController` 的 `delivery-status`、`batch/{taskId}` |
| 管理员管理（撤回/重推/历史/全局彻底删除） | `MessageManageController` 的 `withdraw`、`retry`、历史 `GET`、`DELETE /{messageId}` |
| 实时推送 | `SseController` + `SsePushService`（事件类型 `new_message`/`message_recalled`/`message_deleted`） |
| 接收回执 | `POST /api/v1/messages/{id}/ack` |

## 9. 部署与配置（application.properties 关键项）

| 配置项 | 值 | 说明 |
|--------|-----|------|
| `server.port` | 8090 | 服务端口 |
| `spring.datasource.url` | `jdbc:mysql://localhost:3306/message_center` | 独立库 |
| `jwt.secret` | 与 api 主系统一致 | token 互通 |
| `jwt.expiration` | 360000000 | 同主系统 |
| `crypto.aes-key` / `crypto.hmac-key` | 与 api 主系统一致 | 字段互通解密 |
| `DB_USERNAME` / `DB_PASSWORD` | 默认 root / 123456（环境变量可覆盖） | 数据库连接 |

> 启动注意：若运行环境存在 `SERVER__PORT` 之类环境变量，会被 Spring relaxed binding 映射为 `server.port`，需用 `-Dserver.port=8090` 显式覆盖（已踩坑验证）。

## 10. 后续可扩展

- 投递失败补偿队列（异步重推）、消息归档与冷热分离。
