## 教师职业信息维护功能 - 详细设计方案（v1.0）
================================================================================

### 0. 背景与复用性分析
   user 表已有的教师专属字段：
     - `name`            教师姓名 (varchar 50)
     - `qualification`   资格证书 (text, 存 Base64 图片)
     - `language_type`   语言类型 / 学科 (varchar 20，枚举：英语/日语/韩语/法语/德语/西班牙语)
   不足：user 表没有「文字说明/链接、个人照片、可预约时间段」等字段。
   策略：不直接在 user 表堆新列（以免学生/管理员字段为空），而是新增
   一张独立的「教师职业信息表」teacher_professional，用 user_id(teacher) 1:1 关联。

### 1. 数据库设计（3 张表 + 可选上传表）
================================================================================

---------------- 1.1 教师职业信息主表 teacher_professional ----------------
-- 与 user 表 1:1，主表存文本类信息，图片/证书单独存 URL（或沿用 Base64）
CREATE TABLE IF NOT EXISTS `teacher_professional` (
  `teacher_professional_id` varchar(36) NOT NULL COMMENT '主键UUID',
  `teacher_id`              varchar(36) NOT NULL COMMENT '关联user表user_id（仅限role=teacher）',
  `subject`                 varchar(50)  DEFAULT NULL COMMENT '学科（=language_type冗余便于排序搜索；也可扩为多学科逗号分隔）',
  `personal_photo_url`      varchar(500) DEFAULT NULL COMMENT '个人照片URL（静态文件路径，优先）',
  `personal_photo_base64`   mediumtext   DEFAULT NULL COMMENT '个人照片Base64（与URL二选一，兼容老qualification方式）',
  `bio_text`                varchar(2000)DEFAULT NULL COMMENT '文字说明（教师简介）',
  `bio_url`                 varchar(500) DEFAULT NULL COMMENT '文字说明链接（外部简历/博客URL）',
  `availability_rule`       varchar(1000)DEFAULT NULL COMMENT '可预约时间规则（结构化JSON，见1.2）',
  `min_booking_hours`       int          DEFAULT 4 COMMENT '单次可预约最小课时数（如4小时）',
  `weekly_available_hours`  int          DEFAULT 20 COMMENT '每周可预约总课时上限',
  `certificate_text`        varchar(500) DEFAULT NULL COMMENT '证书文字描述（如CET-8、JLPT N1）',
  `status`                  varchar(10)  NOT NULL DEFAULT 'active' COMMENT '职业信息状态active/inactive/frozen',
  `create_time`             datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`             datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`teacher_professional_id`),
  UNIQUE KEY `uk_teacher_id` (`teacher_id`),
  KEY `idx_subject` (`subject`),
  KEY `idx_status` (`status`),
  CONSTRAINT `fk_tp_teacher` FOREIGN KEY (`teacher_id`) REFERENCES `user`(`user_id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='教师职业信息主表(1:1 user teacher)';

---------------- 1.2 证书图片表 teacher_certificate（支持多张） ----------------
-- 注：如果证书仅需一张，可合并到 1.1；需求"资格证书（图片）"用复数
CREATE TABLE IF NOT EXISTS `teacher_certificate` (
  `certificate_id` varchar(36) NOT NULL COMMENT '主键UUID',
  `teacher_id`     varchar(36) NOT NULL COMMENT '关联教师user_id',
  `cert_name`      varchar(100) DEFAULT NULL COMMENT '证书名称',
  `cert_url`       varchar(500)DEFAULT NULL COMMENT '证书图片URL',
  `cert_base64`    mediumtext  DEFAULT NULL COMMENT '证书图片Base64（兼容）',
  `sort_no`        int         DEFAULT 0 COMMENT '排序号，小在前',
  `create_time`    datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`certificate_id`),
  KEY `idx_teacher_id` (`teacher_id`),
  CONSTRAINT `fk_tc_teacher` FOREIGN KEY (`teacher_id`) REFERENCES `user`(`user_id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='教师资格证书表(1:N)';

---------------- 1.3 可预约时间表 teacher_available_time（结构化） ----------------
-- 推荐：weekly 模板（7 × N 段），前端渲染为「周一至周五 9:00-17:00」卡片。
-- 另可按具体日期覆盖（某周假日关闭）
-- 拟从排期表 teacher_schedule 中提取可预约时间，避免重复定义。需要改进排期表处理，使用预留的可用人数字段，标识是否可预约。
CREATE TABLE IF NOT EXISTS `teacher_available_time` (
  `available_id`   varchar(36) NOT NULL COMMENT '主键UUID',
  `teacher_id`     varchar(36) NOT NULL COMMENT '关联教师user_id',
  `time_type`      varchar(20) NOT NULL COMMENT 'weekly(每周模板) / override(具体日期覆盖) / holiday(假日)',
  `day_of_week`    tinyint     DEFAULT NULL COMMENT '每周模板时生效：1=周一..7=周日',
  `specific_date`  date        DEFAULT NULL COMMENT 'override/holiday时生效：具体日期',
  `start_time`     time        NOT NULL COMMENT '时段开始 如 09:00:00',
  `end_time`       time        NOT NULL COMMENT '时段结束 如 17:00:00',
  `status`         varchar(10) NOT NULL DEFAULT 'active' COMMENT 'active/frozen',
  `create_time`    datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`available_id`),
  KEY `idx_teacher_day` (`teacher_id`, `day_of_week`),
  KEY `idx_teacher_date` (`teacher_id`, `specific_date`),
  CONSTRAINT `fk_tat_teacher` FOREIGN KEY (`teacher_id`) REFERENCES `user`(`user_id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='教师可预约时间段（周模板+按日覆盖）';

---------------- 可选：通用上传记录表 teacher_file_upload ----------------
-- 如果未来照片/证书改为存文件并走上传接口，统一记录在此
CREATE TABLE IF NOT EXISTS `teacher_file_upload` (
  `upload_id`    varchar(36)  NOT NULL COMMENT '主键UUID',
  `teacher_id`   varchar(36)  NOT NULL,
  `file_type`    varchar(20)  NOT NULL COMMENT 'photo/certificate/doc',
  `file_name`    varchar(200) NOT NULL,
  `file_url`     varchar(500) NOT NULL,
  `file_size_kb` int          DEFAULT NULL,
  `mime_type`    varchar(100) DEFAULT NULL,
  `create_time`  datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`upload_id`),
  KEY `idx_teacher_type` (`teacher_id`, `file_type`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='教师上传文件记录表';

### 6. 文件上传约定（照片/证书）
================================================================================
两种存储方式，推荐方式A + 兼容方式B（MVP可先用B）：

  方式A：磁盘文件 + URL 返回
    · 上传目录：本地固定路径（application.properties 配置 teacher.upload.path）
       并通过 WebConfig addResourceHandlers 映射到 /teacher-upload/**
    · SecurityConfig 白名单：/teacher-upload/** permitAll
    · 返回 URL 格式：${API_BASE_URL}/teacher-upload/{ymd}/{uuid}.{ext}
    · 最大体积：10MB（Spring.servlet.multipart.max-file-size=10MB）
    · 校验 MIME：图片仅允许 image/jpeg, image/png, image/gif, image/webp

  方式B：Base64 直接入库（MVP 快，无配置）
    · 沿用现有 qualification 字段的方式，直接把字符串写入
       teacher_professional.personal_photo_base64 / teacher_certificate.cert_base64
    · 缺点：数据库膨胀，列表页拖慢响应；建议中期切到方式A。

### 9. 风险与注意事项
================================================================================
  · 删除教师职业信息：是否同步 user.status？需求未明确。
    策略：默认只删 professional/证书/时间段，不改 user；加参数 forceDisableUser 可选冻结账号。

    新增排期时，应校验该时段落在 teacher_available_time 内。MVP 阶段可先只做展示，---------1、自动从排期中筛选出可用时间 2、手动填写（如特殊日期覆盖）
    后续再在 CourseService 中加校验。
  · 导出 Excel/Word 时的大数据量：一次性全表导出若>1万行会内存爆。
    MVP：限制单次导出最大 5000 条；超过则分 sheet 或分文件。

    学生/教师自己只能查看自己的职业信息（只读）。
    → 建议在 Service 层做角色分支：
        admin：可查全部 + 可改
        teacher：只能改/查 teacherId == currentUserId 的记录
  · 事务：add / update 主表 + 2 张子表必须包 @Transactional，任何一步失败整体回滚。

解决 fetchScheduleListPage 数据同步问题
根源：forEach + async/await 不会等待内部异步任务，返回 pageResult 时 getCourseById 还没完成，后续原地回填对象造成数据晚到；同时存在无并发限流、无缓存、对象副作用等问题。
核心改造思路：
将 forEach(async) → Array.map + await Promise.all()，等待全部行的异步处理完成再返回数据；
增加 courseId 查询缓存，避免相同课程重复请求；
增加并发控制，防止一页大量数据瞬间爆发出大量 getCourseById；
尽量避免直接修改接口返回原始对象（可选，消除引用副作用）；
单条记录异常隔离，一条查询失败不打断整个列表。
对比参考：同文件 datamaintain_fetchAppointmentListPage 已经使用了 map + Promise.all + 缓存Map 的正确模式，可以对齐这套模式。
